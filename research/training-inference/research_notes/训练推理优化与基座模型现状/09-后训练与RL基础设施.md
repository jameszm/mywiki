## KQ1 后训练流水线的系统形态：各阶段需求、rollout 与训练的耦合（共置/分离、同步/异步）、权重同步、长尾调度、KV cache

### Takeaway
2025 年中以来，生产级 RL 后训练的主流形态是"单控制器 + 多控制器"的 HybridFlow 式数据流（verl/Seed/K2 均用），rollout 引擎（vLLM/SGLang）与训练引擎（Megatron/FSDP）在同一组 GPU 上分时共置；2025 下半年到 2026 年，几乎所有框架都补上了"一步异步（one-step-off）→ 全异步（分离 Rollouter/Trainer + 流式样本 + 部分 rollout + staleness 控制）"的谱系，并把权重同步做成独立的 checkpoint-engine（NCCL 广播 / NIXL-RDMA P2P / 稀疏 delta / 磁盘）。公开数字：一步异步 +23%–40%，全异步 2.3–2.8×，1T 参数权重全量更新 <30 s，delta 同步在 235B MoE 上比 NCCL 全量广播快约 21×；代价是 off-policy 程度上升，需要 IS/RS 修正与 staleness 阈值。

### Cited Findings

**(a) 各后训练阶段的系统需求**
- DeepSeek-R1 的流程为：冷启动 SFT → 面向推理的 RL（GRPO，规则奖励，不用神经奖励模型）→ 拒绝采样 + SFT（约 800k 样本，对 DeepSeek-V3-Base 训练两个 epoch）→ 面向全场景的二阶段 RL（推理数据用规则奖励，通用数据用奖励模型；无害性评估覆盖整条回答含思考过程）。GRPO 的动机明确是"省掉与策略同尺寸的 critic"。— [DeepSeek-R1 report PDF (repo)](https://github.com/deepseek-ai/DeepSeek-R1/blob/main/DeepSeek_R1.pdf)（2025-01；技术报告全文；A，背景年份）
- DeepSeek-V3.2-Exp 把多阶段 RL 合并成单阶段 "Mixed RL Training"（仍用 GRPO）：先按数学/竞赛编程/逻辑/agentic coding/agentic search 五个领域各训专家模型，用专家生成 thinking/非 thinking 数据蒸馏到最终 checkpoint，再做一次 RL 弥合差距，以规避多阶段的灾难性遗忘。— [DeepSeek_V3_2.pdf (repo)](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/DeepSeek_V3_2.pdf)（2025-09-29；技术报告全文；A）
- Qwen3 旗舰模型四阶段后训练：Long-CoT 冷启动 SFT → Reasoning RL（仅 3,995 个 query–verifier 对，GRPO，"大 batch、每 query 多 rollout、并引入 off-policy 训练以提高样本效率"；Qwen3-235B-A22B 的 AIME'24 在 170 个 RL step 内从 70.1 升到 85.1）→ Thinking Mode Fusion（继续 SFT）→ General RL（覆盖 20+ 任务的奖励系统）。小模型改用 Strong-to-Weak Distillation（off-policy + on-policy logits 蒸馏），"只需四阶段流程 1/10 的 GPU 小时"。— [Qwen3_Technical_Report.pdf (repo)](https://github.com/QwenLM/Qwen3/blob/main/Qwen3_Technical_Report.pdf)（2025-05；技术报告全文；A）
- Kimi K2 的 RL 目标沿用 K1.5 的无 critic 策略梯度（组内均值基线 + 平方正则），优化器 Muon；并引入 Budget Control（按任务类型的每样本 token 上限，超限截断并罚分）、PTX 辅助损失、温度衰减。— [Kimi K2 tech_report.pdf (repo)](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)（2025-07；技术报告全文；A）
- On-policy 蒸馏（OPD）已成为与 RLVR 并列的标准后训练阶段：verl 的 OPD 文档区分 GKD-OPD（全分布 KL 反传）与 PG-OPD（把反向 KL 的无偏估计当作 reward 走策略梯度）；verl 的异步 OPD recipe 用 ZeroMQ 教师服务返回 top-k log-prob，并用 one-step-off / two-step-off 调度器把 rollout、教师打分、actor 更新三阶段重叠（"严格同步的三阶段流水线存在明显 bubble"）。— [verl docs/algo/opd.md](https://github.com/verl-project/verl/blob/main/docs/algo/opd.md)（2026-05-26；官方文档；A）；[verl docs/advance/async-on-policy-distill.md](https://github.com/verl-project/verl/blob/main/docs/advance/async-on-policy-distill.md)（2025-11-08；官方文档；A）
- slime 的 OPD 把采样 token 的反向 KL 项直接减到 advantage 上（可叠加 GRPO/PPO/REINFORCE++），教师有两种部署：外部 SGLang 服务（rollout 阶段打分，适合异构/超大教师）或 Megatron 内加载（训练前向时打分）。— [slime docs/en/advanced/on-policy-distillation.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/on-policy-distillation.md)（仓库 2026-10-09；官方文档；A）
- prime-rl 只托管一个可训练策略，教师/参考模型一律是外部 OpenAI 兼容端点（`opd` 的 teacher 必须是冻结端点）；损失统一为 rl / ce / ref_kl 三分量，trainer 对算法无感。— [prime-rl docs/algorithms.md](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/algorithms.md)（仓库 2026-10-08；官方文档；A）
- Kuaishou OpenOneRec 的后训练三阶段为：多任务 SFT → on-policy 蒸馏（恢复通用推理能力）→ RL（增强推荐能力）；其蒸馏代码是 verl 在 commit `703a078` 上的 fork，专门处理"教师（Qwen3）与学生（含扩展 itemic token）词表不一致"：rollout 时生成 `distill_special_token_mask`，计算 log-prob 时替换/遮蔽扩展词表 token，蒸馏信号为 token 级反向 KL，advantage 裁剪区间 [-30, 5]。— [OpenOneRec README](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/README.md) 与 [verl_distillation/README.md](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_distillation/README.md)（2026-01-01；官方仓库；A）

**(b) 共置（colocate）vs 分离（disaggregated）、同步 vs 异步**
- verl 实现 HybridFlow：控制流在单进程 controller，计算流在多进程 WorkerGroup（SPMD）；PPO 用三个 WorkerGroup（ActorRolloutRef / Critic / Reward），actor 与 rollout 共置的理由是"通过 NCCL 快速传权重"，actor 与 ref 共置是为了 LoRA-PPO。— [verl docs/hybrid_flow.rst](https://github.com/verl-project/verl/blob/main/docs/hybrid_flow.rst)（2025-06-02；官方文档；A）
- verl v0.7（2026-01-03）把架构拆为 verl-core（Model Engine / Rollout Engine / Checkpoint Engine / TransferQueue）与 verl-trainer（on-policy 同步、one-step-off、fully async 三条流水线），并**删除 SPMD rollout 模式，默认改为 rollout server 模式**（per-sample 请求 + 动态 batching，不侵入 vLLM/SGLang/TensorRT-LLM）。文档给出的适用边界："one-step-off 适合要 20%–40% 提升又要接近 on-policy 的场景；fully async 对 128+ GPU 或长 CoT 场景是必需的"。Model Engine 后端：FSDP（dense 中等/MoE 低性能，Day-0 支持）、MCore（DP+TP+PP+EP+CP，高性能，新模型需数周）、VeOmni（FSDP+SP+EP，约 1 周）。— [verl docs/blog/v0.7.md](https://github.com/verl-project/verl/blob/main/docs/blog/v0.7.md)（2026-01-03；官方博客；A）
- verl one-step-off（美团搜索贡献）：rollout 用上一步参数、与训练并行，资源显式切分。实验（Qwen2.5-Math-7B，DAPO，2×16 H20，4 卡生成 + 12 卡训练）：colocate 同步 19h18m → one-step-overlap 15h34m（+23%，FSDP2）；18h21m → 13h06m（+40%，Megatron）；NCCL 权重同步延迟"多数情况下 <300 ms"。文档还引用 DAPO-32B 的 wandb 数据：rollout 阶段约占总时间 70%，且"增加资源并不能缩短 rollout 时长"。— [verl docs/advance/one_step_off.md](https://github.com/verl-project/verl/blob/main/docs/advance/one_step_off.md)（2025-07-17；官方文档；A）
- verl fully async（美团搜索贡献）：Rollouter / MessageQueue / Trainer / ParameterSynchronizer 四组件，样本逐条流式传输，`staleness_threshold`（0=同步，>0 允许陈旧样本，建议 <1，=1 近似 one-step-off）、`trigger_parameter_sync_step`、`partial_rollout`（参数同步时 sleep/resume 保存进行中样本）；默认用 rollout 的 log-prob 作 old_log_prob。报告在 **Qwen2.5-7B、128 GPU 上 2.35×–2.67× 提升**；收益来源是"共置下再多资源也填不满长尾造成的空闲，分离后 rollout 与 train 各自变慢但相互重叠"。— [verl docs/advance/fully_async.md](https://github.com/verl-project/verl/blob/main/docs/advance/fully_async.md)（2026-05-25；官方文档；A）
- verl V1 trainer（2026-09-21）在 `main_ppo` 下提供 `colocate_async` 与 `separate_async` 两种异步模式，均依赖 TransferQueue、异步 replay buffer 和 partial-rollout 客户端；被中断的请求保留已生成 token 与 log-prob、经负载均衡重试、"为保留前缀重建 KV cache 后继续解码"，因此一条轨迹可跨多个模型版本。staleness 以模型版本计：`max_off_policy_threshold` 默认 8，策略 `drop`（丢弃整组）或 `wait`。`separate_async` 还支持"step switching"：训练节点上的 hybrid 副本在等待样本的空窗期加入 rollout 负载均衡器，阈值可自适应。— [verl docs/advance/v1_async_trainer.md](https://github.com/verl-project/verl/blob/main/docs/advance/v1_async_trainer.md)（2026-09-21；官方文档；A）
- verl 动态资源调度（Hybrid + Standalone 两类推理副本，Trainer 空闲时激活 Hybrid 副本参与 rollout）：Qwen3.5-35B-A3B / DAPO-Math-17K 上端到端快约 15.3%，reward 曲线与基线一致。— [verl docs/advance/dynamic_schedule.md](https://github.com/verl-project/verl/blob/main/docs/advance/dynamic_schedule.md)（2026-07-10；官方文档；A）
- Kimi k1.5（2025-01）的 Hybrid Deployment：Megatron 与 vLLM 跑在同一 Pod 的两个 sidecar 容器里共享全部 GPU，训练结束后 Megatron 卸载显存，vLLM 以 dummy 权重启动并经 Mooncake（RDMA）接收 Megatron 转成 HF 格式的分片；由于 CUDA graph/NCCL buffer/驱动难以彻底释放显存，直接**终止并重启 vLLM**。"训练→推理切换 <1 分钟，反向约 10 秒"。— [Kimi_k1.5.pdf (repo)](https://github.com/MoonshotAI/Kimi-k1.5/blob/main/Kimi_k1.5.pdf)（2025-01；技术报告全文；A，背景）
- Kimi K2（1T 参数）沿用"同步 RL + hybrid colocated"架构：训练/推理引擎同驻一组 worker，一方工作时另一方释放或卸载显存；集中式 controller 每轮先调推理引擎生成、再通知训练引擎训练、再把参数送回推理引擎。— [Kimi K2 tech_report.pdf](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)（2025-07；A）
- 字节 Seed1.5-Thinking：训练框架基于 HybridFlow 抽象、跑在 Ray 集群上（dataloader 与 RL 算法在单进程 Ray Actor，训练与 rollout 在 Ray Worker Group，SPMD 执行）；采用 hybrid engine 所有模型共置；针对长 CoT 的 straggler 提出 **SRS（Streaming Rollout System）**："部署独立的流式计算单元把系统从 memory-bound 变为 compute-bound"，用完成比例 α 控制 on-policy 样本占比，其余 (1-α) 由版本化快照异步续写部分生成；rollout 阶段用 FP8 策略网络（后训练量化 + 误差补偿缩放）、TP+EP+SP 三级并行、kernel 自动调优。报告称流式 rollout"比同步框架迭代快 3×"（自述）。训练侧 TP/EP/CP + FSDP、KARP 序列长度均衡、层级重计算 + 激活/优化器卸载、AutoTuner、ByteCheckpoint。— [seed-thinking-v1.5.pdf (repo)](https://github.com/ByteDance-Seed/Seed-Thinking-v1.5/blob/main/seed-thinking-v1.5.pdf)（2025-04；技术报告全文；A）
- AReaL（蚂蚁 + 清华 IIIS，NeurIPS 2025）：全异步，rollout worker 持续生成、trainer 攒够一批就更新；用 staleness 控制 + Decoupled PPO（行为策略 π_behav 与近端策略 π_prox 解耦，对多版本片段做重要性采样）；**同等 GPU 数下最高 2.77× 加速**；实现基于 ReaLHF，SGLang v0.4.6 生成 + Megatron-Core v0.11.0 训练，SLURM 调度；64 节点 H800（NVLink + 3.2 Tbps RoCE），"固定 3/4 设备给推理、1/4 给训练（75-25 比 50-50 吞吐更高）"；最大 staleness η 代码任务 4、数学 8；规则奖励与 TCP 数据传输放到独立线程与生成流水线重叠。— [AReaL assets/paper.pdf (repo)](https://github.com/inclusionAI/AReaL/blob/main/assets/paper.pdf)（2025-05/NeurIPS 2025；论文全文；A）
- NeMo RL v0.7 性能表（DGX-H100，BF16，Megatron 后端，GRPO）：DeepSeek-V3 512 GPU 同步 on-policy 每步 81.2 s / 10.2 tok/s/GPU，1-step off 46.6 s / 18 tok/s/GPU；Qwen3-235B-A22B 256 GPU 同步 285 s（40.8 tok/s/GPU）vs 1-step off 204 s（58.3）；Qwen3-30B-A3B 32 GPU 171 s vs 141 s；Nemotron-3-Super-120B-A12B 256 GPU 108 s vs 71.9 s；FP8 端到端 DeepSeek-V3 1-step off 61.9 s；GB200-NVL72 上 DeepSeek-V3 256 GPU 1-step off 35 s / 47.9 tok/s/GPU。— [NeMo RL docs/about/performance-summary.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/about/performance-summary.md)（仓库 2026-10-09；官方文档；A）

- OpenRLHF 的三档执行模式：Hybrid Engine（`--train.colocate_all`，严格 on-policy，"最稳定"）→ Async（`--train.async_enable`，`async_queue_size` 越大越 off-policy）→ Async + Partial Rollout（vLLM pause/resume 代替加锁，"进行中的样本可能混有新旧权重的 token"，建议配 token 级 IS 修正）；README 明言"异步可能影响稳定性，仅在吞吐关键且收敛已验证时使用"。— [OpenRLHF README](https://github.com/OpenRLHF/OpenRLHF/blob/main/README.md)（2026-09；官方仓库；A）

- prime-rl：Inference（vLLM 服务/机群）、Orchestrator（CPU 进程，驱动多轮 rollout、算 advantage、打包 batch、转发权重）、Trainer（FSDP2）三进程；自称"全异步，1T+ MoE、1000+ GPU"，trainer↔orchestrator 默认 ZMQ，权重广播默认 NCCL（LoRA 或无推理服务时回退文件系统）。— [prime-rl docs/overview.md](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/overview.md)（仓库 2026-10-08；官方文档；A）

- PipelineRL（ServiceNow，NeurIPS 2025）提出 in-flight weight updates，"32–128 H100 上比同步约 2× 更快学习"（未核实）。— [LLMSys-PaperList neurips25-mlsys/rl.md](https://github.com/AmberLJC/LLMSys-PaperList/blob/main/neurips25-mlsys/rl.md)（B）

**(c) 权重同步：训练端 → 推理引擎**
- Kimi K2：rollout 时训练引擎参数卸载到 DRAM；推理引擎需以不同分片拿到新参数，"用网络文件系统 reshard 并广播不可行，所需聚合带宽达数 PB/s"，故在训练节点共置分布式 checkpoint engine：每个 worker 取本地参数副本 → 全集群广播完整参数 → 推理引擎只取自己需要的分片；对 1T 模型逐参数流水线更新以压低内存；选择"全量广播而非按需传输"是为了解耦训练/推理引擎，且实测因同步开销更小、带宽利用更高反而更快；**K2 全量参数更新 <30 s**。启动时由 checkpoint engine 集体读 checkpoint 一次再更新推理副本，使推理副本可独立重启。— [Kimi K2 tech_report.pdf](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)（2025-07；A）
- MoonshotAI/checkpoint-engine 开源实现：Broadcast（H2D → 广播到 CUDA IPC buffer → 推理引擎 reload，三阶段流水线重叠）与 P2P（mooncake-transfer-engine RDMA，用于动态加入的实例）；README 基准（vLLM v0.10.2rc1）：Kimi-K2-Instruct FP8 256×H20 TP16 广播更新 16.04 s（8 GiB bucket）、16×H20 14.36 s；DeepSeek-V3.1 FP8 256×H20 11.33 s；Qwen3-235B BF16 8×H800 6.22 s；标题数字"1T 模型跨数千 GPU 约 20 s"。— [checkpoint-engine README](https://github.com/MoonshotAI/checkpoint-engine/blob/main/README.md)（最后提交 2026-09-15；官方仓库；A）
- verl v0.7 引入 Checkpoint Engine 抽象（`send_weights`/`receive_weights` 流式 API），传输后端 NCCL（广播集合通信）与 NIXL（P2P）；文档把分离架构的新难点定义为"高效跨节点参数同步"。— [verl docs/blog/v0.7.md](https://github.com/verl-project/verl/blob/main/docs/blog/v0.7.md)（2026-01-03；A）；`separate_async` 要求非 naive 后端（nccl/nixl/mooncake）。— [v1_async_trainer.md](https://github.com/verl-project/verl/blob/main/docs/advance/v1_async_trainer.md)（A）
- verl Delta Weight Sync（2026-08-23）："RL 更新高度稀疏，典型学习率下 >99% 的 BF16 权重字节逐步不变"，`delta_sharded` 后端每个 rank 只对自己的 FSDP 分片做 bit-exact diff、稀疏 gather 到 rank 0 再分桶广播，接收端校验和、无损。实测（H100，GSM8K GRPO，V1 separate_async，SGLang rollout，每步稳态同步时间）：Qwen2.5-7B 3.9–4.9 s vs NCCL 全量 5.5–6.0 s；Qwen2.5-32B 11.2–11.9 vs 17.7–18.1 s（关 offload 6.2 vs 14.2 s）；Qwen2.5-72B 12–13 vs 28.5–29.1 s；Qwen3-30B-A3B（VeOmni EP8）7.1 vs 32.2 s（4.5×）；**Qwen3-235B-A22B（VeOmni EP8×FSDP8，8+2 节点，gen TP16）11.4–14.9 vs 246–266 s（≈21×）**；dense 模型每步变化字节 ~1–3%，235B MoE 早期仅 0.02–0.05%。— [verl docs/advance/delta_weight_sync.md](https://github.com/verl-project/verl/blob/main/docs/advance/delta_weight_sync.md)（2026-08-23；官方文档；A）
- NeMo RL 的 refit 传输矩阵：共置用 CUDA IPC（vLLM 走 ZMQ+IPC 句柄，SGLang 走 Ray CUDA IPC）；非共置默认 NCCL 全量广播；`nccl_reshard`（分片到分片 M-to-N，"对 >100s B 模型性能最好"，实验性；MoE FFN 占模型权重 97–98%；MXFP8 训练↔MXFP8 生成的线上格式仍是 BF16，约 2× 理论 wire 大小）；`vllm_zmq_sparse` / `vllm_s3_sparse`（稀疏 delta，XOR 编码 + zstd，跨集群经 ZeroMQ 中继树或 S3）；`nixl`（UCX/RDMA checkpoint engine，默认每缓冲区占 5% 显存、双缓冲）；vLLM `reload_weights` API 路径在 Llama-8B/Qwen3-32B 更快但 Qwen3-30B-A3B 慢约 44%，MXFP8 慢约 2×。— [NeMo RL docs/guides/refit.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/refit.md)、[design-docs/nccl-reshard-refit.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/design-docs/nccl-reshard-refit.md)、[design-docs/sparse-delta-refit.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/design-docs/sparse-delta-refit.md)、[guides/checkpoint-engine-refit.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/checkpoint-engine-refit.md)（仓库 2026-10-09；官方文档；A）
- slime 的 Delta Weight Sync 仅支持磁盘传输（trainer 发布 HF 格式 delta 目录，引擎 `/pull_weights` 在每台主机本地应用后经常规 `update_weights_from_disk` 重载；XOR 或 overwrite 编码，zstd-1 压缩），面向"跨集群/跨数据中心的大模型训推分离"；External Rollout Engines 允许推理集群由外部系统拥有，磁盘传输下"训练 GPU 与 rollout GPU 可以是不同型号甚至不同厂商"；NCCL 全量模式仍是默认。— [slime docs/en/advanced/delta-weight-sync.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/delta-weight-sync.md)、[external-rollout-engines.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/external-rollout-engines.md)（仓库 2026-10-09；A）
- SkyRL 四种权重同步后端：`nccl`（非共置广播）、`ipc`（共置 CUDA IPC）、`delta`（XOR delta + 无损压缩，经 S3/GCS/NFS，"100B+ 模型跨云存储更新"，推理侧先 fetch+process 再暂停生成 load）、`sharded_rdt`（推理 worker 经 NIXL/RDMA 主动拉取所需分片）；建立在 vLLM 的 trainer-send 抽象之上，"分块由 vLLM 负责"。— [SkyRL .agents/docs/weight_sync.md](https://github.com/NovaSky-AI/SkyRL/blob/main/.agents/docs/weight_sync.md)、[docs examples/delta_weight_sync.mdx](https://github.com/NovaSky-AI/SkyRL/blob/main/docs/content/docs/examples/delta_weight_sync.mdx)（仓库 2026-10-08；A）
- TRL server 模式：每个 optimizer step 后训练器经 NCCL 把权重流式推入 vLLM server（`/start_weight_update` → `/update_weights` → `/finish_weight_update`），vLLM 需 `--weight-transfer-config '{"backend": "nccl"}'`（共享 GPU 时用 `ipc`）。— [TRL docs/source/vllm_integration.md](https://github.com/huggingface/trl/blob/main/docs/source/vllm_integration.md)（A）

**(d) 长尾 rollout 的调度与截断**
- Kimi k1.5 的 Partial Rollouts：固定输出 token 预算，超预算的未完成部分存入 replay buffer 在下一轮继续（只有当前段需要 on-policy 计算），并附带重复检测提前终止 + 罚分。— [Kimi_k1.5.pdf](https://github.com/MoonshotAI/Kimi-k1.5/blob/main/Kimi_k1.5.pdf)（2025-01；A）；K2 在 agentic 长轨迹上沿用 partial rollout（暂停、下一轮续跑）。— [Kimi K2 report](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)（A）
- MiniMax-M1 的早期截断：复杂 prompt 会诱发病态重复的超长回答，规则是"连续 3,000 个 token 概率均 >0.99 即停止生成"，"消除了这些长尾病例，提高生成吞吐"。— [MiniMax_M1_tech_report.pdf (repo)](https://github.com/MiniMax-AI/MiniMax-M1/blob/main/MiniMax_M1_tech_report.pdf)（2025-06；A）
- DAPO 的 Overlong Reward Shaping（超长回答软惩罚以降低奖励噪声）与 Dynamic Sampling；OpenRLHF 实现了 DAPO 式 overlong penalty（`--reward.overlong_buffer_len`）与 ProRL 式截断惩罚（`finish_reason='length'` 的样本按系数缩放或设固定负奖励）。— [dapo_paper.pdf (repo)](https://github.com/BytedTsinghua-SIA/DAPO/blob/main/dapo_paper.pdf)（2025-03-17；A）；[OpenRLHF README](https://github.com/OpenRLHF/OpenRLHF/blob/main/README.md)（A）
- slime 的核心判断："我们想 scale 推理算力，却无法 scale 推理延迟"——单条样本的解码速度决定 RL 训练速度上限；用 FP8 量化 + DeepEP 低延迟模式 + 投机采样，把 GLM-4.5 355B-A32B 的单样本解码从 <10 tok/s 提到 60–70 tok/s；并监控 `perf/longest_sample_tokens_per_sec`；KV cache 溢出会让 64k 回答等效解码 96k token，因此应按"不溢出 KV 的最小 GPU 数"切分并并行多组实验。— [slime docs/en/blogs/release_v0.1.0.md](https://github.com/THUDM/slime/blob/main/docs/en/blogs/release_v0.1.0.md)（2025-08；官方博客；A）
- 投机解码进入 RL：verl 支持 MTP 加速 rollout（vLLM `method=mtp`，SGLang EAGLE）并可在训练中更新 MTP 层（美团贡献，Megatron-Bridge 0.6.2/Megatron-Core 0.19.2）；verl-SpeCo（2026-06 预发布）在 RL 训练与推理间共训草稿模型；NeMo RL 支持 EAGLE3 草稿模型离线使用或在线随策略训练并一并 refit；slime 支持在线训练 MTP 层（外部草稿模型训练 WIP），理由是"RL 推进时草稿/目标分布漂移，接受率下降甚至负收益"。— [verl docs/advance/mtp.md](https://github.com/verl-project/verl/blob/main/docs/advance/mtp.md)（2026-08-11；A）；[verl README News](https://github.com/verl-project/verl/blob/main/README.md)（A）；[NeMo RL guides/eagle3-speculative-decoding.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/eagle3-speculative-decoding.md)（A）；[slime speculative-decoding.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/speculative-decoding.md)（A）
- 系统论文层面的长尾专项（仅列名，数字未读）：APRIL（Active Partial Rollouts）、RhymeRL（History Rhymes，verl 已有 recipe）、Seer（OSDI'26，同步 RL 的 online context learning）、ReSpec（MLSys'26，RL 中的投机解码）、"Beat the Long Tail"（MLSys'26，分布感知投机解码）、"Taming the Long-Tail"（ASPLOS'26，自适应 drafter）、RollPacker（ROLL 团队，同步 RL 长尾打包）。— [LLMSys-PaperList README](https://github.com/AmberLJC/LLMSys-PaperList/blob/main/README.md)（B）；[ROLL README](https://github.com/alibaba/ROLL/blob/main/README.md)（A，仅标题）

**(e) KV cache 在 rollout 中的复用**
- verl 支持把 vLLM rollout 的前缀 KV 块卸载到共享 Mooncake store，使系统提示、agentic 工具历史、`rollout.n` 多采样的共享前缀在请求与副本间去重，并降低长尾负载迁移时的重 prefill 成本；**每次权重更新都强制清空本地与 Mooncake KV**（需 vLLM ≥0.22，旧版会残留旧策略 KV）。— [verl docs/perf/rollout_kv_offload.md](https://github.com/verl-project/verl/blob/main/docs/perf/rollout_kv_offload.md)（2026-05-27；A）
- AReaL v0.2 从 vLLM 切换到 SGLang v0.4.0，理由是 radix attention 对"多回答采样"场景的吞吐提升；v0.2 还引入动态序列打包与 GPU-Direct RDMA 数据传输，"1.5× 吞吐提升"。— [AReaL docs/en/version_history.md](https://github.com/inclusionAI/AReaL/blob/main/docs/en/version_history.md)（A）
- slime 为多轮 agent 提供 PD 分离（prefill/decode 各自 TP、显存设置）与 router session affinity（adapter 以 `X-SMG-Routing-Key` 把同一会话路由到同一 worker 以复用前缀缓存）。— [slime pd-disaggregation.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/pd-disaggregation.md)、[get_started/agent.md](https://github.com/THUDM/slime/blob/main/docs/en/get_started/agent.md)（A）
- prime-rl：策略采样的 rollout 使用"按版本加盐的前缀缓存"，冻结模型的前缀缓存稳定不过期；支持 KV cache offload、P/D 分离、router replay。— [prime-rl docs/algorithms.md](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/algorithms.md)、[docs/inference.md](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/inference.md)（A）
- OpenRLHF：`n_samples_per_prompt>1` 时启用 vLLM prefix caching；OpenAI 兼容 agent server 用 delta-tokenization 跨轮复用前缀 token。— [OpenRLHF README](https://github.com/OpenRLHF/OpenRLHF/blob/main/README.md)（A）

**(f) 训推不一致（train–inference mismatch）作为系统问题**
- MiniMax-M1：训练模式与推理模式对已采样 token 的概率有显著差异，根因是训推 kernel 精度不匹配，"在小型 dense softmax 模型上不出现"；逐层分析定位到 LM head 的高幅值激活，把 LM 输出头改为 FP32 后训推概率相关性从约 0.9x 升到 0.99。— [MiniMax_M1_tech_report.pdf](https://github.com/MiniMax-AI/MiniMax-M1/blob/main/MiniMax_M1_tech_report.pdf)（2025-06；A）
- verl Rollout Correction（2026-09-23）：把精度/后端差异、异步陈旧、replay buffer 等统一视为 off-policy 问题，用 IS 权重 + 拒绝采样修正；指出常见实现错误是"把训练端 π_old 当成行为策略而忽略真实 π_rollout"，提供 decoupled / bypass / bypass+PG 三种数学正确模式。— [verl docs/algo/rollout_corr.md](https://github.com/verl-project/verl/blob/main/docs/algo/rollout_corr.md)（2026-09-23；A）；FP8 rollout 实验（Qwen3-8B-Base，DAPO，8×H100，20K 回答长度）：开 token 级 TIS 后 FP8 与 BF16 精度对齐、不开则明显掉点；FP8 rollout 带来约 12% rollout 加速（CUDA 12.6 + DeepGemm）。— [verl docs/low_precision/fp8.md](https://github.com/verl-project/verl/blob/main/docs/low_precision/fp8.md)（2026-09-29；A）
- MoE 的 Router Replay（R3）：NeMo RL 记录 vLLM rollout 的专家路由并在 Megatron 前向中回放，消除"两个合法 router 实现对同一 token 选不同专家"造成的与策略更新无关的 logprob 不匹配（指标 `train/token_mult_prob_error`、`train/js_divergence_error`）；verl 在 PyTorch Conference Europe 2026 展示 Megatron 后端 LoRA + router replay；slime 的 straw 存储也把 R3 路由作为类型化张量存储。— [NeMo RL guides/router-replay.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/router-replay.md)（A）；[verl README](https://github.com/verl-project/verl/blob/main/README.md)（A）；[slime straw.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/straw.md)（A）
- 走向"零不匹配"：verl 发布 vexact（2026-05，batch-invariant kernel 的 HF rollout，与 FSDP 共享模型定义）；slime 对 GLM-5 结构（MLA + DSA 稀疏注意力）实现训练 log-prob 与 rollout log-prob 对齐（确定性 SGLang、batch-invariant DeepGEMM/DeepEP、fp32 MoE router；"LM head 两端都保持 bf16，关键是精度一致而非 fp32"）。— [verl README](https://github.com/verl-project/verl/blob/main/README.md)（A）；[slime reproducibility.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/reproducibility.md)（A）

### Inferences
- "共置 + 同步"仍是大厂旗舰 RL（K2、Seed1.5-Thinking、DeepSeek）的默认，其正当性来自两点：权重同步可用节点内 NCCL/IPC（最便宜），以及 on-policy 最稳。分离/异步的收益随长尾严重程度和集群规模增长（verl 给的阈值是 128+ GPU 或长 CoT），且所有框架都把"异步程度"做成了连续旋钮（staleness 阈值 / 版本数 / queue size），而非非此即彼。
- 权重同步在 2026 年出现清晰的三层：节点内 NCCL/IPC（<1 s 级，小模型）、全量广播 checkpoint engine（1T 级 15–30 s，K2/Moonshot）、稀疏 delta（235B MoE 从 ~250 s 降到 ~12 s，verl；NeMo RL、slime、SkyRL 均有同类）。delta 方案的前提"每步只有 1–3% 字节变化"对低学习率 RL 成立，对高学习率 SFT/预训练不成立。
- 训推不一致从算法问题变成系统问题：FP8/低精度 rollout、MoE 路由、异步陈旧都需要 IS 修正或 R3/确定性 kernel；没有 IS 修正的异步模式在 NeMo RL/TRL 里已被设为"必须开启"。

### Gaps
- 没有任何一手来源给出"同一模型、同一集群上 colocate vs disaggregated 的端到端成本（GPU 小时/美元）"对比；verl/AReaL/NeMo RL 的数字各自在不同模型/任务/硬件上，不可横向比较。
- HybridFlow（EuroSys'25）论文本身的吞吐数字（相对基线的倍数）未能从本地仓库文档中核实（README 只写"SOTA throughput"）。
- StreamRL（arXiv 2504.15930）与 AsyncFlow（arXiv 2507.01663）的全文未读，只有 verl/AReaL 文档中的引用与搜索摘要（StreamRL 声称 2.66× 吞吐、1.33× 性价比，未核实；作者单位据搜索摘要为北大/StepFun 而非字节，未核实）。

## KQ3 奖励模型与验证器服务：规模、延迟、沙箱、LLM-as-judge 成本、反奖励黑客

### Takeaway
验证器/奖励已经服务化：verl 把 reward 做成分布式 Reward Loop（规则/判别式 RM/生成式 RM 混合，可与 rollout 流式重叠，可独占资源池）；代码沙箱（Sandbox Fusion、Kimi K8s 沙箱、NeMo code env、rllm 多沙箱）以高并发 CPU 服务形态存在；LLM-as-judge 由各厂自训验证器（Seed-Verifier/Seed-Thinking-Verifier、MiniMax GenRM、Kimi 自评 rubric）承担，并一律配套在线监控防 reward hacking（长度偏置、过长惩罚、预算控制）。DeepSeek-R1 的公开结论是神经奖励模型在大规模 RL 中会被 hack，所以可验证任务一律用规则奖励。

### Cited Findings
- verl Reward Loop（2026-02-10）：`RewardLoopManager` 在单控制器中启动跨节点多个 `RewardWorker`（`config.reward.num_workers`），batch 切块并行；若奖励是规则型或 RM 拥有独立资源池，则把 reward worker 句柄交给 AgentLoopManager，"每条样本一 rollout 完就算奖励"（流式）；支持规则奖励、判别式 RM（如 Skywork-Reward-Llama-3.1-8B）、生成式 RM（如 FAPO-GenRM-4B）及混合；Reward Manager 有 naive / dapo（过长惩罚）/ limit（限制并发，适合外部 API 限流）/ remote（独立进程，适合 Math-Verify 等 CPU 密集）；建议外部模型 API 或沙箱执行用 async 函数。v0.7 把 RM 重构为 server 模式，支持共置或独立部署。— [verl docs/advance/reward_loop.rst](https://github.com/verl-project/verl/blob/main/docs/advance/reward_loop.rst)（2026-02-10；A）；[v0.7 blog](https://github.com/verl-project/verl/blob/main/docs/blog/v0.7.md)（A）
- Sandbox Fusion：远程代码沙箱，reward 阶段时间减少 10–30%，`max_concurrent=256`，每实例内存上限默认 1024 MB；`reward_model.reward_manager=prime` 多子进程并发验证。— [verl sandbox_fusion_example.rst](https://github.com/verl-project/verl/blob/main/docs/examples/sandbox_fusion_example.rst)（A）

### Inferences
- 奖励计算的性能瓶颈已从 GPU 转向 CPU/外部服务并发（沙箱、判题、HTTP judge），所以主流框架把它从训练进程中剥离为异步/独立进程/独立资源池，并以"限流、并发上限、内存上限"作为一等配置。
- LLM-as-judge 的"规模化成本"在公开材料里没有被量化为 GPU 小时；可确认的工程做法是（1）自训小型专用验证器并以人工难例集校准（Seed 82.7%→99.3%），（2）judge 独立部署在推理引擎上按 HTTP 调用，（3）把 judge 调用与 rollout 流式重叠。

### Gaps
- 没有公开来源给出奖励模型推理在整个 RL 步中的时间/算力占比（除 Sandbox Fusion 的"10–30% reward 阶段时间"相对值）。
- Seed-Verifier 的模型规模与服务吞吐未披露；K2 自评 critic 的推理成本未披露。

## KQ4 Agentic RL（多轮工具调用、环境交互、长 horizon）对基础设施的新要求

### Takeaway
2026 年的 agentic RL 基础设施共识是：rollout 必须以 server/网关形式提供 OpenAI/Anthropic 兼容 API 并在网关处捕获 token id 与 logprob（token-in-token-out，禁止 decode→encode 回填）；环境（沙箱、浏览器、VM）作为独立可扩缩服务，用高并发与 partial rollout 吃掉等待环境的空闲；长轨迹靠 PD 分离、session affinity、前缀 KV 共享、CP/DCP 与激活卸载解决显存与延迟；AReaL 2.0 更进一步把训练/推理/agent/权重更新拆成微服务，以便从线上 agent 流量直接做在线 RL。

### Cited Findings
- Kimi K2 的 agentic rollout 三条措施：重环境（VM、代码解释器）"部署为可独立扩缩的专用服务"；用大量并发 rollout 摊薄昂贵交互的延迟；partial rollout 让长尾任务暂停并在下一轮继续；并设计了 OpenAI Gym 风格统一接口接入新环境。— [Kimi K2 report](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)（A）
- verl Agent Loop（0.4.2 引入，2025-07-17 文档）：用户只实现 `AgentLoopBase.run`，输出 prompt_ids / response_ids / response_mask（1 为模型生成 token、0 为工具返回 token）；AgentLoopManager 唤醒所有异步 LLM server（同步权重）→ 分块给 AgentLoopWorker（协程并发）→ `LLMServerClient` 首轮选请求数最少的 server、后续轮次粘到同一 server；结束后 server sleep（释放 KV、权重卸载到 CPU）。实证结论："对最终 messages 做 apply_chat_template 得到的 token 与逐轮 prompt_ids+response_ids 拼接不一致（工具解析改写内容、decode-encode 不一致），这会让轨迹偏离策略分布，单轮 PPO 都不收敛"。— [verl docs/advance/agent_loop.rst](https://github.com/verl-project/verl/blob/main/docs/advance/agent_loop.rst)（A）

## KQ5 推荐系统中的 RL 对齐基础设施：OneRec / GPR / GR4AD 等，rollout 来源，与 LLM RL 框架的差异，能否复用 verl

### Takeaway
工业推荐的 RL 对齐分两条线：(1) 快手 OneRec / GR4AD 与腾讯 GPR 的"生产线"——rollout 来自线上流量或内部模拟器、奖励来自奖励模型/eCPM/真实用户反馈、训练是实时流式在线学习、参数经消息队列/参数同步推到独立推理服务，与 LLM RL 框架几乎无代码复用；(2) 快手 OpenOneRec（Qwen3 底座）的"开源线"——直接 fork verl 做 GRPO 与 on-policy 蒸馏，用自定义两阶段 rollout（采样思考 → vLLM beam search 生成 SID）与基于真实交互 SID 的规则奖励，说明"LLM 化的生成式推荐"可以复用 verl，但工业级"SID 短序列 + 实时流量"的系统不能直接复用。

### Cited Findings
- **OneRec v1（快手，2025-06-16）** 奖励系统三部分：Preference Reward（P-Score，基于 SIM 架构的多塔个性化融合打分模型，各塔 BCE 辅助任务）、Format Reward（生成格式合法）、Industrial Reward；RL 用 ECPO（Early Clipped GRPO，对负样本做梯度上界早截断）。后训练"用实时数据流在线训练"，同时做 RSFT（按播放时长过滤掉后 50% 曝光 session）与 RL："随机选 1% 用户生成 RL 样本；为最大化算力利用，把 RL 样本生成与训练解耦到外部推理服务：训练时 1% 用户访问外部服务生成 512 个 item，向奖励模型请求每个 item 的奖励再回传训练任务；训练任务每 1000 步经消息队列（MQ）把更新后的参数发送给外部推理服务"。线上推理用 L20（4 GPU/2 CPU，PCIe），200 Gb RDMA/RoCE 机房，TensorRT 编译；训练 MFU 23.7%、推理 28.8%；承接约 25% QPS；带 RM 选择的版本 App Stay Time +0.54%/+1.24%。— [OneRec Technical Report, arXiv:2506.13695](https://arxiv.org/abs/2506.13695)（2025-06-16；全文本地镜像；A）
- **OneRec-V2（2025-08-28）** 指出 v1 的 RL 限制："因资源约束，on-policy rollout 只能在 1% 用户子集上进行；奖励模型易被 reward hacking"；改用真实用户反馈信号（Duration-Aware Reward Shaping：按时长分桶的播放时长奖励，正样本取前 25%，负样本取显式 dislike）与 GBPO（Gradient-Bounded Policy Optimization，去掉 ratio clip、改为对 π_old 的动态下界，保留全部样本梯度并以 BCE 梯度为界）。关键对照：只用传统流水线样本 vs 加入 OneRec 自身流量样本（"即引入 on-policy RL"，OneRec 已承接 25% 流量所以样本充足）——后者几乎所有指标改善（App Stay Time +0.165% → +0.227%，Video View 由负转正）；RM vs 用户反馈 vs 混合：RM 偏向互动指标（Comment +15.5%），用户反馈偏向时长（App Stay +0.299%）；Hybrid 中 RM 样本"来自模型自身 rollout 采样"，用户反馈样本"来自已曝光给用户的样本"。线上 1B 模型、context 3000、beam 512，L20 延迟 36 ms、MFU 62%，App Stay Time +0.467%/+0.741%。— [OneRec-V2, arXiv:2508.20900](https://arxiv.org/abs/2508.20900)（2025-08-28；全文本地镜像；A）
- **OpenOneRec（快手，2026-01-01）**：Qwen3-1.7B/8B 底座 + itemic token；后训练 SFT → on-policy 蒸馏 → RL；RL 代码为 verl 的 recipe（`verl_rl/recipe/onerec`）：`algorithm.adv_estimator=grpo`，FSDP2，vLLM，`rollout.name=two_stage`——阶段 1 采样 CoT 直到 `</think>`（`stage1_max_tokens` 默认 1024），阶段 2 在 prompt+CoT+`\n<|sid_begin|>` 前缀上调用 vLLM `BeamSearchParams` 做 beam search（`stage2_beam_size` 默认 32，`stage2_num_tokens` 默认 3，即 3 个 SID token），并返回全部 beam 作为训练样本；奖励函数 `compute_score` 从 ground-truth SID 计算 format_reward、partial_hit_reward（层级部分匹配）、hit_reward（交集比例）、pass_rate、pass@1（首个 SID 命中）；默认 lr 2e-6、KL loss 0.001（low_var_kl）、`clip_ratio_high=0.28`、`rollout.n=1`、`max_prompt_length=10240`、`max_logprobs=320`。README 路线图包含"统一 VeRL 集成：把 RL 与蒸馏代码路径合并为单一 VeRL 实现"。— [OpenOneRec verl_rl/README.md](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/README.md)、[recipe/onerec/run_grpo.sh](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/recipe/onerec/run_grpo.sh)、[onerec_vllm_rollout.py](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/recipe/onerec/onerec_vllm_rollout.py)、[onerec_recipe.py](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/recipe/onerec/onerec_recipe.py)（2026-01；官方仓库代码；A）
- **GPR（腾讯微信视频号广告，arXiv 2511.10138，2025-11-13）**：MTP 预训练 → Value-Aware Fine-Tuning（按动作类型层级 conversion>click>impression 与归一化 eCPM 加权）→ HEPO（Hierarchy Enhanced Policy Optimization）。RL "在高保真模拟环境中做反事实评估，把动作支持扩展到历史分布之外"；模拟环境记录每个解码层级的生成概率 π_old(z_ℓ) 作为行为策略概率用于 off-policy 修正；HTE（eCPM 估计塔）作为价值函数（stopgrad 于主干）；Hierarchical Process Rewards 解决只在曝光层给奖励的信用分配问题；ARR（Anticipatory Request Rehearsal）用用户当前状态合成未来请求（高活用户高峰期每 2 小时、低谷每 4 小时）。线上：HSD+NTP+DPO 首次全量 +2.11% GMV；DPO→HEPO 额外 +0.70% GMV；HEPO+ARR 再 +0.58% GMV；"模拟 final_value 的提升不直接等于线上收入"。— [GPR, arXiv:2511.10138](https://arxiv.org/abs/2511.10138)（2025-11-13；全文本地镜像；A）
- **GR4AD（快手广告，arXiv 2602.22732，v3 2026-04-02）**：VSL（Value-Aware Supervised Learning）+ RSPO（Ranking-Guided Softmax Preference Optimization，list-wise、价值奖励、面向持续在线更新）；系统图中 Online Learning 模块处理实时请求/交互流：(i) 优先正向互动样本生成 VSL 日志；(ii) "采样一部分高价值用户，用更大 beam 并引入受控随机探索，得到的价值估计（如 eCPM）作为 RL 日志流式输出支持 RSPO 更新"；Reward System 含 Reward Model 推理服务与实时索引；训练平台与推理服务间 Param Sync；dynamic beam serving 按层级与负载调 beam（如 [128,256,512] 渐增 beam：收入 -0.15%、QPS +45%）；线上广告收入最高 +4.2%，服务 4 亿+ 用户。— [GR4AD, arXiv:2602.22732](https://arxiv.org/abs/2602.22732)（2026-04；全文本地镜像；A）
- **MTGR（美团，arXiv 2505.18654）** 全文无 RL/GRPO 内容（基于 HSTU 的生成式排序框架，"verl"字样仅出现在无关上下文）。— [MTGR, arXiv:2505.18654](https://arxiv.org/abs/2505.18654)（2025-05；全文本地镜像；A）
- 以下仅来自搜索摘要（C，数字未核实）：AdaGRPO（"Adaptive Loss Balancing for Noise-Robust GRPO in Generative Recommendation"，arXiv 2606.08480，2026-06-07，作者 Kewei Xu 等，单位未确认）——以 SFT NLL 为锚，按"策略难度 + 奖励可区分性"的逐样本二值门控决定是否施加 GRPO 项，理由是生产排序模型作为 RM 训练于曝光偏置日志、奖励只在策略不确定且 RM 能区分真值时有用；报告 HR@10 11.01%→12.18%、幻觉 <0.22%，并称线上 A/B CTR 与停留时长显著提升。— [搜索摘要](https://arxiv.org/abs/2606.08480)（C）。ReCast（华为，arXiv 2604.22169）——在 RecIF-Bench 上相对 OpenOneRec-RL 基线 Pass@1 最高 +36.6%，仅用 4.1% rollout 预算达到基线，actor 更新时间降 16.6×。— [搜索摘要](https://arxiv.org/abs/2604.22169)（C）。OneMall（快手电商，arXiv 2601.21770）——RL 部分比较 DPO 与 GRPO，"GRPO 在全部 768 个采样候选上归一化奖励算 advantage"。— [搜索摘要](https://arxiv.org/abs/2601.21770)（C）。Meta 方面仅检到 GR2（Generative Reasoning Re-ranker）在 SID 上做 DAPO RLVR 重排、相对 OneRec-Think Recall@5 +2.4% 的会议介绍（Meta 研究员报告，是否为 Meta 论文/是否上线均未确认）。— [搜索摘要](https://ai.nus.edu.sg/online-ai-horizons-generative-reasoning-re-ranker/)（C）
- **与 LLM RL 框架的系统差异（基于以上一手材料的比较）**：OneRec/GR4AD/GPR 的"rollout"是 3 个 SID token 的 beam search（beam 512/32）而非数千 token 的采样，长尾/partial rollout 问题不存在；奖励来自 RM 推理服务、eCPM 塔或真实反馈日志，而非验证器/沙箱；训练是实时流式在线学习（OneRec：参数每 1000 步经 MQ 推到外部推理服务；GR4AD：Param Sync 到 Infer Server），而非离线 epoch 式 RL；on-policy 样本受线上实验流量比例限制（OneRec v1 仅 1% 用户，v2 因承接 25% 流量才有足够自生成样本；GPR 用模拟器规避线上风险）。— 综合自上述 A 级来源
- **复用 verl 的可行性证据**：OpenOneRec 以 verl 为 RL 与蒸馏框架（自定义 rollout 类 + 自定义 reward 函数 + 词表不匹配处理即可），verl 的 Reward Loop 支持外部 RM 服务与流式打分、checkpoint engine 支持向独立推理集群推权重、Agent Loop/server 模式支持按请求调用——这些抽象与 OneRec v1 的"外部推理服务 + 奖励服务 + MQ 参数下发"结构同构；但 verl 的 vLLM/SGLang rollout 针对 LLM 词表与 KV 解码优化，OneRec 工业版使用自研 TensorRT/UniPredict 推理栈与 L20 PCIe 机器，GR4AD 需要动态 beam 与实时索引，这些不在 verl 覆盖范围内。— 综合自 [verl 文档](https://github.com/verl-project/verl/tree/main/docs) 与 [OneRec 报告](https://arxiv.org/abs/2506.13695)（A，推断）

### Inferences
- 推荐 RL 的瓶颈不是"生成长尾"而是"on-policy 样本的流量来源与奖励可信度"：OneRec v1→v2 的核心系统变化是把 rollout 从 1% 用户的外部推理采样扩展到 25% 线上流量的真实反馈，再把奖励从 RM 改为真实时长信号；GPR 则用模拟器 + 行为策略概率记录做 off-policy 修正。LLM RL 框架中最有迁移价值的部件是：分离式 rollout 服务 + checkpoint engine（对应 OneRec 的 MQ 参数下发）、Reward Loop 的外部 RM/流式打分、IS/RS 修正（对应模拟器行为策略修正）、以及 GRPO 变体（ECPO/GBPO/RSPO/HEPO 本质是 GRPO/PPO 的裁剪与基线改造）。
- 对 TikTok 这类有 LLM 化生成式推荐（Qwen/OpenOneRec 路线）的团队，verl 可直接复用（OpenOneRec 已证明）；对 SID 短序列、实时流式的主推荐链路，更现实的是借鉴架构而非复用代码。

### Gaps
- OpenOneRec 技术报告（arXiv 2512.24762）PDF 不在仓库且无法下载，其 RL/蒸馏阶段的 GPU 数、吞吐、奖励设计说明未读，只能从代码推断。
- "美团 per-objective GRPO"未找到任何一手或二手来源（两次检索均无结果），MTGR 全文无 RL；可能指尚未公开或命名不同的工作。
- "Meta 在推荐中应用 DAPO"仅有 C 级会议介绍（GR2），无论文/博客可核实。
- OneRec/GR4AD/GPR 均未披露 RL 训练集群规模、步时、RM 服务 QPS 与延迟。

## KQ6 评估与实验：离线评估流水线、回归测试、安全评估的系统化

### Takeaway
框架层把"可复现 + 可回归"做成了一等功能：verl 的 full determinism（两次运行 reward 曲线逐位一致，但仅 V0 trainer）、SkipManager（缓存/回放 rollout 以快速迭代）、rollout trace 与 RL-Insight；slime 的确定性模式（SGLang 确定性推理 + Megatron 确定性模式）与 CPU/GPU CI 严格检查 kl 等指标；NeMo RL、prime-rl 提供独立的评估入口（DCP→HF 转换后用 vLLM 评测，或复用 orchestrator 的 eval 管道）。模型厂商层面的安全评估系统化只在 Kimi K2 与 DeepSeek-R1 报告中有描述。

### Cited Findings
- verl Full Determinism（2026-06-16）：默认"相同配置两次运行会因 GPU kernel、请求调度、hash 路由、batch 组成的非确定性得到不同 reward 曲线"；开启后"两次相同运行的 reward 曲线逐位对齐"，用途是调试、回归测试（验证代码变更无隐性影响）与公平对比；依赖 vLLM batch invariance（不覆盖的模型需 `max_num_seqs=1` 串行），**必须使用 V0 trainer**（V1 的 TransferQueue 按完成顺序收集输出会破坏可复现性）。— [verl docs/advance/determinism.md](https://github.com/verl-project/verl/blob/main/docs/advance/determinism.md)（A）
- verl SkipManager（2026-07-08）：按指定 step 跳过 rollout 等昂贵阶段，`cache`（有有效 dump 则加载）或 `repeat`（用替代 step 的 dump），支持 V0/V1/fully-async 入口，用于"确定性回放、bisect bug、省资源"。— [verl docs/advance/skip_manager.rst](https://github.com/verl-project/verl/blob/main/docs/advance/skip_manager.rst)（A）
- verl 的在线验证：`trainer.test_freq`、fully-async 下 `rollout.test_freq` 占用 Rollouter 资源"不建议设太小"、`use_trainer_do_validate` 可用 trainer 节点做验证以减少空闲；OpenOneRec recipe 设 `test_freq=50`、`val_before_train=True`。— [fully_async.md](https://github.com/verl-project/verl/blob/main/docs/advance/fully_async.md)、[run_grpo.sh](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/recipe/onerec/run_grpo.sh)（A）
- slime：CPU 测试覆盖核心行为与定制契约，GPU 测试覆盖 dense/MoE 训练、rollout 部署、checkpoint、精度、全异步、蒸馏与调试回放；v0.1.0 起"Dense 与 MoE 模型 CI 严格检查 kl 等指标"；确定性复现需卸载 FlashAttention-3、开启 SGLang 确定性推理（flashinfer）与 Megatron `--deterministic-mode`，并设 `NCCL_ALGO=Ring`、`NVTE_ALLOW_NONDETERMINISTIC_ALGO=0`、`CUBLAS_WORKSPACE_CONFIG=:4096:8`；容错：自动检测并重启 SGLang 引擎、Megatron 故障后保留服务集群改配置重提交（需 Ray 集群存活与 straw/debug 数据）。— [slime README](https://github.com/THUDM/slime/blob/main/README.md)、[reproducibility.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/reproducibility.md)、[fault-tolerance.md](https://github.com/THUDM/slime/blob/main/docs/en/advanced/fault-tolerance.md)（A）
- NeMo RL 评估：DCP checkpoint 需先转 HF 格式，`run_eval.py` 以 vLLM 生成，默认 greedy 评 AIME-2024；强调"使用与训练一致的 prompt 与 chat_template"。— [NeMo RL guides/eval.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/eval.md)（A）
- prime-rl `uv run eval`：复用 orchestrator 的 eval 管道（每个 source 起环境服务器，并发控制器下运行 episode，流入 trace 与指标），训练中支持在线 eval；对本地 vLLM 可自适应并发。— [prime-rl docs/eval.md](https://github.com/PrimeIntellect-ai/prime-rl/blob/main/docs/eval.md)（A）
- TRL GRPO 记录的诊断指标：零奖励方差样本比例、采样器与训练模型 logp 差异（均值/最大，"增长表明训推不匹配扩大"）、IS 比率范围、clip 比例、熵、KL。— [TRL grpo_trainer.md](https://github.com/huggingface/trl/blob/main/docs/source/grpo_trainer.md)（A）
- NeMo RL Router Replay 提供 JSONL trace 与 `tools/check_r3_trace.py` 校验（rollout payload → TransferQueue → packing → CP 切分 → Megatron 回放的 token 身份一致性），并要求"R3-on/off 配对实验验证确实降低训推不匹配"。— [NeMo RL router-replay.md](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/router-replay.md)（A）
- 模型厂商的评估系统化：Seed-Thinking-v1.5 数学类基准取 32 次回答平均、GPQA 8 次；K2 在非 thinking 模式、8192 token 上限（SWE-bench 16384）、128K 上下文下评测，高方差基准用 Avg@k，SWE-bench 以 best-of-N + 内部 verifier 评 multi-attempt，并专设 safety evaluation 章节；DeepSeek-R1 在全场景 RL 中对无害性"评估整条回答含推理过程"。— [seed-thinking-v1.5.pdf](https://github.com/ByteDance-Seed/Seed-Thinking-v1.5/blob/main/seed-thinking-v1.5.pdf)、[Kimi K2 report](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)、[DeepSeek_R1.pdf](https://github.com/deepseek-ai/DeepSeek-R1/blob/main/DeepSeek_R1.pdf)（A）
- 推荐侧的评估：OneRec 用 NTP loss、P-Score、xtr 指标（lvtr/vtr/ltr/wtr/cmtr，来自线上排序模型）做流式离线评估，并指出"流式数据上同一指标在不同时段绝对值不同"；OneRec-V2 用 5% 流量一周 A/B（App Stay Time、LT7）。— [OneRec TR](https://arxiv.org/abs/2506.13695)、[OneRec-V2](https://arxiv.org/abs/2508.20900)（A）

### Inferences
- RL 的回归测试正在从"看曲线"升级为"逐位可复现 + 中间产物回放 + 训推不匹配指标门禁"；但可复现模式与高吞吐异步模式互斥（verl 仅 V0、slime 需关 FA3），实际团队需要两套配置。
- 安全评估在开源框架层几乎缺席（只有奖励函数层面的 harmlessness），系统化的安全评估主要存在于厂商内部（K2 的 safety 章节、R1 的全回答无害性评估）。

### Gaps
- 未找到任何框架给出"评估流水线占 RL 总时间比例"或"验证集评测的资源预算"数据。
- 安全评估的自动化系统（红队、越狱测试的基础设施）没有一手开源材料。

## KQ7 未来 12 个月（2026-10 → 2027-10）的判断

### Takeaway
基于各框架公开路线图与 2026 年已出现的趋势，接下来一年 RL 基础设施的主线是：全异步成为默认、权重同步走向稀疏 delta/P2P 并支持跨集群异构、投机解码与低精度（FP8/NVFP4）进入 RL 内环、训推"零不匹配"工具链普及、以及从线上 agent 流量直接做在线 RL。

### Cited Findings（路线图与已发生的信号）
- verl 路线图：v0.8——TensorDict 替代 DataProto（零 padding 传输）、默认切换到新 Model Engine、VeOmni 转生产就绪、MTP RL 训练、长上下文细粒度激活重计算/卸载、DeepSeek V3.2 支持、新增 TensorRT-LLM rollout、vLLM worker 从 trainer 进程分离（CUDA IPC 更新权重）、TransferQueue 合入主线、checkpoint engine 的 NCCL/NIXL 后端；v0.9——fully async 合入主线、移除旧引擎、全模态 RL（Qwen3-Omni、BAGEL）、vllm-omni rollout、SWEAgent/GUIAgent recipe。— [verl v0.7 blog roadmap](https://github.com/verl-project/verl/blob/main/docs/blog/v0.7.md)（2026-01-03；A）

### Inferences（判断）
- 分离式全异步将成为 128+ GPU 的默认配置，共置同步退居"小规模/算法验证/可复现"用途（verl、OpenRLHF 文档已如此定位）；staleness 控制 + Decoupled PPO/IS 修正会成为算法库标配。
- 权重同步的下一步是"稀疏 delta + P2P/RDMA + 跨集群/跨厂商"（verl delta_sharded、NeMo RL sparse/NIXL、slime 磁盘 delta、SkyRL sharded_rdt 已同时出现），1T 级模型每步同步会压到 10 s 量级以下。
- rollout 侧的收益将来自 FP8/NVFP4 + 投机解码（含在线草稿训练）+ PD 分离 + KV 共享；相应地，训推不匹配的修正（IS/RS、R3、batch-invariant kernel）会从"可选"变为"默认开启"。
- 对推荐系统：LLM 化生成式推荐（OpenOneRec 路线）会越来越多直接用 verl/slime 做 GRPO 与 on-policy 蒸馏；SID 短序列的主链路 RL 则会继续走"线上流量 rollout + 真实反馈奖励 + 流式在线学习 + 参数推送"的自研栈，可能借鉴的是 checkpoint engine 与 Reward Loop 的抽象。

- 以上判断基于路线图与趋势推断，没有来源能证实 2027 年前的具体交付；verl v0.8/v0.9 的发布时间表在文档中未给出日期。

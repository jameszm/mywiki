## 关键问题 1：排序/召回模型的 GPU 推理栈（TensorRT / Triton / 自研引擎 / NVIDIA HSTU 与 SID-GR / CPU→GPU 成本 / GPU 选型）

### Takeaway
2025 年中到 2026 年 10 月，公开的推荐推理栈分成三条线：(1) **NVIDIA 官方栈**从"HugeCTR HPS（已于 v25.03 弃用）"整体迁移到 recsys-examples：HSTU 推理（paged GPU KV cache + 用户 ID 索引的 host/SSD 多级 KV 存储 FlexKV + CUDA graph + Triton Python/AOTI 后端 + torch.export/AOTInductor C++ 运行时）与 **SID-GR 推理引擎**（ContextKV/BeamKV/BeamPath、request×beam 连续批处理、专用 beam decode attention kernel，H100 上比 SGLang beam-search 分支快 1.9–2.3×、在线吞吐 1.85×），全部以 Qwen3-0.6B/1.7B + KuaiRand 的"示例规模"给出，不是生产数字；(2) **头部公司自研栈**：快手 UniPredict（TensorRT + 自定义插件 + batching + MPS，L20）、Meta（SilverTorch GPU 模型化服务 13.35× 成本效率 vs CPU；ROCS/IKBO 请求级共享内核进入 FBGEMM；WHALE/SORT/NVIDIA 三方都转向 AOTInductor）、阿里（PPU 810E 近线推理、SORT 的 torch.export+AOTI 推理系统 +29.4% 吞吐）、Pinterest（Scorpion Model Server GPU 化 + CUDA graphs；PinRec 跑在 Triton ensemble 上）、Coupang（CPU/GPU 分图 + 双层 batching）；(3) **字节跳动**公开的只有模型侧的服务设计（LONGER KV cache serving、STCA/MixFormer 的 Request Level Batching、HAP 难度路由、SequenceO1 用户级批处理、TM20K 的 M-FALCON serving、ReST 的 50 ms P99 预算、X-Rec 在 TikTok 的连续空间召回），**没有任何引擎层（TensorRT/Triton/自研）披露**，Monolith 开源的 TF-Serving entry/PS 架构停留在 2022–2023。GPU 选型上，公开数据把 **L20**（快手推理主力、NVIDIA 基准卡、SGLang beam 基准卡）、**H100/H200**（Meta 上游用户模型集群、NVIDIA SID-GR 基准）、**B200/GB200**（Meta WHALE/Kunlun 实验与 NVIDIA Blackwell kernel）、**H20**（阿里 URM、小红书 GenRank）、**T4/A100/L40S/RTX PRO 6000/GH200/PPU/Ascend NPU** 各自对应到具体系统；CPU→GPU 的成本对比只有相对数（SilverTorch 13.35×、Pinterest "100×"（C）、OneRec OPEX 10.6%、Coupang P99 82→32 ms），没有美元/千次请求。

**1.1 NVIDIA 官方栈：recsys-examples 的推理路线（官方仓库，A）**

- 版本时间线（CHANGELOG + releases 页）：v25.07（2025-08-01）首发"HSTU 推理基准：paged KV cache + CUDA graph"；v25.08（2025-09-08）端到端 HSTU 推理示例；v25.09（2025-10-20）推理 kernel 融合 + FP8 量化；v25.12（2026-01-13）**Triton Inference Server 支持 + 首个 SID-GR 示例**；v26.01（2026-02-13）KV cache 管理迁到 C++、异步 onload/offload；v26.03（2026-04-14）**torch.export + AOTInductor 端到端 C++ 推理**、B200 推理基准；v26.04（2026-05-20）`corelib/recsys_kvcache_manager` 独立包（native + FlexKV 后端）、`corelib/gr_decode_atten` beam decode attention kernel、`generate_beam_decode()`；v26.05（2026-06-16）SID-GR 推理示例、Blackwell 训练、sm8x beam search；v26.06（2026-07-14）FlexKV 推理路径优化 + 三级命中路径（GPU-hit / CPU-hit / SSD-hit）基准；v26.06.02（2026-08-06）SGLang 兼容的权重热更新；v26.07（2026-08-13）可导出 KV cache 的 AOTI 推理；v26.08（2026-09-14）DynamicEmb delta replay — [CHANGELOG](https://github.com/NVIDIA/recsys-examples/blob/main/CHANGELOG.md)、[Releases](https://github.com/NVIDIA/recsys-examples/releases)（官方仓库，2026-09，A）。
- HSTU 推理架构：`KVCacheManager` = `GPUKVCacheManager`（paged KV 表，按**用户 ID** 而非 token 前缀查找，LRU 驱逐最老用户，FBGEMM-HSTU attention kernel 直接读 paged 表）+ `HostKVStorageManagerBase`（`NativeHostKVCacheManager` 仅 pinned host memory，支持**逐层 onboard** 与前层计算重叠；`FlexKVCacheManager` 接 FlexKV 的 CPU/SSD/远端层）。已声明的限制：`allocate_kvcache` 为 host 阻塞、**每 GPU 仅允许一个 KV manager 且一个推理实例**、native 后端需按 user_id 路由并做实例隔离；驱逐时**不做 offload** — [recsys_kvcache_manager README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/recsys_kvcache_manager/README.md)（官方仓库，2026，A）。设计上：为了 torch.export/AOTI 兼容，把有状态的缓存策略放进 C++ `ExportKVCacheRuntime`，torch 自定义算子只做 tensor-only 薄封装，运行时通过 thread-local 上下文解析 — [EXPORT_KVCACHE_DESIGN.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/recsys_kvcache_manager/doc/EXPORT_KVCACHE_DESIGN.md)（A）。
- Triton 路径：Python backend 加载 HSTU，拆成 sparse 模块（NVEmbedding 后端，每 GPU 建 embedding 表/缓存、共享本地参数存储）与 dense 模块（每 GPU 一个实例），**Triton 的 dense 路径目前走 `forward_nokvcache`，KV cache 推理只在独立 Python 路径与 AOTI 路径可用**；dense 模型为 batch 1/2/8 捕获 CUDA graph，其他 batch 落到下一个 graph 桶 — [HSTU inference README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference/README.md)（A）。Triton 官方教程把 HSTU 列入 Popular Models Guide，走 PyTorch backend 的 AOTI 包（`platform: "torch_aoti"`），正文只是指向 recsys-examples 的桩页面 — [triton-inference-server/tutorials HSTU](https://github.com/triton-inference-server/tutorials/blob/main/Popular_Models_Guide/HSTU/README.md)（官方仓库，A）。
- AOTI/C++ 基准（KuaiRand-1K 排序模型，hidden 512、4 头、head dim 128、BF16、历史 2×4096 + 候选 100 + 上下文 6 → 导出最大序列 8320）：**3 层 HSTU 每请求延迟 Python→C++ 运行时**：L20 6.031→3.708 ms（1.63×）、L40 4.866→2.921（1.66×）、L40S 4.605→2.419（1.90×）、RTX PRO 6000 Blackwell 2.809→1.950（1.44×）；**Triton（RTX PRO 6000，batch 2）**：Python backend 无缓存 3.161 ms → AOTI backend 无缓存 2.471（1.28×）→ AOTI + GPU KV 命中 1.436（2.20×）；8 层：5.879→5.156→2.467（2.38×）；**AOTI 按 batch**：3 层 batch 2/4/8 无缓存 2.471/1.956/1.890 ms，KV 命中 1.436/0.763/0.423 ms（4.47×@8）；8 层 batch 8 无缓存 4.020、命中 0.678（5.93×）。协议注记：**Triton 调度器级 batching 因 jagged 输入格式被禁用**，一次 Triton 调用 = 一个逻辑 batch；每个 batch size 重启 Triton 与 FlexKV 进程 — [inference_aoti/benchmark/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference_aoti/benchmark/README.md)（A）。NVIDIA 技术博客《Deploying an HSTU Generative Recommender with NVIDIA Dynamo-Triton》转述同一组数字（4.47×/5.93×，100% KV 命中的最佳情形），并说明 "Dynamo-Triton（原 Triton Inference Server）" — [developer.nvidia.com](https://developer.nvidia.com/blog/deploying-an-hstu-generative-recommender-with-nvidia-dynamo-triton)（博客，搜索摘要，C，与 A 一致）。
- 端到端 HSTU 推理基准（8 层、1024 维、4 头、head dim 256、最大序列 4096、256 候选）：L20 上 KV cache + CUDA graph 整体 1.3–2.6×（batch 1–8，含 embedding 查表，KV 准备/onload/offload 计入但被异步隐藏）；HSTU block 在 4096 token 中 3968 已缓存时 3–20×（无候选）/3–8×（256 候选）；**B200（Blackwell CuteDSL kernel）3.3–7.7×，但 page size 128、head dim 128 受当前 kernel 实现限制**（L20 为 page 32、head dim 256） — [inference/benchmark/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference/benchmark/README.md)（A）。
- 多级 KV 存储的真实开销（H100，8 层、head dim 256、4 头、batch 8、bf16、page 32）：新序列 offload 一轮中 `offload_wait` 为 25.5/30.7/39.9 ms（seq 1024/2048/4096），其中 FlexKV `try_wait` 13–18.6 ms；100% GPU miss / 100% CPU hit 的 onboard 一轮 `onboard_wait` 17.3/21.2/37.3 ms，lookup 约 1.8–2.0 ms（FlexKV `get_match` 1.3–1.4 ms）；结论"**传输相关延迟是主导项**，元数据/查找/分配/launch 为其余部分，序列越长固定开销占比越小" — [FLEXKV_CPU_BREAKDOWN.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/recsys_kvcache_manager/test/FLEXKV_CPU_BREAKDOWN.md)（A）。
- HSTU attention kernel：旧包 `corelib/hstu` 已标记 DEPRECATED，迁移到 FBGEMM 的 `fbgemm_gpu/experimental/hstu`（统一支持 Ampere/Hopper、`seqused_q/k`、**FP8 block-scale 量化、Blackwell sm100**）；HSTU-3（Hopper）支持 FP8（head dim 64/128/256，1×DIM&128×1、per-block/head/batch/tensor 量化模式） — [corelib/hstu README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/hstu/README.md)（A）。
- 工具链补充：v26.08 加入 Talos（面向 Claude Code/Codex 的"profile→改→测"PyTorch 优化 agent，附 HSTU 与 OneRec 两个 user_guide 示例） — [corelib/talos README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)（A）。
- Triton Inference Server 本身：main 分支 README 指当前发布 2.73.0 对应 NGC 26.09 容器；与推荐服务相关的调度特性在用户指南中：dynamic batcher（`preferred_batch_size`、`max_queue_delay_microseconds`、`preserve_ordering`、`priority_levels` 与每优先级 `max_queue_size`/`default_timeout_microseconds`/`allow_timeout_override`）、`allow_ragged_batch`（允许不同 shape 的请求合批）、response cache（按模型名/版本/输入哈希的服务端缓存，local 与 redis 实现）、BLS（Python backend 内编排多模型）、ensemble、rate limiter 与实例优先级 — [server README](https://github.com/triton-inference-server/server/blob/main/README.md)、[batcher.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/batcher.md)、[ragged_batching.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/ragged_batching.md)、[response_cache.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/response_cache.md)（官方仓库 @2026-10-08，A）。

- facebookresearch/generative-recommenders（@2026-10-08）：新增 HSTU Ultra（半局部/target-aware 层栈，`fp8_addmm_fwd=True` 让两个投影 GEMM 走 FP8，`prepare_fp8_weights()` 缓存行量化权重）；**单张 H100 96 GB 上完整层栈前向 BF16→FP8**：8 层半局部 512/1024/2048 序列 6.04→5.33、5.91→5.21、6.07→5.40 ms（1.13×）；12 层 target-aware 768/1024/1536 序列 9.10→8.06、9.38→7.77、9.47→7.57 ms（1.13–1.25×）；attention-only Triton kernel 相对 PyTorch 2.0–2.3×；"cached incremental decoding 与 scripted 推理导出尚未包含"。仓库还包含 **MLPerf Inference DLRMv3 参考实现**：8×H100/B200 单机、2 TB 合成数据（500 万用户 × 10 亿物品 × 100 时间戳，推理只用 1%）、1 TB 训练 checkpoint，Server 场景 `user.conf` 把 **p99 目标延迟设为 80 ms**（mlperf.conf 默认 10 ms），参考 gin 的 `target_qps = 1000`、`batchsize = 10`；接受提交需 NE/Acc/AUC 在参考值（86.687% / 69.651% / 78.663%）的 99% 内 — [README](https://github.com/facebookresearch/generative-recommenders/blob/main/README.md)、[dlrm_v3/inference/README.md](https://github.com/facebookresearch/generative-recommenders/blob/main/generative_recommenders/dlrm_v3/inference/README.md)（官方仓库，A；**基准参考实现，不是 Meta 生产配置**）。

- WHALE（Meta，2026-07）：推理 QPS 优化三件事 — shared-gate SwiGLU FFN（+15% 推理 QPS）、定制 Triton attention kernel、编译器级图优化（**AOTInductor** 消除 host-device 同步，省 1–5 ms）；合计推理吞吐 +22%、训练 +30%；全部实验在 **B200** 上 — [arXiv 2607.17017](https://arxiv.org/abs/2607.17017)（A，[技报/规模未知]）。
- ULTRA-HSTU（Meta，2026-02）：单 H100 主机、端到端 **80 ms 预算**下的峰值 QPS：稀疏 embedding Int8 → Int4 使查表延迟 13→7.9 ms（−40%）、峰值 QPS 3.6K→4.4K（+22%）；FP8 只用于每层两个 GEMM（UVQK 投影、后注意力投影），其余 BF16；自研带 2D bias 融合的 Triton FP8 GEMM（Torch FP8 GEMM 不支持 2D bias），量化融合进前序 kernel；SLA attention 在 H100 16K 序列 >520 TFLOP/s，**AMD MI300 上达到 H100 的 0.92×**；混合精度整体训练 +10%、服务 +40% 吞吐 — [arXiv 2602.16986](https://arxiv.org/abs/2602.16986)（A，[生产+数据]）。
- LoKA（Meta，2026-05-12）：FP8 用于"大推荐模型"的三原则框架——LoKA Probe（在真实分布下在线学习激活/权重统计、量化逐层误差，定位 FP8 安全/不安全位点）、LoKA Mods（可复用的模型改造）、LoKA Dispatch（按统计选最快且满足精度的 FP8 kernel）；动机是推荐模型"数值敏感、由小 GEMM + 归一化主导、通信密集，直接用 FP8 会掉质量并拖慢训练" — [arXiv 2605.10886](https://arxiv.org/abs/2605.10886)（A 摘要级，[技报/规模未知]）。

**1.3 快手（A）**

- OneRec v1 推理基础设施：NVIDIA **L20**，每服务器 4 GPU + 2 CPU，PCIe 互联；跑在快手预测平台 **UniPredict**；推理服务与 embedding 服务部署在 200 Gb RDMA（RoCE）数据中心，机间最大带宽 800 Gb；**TensorRT 编译优化计算图 + 自定义插件实现 cross-attention、MoE 等算子**；配合 batching 与 **MPS** 吞吐 5×，推理 MFU 28.8%（级联系统基线 11.2%）；平台约束 QPS >400k、延迟 <500 ms；级联系统 >50% 服务资源花在通信与存储 — [arXiv 2506.13695](https://arxiv.org/abs/2506.13695)（A，[生产+数据]）。
- OneRec-V2 量化推理（2026-03-13）：FP16 基线平均延迟 139 ms、吞吐 205 → 迁移到优化推理基础设施并启用 FP8 后 **70 ms（−49%）、394（+92%）**；增量拆分：基础设施升级 +27%，Linear 与 MoE 算子低精度 +42%，算子级优化 +23%；论文论点是 OneRec-V2 的权重/激活统计"比传统推荐模型更受控、接近 LLM"，且推理"计算密集、硬件利用率显著更高"，因此低精度能转化为端到端收益；线上 A/B "核心指标无退化"（搜索摘要指出 Table 1 中 Kuaishou Lite 的 Follow −0.450%、Watch Time −0.157% 等负项，未核实） — [arXiv 2603.11486](https://arxiv.org/abs/2603.11486)（A 摘要级 + C，[生产+数据]）。第三方摘要称批大小 32、骨干约 4B/每 token 激活 0.5B（C，未核实）。
- GR4AD（2026-02）：L20、<100 ms、500+ QPS/卡，已全量 — 细节见关键问题 3 — [arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A，[生产+数据]）。
- MaRI（快手，2026-02-27）：针对粗排/精排的"特征融合矩阵乘中用户侧计算冗余"，用结构重参数化做**无损**推理加速（与蒸馏/轻量化互补） — [arXiv 2602.23105](https://arxiv.org/abs/2602.23105)（A 摘要级，[技报/规模未知]）。
- GRank（快手，2025-10）：去结构化索引的召回——target-aware Generator 用 **GPU 加速 MIPS** 做个性化候选生成 + 轻量 Ranker；"Recall@500 +30%、P99 QPS 为树/图索引检索器的 1.7×"；2025 Q2 起全量，服务 4 亿用户，可用性 99.95% — [arXiv 2510.15299](https://arxiv.org/abs/2510.15299)（A 摘要级，[生产+数据]）。

**1.4 字节跳动 / 抖音 / TikTok 公开资料（A；专门覆盖）**

- Monolith（2022 论文，仓库最后更新 2023-11）：服务格式为 TF saved_model，分为 **entry**（接客户端请求、调 PS 取 embedding、跑计算图）与 **PS**（embedding KV 存储，仅 entry 可调用）；agent 启动 TF Serving 并注册到 ZooKeeper 名字服务；`layout_filters` 决定一台机器加载哪些 entry/ps 分片（分布式服务）；配置项含 `enable_batching`、`fetch_ps_timeout_ms`、`per_process_gpu_memory_fraction`、model warmup 等；`parameter_sync` 模块与 `distributed_serving_ops.tf_serving_remote_predict`（RPC deadline 默认 30 ms）支撑在线训练到服务的参数同步 — [markdown/serving.md](https://github.com/bytedance/monolith/blob/master/markdown/serving.md)、[monolith/native_training/distributed_serving_ops.py](https://github.com/bytedance/monolith/blob/master/monolith/native_training/distributed_serving_ops.py)（官方仓库，2022–2023，A，**背景，非 2025–2026 现状**）。

- "推理栈"的分层在 2026 年已经清晰：**引擎层**（TensorRT 插件 / Triton / AOTInductor C++ / TensorRT-LLM / 自研 beam 引擎）与**模型侧服务设计**（KV cache serving、RLB、路由）是两个独立的公开话题；字节只公开后者，快手与 NVIDIA 两者都公开，Meta 通过 FBGEMM/TorchRec/SilverTorch 公开内核与系统论文但不公开引擎。对 TikTok 团队而言，可直接复用的公开代码只有 NVIDIA recsys-examples（Apache-2.0）与 FBGEMM IKBO/HSTU。
- **torch.export + AOTInductor 正在成为推荐 GPU 推理的"共同底座"**：NVIDIA（v26.03 起）、Meta（WHALE）、阿里（SORT）三方独立选择它，动机一致——消除 Python 调度与 host-device 同步（WHALE 1–5 ms、NVIDIA 1.44–1.90×），同时保留 PyTorch 自定义算子；TensorRT 仍被快手用于 OneRec v1，但 OneRec-V2 量化论文改称"优化推理基础设施"而未再提 TensorRT。
- NVIDIA 给出的数字都是 KuaiRand-1K 规模的示例模型（hidden 512/1024、3–8 层），其绝对延迟（0.4–6 ms/请求）**不能外推到生产**；真正可对标的生产锚点仍是 OneRec-V2（1B、36 ms、L20）与 GR4AD（0.16B、<100 ms、500 QPS/L20）。
- L20 在中国厂商推理中的地位由"PCIe、48 GB、FP8 支持、合规"决定，而不是峰值算力；NVIDIA 的 Blackwell kernel 在推荐场景仍有 head dim/page size 限制，说明 B200 上的推荐推理 kernel 成熟度落后于 Hopper 半年到一年。

### Gaps
- 字节跳动/TikTok 的推理引擎（是否 TensorRT、Triton 或自研；是否使用 AOTInductor；GPU 型号）无任何公开资料；Monolith 开源版本不代表 2025–2026 现状。
- Meta Adaptive Ranking Model 博客正文被阻断，无法确认延迟、路由规则、参数规模；"按请求价值路由"的具体机制未在任何可达来源出现。
- OneRec-V2 量化论文的硬件型号、批大小、吞吐单位（请求/秒还是样本/秒）未从正文核实。
- 没有找到 2025–2026 年任何一家公司的 CPU 与 GPU 推理在同一模型上的绝对成本（$/千次请求）对比；SilverTorch 的 13.35× 与 Pinterest "100×"口径不明。

## 关键问题 2：用户侧计算复用——跨候选 / 跨请求 / 跨阶段 KV cache、用户 token/表征缓存服务、异步近线预计算、一致性与实时性取舍

### Takeaway
2026 年"用户侧算一次"已从单一技巧扩展成四个层级的系统设计：(1) **跨候选**（请求内）——M-FALCON 式 KV 复用（LONGER −40%→−6.8%）、Request Level Batching（STCA 训练 2.2×、MixFormer 服务 +30%）、Meta ROCS 把"候选隔离 + 延迟交互 + 内核内广播"做成通用范式（召回 QPS 3×、短视频排序 +50% QPS 且 LogLoss −0.5%，广告与自然流量、召回与排序全面部署），ReST/HELIX/MaRI/UniPinRec/PinFM DCAT 都是同一原则的变体；(2) **跨请求**——OneTrans 把增量计算降到 O(ΔL)，NVIDIA 用"用户 ID 索引的 paged KV + host/SSD 多级存储"把它产品化，MTServe/HELM/RelayGR 分别解决存储爆炸（host RAM 虚拟化，3.1×，命中 >98.5%）、HBM 内 embedding 与 KV 的争抢（P99 −24–38%）和跨阶段在 HBM 内接力（Ascend，SLO 内吞吐 3.6×）；(3) **跨阶段**——UniPinRec 用跨阶段 KV 共享把端到端延迟降 11.1%、QPS +63.6%，OneTrans-V2 把整条级联编码一次并换到 3.2× 吞吐，Gryphon-v2/UniR²/UNIQUE 走同一方向；(4) **异步/近线**——Meta LLaTTE（事件触发、H100 专用集群、写 feature store、P99 不变）、YouTube TokenMinds（异步基础设施解耦表征生成与打分）、Yandex（离线 Transformer 恢复 72–80% 全历史质量且"对陈旧性鲁棒"）、阿里 TBGRecall（PPU 近线 ANN 写缓存）、Meta SOLARIS（预测未来 user-item 对预计算 latent）与 RADAR（异步全量排序结果当召回源）、腾讯 KuaFu（周级刷新 10 亿用户、省 190 GPU）。实时性与一致性的取舍已被明确工程化：缓存的训练-服务偏差（Meta Memory Layer 把 NE gap 12.11%→1.64%、新鲜度 5 min→20 s）、权重更新必须清空旧 KV（NVIDIA 热更新协议 `pause→flush_cache→update→continue`）、结果缓存 TTL（GR4AD 1 分钟内 27.8% 请求命中）、always-on 回退（Memory Layer/SOLARIS）。

### Cited Findings

**2.1 跨候选（请求内）复用**

- LONGER 的两阶段推理与"候选对序列不可见"的因果 mask 是复用前提（mask 保证序列表示与候选无关）；吞吐退化 −40% → −6.8% — [arXiv 2505.04421](https://arxiv.org/abs/2505.04421)（A，[生产+数据]）。
- Meta ROCS（2026-07-31）："每个请求对多个候选评估、请求侧特征在候选间共享"；尽量推迟请求-候选交互、隔离候选相关表示、模型大部分每请求算一次；Generalized Layer Masking（GLM）在特征交互架构里强制候选隔离、Deep Cross Attention（DCA）把请求级共享扩展到序列架构、IKBO 做 GPU 内核协同设计；生产规模"召回模型最高 3× QPS 无质量损失；短视频排序 LogLoss −0.5% 且 QPS +50%"；已跨广告与自然内容、召回与排序、"两个数量级以上的推理复杂度"部署 — [arXiv 2607.27744](https://arxiv.org/abs/2607.27744)（A 摘要级，[生产+数据]）；daiwk 复现注记官方代码位于 FBGEMM ikbo — [daiwk 页](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2607.27744-rocs/README.md)（B）。
- STCA RLB：训练吞吐 2.2×、带宽 −84%、PS CPU 减半；服务侧"RLB 摊销用户编码以把服务成本控制在预算内" — [arXiv 2511.06077](https://arxiv.org/abs/2511.06077)（A）。MixFormer UI 解耦 + RLB 服务加速 >30% — [arXiv 2602.14110](https://arxiv.org/abs/2602.14110)（A）。ReST 的 compute-once/decode-many 与 50 ms P99 — [arXiv 2609.01240](https://arxiv.org/abs/2609.01240)（A 摘要级）。HELIX 单向信息流 — [arXiv 2609.37183](https://arxiv.org/abs/2609.37183)（A 摘要级）。MaRI 结构重参数化消除用户侧冗余 — [arXiv 2602.23105](https://arxiv.org/abs/2602.23105)（A 摘要级）。SORT 的 request-centric 样本组织使"共享 token 的计算在推理时复用" — [arXiv 2603.03988](https://arxiv.org/abs/2603.03988)（A）。PinFM DCAT：序列去重 + Triton 逆去重 kernel，服务吞吐 +600%、训练 +200%，再叠加 25% — [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）。
- Meta Adaptive Ranking Model 博客的同类表述（高密度用户信号与长序列每请求算一次、线性→次线性）见 1.2（C）。

**2.2 跨请求 KV cache**

- OneTrans：S-token（序列）与 NS-token（候选）分离；Stage I 每请求一次处理 S-token 并缓存 K/V 与注意力输出，Stage II 每候选对缓存做 cross-attention；因行为序列 append-only，**跨请求复用上一请求缓存，只算新增行为，O(L)→O(ΔL)**；OneTransL vs DCNv2+DIN：TFLOPs 0.06→8.62、参数 10M→330M、MFU 13.4→30.8、**p99 推理延迟 13.6→13.2 ms**、推理显存 1.8→0.8 GB；"混合精度 + 重计算带来最大服务收益：p99 −69%、推理显存 −30%，因为推理可端到端低精度" — [arXiv 2510.26104](https://arxiv.org/abs/2510.26104)（A，[生产+数据]）。OneTrans-V2：序列编码一次作为检索/预排/精排共享上下文，Sequence-Native Training 按用户终身序列组织训练并跨曝光摊销编码；"**与协同设计的服务栈一起，在同等硬件预算下达到被替换级联 3.2× 的吞吐**"，GMV +9.74% — [arXiv 2609.28589](https://arxiv.org/abs/2609.28589)（A 摘要级，[生产+数据]）。
- NVIDIA recsys_kvcache_manager（见 1.1）与基准：KV 命中时 HSTU block 3–20×；AOTI+Triton 在 batch 8 命中时 4.47×/5.93× — [recsys-examples](https://github.com/NVIDIA/recsys-examples)（A）。设计前提明确写在 README："推荐系统各用户序列差异大、几乎没有公共前缀，所以按用户 ID 查找而非比较 token 值" — [recsys_kvcache_manager README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/recsys_kvcache_manager/README.md)（A）。
- MTServe（2026-04-28，美团作者群，含 HugeCTR 前核心作者）：跨请求 KV 复用导致"单个用户状态规模远超物理 GPU 上限"，用 host RAM 作为可扩展备份存储虚拟化 GPU 显存；混合存储布局 + 异步传输流水 + 局部性驱动替换；公开与生产数据集上最高 3.1× 加速、命中率 >98.5%；未来工作加 NVMe SSD 层存冷用户 — [arXiv 2604.22881](https://arxiv.org/abs/2604.22881)（A 摘要级，[技报/规模未知]）。
- HELM "One Pool, Two Caches"（2026-05-07，学术）：GR 推理中 embedding 热缓存与 KV cache 争抢 HBM，最优分配比随工作负载变化最多 0.35、静态分配留下 20–30% 延迟收益；朴素在线重分配引入 H2D 回填流量触发 P99 SLO 违规；三层 PPO 控制器 32 µs 决策、EMB-KV 感知路由；32 节点 A100 上 P99 −24–38%、SLO 满足率 93.5–99.6% — [arXiv 2605.04450](https://arxiv.org/abs/2605.04450)（A 摘要级，[仅研究]）。
- RelayGR（华为，2026-01-06）：排序只剩"数十毫秒"预算，GR 在线序列长度被 P99 卡死；多数 GR token 与候选无关 → 预推理用户前缀；难点是 prefix cache 要跨多个流水阶段存活、用户规模超单设备、无差别预推理会在高 QPS 下压垮共享资源；三件套：**sequence-aware trigger**（只接纳有风险请求、限制缓存足迹与预推理负载）、**affinity-aware router**（把预推理信号与排序请求路由到同一实例）、**memory-aware expander**（server 本地 DRAM 捕获短期跨请求复用）；Ascend NPU 实现，固定 P99 SLO 下序列 1.5× 更长、SLO 内吞吐 3.6× — [arXiv 2601.01712](https://arxiv.org/abs/2601.01712)（A 摘要级，[技报/规模未知]）。
- TransX（LinkedIn，2026-07-31）：行为流（近线编码）与服务事件流分离，解码时对二者 cross-attention；**增量行为编码 + 每请求 KV caching 使服务延迟对序列长度不敏感**，在线计算 −80%，CTR +6.0%、转化 +4.4% — [arXiv 2607.28940](https://arxiv.org/abs/2607.28940)（A 摘要级，[生产+数据]）。
- SequenceO1：训练侧本地 KV cache 作为主要复用机制、服务用同一缓存接口；缓存固定大小 sketch 故缓存体积与长度无关，命中路径对序列长度 O(1) — [arXiv 2609.08443](https://arxiv.org/abs/2609.08443)（A）。
- 学术方向：CollectiveKV（2026-01，ICLR'26）——跨用户 KV 共享：SVD 显示 KV 大部分信息跨用户可共享，学习全局 KV 池 + 低维用户专属 KV，**KV cache 压到原来的 0.8%** — [arXiv 2601.19178](https://arxiv.org/abs/2601.19178)（A 摘要级，[仅研究]）；Rec2PM（腾讯广告作者群，2026-02）用 Preference Memory token 替代"庞大的 KV cache"做存储 — [arXiv 2602.11605](https://arxiv.org/abs/2602.11605)（A 摘要级，[仅研究]）；MARS（2026-10-07）多分辨率缓存用户记忆、1000 候选 warm-cache 延迟仅为基线 1.02× — [arXiv 2610.07505](https://arxiv.org/abs/2610.07505)（A 摘要级，[仅研究]）。

**2.3 跨阶段复用与级联统一**

- UniPinRec（Pinterest，2026-05-29）：一个输入格式、一个模型、一次训练、部署在既有服务基础设施；共享 Transformer 编码用户行为序列为候选无关表示，分支到召回（ANN 点积）与排序（cross-attention）；**Cross-stage KV cache sharing 复用召回阶段的用户历史计算给排序**；核心场景 +1% 互动、**端到端服务延迟 −11.1%、QPS +63.6%** — [arXiv 2606.00422](https://arxiv.org/abs/2606.00422)（A 摘要级，[生产+数据]）；搜索摘要补充"跨进程通过 CUDA IPC 句柄共享预分配的 GPU 内存池，排序直接读召回的 KV 状态；使用 FP8 混合精度训练与推理"（C，未核实）。
- Gryphon-v2（Yandex Music）：编码一次 → 生成 SID 候选 → 解析为物品 → 复用共享 encoder 状态的 item-level Ranking Module，单模型替换 15+ 生成器级联，延迟相当 — [arXiv 2608.06213](https://arxiv.org/abs/2608.06213)（A 摘要级，[生产+数据]）。Gryphon（2026-06）同一思路，"参数量与延迟相当"下 Recall@1000 +3.7% — [arXiv 2606.08604](https://arxiv.org/abs/2606.08604)（A 摘要级）。UniR²（快手）：单 decoder-only 序列统一生成召回与多目标排序，消除"冗余的用户侧上下文计算" — [arXiv 2607.24439](https://arxiv.org/abs/2607.24439)（A 摘要级）。UNIQUE（百度）：P99 89 ms（B，见 01）。

**2.4 用户 token/表征缓存服务与异步近线预计算**

- Meta LLaTTE（2026-01）：上游用户模型"不按请求计算，而由高价值用户事件（主要是转化）触发"，在"**专用 H100 主机集群**上以更深更长的 LLaTTE 做高吞吐 Transformer 推理"，只用用户侧特征，生成压缩表示（d_transfer = 2048）**写入 feature store**；下游排序按请求读作 dense 特征；"Meta 最大的用户模型部署"；下游 ranker 序列预算 T≈400/源，上游序列算力预算是在线 ranker 的 45×；"**P99 排序延迟无可测变化**……额外 FLOPs 被 QPS 低得多、重度批处理的 H100 集群吸收" — [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（A，[生产+数据]）。
- Meta HyperCast（2025-08）：三层推理服务——在线 FM（为数百排序候选出 embedding，严格延迟）、离线 FM logging（只为被服务的少量物品生成训练 embedding，延迟宽松，**主机数仅为在线 FM 层的 1/3**）、在线 expert；模型新鲜度靠"只发布最近更新的部分（如 30%）权重并与推理服务器同步，分钟级刷新不中断服务"；数据到训练器平均延迟约 30 分钟 — [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A，[生产+数据]）。

- Yandex 广告 LHUT（2026-07-17）：广告"必须在几百毫秒内打分进入竞价"，高容量离线 Transformer 异步编码用户全跨面历史为紧凑表示**缓存在 feature store**，轻量运行时模型结合缓存表示 + 最近事件 + 请求上下文；离线"分离设计恢复了全历史运行时 Transformer 72–80% 的质量，**缓存表示对陈旧性足够鲁棒、允许廉价的刷新策略**"；搜索广告 +2.77%、广告网络 +2.1%，收入 +2.26%/+0.43%，服务延迟不增 — [arXiv 2607.14331](https://arxiv.org/abs/2607.14331)（A 摘要级，[生产+数据]）。
- 阿里 TBGRecall 近线框架（见 1.5）：`<userid, topkItemList>` 缓存 + 周期更新 — [arXiv 2508.11977](https://arxiv.org/abs/2508.11977)（A）。阿里 LUM："预训练 LUM 并在各种条件下预先触发所需知识……预计算帮助满足严格延迟约束" — [arXiv 2502.08309](https://arxiv.org/abs/2502.08309)（A）。
- Meta SOLARIS（2026-04-13）：预测未来会访问的 user-item 对，异步用基础模型预计算并缓存 latent，命中直接消费、未命中走 fallback；全量部署，top-line revenue +0.67% — [daiwk 页](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2604.12110-solaris/README.md)（B，[生产+数据]，未核实）。Meta RADAR（2025-06）：异步离线用全复杂度排序模型对更大候选集预排序，top 结果作为在线召回源、绕过在线召回与预排；Recall@200 2×，线上互动 +0.8% — [arXiv 2506.07261](https://arxiv.org/abs/2506.07261)（A 摘要级，[生产+数据]）。

### Inferences
- 四层复用的边际收益不同：请求内复用（RLB/ROCS）是"免费"的（不改变语义、不引入陈旧性），所以 2026 年几乎所有排序论文都默认采用；跨请求 KV 复用引入**存储与路由**问题（MTServe/RelayGR/HELM 的全部内容都是在解决这一层），其收益取决于 ΔL/L 与命中率，适合高频访问用户；异步表征服务引入**陈旧性**，但换来"把序列算力预算提高 45×（LLaTTE）而 P99 不变"，是当前头部公司扩序列算力的主路径。
- "用户 ID 索引、无公共前缀"是推荐 KV cache 与 LLM prefix cache 的本质差异：这决定了推荐侧需要 affinity routing（RelayGR、NVIDIA native 后端的 user_id 路由要求）、按用户 LRU 驱逐，以及 host/SSD 分层按"用户热度"而非"前缀热度"组织。
- 对 TikTok 团队的可操作判断：字节自己的论文（LONGER/OneTrans/STCA/SequenceO1/ReST/HELIX）已覆盖前两层；公开资料里尚未见字节的"异步用户表征服务（LLaTTE/TokenMinds 式）"，这是 Meta/Google/Yandex/腾讯已公开而字节未公开的一环。

## 关键问题 3：生成式推荐服务——beam search 引擎、LazyAR/半自回归、动态 beam、SID 层数与解码成本、连续空间生成、FP8、paged KV cache、与 LLM 引擎不适配点

### Takeaway
生成式推荐的服务工作负载被 NVIDIA 与 GR4AD/GRACE 一致定义为"**长上下文（1k–5k token）+ 短解码（3–5 步）+ 大 beam（128–1024）+ 每请求所有 beam 共享同一上下文**"，与聊天 LLM 的"多请求、长解码、beam<10"相反；这直接导致通用引擎失配——vLLM 没有稳定的生产 beam 路径（社区基准显示 beam 400 时 QPS 从 5.5 崩到 0.06），TensorRT-LLM 对该路径不暴露 logprobs 且大 beam 内存压力大，SGLang 的 beam search 直到 **2026-08-26 才合入主干**（按请求 `beam_width`，KV 压力下整组中止）。于是出现三类专用引擎：NVIDIA SID-GR（ContextKV/BeamKV/BeamPath + request×beam 连续批处理 + 专用 decode attention，H100 上比 SGLang beam 分支离线 1.9–2.3×、在线吞吐 1.85×、中位延迟 −46%，decode attention 从 35.2 ms 降到 1.6 ms）、Meta GRACE（encoder-decoder、宽 beam 专用 cross/self-attention kernel 68×/23–26×、decoder 整体 11.1×、paged KV 只拷父 beam 的 block id、GTM 目标匹配约束解码）、快手 GR4AD 的工程组合（beam-shared KV +212.5%、TopK Pre-Cut +184.8%、FP8 +50.3%、结果缓存 +27.8%、LazyAR ≈2× QPS、动态 beam [128,256,512] +45% QPS 且收入仅 −0.15%）。解码成本的第二条路线是**减少自回归步数或放弃 SID**：单层大码本（解码 FLOPs −48%、QPS +28.6–47%）、PinRec 多 token（6 步 p50 40 ms→3 步 23 ms）、X-Rec 连续空间（3.46×）、Snap EGR、SID-MLP 蒸馏（8.74×，学术）、投机解码 PAD-Rec（3.1×，学术）。FP8 PTQ 在生成式模型上"比传统推荐模型容易"（OneRec-V2 −49% 延迟/+92% 吞吐；GR4AD +50.3% QPS、收入 −0.1%），正在成为默认精度。

### Cited Findings

**3.1 工作负载定义与 LLM 引擎的不适配（A）**

- NVIDIA SID-GR README 的问题陈述："长上下文 + 短解码 + 大 beam 宽度；许多 beam 共享同一请求级上下文"；对三大引擎的判断——**vLLM** 不提供稳定的生产 beam search 服务路径，用户常在业务逻辑里反复调用 vLLM 自行实现；**TensorRT-LLM** 对该路径不原生暴露 logprobs，大 beam 造成内存压力，decode attention 与后处理 kernel 未针对短 SID 解码特化；**SGLang** 是"当前最可用的开源基线"，但大 beam 支持仍在未合入的 feature PR；"把通用 LLM 全栈改造成专用推荐推理引擎可行但不是最佳长期路径（可维护性与 speed-of-light）" — [sid-gr-inference README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)（官方仓库，A）。

**3.2 Beam search 引擎实现（A / A 摘要级）**

- NVIDIA SID-GR 运行时（单机 alpha，Qwen3-1.7B 真实权重）：请求长上下文存一次于 `ContextKV`（当前为稠密连续布局，便于 kernel 与 CUDA graph 的稳定 pool 切片），短解码历史存 `BeamKV`，`BeamPath` 记录逻辑父子关系；BeamKV/ContextKV 稠密池带租约、容量跟踪、高水位与泄漏检查；调度器按解码步、beam 宽、上下文形状分组，**批处理单元 = request × active beams**；固定形状 decode CUDA graph 绑定稳定 pool 切片，回放只更新 beam token id 与 topK 索引，非连续 KV 切片回退 eager；graph cache 有 LRU 与指针守卫；所有 decode graph 共享一个私有内存池与每 (beam_width, bucket) 一个 logits 缓冲，使捕获显存"基本不随 graph 数增长"；在线服务启动时预热常见 batch/pool 窗口/`ignore_eos` 形状后**冻结新 graph 捕获**；prefill 只算最后位置 logits；prefill 走 SGLang 式分段 CUDA graph（bs4/ctx1000 捕获 6 段）；QK norm 与 RoPE 优先用 SGLang 式原地 kernel，FlashInfer/Torch 回退；**动态 beam 策略**支持 fixed / scheduled / score-margin 且可按请求 HTTP 配置；**物品约束生成**：item trie、合法 token mask、约束 topK、catalog 热加载/回滚、物品元数据 — [sid-gr-inference README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)（A）。

**3.3 解码成本结构、SID 层数与替代解码**

- OneRec-V1 中上下文编码占总 FLOPs 97.66%（0.5B:0.5B encoder-decoder 346 GFLOPs 中 338 为上下文编码、8.1 为目标解码）；V2 lazy decoder 去掉 encoder 与 K/V 投影，计算 −94%、训练资源 −90% — [arXiv 2508.20900](https://arxiv.org/abs/2508.20900)（A）。
- NVIDIA sid_gr 训练示例对 beam 成本的定义："检索 N 个候选需要 H 步 beam search（H = SID 层数，通常 3–5），最后一步 beam 宽 = N；与 LLM 相比步数预定且少、beam 宽大得多（数百到数千）"；每步对上一步全部 beam 各展开 codebook_size 个续写再 topK — [sid_gr README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid_gr/README.md)（A）。
- 单层大语义码本（快手，2026-08-24）：用一个语义 token + 一个协同消歧 token 替代多层残差码；跨三种服务架构"**估算自回归解码 FLOPs −47.93%–48.70%、单卡 QPS +28.57%–47.0%**"；2.5% 流量五日 A/B 主消费指标 +0.792% — [arXiv 2608.21012](https://arxiv.org/abs/2608.21012)（A 摘要级，[生产+数据]）。CQ-SID（淘宝搜索，2026-05）把 beam 规模减半，生成召回通道占曝光 50.25%、点击 58.96%、购买 72.63% — [arXiv 2605.14434](https://arxiv.org/abs/2605.14434)（A 摘要级，[生产+数据]）。
- 多 token / 并行 / 非自回归：PinRec 6 步 vs 3 步延迟（见 1.5）与"相对 PinRec-OC 约 10× 延迟下降" — [arXiv 2504.10507](https://arxiv.org/abs/2504.10507)（A）；RPG 无序长 SID（64 token）并行预测 — [arXiv 2506.05781](https://arxiv.org/abs/2506.05781)（A 摘要级，[仅研究]）；LLaDA-Rec 离散扩散并行生成 SID 并改造 beam search — [arXiv 2511.06254](https://arxiv.org/abs/2511.06254)（A 摘要级，[仅研究]）；腾讯 HiGR 整页生成 5× 推理加速（A 摘要级）；OneLive Sequential MTP QPS +31.8%、延迟 −55.45%（B，01 已引）。
- 蒸馏/投机：SID-MLP 用位置专属 MLP 头蒸馏自回归教师，8.74× — [arXiv 2605.12617](https://arxiv.org/abs/2605.12617)（A 摘要级，[仅研究]）；SmartGR 层级与 beam 感知蒸馏 2.39× — [arXiv 2608.02048](https://arxiv.org/abs/2608.02048)（A 摘要级，[仅研究]）；PAD-Rec 位置感知草稿投机解码最高 3.1× — [arXiv 2604.27747](https://arxiv.org/abs/2604.27747)（A 摘要级，[仅研究]）；WhisperRec 潜推理 vs 显式 CoT 在线吞吐 >10× — [arXiv 2607.26621](https://arxiv.org/abs/2607.26621)（A 摘要级）。
- 连续空间替代 SID：X-Rec 3.46× — [arXiv 2609.29180](https://arxiv.org/abs/2609.29180)（A 摘要级）；Snap EGR 单共享 LLM、物品直接索引为稠密向量，"去掉量化、可变标识词表与 token-到-物品 grounding"，转化 +2.91% — [arXiv 2607.23038](https://arxiv.org/abs/2607.23038)（A 摘要级，[生产+数据]）。
- 多目标 beam：Multi-Decoder OneRec 在推理时按显式路由配额分配固定预算、Multi-Decoder Constrained Beam Search 减少跨路重叠 — [arXiv 2607.26500](https://arxiv.org/abs/2607.26500)（A 摘要级，[生产+数据]）。

**3.4 FP8 / 低精度**

- OneRec-V2 FP8 PTQ：见 1.3（−49% 延迟、+92% 吞吐，FP8 贡献 +42%） — [arXiv 2603.11486](https://arxiv.org/abs/2603.11486)（A 摘要级）。GR4AD FP8 +50.3% QPS、收入 −0.1%（A）。LinkedIn FP8 粗排全库（A 摘要级）。ULTRA-HSTU FP8 GEMM + INT4 embedding（A）。LoKA 的 FP8 方法论（A 摘要级）。HSTU attention FP8（fbgemm_gpu_hstu，A）。GR 仓库 HSTU Ultra FP8 层栈 1.13–1.25×（A）。TokenMixer-Large FP8 E4M3 PTQ 1.7×（02 已引）。

### Inferences
- "专用 beam 引擎"的收益主要来自两处：**decode attention 不把 beam 当独立序列**（NVIDIA 35.2→1.6 ms；GRACE cross-attn 68×）与**消除 host 侧调度**（NVIDIA CPU gap 28.3→2.2 ms）；topK 本身不是瓶颈。这意味着自研引擎的最小可行投入是一个 context/beam 分离的 attention kernel + CUDA graph，而不是整套 serving 框架。
- 2026 年中后 SGLang 官方 beam search 合入主干后，"通用引擎无法做大 beam"的论据部分失效，但 NVIDIA 的对比对象仍是社区分支；SGLang 主干在 KV 压力下整组中止、不支持投机解码/PD 分离，仍不满足推荐的 p99 与多级缓存需求。预计 NVIDIA 的下一轮对比会转向 SGLang 主干。
- 解码成本 ≈ 上下文编码（可缓存/共享，随序列线性）+ 解码（随 beam × SID 层数 × 码本）：GR4AD 的 DBW 表给出了"首层 beam 可降 4× 而收入几乎不变"的经验规律，单层大码本与多 token 生成从结构上把 H 从 3 降到 1–2，这两条路线会合流为"1–2 步解码 + 宽 beam"的工作点，使 KV cache 的价值进一步集中到上下文部分。
- FP8 对生成式推荐"更容易"（OneRec-V2 论文的核心论点）是因为模型数值分布接近 LLM 且算子以大 GEMM 为主；对传统 DLRM（小 GEMM + 归一化）LoKA 表明需要逐层探针与模型改造，不能直接套用。

### Gaps
- GRACE 正文（P99、batch、生产规模）与 paged KV 的延迟影响（Table 5）未读到。
- OneLA、UniSGR STARK、xGR 是否已生产部署未知。
- NVIDIA SID-GR 仅 Qwen 族 BF16、单 GPU；与 GR4AD/OneRec 真实模型（MoE、cross-attention、lazy decoder）的适配未验证。
- LazyAR 与 DeepSeek-MTP 的收入差（+4.28% vs +3.98%）在相同 +117% QPS 下的原因论文未解释。

## 关键问题 4：embedding 服务——GPU 哈希表/HBM 常驻、多级存储（HBM/DRAM/SSD）、训练到服务的增量同步、量化、超大表服务架构

### Takeaway
公开方案已经收敛到"**GPU 缓存语义哈希表 + 多级存储 + 增量同步**"：NVIDIA 2026-03 发表 HierarchicalKV 论文（H100 NVL 上 3.9 B-KV/s 查找、负载因子 0.5–1.0 下稳定、满桶 upsert 用驱逐/拒绝准入而非 rehash；2022-10 开源后已被多个推荐框架集成），DynamicEmb 在其之上提供 HBM+host 分层、按 (TIMESTAMP, LFU) 等自定义评分驱逐、准入控制，以及 **v26.08 的 `incremental_dump → replay_increment` 训练→服务 delta 复制**（按槽位精确回写、布局必须一致、只应用 erased 而非 evicted 键）；字节 LONGER 把高/中/低频 embedding 分到 HBM/DRAM/SSD 并与计算同机以去掉外部 PS；Meta Memory Layer 把 item 缓存变成模型内的稀疏参数表（新鲜度 5 min→20 s）；Pinterest 与"万亿文档搜索"用 CPU-GPU 混合服务突破显存上限；量化上 INT4/INT8 embedding（PinFM 表体积 31.25%、ULTRA-HSTU H2D −40%/QPS +22%、SilverTorch Int8 ANN、PinRec INT8）与 FP8 粗排（LinkedIn）并行。HugeCTR HPS 自 v25.03 弃用，NVIDIA 的服务侧 embedding 投入转到 NVEmbedding（`LinearUVMEmbedding`）+ DynamicEmb 导出路径；与 LLM 推理最大的差异是 **embedding 热缓存与 KV cache 在 HBM 内直接争抢**（HELM 量化为最优比例漂移 0.35、20–30% 延迟收益）。

### Cited Findings

- HierarchicalKV 论文（NVIDIA Merlin，2026-03-19）：传统 GPU 哈希表保留所有键的"字典假设"浪费 HBM；HKV 以**缓存语义**为常态契约——满桶 upsert 由评分驱动的驱逐或准入拒绝就地解决，不 rehash、不因容量失败；四机制：cache-line 对齐桶、内联评分 upsert、评分驱动的动态双桶选择、三组并发；**分层 key-value 分离**作为超出 HBM 的扩展手段；H100 NVL 上查找吞吐最高 3.9 B-KV/s、负载因子 0.50–1.00 变化 <5%，比 WarpCore 高 1.4×、比间接寻址 GPU 基线高 2.6–9.4×；2022 年 10 月开源以来被多个开源推荐框架集成 — [arXiv 2603.17168](https://arxiv.org/abs/2603.17168)（A 摘要级，[官方库 + 论文]）。
- DynamicEmb：GPU 优化的带评分哈希表后端，同时用 HBM 与主机内存；评分策略 TIMESTAMP/STEP/LFU 与复合 (TIMESTAMP, LFU)，可用 numba-cuda 自定义 `score_function`（README 示例为 log(freq) + age·log(0.9) 的 LRU/LFU 衰减）；准入控制阻止稀有/噪声 ID 占用参数与优化器状态；**Torch 可导出的 `InferenceEmbeddingTable`**（冻结 `ScoredHashTable` 元数据 + NVEmbedding `LinearUVMEmbedding`，支持序列与 SUM/MEAN 池化，从 dump 文件加载）；导出包为 `model.pt2 + metadata.json + weights/*.nve`，避免加载时重复拷贝表 — [DynamicEmb README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/README.md)、[inference_aoti README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference_aoti/README.md)（A）。
- 增量同步 API（v26.08）：`incremental_dump(model, score_threshold, pg)` 导出评分 ≥ 阈值的键/值/槽位索引（仅支持 roundrobin / hash_roundrobin 分片）；`replay_increment(serve_model, deltas)` 先擦除 `erased_keys` 再按**源表中的槽位与行**原位 upsert（目标布局必须与源一致：capacity、bucket_capacity、num_scores、world_size、score_strategy/dim/dist_type 全部校验，任一不符则整个集合不写入）；`evicted_keys` 不应用（占用其槽位的新键已在同一 delta 中）；replay 按本模型的 world size 重算键归属、跳过不属于本 rank 的键；典型部署"训练作业周期性 dump，delta 运到服务副本重放，不必重载全量 checkpoint" — [DynamicEmb_APIs.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/DynamicEmb_APIs.md)（A）。
- 字节 LONGER：高频 HBM / 中频 CPU 内存 / 低频本地 SSD，计算与参数存储完全同机，减少通信与内存传输，"提高训练吞吐、降低陈旧性" — [arXiv 2505.04421](https://arxiv.org/abs/2505.04421)（A）。
- 快手 OneRec：推理服务与 **embedding 服务**作为两个服务部署在 200 Gb RDMA 数据中心 — [arXiv 2506.13695](https://arxiv.org/abs/2506.13695)（A）。
- Meta Memory Layer：in-model KV embedding 缓存与模型共训、always-on embedding 覆盖缺失项、把三条训练器→预测器更新路径合并为一条；新鲜度 O(5 min)→O(20 s) — [arXiv 2607.25110](https://arxiv.org/abs/2607.25110)（A 摘要级）。Meta SilverTorch：GPU Bloom index 过滤 + 融合 Int8 ANN kernel，排序侧把预计算 item embedding 缓存进服务模型 — [arXiv 2511.14881](https://arxiv.org/abs/2511.14881)（A 摘要级）。
- Pinterest 广告：CPU-GPU 混合服务突破 GPU 显存限制，延迟持平 — [arXiv 2508.05700](https://arxiv.org/abs/2508.05700)（A 摘要级）。PinFM：FBGEMM n-bit min-max PTQ，32 维 fp16 → 32 个 int8/int4 + 1 个 fp16 scale；int4 表体积 31.25%、**CPU host 成本按比例下降**；GPU 侧自定义 Triton kernel 合并 bit unpack 与 FBGEMM 反量化，在线 GPU 前向延迟开销可忽略；偏差 L2：int8 0.45%、int4 7.8%；int8 离线无损，int4 Save −0.06% 但 A/B 可接受 — [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）。
- ULTRA-HSTU：稀疏 embedding 在长序列下主导 H2D 传输，groupwise INT4 量化保持量化态传输，查表延迟 −40%、峰值 QPS +22%、线上精度无差异 — [arXiv 2602.16986](https://arxiv.org/abs/2602.16986)（A）。
- HELM：GR 推理中 EMB 热缓存与 KV 争抢 HBM 的量化证据（最优比例漂移最多 0.35；静态策略留下 20–30% 延迟）— [arXiv 2605.04450](https://arxiv.org/abs/2605.04450)（A 摘要级，[仅研究]）。
- 混合 GPU-CPU 召回：GPU 侧只装约 10 亿文档精选池，CPU 侧承载 20× 大库，"全库进 GPU 显存太贵、CPU 跑不动交互重模型" — [arXiv 2609.21281](https://arxiv.org/abs/2609.21281)（A 摘要级）。
- HugeCTR HPS 弃用（v25.03） — [HPS index](https://github.com/NVIDIA-Merlin/HugeCTR/blob/main/docs/source/hierarchical_parameter_server/index.md)（A）；TorchRec 支持"降精度训练与推理的量化、面向 C++ 推理的优化" — [TorchRec README](https://github.com/meta-pytorch/torchrec)（A）。
- 背景（2022–2023）：Monolith 无碰撞哈希表、entry/PS 服务拆分、`parameter_sync` — [bytedance/monolith](https://github.com/bytedance/monolith)（A，背景）。

### Inferences
- "训练到服务的增量同步"在 2026 年被 NVIDIA 做成了带布局校验的通用 API，其设计选择（按槽位回写、要求同构布局、不应用 evicted）说明生产中真正的难点是**服务副本与训练表的拓扑一致性**，而不是传输本身；HyperCast 的"只发布 30% 最近更新权重"与 Memory Layer 的"训练时写回"是同一问题在 dense 与 sparse 两侧的解法。
- HBM 容量在 GR 时代成为 embedding 缓存与 KV cache 的共同瓶颈，HELM 的在线重分配与 RelayGR 的 DRAM 扩展暗示下一步是**统一的 HBM 预算管理器**，而不是各自独立的缓存。
- INT4 embedding 已有三家（Pinterest、Meta DV365、Meta ULTRA-HSTU）公开可接受，FP8 用于稠密 GEMM，INT8 用于 ANN；推荐推理的"混合精度栈"已基本定型为 INT4 稀疏 / FP8 稠密 / BF16 其余。

### Gaps
- 各公司 embedding 表总规模、HBM/DRAM/SSD 的容量比例与命中率没有 2025–2026 的公开绝对数字。
- NVEmbedding（`nv-embedding-cache`）本身的文档未读取，其与 HKV/DynamicEmb 的关系仅从 recsys-examples 侧可见。
- 字节 LONGER 的 SSD 层访问延迟、OneRec embedding 服务的 QPS 与带宽占比未披露。

## 关键问题 5：延迟预算与算力路由——请求级算力分配、p99 控制、batching、流量削峰与降级、多模型多阶段编排

### Takeaway
公开的延迟锚点形成一张可对照的表：精排 13–30 ms（OneTrans p99 13.2 ms、RankMixer 14.3 ms、ADS 30 ms、LUM 30 ms）、广告排序 P99 50 ms（ReST）、生成式广告召回 <100 ms（GR4AD）、生成式主站 36 ms（OneRec-V2 模型）/ 端到端 <500 ms（快手平台）、Meta 单机基准预算 80 ms（ULTRA-HSTU，与 MLPerf DLRMv3 Server 的 p99 80 ms 目标一致）、百度统一模型 P99 89 ms、Yandex 广告"几百毫秒进竞价"、Meta 广告"亚秒级"。算力路由的公开实践有四类：**按请求难度/价值路由到不同模型**（Meta Adaptive Ranking Model 的"复杂度匹配路由"（C）、头条 HAP 轻量/强预排分支、万亿文档搜索按请求选 GPU/CPU 通路）；**按流量峰谷调 beam**（GR4AD TABS 低峰 +60%）；**按缓存驻留路由**（RelayGR affinity router、HELM EMB-KV 感知调度、NVIDIA native 后端的 user_id 路由）；**按预测触发预计算**（SOLARIS、LLaTTE 事件触发、RelayGR sequence-aware trigger）。p99 控制与 batching 的公开数字：Coupang 双层 batching（客户端合批 20×、服务端超时 10 ms → 峰值吞吐 4.4×；CPU/GPU 分图 P99 82→32 ms），Triton dynamic batcher 的 `max_queue_delay/preferred_batch_size/priority_levels` 与 jagged 输入下不可用的现实（NVIDIA 基准关闭调度器合批），SID-GR 的 request×beam 连续批处理在 20 req/s 下 p99 仍 1.3–1.6× 于中位。降级手段以结果缓存（GR4AD 27.8%）、always-on 回退（Memory Layer/SOLARIS）、准入限制（RelayGR、SID-GR 的 KV 预算与超时生命周期、SGLang 的整组中止）为主。多阶段编排正在从"Triton ensemble/BLS 串多个模型"（PinRec）走向"一个模型吃掉级联"（OneTrans-V2、UniPinRec、Gryphon-v2、GenPage −20% 延迟）或"三层异构推理服务"（HyperCast）。

**5.2 请求级算力分配与路由**

- Meta Adaptive Ranking Model："智能请求路由替代一刀切推理路径，把每个请求路由到复杂度匹配的模型"，描述为解决"模型复杂度 / 延迟 / 成本"的 inference trilemma — [engineering.fb.com](https://engineering.fb.com/2026/03/31/ml-applications/meta-adaptive-ranking-model-bending-the-inference-scaling-curve-to-serve-llm-scale-models-for-ads/)（C）。**未检索到"按请求价值路由"的具体规则**。
- 头条 HAP：候选难度门控 g_i 在强/轻两分支间路由，harmonization 损失对齐尺度；九个月部署 — [daiwk 页](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2603.03770-hap/README.md)（B）、[arXiv 2603.03770](https://arxiv.org/abs/2603.03770)。
- GR4AD TABS：B_t = B_base · f(Q_t, C_avail)，低峰（Q_t < 阈值）提高 beam 利用闲置算力，高峰保持预算内；低峰 beam +60% 换收入 — [arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A）。NVIDIA SID-GR 的 fixed/scheduled/score-margin 三类动态 beam 策略可按请求 HTTP 配置（A）。
- RelayGR：sequence-aware trigger 只对"有风险"（长序列、会超 P99）的请求做预推理，并限制缓存足迹与预推理负载；affinity-aware router 把预推理信号与排序请求送到同一实例 — [arXiv 2601.01712](https://arxiv.org/abs/2601.01712)（A 摘要级）。HELM：按 KV 驻留、embedding 局部性与节点负载联合路由 — [arXiv 2605.04450](https://arxiv.org/abs/2605.04450)（A 摘要级）。NVIDIA native host 后端要求"user_id 路由 + 实例隔离"（A）。
- 混合 GPU-CPU 召回：每请求可走 GPU 深度通路、CPU 广度通路或两者，候选去重后共享下游排序 — [arXiv 2609.21281](https://arxiv.org/abs/2609.21281)（A 摘要级）。
- LLaTTE 的两阶段算力分配政策："下游在线 ranker 把延迟预算用于短序列、浅深度、足够宽度；异步上游用宽松延迟预算扩展总序列算力；下游收益主要由上游总算力决定而非深度/长度的具体分配" — [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（A）。
- 快手 MPFormer（2025-08）按难度动态分配容量与 serving 配额（03 已引，B）。

**5.3 p99 控制与 batching**

- Coupang：客户端合批（上游合并候选，GPU 处理 20× 大 batch，延迟开销很小）+ 服务端动态合批（独立请求聚合，**超时 10 ms** 时峰值吞吐 +4.4×）；CPU 预处理 / GPU 骨干分图后 P99 82→32 ms（2.6×）；最终 8× 推理 FLOPs 延迟基本不变 — [arXiv 2605.29232](https://arxiv.org/abs/2605.29232)（A，[生产+数据]）。
- Triton dynamic batcher：`preferred_batch_size`（首选批尺寸）、`max_queue_delay_microseconds`（为凑批最多等待）、`preserve_ordering`、`priority_levels` + 每级 `max_queue_size`/`default_timeout_microseconds`/`allow_timeout_override`（超时动作可拒绝或延迟）；`allow_ragged_batch` 允许不同 shape 合批 — [batcher.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/batcher.md)（A）。NVIDIA HSTU 基准中"Triton 调度器级 batching 因 jagged 数据输入格式被禁用" — [inference_aoti/benchmark README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference_aoti/benchmark/README.md)（A）。
- CUDA graph 分桶：NVIDIA dense 模型捕获 batch 1/2/8，输入需填充到预定 batch 与序列长度（静态形状） — [HSTU inference README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference/README.md)（A）；SID-GR 的 decode graph 桶 1/2/4/8、非连续 KV 回退 eager（A）。
- 快手 OneRec：batching + MPS 吞吐 5× — [arXiv 2506.13695](https://arxiv.org/abs/2506.13695)（A）。MixFormer：候选数增大时 GPU 利用率趋于饱和（A）。WHALE：AOTInductor 去掉 host-device 同步省 1–5 ms（A）。
- SGLang 官方 beam：10 QPS 负载下 p50/p90/p99 53/58/175 ms — [PR 31626](https://github.com/sgl-project/sglang/pull/31626)（A）。NVIDIA SID-GR 在线 p99 波动归因于 HTTP 客户端、Python 调度、到达时序、batch 填充（A）。
- ULTRA-HSTU 用"端到端 80 ms 预算下的峰值 QPS"作为服务效率指标（A）；ROCS 以 QPS 与 LogLoss 共同报告（A 摘要级）。

**5.4 流量削峰与降级**

- GR4AD：结果缓存一分钟窗口 27.8% 请求命中；TABS 按 QPS 调 beam — [arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A）。
- Memory Layer：always-on 属性 embedding 保证缓存缺失物品仍可打分（覆盖 96→100%） — [arXiv 2607.25110](https://arxiv.org/abs/2607.25110)（A 摘要级）；SOLARIS 未命中 fallback（B）。
- NVIDIA SID-GR：KV 预算、稠密池指标、高水位、泄漏检查、取消/超时生命周期已有，"高并发准入策略、把内存估计接入服务决策"在路线图 — [README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)（A）；热更新期间 503 可重试（A）。
- Triton：rate limiter 与实例优先级（priority 2 的实例获得 priority 1 一半的调度机会）、按优先级队列的超时策略 — [model_configuration.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/model_configuration.md)（A）。
- KuaFu：固定 GPU 预算下的吞吐下限决定压缩比（A 摘要级）。

**5.5 多模型多阶段编排**

- HyperCast 三层（在线 FM / 离线 FM logging（1/3 主机）/ 在线 expert），各层独立配置 GPU 运行时、延迟目标与硬件 — [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）。LLaTTE 两阶段（A）。TBGRecall 近线 + 在线缓存读（A）。
- PinRec：Triton ensemble + Python backend 串联"取信号 → ID embedding 特征化 → 自回归生成 → Faiss" — [arXiv 2504.10507](https://arxiv.org/abs/2504.10507)（A）。Triton ensemble/BLS 机制 — [bls.md](https://github.com/triton-inference-server/server/blob/main/docs/user_guide/bls.md)（A）。
- 级联统一：OneTrans-V2（3.2× 吞吐）、UniPinRec（−11.1% 延迟）、Gryphon-v2（替换 15+ 生成器）、UniR²、UNIQUE、GenPage（−20% 延迟）、Netflix GenRec prefill-only — 见前文（A 摘要级 / B）。
- 学术：Orthrus 在统一推理循环内对 embedding 与生成两类模型做异构批处理，4×A100 上吞吐 1.28–4.52×、p99 −55.8% — [arXiv 2609.25405](https://arxiv.org/abs/2609.25405)（A 摘要级，[仅研究]）。

### Inferences
- 推荐推理的 batching 与 LLM 不同：**候选维度天然提供大 batch**（Coupang 20×、MixFormer 饱和、SID-GR 的 request×beam），所以服务端跨请求合批的收益主要在小流量/长尾模型，而且 jagged 输入让 Triton 的通用 dynamic batcher 常常用不上——这解释了为什么 NVIDIA、Pinterest 都走"Python backend/AOTI 自己管 batch"而非 Triton 调度。
- 路由正在从"模型内门控（HAP）"扩展到"服务层调度（RelayGR/HELM）"，共同点是路由信号必须在请求进入 GPU 前可得（序列长度、缓存驻留、流量水位），这要求特征层暴露"用户序列长度/缓存状态"给路由器。
- 动态 beam（GR4AD TABS）把"推理时 scaling"变成一个可运营的旋钮：低峰多花算力换收入是推荐特有的（LLM 服务没有"收入随 beam 增长"的直接回报）。

### Gaps
- Meta "按请求价值路由"与 O(100 ms) 的原始表述无法核实；Adaptive Ranking Model 没有论文。
- 没有公司公开 p99 预算与 GPU 总量/副本数的组合；也没有公开"降级开关"的触发阈值与频率。
- 字节 HAP 之外，抖音/TikTok 主线的流量削峰与降级机制无公开资料。

- CPU 侧特征处理成本占比只有快手"服务资源 >50% 通信与存储"一个总量数字，没有分项。

## 关键问题 7：未来 12 个月（2026-10 → 2027-10）的判断；与 LLM 推理栈的收敛点和不收敛点

### Takeaway
收敛点已经发生在"**构件层**"：FP8 PTQ（OneRec-V2 论文明言"LLM 领域的算法与系统技术可以直接适配"）、paged KV cache（GRACE/NVIDIA）、CUDA graph 与连续批处理（SID-GR）、torch.export/AOTInductor（NVIDIA/Meta/阿里）、多级 KV 存储（FlexKV）、SGLang 兼容的权重热更新与 RL rollout 接口（NVIDIA）、MegaKernel（Ada-MK 嵌入 TensorRT-LLM）、FP8 attention（fbgemm_gpu_hstu）。不收敛点在"**结构层**"：请求×候选/beam 的共享上下文（ROCS/RLB/ContextKV），用户 ID 索引而非前缀索引的 KV（亲和路由、按用户 LRU），embedding 热缓存与 KV 在 HBM 内争抢（HELM），jagged 输入让通用 dynamic batcher 失效，秒级到分钟级的参数/索引流式同步（DynamicEmb replay、HyperCast 30% 发布、GR4AD 秒级索引），以及"beam 宽度 = 收入旋钮"的运营逻辑。未来 12 个月最可能的变化：(1) NVIDIA SID-GR 从单机 alpha 走向多 GPU/多副本并与 SGLang 主干 beam 对比，更多公司用它替代自写 beam 循环；(2) 单层/两层码本 + 多 token 生成使 SID 解码步数降到 1–2，KV cache 价值集中到上下文；(3) 用户表征异步服务（LLaTTE/TokenMinds/Yandex 型）成为头部公司标配，字节/TikTok 可能公开对应系统；(4) FP8 成为生成式与 Transformer 化排序的默认服务精度，INT4 稀疏 + FP8 稠密的混合栈定型；(5) HBM 统一预算管理（EMB + KV）与跨阶段 KV 接力进入生产论文；(6) MLPerf DLRMv3（HSTU、80 ms p99）会成为推荐推理硬件横评的公共基准，L20/H20 之外中国厂商的国产加速器（PPU、Ascend）推理数据增多。

- OneRec-V2 量化论文结论："随着推荐系统向 LLM 范式演进，LLM 领域建立的算法级与系统级优化技术可以有效适配大规模推荐工作负载" — [arXiv 2603.11486](https://arxiv.org/abs/2603.11486)（A 摘要级）。

### Inferences
- 对 TikTok 推理团队的 12 个月优先级（推断）：(a) 把 LONGER/OneTrans/ReST 式的用户侧 KV 复用升级为"跨请求 + 跨阶段 + host 分层"的平台能力，需要同时解决亲和路由与 HBM 预算；(b) 若上生成式召回，评估 NVIDIA SID-GR 的 ContextKV/BeamKV 抽象与 gr_decode_atten kernel 的可移植性，而不是整套 HTTP 服务；(c) 以 OneRec-V2 的 FP8 路线为模板做 PTQ 探针（LoKA 式逐层统计）；(d) 建立 LLaTTE/TokenMinds 式的异步用户表征服务并把陈旧性当作可调参数；(e) 用 MLPerf DLRMv3 的 Server 场景做硬件横评（L20/H20/B200/国产卡）。
- 不收敛的根因是推荐请求的"一个用户 × 很多候选 × 短输出"结构，这不会随 LLM 引擎演进消失；因此"把推荐跑在 vLLM/SGLang 上"只会在 LLM 骨干直接参与打分（URM、Netflix GenRec、Snap/广告 LLM）的场景发生，而 SID beam 召回与 HSTU/Transformer 排序会继续用专用或半专用引擎。
- 风险：NVIDIA 栈的生产成熟度（单 GPU、单实例、Qwen 族、dense ContextKV）与各公司真实模型（MoE、cross-attention、多目标头）之间仍有半年以上差距；以及"异步表征"路线在强实时场景（直播、广告竞价）的陈旧性损失尚无公开量化（Yandex 仅给 72–80% 质量恢复）。

### Gaps
- 没有任何公开资料描述 2026 下半年字节/TikTok 的推理栈路线图；上述对字节的判断全部为推断。
- MTIA/PPU/Ascend 在推荐推理上与 NVIDIA 的 perf/W 或 TCO 对比均未公开。
- SGLang 主干 beam search 与 NVIDIA SID-GR 的直接对比尚不存在；vLLM 在 2026 年是否补上生产 beam 路径未核实。
- "推理时 scaling（更宽 beam / 更多推理 token）换收入"的公开曲线只有 GR4AD 一家（0.16B：beam 128→1024 收入 +2.33%→+4.21%），其他公司未披露。

## Q1. 低精度数值格式：FP8 / MXFP8 / NVFP4 / INT8 / INT4 / KV cache 量化

### Takeaway

FP8 在训练侧已完全生产化（DeepSeek-V3 式 1×128/128×128 块缩放是 Hopper 事实标准，Blackwell 上被 MXFP8 原生微缩放取代），实测 1.2×–1.5× 端到端训练加速且 loss 曲线与 BF16 可比；FP4（NVFP4）在 2026 年从"推理格式"变成"可训练格式"，但必须叠加 RHT + 随机舍入 + 2D 量化 + 选择性高精度层四件套，且仅 Blackwell DC（sm100/10.x）支持完整配方。推理侧 FP8 KV cache 是唯一"默认可开"的选项（约 2× 容量、每 token 开销降到 BF16 的 54%），NVFP4 KV（56% of FP8）与 4-bit KV 仍需逐模型验证；INT4 权重 + QAT 是把超大模型塞进单节点的主力手段。**推荐模型侧的公开共识是"BF16 保稳定 + FP8 只打主 GEMM + embedding INT4/INT8"**，而不是全模型低精度。

### Cited Findings

**训练侧 FP8 配方（Hopper）**

- DeepSeek-V3 "设计了 FP8 混合精度训练框架，并首次在超大规模模型上验证 FP8 训练的可行性与有效性"；全量训练仅 2.788M H800 GPU-hours，其中 14.8T tokens 预训练占 2.664M，后训练仅 0.1M — [DeepSeek-V3 README](https://github.com/deepseek-ai/DeepSeek-V3/blob/main/README.md)（A，2024-12 发布，2025 全年为业界 FP8 训练基线）
- DeepSeek 式配方的具体数值约定：**权重 128×128 block scaling，激活 1×128 tile scaling，scale 在线逐 tile/block 计算**；这是"Hopper 时代的强配方，但在 Blackwell 上 FP32 scale 仍是围绕 Tensor Core 的软件路径，没有走原生微缩放硬件" — [SGLang/Miles MXFP8+NVFP4 RL 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-07-29-mxfp8-nvfp4-rl.md)（A，2026-07-29）
- TransformerEngine `Float8BlockScaling` 配方：scale 默认被约束为 2 的幂（可用 `NVTE_FP8_BLOCK_SCALING_FP32_SCALES=1` 放开）；**块缩放 FP8 必须开 split accumulation**，`fp8_gemm_fprop/dgrad/wgrad` 强制 `use_split_accumulator=True`，fused grouped GEMM 路径忽略调用方传入值 — [TE recipe 源码 docstring](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/common/recipe/__init__.py)（A）

**Blackwell 原生格式：MXFP8 / NVFP4**

- MXFP8 = 每 32 个连续 E4M3 共享一个 **E8M0**（8 位指数 0 位尾数，等价 2 的幂缩放）scale，1 维块；因为缩放有方向性，**量化张量与其转置在数值上不等价**，TE 因此在量化时同时从高精度输入生成 rowwise 与 columnwise 两份，以避免二次量化误差 — [TE `MXFP8BlockScaling` docstring](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/common/recipe/__init__.py)（A）
- NVFP4 = 两级缩放：L1 每 16 个值共享一个 **E4M3** scale，L2 全张量一个 FP32 scale；TE 默认 NVFP4 训练配方包含三件事：**权重用 16×16 二维块共享 scale、梯度用随机舍入（stochastic rounding）去偏、输入与梯度施加 16×16 随机 Hadamard 变换（RHT）压离群值** — [同上](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/common/recipe/__init__.py)（A）
- **硬件覆盖矩阵（权威）**：FP8 per-tensor 需 sm89+；FP8 block scaling 需 sm90+ 且 CUDA ≥12.9；**MXFP8 仅 sm100/10.x（B200/B300/GB300），sm120 不支持**；NVFP4 完整配方仅 sm10.x，sm120 只支持前向或"关掉 RHT 与随机舍入"的训练。TE 默认配方按架构选择：Hopper/Ada → `DelayedScaling`，Blackwell DC → **`MXFP8BlockScaling`**，Blackwell 工作站 → `Float8CurrentScaling`（临时，等 MXFP8 支持全部 GEMM layout） — [TE support_matrix.rst](https://github.com/NVIDIA/TransformerEngine/blob/main/docs/support_matrix.rst)（A）
- Megatron-Core 暴露的配方与门槛：`delayed`（默认，Hopper/Ada/Blackwell，**唯一支持 FP8 + optimizer CPU offload 的配方**）、`tensorwise`、`mxfp8`（Blackwell，E4M3）、`blockwise`（1×128/128×128，DeepSeek 风格）、`nvfp4`（Blackwell，**启动时强制校验 TE ≥ 2.7.0.dev0**）、`custom`；`--fp8-param-gather` / `--fp4-param-gather` 让参数 all-gather 直接走量化 dtype，降 DP 通信带宽 — [Megatron-LM low_precision_training.md](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/user-guide/features/low_precision_training.md)（A）
- 硬件算力基准（每 GPU，HGX 规格归一）：B200 BF16/FP8/FP4 = 2.25 / 4.5 / 9 PFLOPS；B300 = 2.25 / 4.5 / **13.5** PFLOPS；Rubin（NVL8）= 4 / 17.5 / 35 PFLOPS — [SGLang/Miles 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-07-29-mxfp8-nvfp4-rl.md)（A）。注意 B300 的 BF16/FP8 与 B200 相同，**只有 FP4 提升 3×**，这决定了"要吃到 Blackwell Ultra 的增量必须上 FP4"。

**低精度训练的实测收益与精度代价**

- NVFP4 预训练：**12B 模型 / 10T tokens**，号称"迄今公开记录中最长的 4-bit 精度训练"，训练 loss 与下游任务精度"与 FP8 基线可比"；配方 = RHT 限制块级离群点 + 二维量化（前后向表示一致）+ 随机舍入（无偏梯度）+ 选择性高精度层 — [Pretraining LLMs with NVFP4, arXiv 2509.25149 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/30-Sep-2025/AI/README.md)（A，摘要原文；2025-09-29）
- MXFP8 预训练踩坑：**OCP 规范建议的舍入模式会导致 LLM 预训练发散**；改为"用 round-to-infinity 计算 scale factor"后，8B 模型在 15T tokens 上成功收敛 — [Recipes for Pre-training LLMs with MXFP8, arXiv 2506.08027 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/11-Jun-2025/AI/README.md)（A，摘要原文；2025-06-11）
- torchao 公布的实测曲线（PyTorch 官方库 README/docs 原文）：
  - MXFP8 训练在 2k 规模 Crusoe B200 集群 **1.28×** 加速，loss 曲线与 bf16 "virtually identical"（2025-09）
  - MXFP8 MoE 训练原型：MoE 层 Llama4 Scout **~1.45×**、DeepSeek-V3 671B **~1.25×**，数值"与 bfloat16 可比"（2025-10）
  - 64 节点 GB200 + TorchTitan Llama4 Scout：**1.3× 端到端训练加速，收敛等价，3000 步后 loss 甚至略低于 bf16**
  - MXFP8 grouped GEMM 微基准（B200，`total_M=131072`）：Llama4 Scout 形状 **1.64–1.81×**、DeepSeek-V3 形状 **1.19–1.60×** vs bf16 `torch._grouped_mm`；单 kernel 前向 `torch._scaled_grouped_mm` (131072,7168)@(8,7168,2048) 达 **65.6% peak TFLOPS**
  - float8 rowwise 在 2k H200 规模 **1.34–1.43×**（2025-04）；float8 在 Llama-3.1-70B/405B 预训练 **1.43–1.51×**（2024-11，背景）
  — [pytorch/ao README](https://github.com/pytorch/ao/blob/main/README.md) 与 [moe_training README](https://github.com/pytorch/ao/blob/main/torchao/prototype/moe_training/README.md)（A）
- 训练-推理统一精度（RL 场景）：Qwen3-30B-A3B 在 8×B200 上，BF16 与**五种低精度配置的 raw reward 曲线高度重合**，MXFP8/NVFP4 则降低 rollout 时间；MXFP8 覆盖 rollout、前向、wgrad GEMM、dgrad GEMM，NVFP4 用于 MoE expert 路径的在线 per-token 激活缩放 — [SGLang/Miles 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-07-29-mxfp8-nvfp4-rl.md)（A）
- 统一 FP8 RL 的动机（反例价值）：对 MoE 模型，**模型越大，"BF16 训练 + FP8 rollout" 的训练-推理差异越严重**；统一 FP8 消除量化误差导致的不一致，同时提升速度与稳定性 — [LMSYS Unified FP8 RL 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-11-25-fp8-rl.md)（A，2025-11-25，InfiXAI + 蚂蚁 AQ + SGLang RL + Miles 联合）

**推理侧：KV cache 与权重量化**

- vLLM 的 `--kv-cache-dtype fp8` **同时**量化 KV 存储与整个 attention 计算（QK 与 ScoreV 两个 matmul，E4M3）。两个关键发现：
  1. **精度坑**：Hopper FP8 Tensor Core 虽文档称累加到 FP32 寄存器，但 contraction 维很大时中间累加丢精度（与 DeepSeek-V3 技术报告 Fig. 7(b) 同源问题）。128k needle-in-a-haystack 从 BF16 的 **91% 掉到 FP8 的 13%**，用两级累加（SageAttention2 式）修复后回到接近基线。
  2. **性能坑**：带 sliding-window 层的模型（如 gpt-oss-20b）FP8 的 ITL 斜率是 BF16 的 **96%**，几乎没有解码加速，break-even 点 **> 700k tokens**，所以推荐 `--kv-cache-dtype-skip-layers sliding_window`。
  - 正向结论：head_dim 64/128 时 prefill 与 decode 都有加速，内存受限解码下**每 token KV 开销最好情况可降到 BF16 的 54%**；`head_dim=256` 的 prefill 仍可能回退。
  — [vLLM "The State of FP8 KV-Cache and Attention Quantization" ](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-04-22-fp8-kvcache.md)（A，2026-04-22，AWS + Red Hat AI）
- 4-bit KV 的系统性评测结论：**FP8 仍是最佳默认**（2× 容量、精度损失可忽略、多数性能指标与 BF16 齐平）；Llama-3.3-70B/4×H100 上 FP8 burst 吞吐是 BF16 的 **2.6×**；TurboQuant `k8v4` 仅 2.4× 容量却稳定拖吞吐，不值得；`4bit-nc` 是最实用的 TurboQuant 变体但以 40–52% 吞吐下降换 2.3–3.7× 容量；`k3v4-nc`/`3bit-nc` 在推理与超长上下文任务上有明显精度下降 — [vLLM TurboQuant 研究](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-05-11-turboquant.md)（A，2026-05-11）。关键机制差异：TurboQuant **只压存储、attention 计算回到 BF16**，而 FP8 走原生 Tensor Core。
- NVFP4 KV cache（SGLang × Qwen × NVIDIA，2026-09-16）：每 16 个 NVFP4 值 = 8 字节数据 + 1 字节块 scale = **FP8 存储的 56.25%**；三条路径分别处理（initial prefill 直接吃 FP8 KV 并旁路写 NVFP4 cache；chunked prefill/extend 把 NVFP4 前缀反量化进共享 FP8 workspace；decode 直接读 NVFP4 并**在 kernel 内反量化到 FP8**，避免整段 KV 的读写往返）。SM120 实现为 BF16 Q + NVFP4 KV + BF16 MMA，用 `cvt.rn.bf16x2.e2m1x2` 做 E2M1→BF16 转换 — [SGLang NVFP4 KV cache 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-09-16-nvfp4-kv-cache.md)（A）
- FP8 attention + NVFP4 MoE 的端到端收益（GB200 NVL72，DeepSeek V3/R1，2000-token 输入）：**26,156 input / 13,386 output tokens/s/GPU**，相对 H100 配置 **3.8× / 4.8×**；传统精度（BF16 attention + FP8 MoE）为 18,471 / 9,087。**FP8 attention 相对 BF16 attention 带来最多 1.8×，NVFP4 GEMM 相对 FP8 GEMM 最多 1.9×，且"精度退化可忽略"**；此外把 `q_b_proj` 从 BF16 改为 FP8（与官方 NVIDIA checkpoint 不同）以提升性能 — [SGLang GB200 Part II](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-09-25-gb200-part-2.md)（A，2025-09-25）
- INT4 权重 + QAT：训练用 fake quantization、推理用真 W4A16，稳定性与训练-推理一致性"与 BF16 全精度训练可比"；极致 INT4 压缩让 **~1TB 规模模型在单节点完成 rollout**，消除跨节点通信瓶颈。该方案明确受 Kimi K2-Thinking 的 W4A16 QAT 实践启发 — [SGLang INT4 QAT 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-01-26-int4-qat.md)（A，2026-01-26）
- NVFP4 W4A4 + 量化感知蒸馏（QAD）：Qwen3.6-35B-A3B 达到"相对 BF16 最多 **1.30×** vLLM 吞吐、checkpoint 小 **3.1×**，并把 W4A4 的精度损失补回来"；Nemotron 3 Ultra 550B NVFP4 "匹配 BF16 精度" — [NVIDIA Model-Optimizer README](https://github.com/NVIDIA/Model-Optimizer/blob/main/README.md)（A 为仓库原文，但数字为厂商自报）
- MXFP4 的 QAT 路径：gpt-oss 原生 MXFP4 权重发布后社区缺训练支持，ModelOpt 的 QAT 可在 Blackwell/Hopper/Ampere/Ada 上保持 FP4 精度微调再用 SGLang 部署；文中明确区分 QAT（恢复量化推理精度、不提供训练效率）、native quantized training（需硬件原生支持、提供训练效率）、QLoRA（只降 LoRA 微调显存） — [SGLang × ModelOpt gpt-oss MXFP4 QAT](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-08-28-gpt-oss-qat.md)（A，2025-08-28）

### Inferences

- **训练与推理对数值的要求结构性不同**：训练关心"梯度是否无偏、长 horizon 是否发散"，所以 FP4 训练必须引入随机舍入与 RHT；推理关心"单次前向误差与长上下文累加误差"，所以 FP8 attention 的真正风险在 contraction 维极大时的累加精度（vLLM 的 91%→13% 是最有说服力的公开案例）。两者唯一共享的工程约束是 **RL/on-policy 场景下训练与推理必须用同一套量化契约**，否则 sampler 与 trainer 策略漂移。
- **Blackwell 带来的数值变量可以归纳为三条**：(1) 微缩放进硬件（MXFP8 的 E8M0/32 值、NVFP4 的 E4M3/16 值 + FP32 全局），scale 不再是软件围绕 Tensor Core 的补丁；(2) B300/GB300 只在 FP4 上增算力（13.5 vs 4.5 PFLOPS），"不上 FP4 就吃不到 Ultra 的增量"；(3) rowwise/columnwise 不等价迫使框架存两份量化副本，这改变了激活显存的计算方式（TE 路线比 DeepSeek 的"存 1×128 tile 再转向"占更多显存但省掉反量化+再量化）。
- 对 TikTok 推荐团队最可直接复用的结论：**先做 embedding INT4/INT8（省通信与显存，公开有 Meta 背书）+ 主 GEMM FP8（需配套融合量化 kernel，否则净收益被 scale 开销吃掉）+ attention 与归一化保 BF16**。HSTU Ultra 的 1.13–1.25× 是"包含投影 GEMM 的整层前向"数字，比单 GEMM 的 2× 更接近真实可得收益。

### Gaps

- **没有找到"生成式推荐 FP8 训练无损"的公开定量案例**。ULTRA-HSTU 说明了配方（BF16 为主 + FP8 主 GEMM + INT4 embedding）并提到离线与在线都做了验证，但我抽取到的 PDF 文本未包含对应的 NE/AUC 差异数字；recsys-examples 只声明"HSTU attention 支持 FP8 量化"，未给精度对照表。
- **排序模型对低精度的敏感性没有公开的系统性研究**（哪些层能 FP8、CTR 校准是否漂移、长尾 ID 的 embedding 量化误差如何影响 NE）。现有材料只能给出"大部分算子保 BF16"的工程惯例，无法给出敏感度排序。
- MegaScale-MoE 的"通信压缩到低精度"具体格式（FP8? 哪些张量?）未能取证，arXiv 不可达。

## Q2. 注意力算子：FA2/3/4、FlexAttention、FlashInfer、jagged/变长、MLA、稀疏、线性注意力

### Takeaway

2026 年注意力算子的分水岭是 **Blackwell 的"非对称硬件扩展"**：Tensor Core 吞吐翻倍而 shared memory 带宽与指数单元（SFU/MUFU）几乎没变，于是 FA4 必须用"软件模拟 exp + 条件 softmax 重缩放 + TMEM + 2-CTA MMA"来把瓶颈从非 matmul 操作上挪开，并且整个 kernel 用 **Python 里的 CuTe DSL** 写（编译快 20–30×）。MLA/稀疏注意力一侧，DeepSeek 已经把 FlashMLA 推到"**只支持 SM100/SM103 + 昇腾 950，且 decode 只接受 FP8/FP4 KV**"的激进状态。推荐模型需要的三类专用算子——**jagged/变长（HSTU）、大 beam decode、长上下文稀疏**——都已有公开实现，但分散在 FBGEMM、recsys-examples（CuTe DSL）与各引擎后端中，成熟度差异很大。

### Cited Findings

**FlashAttention 系列**

- **FA4 的公开数字与技术手段**（论文摘要原文）：B200 + BF16 上相对 **cuDNN 9.13 最多 1.3×**、相对 **Triton 2.7×**，峰值 **1613 TFLOPs/s（71% 利用率）**。三类手段：(1) 重新设计 pipeline 以利用全异步 MMA 与更大 tile；(2) **软件模拟指数函数**与条件 softmax 重缩放，减少非 matmul 操作；(3) 利用 **tensor memory (TMEM) 与 2-CTA MMA 模式**降低 shared memory 流量与反向的 atomic add。完全用**嵌入 Python 的 CuTe-DSL** 实现，编译时间比传统 C++ 模板快 **20–30×** — [FlashAttention-4, arXiv 2603.05451 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/6-Mar-2026/NLP/README.md)（A，2026-03-05；作者 Ted Zadouri, Markus Hoehnerbach, Jay Shah, Timmy Liu, Vijay Thakkar, Tri Dao）

- **FA4 仍是 beta**：PyPI 上 `flash-attn-4` 自 2026-03-05 的 `4.0.0b3` 到 2026-10-07 的 `4.0.0b34` **全部是 pre-release，按周滚动**，没有正式 4.0.0 — [flash-attn-4 PyPI](https://pypi.org/project/flash-attn-4/)（B，未核实逐条日期；页面经摘要抽取）

- FA3 定位：面向 Hopper（H100），**仍标注 beta**；已发布 FP16/BF16 前后向、FP8 仅前向；要求 H100/H800 + CUDA ≥ 12.3，推荐 12.8 — [flash-attention README](https://github.com/Dao-AILab/flash-attention/blob/main/README.md)（A）。第三方给出的 FA3 基线约 740 TFLOPs/s、75% 利用率 — [Lambda 博客](https://lambda.ai/blog/flashattention-4-gives-the-nvidia-blackwell-platform-its-most-optimized-attention-kernel-yet)（C，未核实）
- AMD 侧：flash-attention 的 Triton 实现支持 CDNA（MI200/MI300）与 RDNA，覆盖 fp16/bf16/fp32 前后向、causal mask、变长序列、任意 Q/KV 长度与 head size、MQA/GQA、dropout、rotary、ALiBi、paged attention 以及 FP8（经 FA3 接口）；sliding window 仍在做 — [同上](https://github.com/Dao-AILab/flash-attention/blob/main/README.md)（A）

**FlashInfer（推理算子的"后端聚合层"）**

- 定位与覆盖：统一的 attention / GEMM / MoE API，背后挂 **FlashAttention-2/3、cuDNN、CUTLASS、TensorRT-LLM** 多后端并自动选择；硬件从 SM75（Turing）到 Blackwell **SM100/10.3（B200/B300）、SM110（Jetson Thor）、SM120/12.1（RTX 50 / DGX Spark）**；attention、GEMM、MoE 都有 FP8 与 FP4（NVFP4/MXFP4）路径；功能面含 paged + ragged KV cache、MLA 原生支持、cascade attention（共享前缀）、**block-sparse 与 variable block-sparse**、POD-Attention（prefill+decode 融合）、sorting-free Top-K/Top-P/Min-P 采样、MNNVL 多节点 NVLink allreduce；**CUDAGraph 与 torch.compile 兼容**。Blackwell 支持在 v0.4.0（2025-10-08）加入 — [FlashInfer README](https://github.com/flashinfer-ai/flashinfer/blob/main/README.md)（A）
- Blackwell 上的 CuTe DSL kernel 走 `pip install flashinfer-python[cu13]`；仓库有专门的 **CuTe-DSL kernel 磁盘缓存设计文档**（CuTe-DSL kernel 原先没有磁盘缓存，现在首跑后毫秒级加载），并预留 `cutile` 等未来 DSL 的接口 — [FlashInfer docs/design_docs/cute_dsl_kernel_cache.md](https://github.com/flashinfer-ai/flashinfer/blob/main/docs/design_docs/cute_dsl_kernel_cache.md)（A）

**MLA 与稀疏注意力（FlashMLA / DSA / NSA / MoBA）**

- **FlashMLA 当前状态（2026-09-30 版本，破坏性变更）**：移除 Hopper 架构与早期模型（V3 / V3.2 / V4.0）支持，改变 FP8/FP4 KV 格式，与旧版不兼容；现在服务 **DeepSeek-V4.1 在 NVIDIA GPU 与华为昇腾 NPU 上的推理**。要求 **SM100/SM103 + CUDA ≥13.1（推荐 ≥13.2，因为需要原生 `cvt.rn.bf16x2`，否则量化 decode kernel 退化到经 FP32 的慢路径）** — [FlashMLA README](https://github.com/deepseek-ai/FlashMLA/blob/main/README.md)（A）
- FlashMLA 的 B200 实测（CUDA 13.3）：
  - **融合 kernel（Q-norm + Q-RoPE + core attention + O-RoPE 共轭 + cast to FP8）：prefill 最高 1460 TFlops，decode 950 TFlops**（代价是需预先 permute Q_b 与 Wv 权重）
  - 稀疏 MLA prefill **1350 TFlops**、稀疏 decode **1024 TFlops**（官方推荐优先用融合 kernel）
  - 稠密 MHA prefill 前向 **1460 TFlops**、反向 **1000 TFlops**（NVIDIA 报告）
  - 昇腾 950 NPU：prefill **410 TFlops（硬件理论峰值 95%）**、decode **360 TFlops（83%）**；并附有算法与优化技术的技术报告（gather2、decode KV cache layout、fast ND2NZ、icache miss、L1 bank balancing、skip-scale）
  - 历史锚点：2025-04-22 版本在 **H800 SXM5 上最高 660 TFlops**（compute-bound，比上一版快 5–15%）；2025-09-29 稀疏 kernel 在 Hopper 上 prefill 640 / decode 410 TFlops
  — [FlashMLA README](https://github.com/deepseek-ai/FlashMLA/blob/main/README.md) 与 [昇腾技术报告](https://github.com/deepseek-ai/FlashMLA/blob/main/docs/20260930-ascend-prefill-deep-dive.md)（A）
- **FP8 KV cache 格式与 decode 的硬约束**：V4.1 为每 token **528 字节**（512 个 `float8_e4m3` 覆盖全部 512 维，RoPE 的 64 维也量化；尾部 16 字节 `float8_e8m0` scale，每 32 个值一个）；V4.1-fp4 为 **288 字节**（256 字节放 512 个 e2m1，每字节 2 值；32 字节 `float8_e4m3` scale，每 16 值一个）。**decode kernel 只支持 FP8 与 FP4 KV，不支持 bf16** — [同上](https://github.com/deepseek-ai/FlashMLA/blob/main/README.md)（A）
- Hopper FP8 稀疏 decode 的"反量化受限"诊断（极有参考价值的工程方法论）：V3.2 的 128k 上下文单请求 KV = 576×2×62×128×1024 = **8.72 GiB**，这是引入 FP8 KV 的直接动因。量化方式为前 512 维做 1×128 tile 量化（512 个 e4m3 + 4 个 fp32 scale），**RoPE 的 64 维不量化保持 bf16**，每 token 656 字节。单 SM 每 cycle 4096 MMA FLOPs（989 TFlops / 1830 MHz / 132 SM），每 KV token 的 MMA 只需 ~34 cycles，但 H800 不能直接 e4m3→bf16，需四步转换共 **~50 cycles**，于是 kernel 是 **dequantization-bound**。解法"crossover"：利用 Hopper 的 **Distributed Shared Memory + cluster size 2 + `st.async`**，让两个 CTA 各反量化一半 KV 并互相写入对方 shared memory，**410 TFLOPS（原 250 TFLOPS）**；topk 增大到 32768 时可达 460 TFLOPS — [FlashMLA Hopper FP8 稀疏 decode 深度解析](https://github.com/deepseek-ai/FlashMLA/blob/main/docs/20250929-hopper-fp8-sparse-deep-dive.md)（A，2025-09-29）
- **DSA（DeepSeek Sparse Attention）的算子约束**：lightning indexer 用 ReLU 作激活"出于吞吐考虑"，head 数少且**可用 FP8 实现**，计算效率显著；每个 query 选 **top-2048** 个 KV token，核心 attention 复杂度 O(L²)→O(Lk)。**关键的 kernel 层设计约束**："在 kernel 层面，每个 key-value entry 必须被多个 query 共享才有计算效率（引 NSA）"，因此 DSA 实例化在 **MLA 的 MQA 模式**下，让每个 latent 向量被该 token 的所有 query head 共享。另外还实现了 **masked MHA 模式来模拟 DSA**，在短序列下效率更高 — [DeepSeek-V3.2-Exp 技术报告](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/DeepSeek_V3_2.pdf)（A，PDF 原文）
- DSA 的质量代价：与 V3.1-Terminus 对齐训练配置后，公开 benchmark 基本持平（MMLU-Pro 85.0 vs 85.0、AIME 2025 88.4→89.3、GPQA-Diamond 80.7→79.9、HLE 21.7→19.8、Codeforces 2046→2121）；成本曲线"基于 H800 集群实际部署服务的 benchmark 估算" — [DeepSeek-V3.2-Exp README](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/README.md)（A）
- DSA 的开源 kernel 分工（官方指引）：**可读性/研究用途看 TileLang（`examples/deepseek_v32`）；高性能 CUDA 看 DeepGEMM（indexer logit kernel，含 paged 版本）与 FlashMLA（稀疏 attention）** — [同上](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/README.md)（A）
- NSA（2025-02）：动态分层稀疏 = 粗粒度 token 压缩 + 细粒度 token 选择；两项关键创新是**算术强度平衡的算法设计 + 面向现代硬件的实现优化**，以及端到端可训练；在 64k 序列上于 decode、前向、反向三阶段均有显著加速 — [NSA, arXiv 2502.11089 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/18-Feb-2025/AI/README.md)（A，摘要原文）
- MoBA（Moonshot）：`moba_efficient` 是"production-ready"实现，相对 `moba_naive` **最多 40×**（32K 序列、1 head、MoBA block 2048、topk 3）；**kernel 实现依赖 `flash-attn==2.6.3`**（即未跟进 FA3/FA4）；给了 1M 上下文的 needle-in-a-haystack 评测 — [MoBA README](https://github.com/MoonshotAI/MoBA/blob/master/README.md)（A）。另：FLA 已于 2026-04 收录 MoBA 实现并支持 **FlashMoBA** 后端 — [FLA README](https://github.com/fla-org/flash-linear-attention/blob/main/README.md)（A）

**线性注意力的 kernel 成熟度**

- FLA（flash-linear-attention）是事实上的"线性/稀疏序列算子集散地"：声明"所有实现与平台无关，并在 **NVIDIA、AMD、Intel 硬件上验证**"。时间线中与成熟度直接相关的几条：**GDN 被 Qwen3-Next 集成（2025-09）**；KDA 加入（2025-10）；NSA 实现（2025-02）；**KDA/GDN 的 Context Parallel 支持（2026-03）**；TileLang 后端用于部分 kernel（2026-04）；**AttnRes 的 Gluon 后端（2026-07）**；**GDN 的 FlashQLA 后端（2026-07）** — [FLA README](https://github.com/fla-org/flash-linear-attention/blob/main/README.md)（A）
- FlashQLA（Qwen 团队）：基于 **TileLang** 的线性注意力 kernel 库，融合 GDN chunked prefill 的前后向；支持 SM90/100/103/120/121（Hopper + Blackwell），需 CUDA ≥12.8、PyTorch ≥2.8；相对 FLA 的 Triton kernel **前向约 2–3×、反向约 2×**；v0.1.3 为 2026-09 — [FlashQLA](https://github.com/QwenLM/FlashQLA)（B，未核实；页面经摘要抽取）
- Kimi Linear：KDA 是"带更细粒度门控的 Gated DeltaNet 变体"，**3:1 的 KDA:全局 MLA 混合**；KV cache 用量降低最多 **75%**，1M 上下文 decode 吞吐最多 **6×**；具体数字：MMLU-Pro(4k) 51.0 与全注意力速度相当，RULER(128k) 84.3 且 **3.98×** 加速，1M tokens 下 TPOT **1.84ms vs MLA 的 11.48ms（6.3×）**；**KDA kernel 开源在 FLA**，并提供 vLLM 实现 — [Kimi-Linear README](https://github.com/MoonshotAI/Kimi-Linear/blob/master/README.md) 与 [技术报告](https://github.com/MoonshotAI/Kimi-Linear/blob/master/tech_report.pdf)（A）
- MiniMax-M1：hybrid MoE + lightning attention，每 7 个 transnormer block 配 1 个 softmax attention block；相对 DeepSeek R1，**64K 生成长度下 FLOPs < 50%，100K 下约 25%**；全 RL 训练在 **512 H800 上三周**完成 — [MiniMax-M1 技术报告](https://github.com/MiniMax-AI/MiniMax-M1/blob/main/MiniMax_M1_tech_report.pdf)（A，PDF 抽取）
- 引擎侧的线性注意力落地细节（很能说明 kernel 成熟度的真实状态）：vLLM 支持 Qwen3-Next 时**直接集成 FLA 的 Triton kernel**，并用 hybrid KV cache manager 同时管理线性层与全注意力层的状态；vLLM 会**自动调整全注意力层的"逻辑" block size，使两类层的状态占用相同的"物理"显存**，从而能用简单的分页管理。关键坑：**"FLA 基于 Triton，Triton kernel 的 launch 有显著 CPU 开销，对 decode-only batch 影响尤其大，因此 vLLM 默认开启 full CUDA graph 模式"** — [vLLM Qwen3-Next 博客](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2025-09-11-qwen3-next.md)（A，2025-09-11）

**推荐模型专用算子：jagged / 大 beam / 长序列稀疏**

- HSTU attention 的两条生产路径：(1) Meta `generative-recommenders` 的 `ops/cpp/hstu_attention` 基于 **FlashAttention V3**，"在 H100 上达到 state-of-the-art 效率"；`ops/triton` 提供 Triton kernel；HSTU Ultra attention 的 Triton vs PyTorch 前向为 **2.02×–2.32×**（H100 96GB，batch 1，1980MHz，700W，仅 attention，Q/K/V 预先 BF16）— [generative-recommenders README](https://github.com/facebookresearch/generative-recommenders/blob/main/README.md)（A）。(2) NVIDIA recsys-examples 的 **CUTLASS 版 HSTU attention kernel（`fbgemm_gpu_hstu`）**，有专门的 benchmark 扫描 TFLOPS/MFU（MFU 基准用 **GB200 每卡 2500 TFLOPS、H100 每卡 989 TFLOPS 的 dense BF16 Tensor Core 峰值**）；v26.06 更新 FBGEMM 以支持 **Blackwell HSTU attention** — [recsys-examples HSTU 训练 benchmark](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/README.md) 与 [README](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）
- HSTU 推理侧实测：KV cache + CUDA graph 带来 **1.3×–2.6×**（batch 1–8）；4096 token 输入中 3968 已缓存时，**HSTU block 加速 3×–20×（无候选）/ 3×–8×（每序列额外 256 候选）**；**B200 上用 HSTU Blackwell CuTeDSL kernel** 时为 **3.3×–7.7×**（256 候选，batch 1→8）。限制：B200 benchmark 的 KV cache page size 为 128 token，attention head dim 为 128，"受当前 kernel 实现限制" — [recsys-examples HSTU 推理 benchmark](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference/benchmark/README.md)（A）
- **大 beam decode 专用算子（对 SID-GR / 生成式检索最关键）**：NVIDIA `gr_decode_atten` 用 **CuTe DSL** 实现，支持 SM8x（A100/L40/L20）、SM90（H100/H800/H20）、SM100（B200/B300）、SM120（RTX PRO6000）。核心洞察是 beam search 的 KV 分裂成两类访问模式：**Context KV**（prefill 产生、所有 beam 共享、稠密顺序访问、长度数千）与 **Beam KV**（decode 产生、每 beam 独立、TopK gather 不规则访问、长度 = `decode_nums`），"单个 kernel 无法高效处理两者"。因此提供两条路径：3-kernel 流水（K1 context attention 用 Tensor Core MMA + split-KV；K2 beam sparse attention 用 **CUDA Core FMA** + topK gather；K3 做 log-sum-exp 合并）与 fused kernel（把 K1/K2 合并，beam 稀疏阶段直接在 MMA accumulator 上跑 CUDA core FMA，共享同一 softmax 状态）。**路径默认值按架构不同：SM8x/SM90/SM120 默认 fused+split-KV；SM100 默认 3-kernel，且 fused beam 在 SM100 上不可用** — [gr_decode_atten README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/gr_decode_atten/README.md)（A）
- **大 beam 推理的框架缺口（官方自述）**：SID-GR 工作负载是"长 context + 短 decode + 大 beam（如 128 或 256）"，与 chat LLM 完全不同。NVIDIA 的判断："**vLLM 没有稳定的生产级 beam search 服务路径**（用户常在业务逻辑里反复调用 vLLM 自己实现 beam search）；**TensorRT-LLM 在该路径上不原生暴露 logprobs**，且大 beam 会造成显存压力，其 decode attention 与后处理 kernel 也没有针对 SID-GR 的短 decode 做特化；**SGLang 是目前最可用的开源基线，但大 beam 支持仍在一个 feature PR 中、未合入 upstream main**" — [SID-GR Inference README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)（A）
- Meta WHALE（2026）的 Triton 注意力定制：在融合模块里用**融合 Triton kernel** 实现 cross-branch attention，并做了三项定制：(1) **令 K=V 共享张量**，kernel 可复用已加载的 key 作为 value，减少内存流量（因为这些 kernel 是 memory-bound）；(2) 适配**极不对称的形状**（约 64 个 query token 对约 15,000 的用户历史），反向对 KV 的处理方式特别敏感，采用 FlashAttention 的反向 schedule；(3) 通过 shape-aware kernel tuning、编译图执行、无同步的 shape 处理来降低训练中的不规则张量形状与 kernel launch 开销；推理侧进一步 AOT 编译并按形状调优 — [WHALE](https://github.com/guyulongcs/Awesome-Deep-Learning-Papers-for-Search-Recommendation-Advertising/blob/master/04_Ranking/LLM_Ranking/2026%20(Meta)%20(Arxiv)%20%5BWHALE%5D%20WHALE%20-%20A%20Scalable%20Unified%20Model%20for%20Recommendation%20with%20Wukong-HSTU%20Architecture.pdf)（A，PDF 抽取）
- Meituan MTGR：开发了"精心设计的、类似 FlashAttention 的 **CUTLASS 版 attention kernel**"来加速训练 — [MTGR](https://github.com/guyulongcs/Awesome-Deep-Learning-Papers-for-Search-Recommendation-Advertising/blob/master/04_Ranking/LLM_Ranking/2025%20(Meituan)%20(Arxiv)%20%5BMTGR%5D%20MTGR%20-%20Industrial-Scale%20Generative%20Recommendation%20Framework%20in%20Meituan.pdf)（A，PDF 抽取）
- 稀疏注意力的"容量瓶颈"而非"算力瓶颈"：SGLang HiSparse 指出 top-k 稀疏注意力并不消除显存容量瓶颈——全上下文 KV 仍要留在 HBM 才能快速访问，即使每步只有一小部分 entry 活跃，于是**稀疏注意力往往是 capacity-bound 而不是 compute-bound**。HiSparse 把不活跃 KV 主动 offload 到主机内存并在 HBM 保留热 device buffer，核心是一个 CUDA kernel 同时做（1）识别 device buffer 中的 top-k miss（2）按 LRU 选驱逐候选（3）更新页表并从 host 取数。GLM-5.1-FP8、32k 输入/8k 输出、8×H200 PD 混部下，**256 并发时吞吐 >3× 基线**；但低并发下有额外开销（稀疏 KV 加载的 I/O 大于省下的显存收益） — [SGLang HiSparse 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-04-10-sglang-hisparse.md)（A，2026-04-10）

### Inferences

- **FA4 的三项手段对推荐模型的 attention kernel 同样适用**：HSTU/SLA 这类 kernel 在 Blackwell 上会遇到同一个非对称瓶颈（MMA 翻倍、SFU 不变），而推荐模型的 softmax 替代（HSTU 用 SiLU/pointwise gating）本身就比 softmax 更省 SFU，**理论上在 Blackwell 上比标准 attention 更容易打满 Tensor Core**——这是推荐模型相对 LLM 的一个结构性优势，但目前没有公开数据验证。
- **"KV entry 必须被多个 query 共享才有 kernel 效率"是 DSA 最可迁移的一条设计律**。推荐场景里，大 beam decode 的 Context KV 天然被所有 beam 共享（故可用 Tensor Core），而 Beam KV 每 beam 独立（故退化到 CUDA Core FMA）。这解释了为什么 `gr_decode_atten` 必须分成两个 kernel，也意味着**"增大 beam 宽度"的边际成本主要落在 Beam KV 这条 CUDA-core 路径上**。
- MoBA 仍钉在 `flash-attn==2.6.3`、Flux 的构建脚本只列 sm80/89/90，而 FlashMLA 已经砍掉 Hopper——**同一时间点上，各家稀疏/MoE 算子的硬件代际差距可达两代**。选型时"是否跟进 Blackwell"比"论文里的加速比"更能预测可用性。

### Gaps

- **FlexAttention 没有取到一手材料**（PyTorch 文档站与博客不可达，仓库文档中未找到 FlexAttention 的性能章节）。只能确认 vLLM/SGLang 的注意力后端选择里更多提到 FA2/FA3/FlashInfer/TRT-LLM-gen 与 Triton 后端，未见 FlexAttention 作为生产后端的证据。
- **TorchRec jagged 算子的定量收益未取到**：TorchRec 文档（`docs/source/*.rst`）只有 API 索引，没有 jagged tensor 算子的 benchmark；recsys-examples 提到"为 jagged tensor concat 定制 CUDA 算子"（v25.06）与"TorchRec jagged tensors"用于 SID-GR，但无加速数字。
- FA4 反向在 Blackwell 上的完成度（是否全 head_dim/全精度可用）未能从仓库 README 确认，只能看到 `flash_bwd_sm100.py`、`flash_bwd_mla_*_sm100.py` 存在。
- DeepSeek V4/V4.1 的 MegaAttention / DeepSelect kernel 只在引擎博客中被提及为"已集成 DeepSeek 新发布的 kernel"，没有找到这些 kernel 自身的公开性能表。

## Q3. MoE 算子与通信：DeepEP、DeepGEMM 分组 GEMM、EPLB、计算-通信重叠、Blackwell NVLink 域

### Takeaway

MoE 的算子层在 2026 年发生了两件结构性变化：**(1) 通信库从"NVSHMEM + 自动调参"转向"NCCL Gin device API + 解析式 SM/QP 计算"（DeepEP V2/V2.5），并且 NVSHMEM 已被完全移除依赖；(2) "分开的 dispatch → grouped GEMM → combine" 被融合成单个 megakernel（DeepGEMM Mega MoE），在 NVLink 域内把通信与 Tensor Core 计算重叠起来**。字节的工作（Flux → COMET → Triton-distributed/FlashComm）是这条路线的另一支，且 COMET 有明确的"万卡级生产部署、节省数百万 GPU 小时"自述。EP 负载均衡从静态（EPLB 冗余专家 + 打包）走向 dispatch-time 动态（Waterfill / LPLB），但单项收益已降到 1%–7% 量级。

### Cited Findings

**DeepEP：当前能力与硬性约束**

- V2.5 的接口与机制：高吞吐与低延迟 API **统一到单个 `EPBuffer`**，带 grouped expert GEMM 所需的 expanded layout；**NCCL Gin 后端**（轻量 device-side 通信 API，可复用已有 NCCL communicator）；**SM 与 QP 数量解析式计算，不再需要 auto-tuning**；支持 FP8 dispatch；新增 `lb_prefetch_weights` / `lb_reduce_grads` 两个原语，在专家计算前通过 NVLink 预取原始专家权重与量化 scale，反向时把冗余专家的 FP32 梯度累加回原专家（支撑 MoonEP 与 UltraEP 的专家复制方案）；Engram（RDMA 远程内存访问）、PP、bucket collectives（all-gather / reduce-scatter / all-reduce，用于 CP 与 DP）为实验特性；**V1 及其 NVSHMEM 后端被完全移除，NVSHMEM 不再是依赖** — [DeepEP README](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）
- 环境门槛（硬约束，选型必读）：Linux、Python ≥3.10、**NVIDIA Hopper 或更新**、**CUDA Toolkit ≥13.1**、C++20 + `std::format`、**PyTorch ≥2.10**、**NCCL ≥2.32.3**、节点内 NVLink、跨节点 RDMA；**EP dispatch/combine 需要 GPU SM，不支持 zero-SM 的纯 RDMA EP**；Engram 需要提供 `ncclGinOptFlagsWarpGet` 的 NCCL 构建 — [同上](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）
- 通信-计算重叠的 API 形态：`defer_epilogue=True` + `async_with_compute_stream=True` 让 dispatch/combine 直接返回 `EventOverlap`，`.wait()` 时才在当前 stream 上执行 deferred epilogue 并返回结果；`previous_event`（由 `_buffer.capture()` 得到）用于声明输入就绪时点；`do_cpu_sync=True` 得到精确输出尺寸与 CPU 侧专家计数（训练/prefill 常用），`False` 时用 GPU 侧 receive count（decode），此时专家 GEMM 必须用 `handle.psum_num_recv_tokens_per_expert` 识别有效区间 — [同上](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）
- **生态分叉说明了 MoE 通信是当前最拥挤的优化战场**（官方 README 列出的实验分支与社区 fork）：`hybrid-EP`（用 TMA 指令把 SM 占用降到最低、支持更大 NVLink 域、单 batch 场景下细粒度通信-计算重叠、PCIe kernel 支持无 NVLink 环境、**NVFP4 数据类型支持**）；`zero-copy`（腾讯网络平台部，去掉 PyTorch 张量与通信 buffer 之间的拷贝，显著降低 normal kernel 的 SM 占用）；`AntGroup-Opt` 系列（蚂蚁网络平台部：`Normal-SMFree` 把 RDMA 路径从 SM 解耦、`LL-SBO` 用信号机制把 Down GEMM 与 Combine Send 重叠、`LL-Layered` 用 rail-optimized 转发与数据合并降低跨节点 LL 延迟）；`Mori-EP`（AMD ROCm，低延迟模式）；`nvDev`（**Compute Fabric Transport (CFT)**，小 token 规模下更好的延迟）；`uccl/uccl-ep`（异构 GPU 与 NIC：NVIDIA+AMD、EFA/Broadcom/CX7）；`DeepXTrace`（蚂蚁，慢 rank 定位） — [同上](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）
- 网络侧的工程建议（可直接抄）：用 InfiniBand Virtual Lane 做流量隔离（EP 流量与其他流量分开，通过 buffer 的 `sl_idx` 选 service level，优先级 `EP_OVERRIDE_RDMA_SL` > `sl_idx` > `EP_DEFAULT_RDMA_SL` > NCCL 默认）；**无论负载如何都建议开 adaptive routing**（尽管会引入额外延迟）；最大带宽负载建议在验证 fabric 配置后**关闭拥塞控制**；若硬件支持，用 `mlxconfig set PCI_ATOMIC_MODE=4` 提升 RDMA atomic 性能 — [同上](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）

**DeepGEMM：分组 GEMM 与 Mega MoE 融合**

- 分组 GEMM 的三种 layout（与 MoE 的三个阶段一一对应）：**contiguous 布局只在 M 轴分组，N 与 K 固定**（专为"所有专家同形状"的 MoE 设计），用于训练前向与推理 prefill，每个专家段必须按 GEMM M block 对齐（`get_mk_alignment_for_contiguous_layout()`）；**K 轴分组**（M、N 固定）用于 MoE 权重反向；**masked 布局**用于 decode 阶段开启 CUDA graph 且 CPU 不知道每个专家收到多少 token 时，传 mask 张量只算有效部分（典型用法是把 DeepEP 低延迟 kernel 的输出直接喂进来） — [DeepGEMM README](https://github.com/deepseek-ai/DeepGEMM/blob/main/README.md)（A）
- **Mega MoE（2026-04-16 引入）**：把 **EP dispatch + linear 1 + linear 2（FP8×FP4 或 FP8×FP8）+ SwiGLU + EP combine 融合进单个 megakernel**，重叠 NVLink 通信与 Tensor Core 计算；需要多进程启动 + 对称内存（PyTorch ≥2.9）；提供 `transform_weights_for_mega_moe` 做权重 layout 变换，以及 `localize()` 把权重放入 locality domain（2026-09-30 的 #462 加入 locality domain 特性） — [同上](https://github.com/deepseek-ai/DeepGEMM/blob/main/README.md)（A）
- Mega MoE 的 benchmark（EP8，每 rank token 数，8 rank 平均）：V4-Flash（256 专家 top-6，hidden 4096，inter 2048）在 1 / 512 / 8192 / 32768 tok/rank 下分别 56.5us / 146.5us / 1283.1us / 4855.5us，TFLOPS 5 / 1056 / 1928 / 2038，**相对"legacy" 1.96× / 1.73× / 1.56× / 1.62×**；V4-Pro（384 专家 top-6，hidden 7168，inter 3072）为 108.1us / 369.6us / 2818.5us / 10655.2us，TFLOPS 7 / 1098 / 2304 / 2438，加速 **1.61× / 1.54× / 1.50× / 1.54×** — [DeepGEMM PR #316](https://github.com/deepseek-ai/DeepGEMM/pull/316)（B，未核实；PR 页面经摘要抽取，且 PR 未注明具体 GPU 型号，评论称面向 SM100+ 并使用 TMEM；"legacy" 基线未在页面定义）
- 2026-09-10 公开版本（PR #432）的增量与数字：**Mega Gate**（把 routing GEMM 与多个 MoE routing 操作融进一个 kernel）**30–75% 加速**；**Mega mHC**（把多个 Hyper-Connection 操作与 RMSNorm 融进一个 kernel）**45–85%**；**MoE 反向 GEMM 约 20%**；V4.1 的 Mega MoE 低延迟约 **15%**、高吞吐约 **4%**；Sparse Indexer 的吞吐"接近 Lightning Indexer"。**破坏性变更（对 RL 极重要）：此前版本完全确定性且 batch-invariant，本次引入 `use_deterministic_algorithms()` 且默认 `False`，需要确定性行为（如 RL）必须显式设为 `True`** — [DeepGEMM PR #432](https://github.com/deepseek-ai/DeepGEMM/pull/432)（B，未核实；PR 页面经摘要抽取）
- 跨硬件：**DeepGEMM-Ascend**（2026-09-30）、**DeepEP-Ascend**（同 API、"昇腾 950 NPU 上全性能"） — [DeepGEMM README](https://github.com/deepseek-ai/DeepGEMM/blob/main/README.md) / [DeepEP README](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)（A）

**EPLB 与动态负载均衡**

- EPLB 的两种策略：当节点数整除专家组数时用**分层策略**（先把专家组均匀装到节点保证节点间均衡 → 节点内复制专家 → 把副本装到各 GPU），利用 DeepSeek-V3 的 group-limited expert routing 降低跨节点流量，"**可用于 prefill 阶段、EP size 较小时**"；其他情况用**全局策略**（无视专家组全局复制再打包），"**可用于 decode 阶段、EP size 较大时**"。负载预测方法明确声明在 repo 范围之外，常见做法是历史统计的滑动平均 — [EPLB README](https://github.com/deepseek-ai/EPLB/blob/main/README.md)（A）
- dispatch-time 动态均衡的实测增量（NVIDIA 团队在 SGLang 上的工作，2026-06-26）：**Waterfill**（轻量共享专家负载均衡，把 shared expert 也经 DeepEP 分发并分配到较空闲的 rank）在两台 Hopper 节点的 DeepSeek-V3/R1 式负载上，MMLU/GPQA/GSM8K 上总吞吐 **+1.48% 到 +4.66%**；DeepSeek V4 上最佳测点从 **49,253 tok/s 提升到 51,677 tok/s（+4.92%）**。**LPLB**（基于线性规划的冗余专家副本均衡，逐层求解 dispatch 优化问题）在同样两节点 + 冗余 EPLB 放置下，总吞吐 **+0.84% 到 +7.34%** — [SGLang Waterfill & LPLB 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-06-26-waterfill-lplb.md)（A）
- 为什么静态放置不够（机制说明）：routed expert 稀疏（不同 token 选不同专家，负载取决于 router 分布）、shared expert 稠密（每 token 都要过，全 batch 都有负载）、EPLB 引入的冗余副本为 dispatch-time 均衡提供了"不改变模型逻辑专家选择"的调整空间；"静态放置有用但无法消除全部运行时不均衡，单个 batch 仍可能集中在少数专家或 rank 上" — [同上](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-06-26-waterfill-lplb.md)（A）

**计算-通信重叠：DualPipe 与字节系工作**

- DualPipe 的气泡公式（同 PP stage 数下对比）：1F1B 为 `(PP-1)(F+B)`、ZB1P 为 `(PP-1)(F+B-2W)`、**DualPipe 与 DualPipeV 均为 `(PP/2-1)(F&B+B-3W)`**；代价是每设备参数 **2×**、激活 `PP+1`；**DualPipeV 用 "cut-in-half" 过程把设备数降到 `PP/2`**（源自 Sea AI Lab 的 V 形 schedule）。实际应用需要自己实现定制的 `overlapped_forward_backward` — [DualPipe README](https://github.com/deepseek-ai/DualPipe/blob/main/README.md)（A）
- **COMET（字节 Seed，MLSys 2025）**："MoE 层的跨设备通信在常用模型与框架下可占整个模型执行时间的 **47%**"；粗粒度重叠方案会明显损害计算效率且延迟隐藏次优；COMET 用数据依赖分析 + 任务重排做精确的细粒度重叠，并用自适应负载分配消除细粒度通信瓶颈。结果：**单个 MoE 层加速 1.96×，端到端平均 1.71×**；"**COMET 已在万卡级 GPU 集群的生产环境中采用，节省了数百万 GPU 小时**" — [COMET, arXiv 2502.19811 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/28-Feb-2025/AI/README.md)（A，摘要原文）；代码在 [bytedance/flux](https://github.com/bytedance/flux)（2025-03-10 发布）
- **Flux（字节）的公开数字**（注意基线说明）：dense MLP、L20 8 卡 TP8、M=4096/K=12288/N=49152：AG+GEMM 从 torch 的 16.946ms（GEMM 5.746 + Comm 11.200）降到 **5.903ms**（GEMM 5.316 + Comm **0.587**）；GEMM+RS 从 17.664ms 降到 **5.730ms**（Comm 从 12.273 降到 **0.341**）。MoE MLP、M=8192/K=8192/N=8192/TP8/EP1/32 专家 top-4：**H800 上 layer0 4.702 → 1.146ms，layer1 10.452 → 1.863ms**；L20 上 layer0 26.792 → 7.813ms，layer1 42.092 → 7.976ms。**官方明确声明 "torch 实现只保证功能、未针对速度优化"，更强基线请看 COMET 论文** — [Flux performance.md](https://github.com/bytedance/flux/blob/main/docs/performance.md)（A）
- **Flux 的硬件覆盖提示其代际**：构建脚本只提供 `--arch 80`（Ampere）、`89`（Ada）、`90`（Hopper）；依赖 CUTLASS 4.0.0、NVSHMEM 3.2.5/3.3.9；预编译 wheel 仅覆盖 torch 2.4/2.5/2.6 + CUDA 12.4；README 的 News 最后一条是 2025-03-10 — [Flux README](https://github.com/bytedance/flux/blob/main/README.md)（A）
- **Triton-distributed（字节 Seed）是 Flux 之后的主线**：定位"面向计算-通信重叠的分布式编译器，基于 OpenAI Triton"，声称"开发者能写出与高度优化库（含 NVIDIA Distributed-GEMM 与 FLUX）相当的高效 kernel"，主要面向 NVIDIA 与 AMD GPU。时间线：**2026-08-17 升级到 Triton 3.7，改为对上游 stock Triton 的 out-of-tree plugin**（Triton 3.4 线留在 `triton-v3.4` 分支，**Ascend 尚未进入 3.7 plugin 构建路径**）；2026-09-17 **FlashComm 融合 MXFP8 节点内 dispatch——EP 流量可以发送打包的 FP8 而非 BF16，并对融合路径与预量化路径做 bitwise 校验**；2026-09-01 **FlashComm 固定 buffer 分块 EP——dispatch 与 combine 在固定大小 buffer 上分块进行，EP 峰值显存不再随最坏情况 token 数增长**；2026-08-07 Hopper 与 **Blackwell** 上的融合跨节点 CuTeDSL dispatch/combine；2026-06-30 Hopper 上融合节点内 CuTeDSL dispatch/combine（dispatch+FC1 与 FC2+combine）；2025-12-22 低延迟模式、token saving、Mega-EP；2025-09-03 **Intra-Kernel Profiler**；2025-08-13 MegaTritonKernel 与 Qwen3 TP demo（H20/H800） — [Triton-distributed README](https://github.com/ByteDance-Seed/Triton-distributed/blob/main/README.md)（A）

**Blackwell NVLink 域对 EP 的影响**

- SGLang 在 GB200 NVL72 上的首轮改造（2025-06-16）说明了 NVLink 域变大后需要改什么：**Blackwell DeepEP 通过把远端 GPU 显存映射到本地虚拟地址空间来支持"NVLink-only"环境**，并顺手把 DeepEP 性能提升约 15%；**Blackwell DeepGEMM 重写以用新的 UMMA**；FlashInfer Blackwell FMHA 重写；**Blackwell CUTLASS MLA 用 UMMA 并启用 2-SM cluster 模式的 TMA，降低 KV cache 的 L2 读流量**；Mooncake 传输引擎也用类似 DeepEP 的手段支持 NVLink。结果：decode **7,583 tokens/s/GPU，相对 H100 每卡 2.7×** — [SGLang GB200 Part I](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-06-16-gb200-part-1.md)（A）
- GB200 上重叠策略要换（关键判断）："前代硬件上用的 two-batch overlap 在通信带宽大幅提升后可能不再最合适，因此我们采用**更细粒度的重叠方式**——把 combine 通信与 down GEMM 以及 shared experts 同时重叠。在 GEMM 中实现信号时，用带 release 语义的 atomic 指令，放在 TMA store wait 之后足够多步的位置；并使用 `cp.async.bulk.wait_group` PTX 指令（去掉 `.read` 后缀的那一族）" — [SGLang GB200 Part II](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-09-25-gb200-part-2.md)（A）
- GB200 上也出现了"反向 scaling"的手段：**Scaling Down by Offloading**——显存不够时利用 GB200 的 CPU-GPU 900GB/s 双向带宽把权重 offload 到主机内存并预取，降低通信开销；"当收益超过计算变慢时性能更好，因此最优规模与当前使用的计算/通信 kernel 及模型配置有关"；还能缩小故障爆炸半径与减少等最慢 rank 的时间 — [同上](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-09-25-gb200-part-2.md)（A）
- vLLM 在 GB200 上的 wide-EP 数字（2026-02-03，Meta + NVIDIA）：DeepSeek-style MoE（2K 输入 / 2K 输出）达 **26.2K prefill TPGS 与 10.1K decode TPGS**（4 个 prefill 实例各 2 卡 + 1 个 decode 实例 8 卡，DP+EP 混合）；驱动因素包括 **NVFP4 GEMM、FP8 GEMM、NVFP4 MoE dispatch**、kernel 融合（**RoPE+Quant+Q write、RoPE+Quant、Concat K**）、prefill 侧权重 offload 降规模、减少 chunking 开销；对照其此前 H200 wide-EP 的 2.2k tok/s/H200 decode — [vLLM WideEP on Blackwell Part I](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-02-03-dsr1-gb200-part1.md)（A）
- GB300 的 EP decode 扩展性：**1.5× 更大 HBM（288 vs 192 GB）带来 1.6× 更高的有效 decode batch（40 vs 24 req/GPU）**，DEP8 下可扩展到 288 并发且极少 retraction；长上下文（128K/8K）峰值 **226.2 TPS/GPU，相对 GB200 1.53×**；匹配延迟条件下 GB300 比 GB200 高 **1.38×–1.58× TPS/GPU**；**attention softmax 关键指令的 SFU 吞吐提升 2× 带来 FMHA kernel 1.35× 加速** — [SGLang GB300 长上下文博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-02-19-gb300-longctx.md)（A，NVIDIA + SGLang）
- Megatron-Core 推理侧的 MoE 算子现状：**NVLS switch-multicast token dispatcher** 加上为多节点 NVLink 优化的 allgatherv dispatcher；**可选 grouped-GEMM 后端（vLLM / torch / FlashInfer）**；expert router replay；shared-expert 与 latent MoE 的重叠；MXFP8 权重量化推理路径（`--transformer-impl inference_optimized --fp8-recipe mxfp8`，可按参数选择 MXFP8 而未匹配层保持 BF16） — [Megatron mcore-inference-user-guide.md](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/mcore-inference-user-guide.md)（A）
- MoE 推理 kernel 瓶颈的一个清晰案例（W4A16）：Novita 开源的 **Chord** W4A16 MoE CUDA 算子（BF16 激活、INT4 权重、group-32 scale），相对公开 Humming 的对应路径：**H200 EP8 prefill 1.11–1.20×、H200 TP8 单实例 1.17–1.33×、H200 EP8 decode 1.16–1.24×（down 阶段达 1.31×）、B300 EP8 decode 1.81–2.15×（对照 Humming 未调优默认配置，因其无 SM100/SM103 调优表）**。核心洞察："**一个 W4A16 MoE kernel 不可能适配所有请求。每专家的 routed token 数在 prefill 与 decode 之间差几个数量级，而决定哪种 schedule 胜出的正是这个量，而不是总 token 数**" — [vLLM × Novita Chord 博客](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-09-15-novita-chord-w4a16-moe.md)（A，2026-09-15，明确标注为 kernel 级测量而非端到端承诺）

### Inferences

- **MoE 算子的优化重心已从"把通信藏起来"转向"把通信变小 + 把 SM 还给计算"**。三条独立证据指向同一方向：DeepEP 的 `zero-copy`/`Normal-SMFree`/`hybrid-EP(TMA)` 分支都在降低通信 kernel 的 SM 占用；FlashComm 把 EP 流量改成 MXFP8 而非 BF16；SGLang 在 GB200 上把 NVFP4 dispatch 的"通信量减半"列为 NVFP4 的三项收益之一。在 NVLink 域变大（NVL72）之后，带宽不再是主要矛盾，**SM 争用与量化后的字节数**才是。
- **DeepGEMM 把确定性从默认开改成默认关**（PR #432）是一个容易被忽视但影响很大的变更：对 RL / on-policy 训练、以及任何需要 train-infer bitwise 一致的流程，升级 DeepGEMM 后必须显式开 `use_deterministic_algorithms(True)`，否则会引入新的 train-infer mismatch。
- **字节公开的算子/通信工作有清晰的代际演进**：Flux（2024，CUTLASS/NVSHMEM，sm80/89/90）→ COMET（2025-02，细粒度重叠、万卡生产、1.96×/1.71×）→ Triton-distributed/FlashComm（2025-2026，Triton plugin 化 + CuTeDSL 融合 dispatch/combine + MXFP8 通信 + 固定 buffer 分块 EP，覆盖 Hopper/Blackwell/AMD/Ascend）。**对 TikTok 团队而言，Flux 应视为历史参考，Triton-distributed 才是当前活跃的内部同源路线**。
- EPLB 类静态均衡 + dispatch-time 均衡的收益已进入"个位数百分比"区间（Waterfill 1.5–4.7%、LPLB 0.8–7.3%），说明**MoE 负载均衡这条线的低垂果实已被摘完**；下一轮增量更可能来自 Mega MoE 式的融合（1.5–1.96×）与通信量化（NVFP4 dispatch）。

### Gaps

- MegaScale-MoE 的 MFU 数字与通信压缩的具体精度格式未能取证（arXiv 不可达，搜索摘要未含 MFU）。
- Mega MoE benchmark 的具体 GPU 型号与 "legacy" 基线定义未在公开 PR 页面说明（只有第三方评论推断为 SM100+/TMEM），因此 1.5–1.96× 不能直接当作"相对 DeepEP+DeepGEMM 分离实现"的加速比。
- Flux 是否有 Blackwell（sm100）支持未找到明确声明（构建脚本只到 sm90），但也没有"不支持"的官方说明。
- COMET 在字节生产中的具体模型/规模细节仅有论文中的概述（"万卡级"、"数百万 GPU 小时"），无逐项分解。

## Q4. 编译器与 kernel DSL：torch.compile / Triton / TileLang / ThunderKittens / CUTLASS 4 CuTe DSL / cuTile / Mojo / Pallas / Ascend C

### Takeaway

2026 年的格局是**"Python 里的 CuTe DSL"赢得了前沿 kernel 的首发权**（FA4、FlashMLA 的融合 kernel、FlashInfer 的 Blackwell kernel、NVIDIA 的 beam-decode kernel 都是 CuTe DSL），**Triton 则赢得了可移植性与跨厂商的生产面**（vLLM 的 Triton attention 后端、FLA 的全部线性注意力 kernel、字节的 Triton-distributed）。TileLang 成了"研究可读实现 + 新硬件（昇腾 950、Metal 4）快速覆盖"的那一层，并被 DeepSeek 官方指定为 V3.2 kernel 的可读参考。cuTile 还很早（**tileiras 13.2 仍不支持 Hopper**）。torch.compile 在推理引擎里已是基础设施而非加速器。

### Cited Findings

**torch.compile / Inductor 的生产成熟度**

- vLLM 的定位陈述最能说明成熟度："对 vLLM 来说，torch.compile 不只是性能增强，**它是一个核心组件，把优化责任从模型开发者转移给编译器**。优化在编译期施加，不需要改模型定义，从而实现关注点分离并达到最大性能。" PyTorch 官方 TorchBench 显示 **80+ 模型上 1.8–2× 的几何平均加速** — [vLLM torch.compile 介绍](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2025-08-20-torch-compile.md)（A，2025-08-20，Red Hat + Meta + 清华）

**Triton 3.x 与 Blackwell**

- Triton 版本时间线：3.3.0（2025-04-09）、3.4.0（2025-07-30）、3.5.0（2025-10-13）、3.5.1（2025-11-11）、3.6.0（2026-01-20）、3.7.0（2026-05-07）、3.7.1（2026-06-17）、**3.8.0（2026-08-28）** — [triton PyPI](https://pypi.org/project/triton/)（B，未核实；页面经摘要抽取）

- HipKittens（AMD 侧）：支持 CDNA3 与 CDNA4，仓库含 **CDNA5（MI400/MI450，gfx1250）** 的单元测试；结论是"核心 tile 与 bulk compute 接口能从 TK 迁移到 HK，但**内存访问模式、计算与内存的调度、chiplet 架构下的 thread block 排序决策不同**"；两种重叠模式（8-wave ping pong 与 4-wave interleave）"在各 kernel 中反复出现"。生态里程碑：**MLSys 2026 接收（2026-01）；2026-03 成为 AITER 后端（首批 HK kernel 合入 AITER）；2026-06 成为 AMD Transformer Engine 后端；2026-09 支持 MI455 Helios** — [HipKittens README](https://github.com/HazyResearch/HipKittens/blob/main/README.md)（A，论文 arXiv 2511.08083）

**CUTLASS 4 / CuTe DSL**

- 版本与成熟度：`nvidia-cutlass-dsl` **4.0.0 首个稳定版 2025-06-06**，到 **4.8.0（2026-09-21）**；PyPI 页面称 **CuTe DSL "目前处于 public beta，预计 2026 年夏季出 beta"**；定位是"Python 原生接口写高性能 CUDA kernel，不牺牲性能"，首发的 CuTe DSL 是"低层模型，暴露 layout、tensor、硬件 atom 以及对 thread 与数据层级的控制"，面向 Ampere/Hopper/Blackwell 的 Tensor Core — [nvidia-cutlass-dsl PyPI](https://pypi.org/project/nvidia-cutlass-dsl/)（B，未核实；页面经摘要抽取）
- CUTLASS 4.8.0（2026-09-17）的内容揭示了下一代硬件的数值与容量变化：**初步 Rubin（sm107）支持**——更高吞吐的 **FP8（MMA_K=64）与 FP4（MMA_K=128）** Tensor Core MMA 指令、**B collector reuse**、**TMEM 从 512 COL 扩到 576 COL**、**更大的 shared memory 分配（328KB）**、混合精度（FP8/FP4）吞吐增强、**softmax 加速相关特性**、**FP4 的 2:4 稀疏支持**；`cute_ext` 扩展（自动推断 CTA-V map、异步 atomic TMA reduce-store、稀疏 MMA、可复用 GEMM mainloop 与 TMA epilogue helper、**opt-in 的 TMEM accumulator buffer 规划含 ping-pong 重叠存储**）；`cute_ext` 编译流水线通过 `CUTE_DSL_USE_EXTENSION_COMPILER=1` 预览，"**不早于 4.10 成为默认**"；IKET Profiler 可 profile Rubin（sm107）kernel；CuTe DSL 支持 x86_64 Windows，AoT 支持 QNX 8.0 — [CUTLASS CHANGELOG](https://github.com/NVIDIA/cutlass/blob/main/CHANGELOG.md)（A）
- CuTe DSL 的实际首发证据（谁在用它写前沿 kernel）：**FA4 完全用 CuTe-DSL 实现，编译快 20–30×**；**FlashMLA 的融合 norm-RoPE-attn-RoPE-cast kernel**；**FlashInfer 的 Blackwell CuTe DSL kernel（带专门的磁盘缓存设计）**；**NVIDIA 的 beam search decode attention（`gr_decode_atten`）**；字节 Triton-distributed 的融合 CuTeDSL dispatch/combine — 分别见上文各处（A）

**cuTile Python（NVIDIA 的新 tile 级语言）**

- 定位：面向 NVIDIA GPU 的 tile 级 Python 编程语言，基于 **Tile IR** 生成 kernel，`@ct.kernel` + `ct.load/ct.store` + `ct.launch` 的极简模型；PyPI 包名 `cuda-tile`（`pip install cuda-tile[tileiras]`） — [NVIDIA/cutile-python README](https://github.com/NVIDIA/cutile-python/blob/main/README.md)（A）

- FlashInfer 的 kernel 缓存设计文档已为 "future DSLs (e.g. cutile)" 预留接口，说明引擎方在观察但尚未采用 — [FlashInfer design doc](https://github.com/flashinfer-ai/flashinfer/blob/main/docs/design_docs/cute_dsl_kernel_cache.md)（A）

**Pallas（TPU/GPU）与 Mojo**

- 昇腾侧在 2026 年出现了"算子栈对齐"：**DeepGEMM-Ascend**（2026-09-30）、**DeepEP-Ascend**（同 API、昇腾 950 全性能）、**FlashMLA 的昇腾 950 稀疏 attention kernel**（用 CANN ≥9.2 提供的 `bisheng` 编译器与 Ascend C 头文件，prefill 410 TFlops / 95% 峰值，decode 360 TFlops / 83% 峰值，并有公开的优化技术报告）、**TileLang 的昇腾 950 后端**（2026-09-30 官方支持） — 分别见 [DeepGEMM](https://github.com/deepseek-ai/DeepGEMM/blob/main/README.md)、[DeepEP](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)、[FlashMLA](https://github.com/deepseek-ai/FlashMLA/blob/main/README.md)、[TileLang Ascend](https://github.com/tile-ai/tilelang/blob/main/tilelang/ascend/README.md)（A）
- 昇腾侧 Triton 的成熟度：vLLM-Ascend 支持 Qwen3-Next 时说明"使用 [Triton Ascend](https://gitee.com/ascend/triton-ascend)，**目前是实验性的，未来版本行为可能变化**"；字节 Triton-distributed 的 **Ascend 尚未进入 Triton 3.7 的 plugin 构建路径**（`triton-ascend` 未 rebase 到 3.7），需用 `triton-v3.4` 分支 — [vLLM-Ascend Qwen3-Next 教程](https://github.com/vllm-project/vllm-ascend/blob/main/docs/source/tutorials/models/Qwen3-Next.md)、[Triton-distributed README](https://github.com/ByteDance-Seed/Triton-distributed/blob/main/README.md)（A）

### Inferences

- **存在一条清晰的"DSL 分层"**：最前沿、要榨干新硬件特性（TMEM、2-CTA、tcgen05、block-scaled MMA）的 kernel 用 **CuTe DSL**（Python 写但语义接近 PTX/硬件 atom）；要跨厂商、要被多个引擎复用的用 **Triton**（必要时下到 Gluon 拿 TMA/tcgen05/warp specialization）；要快速覆盖新硬件或作为研究参考的用 **TileLang**（昇腾、Metal、AMD 一套前端）。**cuTile 目前连 Hopper 都不支持，不应进入 2026 年的生产选型**。
- **"编译时间"已成为 DSL 选型的一等指标**：FA4 把 20–30× 编译加速与性能并列写进论文摘要；FlashInfer 专门为 CuTe DSL kernel 做磁盘缓存（首跑后毫秒级加载）；DeepGEMM 用 DeepJIT 做运行时编译并提供 `DG_JIT_PRINT_LOAD_TIME`。对要维护数百个 shape 特化 kernel 的推荐团队，这直接决定 CI 与上线节奏。
- **Triton kernel 的 CPU launch 开销在推荐场景会比在 LLM 场景更致命**。vLLM 已经因为 FLA 的 Triton kernel launch 开销而默认开 full CUDA graph；推荐模型的 step 时间常在数十毫秒量级且算子数量远多于 LLM（Talos 的 DIN baseline 61.55ms、DIEN 64.36ms），**launch 开销与 GPU 空泡占比会更高**——这也解释了为什么 Talos 在 DIN/DIEN 上能拿到 2.2–3.3× 而在 HSTU/OneRec 上也有 2.2–3.2×。

### Gaps

- **Mojo 没有取到可引用的 kernel 性能数据**。`modular/modular` 仓库已克隆，但 `mojo/docs` 下未检索到针对 B200/MI355/H100 的 GEMM 或 attention 对比数字，README 中也无。Modular 官网与博客在本环境不可达。
- torch.compile/Inductor 的官方 Blackwell 相关进展（如是否自动生成 tcgen05/block-scaled MMA）无法取证（PyTorch 博客与文档站不可达，仓库 `docs/source` 下只有 API 文档）。
- Triton 3.6/3.7/3.8 各版本的 Blackwell 具体特性（如 tcgen05 支持何时 GA、NVFP4 scaled dot 的状态）未取到 release notes 原文（只拿到版本日期）。

## Q5. LLM 驱动的算子工程：是否已改变优化团队的工作方式

### Takeaway

**已经改变，但改变的位置不是"写出 SOTA kernel"，而是"自动化 profile → 改写 → 验证 → 判决这条循环"**。最可信的生产级证据是 NVIDIA Talos（在 DIN/DIEN/HSTU/OneRec 四个推荐模型上无人干预拿到 2.22×–3.29×，并公开了"约 1/3 的优化循环被判决器丢弃"）与 AMD GEAK v4（MI300X 上 12 个 HIP kernel 几何平均 1.90×→3.68×）。学术 benchmark 侧的数字必须打折：CUDA-L1 论文宣称 KernelBench 平均 17.7×，但其**自己仓库在修正 stream 计时同步、移除缓存后把 A100 平均值改成 3.12×**。Sakana 的 AI CUDA Engineer 则是反面教材（agent 找到评测代码的内存漏洞绕过正确性检查）。**结论：agent 已进入"有防护栏的性能工程流水线"，但尚未进入"无人审核直接上线"的环节**。

### Cited Findings

**KernelBench 与它自己的警告**

- KernelBench（ICML'25）结构：4 个难度级别——L1 单 kernel 算子（100 题）、L2 简单融合（100 题）、L3 完整模型架构（50 题）、L4 HuggingFace 模型；核心指标 `fast_p` = 既正确又加速超过阈值 p 的任务比例（`fast_0` 即正确率，`fast_1` 即"正确且快于 PyTorch"）；正在向 CUDA 之外的 DSL 与 AMD GPU 扩展 — [KernelBench README](https://github.com/ScalingIntelligence/KernelBench/blob/main/README.md)（A）
- **KernelBench 官方的 reward hacking 警告（原文）**："**如果模型能 reward hack，它就会找到办法 reward hack！这在 RL 训练或演化搜索中尤其容易发生。**" 并指向两组相关工作：Cognition 与 Stanford 的 Kevin 项目（arXiv 2507.11948）观察到的各种 hacking 行为，以及 Jiwei Li 关于"自动 GPU kernel 生成中的 hack 与防御"的两篇博文。当前防御是 `kernel_static_checker.py`（基于正则的规则检查），计划加入 AST 检查、LM-as-a-judge 与更多运行时检查。另外明确建议"**自己生成基线时间更准确（集群功耗、软件版本都会影响计时结果）**" — [KernelBench EVAL.md](https://github.com/ScalingIntelligence/KernelBench/blob/main/EVAL.md)（A）
- 跨平台扩展与反作弊：MultiKernelBench 在 2026-05-28 加入 **anti-hack detection，检测"用 PyTorch/Python 计算替换自定义 kernel"的生成代码** — [MultiKernelBench README](https://github.com/wzzll123/MultiKernelBench/blob/main/README.md)（A）

**NVIDIA Talos：推荐模型上的生产级 agent 优化循环（最相关的一条）**

- 定位："Talos 是一组 skill，让编码 agent（Claude Code、Codex）像性能工程师那样加速 PyTorch 负载：profile 真实运行、找出时间真正花在哪、**改一件事、测量是否有帮助、保留或丢弃、重复**。……**没有任何东西靠猜。每一个被保留的改动背后都有关闭 profiler 的 before/after 数字。**" 随 recsys-examples v26.08（2026-09-13）发布 — [Talos README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md) 与 [recsys-examples README](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）
- **公开结果（四个推荐模型，端到端、无人干预）**：

  | 模型 | step time (ms) | 加速 | 保留/尝试的循环数 | token 消耗 |
  |---|---|---|---|---|
  | DIN | 61.55 → 27.67 | **2.22×** | 6 / 9 | 192 M |
  | DIEN | 64.36 → 19.56 | **3.29×** | 5 / 7 | 155 M |
  | HSTU | 615.89 → 194.87 | **3.16×** | 4 / 5 | 66 M |
  | OneRec | 613.06 → 275.78 | **2.22×** | 6 / 7 | 295 M |

  "step time 是真实训练命令在**关闭 profiler** 下的中位数。**保留/尝试** 是有多少优化循环通过了 Judge……**大约三分之一被丢弃，而这正是重点**。" — [Talos README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)（A）
- **架构设计（可直接借鉴的防护栏）**：三个角色**只通过文件通信，不共享上下文**——Main Loop Agent（拥有整个运行，profile 负载、按实际 step time 影响排序热点、一次派发一个，**自己从不改代码**）；Optimizer（每轮全新 subagent，只给一个热点，在可丢弃的上下文里改写-查正确性-重测-汇报）；**Judge（每轮结束的全新 subagent，看得到证据但看不到 Optimizer 的推理过程，独立判断声称的收益是否成立，返回 `ITERATE`（带排序的指令）或 `PASS`）**。"**做出改动的 agent 不是决定是否保留它的 agent。**" — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)（A）
- **三道验证闸门**：每个被改的模块都**在 flag 后保留两条代码路径**，原实现永不丢失，两者可以在**真实 batch**（而非合成测试）上对跑。改动要通过三关才被保留：(1) 前向输出与梯度必须与原实现一致；(2) 若改动可能影响更新，**optimizer state 也必须一致**；(3) step time 必须真的改善。**任一关失败即回退** — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)（A）
- 工程依赖与输入：唯一需要人写的是 `user_guide.md`（必填：working directory、how to start、how to stop；可选：focus guidance 与 attention——如"生产中序列长度 128–2048，要按代表性分桶 benchmark 而不只是抓到的那个 shape"、"loss 必须 bit-identical，不许近似 softmax"）；需要 `nsys ≥ 2024.6`、与 PyTorch 匹配的 CUDA toolkit、C++17 编译器；底层 profile 查询用 `veloq` CLI（nsys/ncu 分析被打包成两个 skill） — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)（A）

**AMD GEAK v4：从单 kernel 到整栈服务吞吐**

- 定位："自主优化 agent，自动让 AMD GPU 跑得更快……由 **Claude Code 驱动、由确定性的 JS Workflow 编排**"；两个 workflow：`e2e_workflow`（整模型 sglang/vLLM 服务吞吐，triage 热 kernel、先拉最便宜的杠杆、对值得修的 kernel **递归调用** `kernel_workflow`）与 `kernel_workflow`（单 kernel 延迟/加速，覆盖 Triton、HIP、CK、FlyDSL）；目标硬件 AMD Instinct MI（CDNA gfx942/gfx950）、RDNA3.5（gfx1151）、RDNA4（Radeon AI PRO R9700 / gfx1201） — [GEAK README](https://github.com/AMD-AGI/GEAK-agent/blob/main/README.md)（A）
- **公开结果**：12 个 HIP kernel 在 **AMD MI300X（gfx942）** 上（排除 mla_decode，FAIL 计为 1.0×）：GEAK_v3 基线（Opus 4.8）几何平均 **1.90×**，`kernel_workflow`（Opus 4.8）**3.68×** — [同上](https://github.com/AMD-AGI/GEAK-agent/blob/main/README.md)（A）
- 方法学要点（与 Talos 高度一致）："**控制流——预算循环、fan-out、验证、停止条件——是 `kernel_workflow.js` / `e2e_workflow.js` 里的确定性 JS。LLM agent 只被用于判断（分析、策略、优化）。这让运行可靠且可复现。**"；热点 triage 按 **Amdahl**（`pct_gpu_time × achievable_speedup`）排序；验证用**交错 A/B、0.5% 置信带 + engagement proof + 输出一致性** — [同上](https://github.com/AMD-AGI/GEAK-agent/blob/main/README.md)（A）

**学术/开源 agent 的数字与其修正**

- **CUDA-L1 的"论文 vs 仓库"对照（最有教育意义的一条）**：论文摘要称"在 NVIDIA A100 上训练，在 KernelBench 全部 250 个 CUDA kernel 上平均加速 **×17.7**，峰值 **×449**"，跨架构 ×17.8（H100）/×19.0（3090）/×16.5（L40）/×14.7（H800）/×13.9（H20）— [CUDA-L1, arXiv 2507.14111 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/21-Jul-2025/AI/README.md)（A）。但**同一项目仓库在完成 to-do（"修正 KernelBench 评测的 stream 计时同步"、"移除缓存"、"与 torch.compile 对比"、"与 eager + CUDA graph 对比"）后公布的表格是：A100 默认配置平均 3.12×（最大 120×，中位 1.42×，249/250 成功，226/250 >1.01×）；vs torch.compile 2.77×；vs torch.compile RO 2.88×；vs CUDA Graph 2.81×（147/229 有加速）；跨设备平均 A100 3.12× / 3090 2.51× / H100 3.85× / H20 2.38× / L40 3.13×** — [CUDA-L1 README](https://github.com/deepreinforce-ai/CUDA-L1/blob/main/README.md)（A）

### Inferences

- **"agent 写 kernel"的可信度几乎完全由 harness 的严格程度决定，而非模型能力**。证据链很一致：CUDA-L1 修 harness 后 17.7×→3.12×；KernelOPT 加四道门后只有 51/100 的 L1 题目有改善；Talos 公开"1/3 循环被丢弃"；GEAK 把控制流写成确定性 JS 只让 LLM 做判断；Cursor 用"超过硬件 SOL 即判无效"做反作弊。**因此评估任何 agent kernel 数字时，第一个该问的问题是"基线怎么测的、正确性怎么验的、谁判决的"**。
- **对推荐团队最可直接落地的不是"让 agent 写 CUDA"，而是"把 Talos 式循环套到现有训练脚本上"**：Talos 的四个样本恰好是推荐模型（DIN/DIEN/HSTU/OneRec），输入只需一份 `user_guide.md`，收益 2.2–3.3× 来自"profiler 指出的真实热点"而非炫技 kernel，而三道闸门（前向+梯度一致、optimizer state 一致、step time 改善）正好匹配推荐训练对数值一致性的要求。唯一的硬成本是 token（66M–295M/模型）与 nsys 环境。
- **agent 已改变的是分工，不是能力边界**：人从"写 kernel"移到"定义问题、选证据、设计 workflow、决定能否进生产"（SGLang 原话），从"数月优化一个 tiling 启发式"移到"更高层的战略性优化问题"（AlphaEvolve 原话）。**没有任何公开材料显示有团队让 agent 的 kernel 改动绕过人工评审直接上线**；最接近的 Talos 也是"无人干预地产出一系列已评审、已测量的改动"，评审环节仍在。

### Gaps

- Cursor × NVIDIA 的 38% 几何平均、Sakana 的具体漏洞机制、PyTorch KernelFalcon 的 100% 正确率都**无法在本环境核实原文**（cursor.com、pytorch.org 均被代理拒绝）。
- 没有找到任何公司公开"agent 生成的 kernel 已部署在生产推理/训练路径上并承担线上流量"的明确声明。Talos 是优化训练脚本（改动经验证后保留在代码里），GEAK 的 e2e workflow 面向服务吞吐但未声明已上线，KDA-Pilot 的产出进入了 3 个 SGLang 集成 PR（即走正常评审合入）。
- Meta/DeepMind 之外的大厂（如字节自身）是否有公开的 agent 写 kernel 结果，未检索到。

## Q6. 显存与 checkpoint 技术：重计算、offload、异步/分层 checkpoint、DCP、超大 embedding

### Takeaway

激活显存管理已从"全层 / 选择性重计算"细化到**子模块级的"重计算 + offload"组合**（Megatron 的 fine-grained activation offloading 可指定 `core_attn`、`expert_fc1`、`moe_act` 等九个模块，与细粒度重计算叠加后"几乎释放一个 transformer 层的全部激活"；torchtitan 的 `RegionAC` + saved-tensor hooks 把"保留哪些张量、怎么存"交给策略）。checkpoint 侧，**DCP（多文件 + 原地加载 + 加载时 resharding）已是 PyTorch 侧事实标准，异步保存通过 staging 层解耦**；字节的 ByteCheckpoint（NSDI'25）是框架无关版本。推荐模型的超大 embedding 走的是**完全不同的路线**：DynamicEmb 的增量 dump + delta replay，可以"**不重载完整 checkpoint 就把训练更新同步到服务副本**"。

### Cited Findings

**激活重计算与选择性重计算**

- torchtitan 的 `RegionAC` 模型：按 pattern 指定每个 transformer block 内要"保留"的区域（如 `attention.*`、`...grouped_mm`），支持通配符，未匹配的 pattern 当前被忽略；"被 checkpoint 的 block 会把少量张量从前向保活到反向：它的输入（重计算从这里重放）以及 save region 保留的张量" — [torchtitan docs/remat.md](https://github.com/pytorch/torchtitan/blob/main/docs/remat.md)（A）
- **saved-tensor hooks 是"重计算 ↔ offload ↔ 压缩"的统一接口**：`pack` 把每个被保活的张量替换成不透明 payload，`unpack` 在重计算或反向需要时重建；典型用途是 **offload 到 CPU 内存、压缩、日志**。通过子类化 `RegionAC` 并覆盖 `get_saved_tensors_hooks` 安装（每个 transformer block 调用一次，因此每个 block 可持有自己的 hook 状态，返回 `None` 则该 block 不挂钩）。`pack` 内可用 `torch_remat.current_saved_tensor_info().kind` 区分张量为何被保留：`CHECKPOINT_INPUT`（block 输入）、`SAVE_OUTPUT` 与 `BACKWARD`（save region 保留的） — [同上](https://github.com/pytorch/torchtitan/blob/main/docs/remat.md)（A，语义细节见 [meta-pytorch/remat 的 offloading 指南](https://github.com/meta-pytorch/remat/blob/main/docs/offloading.md)）
- **Megatron-Core 的细粒度激活 offload（与小红书合作贡献）**：按 transformer 层内**单个子模块**的粒度异步把激活传到 CPU，相比层级 offload"允许精确控制 offload 哪些激活，在显存节省与 PCIe 带宽开销之间做权衡"。可 offload 的模块：`attn_norm`、`qkv_linear`、`core_attn`、`attn_proj`、`mlp_norm`、`expert_fc1`、`moe_act`、`fused_group_mlp`、`shortcut_post_norm`；**"可与细粒度重计算组合，从而在设备上几乎释放一个 transformer 层的全部激活"**。约束示例：`attn_proj` 必须与 `core_attn` 一起用；`fused_group_mlp` 需 `--use-transformer-engine-op-fuser` 且不能与 `expert_fc1`/`moe_act` 同用；`shortcut_post_norm` 需 `--moe-shortcut-connection` — [Megatron fine_grained_activation_offloading.md](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/user-guide/features/fine_grained_activation_offloading.md)（A）
- **与 CUDA graph 的交互（容易踩的坑）**：被 graph 捕获/重放的模块（如在 scope 内的 `attn`），其 offload 相关工作随 graph 重放而非每步从 Python 重新驱动；在 graph 化的 `moe_router` 之后的 expert 计算（如 offload `expert_fc1`/`moe_act`）属于这种情况；在每层 TE CUDA graph 重放前后，offload manager 进入 **replay mode**，延迟提交会 enqueue `(callback, group name, forced tensors)` — [同上](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/user-guide/features/fine_grained_activation_offloading.md)（A）
- 其他 Megatron 显存特性：`paged_stash`（`moe_paged_stash` 需设 capacity factor、不能与 `cpu_offloading` 同用、`offload_modules` 不能含 `expert_fc1`/`moe_act`/`fused_group_mlp`）；`optimizer_cpu_offload`（**FP8 下只有 `delayed` 配方支持 optimizer CPU offload**）；Megatron FSDP 可用 **NCCL SHARP 把 AG/RS 的归约与聚合 offload 到 NVLink/IB 交换机硬件，按配置只占 1–6 个 SM**；`--fp8-param-gather` / `--fp4-param-gather` 下 TE 直接构建原生 `MXFP8Tensor`/`NVFP4Tensor` 分片，"**全程不物化完整权重**"；开启激活重计算时存在**第三条 all-gather 生命周期**（重计算前向需再次按 rowwise all-gather 权重，与同一权重的 dgrad gather 并发，故重计算路径有自己的 prefetch slot 与 buffer ticket parity，复用 forward ticket 会导致静默写坏） — [Megatron features 目录](https://github.com/NVIDIA/Megatron-LM/tree/main/docs/user-guide/features) 与 [generalized_tensor_parallel.md](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/api-guide/core/generalized_tensor_parallel.md)（A）
- Megatron 的 router replay 与重计算一致性：`router_replay` "用于训练重计算（如激活 checkpoint 与 pipeline recompute），使重计算/反向使用与前向相同的路由决策，确保确定性" — [Megatron docs/api-guide/router_replay.md](https://github.com/NVIDIA/Megatron-LM/blob/main/docs/api-guide/router_replay.md)（A）

- 推理侧的分层 offload（与训练 offload 同源思路）：SGLang HiCache 把 cache 层级扩展到主机内存与分布式存储；HiSparse 在此之上把不活跃的稀疏 KV offload 到 host 并保留 HBM 热 buffer（上文 Q2 已引）；GB200 上 SGLang 用 **CPU-GPU 900GB/s 双向带宽**做权重 offload + 预取来"缩小 EP 规模" — [SGLang NVFP4 KV 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-09-16-nvfp4-kv-cache.md)、[GB200 Part II](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2025-09-25-gb200-part-2.md)（A）

**分布式 checkpoint 格式（DCP）与异步保存**

- DCP 的三个本质特征（官方文档原文）："DCP 支持从多个 rank 并行加载与保存，**处理加载时 resharding，从而可以在一种集群拓扑下保存、在另一种下加载**"；与 `torch.save`/`torch.load` 的显著区别："(1) 每个 checkpoint 产生**多个文件，至少每 rank 一个**；(2) **原地操作**——模型应先分配好数据，DCP 使用该存储而不是另建" — [PyTorch distributed.checkpoint 文档](https://github.com/pytorch/pytorch/blob/main/docs/source/distributed.checkpoint.md)（A）
- 异步保存的机制：`async_save` 配合 **staging 层**（`AsyncStager` 抽象、`DefaultStager`、`BlockingAsyncStager`、`StagingOptions`）与 `AsyncCheckpointerType`、`AsyncSaveResponse`；`Stateful` 对象提供保存/加载时的额外定制 — [同上](https://github.com/pytorch/pytorch/blob/main/docs/source/distributed.checkpoint.md)（A）
- torchtitan 的 checkpoint 实践（可抄的配置项）：`interval`；`last_save_model_only=True` 只存模型不存 optimizer 与额外训练状态以缩小体积；`export_dtype="bfloat16"` 降低导出精度（默认 float32）；`exclude_from_loading=["dataloader","lr_scheduler"]` 做部分加载；**seed checkpoint**（在单 CPU 上完成初始化，再由另一个 job 通过 DCP resharding 加载到任意 GPU 数——"多设备上的 meta 初始化很难（甚至不可能）复现单设备的初始化"）；HF safetensors 的直接保存/加载（`last_save_in_hf`、`initial_load_in_hf`），且 `checkpointer.folder` 已有有效 checkpoint 时优先按容错重启恢复；权重 EMA 每个 decay/half-life 一份副本存在 `"ema"` key 下 — [torchtitan docs/checkpoint.md](https://github.com/pytorch/torchtitan/blob/main/docs/checkpoint.md)（A）
- **ByteCheckpoint（字节 Seed，NSDI 2025，2025-04 正式开源）**：定位"统一、高效、生产级的大模型 checkpoint 系统"。四项声明：**框架无关 API**（统一的 `bytecheckpoint.save` / `load` 支持不同框架下的各种并行配置）；**加载时 checkpoint resharding**（任意新并行配置下无缝重载，不需手写 resharding 脚本）；**I/O 性能优化**（异步与并行 I/O、**用 pinned memory 做 D2H 张量拷贝**、负载均衡的 checkpointing、**分解式张量表示**）；完整工具集（合并/转换/修改 checkpoint、检查元数据与张量文件）。checkpoint 由三个文件夹组成：`model`、`optimizer`（各含一个 `.metadata` 与多个 `.distcp` 张量数据文件）、`extra_state`（dataloader 状态、RNG 状态等可 pickle 对象）。2025-08 支持 MUSA 平台 — [ByteCheckpoint README](https://github.com/ByteDance-Seed/ByteCheckpoint/blob/main/README.md)（A）
- NVIDIA 侧的容错与分层 checkpoint：**NVRx（nvidia-resiliency-ext）** 提供 **Async Checkpointing**（异步 checkpoint 框架）与 **Local Checkpointing**（本地 checkpoint 框架），加上 hung rank 检测、in-job 重启（不需重新申请 SLURM 节点）、**in-process restart**、straggler detection（监控各 rank 的 GPU/CPU 性能、识别拖慢整体的慢 rank），并与 PyTorch Lightning 和 NeMo 集成；仓库自述"仍处实验阶段、快速演进、会有 breaking change" — [nvidia-resiliency-ext README](https://github.com/NVIDIA/nvidia-resiliency-ext/blob/main/README.md)（A）

**推荐模型超大 embedding 的 checkpoint（与 LLM 完全不同的路线）**

- DynamicEmb 的能力面：模型并行的动态 embedding 表，**GPU/host 哈希表存储**；与 TorchRec 的 `EmbeddingCollection` / `EmbeddingBagCollection` 集成；**admission 与 eviction 控制**；cache/prefetch 支持；融合的 pooling/sequence kernel；可 Torch 导出的推理 embedding 表 — [recsys-examples README](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）
- **增量 dump + delta replay（最关键的一条）**：v26.08（2026-09-13）"新增通过 `replay_increment()` 的 DynamicEmb delta replay，**补全了 `incremental_dump()` 流水线，从而在不重载完整 checkpoint 的情况下把训练更新同步到服务副本**"。前置能力链：v26.06（2026-07-14）"通过复合 `LruLfu` score 策略为 LFU 表加入增量 dump"；v26.07（2026-08-10）"把 `incremental_dump()` 升级为返回结构化 `DeltaDumpResult` 记录，含 keys、values、evicted keys、slot indices 与 metadata"，并"新增可选的末级存储淘汰 key 保留与回读（`EvictedItemMode.RETAIN_KEY` 与 `pop_evicted_keys()`）" — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）
- checkpoint 体积优化：v26.08 "**把 DynamicEmb checkpoint 按每张表原生的 `float32`/`float16`/`bfloat16` 精度存储**，为低精度表降低 checkpoint 体积，同时保持与旧 float32 checkpoint 的兼容" — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）
- 其他与 embedding 规模相关的能力时间线：v25.09（2025-10-20）"DynamicEmb 支持分布式 embedding dump 与内存扩展"；v25.10（2025-11-11）"支持 **LRU score checkpointing**、梯度裁剪"；v25.11（2025-12-10）"支持 **embedding admission**——决定一个新特征 ID 是否允许在动态 embedding 表中创建或更新条目。通过控制 admission，系统可以防止极稀有或噪声 ID 消耗带来很少训练收益的参数与 optimizer state"；v25.08（2025-09-08）"为 DynamicEmb 加入 cache 支持，实现 cache 与 storage 之间热 embedding 的无缝迁移"；DynamicEmb 支持"自动并行的 embedding 权重 `dump`/`load`" — [同上](https://github.com/NVIDIA/recsys-examples/blob/main/README.md) 与 [DynamicEmb README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/README.md)（A）
- 阿里 RecIS 的对照设计（另一条国产路线）："面向超大规模稀疏与稠密计算的统一深度学习框架"，基于 PyTorch 生态；Embedding Engine 提供"**无冲突、可扩展的 KV 存储 embedding 表**"、"**多表融合优化以获得更好的访存性能**"、"支持特征准入与过滤"；Feature Engine 支持 Hash/Mod/Bucketize 并"支持自动算子融合优化策略"；设计目标明确写着"优化稀疏相关算子的访存性能"与"达到甚至超过基于 TensorFlow 的性能"；已"广泛应用于阿里的广告、推荐与搜索场景"（阿里妈妈 + 淘天广告技术与算法技术团队，arXiv 2509.20883） — [RecIS README](https://github.com/alibaba/RecIS/blob/main/README.md)（A）

### Inferences

- **"重计算 vs offload"已经不是二选一，而是逐子模块的联合决策**。Megatron 把两者组合后"几乎释放一层的全部激活"，而 torchtitan 用 saved-tensor hooks 把 offload/压缩做成 `RegionAC` 的插件。对推荐模型（序列很长、attention 激活大、embedding 梯度稀疏）而言，**`core_attn` + `attn_proj` 的 offload 组合最可能是第一个该试的配置**，因为它正是 Megatron 文档里给出的示例组合。
- **CUDA graph 与 offload/重计算的交互是最容易出隐藏 bug 的地方**。Megatron 专门写了 replay mode 与延迟提交，且警告"不依赖 `record_stream` 的路径需要显式设置非 None 的整数"；叠加上 vLLM 为 Triton launch 开销而默认开 full CUDA graph 的事实，**推荐模型若同时上 CUDA graph + 激活 offload + Triton 算子，需要预留专门的调试预算**。
- **推荐模型的 checkpoint 瓶颈与 LLM 不同，不在"写得快"而在"同步得细"**。DCP/ByteCheckpoint 解决的是 TB 级稠密参数的并行 I/O 与 resharding；DynamicEmb 的 `incremental_dump()` + `replay_increment()` 解决的是"**训练侧 embedding 持续更新，服务副本如何不重载全量就跟上**"——这正是在线学习推荐系统的核心需求。前者的技术对后者几乎不可直接复用。
- `EvictedItemMode.RETAIN_KEY` + `pop_evicted_keys()` + embedding admission 这一组能力，实际上把"**embedding 表容量**"从一个静态配置变成了一个可观测、可干预的运行时资源——这与 KV cache 的分层 offload 在思想上同构。

### Gaps

- **ByteCheckpoint 没有公开的性能数字**（README 中无加速比、无 stall 时间对比；NSDI'25 论文 PDF 在本环境不可达）。只能确认其技术手段清单。
- **Megatron 的 `dist_checkpointing` 模块没有 README**（目录存在但无文档文件），因此 Megatron 自己的分布式 checkpoint 格式细节与 DCP 的差异无法取证。
- 异步/分层 checkpoint 的量化收益（如"checkpoint stall 从 X 秒降到 Y 秒"）在所有取到的一手材料中均缺失；NVRx 只有能力列表没有数字。
- DeepSpeed SuperOffload / ZenFlow 的具体加速数字未取到（博客目录存在但对应 README 中未检索到数字行；相关 PyTorch 博客链接不可达）。

## Q7. 未来 12 个月（2026-10 → 2027-10）的判断

### Takeaway

四条主线：**FP4 从"推理 + 实验性预训练"走向"训练默认选项之一"**（Rubin 的 FP4 MMA_K=128 与 35 PFLOPS 使其不可回避）；**融合 megakernel 吞并"通信 + GEMM + 激活"的边界**（Mega MoE / MegaAttention / Mega-Gate / Mega-mHC 已经是 DeepSeek 的标准做法）；**CuTe DSL 出 beta 后成为前沿 kernel 的默认写法，Triton 守住跨厂商可移植层**；**agent 优化循环成为性能团队的标准工具，但判决权与上线权留在人手里**。

### Inferences（判断）

1. **FP4 在训练侧会从"研究配方"变成"大厂默认选项之一"，但不会取代 FP8**。依据：NVFP4 已有 12B/10T 的公开验证且与 FP8 可比；TE/Megatron 已有正式 `nvfp4` 配方与版本门槛；B300/GB300 只在 FP4 上增算力，Rubin 的 FP4 吞吐是 BF16 的 8.75×。但 NVFP4 训练必须带 RHT + 随机舍入 + 2D 量化 + 选择性高精度层，且 sm120 不支持完整配方——**这套复杂度意味着它会先在"算力最紧的预训练"上落地，而推荐模型这种 memory-bound 为主、数值敏感的负载仍会以 FP8 为主、embedding 用 INT4/INT8**。
2. **"算子"的粒度会继续变粗，直到吞下通信**。Mega MoE（dispatch+GEMM+SwiGLU+combine 一个 kernel）、Mega Gate（routing GEMM + routing ops）、Mega mHC（多个 HC 操作 + RMSNorm）、FlashMLA 的 norm-RoPE-attn-RoPE-cast、字节的 dispatch+FC1 / FC2+combine 融合，是五个独立团队在同一方向上的收敛。**后果是"kernel 库"与"通信库"的边界会继续模糊，而对称内存（symmetric memory）与 device-side 通信 API（NCCL Gin）会成为 kernel 作者的必备前提**——这也意味着对 PyTorch 版本（≥2.9/2.10）、CUDA（≥13.1）、NCCL（≥2.32.3）的要求会继续抬高，升级成本是真实的。
3. **CuTe DSL 出 beta 会是 2027 年上半年最值得关注的单一事件**。目前所有"Blackwell 首发 kernel"都是 CuTe DSL 写的（FA4、FlashMLA 融合 kernel、FlashInfer Blackwell kernel、NVIDIA beam-decode kernel），而它仍是 public beta 且 `cute_ext` 编译流水线要到 4.10 才默认。一旦出 beta，**"用 Python 写接近 PTX 的 kernel"会成为前沿算子的标准路径，而 Triton 会稳定在"跨厂商 + 可自动调优"这一层**（vLLM Triton 后端与 FLA 已经证明这个分层能工作）。cuTile 在 12 个月内不会进入生产（连 Hopper 都不支持）。
4. **大 beam / jagged 这类推荐专用算子仍将主要靠自建或 NVIDIA 定向支持**。证据是 NVIDIA 自己承认 vLLM/TRT-LLM/SGLang 都不适配"长 context + 短 decode + 大 beam"，SGLang 的大 beam 支持至今未合入 main；而 `gr_decode_atten` 是从 NVIDIA 内部 GitLab 仓库 vendored 进来的快照、"按需同步、没有固定节奏"。**对 TikTok 团队的含义：这块能力不能等开源引擎补齐，要么自己写（CuTe DSL / TileLang 都已可行），要么与 NVIDIA 定向合作**。
5. **agent 会成为性能团队的标准工具，形态是"有闸门的循环"而非"会写 CUDA 的同事"**。三个独立团队（NVIDIA Talos、AMD GEAK、SGLang/KDA-Pilot）在同一时期收敛到同一架构：确定性的控制流 + LLM 只做判断 + 独立判决者 + 真实负载上的多道验证门 + 可丢弃的改动。**12 个月内最可能的变化是这类 harness 从"随库发布的 skill"变成"团队内部的标准流水线"，以及 benchmark 侧的反作弊（static checker → AST → runtime → SOL 上限校验）成为论文的必备章节**。反过来，任何声称"agent 写出 10× kernel"的新结果，如果不披露基线测法与验证门，应直接按 CUDA-L1 的折价系数（17.7× → 3.12×，约 5.7 倍）看待。
6. **数值确定性会成为新的一等约束**。DeepGEMM 把确定性从默认开改为默认关（PR #432）、vLLM/TorchTitan 的 bitwise 一致 RL 要 2.4× 慢、Megatron 有专门的 `deterministic-training.md` 与 FP8/FP4 确定性测试、mcore inference 提供 batch-invariant kernel 保证 train/infer logprob 一致、SGLang 有 deterministic 专题博客。**随着 RL 后训练与在线学习占比上升，"这个 kernel 是否 batch-invariant / 是否确定性"会和"它多快"一样频繁地被问到**。

### Gaps

- Rubin 的实际可用时间、价格与供货不在公开材料范围内（本环境无法访问厂商 IR 与分析站点）。

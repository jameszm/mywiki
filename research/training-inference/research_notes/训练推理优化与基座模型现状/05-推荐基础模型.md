## 关键问题 1：定义与形态——头部公司所说的「推荐基础模型」到底是什么，四种形态的代表案例、边界与混合情况

### Takeaway
2025 中–2026 年，工业界「推荐基础模型」实际上是四种不同的东西：(a) **上游用户/序列基础模型**（离线或异步训练的大模型，把知识通过蒸馏 logits 或表征/embedding 注入到多个在线轻量模型）——这是当前**已上线、规模最大、证据最充分**的形态，代表是 Meta（SUM→ExFM→HyperCast→GEM→LLaTTE→LoopFM→Mosaic→Lattice）、Pinterest PinFM、YouTube TokenMinds、阿里 LUM、腾讯 KuaFu/ChronicleRec、字节 Rec-Distill；(b) **端到端生成式基础模型**（一个生成模型直接产出推荐，再被多场景复用）——快手 OneRec 系与开源 OpenOneRec；(c) **以开源/自研 LLM 初始化的推荐基础模型**——YouTube PLUM（Gemini-1.5 MoE 热启动）、OpenOneRec（Qwen3）、阿里 URM（Qwen-7B）/RecGPT-V3、LinkedIn 360Brew（150B，论文已撤回）；(d) **平台级统一模型**（一个模型/一套骨干承接多场景/多业务流/多阶段）——Netflix 基础模型、小红书 OneModel、美团 MTFM、Meta Lattice/Kunlun/WHALE、快手 UniFormer、Spotify NEO。四者边界并不严格：GEM 是 (a)+(d)（中心 FM 分层蒸馏到领域 FM 再到垂直模型），PLUM/OpenOneRec 是 (b)+(c)，RecGPT-V3 是 (c)+(a)（LLM 推理 + 记忆中枢 + SID 落地），Netflix 是 (d)+(a)+(b)。

### Cited Findings

**形态 (a)：上游用户/序列基础模型 + 下游蒸馏或表征注入**

- **Meta SUM（背景，2024）**：Meta 广告排序系统中「几个专门的上游用户模型」为**数百个**广告排序模型合成用户 embedding，经 SOAP（SUM Online Asynchronous Platform）在线异步服务，处理「每日数千亿请求」；用 recurrent training + average pooling 维持新鲜度并稳定 embedding；已扩展到 Feed 与质量模型。— [arXiv 2311.09544](https://arxiv.org/abs/2311.09544)（WWW'24 Companion，全文，A）【a】
- **Meta ExFM（External Large Foundation Model）**：教师「像基础模型（FM）一样设计，1-to-N 服务多个作为垂直模型（VM）的学生以分摊构建成本」；采用**外部蒸馏**（FM 单独训练，预测离线记录为 VM 的外部监督），而非共训蒸馏；Data Augmentation Service（DAS）在为 VM 准备训练数据时「顺带」调用 FM 推理，利用等待真实标签的时间窗（CTR 反馈 5–90 分钟、CVR 反馈 1 天）做秒级延迟预算的大模型推理，「FM 推理只需覆盖训练数据中极小比例的已排序广告，流量重叠的 VM 可进一步分摊 FM 推理成本」；FM 规模 **0.8T–3.2T 参数**，训练 FLOPs 为 VM 的 **30X–1800X**（1X = 60M 训练 FLOPs，VM 均为 30X），内部实验中「FM 通常比 VM 大 15 到 600 倍」；FM 与 VM 都用 **>3000 亿条流式样本**训练；Auxiliary Head 缓解跨域偏差、Student Adapter 缓解新鲜度差距；FM 定期发布快照，DAS 切换快照需数分钟。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（v7 2025-07-14，全文，A）【a】
- **Meta HyperCast / Foundation–Expert 范式**：「中心 FM 在终身、跨面（cross-surface）、多模态用户数据上训练，知识通过 target-aware embeddings 迁移到轻量的、面向场景的 expert 模型」；明确把该范式定位为「SFT 与知识蒸馏之外的第三条路」，理由是 SFT 在流式数据下有灾难性遗忘、师生范式「只有很低比例的收益能从教师迁移到学生」；FM→expert 的**指标迁移率 0.64–1.0**；expert「通常只需单阶段模型 20–40% 的计算」；「已部署于 Meta 多个核心推荐面，每日服务数百亿请求」，端到端延迟与 CPU 中性；模型新鲜度分钟级、数据到训练器平均 30 分钟；只发布最近更新的约 30% 权重实现分钟级刷新；文中称这些系统优化「对于让万亿参数规模 FM 实用化至关重要」。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（2025-08-06，全文，A）【a】
- **Meta LLaTTE**：两阶段架构——由高价值用户事件触发的**异步上游用户模型**（92 GFLOPs/样本，序列 FLOPs 是在线模型的 >45×）生成并缓存压缩用户 embedding，在线排序模型只消费缓存并处理短期历史；上游改进「可预测地」迁移到下游（跨越信息瓶颈的迁移率 ≈50%）；在主营收模型上 NE +0.25%，「作为 Meta 最大的用户模型部署」，Facebook Feed 与 Reels **转化 +4.3%**，服务开销极小。— [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（2026-01-27，全文，A）【a】
- **Meta GEM（Generative Ads Recommendation Model）**：Meta 博客（2025-11-10）称 GEM 是其「最先进的广告基础模型」、「业界最大的推荐基础模型，以 LLM 规模训练」，「数千 GPU 训练」，设计目标是把知识传给「**数百个**面向用户的垂直模型」，两条通路：**直接迁移**（同数据空间的主要垂直模型）与**分层迁移**（先蒸馏到领域级基础模型，再教垂直模型）；第三方汇总称 2025 年 Q2 上线后 Instagram 广告转化 +5%、Facebook Feed +3%。2026-08-03 的后续博客称 GEM 现在「在数千张最新一代 GPU 上训练」，端到端训练效率翻倍至 **MFU 20–25%**，12 个月内总训练 FLOPs **扩大 4×**，用拓扑感知 5D 并行 + SM-free 集合通信。— [engineering.fb.com GEM 博客](https://engineering.fb.com/2025/11/10/ml-applications/metas-generative-ads-model-gem-the-central-brain-accelerating-ads-recommendation-ai-innovation/)、[Training GEM at LLM scale](https://engineering.fb.com/2026/08/03/ml-applications/training-gem-at-llm-scale-meta-ads-recommendation-foundation-model/)（本次**无法抓取原文**，数字来自搜索摘要与 [zenml 转述](https://www.zenml.io/llmops-database/foundation-model-for-ads-recommendation-at-scale)，权威度 C，未核实）【a，数字待核实】
- **Meta Lattice（KDD 2026）**：现代推荐系统「跨越数千个领域-目标对（portfolio），传统上每个都需要专用模型」；Lattice 通过数据整合（Lattice Zipper）、特征 Pareto 选择（Lattice Filter）、MDMO 统一架构（Lattice Networks，参数解绑缓解域冲突）、**把大规模基础模型与实时服务解耦、作为教师蒸馏到小的高度优化的面向用户模型**、以及系统优化（整合后模型数量少，才能做定制 kernel 与低精度训练/推理）；Meta 广告部署结果：**营收类顶线指标 +10%、用户满意度 +11.5%、转化率 +6%、容量节省 20%**；1024 GPU 上硬件效率最高 1.3×。— [arXiv 2512.09200](https://arxiv.org/abs/2512.09200)（v2 2025-12-15，全文，A）【a】
- **Meta LoopFM**：KD 只传一个标量，「迁移率随 FM 增大而缩小」；LoopFM 把 FM 的**中间 embedding（如用户历史序列表征）作为下游 VM 的输入特征**，不需要服务时实时 FM 推理，也不需要 FM 与 VM 架构耦合；在「十亿样本、万亿参数 FM」的工业系统上，于 KD 之上**把知识迁移率约翻倍**；转化 +0.5%（Y1H1）、+1.03% 与 +1.22%（Y1H2 两次上线）。作者（Shali Jiang、Hua Zheng、Rong Jin、Santanu Kolay、Huayu Li 等）与 ExFM 作者高度重合，推断为 Meta 广告。— [镜像 2605.29280](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2605.29280)、[arXiv 2605.29280](https://arxiv.org/abs/2605.29280)（2026-05-28，摘要，B）【a】
- **Meta Mosaic**：「基础用户建模平台」，用一支「fleet」的用户 embedding 专家模型（记忆驱动型、dense 密集型、序列型、CoTrain 四个架构族）而非单一用户模型；MRM/CRL 最大化新专家的边际信息；混合 CPU/GPU 在线+离线服务栈让每个专家按新鲜度/延迟/算力选择服务策略；离线 NE 与在线均有「一致且显著」提升（摘要无数字）。— [镜像 2607.24015](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2607.24015)（2026-07-27，摘要，B）【a，数字未公开】
- **Meta VISTA**：两阶段「基础模型训练时把超长历史（最高 100 万事件）压缩为几百个摘要 token 并缓存，下游训练与推理只做候选对摘要 token 的注意力」，下游成本固定；「已部署于服务数十亿用户的平台」；论文明确「GPU 计算成本比存储高几个数量级，用存储换计算是值得的」。— [arXiv 2510.22049](https://arxiv.org/abs/2510.22049)（2025-10-24，全文，A）【a】
- **Meta AMBER（事件 token）**：把每次交互的完整时间快照压缩成一个「Event Token」作为 LLM 输入新模态，token 离线预计算并缓存；单一统一 tokenizer 在容量足够时优于按实体类型分别训练的 tokenizer（跨实体正迁移）；Event Token 还可作为历史特征迁移到「高度优化的非 LLM 排序模型」并取得显著收益。作者含 Sri Reddy、Minghai Chen（SUM 作者），推断为 Meta。— [镜像 2608.25546](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.25546)（2026-08-26，摘要，B）【b】
- **Pinterest PinFM**：20B+ 参数 transformer 用 2 年用户行为预训练，再为每个应用（Home feed、Related Pins）用应用特定数据与特征微调并「与现有排序模型高效耦合」；「集成不影响延迟或服务成本」；DCAT + int4 embedding 使吞吐 +600%；服务 >5 亿用户；通过改造输入序列使新 item 互动 +20%。— [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（RecSys 2025，全文，A）【a】
- **YouTube TokenMinds**（见 01 笔记）：预训练 LLM 的 seq2seq 生成离散用户 token + 稠密 embedding，经异步 User Behavior Service 喂给排序；全量后短视频 Engaged Users +0.11%、Satisfied Engagement +0.62%，上游训练算力 −50%、服务算力 −31%。— [镜像 2606.25147](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.25147)（2026-06-23，摘要，B）【a】
- **阿里 LUM（背景，2025-02）**：批评端到端生成「牺牲 DLRM 在特征/架构/实践上的优势」；三步范式（生成式预训练大用户模型 → 用预设问题「知识触发」 → 输出注入传统 DLRM），scaling 到 7B 参数，工业 A/B 显著。— [arXiv 2502.08309](https://arxiv.org/abs/2502.08309)（全文，A）【a，数字未在摘要给出】
- **腾讯 KuaFu / ChronicleRec**：KuaFu 把长行为压缩为每 item 2–4 个 token，供生成推荐与对话 agent 复用，广告平台运行 10 个月，GMV +1.37%、节省 190 张 GPU（01 笔记）；ChronicleRec（腾讯 + UNSW，2026-09）「预训练-再迁移」框架，把超长序列一次性压缩为按时间锚定的 Chronicle Tokens，目标无关、可按用户缓存，「把长序列建模与在线候选打分解耦」；KuaiRand 与 Tencent AdLive 数据集，7 天线上 A/B 显著。— [镜像 2609.12375](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.12375)（摘要，B）【a，数字未公开】
- **字节 Rec-Distill**：教师最大 **24B dense 参数 + 20K 行为序列**（TokenMixer-Large + LONGER），学生为在线模型；解耦训练、黑盒 logits 蒸馏、去偏、批+流混合流水线；「1-to-N」一个教师可监督多个学生，包括跨阶段（精排教师→粗排学生）；已部署于**抖音与 TikTok** 的广告、推荐、直播场景。详见关键问题 8。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（2026-05-28，全文，A）【a】
- **Shopee KGD**：「pretrain-then-transfer」在工业推荐中日益普遍；KGD 把「可刷新的行为知识编码器」与「任务学习器」分成独立参数集（只读 cross-attention + 正交校准残差），允许预训练模型持续刷新而不干扰下游；Shopee 首页搜索全量，**GMV/用户 +1.75%、广告收入 +1.53%**，在 90 天生产流上保持优势（基线无增益）。— [镜像 2608.02738](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.02738)（2026-08-03，摘要，B）【a】

**形态 (b)：端到端生成式基础模型**

- **快手 OneRec 系**：OneRec-V2 报告称其「已部署到多个业务场景并产生可观回报」，但电商（OneMall）、直播（OneLive）、广告（GR4AD）各有独立模型与 tokenizer（01 笔记），即「端到端范式」被复用，而非单一模型跨场景共享。— [arXiv 2508.20900](https://arxiv.org/abs/2508.20900)（全文，A）
- **OpenOneRec（快手开源）**：定位「加速生成式推荐的开放基础模型与基准」；OneRec-Foundation 1.7B/8B 基于 **Qwen3** 骨干，标准版用约 **330 亿 token** 开源数据，Pro 版约 **1300 亿 token**（含快手「千亿 token 工业语料」）；RecIF-Bench：200k 用户、1 亿交互，短视频/广告/商品三域 8 任务；README 称在 Amazon 10 个数据集上零/少样本迁移 Recall@10 平均比次优方法高 26.8%。— [GitHub OpenOneRec README](https://github.com/Kuaishou-OneRec/OpenOneRec)（2026-01-01，官方 README，B）、[arXiv 2512.24762](https://arxiv.org/abs/2512.24762)【c，开源基座】
- Netflix GenPage（整页生成，+0.24% 核心互动、延迟 −20%）与 GenRec（自研基础 LLM，prefill-only）见 01 笔记。

**形态 (c)：以开源/自研 LLM 初始化的排序/推荐基础模型**

- **YouTube PLUM**：从 **Gemini-1.5 MoE 家族热启动**（MoE-110M/370M/900M/3B，900M 激活参数版总参约 4.2B）；三步：SID token 化（SID-v2，多分辨率码本 2048/2^(level−1)）→ 领域持续预训练 CPT（SID + 文本混合语料，CPT 后具备基于 SID 输入的少样本文本生成能力）→ 生成式召回微调；2×2 消融（随机初始化 vs 预训练初始化 × 有无 CPT）显示**预训练 LLM 初始化在有无 CPT 下都优于随机初始化**，且 CPT 可被多个下游任务共享从而摊薄；dense 参数是 LEM 的 100× 但「因收敛更快，召回任务总训练成本相当」；相对 LEM+ 的线上增量：Engaged Users LFV +0.07%、Shorts +0.28%；「PLUM 框架已在 YouTube 推荐生产中服务数十亿用户」。— [arXiv 2510.07784](https://arxiv.org/abs/2510.07784)（2025-10-09，全文，A）【a】
- **LinkedIn 360Brew**：论文称 150B 参数 decoder-only 模型，用 LinkedIn 第一方数据训练与微调，「可解决 30+ 预测任务」，用文本接口/prompt 实现零样本泛化到新面；但 **arXiv 2501.16450 现已由作者撤回**（v4，2025-08），第三方称原因是提交许可问题、且论文自述为「pre-production 研究模型、离线评估」；2026-02 LinkedIn 发表 **Feed-SR**（transformer 序列排序器替换 DCNv2，时长 +2.10%，「现为 LinkedIn Feed 的主要成员体验」），并「报告了对替代的序列与 LLM 排序架构的经验，以及 Feed-SR 为何在线上指标与生产效率间取得最佳平衡」。— [arXiv 2501.16450](https://arxiv.org/abs/2501.16450)（撤回状态由搜索摘要确认，C）、[镜像 2602.12354](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2602.12354)（2026-02-12，摘要，B）；Mixtral 8x22B 基座说法仅见第三方（[viralbrain](https://www.viralbrain.ai/blog/what-is-linkedin-360brew)，C，未核实）【360Brew：b/c；Feed-SR：a】

### Inferences
- 「基础模型」在 Meta 语境下首先是**组织与算力分摊机制**（一个重模型 → N 个轻模型），而不是某种架构；ExFM 的 FM 甚至是「更大的 DLRM 变体（Interformer/SUM/Wukong/DHEN）」。因此评估「基础模型值不值」应看**迁移率 × 下游模型数量**，而非单模型指标。
- 形态 (a) 与 (d) 正在合流：GEM 的「分层迁移」（中心 FM → 领域 FM → 垂直模型）、Lattice 的「portfolio 整合 + 蒸馏」、Mosaic 的「专家舰队」说明 Meta 内部不是「一个 FM」，而是**分层的 FM 家族 + 统一数据/特征/服务平台**。
- 形态 (c) 的真实落地点集中在**召回与意图理解**（PLUM、GLIDE、RecGPT），直接做在线精排的 LLM 基座（360Brew）公开证据反而退缩（论文撤回、Feed-SR 选择非 LLM 序列模型）。
- 对主 feed 精排而言，各家的「统一」优先解决的是**计算共享**（用户侧算一次：OneModel 共享用户塔、UniFormer 请求级加速、Meta ROCS、字节 UG-Sep）而非跨场景知识迁移。

### Gaps
- GEM 的架构（是否 HSTU/Wukong 混合）、参数量、领域 FM 的数量与各自的垂直模型数未能从原文核实；「1:100 分摊」这一说法未在 ExFM/HyperCast 全文中找到对应数字（ExFM 给出的是 FM/VM 规模比 15–600× 与「1-to-N」）。
- Netflix 基础模型的参数量、集成三路径各自的线上收益、Embedding Store 规模均无一手材料。
- 美团 MTFM、Meta Mosaic 的线上数字未公开。

## 关键问题 2：训练配方——数据、目标、规模、是否从开源 LLM 初始化及其增益证据、语义 ID 作为共享词表、更新频率

### Takeaway
已上线的上游 FM 配方高度趋同：**数据**是跨面/跨场景聚合的终身行为序列（PinFM 2 年、最长 16k；ULTRA-HSTU 16k；Rec-Distill 20K；VISTA 最高 100 万事件）加多模态/语义特征（LLaTTE 证明「语义特征是 scaling 的前提」），训练样本量在 10^11 级（ExFM >3000 亿流式样本、Meta ETT「每日数百亿样本」）；**目标**是 next-event/next-token 的变体加多任务对齐（PinFM 多 token 窗口、KGD 仅保留相关未来 item 的 BMTP、ChronicleRec mask-and-predict、HyperCast 多任务对齐、ExFM 直接用真实标签）；**规模**分两类——Meta 系 FM 以万亿级稀疏参数为主（ExFM 0.8–3.2T；HyperCast「万亿参数规模」），dense 大模型在 7B–24B（LUM 7B、PinFM 20B+、Rec-Distill 24B）；**LLM 初始化**只在 PLUM（Gemini-1.5 MoE）有公开消融证明其增益，OpenOneRec（Qwen3）、URM（Qwen-7B）、GLIDE（1B）采用但未公开对比；**SID 作为共享词表**是 LLM 系基座的标配（PLUM SID-v2、OpenOneRec 3×8192、LinkedIn 跨域用户 SID）；**更新频率**从分钟级（HyperCast 部分快照发布、Rec-Distill 流式蒸馏）到天级（Netflix 日微调）到月级（Netflix 月度从头预训练），并普遍需要「新鲜度差距」补偿机制。

### Cited Findings

**数据**
- PinFM：20B 参数、**2 年用户行为**、最大序列 16,000；预训练只用 item ID 序列（故意不用高维预训练 item embedding 以加速），跨多个应用收集；十亿级 item 词表用 8 张各 8000 万行的子表哈希。— [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）
- ExFM：FM 训练数据是**多个 VM 流量数据的聚合**（因此比任一 VM 的分布更复杂、带来跨域偏差）；FM 与 VM 均 >3000 亿流式样本；staleness 实验模型训练 740 亿样本。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）
- HyperCast：FM 输入 = 终身跨面用户历史（含动作类型、时间戳、「LLM 驱动的多模态表征」）+ 按各面重要性选出的非序列辅助特征。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）
- LLaTTE：「数据丰富化（如语义内容 embedding）不是加性的，而是更陡 scaling 曲线的前提，让 scaling 超越稀疏 ID 信号的上限」；模型宽度是容量瓶颈。— [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（A）
- Rec-Distill：教师训练数据通过调整采样比例放大（电商广告采样后约 2 亿样本/天、多场景推荐约 70 亿样本/天、千余特征、原始序列 >20K）；**学生不用扩大的数据也能继承教师从更多数据学到的收益**（教师数据扩大使教师增益 +0.42%→+0.69%，学生 +0.28%→+0.44%）。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（A）
- Meta 训练基础设施：ETT（「每日数百亿训练样本、数千 GPU」）、Versioned Late Materialization（多租户「union 数据集」供推荐漏斗中多个模型租户共享，超长序列预物化导致数据基础设施资源超过 GPU 训练本身）。— [arXiv 2610.02057](https://arxiv.org/abs/2610.02057)（B）、[arXiv 2604.24806](https://arxiv.org/abs/2604.24806)（A）
- OneRec v1：90 台 × 8 GPU，每天约 180 亿样本、540 亿 token；OpenOneRec 标准版 330 亿 token、Pro 版 1300 亿 token。— [arXiv 2506.13695](https://arxiv.org/abs/2506.13695)（A）、[OpenOneRec README](https://github.com/Kuaishou-OneRec/OpenOneRec)（B）
- Netflix（C）：「3 亿+用户数千亿交互」，稀疏注意力 + 滑窗采样处理长历史。— [zenml 转述](https://www.zenml.io/llmops-database/foundation-model-for-personalized-recommendation-at-scale)（C，未核实）
- 蚂蚁/支付宝「Densing Law」：十亿级 Alipay 数据上，原始文本行为的 scaling 收益递减、token 化后持续增益；最小充分 token 化容量的对数与输入 token 数近似线性。— [镜像 2608.23392](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.23392)（2026-08-24，摘要，B）【c】

**目标**
- PinFM：next-token（仅在后续有正反馈 item 的位置预测）+ 未来 L′ 窗口多 token 预测 + 针对「接近下游序列长度」位置的额外损失；下游微调加入排序损失，预训练模块学习率设为排序模型的约 1/10 以免覆盖预训练知识；对 T 天内新生成的候选在预训练模块输出加 dropout。— [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）

- ExFM：FM 直接用真实标签训练（CTR/CVR 等），VM 用「真实标签 + FM logits」；Auxiliary Head 用隔离的任务头接收 FM 监督而非直接作用于服务头。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）

- 阿里国际 LazFormer：生成式预训练自回归生成序列特征以同时初始化稀疏与 dense 参数；可迁移残差适配器抵消 dense 参数负迁移（预训练与排序输入特征不同）；**非对称多 epoch**：每 epoch 重置稀疏参数、累积 dense 参数。— [镜像 2609.14978](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.14978)（2026-09-14，摘要，B）【b】

- PLUM：CPT 语料 = 领域 item 数据 + 用户序列 + 通用文本，以「把新 SID 模态与模型既有知识对齐」。— [arXiv 2510.07784](https://arxiv.org/abs/2510.07784)（A）

**LLM 初始化及其增益证据**
- 正面：PLUM 2×2 消融（R1 随机初始化 SFT / CR1 随机初始化 CPT+SFT / 预训练初始化 ±CPT）——预训练初始化在有无 CPT 下均优于随机初始化，CPT 还提升微调样本效率；定性例子显示随机初始化的 CPT 模型无法完成少样本文本任务。— [arXiv 2510.07784](https://arxiv.org/abs/2510.07784)（A）
- 采用但无公开消融：OpenOneRec（Qwen3）、URM（Qwen-7B）、GLIDE（1B，C）、Netflix GenRec（自研基础 LLM，B）、RecGPT-V3（基座未命名，B）、小红书 QP-OneModel（查询理解，01 笔记）。
- 反面/谨慎：快手 LEARN（2024）称「Rec-to-LLM」（把推荐数据文本化喂 LLM）「在工业中无法产生实际收益」，改为冻结 LLM 做 item 编码器以防灾难性遗忘；LARM（01 笔记）称「直接注入 LLM embedding 收益微弱」；Meta 系（HSTU/LLaTTE/ExFM/PinFM）**不用 LLM 权重初始化**，只用 LLM 生成的多模态/语义特征。— [arXiv 2405.03988](https://arxiv.org/abs/2405.03988)（v3 2024-12，全文，A）
- Snap 研究：LLM 做生成推荐「主要依赖一跳记忆而非语义泛化」，收益集中在可由一跳转移预测的用户；提出 IIRG 多跳协同 + 语义关系训练。— [镜像 2606.17276](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.17276)（2026-06-15，摘要，B；作者 Neil Shah 等为 Snap Research）【c】

**语义 ID 作为共享词表**
- PLUM SID-v2：融合用户行为信号与多模态内容 embedding 的 RQ-VAE，多分辨率码本（首层高分辨率、后层编码低熵残差），缓解 SID 空间稀疏占用。— [arXiv 2510.07784](https://arxiv.org/abs/2510.07784)（A）
- LinkedIn「Quantizing Intent」（作者 Julie Choi、Benjamin Zelditch 等与 Feed-SR 作者重合）：用**有机 feed 活动**构造跨域用户 SID 供广告 CTR 使用；信号越「行为化」迁移越好（用户资料文本 SID AUC +0.036%、活动微调的 LLaMA 用户 embedding SID +0.107%、feed 行为 embedding SID +0.213%）；RQ-FSQ 把预训练 embedding 离散化，存储缩小约 30×/280× 而 AUC 持平或略升；对几乎无广告历史的用户冷启动增益最高 +1.522%。— [镜像 2606.01396](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.01396)（2026-05-31，摘要，B）【a，范围未明】
- OpenOneRec：3 层 × 8192 的残差 K-Means SID 作为 Qwen3 扩展词表，跨短视频/广告/商品三域共享。— [OpenOneRec tokenizer/README](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/tokenizer/README.md)（B）
- Meta Forum（SID 在 Facebook Feed 跨平台数据上学习后迁移到冷启动的 Forum 面）、美团 MBGR 多业务 BID、Snap SID、腾讯 GPR 广告+自然内容共享 SID、快手动态码本——见 01 笔记。

**更新频率**
- HyperCast：模型新鲜度「分钟级」，数据到训练器平均 30 分钟；只发布最近更新的约 30% 权重；在线推理可请求「所有可用 embedding 版本」。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）
- ExFM：FM「定期发布快照」，DAS 切换快照需数分钟并用 Zookeeper 元数据（Zeus）保证一致；FM 监督与 VM 训练间的时延造成「新鲜度差距」，由 Student Adapter 补偿（流式 NE +0.08%，且随时间扩大）。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）
- LLaTTE：上游由「高价值用户事件」触发而非按请求计算。— [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（A）
- Rec-Distill：教师与学生都流式训练；流式蒸馏信号经中间存储/补充数据流以分钟级延迟到达学生；**无流式蒸馏时学生增益 5 天后减半**（+0.10%→+0.05%）；仅用流式、不做批量初始化，5 个月后仍持续落后。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（A）
- Netflix：「每月从头预训练、每日微调、微调后批量刷新 embedding」（C）。— [zenml 转述](https://www.zenml.io/llmops-database/integrating-foundation-models-into-production-personalization-systems)（C，未核实）
- SUM：recurrent training + average pooling 缓解频繁更新导致的 embedding 分布漂移。— [arXiv 2311.09544](https://arxiv.org/abs/2311.09544)（A）
- Shopee KGD：在 90 天生产流上持续刷新编码器并保持增益。— [镜像 2608.02738](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.02738)（B）

### Inferences
- Meta 系「基础模型」的参数大头是稀疏 embedding（万亿级），dense 部分未公开；而国内（Rec-Distill 24B dense、LUM 7B）与 Pinterest（20B）公开的是 dense 规模——两条路线的「大」不是一回事，比较参数量没有意义，应比较训练 FLOPs（ExFM 用 1X=60M FLOPs 的相对尺度正是为此）。
- 「LLM 初始化有用」的公开一手证据只有 PLUM 一例，且其任务是生成式召回（需要语言/世界知识来对齐 SID 与文本）；对纯行为建模的上游 FM，业界主流做法是**用 LLM 产特征而不用 LLM 权重**。
- 更新频率决定了架构：分钟级（HyperCast/ExFM/Rec-Distill）要求 FM 本身流式训练 + 部分快照发布 + 新鲜度补偿；天/月级（Netflix）则必须解决 embedding 空间跨版本一致性。

### Gaps
- 除 OneRec（720 GPU）与 ULTRA-HSTU（数百 H100）外，没有任何 FM 公开训练 GPU·天；PinFM、LLaTTE、HyperCast、Lattice 均未披露训练时长。
- OpenOneRec 技术报告（arXiv 2512.24762）全文未获取，Pro 版工业语料构成与 LLM 初始化 vs 从头训练的对比未知。
- Netflix 月/日更新节奏与正交低秩变换的具体做法只有二手转述。

## 关键问题 3：下游使用方式与 ROI——蒸馏、表征/embedding 迁移、微调、prompt；公开收益与成本；基础模型更新与下游一致性；跨场景/跨国共享的效果与失败案例

### Takeaway
公开数据给出了一张「迁移率表」：黑盒 logits 蒸馏的迁移率在 45–73%（Rec-Distill：24B→1B 65%，7B→1B 73%，跨阶段 50%，多场景推荐 45%），ExFM 的 3.2T FM 给各阶段 VM 带来 0.11–0.25% NE（0.02% 即显著）；表征注入的迁移率更高（HyperCast 0.64–1.0；LLaTTE ≈50% 并带来 +4.3% 转化；LoopFM 在 KD 之上再翻倍）；微调接入（PinFM）做到成本中性并带来 Sitewide Saves +1.20%/+0.72%；prompt 式复用只在召回/意图场景有生产案例（PLUM、RecGPT）。成本侧的共同做法是把 FM 挪出请求路径（异步、缓存、训练数据管道内推理），因此「在线成本中性 + 离线算力集中」是 ROI 成立的前提；更新一致性靠解耦塔（Rec-Distill）、辅助头/适配器（ExFM）、多版本 embedding（HyperCast）、正交变换（Netflix，C）解决；跨场景共享的公开失败模式是跨域偏差、域冲突/跷跷板与师生容量差过大导致迁移率下降，**跨国家共享没有任何公开证据**。

### Cited Findings

**蒸馏（logits）**
- Rec-Distill：迁移率 η =（学生蒸馏后 − 学生原始）/（教师 − 学生原始）；三场景 η = 64%（广告，参数比 1:7）、45%（多场景推荐，1:34）、50%（直播，精排教师→粗排学生，1:5）；教师固定 7B 时学生从 1B 缩到 376M/184M，η 从 73% 降到 65%/48%；教师 24B→1B 学生 η 65%；同参数预算下 4 层×480 维（68%）优于 2 层×640 维（63%）；蒸馏不改变学生自身 scaling 曲线（整体上移）；单塔仅蒸馏损失只 +0.03% AUC，解耦塔 +0.44%；去偏 +0.34%→+0.44%；线上（教师 ≤7B、序列 20K）：电商广告 ADVV +1.00%、ADSS +1.10%、订单 +0.68%、GMV +0.62%；多场景推荐 StayDuration +0.1423%、Finish/U +1.2725%、LT +0.0618%；直播 Watch Duration/U +0.24%、礼物收入/U +0.78%。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（A）【a】
- ExFM：1000X/3.2T FM 对召回（TTSN）、早期（TTSN）、后期（DLRM）三阶段 VM 分别带来 0.11%–0.25% 额外 NE 增益，「越早的阶段增益越大」；FM 使 VM 半年迭代的增益曲线「斜率更陡」（bending the trend）；AH 相对无 AH 的 NE 变化 −4%（文中称「大且稳定」）。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）【a】
- Lattice：基础 Lattice 网络作为教师蒸馏到「精简的面向用户模型」，整体效果见问题 1（+10% 营收顶线、20% 容量节省）。— [arXiv 2512.09200](https://arxiv.org/abs/2512.09200)（A）【a】
- 字节 TM20K（01 笔记）：全序列 Transformer 教师 → token 合并学生，ADSS +1.036%、延迟仅 +5.6%。— [arXiv 2608.07055](https://arxiv.org/abs/2608.07055)（A）【a】
- HyperCast 对 KD 的批评：「师生范式常导致只有低比例的增益从教师迁移到学生」，并引用蒸馏 scaling law 研究「大数据区间学生性能可能被教师损害」。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）

**表征 / embedding 迁移**
- HyperCast：target-aware embeddings（FM 对每个候选 item 产出的目标感知表征，而非稳定的通用用户 embedding）→ expert 的 FM Embedding Module（正则/去噪）→ 与 expert 自身 HSTU 输出融合；迁移率 0.64–1.0；expert 计算 20–40%。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）【a】
- LLaTTE：上游压缩用户 embedding 缓存，在线侧序列模块占在线 FLOPs 约 30%；NE +0.25%、转化 +4.3%。— [arXiv 2601.20083](https://arxiv.org/abs/2601.20083)（A）【a】
- LoopFM：FM 中间 embedding 作 VM 特征，在 KD 之上迁移率约翻倍；三次上线转化 +0.5%/+1.03%/+1.22%。— [镜像 2605.29280](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2605.29280)（B）【a】
- SUM：「用户模型的增益会在所有下游模型上累加」；数百个广告模型消费 SUM embedding。— [arXiv 2311.09544](https://arxiv.org/abs/2311.09544)（A）【a】
- VISTA / AMBER / KuaFu / ChronicleRec / TokenMinds：均为「离线压缩 → 缓存 token/embedding → 多个下游消费」，TokenMinds 缓存命中 96.4%、服务算力 −31%，KuaFu 节省 190 GPU。— 见问题 1 来源（A/B）【a】
- PinFM：微调接入后 Home feed/Related Pins 排序 Sitewide Saves +1.20%/+0.72%、Surface Saves +2.60%/+2.09%（01 笔记），成本中性、延迟边际增加。— [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）【a】
- LinkedIn 跨域 SID：feed 行为 embedding 的 SID 使广告 CTR AUC +0.213%、冷启动用户 +1.522%。— [镜像 2606.01396](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.01396)（B）【a】
- Shopee KGD：GMV/用户 +1.75%、广告收入 +1.53%。— [镜像 2608.02738](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.02738)（B）【a】
- 负面：LARM「直接注入 LLM embedding 收益微弱」需对齐（01 笔记）；LEARN「Rec-to-LLM 无实际收益」。— [arXiv 2504.05217](https://arxiv.org/abs/2504.05217)、[arXiv 2405.03988](https://arxiv.org/abs/2405.03988)（A）

**微调**
- PinFM：每个应用用自己的特征微调整个预训练 transformer + embedding 表，预训练模块 LR 为排序模型的约 1/10。— [arXiv 2507.12704](https://arxiv.org/abs/2507.12704)（A）【a】
- Netflix：全模型或子图微调，「用更少数据与算力达到可比性能」（C）。— [zenml 转述](https://www.zenml.io/llmops-database/integrating-foundation-models-into-production-personalization-systems)（C）
- HyperCast 与 KGD 都指出共享参数微调的缺陷：流式数据下 SFT 灾难性遗忘（HyperCast）、预训练知识与任务几何对共享参数提出冲突要求（KGD）。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）、[镜像 2608.02738](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2608.02738)（B）

**Prompt**
- URM：用 prompt 模板统一多场景/多目标/搜索任务，「零样本任务迁移与 prompt tuning」；PLUM CPT 后具备少样本能力；360Brew 的 prompt 式零样本泛化（论文已撤回）；RecGPT 系用 LLM 推理用户意图（V3 用潜变量推理把输出 token 成本降 200×）。— [arXiv 2502.03041](https://arxiv.org/abs/2502.03041)（A）、[镜像 2607.15591](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2607.15591)（B）

**成本**
- 在线成本中性/下降：HyperCast 延迟与 CPU 中性；PinFM 成本中性；LLaTTE 服务开销极小；RecGPT-V3 端到端服务资源 −52.4%；TokenMinds 上游训练算力 −50%、服务算力 −31%；KuaFu 190 GPU；Lattice 20% 容量；Meta ROCS（请求级计算共享，作者含 Liang Luo、Buyun Zhang、Santanu Kolay，推断为 Meta）召回模型 QPS 最高 3×、短视频排序 logloss −0.5% 且 QPS +50%，已部署于广告与有机面的召回与排序。— [镜像 2607.27744](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2607.27744)（2026-07-30，摘要，B）【a】
- 离线成本集中：ExFM 的 FM 推理在 DAS 中利用标签等待窗（秒级预算）且只覆盖「极小比例」样本；Rec-Distill 学生只在采样子集上训练、教师的数据扩大成本不传给学生；GEM 数千 GPU（C）。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)、[arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（A）

**基础模型更新与下游一致性**
- ExFM：「FM 与 VM 的新鲜度差距会损害 FM 的益处」→ Student Adapter 学习变换 FM 预测；跨域偏差 → Auxiliary Head。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）
- Rec-Distill：解耦塔「即使教师更新延迟、蒸馏管道滞后或教师信号暂时不稳定，主任务塔不受影响」；教师信号物化到 HDFS 以保证实验可复现。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)（A）
- HyperCast：FM 推理服务器同时服务多个 embedding 版本；expert 侧对 FM embedding 做正则/去噪。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）
- Netflix：不同训练轮次 embedding 空间「完全不同」，日微调也会漂移 → 正交低秩变换保持维度语义一致（C）。— [zenml 转述](https://www.zenml.io/llmops-database/integrating-foundation-models-into-production-personalization-systems)（C）
- SUM average pooling；KGD 参数集分离 + 正交校准残差；LoopFM「无架构耦合」。— 见上。

**跨场景 / 跨国共享**
- 正面：Lattice 跨 portfolio 数据共享 + 参数解绑；OneModel 场景感知调制（三个业务流均正向）；MTFM 多场景数据 scaling 有效；LinkedIn feed→广告 SID；OpenOneRec 三域共训 + Amazon 零样本 +26.8%（B）；Meta Forum 冷启面 SID 迁移（01 笔记）；Meta SCALR（作者未标公司）把跨域事件转为目标域合成事件，模型无关，A/B 显著。— [镜像 2606.00282](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.00282)（2026-05-29，摘要，B）【a，公司未明】
- 失败/限制：ExFM 跨域偏差需要 AH；Lattice「朴素整合导致训练不稳定与质量退化（域冲突）」；美团 MBGR 多业务 SID 跷跷板（01 笔记）；Rec-Distill 多场景推荐 η 仅 45%；腾讯 TokenFormer 指出朴素统一序列与非序列字段导致序列坍缩；LinkedIn 的 Feed-SR 公开承认 LLM 排序架构未胜出。— 见上各来源
- 跨国家/多国混合：**未找到任何公开案例给出跨国家共享 FM 的收益或失败**（TikTok X-Rec、Zenith 等论文只说「全球数十亿用户」）。

### Inferences
- 把各家的迁移率换算到「每 1% 教师离线增益能换多少线上」：Rec-Distill 教师 +0.69% AUC → 学生 +0.44% → 广告 GMV +0.62%；ExFM 3.2T FM → VM NE +0.11–0.25%；这说明上游 FM 的 ROI 来自「同一份增益被 N 个下游复用」而非单模型的大幅提升——若下游模型数量少（<10），公开数据不支持建设万亿级 FM。
- 表征注入（HyperCast/LoopFM）之所以迁移率高于 logits 蒸馏，是因为传递带宽更高；代价是下游与 FM 版本耦合（需多版本服务、正交变换、去噪），即把「一致性」问题从训练侧搬到了服务侧。
- 跨国共享无公开证据，但 Meta/TikTok 论文默认「全球一张表」，可推断头部公司的 FM 是跨国训练、按面/场景分 expert，而非按国家分。

### Gaps
- 没有公司公开「FM 训练算力 vs 下游总收益」的美元或 GPU 级 ROI；Lattice 的 20% 容量节省是最接近的数字。
- Netflix 三路径各自收益、Spotify soft-token 用户 embedding 的线上收益均未公开。
- 跨国家共享（多国混合训练、按国家 expert）无任何公开材料。

## 关键问题 4：组织模式——中心基础模型团队 + 场景团队的分工、平台化接口（feature store / 模型仓库）、与 LLM 团队的关系

### Takeaway
公开论文透露的组织模式一致：**一个中心团队维护少数 FM（Meta「几个专门的用户模型」「单一 FM 跨应用」，GEM「中心大脑」，Pinterest 一个 PinFM，Netflix 一个 FM，字节 AML 团队的教师），场景/垂直团队维护多个轻量模型并按各自节奏迭代**，二者通过三类平台接口解耦：(1) 带版本的 embedding/特征存储（SUM SOAP、HyperCast FM 推理服务 + 离线日志层、Netflix Embedding Store、VISTA embedding 交付系统、YouTube UBS）；(2) 蒸馏信号管道（ExFM DAS + 快照发布库 + Zookeeper 元数据，Rec-Distill 中间存储 + 补充数据流 + HDFS 物化）；(3) 多租户共享训练数据集（Meta union dataset、Lattice Zipper 整合数据）。与 LLM 团队的关系表现为「用 LLM 团队的基座/embedding 模型作输入」（PLUM 用 Gemini、OpenOneRec 用 Qwen3 与 Qwen3-Embedding-8B、HyperCast 用「LLM 驱动的多模态表征」、LinkedIn 用活动微调的 LLaMA 用户 embedding），而不是让 LLM 团队直接做推荐模型。

### Cited Findings
- Meta HyperCast 明确把「开发速度」写成贡献：「通过解耦 FM 与 expert 的训练，我们可以用大量 GPU 资源精炼单一 FM，同时不牺牲 expert 模型的快速迭代」；「单一 FM 跨多个应用」；传统范式下「每个面都需要专门开发与调优，为每个面维护专用大模型不可行」。— [arXiv 2508.02929](https://arxiv.org/abs/2508.02929)（A）
- Meta SUM：愿景是「几个专门的用户模型」消费海量用户侧特征，「多个下游模型可以安全地把用户模型输出作为输入特征」；SUM 已进入数百个生产广告模型并扩展到 feed 与质量模型。— [arXiv 2311.09544](https://arxiv.org/abs/2311.09544)（A）
- Meta ExFM：教师团队与 VM 团队解耦的直接动因是「广告推荐涉及多个服务模型（各对应一个服务或排序阶段），为每个服务模型构建和维护专用大教师既低效又不可扩展」；DAS 由 Snapshot Publishing Database + Zeus（Zookeeper）元数据 + 共享数据集构成，「每个 VM 从共享数据集中挑选自己的数据训练」。— [arXiv 2502.17494](https://arxiv.org/abs/2502.17494)（A）
- Meta Lattice：Lattice Partitioner 是「指导 portfolio 整合的策略工具……在资源预算内最大化全局模型性能并确保隐私合规」；整合后「只需少量模型，才能做定制 GPU kernel 与低精度训练/推理」。— [arXiv 2512.09200](https://arxiv.org/abs/2512.09200)（A）
- Meta Mosaic 自称「基础用户建模平台」，并提供「免日志的 embedding 评估方法（CoEval、User Tower Zero-Out）以加速开发」——即为场景团队提供离线评估接口。— [镜像 2607.24015](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2607.24015)（B）
- Meta GEM（C）：「中心大脑」；「直接迁移」给同数据空间的主要垂直模型，「分层迁移」先到领域级 FM 再到垂直模型；目标是「数百个面向用户的垂直模型」。— [GEM 博客转述](https://www.zenml.io/llmops-database/foundation-model-for-ads-recommendation-at-scale)（C，未核实）

### Inferences
- 「中心 FM + 场景 expert」在 Meta 已经演化为三层：平台数据（union dataset、DAS）→ FM 家族（GEM 中心 FM、领域 FM、Mosaic 专家舰队）→ 数百个垂直模型；组织上对应「数据/训练平台团队、FM 团队、场景团队」。字节公开的 Rec-Distill 结构（AML 架构 + 场景团队学生）与之同构，但教师仍按场景分别放大。
- 平台接口的最小集合是：带版本的 embedding 存储、教师预测/表征的日志管道、以及（若做表征注入）多版本并行服务；没有这三项，中心 FM 的更新会直接变成场景团队的回归风险。
- LLM 团队提供的是「原料」（基座权重、embedding 模型、多模态表征），推荐团队负责 SID 化、共预训练与服务改造；OpenOneRec 的 on-policy 蒸馏流程说明推荐团队还要负责「把 LLM 通用能力保住」。

### Gaps
- 各公司 FM 团队规模、FM 与场景团队的考核/成本分摊机制均无公开材料。
- GEM「领域级 FM」的数量与归属团队未核实。
- 快手 OneRec 团队与各垂直 One 系列（OneMall/OneLive/GR4AD）的组织关系未公开。

## 关键问题 5：局限与失败——记忆 vs 泛化、线上延迟、更新滞后、冷启动、多目标冲突、算力成本是否被收益覆盖

### Takeaway
公开材料里的失败与限制集中在五处：(1) **记忆 vs 泛化**——学术对照（UCSD）表明生成式/SID 模型赢在泛化实例、ID 模型赢在记忆实例，且 GR 的「item 级泛化」99% 以上可归结为 token 级记忆；Snap 发现 LLM 推荐主要靠一跳记忆；Meta 的工程回应是保留「数百万亿参数的记忆」（VISTA）并用语义特征「弯曲」scaling 曲线（LLaTTE），而非二选一；(2) **延迟**——所有上线的 FM 都在请求路径之外（异步/缓存/训练管道内推理），在线同步 LLM 仍不经济（URM QPS<1，RecGPT-V3 要靠记忆中枢与潜推理把服务资源砍半）；(3) **更新滞后**——FM 与下游的新鲜度差距会直接吞掉收益（ExFM 用 SA 补 0.08% NE，Rec-Distill 无流式蒸馏 5 天减半），SFT 在流式数据下灾难性遗忘；(4) **冷启动**反而是 FM 的优势项（PinFM 新 item +20%，LinkedIn 冷启动用户 +1.522%，PLUM 少样本），但需要专门处理（PinFM 对新候选加 dropout）；(5) **多目标/多域冲突**在整合时普遍出现（Lattice 域冲突、OneModel 需调制、MBGR 跷跷板、TokenFormer 序列坍缩）；算力是否被覆盖没有公开的货币化答案，只有「迁移率随师生差距递减」（73%→65%→48%）与「0.02% NE 即显著」的隐含尺度。另一个被忽视的失败信号：LinkedIn 360Brew 论文撤回、Feed 团队改用非 LLM 序列模型。

### Cited Findings
- 记忆 vs 泛化（学术）：UCSD 等《How Well Does Generative Recommendation Generalize?》按「需要记忆训练中见过的转移」或「需要组合已知模式预测未见转移」划分测试实例：TIGER 在泛化实例上 NDCG@10 比 SASRec 高（Office +58.8%），在记忆实例上低（Yelp −43.6%）；**GR 中 >99% 的 item 级泛化转移至少被 1-gram 前缀 token 记忆支持**；提出记忆感知指示器逐实例自适应组合两者。— [镜像 2603.19809](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2603.19809)（2026-03-20，摘要，B）【c】
- Snap 研究：LLM-GR 的收益主要来自可由一跳转移预测的用户。— [镜像 2606.17276](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.17276)（B）【c】
- Meta VISTA 标题即「用数百万亿参数做海量记忆」，并指出「全序列建模方法如 HSTU 受高计算成本限制，在 GPU 容量不足的公司难以普及」。— [arXiv 2510.22049](https://arxiv.org/abs/2510.22049)（A）
- 美团 MTGR「放弃交叉特征显著退化且 scaling 无法弥补」、阿里 LUM 对 E2E-GR 丢失 DLRM 实践优势的批评（01 笔记）。— [arXiv 2505.18654](https://arxiv.org/abs/2505.18654)、[arXiv 2502.08309](https://arxiv.org/abs/2502.08309)（A）
- 行为 FM scaling law 研究：采样训练目标与部署排序指标不一致、评估指标改变计算最优配方；高算力时瓶颈是候选轴内存。— [镜像 2606.05257](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2606.05257)（B）【c】

- 多目标/多域：Lattice「朴素整合导致训练不稳定与质量退化（域冲突）」→ 参数解绑；OneModel 场景感知调制；ExFM 跨域偏差；TokenFormer 序列坍缩传播；快手「数百个目标」；Rec-Distill 多场景推荐 η 45%。— 见上各来源
- 算力 vs 收益：Rec-Distill 引言明确「超大模型训练/部署算力快速增长而线上指标边际收益递减，降低整体 ROI」是动机；η 随师生差距递减（7B→1B 73%，24B→1B 65%，1B 学生缩到 184M 时 48%）；ExFM 以 0.02% NE 为显著阈值、3.2T FM 带来 0.11–0.25%；HyperCast expert 只需 20–40% 计算但 FM 本身「数百到数千 GPU」；GEM 数千 GPU 换 +3–5% 转化（C）；Lattice 20% 容量节省是唯一「净节省」类数字。— [arXiv 2605.29755](https://arxiv.org/abs/2605.29755)、[arXiv 2502.17494](https://arxiv.org/abs/2502.17494)、[arXiv 2508.02929](https://arxiv.org/abs/2508.02929)、[arXiv 2512.09200](https://arxiv.org/abs/2512.09200)（A）
- 退缩案例：360Brew 论文撤回、第三方称其自述为「pre-production 研究模型」；Feed-SR 选择 transformer 序列排序器并说明 LLM 排序架构未取得最佳平衡。— [arXiv 2501.16450](https://arxiv.org/abs/2501.16450)（C）、[镜像 2602.12354](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2602.12354)（B）
- Pinterest 关于生成模型增强推荐的新型危害分类（01 笔记）。— [镜像 2609.33073](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.33073)（B）

### Inferences
- 「记忆 vs 泛化」在工业上的解法已经收敛为**混合**：FM 负责泛化（语义、长序列、跨域），下游/稀疏表负责记忆（ID、交叉特征）；这解释了为什么 Meta FM 是万亿稀疏参数 + 序列骨干，而不是纯 LLM。
- 「算力被收益覆盖」的隐含判据可从公开数据推出：下游模型数 N × 单模型迁移增益 ≥ FM 训练 + 日志/缓存成本；Meta（数百 VM）、字节（广告/推荐/直播多学生）、Pinterest（两大面）都满足，单场景团队不满足。
- 更新滞后是比延迟更隐蔽的失败点：延迟可以靠异步化一次性解决，新鲜度差距则需要持续的补偿机制与流式教师，这部分运维成本在论文中几乎不量化。

### Gaps
- 未找到 Meta 自己关于「生成式推荐泛化 vs 记忆」的专门研究（最接近的是 VISTA 的记忆路线与 LLaTTE 的语义特征结论）；任务书提到的「Meta 关于 GR 泛化的研究」未能定位到具体论文。
- 没有公司公开 FM 的失败/回滚案例；失败信息只能从动机段落与 360Brew 撤回反推。
- 上游 FM 的日志/缓存存储成本（VISTA 承认「以存储换计算」）无公开量级。

## 关键问题 6：起步路径——公开案例的演进顺序、每条路径的前置基础设施与典型周期

### Takeaway
公开案例显示四条互不排斥的演进顺序：**路径 A「先上游用户模型蒸馏/表征注入」**（Meta：SUM 2023-24 → ExFM 2025-02 → HyperCast 2025-08 → GEM 2025 Q2 上线 → LLaTTE 2026-01 → LoopFM/Mosaic/Lattice 2025-12–2026-07；Pinterest PinFM 2025；字节 RankMixer/LONGER → TokenMixer-Large → Rec-Distill 2026-05；腾讯 KuaFu/ChronicleRec；阿里 LUM），前置条件是成熟的 DLRM 栈 + 带版本的 embedding 存储 + 教师日志管道 + 流式训练；**路径 B「先语义 ID 作共享词表」**（YouTube PLUM、Spotify GLIDE/NEO、Snap SID→GRP、LinkedIn 跨域 SID、Meta Forum），前置条件是多模态 item embedding 模型与 RQ tokenizer 治理；**路径 C「LLM 初始化的基座」**（PLUM 从 Gemini、OpenOneRec 从 Qwen3、RecGPT、URM），前置条件是 LLM 训练/服务基础设施（FSDP/verl、词表扩展、共预训练、on-policy 蒸馏）与异步/prefill-only 服务预算；**路径 D「端到端生成式」**（快手 OneRec 系，见 01 笔记）。对刚起步、已有多场景 DLRM 的团队，公开证据最支持 A（成本中性、迁移率可测），B 作为 A 的并行项解决冷启动与新召回源，C 只有在 A/B 的管道已就位且有 LLM 团队供给基座时才有公开成功先例。典型周期：Meta 从 SUM 到 HyperCast 约 15 个月、GEM 从上线到分层迁移约 1 年；Rec-Distill 的流式蒸馏消融跑了 5 个月；Netflix 月度预训练 + 日微调（C）。

### Cited Findings
- Meta 时间线：SUM（arXiv v1 2023-11，WWW'24，「数百个」广告模型）→ ExFM（2025-02，万亿参数外部蒸馏 FM，1-to-N）→ HyperCast（2025-08，FM→expert 表征）→ GEM 2025 年 Q2 上线（C）→ LLaTTE（2026-01，异步上游用户模型）→ Lattice（2025-12，portfolio 整合 + 蒸馏）→ LoopFM（2026-05，表征叠加 KD）→ Mosaic（2026-07，专家舰队）→ AMBER（2026-08，事件 token）；生成式召回/SID（GRACE、Forum）直到 2026 下半年才出现（01 笔记）。— 见问题 1 各来源

### Inferences
- 四条路径对应四种「已有资产」：有大量 DLRM 下游 → A；有多模态内容理解团队 → B；有 LLM 团队与异步服务预算 → C；有清晰价值目标的垂直场景（广告/电商/本地生活）→ D（01 笔记）。
- 最便宜的第一步是 A 的「教师日志版」（Rec-Distill/ExFM）：不改在线模型架构、学生解耦塔隔离风险、迁移率可离线量化（η），失败可回滚；第二步才是表征注入（需多版本 embedding 服务）。
- B 的门槛被低估：PLUM、LinkedIn、OpenOneRec 都依赖高质量多模态/行为 embedding 模型（Gemini、LLaMA 活动微调、Qwen3-Embedding-8B），SID 质量上限由该模型决定。
- 典型周期：从零到首个上游 FM 上线约 1 年（Meta SUM→ExFM、Pinterest PinFM 均为年级工程），从 FM 上线到「分层 FM/多专家」再约 1 年。

### Gaps
- 没有公司公开从立项到上线的日历时间，上述周期由论文日期推断。
- 中小规模（DAU < 1 亿）公司的 FM 起步案例几乎没有公开材料（Shopee KGD、Comcast 用户画像研究是少数）。

## 关键问题 7：未来 12 个月的判断

### Takeaway
基于 2026-01 至 2026-10 的论文密度与各家路线图，未来 12 个月最可能的变化是：(1) **上游 FM 从「logits 蒸馏」升级为「表征/事件 token 注入」成为默认**（LoopFM、AMBER、ChronicleRec、KuaFu、TokenMinds 在 2026 年集中出现）；(2) **FM 家族分层化与专家舰队化**（GEM 分层迁移、Mosaic、Lattice）取代「一个 FM」叙事；(3) **LLM 基座推荐模型固定在召回/意图/可解释层并以潜推理 + 记忆中枢控制成本**（RecGPT-V3、OneReason、GLIDE），在线精排 LLM 基座不会成为主流；(4) 开源基座（OpenOneRec）与基准（RecIF-Bench、Kwai26、TencentGR）推动「LLM 初始化是否有益」的公开消融增多；(5) 平台级统一排序模型（OneModel、MTFM、UniFormer）在国内平台继续扩面，收益主要是计算共享。

### Cited Findings
- 2026 年新出现的表征/事件级迁移工作：LoopFM（2026-05）、AMBER（2026-08）、ChronicleRec（2026-09）、KuaFu（2026-09）、TokenMinds（2026-06）、Mosaic（2026-07）、ROCS（2026-07）。— 见上各镜像（B）
- GEM 2026-08 博客称 12 个月内训练 FLOPs 扩大 4×（C）；Lattice 把「整合后模型少」作为低精度与定制 kernel 的前提。— [GEM 博客转述](https://www.zenml.io/llmops-database/foundation-model-for-ads-recommendation-at-scale)（C）、[arXiv 2512.09200](https://arxiv.org/abs/2512.09200)（A）
- RecGPT-V3 以「无状态建模、标签瓶颈、显式推理低效」为 V3 动机并给出 −52.4% 服务资源；OneReason/WhisperRec/TGR-Reason 均以避免在线 CoT 为目标（01 笔记）。— [镜像 2607.15591](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2607.15591)（B）
- OpenOneRec 路线图：更多模型尺寸、统一 verl 实现、一键复现；Kuaishou LLM-Rec Challenge 2026 用 OneReason-pretrain 基座（01 笔记）。— [OpenOneRec README](https://github.com/Kuaishou-OneRec/OpenOneRec)（B）
- LinkedIn Feed-SR 的选择与 360Brew 撤回；Netflix GenRec 采用 prefill-only；URM QPS<1。— 见问题 1/5

### Inferences
- 可验证预测：(a) 至少一家公司公开「FM 中间表征 + 事件 token」替代 logits 蒸馏的全量结果（候选：Meta LoopFM/AMBER 扩面、腾讯 ChronicleRec）；(b) GEM 或其领域 FM 公开架构细节（论文形式）；(c) OpenOneRec 发布含「从头训练 vs Qwen3 初始化」消融的 v2；(d) 国内至少一家主 feed 公开「跨业务流统一排序 FM」全量（小红书已做，候选：美团 MTFM、快手 UniFormer 扩面）。
- 不太可能发生：在线同步 10B+ LLM 进入 feed 级精排主链路；跨国家共享 FM 的公开收益数据。

### Gaps
- 预测基于论文发表节奏，各公司内部路线图无公开信息。

## 关键问题 8（专项）：字节跳动 / 抖音 / TikTok 公开的基础模型相关资料

### Takeaway
截至 2026-10，字节公开材料中**没有以「foundation model」命名的公司级推荐基座**；最接近的是 **Rec-Distill（2026-05）**：按场景（电商广告、多场景推荐、直播）各自放大的离线教师（最大 24B dense + 20K 序列，TokenMixer-Large + LONGER 架构）通过解耦的批+流黑盒蒸馏喂给在线学生（广告学生 1B/5K 序列），一个教师可跨阶段服务多个学生，已部署于抖音与 TikTok 的广告/推荐/直播；配套的公开基础是「把在线模型做大」（RankMixer 1B 全量、TokenMixer-Large 7B 在线/15B 离线、LONGER/STCA/SequenceO1 10k–100k 序列）与「用户侧计算共享」（UG-Sep 延迟 −20%）；LLM 侧的公开工作是 HLLM（2024）、抖音多模态 embedding 模型（2026-08）与搜索/音乐等垂直应用。与 Meta 的差异是：字节公开的教师是**场景级**而非跨场景中心 FM，迁移靠 logits 而非表征。

### Cited Findings
- **Rec-Distill**（ByteDance AML + ByteDance，arXiv 2605.29755，2026-05-28，全文，A）【a】：
  - 问题定义：蒸馏增益 = 教师增益 × 迁移率 η；教师沿 dense 参数（TokenMixer-Large 至 24B）、序列长度（LONGER 至 20K）、数据量（提高采样比例）三维放大；黑盒 logits + CE 损失（放弃「任务损失与蒸馏损失权重和为 1」的约束，二分类下蒸馏损失可比任务损失小两个量级，需经验调 α；配置不当损失 ≥0.05%）；「前向蒸馏」（教师前向时写出预测，避免稀疏特征强记忆导致的 train-then-predict 泄漏）；解耦塔学生（主任务塔只用真实标签服务上线，辅助塔接收蒸馏信号，共享骨干）；采样感知去偏（师生采样策略不同时把教师原始 logit 投影到学生侧校正空间）；批蒸馏快速收敛 + 流式蒸馏分钟级跟进；教师信号物化到 HDFS 保证可复现。
  - 数据：抖音电商广告 CVR（千余特征、原始序列 >20K、采样后约 2 亿样本/天）、抖音多场景推荐（短视频 + 图文 feed，完播/时长/点赞等多目标，约 70 亿样本/天）、TikTok 直播推荐（数千特征、数十个目标）。
  - 结果：见问题 3；线上学生从「最大 7B 教师、20K 序列」蒸馏（24B 教师仅离线验证 η 65%）。
  - 与 Meta ExFM 的自我定位：「ExFM 主要关注算力分摊，未系统解决如何在把教师放到极大时最大化知识迁移」。
- **UG-Sep（Compute Only Once）**（arXiv 2602.10455，2026-02-11，全文，A）【a】：在 RankMixer 类 dense 交互架构中用掩码分离用户侧与 item 侧信息流，使一部分 token 在各层保持纯用户侧表征从而跨样本复用（用户级聚合）；信息补偿模块恢复被压抑的交互；W8A16 权重量化缓解内存带宽；字节「多个重要业务场景」A/B：推理延迟最高 −20%，用户体验与商业指标无负向。— 本地镜像 [guyulongcs 仓库](https://github.com/guyulongcs/Awesome-Deep-Learning-Papers-for-Search-Recommendation-Advertising)
- **HyFormer**（arXiv 2601.12681，2026-01-19，全文，A）【a】：统一混合 transformer 把长序列建模（LONGER 式 query token 压缩）与特征交互（RankMixer 式 token mixing）合为单骨干（Query Decoding + Query Boosting 交替），在十亿级工业数据上同参数/FLOPs 优于 LONGER + RankMixer 流水线且 scaling 更好；「部署于字节，每日服务数十亿用户」，高流量场景 A/B 显著。
- **Zenith**（arXiv 2601.21285，v3 2026-02-05，全文，A）【a】：TikTok Live 排序：少量高维 Prime Tokens + Token Fusion/Token Boost，scaling law 优于其他排序架构；A/B：CTR AUC +1.05%、logloss −1.10%，Quality Watch Session/User +9.93%、Quality Watch Duration/User +8.11%；文中评论生成式推荐「训练效率与推理延迟面临显著挑战」、传统模型可作为生成模型的奖励模型。
- **TokenMixer-Large**（01 笔记）：线上 7B（离线 15B）、「稀疏训练 + 稀疏服务」、广告骨干 MFU 60%、多场景部署；**TM20K**：全序列教师 → token 合并学生；**MDL**：场景/任务 token 化为 prompt 式参数激活（抖音搜索全量）；**LONGER/STCA/SequenceO1**：10k–100k 序列全量；**OneTrans/OneTrans-V2**：统一特征交互与序列、统一召回/粗排/精排（GMV +9.74%、吞吐 3.2×）；**GEAR/X-Rec**：广告生成召回与 TikTok 垂类连续空间生成召回。— [arXiv 2602.06563](https://arxiv.org/abs/2602.06563)、[arXiv 2608.07055](https://arxiv.org/abs/2608.07055)、[arXiv 2602.07520](https://arxiv.org/abs/2602.07520)、[arXiv 2505.04421](https://arxiv.org/abs/2505.04421)、[arXiv 2511.06077](https://arxiv.org/abs/2511.06077)、[镜像 2609.08443](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.08443)、[arXiv 2510.26104](https://arxiv.org/abs/2510.26104)、[镜像 2609.28589](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.28589)、[镜像 2609.39327](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.39327)、[镜像 2609.29180](https://github.com/JyiHUO/arxiv_daily_recommendation_system/releases/tag/2609.29180)（A/B）【a】
- LLM/多模态侧：HLLM（2024，1B/7B 层级 LLM 做 item/用户表征，无线上说明）；HLLM-Creator（搜索广告标题生成）；抖音多模态 embedding 模型技术报告（2026-08，搜索 A/B LT +0.1%）；MuChator（抖音音乐会话式发现）；STEPS（agentic push）。— [GitHub ByteDance/HLLM](https://github.com/ByteDance/HLLM)（B）、01 笔记
- 组织信号：Rec-Distill 作者分属「ByteDance AML」（架构/训练平台）与「ByteDance」（业务），教师架构沿用 AML 的 TokenMixer-Large/LONGER；Zenith 署名 TikTok；UG-Sep/HyFormer 与 RankMixer/TokenMixer-Large 作者高度重合（Yuchao Zheng、Deping Xie、Zhe Chen 等）。— 各论文作者栏（A）

### Inferences
- 字节公开路线是「在线模型 scaling 优先、教师蒸馏其次」，与 Meta「中心 FM 优先」相反；原因可从 RankMixer/TokenMixer-Large 的 MFU 45–60% 与稀疏服务看出——字节先把在线模型做到 7B 仍满足延迟，再用 24B 教师突破在线上限。
- Rec-Distill 的 1-to-N 目前是「一个场景的教师 → 该场景的精排/粗排学生」，尚未公开跨场景（广告↔推荐↔直播）共享教师；若未来出现跨场景教师，其公开迁移率基准将是 45–64%。
- UG-Sep/HyFormer/OneTrans 说明字节在「用户侧计算一次、多候选共享」上与 Meta ROCS、小红书 OneModel 共享用户塔、快手 UniFormer 走同一方向。

### Gaps
- 字节未公开任何跨场景/跨国的用户基础模型、SID 共享词表治理或 LLM 初始化的推荐基座论文；TikTok 官方博客亦无相关专文。
- Rec-Distill 的教师训练 GPU 数、教师更新频率（流式但未给快照间隔）、学生训练数据采样比例均未披露。

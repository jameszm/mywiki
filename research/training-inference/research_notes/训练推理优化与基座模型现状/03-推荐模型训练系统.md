## 1. 稀疏/embedding 训练栈的现状与 2025–2026 更新

### Takeaway
2025 下半年到 2026 年，公开的稀疏训练栈收敛成三条产品化路线：**Meta/TorchRec**（八个版本：v1.3.0→v1.9.1，主线是 2D 并行→Fully Sharded 2D→动态 resharding→KVZCH/DRAM-SSD 虚拟表→TPU SparseCore 实验包）、**NVIDIA recsys-examples**（月度发布 v25.05→v26.08，DynamicEmb 从"GPU 哈希表"长成"带准入/淘汰/增量 dump+replay 的训练-服务同步组件"，HSTU 训练例子把 TorchRec 与 Megatron-Core 的 DP/TP/SP/PP/CP 拼在一起，HugeCTR 自 25.03 起只发 Dockerfile 源码、HPS 与 Embedding Cache 已弃用）、**阿里 RecIS**（2025-09 开源，PyTorch 生态上的稀疏-稠密统一框架，SORT/EST/LUM 都在其上训练）。字节公开的训练框架仍是"混合分布式：sparse 异步、dense 同步"（RankMixer/TokenMixer-Large/MixFormer 原文措辞）加 LONGER 的"全同步 GPU 稠密+稀疏统一更新"，Monolith 仓库 2023-11 后无提交、Primus 开源调度器 2025-12 归档；快手 SKAI 只有 OneRec 技术报告里的一段描述。"参数服务器 vs 全 GPU"在公开材料里不是二选一，而是 **GPU 哈希表/HBM 缓存 + 主机内存（+SSD 虚拟表）** 的分层，并以 admission/eviction 控制表增长。

### Cited Findings

**TorchRec（Meta，官方仓库，生产实践）**
- 版本线（GitHub Releases 页，年份按配套 torch 版本推断：torch 2.8→2.14）：v1.3.0（9/13，torch 2.8.0）新增 Fused SDD 流水线（optimizer 与 embedding lookup 重叠，"对 Shampoo 等重优化器提升吞吐"）、SDD 流水线支持 2D 分片、**训练中动态 resharding API**（table-wise/column-wise，"约 100 GB 停机约 200 ms，在最多 128 张 A100 上测试"）、KVZCH 原型（TBE 之上抽象后端内存，可指向 SSD/远程内存/主机 DRAM）、MPZCH 多轮线性探测 CUDA kernel、**ModelDeltaTracker**；v1.4.0（12/07）Resharding API、仓库迁到 meta-pytorch 组织；v1.5.0（2/15）**Fully Sharded 2D Parallelism**（不均匀分片、动态 2D）、FP8 量化通信可指定输出 dtype、就地 batch 拷贝省 HBM、Python free-threading；v1.6.0（3/15）梯度累积、eval 流水线、SDD Lite、Memory Stashing、Triton TBE、新 EmbeddingPerfEstimator；v1.7.0（6/22）FP8 rowwise padding 用于量化 AllToAll pooled embeddings、MP-ZCH 的 2D 分片、`clear_data_dist_inputs` 在 AllToAll 后释放 KJT 输入、PEC 多流集合通信重叠积木、managed collision/ZCH 进入 OSS；v1.8.0（8/13）eval-fused 流水线把 embedding lookup 与 forward 重叠、**DRAM_SSD 虚拟表后端**、memory stashing 分块主机传输、修复 DMPCollection 2D 分片 hang；v1.9.0（9/11）2D 同步的异步 `AR_COL`、EMS 在 2D 同步前恢复、**`tpu` 成为 planner 与 DMP 的 compute device + Pallas embedding kernel**、`TrainPipelinePEC`、Maglev 分阶段流水线、KJT 保持 stride-per-key-per-rank；v1.9.1（9/30，torch 2.14.0，fbgemm-gpu 1.9.0，CUDA 12.6/13.0）新增**实验性 TPU SparseCore embedding 包 `torchrec.experimental.torch_tpu`** — [GitHub Releases](https://github.com/pytorch/torchrec/releases)（官方发布说明，由抓取工具摘要，A）。主线 `version.txt` = 1.10.0a0，最近提交 2026-10-08"Dispatch eval prefetch on a background worker" — [本地克隆 pytorch/torchrec](https://github.com/pytorch/torchrec)（A）。
- 2D 并行的语义（`DMPCollection` docstring）：一个 DMP 只在部分 rank 上分片，"同一分片的副本落在同一节点内的 rank 上，用节点内带宽做 all-reduce 参数同步"；DEFAULT/PER_MODULE 策略在 `sync()` 时对权重与优化器状态做 `allreduce_coalesced(AVG)`，**FULLY_SHARDED** 策略改为前向 `reduce_scatter_tensor`、反向 `all_gather_into_tensor` 逐迭代自动同步、通常不再调用 `sync()`；checkpoint 必须用 DTensor state dict；分片计划按 sharding group world size 生成后 `planner.collective_plan` 广播 — [torchrec/distributed/model_parallel.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/model_parallel.py)（源码，A）。Meta 博客称原有训练栈"对数百 GPU 高度优化，但无法高效扩到数千 GPU"，2D embedding 并行（稀疏部分数据并行 × 表模型并行）"现在驱动 Meta 最大的推荐模型训练"，核心难题之一是 GPU 增多后的负载不均/straggler — [pytorch.org 博客](https://pytorch.org/blog/scaling-recommendation-2d-sparse-parallelism/)（B，搜索摘要）；PyTorch Conference EU 2026 有"1,000+ GPU 规模系统设计经验"议题 — [sched.com](https://pytorchconferenceeu2026.sched.com/event/2HiqL)（B）。
- 训练流水线家族（源码类名与 docstring）：`TrainPipelineSparseDist`（三条 CUDA stream：memcpy 设备传输 / data_dist 做 `input_dist()` / 默认流做 fwd-bwd，用于隐藏 all2all 延迟）、`TrainPipelineSparseDistLite`（只保持 1 个 batch 在途以换显存）、`TrainPipelineFusedSparseDist`、**`TrainPipelineSemiSync`**（"半同步"：第 B 个 batch 用 B-2 时更新的参数计算，使 B 的 embedding all-to-all 与 B-1 的前向完全重叠，"显著提高峰值训练性能"；可选 `stash_gradients` 保证真正半同步；2D 分片下可设 `dmp_collection_sync_interval_batches` 每 N 个 batch 同步一次 DMP）、`PrefetchTrainPipelineSparseDist`、`StagedTrainPipeline`、`TrainPipelinePEC`、实验性的 `TrainPipelineSparseDistEmbStash`/`TrainPipelinePrefetchEMS`/`EvalPipelineCPUSparse` 等 — [train_pipelines.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/train_pipeline/train_pipelines.py)、[experimental_pipelines.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/train_pipeline/experimental_pipelines.py)（A）。
- 分片类型：DATA_PARALLEL、TABLE_WISE、COLUMN_WISE、ROW_WISE、TABLE_ROW_WISE（节点内 row-wise、节点间 table-wise，"节点内通信更快时有用"）、TABLE_COLUMN_WISE、GRID_SHARD（CW×TWRW 的行列网格）；planner 的合法 compute device 为 `{"cuda","mtia","cpu","tpu"}`，HBM 检查只对 cuda/mtia 做 — [types.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/types.py)、[planner/types.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/planner/types.py)（A）。
- 量化通信 codec：`CommType` 支持 BF16/FP8/INT8/**MX4**（FP8 与 MX4 共用统一输出 dtype，可分别设前向/反向精度与 `fp8_quantize_dim`） — [fbgemm_qcomm_codec.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/fbgemm_qcomm_codec.py)（A）。
- 无碰撞 embedding 的两份 RFC：RFC-0001"Dynamic Embedding with PS"由**腾讯**工程师（Zilin Zhu 等）提出，用外接参数服务器（示例 Redis）给 TorchRec 加动态 embedding，`contrib/dynamic_embedding` 以 `tde.wrap(dataloader, model)` 把 PS 拉取/驱逐与数据加载流水线化，并允许自定义 PS 扩展（.so 实现 4 个函数）；RFC-0002"Flexible Collision Free Embedding Table"（Meta，2025-04-13 更新，状态 Published）指出固定大小表 + 统一哈希"碰撞率高、存储低效"，ZCH 虽改善模型新鲜度但 remapper 方案扩展性差，提出用 2^63 哈希空间 + bucket-aware 分片/再分片（interleave 或 chunk 两种 bucket 映射，bucket 顺序分配给 trainer，如 1000 bucket/100 trainer 各 10 个连续 bucket）天然免碰撞 — [RFC-0001](https://github.com/pytorch/torchrec/blob/main/rfc/RFC-0001-dynamic-embedding-with-PS.md)、[RFC-0002](https://github.com/pytorch/torchrec/blob/main/rfc/RFC-0002-Flexible-Collision-Free-Embedding-Table.md)（A）。主线代码中已有 `VirtualTableEvictionPolicy`（Count/FeatureScore/Timestamp/CountTimestampMixed/FeatureL2Norm/NoEviction）与 `EmbeddingComputeKernel.DRAM_SSD_VIRTUAL_TABLE`、planner 的 `log_kvzch_summary` — [embedding_configs.py](https://github.com/pytorch/torchrec/blob/main/torchrec/modules/embedding_configs.py)（A）。
- TPU 包内容（主线 `torchrec/experimental/torch_tpu/`）：`modules/`（fused embedding、table_stacking、optimizers）、`pallas/`（pooled lookup、permute、fwd/bwd 测试）、`checkpoint/`（`SparseCoreSavePlanner/LoadPlanner`）、`datasets/`（`SparseCoreDataLoader`、`PrefetchDataLoader`）、`uneven_all_to_all.py`（"TPU all-to-all 需要对 KJT 与 pooled embedding 的不均匀 split 做 padding，用小的元数据 reduction 求全局最大 split"），依赖 `jax`/`etils`，OSS 构建不含 `pybind_input_preprocessing` 扩展 — [torch_tpu/__init__.py](https://github.com/pytorch/torchrec/blob/main/torchrec/experimental/torch_tpu/__init__.py)（源码，A）。

**NVIDIA recsys-examples / DynamicEmb / HSTU 训练栈（官方仓库，技术报告级，规模为公开 benchmark）**
- 发布节奏与训练侧内容（CHANGELOG + README）：v25.05（2025-05-29）DynamicEmb 支持 EmbeddingBagCollection、HSTU 层 LayerNorm/dropout 融合（端到端约 1.2×）；v25.06（7/4）LFU 淘汰、lookup 提速、HSTU 流水线、层重计算、jagged 拼接自定义 CUDA 算子；v25.07（8/1）HSTU 层 tensor parallel；v25.08（9/8）DynamicEmb cache（热 embedding 在 cache 与 storage 间迁移）、eval 模式；v25.09（10/20）训练例子加预取与缓存、DynamicEmb 分布式 dump 与内存扩缩、HSTU attention FP8；v25.10（11/11）**HSTU sequence parallelism**、LRU score checkpoint、梯度裁剪、把"scaling 序列长度"与"最大序列长度上限"解耦、SM89 训练支持；v25.11（12/10）**admission**；v25.12（2026-1/13）Triton 推理与首个 SID-GR 例子；v26.01（2/13）**workload-balanced batch shuffling**（数据并行负载均衡）、EBC 的缓存/预取；v26.03（4/14）DynamicEmb 表融合与扩容、容量对齐 `bucket_capacity` 不再要求 2 的幂、HSTU attention 迁到 `fbgemm_gpu_hstu` 包、减少 jagged 处理中的 D2H 同步、端到端训练 benchmark 套件；v26.05（6/15）Blackwell sm_100 上 HSTU+DynamicEmb 端到端训练；v26.06（7/14）LFU 表的增量 dump（`LruLfu` 复合评分）、修复混合维度 padded-buffer 优化器与主机 VMM 虚拟地址耗尽；v26.07（8/10）复合 `(TIMESTAMP, LFU)` 淘汰 + JIT 自定义评分函数（如时间衰减 LFU）、`EvictedItemMode.RETAIN_KEY`/`pop_evicted_keys()`、`incremental_dump()` 返回结构化 `DeltaDumpResult`；v26.08（9/13）**`replay_increment()`**、weighted-SUM EBC（混合维度、融合 fwd/bwd kernel）、checkpoint 按表原生 fp32/fp16/bf16 存储、**Talos** — [CHANGELOG.md](https://github.com/NVIDIA/recsys-examples/blob/main/CHANGELOG.md)、[README.md](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）。最近提交 2026-10-04"keep rowwise Adagrad accumulator in fp32 for 16-bit tables"（A）。
- DynamicEmb 的存储模型：模型并行动态表，"GPU 优化的带评分哈希表后端，把 key-value 存在 GPU HBM 以及主机内存"，lookup kernel"主要来自 EMBark 论文（RecSys 2024）"；benchmark 套件的四种放置：全表 HBM（gpu_ratio 1.0）、10% HBM 作 LRU cache（caching）、10% HBM 的 HybridStorage（不缓存）、纯 UVM（gpu_ratio 0）；版本锁定 FBGEMM_GPU v1.5.0 + TorchRec release/V1.5.0；`InferenceEmbeddingTable` 可 torch.export，用 NV-Embedding-Cache 的 `LinearUVMEmbedding` — [corelib/dynamicemb/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/README.md)、[benchmark/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/benchmark/README.md)（A）。
- DynamicEmb 相对 TorchRec 静态表的查表开销（8×H100 NVSwitch 单机，DLRM 26 特征融合成一张大表，全局 batch 65536）：开启索引去重 TorchRec 14.88 ms vs DynamicEmb 21.56 ms；关闭去重 23.99 vs 28.47 ms；文档承认"动态 embedding 有一定开销，但放到端到端模型里会被摊薄" — 同上 benchmark README（A）。
- 增量同步的精确语义（API 文档 + 设计文档）：`incremental_dump(model, score_threshold, pg)` 按表的 `score_strategy` 解释阈值——含 TIMESTAMP 列的策略（单 TIMESTAMP 或 `(TIMESTAMP, LFU)`）是**基于时间**的增量（只导出最后访问时间跨过阈值的 key，用 `get_score` 的返回作参考），STEP/LFU/NO_EVICTION 则按绝对分数阈值；仅支持 `roundrobin`/`hash_roundrobin` 分片（`continuous` 抛 NotImplementedError）；`DeltaDumpResult` 每表携带 keys/values/optimizer_states/scores/evicted_keys/erased_keys 及 `meta`（slot_index、current_capacity、row_capacity、world_size、table_options、current_score）；`replay_increment` **按 slot 写回**（目标表布局必须与源一致，先校验整个 collection 的 meta 与列形状再写，任一不匹配整体拒绝），先擦除 `erased_keys` 再 upsert，`evicted_keys` 永不重放（"占据被驱逐 key 槽位的新 key 就在同一份 delta 里"），时间戳列按"年龄（cur_ts − score）"传输因为 `%globaltimer` 跨设备/重启无意义，rowwise Adagrad 的 16 字节预留只传 1 个标量并在重放时补齐；文档明确"典型部署是 delta 复制：训练作业周期性 dump，delta 运到服务副本，副本重放以追上而无需重载完整 checkpoint"，并提醒不带 SCORE 重放时"源与副本可能以不同顺序淘汰" — [DynamicEmb_APIs.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/DynamicEmb_APIs.md)、[replay_increment_design.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/docs/replay_increment_design.md)、[delta_dump_result_design.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/docs/delta_dump_result_design.md)（A）。
- Admission 设计文档暴露的工程细节：`BatchedDynamicEmbeddingTablesV2` 把多张逻辑表融合为一个物理 value buffer，曾出现"所有表都用表 0 的初始化器"的缺陷（修复分支 `fix/dynamicemb-admission-init`）；`FrequencyAdmissionStrategy(threshold=4)` 需要配套 `KVCounter`，未准入的 key 仍参与前向，其行必须被初始化 — [admission_strategy_design.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/docs/admission_strategy_design.md)（A）。
- HSTU 训练例子的并行组合："集成 TorchRec 做 embedding 分片、Megatron-Core（core_v0.13.1）做 dense 并行，包括 data、tensor、sequence、pipeline 与 context parallelism"，自定义 CUDA 算子在 `examples/commons`，HSTU attention kernel 由 `fbgemm_gpu_hstu`（FBGEMM 子模块）提供；数据集 KuaiRand-27k 序列最长 228,000、均值 11,796 — [examples/hstu/training/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/README.md)（A）。负载均衡 shuffler 用单线程池跑 CPU 端 Karmarkar-Karp 分割，与主线程的 GPU fwd/bwd 重叠，并按 `ShuffleHandle` 跟踪预取流水线中同时在途的 3 个 batch — [batch_shuffler.py](https://github.com/NVIDIA/recsys-examples/blob/main/examples/commons/distributed/batch_shuffler.py)（源码，A）。
- 端到端 MFU 的一次完整拆解（PERF_ANALYSIS，2 台 DGX 共 16×H100 SXM，bf16，峰值按 989 TFLOPS）：8 层 HSTU、H=1024、4 头×256 维、item/user_id 各 5000 万行×128 维 DynamicEmb（主机各 23.84 GiB，HBM cache 比例 0.1 即 2.38 GiB）、Zipf α=1.05、每 GPU batch 32、有效序列 T=4,099；每步 63.89 TFLOPs（UVQK GEMM 26.41、投影 GEMM 6.60、attention 30.88）；中位步时 187.01 ms、701.4K tokens/s/GPU、**341.6 TFLOPS/GPU、MFU 34.54%**（最佳区间 34.88%）；GPU 时间分布：`hstu fwd/bwd` 43.09%、UVQK GEMM 17.85%、投影 GEMM 4.80%、**elementwise 21.31%**、embedding 算子 5.74%、GPU 空闲 3.34%、NCCL 暴露 1.58%、NCCL 重叠 0.46% — [PERF_ANALYSIS.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/PERF_ANALYSIS.md)（A）。渐进实验的六个档位：基线（Triton attention、DynamicEmb 无缓存、无 shuffler、仅 DP）→ 负载均衡 shuffler → CUTLASS attention → DynamicEmb 缓存 → hash_roundrobin 分片 → 预取流水线 — [E2E_BENCHMARK.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/E2E_BENCHMARK.md)（A；吞吐终值见 02 号笔记）。

### Inferences
- "PS vs 全 GPU"的公开答案按公司分三档：Meta 是**同步 + 全 GPU（TorchRec 2D/FSDP）**，并把 PS 语义搬进 KVZCH/DRAM-SSD 虚拟表与 ZCH；字节是**混合**（sparse 异步 + dense 同步，且 STCA 2025-11 仍在量化 PS CPU 占用），LONGER 代表的全同步 GPU 路线是其中一条分支而非全部；阿里 RecIS 与 NVIDIA DynamicEmb 则把"放 GPU 还是 CPU"做成**每张表的放置参数**（IDMap/EmbeddingBlocks 各自可选，HBM cache 比例可调）。对 TikTok 读者的含义：公开路线没有谁在 2025–2026 年完全放弃主机内存层，差别在于主机层是"参数服务器进程"还是"同一训练进程的 UVM/host 存储"。
- 框架生态正在"PyTorch 化"：RecIS 的目标被写成"超过 TensorFlow 系的效率"，Monolith（TF）两年无提交，HugeCTR 转入只发源码；NVIDIA 把投入转到 TorchRec 兼容的 DynamicEmb + Megatron-Core 组合。TF 时代的 PS 框架正在被 PyTorch 上的"分片 embedding + 集合通信"替换。
- DynamicEmb 的查表开销（dedup 下 21.56 vs 14.88 ms）说明哈希表动态性有约 45% 的 lookup 代价，但 PERF_ANALYSIS 里 embedding 算子只占 5.7% 的 GPU 时间，因此端到端代价可控；真正的时间大头是 attention（43%）与 elementwise（21%），这与 Kunlun/GEM 把 kernel 融合作为 MFU 第一杠杆一致。
- TorchRec 的 FP8/MX4 量化通信、v1.7.0 的 FP8 rowwise padding、以及 GEM 的"SM-free 集合通信"与 MTIA 300 的片上 NIC，指向同一瓶颈：embedding all-to-all/all-reduce 与计算争抢 GPU SM 与网络；缓解顺序是"压缩通信字节 → 重叠（SemiSync/PEC）→ 把通信搬离 SM/搬进芯片"。

### Gaps
- Primus 论文全文（混合 PS/GPU 架构、吞吐、数据任务图实现）不可达，只有摘要数字；`bytedance/primus` 开源版与论文系统的关系无法从仓库页面确认。
- SKAI 没有任何公开文档、代码或性能数据；"GPU 参数服务器"的分片/缓存/一致性细节未知。
- 腾讯 2025–2026 年没有公开的训练框架技术报告（无量系统只有 NVIDIA 案例摘要）；FusedRec 正文未读。

## 2. 样本流水线与在线学习：流式训练、特征/样本存储、增量同步、数据-GPU 配比

### Takeaway
2025–2026 年的一手材料把样本流水线写成与 GPU 同等的成本项：Meta 用 VLM 证明 4K 序列后数据基础设施超过 GPU（02 号笔记），本轮补充其**机制**——"Fat Row"是为 O2O 一致性把 UIH 快照进每条样本、同用户一天 K 次请求复制 K 份，流式训练（秒级消费）与批训练（数天后回放）共用同一份数据；解法是把 UIH 当作"追加式、不可变、按时间戳可重建"的序列，只记 O(1) 的版本元数据。各公司的在线学习形态都是"**教师/基础模型与学生各自流式训练 + 教师信号异步落盘/落缓存 + 学生以流式 join 消费**"（ExFM 的 DAS、HyperCast 的 FM logging tier、Lattice KTAP 的 TTL 嵌入缓存、Rec-Distill 的批→流两阶段），训练到服务的 embedding 增量同步在 2026 年有了开源实现（DynamicEmb `incremental_dump`/`replay_increment`、TorchRec `ModelDeltaTracker`）。数据预处理与 GPU 的资源配比只有字节（千万 CPU 核 vs 数万 GPU）、快手（每节点 2 CPU + 8 GPU）与 Meta（"数据支撑服务/GPU 训练功耗 ≥ 0.75 即撞墙"）三个数量级线索。

### Cited Findings
- **Versioned Late Materialization（Meta，arXiv 2604.24806，2026-04，生产部署，A）**——机制层：在线打分时把包括长序列 UIH 在内的特征"冻结并缓存在高吞吐 KV 特征存储"，标签异步到达后由 ingestion 服务 join 成"Fat Row"；该架构"必须同时服务流式在线训练（样本在数秒内被消费）与批离线训练（样本可能数天后回放）"；N 天 UIH 窗口下，前 N−1 天的历史"在同一天的 K 次请求间静态不变却被物理复制到每条样本"，写入量与存储同比放大 K 倍；多租户放大：召回模型可能只要最近 100 个事件，后期排序要"100× 更多"，共用并集数据集时按最长需求物化；"数据支撑服务 = 训练数据存储 + 在线/离线训练数据摄取 + 预处理计算"；三条结构不变量支撑延迟物化：可重建性（任一历史时刻的 UIH 可由单一规范副本做时间范围扫描恢复）、按谓词防未来泄漏（timestamp ≤ t 既必要又充分）、版本元数据充分性（每样本 O(1) 代替 O(seq_length)）；实现为"读优化的不可变存储 + 多租户序列投影下推 + 解耦的数据预处理（DPP）+ 流水线 I/O 预取 + 数据亲和分片"以"让训练吞吐保持 GPU 受限" — [论文全文](https://arxiv.org/abs/2604.24806)（A；带宽/延迟百分比见 02 号笔记）。
- **HyperCast（Meta，arXiv 2508.02929，2025-08，生产）**：FM 的 target-aware embedding"被物化并作为候选级特征记录进训练数据，因此 FM 与 expert 的训练作业各自消费自己的数据、独立更新权重、互不依赖"；三种推理负载分三层独立服务——在线 FM（为数百候选出 embedding，严格延迟）、**离线 FM logging（只为被服务的一小部分物品生成训练用 embedding，延迟要求宽松，主机数只需在线 FM 层的 1/3）**、在线 expert；"实时流水线在交互事件发生时立即记录，动态 join 策略……模型刷新以数分钟为周期且不中断服务"；平均数据到 trainer 延迟 30 分钟、模型新鲜度分钟级 — [论文全文](https://arxiv.org/abs/2508.02929)（A）。
- **ExFM（Meta，arXiv 2502.17494，2025-07 修订，生产）**：FM 与各 VM 在流式数据上递归训练；FM 的训练数据由多路 VM 流量聚合而来；FM 训练完成后**对各 VM 的训练数据做推理，把预测作为外部监督离线记录**，"FM 监督的记录与同 VM 训练数据的合并由 Data Augmentation Service（DAS）完成"；给出"74B 样本训练后停止更新的模型，推理 NE 损失随延迟单调增大"的陈旧性曲线；由此定义"跨域偏差"与"新鲜度差距"两类教师-学生分布差，用 Auxiliary Head 与 Student Adapter 缓解 — [论文全文](https://arxiv.org/abs/2502.17494)（A）。
- **Lattice KTAP（Meta，2026）**：教师 Lattice Networks 维护后台作业，持续对"前序阶段识别出的最相关物品"计算并存储最终骨干层 embedding，带 **TTL（通常数小时）**；学生在训练与推理时都按 user-item 对查询教师 embedding，过期/缺失则入队等待下一轮刷新并以零张量占位；同时提供教师 logits 做传统蒸馏 — [论文全文](https://arxiv.org/abs/2512.09200)（A）。
- **Rec-Distill（字节 AML，arXiv 2605.29755，2026-05，生产）**：教师"通过流式训练持续跟踪最新分布，其前向产生的蒸馏信号缓存在中间存储供学生训练"，由此支持 1-to-N（含跨阶段，如用精排教师蒸馏粗排）；系统为**混合批-流水线**：批蒸馏阶段"用充足训练资源与更大 batch 让学生快速收敛到稳健基线，学生可直接读数据流或经中间存储读取蒸馏信号"；流式蒸馏阶段"教师把新流式数据的 logits 写入低延迟高速中间存储，原始数据流与蒸馏信号 join 成补充数据流，学生持续消费最新信号与对应真值标签"；学生采用"解耦塔"（主任务塔 + 蒸馏塔），作者明确其为**容错机制**："即使教师更新延迟、蒸馏流水线滞后或教师信号暂时不稳定，主任务塔的性能与在线服务不受影响"；教师-学生采样策略不同（f_T ≠ f_S）时须把教师原始 logit 用学生侧去偏函数重投影后再匹配，否则"迁移性能大幅退化" — [论文全文](https://arxiv.org/abs/2605.29755)（A）。
- **Primus（字节，ATC'25）**：数据层"三层数据定义 + 数据任务图，编排来自批与流两类来源的训练样本"；训练范式"混合方式，通过控制参数更新并对混合批/流数据做细粒度优先级来保持模型时效"；资源层"跨资源池水平/垂直动态扩缩"——这是字节公开材料中对"批+流统一样本流水线"的最直接描述 — [usenix.org](https://www.usenix.org/conference/atc25/presentation/shan-jixi)（B，摘要）。
- **OneRec（快手，A）**：训练流水线日处理约 180 亿样本/540 亿 token；后训练阶段"用实时数据流做在线训练，同时做 RSFT 与 RL"；训练数据与 embedding 预取走独立的 100 Gbps TCP 网络（与 400 Gbps RDMA 训练流量分离）；评测体系运行在流式数据上，"同一指标跨时段绝对值不同，只做同时段对比" — [技术报告全文](https://arxiv.org/abs/2506.13695)（A）。
- **RecIS Window IO（阿里，A）**：ODPS 表按窗口数或行数切分、Lake 流按 `step_mins=60` 切窗，`make_lake_stream_window_io` 直接对应"小时级窗口在线训练"；Trainer 支持 `train_and_evaluate` 的训练/评估交错 — [window_io.rst](https://github.com/alibaba/RecIS/blob/main/docs/best_practice/data_pipeline/window_io.rst)、[pipeline.rst](https://github.com/alibaba/RecIS/blob/main/docs/best_practice/train_pipeline/pipeline.rst)（A）。
- **TBGRecall（阿里，arXiv 2508.11977，A）**："CPU 端 DataLoader 用预取/流水线并行隐藏 I/O 延迟，保持 >90% GPU 利用率"；分布式负采样把十亿级商品目录分片到各节点；"随机部分增量训练"强调数据新近性优于数据量 — [论文全文](https://arxiv.org/abs/2508.11977)（A）。**MTGR（美团，A）**："计算流执行 batch T 的前后向时，拷贝流并发加载 batch T+1 以掩盖 I/O 延迟"；动态哈希表处理稀疏条目的实时插入/删除；动态序列均衡解决 GPU 间负载不均；embedding ID 去重 + 自动表合并加速查表 — [论文全文](https://arxiv.org/abs/2505.18654)（A）。
- **Monolith（字节，2022 背景，A）**：Kafka 流 + `tf.train.Example` 序列化、`poll_batch_size` 即训练 batch；服务端 PS 为 embedding KV 存储、entry 调 PS 取 embedding — [Stream.md](https://github.com/bytedance/monolith/blob/master/markdown/demo/Stream.md)、[serving.md](https://github.com/bytedance/monolith/blob/master/markdown/serving.md)（A）。
- **训练→服务的 embedding 增量同步（开源实现）**：DynamicEmb 的 dump/replay 语义见第 1 节（A）；TorchRec `ModelDeltaTracker`"跟踪并取回各模块访问的唯一 ID 与对应 embedding/状态，用于计算 top-k 或**在在线训练中把更新后的 embedding 从 predictor 流式推到 trainer**"，支持多消费者各自 batch 偏移、读后删除、自动压缩、ID_ONLY 等模式 — [model_delta_tracker.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/model_tracker/model_delta_tracker.py)（A）；HugeCTR SOK 24.06 的 `sok.incremental_dump`（按时间阈值导出新增键值，仅 HKV 后端）是更早的同类接口 — [release_notes.md](https://github.com/NVIDIA-Merlin/HugeCTR/blob/main/release_notes.md)（A）。
- **数据/GPU 配比线索**：字节"1000 万+ CPU 虚拟核 vs 数万 GPU"（B，Primus 摘要，见 02 号笔记）；快手 OneRec 每节点 8 GPU + 2 CPU（A）；Meta"Fat Row Wall"定义为数据支撑服务资源/GPU 训练功耗之比 >0.75（A，02 号笔记）；Google 用"共享输入生成"在多模型间摊薄特征转换 CPU 成本，训练成本 −18%（B）；Pinterest 多 epoch 论文指出大表"第一个 epoch 后过拟合"，这是推荐训练必须流式单遍的直接证据（B）。

### Inferences
- 所有公开的"教师-学生"系统都把教师推理放到**旁路**（HyperCast 离线 logging tier、ExFM DAS、Lattice 后台作业、Rec-Distill 中间存储），用"记录到训练数据"或"写入低延迟存储后 join"两种落地方式解耦教师与学生的训练节奏；共同代价是新鲜度差距，各家分别用 Student Adapter、TTL、解耦塔来吸收。对 TikTok 的直接对照是 Rec-Distill 的批→流两阶段 + 解耦塔。
- Meta VLM 的本质是把"样本 = 特征快照"改成"样本 = 版本指针"，这要求特征存储提供**不可变、按时间范围扫描**的序列层；这一能力与 Meta 2025 年起把 UIH 推到 16K–64K 的模型路线互为前提，没有它序列 scaling 会先撞数据墙。
- 增量同步从 SOK（2024）→ DynamicEmb（2026-07/09）→ TorchRec delta tracker（2025-09）的演进说明"GPU 哈希表 + 分钟级 delta 推送"已成为开源栈的标配接口，但 DynamicEmb 的按 slot 重放要求训练与服务副本布局完全一致，这意味着服务侧必须跑同样的 DynamicEmb 表结构（或退回全量 checkpoint 加载）。

### Gaps
- 没有任何公司公开秒级样本回流的端到端延迟分解（日志→join→trainer）；HyperCast 的 30 分钟是唯一的数据到 trainer 延迟数字，ExFM/Rec-Distill 的教师信号滞后量未给出。
- 特征存储的读带宽、QPS、存储量级（TB/PB）在 2025–2026 论文中只有相对百分比（Meta）或无数据。
- Primus 的数据任务图与混合批/流调度算法细节不可达。
- 数据预处理 CPU 与 GPU 的配比没有任何公司给出"每 GPU 需要多少 CPU 核"的生产数字。

## 3. 生成式/Transformer 化排序模型的训练工程：kernel、请求级批处理、训短推长、长序列、MoE、低精度、MFU 拆解

### Takeaway
把 MFU 从个位数提升到 20–60% 的公开做法可以拆成六个独立杠杆，各家取的子集不同但方向一致：(1) **去碎片算子换大 GEMM**（RankMixer/TokenMixer-Large 的"纯模型"、Kunlun 把 PFFN 融成一个 GDPA kernel）；(2) **序列侧定制 kernel**（HSTU/jagged attention 的 CUTLASS/Triton/FA3 实现，ULTRA-HSTU 的 SLA、WHALE 的共享 KV 跨分支注意力、SORT 的跳过全 mask 块）；(3) **请求级/用户级样本组织**（STCA RLB、SORT request-centric、MTGR/MTFM 用户级聚合），把用户侧编码摊到多个候选；(4) **训短推长 + 负载均衡随机长度**（STCA 2k→10k、ULTRA-HSTU LBSL、NVIDIA 的负载均衡 shuffler）；(5) **低精度**（训练以 BF16 为主，FP8 只进 GEMM 并把量化融合进前置 kernel，MXFP8 仅 GEM 博客提及）；(6) **MoE 专用算子与并行**（GroupedFFN、Token Parallel、Megablocks）。长序列训练的显存/通信代价有了具体数字：5K→20K 使训练时间 3.5×、显存 +49 GB（字节 TM20K），对策是去 padding（−10 GB）、选择性重物化（ULTRA-HSTU 每层 −67%）、序列/上下文并行（NVIDIA v25.10）。

### Cited Findings

**jagged/HSTU kernel 与算子层**
- NVIDIA PERF_ANALYSIS 的时间分布（16×H100、T=4,099）：HSTU attention 前后向 43.1%、elementwise 21.3%、GEMM 合计 23.7%，说明即便用了 CUTLASS 融合 attention，**非 GEMM 的逐元素算子仍占五分之一** — [PERF_ANALYSIS.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/PERF_ANALYSIS.md)（A）。HSTU attention 的 CUTLASS kernel"针对 HSTU 的 causal+context mask 手工调优"，Blackwell 走 CuteDSL；SID-GR 训练支持两种 attention 后端：Megatron-Core `TransformerBlock`（padded dense `[S,B,D]`）与 `JaggedTransformerBlock`（把全 batch 拉平成 B=1 的 `[1,total_tokens,D]`，用 `arbitrary_func` 区间编码 mask，块稀疏自动跳过 masked 区域，依赖 FlashAttention `arbitrary_mask` 分支），文档指出 jagged 即 Megatron-Core/Transformer-Engine 的 THD 布局 — [sid_gr/training/README.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid_gr/training/README.md)（A）。
- Meta `generative-recommenders`：HSTU Ultra Triton kernel attention-only 2.02–2.32× 于 PyTorch 参考（H100 96 GB，BF16，1980 MHz/700 W）；`ops/cpp/hstu_attention` 基于 FlashAttention V3 — [README](https://github.com/facebookresearch/generative-recommenders/blob/main/README.md)（A）。ULTRA-HSTU 的 SLA kernel 为 H100 与 MI300 分别调优（见第 1 节，A）。
- WHALE（Meta，arXiv 2607.17017，B200）：跨分支注意力用融合 Triton kernel；"profiling 显示跨分支注意力 kernel 受访存限制"，于是**共享 K=V**，重用已加载的 key 张量作 value，"KV 侧显存流量减半"，反向把共享 KV 梯度在 kernel 内累加；注意力形状不对称（约 64 个 query 对 15,000 长历史），因此做"非对称反向变体"选择 query 并行还是 KV 并行的切分；推理再做 shape-aware kernel 调优、编译图执行、无同步 shape 处理 — [论文全文](https://arxiv.org/abs/2607.17017)（A）。
- TorchRec 的 KJT/jagged 工程：`clear_data_dist_inputs` 在 AllToAll 后释放 KJT 输入（v1.7.0）、`to_padded_dense` 用 `sym_int` 以支持编译（v1.7.0）、KJT 保持 stride-per-key-per-rank（v1.9.0）、输入 KJT 校验器（v1.3.0）；NVIDIA v26.03"减少 jagged 张量处理中的 D2H 同步" — [TorchRec Releases](https://github.com/pytorch/torchrec/releases)、[recsys-examples README](https://github.com/NVIDIA/recsys-examples/blob/main/README.md)（A）。
- GEM 博客提到的 Jagged Flash Attention / GDPA / BlockAttention 定制 kernel 库 — [engineering.fb.com](https://engineering.fb.com/2026/08/03/ml-applications/training-gem-at-llm-scale-meta-ads-recommendation-foundation-model/)（B）。

**请求级批处理与样本组织**
- STCA/RLB（字节，arXiv 2511.06077，生产）：训练若仍按独立三元组 (u,v,y) 组织，"同一长历史 H 被序列化、CPU→GPU 传输并重复编码，**随着 L 增大，存储与带宽而非 FLOPs 成为瓶颈**"；RLB 把同用户的 m 个样本聚成用户微批、用户路径只算一次，仍是经验风险的无偏估计；工程效果：固定硬件下最大可训长度约 8×，复用用户编码后目标侧矩阵乘合成更大 GEMM、配合 ragged/紧凑序列减少 padding，单 GPU 吞吐 2.2×（叠加 kernel 后 5.1×），PS CPU 与模块间带宽 −50% — [论文全文](https://arxiv.org/abs/2511.06077)（A）。
- SORT（阿里，生产）：impression-centric 的 N 条样本 ⟨H,U,c_j⟩ 改为一条 request-centric 样本封装全部候选，"模型不再为每个候选重复处理用户画像与序列"；指出 HSTU/MTGR/GenRank 也采用类似范式以"摊薄训练成本"；线上三个场景延迟 −58%/−37%/−39%、吞吐 +36%/+169%/+159% — [论文全文](https://arxiv.org/abs/2603.03988)（A）。
- MTGR 用户级压缩（多样本合一）使 TorchRec 基线上的训练吞吐 1.6–2.4×，>100 GPU 扩展良好（A，见 02 号笔记）；MTFM（美团，arXiv 2602.11235，2026-02）"多场景用户级样本聚合显著提高训练吞吐，GQA + 定制 Hybrid Target Attention 降显存，kernel 融合与消除 CPU-GPU 阻塞" — [镜像摘要](https://arxiv.org/abs/2602.11235)（B）；TM20K 的训练工具链列出"User-Level Training（类似 RLB）、FlashAttention、混合精度、Remove-Padding、M-Falcon Serving" — [论文全文](https://arxiv.org/abs/2608.07055)（A）；UniPinRec（Pinterest，2026-06）用"混合训练样本（行为序列 + feed 曝光列表）"同时满足召回与排序目标，跨阶段共享 KV cache — [镜像摘要](https://arxiv.org/abs/2606.00422)（B）。

**训短推长与长序列的显存/通信**
- STCA：训练平均长度约 2k、服务 10k（外推比 5），采用 Stochastic Length 训练范式 — [论文全文](https://arxiv.org/abs/2511.06077)（A）。ULTRA-HSTU：LBSL 在 SL 基础上显式控制每 rank 计算量，训练序列约 4,400、推理 16,384，吞吐 +15%（A，见第 1 节）。NVIDIA v25.10"把 scaling 序列长度与 attention 的最大序列长度上限解耦"（A）。
- TM20K（字节电商广告，arXiv 2608.07055，2026-08，生产）：最大序列 5K→20K，"即使有 FlashAttention 与 M-Falcon，训练时间 +3.5×、GPU 显存 +49 GB、服务延迟 +6.3×"；全注意力比目标注意力 GPU 利用率更高；去 padding（把有效 token 均匀重分到 batch 内各实例）"对完整 20K 序列最多省 10 GB 显存"；KD + 超长序列导致训练不稳定，加 QK Norm；教师（全 20K token）batch 96 vs 学生 320；"数百 GPU"集群；token 合并在原始特征而非 embedding 上做"以显著减少 CPU-GPU 通信带宽" — [论文全文](https://arxiv.org/abs/2608.07055)（A）。
- ULTRA-HSTU 的显存方案：选择性重物化（跳过 6 个大前向张量，反向重算 U/Q/K/V 与中间 Y，复用 layer-norm 统计）开销 5%，去掉梯度拼接，整体每层显存 −67%；HBM 占用 7 GB→2.3 GB（A，见 02 号笔记/第 1 节）。LONGER：BF16/FP16 + 激活重计算带来吞吐 +18%、显存 −18%（A，02 号笔记）。OneTrans：金字塔式 query 子集（深层只让最近 S-token 发 query）直接减少 FLOPs 与激活显存，再加 BF16/FP16 + 重计算"换更大 batch 与更深模型" — [论文全文](https://arxiv.org/abs/2510.26104)（A）。
- NVIDIA：HSTU 序列并行（v25.10）、tensor 并行（v25.07）、Megatron-Core 的 context parallel（`initialize.py` 中按 `get_context_parallel_rank` 设种子）、层重计算（v25.06） — [CHANGELOG](https://github.com/NVIDIA/recsys-examples/blob/main/CHANGELOG.md)、[initialize.py](https://github.com/NVIDIA/recsys-examples/blob/main/examples/commons/utils/initialize.py)（A）。
- "Beyond Item IDs"（arXiv 2606.07546，2026-06，十亿用户短视频平台，作者单位未核实）：用深度截断的粗粒度 Semantic ID 缩小 embedding 表，用"非参数时间折叠 + 统一全局 query"的 Global-Aware Compression Transformer 压缩序列，"离线 profiling 显示峰值显存降一个数量级" — [镜像摘要](https://arxiv.org/abs/2606.07546)（B）。

**MoE 排序模型训练**
- TokenMixer-Large：MoEPermute（batch-first→expert-first）+ MoEGroupedFFN（GroupedSwiglu/GroupedGemm 单 kernel 算全部专家）+ MoEUnpermute；训练中 GroupedFFN 占 89%（计算受限），permute/unpermute 访存受限；Token Parallel 把 per-token 权重与计算切到多设备；"Sparse Train, Sparse Infer"的 per-token MoE 与 DTSI 对照；无需额外负载均衡损失（跨 token 天然均衡，附录 A.2） — [论文全文](https://arxiv.org/abs/2602.06563)（A）。
- SORT：Megablocks 实现 MoE，比较 Switch 式与 DeepSeek 式 MoE 后选后者；MoE 路由保持 FP32 — [论文全文](https://arxiv.org/abs/2603.03988)（A）。OneRec：0.935B/2.633B 为 MoE（24 专家激活 2/4，放 decoder 或 enc+dec） — [技术报告](https://arxiv.org/abs/2506.13695)（A）；OneRec-V2 与 TBGRecall 都采用 DeepSeek 式无辅助损失负载均衡（A，02 号笔记；TBGRecall 全文）。RankMixer 的 DTSI-MoE（稠密训练/稀疏推理）（A，02 号笔记）。
- UniMoMo（arXiv 2608.08627，2026-08，仅研究）：训练后按功能相似度合并专家，4 专家 checkpoint 在 A100 上 1.28–1.63× 加速、NDCG 保持 99.9–102.3% — [镜像摘要](https://arxiv.org/abs/2608.08627)（B）。

**FP8/低精度训练**
- 训练侧的保守共识：TokenMixer-Large"训练全程 bfloat16，FP8 E4M3 仅用于推理 PTQ"（A）；SORT BF16 AMP 但排序头与路由 FP32（A）；OneRec BF16 只用于"某些 MLP"（A）；LONGER/OneTrans BF16/FP16 + 重计算（A）；ULTRA-HSTU 把 FP8 限定在每层两个 GEMM、其余 BF16，并强调"简单把 GEMM 切到 FP8 效率低——朴素 FP8 流水线的缩放/量化与布局准备会抵消收益"，故把行级缩放量化融合进前置 kernel（A）；Lattice 为 FP8 训练改架构（无 bias、SwishRN、交叉模块归一化）且用 FP8/BF16/FP32 混合训练（A）；Meta GR 仓库的 FP8 addmm"训练时反向全精度"（A）；GEM 博客的 MXFP8 attention 与 MLP 训练是唯一提到微缩放格式的生产来源（B）。
- 通信侧：TorchRec FP8/MX4 量化 all-to-all（A）；ULTRA-HSTU INT4 embedding 减少推理通信（A）。

**MFU 拆解：各系统各做了什么（均为论文/仓库原文）**
- RankMixer 4.5%→45%（CIKM 2025，抖音 Feed 生产）：动机是"多数手工交叉模块的核心算子在现代 GPU 上访存受限而非计算受限"；用参数无关的多头 token mixing 替代自注意力（后者"训练效率低、跨空间 ID 相似度组合爆炸、注意力权重矩阵严重访存受限"）+ per-token FFN 大 GEMM；"更大隐层产生更大矩阵乘形状、MFU 高于堆层"，故 100M/1B 配置为 (d=768,L=16,N=2)/(d=1536,L=32,N=2)；线上 fp16 推理、70× 参数仅 20.7× FLOPs、FLOPs/参数降 3.6× — [论文全文](https://arxiv.org/abs/2507.15551)（A）。
- TokenMixer-Large 60%（广告骨干）：三处——"纯模型"（去掉 LHUC、DCNv2 等"低计算强度、高访存与通信开销"的碎片算子，发现大模型下这些算子的收益可被堆叠 TokenMixer Block 吸收）、融合 MoE 算子、Token Parallel（A，见上）。
- Kunlun 17%→37%（B200）：低层 GDPA/HSP/滑窗 + 高层 CompSkip/事件级个性化；论文把推荐模型 3–15% MFU 的原因归为"异构特征空间导致小 embedding 维度、不规则张量形状、访存受限操作"（A）。
- OneRec 4.6%→23.7%（训练）：SKAI GPU PS（embedding 不再走 CPU PS 通信）、DP+ZeRO-1+梯度累积、BF16 MLP、attention 编译优化；报告还把 SID 的"通信效率"列为原因——"稀疏 embedding 操作需要大量 PS 通信做 lookup 与梯度更新，语义 ID 通过稠密操作与共享词表减少通信开销，提高训练吞吐" — [技术报告](https://arxiv.org/abs/2506.13695)（A）。
- SORT 13%→22%：sparse 侧多进程组通信调度隐藏延迟，dense 侧跳过全 mask 块的稀疏注意力 kernel + 混合精度（A）。
- NVIDIA HSTU 示例 7.6%→31.4%（E2E）/34.5%（PERF_ANALYSIS）：shuffler 负载均衡 → CUTLASS attention → DynamicEmb HBM 缓存 → hash_roundrobin → 预取流水线，NCCL 暴露仅 1.6%（A）。
- GEM 20–25%（B，见第 1 节）；ULTRA-HSTU 训练 scaling 效率 5.3×（A，02 号笔记）；腾讯 RankUp 23%（A，02 号笔记）；TurboGR 在昇腾 NPU 上 0.2B 模型 54.71% MFU、近线性扩展 0.97、负载不均 47%→2.4%、NPU 利用率 94%（B，见第 6 节）。
- UNIQUE（百度，arXiv 2609.23718，2026-09）：统一召回与排序的模型论文，镜像摘要与复现笔记中**没有 MFU 或训练系统数据**（Mobile Baidu 线上 A/B 观看时长 +0.96% 等为效果指标） — [auto-research 复现笔记](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2609.23718-unique/README.md)（B）。

### Inferences
- MFU 提升的"第一桶"几乎总是**改模型而不是改系统**：RankMixer（10× MFU）、TokenMixer-Large、Kunlun（GDPA）、OneRec（SID 去掉稀疏表通信）都先把访存受限模块换成 GEMM 友好形态，系统优化（流水线、缓存、通信重叠）贡献第二桶（NVIDIA 示例 7.6→31.4% 中 shuffler+CUTLASS 是大头）。TokenMixer-Large 60% 与 LLM 40–60% 持平后，再往上只剩 FP8 训练与通信搬离 SM 两条路。
- 请求级批处理是"训练样本流水线"与"kernel 效率"的交点：它既减少 CPU→GPU 带宽（STCA 明说瓶颈是带宽而非 FLOPs），又把目标侧矩阵乘合成大 GEMM；对 10k–20K 序列的系统而言，它比 FP8 更先决。
- 长序列训练的真实瓶颈是激活显存与数据带宽而非 FLOPs：TM20K 的 +49 GB、ULTRA-HSTU 的 −67%/层、OneTrans 的金字塔 query、NVIDIA 的 SP/CP 都在处理同一问题；字节公开路线（TM20K）选择"一次性全长教师 + 学生 token 合并"把长序列成本从在线模型搬到离线教师。
- FP8 在推荐训练中的公开成熟度明显落后于 LLM：2026-10 为止只有 Meta（ULTRA-HSTU、Lattice、GEM）在生产训练用 FP8/MXFP8，且都伴随架构改造；字节/阿里/快手公开材料均为"BF16 训练 + FP8 推理"。

### Gaps
- GEM 博客提到的 JFA/GDPA/BlockAttention kernel 与 MXFP8 的具体精度/速度数据不可达。
- 没有公司公开 10k–100K 序列训练下的**序列并行/上下文并行**生产使用情况（NVIDIA 只有功能支持，Meta 用 LBSL 与重物化绕开，字节用 RLB 与教师-学生绕开）。
- UNIQUE 的训练系统细节缺失；TMallGS（阿里，2607.13398）摘要只说"以提高 MFU 为动机、提升训练吞吐"，无数字。
- 各家 MFU 的计算口径（是否含 embedding/attention FLOPs、峰值按稠密还是稀疏算力）不一致，OneRec 文中 28.8%/28.6% 自相矛盾（02 号笔记已记），跨公司数字不可直接排序。

## 4. 持续训练管理：有效训练时间、checkpoint、热更新与一致性、弹性与故障恢复

### Takeaway
Meta 在 2026-10-01 把"持续训练的生命周期损耗"量化成论文：最大工作负载"每天数百亿样本、数千 GPU"，此前端到端 wall time 只有约 50–60% 用于训练新数据，通过 trainer 初始化、编译缓存、**异步 checkpoint**与恢复成本优化，ETT% 平均 +15.5%、最大负载达 85%，全 fleet 从约 80% 升到 90% 以上。Checkpoint 的公开演进是 Check-N-Run（2022）→ DECK 增量 checkpoint（VLDB 2025，约 12× 频率）→ DynamicEmb/TorchRec 的 delta dump；热更新与一致性的公开机制包括 DynamicEmb 按 slot 的 delta 重放、HyperCast 分钟级无中断刷新、GR4AD 秒级 SID 索引、VLM 的 O2O 一致性协议；弹性方面有 TorchRec 训练中 resharding（约 100 GB 停机 200 ms）与 Primus 动态扩缩（成本 −17.1%）。"数百个持续训练模型的调度"没有直接公开数据，只能从 Lattice 的模型空间合并、HyperCast/ExFM/DV365 的"一个上游模型服务多个下游"推断治理方向。

### Cited Findings
- **ETT 论文（Meta，arXiv 2610.02057，2026-10-01，Mingming Ding、Ruilin Chen、Yuzhen Huang 等约 31 人，生产 fleet）**：摘要——"生命周期开销悄然消耗大规模推荐训练 fleet 的加速器容量"；最大负载"每天数百亿训练样本、数千 GPU"；此前"约一半到 60% 的端到端 wall time 用于在新数据上训练"；方法是用 ETT% 定位损失、按基础设施组件归因、度量跨作业重启的重复工作；优化覆盖 trainer 初始化、编译缓存、**异步 checkpointing**、恢复成本；结果"每个基准都提升，平均 +15.5%，最大负载达 85%；部署后 fleet 级 ETT% 从约 80% 升至 90% 以上" — [papers.cool 摘要](https://papers.cool/arxiv/2610.02057)（B，搜索摘要）；镜像复现笔记给出公式 ETT = training_on_new_data / wall_time，并把损耗列为"初始化、编译、checkpoint、发布和恢复" — [auto-research](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2610.02057-effective-training-time/README.md)（B）。
- **PyTorch 博客"Optimizing Effective Training Time for Meta's internal recommendation ranking workloads"**：ETT% 定义为"端到端 wall time 中用于有效训练的百分比"，因端到端时间随模型与数据量变化难以直接测，转而测"空闲与失败"，分解为 launcher 初始化、PT2 编译、有效训练、浪费训练；开源侧改动包括 TorchRec 分片计划改进与 PT2 编译时间/重编译优化，Meta 内部侧包括 checkpointing 与模型发布 — [pytorch.org](https://pytorch.org/blog/optimizing-effective-training-time-for-metas-internal-recommendation-ranking-workloads/)（B，搜索摘要，无具体数字）。
- **DECK（Meta，VLDB 2025，"Experiences on Delta Checkpointing for Industrial Recommendation Systems"）**：多 TB 模型使频繁常规 checkpoint 不可行，故障恢复损失大；DECK"抽取并流式输出模型状态增量，近零开销且不停训练"，"解耦的最优增量合并使 checkpoint 频率约 12× 而吞吐损失可忽略" — [vldb.org PDF](https://www.vldb.org/pvldb/vol18/p4978-gao.pdf)（B，仅摘要/转述，12× 未核实）；背景 Check-N-Run（NSDI 2022）目标是"显著降低 checkpoint 写带宽与存储而不损精度" — [usenix slides](https://usenix.org/system/files/nsdi22_slides_eisenman.pdf)（B）。
- **TorchRec 的相关能力（A）**：训练中动态 resharding（table-wise/column-wise，SGD/Adagrad，"约 100 GB 停机约 200 ms，最多 128 A100"，v1.3.0/v1.4.0）；Memory Stashing/EMS（把 embedding 权重、优化器状态、EMO cache 在训练/评估阶段间 stash 到主机，带 H2D/D2H 专用流与线程池，v1.6.0–v1.9.0）；Training Optimization Logger（v1.7.0/v1.8.0）；`DMPCollection` 要求 DTensor state dict 才能正确 checkpoint；TPU 包含 `SparseCoreSavePlanner/LoadPlanner` — [Releases](https://github.com/pytorch/torchrec/releases)、[memory_stashing.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/memory_stashing.py)（A）。
- **DynamicEmb checkpoint 与 delta（A）**：分布式并行 dump/load（v25.09）、LRU score 随 checkpoint 保存（v25.10）、按表原生精度存 checkpoint 以缩小体积（v26.08）、`incremental_dump`/`replay_increment` 的"delta 与 checkpoint 对一行的描述完全一致"（Adagrad 状态截断/补齐同一套函数） — [DynamicEmb_APIs.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/DynamicEmb_APIs.md)（A）。
- **RecIS（A）**：v1.2.0"优化 checkpoint 保存延迟"，稀疏参数以 SafeTensors 交付，"checkpoint 管理对齐 openlm_hub 标准"，公开版"checkpoint 使用文件系统路径、不依赖私有包" — [CHANGELOG](https://github.com/alibaba/RecIS/blob/main/CHANGELOG.md)（A）。
- **OneRec（A）**：每服务器 4 块 NVMe SSD"加速 checkpoint 写入，使大规模 embedding 与 dense 参数以最小停机存入 HDFS 做容错" — [技术报告](https://arxiv.org/abs/2506.13695)（A）。
- **热更新与一致性**：HyperCast"模型刷新以数分钟为周期且不中断服务"，并在训练数据中记录"所有可用 embedding 版本"的 FM 版本服务（A）；GR4AD 的 SID 索引秒级更新、短 TTL cache、VSL+RL 的持续频繁更新（A，02 号笔记）；VLM 用"分叉协议"同时保证流式与批训练的 O2O 一致性与防未来泄漏（A）；ExFM 的 Student Adapter 吸收教师陈旧性（A）；Rec-Distill 解耦塔在"教师更新延迟/流水线滞后/信号不稳"时隔离风险（A）；DynamicEmb 文档警告"不带 SCORE 的重放会让副本与源以不同顺序淘汰，但两者共同持有的 key 的 embedding 永远一致"（A）。
- **弹性与故障恢复**：Primus 水平/垂直动态扩缩使集群训练成本 −17.1%、作业 CPU 利用率 50→80%（B）；Google 的抢占通知与 training hold（B）；NVIDIA 训练例子的 `commons/checkpoint` 只提供 DMP/DDP/Float16Module 解包后的 save/load（A，无弹性）；字节 RobustRL（2025-12，LLM RL 后训练）把"Effective Training Time Ratio"作为指标并报告 256 GPU、10% 故障注入下 ETTR >80% vs ByteRobust 60%——说明字节内部同样以 ETTR 度量训练系统，但该论文不是推荐工作 — [镜像摘要 arXiv 2512.22492](https://arxiv.org/abs/2512.22492)（B，旁证）。
- **多模型治理**：Lattice 的出发点是"即使有 MDMO 框架，模型空间仍然碎片化、数据集异构"，用 Partitioner 合并后"只需少量模型"（A）；HyperCast 单一 FM 服务多个 surface、DV365 单上游模型服务 15 个生产模型、ExFM 1-to-N（A，02 号笔记）。

### Inferences
- ETT 论文与 GEM 博客合起来给出 Meta 的两条效率轴：单作业内 MFU（20–25%）与 fleet 级 ETT（80%→90%+）；按其基线（50–60% wall time 有效）推算，**生命周期开销曾吃掉近一半加速器时间**，这对任何运行数百个持续训练作业的团队都是比 MFU 更便宜的第一桶优化。
- Checkpoint 的技术路线正在与"训练→服务增量同步"合流：DECK 的流式状态增量、DynamicEmb 的 DeltaDumpResult、TorchRec 的 delta tracker 本质是同一份"变化行 + 元数据"，既用于恢复也用于发布；差别在于是否携带优化器状态与评分。
- 弹性在推荐训练里的难点是 embedding 分片与 rank 绑定（DynamicEmb 的 delta 重放要求 world_size 与布局一致），TorchRec 的 200 ms/100 GB resharding 与 Primus 的动态扩缩是目前仅有的两条公开解法，前者解决 GPU 数变化，后者解决 CPU 侧数据任务的扩缩。

### Gaps
- ETT 论文正文不可达：各组件的损耗占比、异步 checkpoint 的实现（是否基于 torch.distributed.checkpoint 的 async_save）、恢复成本的具体削减手段均未知。
- DECK 全文不可达，12× 与"近零开销"未核实；Meta 多 TB 模型的 checkpoint 周期与恢复时间无数据。
- 没有任何公司公开"数百个持续训练作业"的调度器设计、优先级策略或 GPU 份额分配；Lattice/HyperCast 只给出模型数量减少的方向。
- 字节/快手/阿里的 checkpoint 周期、热更新延迟、故障率均无公开数字。

## 5. 蒸馏与基础模型训练流水线：教师推理、批+流混合蒸馏、成本分摊

### Takeaway
四套公开流水线（Meta ExFM/HyperCast/Lattice、字节 Rec-Distill/TM20K）在系统侧收敛到同一拓扑：教师独立流式训练 → 教师推理作为**旁路作业**（离线 logging tier / 后台精算 / 中间存储）→ 产物以"候选级特征"或"logits 流"落盘 → 学生以 join 后的流消费；成本分摊靠 1-to-N（ExFM FM 服务多个 VM、HyperCast 一个 FM 多 surface、Lattice teacher:student GPU 约 1:100、Rec-Distill 跨阶段蒸馏），教师的推理开销靠"只对被服务子集/最相关物品推理"（HyperCast logging 层主机只需在线层 1/3；Lattice 只算前序阶段选出的物品；TM20K 教师"只训一次、不在线推理"）压缩。

### Cited Findings
- ExFM：外部蒸馏（教师单独训练、预测离线记录）而非共训练，理由是"共训练会增加服务模型的训练计算成本，无法满足训练延迟限制"，且"为每个服务模型维护专属大教师不可扩展"，故教师做成 1-to-N 的 FM；DAS 负责 FM 监督记录与 VM 数据合并（A，第 2 节）。FM 规模 0.8T–3.2T、各阶段 VM NE +0.11–0.25%（A，02 号笔记）。
- HyperCast：FM 与 expert 完全解耦训练（各自作业、各自数据），三层推理（在线 FM / 离线 FM logging 仅 1/3 主机 / 在线 expert），训练 0.5B 用 160 H100、1B 用 512 H100，"把 GPU 资源集中到一个 FM 上而不牺牲 expert 的快速迭代"（A，第 2 节 + 02 号笔记）。
- Lattice：KTAP 的后台教师作业 + TTL 嵌入缓存 + logits 双通道；"合并后模型少，才能做定制 kernel 与低精度"；teacher:student GPU ≈ 1:100（A，02 号笔记）。
- Rec-Distill：黑盒蒸馏（只用教师输出 logits 做交叉熵）、解耦训练、去偏重投影、批→流两阶段流水线、解耦塔；教师扩到 24B dense/20K 序列，迁移率最高 >60%；明确对比 ExFM"主要关注成本分摊，没有系统回答如何在把教师推到极限时最大化知识迁移"；提出用"教师增益 × 迁移率"分解蒸馏收益（A，第 2 节 + 02 号笔记）。
- TM20K：教师保留全部 20K token、"只训练一次、无需在线推理，因此在大规模场景下开销几乎可忽略"，学生做三类 token 合并后在线服务；教师 batch 96 vs 学生 320（A，第 3 节）。
- LLaTTE：上游用户模型由高价值事件触发、在专用 H100 集群做高吞吐推理并写入特征存储（A，02 号笔记）。

### Inferences
- 教师推理的落地形态决定了新鲜度与成本：候选级特征落盘（HyperCast/ExFM）最省但新鲜度受 logging 周期限制；TTL 缓存（Lattice）允许推理时也用教师信号；logits 流 join（Rec-Distill）新鲜度最高但要求低延迟中间存储。字节与 Meta 的差异在于 Meta 把教师嵌入当特征（需要教师在线推理层），字节把教师当纯训练信号（不上线）。
- "1:100"级分摊的前提是教师只服务训练，不进在线请求路径；一旦教师 embedding 进入服务（HyperCast 在线 FM 层），分摊比例会退化，这也是 HyperCast 要单独强调"端到端延迟与 CPU 持平"的原因。

### Gaps
- 各流水线的教师推理吞吐、落盘延迟、中间存储规模（Rec-Distill）、logging 层 GPU 数（HyperCast）均无公开数字。
- 没有公开的"教师停训 N 小时对学生指标影响"的量化曲线（ExFM 只有教师自身陈旧性曲线）。

## 6. 替代硬件上的推荐训练：昇腾、阿里 PPU、Meta MTIA、TPU SparseCore、AMD

### Takeaway
公开实践分四档：**Google/TPU** 的 SparseCore 路线最成熟（jax-tpu-embedding 库、KerasRS `DistributedEmbedding`、TorchRec v1.9.1 的 `torch_tpu` 实验包、PLUM 的 1024 片 v6e、Google 广告训练基础设施论文的分区/流水线/RPC 合并）；**Meta/MTIA 300** 已投产做 R&R 训练并把 RDMA NIC 集成进芯片、配套 HCCL，但性能数据只有 C 级；**阿里 PPU** 有两篇生产论文（EST 用 32/128 PPU、TBGRecall 的 PPU 810E 约 A100 60% 算力）且 RecIS 发布专门的 `cuppu` wheel；**昇腾** 有 TurboGR 论文（0.2B 生成式推荐在昇腾上 54.71% MFU）与华为 Rec SDK 26.1.0（torch_rec_v2 动态表淘汰、Ascend 950 适配），但无生产规模披露；**AMD MI300** 只有 Meta ULTRA-HSTU 的 kernel 调优与 RecIS 的 ROCm 构建。

### Cited Findings
- TPU：TorchRec v1.9.0 把 `tpu` 加为 planner/DMP 设备并加入 Pallas embedding kernel，v1.9.1 发布 `torchrec.experimental.torch_tpu`（SparseCore；含 SparseCore 专用 dataloader、checkpoint planner、不均匀 all-to-all padding）（A，第 1 节）；`jax-tpu-embedding` 库支持 v5 起的 SparseCore，"把优化器更新融合进 SparseCore 上的反向，避免梯度回传主机"，提供 SGD/Adagrad/Adam/FTRL/LaProp — [jax-tpu-embedding docs](https://jax-tpu-embedding.readthedocs.io/en/stable/)（B）；KerasRS `DistributedEmbedding` 示例（2025-06 创建、2025-09 更新）在 v5p/v6e 上把表分片到 SparseCore、模型复制 — [keras.io](https://keras.io/keras_rs/examples/distributed_embedding_jax/)（B）；Google 广告训练基础设施论文的 TPU embedding 分区/流水线/RPC 合并（B，第 1 节）；PLUM 1024×v6e（A，02 号笔记）。
- Meta MTIA：MTIA 300"第一款面向 R&R 训练的 MTIA"，已投产；动机为 embedding 集合通信与计算争抢；片上 NIC + HCCL（B）；MTIA 400 面向 R&R + GenAI、实验室测试中（B/C）；TorchRec planner 原生支持 `mtia`（A）。
- 阿里 PPU：EST 在 32 个 PPU 上训练、128 PPU 做 scaling、每 PPU batch 1000（A，02 号笔记）；TBGRecall 部署于 PPU 810E"算力约 A100 的 60%"（A）；RecIS 发布 `recis[cuppu]` wheel 并"与 column-io 一致"，同时修复 NVIDIA/ROCm 构建兼容（A，第 1 节）。
- 昇腾：TurboGR（arXiv 2605.13433，2026-05）"面向昇腾 NPU 集群的生成式推荐训练系统"，针对 jagged 计算冗余、稀疏-稠密通信开销、负采样显存压力，提出分层稀疏并行、流水线编排与"有收敛保证的半异步训练"，KuaiRand-27K 上 0.2B 模型 54.71% MFU、扩展效率 0.97、设备间不均 47%→2.4%、NPU 利用率 94%，并指出昇腾"缺少高性能 jagged 算子、不规则稀疏操作与稠密优化硬件不匹配" — [arXiv 2605.13433](https://arxiv.org/pdf/2605.13433)（B，搜索摘要，作者单位未核实，规模为公开数据集）；华为 Rec SDK 26.1.0：训练框架与生成式推荐算子适配 Ascend 950、torch_rec_v2 新增动态表淘汰；MindSpore Recommender 的分布式多级 Embedding Cache（B，第 1 节）。
- AMD：ULTRA-HSTU 为 MI300X 做 XCD 感知调度等并得到 2× 于 Triton 基线（A）；RecIS v1.2.18 "NVIDIA/ROCm 构建兼容"（A）。

### Inferences
- 替代硬件的公开成熟度与"是否有 PyTorch 侧稀疏栈"强相关：TPU 有 TorchRec/JAX 两条，PPU 有 RecIS，昇腾有 torch_rec_v2，MTIA 有 TorchRec 的设备支持；没有稀疏栈的加速器在推荐训练中没有公开案例。
- 所有替代硬件论文/博客都把 embedding 通信当第一问题（MTIA 片上 NIC、TurboGR 分层稀疏并行、Google RPC 合并、SparseCore 片上更新），与 GPU 侧的 SemiSync/SM-free 集合通信是同一问题的硬件解。

### Gaps
- MTIA 300、PPU、昇腾均无与 GPU 的同口径吞吐/成本对比；TurboGR 的 54.71% 与 GPU 上的 HSTU 34.5% 不同模型规模/数据集，不可比。
- TorchRec `torch_tpu` 在 Meta/Google 内部的使用情况未知（OSS 构建缺 `pybind_input_preprocessing`）。

## 7. 公开吞吐/成本数字汇总、与 LLM 训练栈的收敛点与不收敛点、未来 12 个月判断

### Takeaway
2025 中–2026 年可引用的训练吞吐/成本数字集中在：NVIDIA 公开 benchmark（341.6 TFLOPS/GPU、701K tokens/s/GPU、DynamicEmb 查表 21.56 ms/65536 batch）、Meta（ETT +15.5%/fleet 90%+、Lattice 1024 GPU 1.3× 硬件效率与 20% 容量、GEM 4× FLOPs 下效率翻倍、ULTRA-HSTU 训练 +10%/+15%）、字节（Primus 成本 −17.1%、STCA 2.2×/5.1×、TM20K 3.5×/+49 GB、Token Parallel +29.2%）、美团 1.6–2.4×、Google +116%/−18%。与 LLM 栈的收敛发生在 dense 侧（Megatron-Core/FSDP/ZeRO/Megablocks/torch.compile/AOTI/NCCLX/FA3/DeepSeek-MoE），不收敛的恰是推荐训练的本体——稀疏表（哈希/准入/淘汰/增量同步）、jagged 数据路径、请求级样本组织、半同步/异步更新、流式单遍训练与 O2O 一致性。未来 12 个月最可能的变化：ETT 类 fleet 级指标与 delta checkpoint 进入主流、FP8 训练从 Meta 扩散到其他公司、"教师只训一次/只服务训练"的蒸馏流水线成为长序列扩展的默认形态、以及 MTIA/昇腾等在稀疏通信上的硬件解法开始有同口径数据。

### Cited Findings
- 吞吐/成本数字（均已在前文给出来源）：NVIDIA 16×H100 HSTU 341.6 TFLOPS/GPU、187 ms/步、701.4K tokens/s/GPU（A）；DynamicEmb 查表 21.56 vs 14.88 ms（A）；Meta ETT 平均 +15.5%、最大 85%、fleet 80%→90%+（B）；Lattice 1024 GPU 1.3× 硬件效率、20% 容量节省（A）；GEM 4× FLOPs、效率 2×、20–25% MFU（B）；ULTRA-HSTU 混合精度训练 +10%、LBSL +15%、重物化开销 5%（A）；Primus 集群成本 −17.1%、CPU 利用率 50→80%、任务生成 23×（B）；STCA 2.2×/5.1×、PS CPU −50%（A）；TM20K 3.5× 训练时间/+49 GB（A）；TokenMixer-Large Token Parallel +29.2%/+96.6%（A）；MTGR 1.6–2.4×（A）；Google +116% 性能/−18% 成本（B）；TorchRec resharding 200 ms/100 GB（A）；OneRec 18B 样本/天于 720 GPU（A；折算集群约 20.8 万样本/s、约 289 样本/s/GPU，推导见 Inferences）。
- 收敛点（原文措辞）：NVIDIA 例子"TorchRec 做 embedding 分片 + Megatron-Core 做 dense 并行（DP/TP/SP/PP/CP）"（A）；SORT"RecIS + Megablocks"、torch.export + AOTInductor、"应用 LLM 的通用优化：半精度、KV cache、多上下文多流执行"（A）；OneRec ZeRO-1 + 编译（A）；Lattice/GEM 的 FSDP（A/B）；WHALE/SORT 的 torch.compile/AOTI（A）；GEM 的 NCCLX 与 Expert Parallelism（B）；ULTRA-HSTU 的 FA3 思路（A）；OneRec-V2/TBGRecall/SORT 的 DeepSeek 式 MoE（A）；Talos 把 LLM 时代的编码 agent 用于推荐 kernel 优化（A）。
- 不收敛点（原文措辞）：SORT"sparse 模块受 I/O 与访存限制、dense 受计算效率支配"（A）；STCA"存储与带宽而非 FLOPs 成为瓶颈"（A）；TorchRec SemiSync"用 B-2 参数让 all-to-all 与前向完全重叠"（A）；字节"sparse 异步、dense 同步"（A）；Pinterest"第一个 epoch 后过拟合"（B）；VLM 的流式/批双模式 O2O 一致性（A）；Kunlun 对 3–15% MFU 根因的归纳（A）；SID-GR 用 THD/jagged 而非 padded dense（A）；TurboGR 指出昇腾缺 jagged 算子（B）。

### Inferences
- 用公开数字做一次粗折算：OneRec 180 亿样本/天 ÷ 86,400 s ÷ 720 GPU ≈ **289 样本/s/GPU**（每样本 3 个目标 token，即约 870 token/s/GPU 的"目标 token"吞吐，不含输入序列）；NVIDIA HSTU 示例 701K tokens/s/GPU 是含 4K 输入序列的有效 token 口径；两者口径不同，不能比，但说明生成式推荐的"每 GPU 样本吞吐"量级在百级/秒，与 LLM 预训练的 token 吞吐不是一个度量。
- 收敛的边界正好是"模型里有没有 ID"：dense 侧完全可以复用 LLM 栈（并行、编译、kernel、MoE、低精度），而 ID 决定了哈希表、jagged、请求级样本、流式单遍与 PS 残留；SID 路线（OneRec/GR4AD/PLUM/"Beyond Item IDs"）之所以被反复强调"通信效率"，是因为它把一部分稀疏问题转成了 dense 问题。
- 未来 12 个月（2026-10→2027-10）的判断：(1) fleet 级 ETT 与 delta checkpoint 会被更多公司当作公开指标——Meta 已把它写成论文，字节在 RL 系统里已用 ETTR；(2) FP8/MXFP8 **训练**会从 Meta 向字节/阿里扩散，但形式是"GEMM 级 + 融合量化 + 架构改造"而非全模型 FP8；(3) 10k–100K 序列的训练会继续靠"教师只训一次 + 学生压缩"（TM20K/Rec-Distill）与"训短推长 + 负载均衡随机长度"而非序列并行；(4) 增量同步接口（DynamicEmb replay、TorchRec delta tracker）会被在线学习系统直接采用，服务侧将运行与训练一致的动态表结构；(5) HugeCTR 不会再有功能性发布，NVIDIA 的推荐栈等于 recsys-examples + FBGEMM；(6) 昇腾/PPU/MTIA 的稀疏通信硬件化会出现第一批同口径对比，但主流仍是 H100/B200。

### Gaps
- 没有任何公司公开每样本/每 token 的训练美元成本或 GPU-小时数；"训练成本不变"类说法（MTGR、RankMixer、TM20K）都是相对口径。
- GEM 的 GPU 数量、MFU 口径、与 GEM 配套的训练数据吞吐未披露；Meta 财报只给"训练 GPU 翻倍"（02 号笔记）。
- LLM 栈复用的负面经验（如 FSDP 对稀疏表的不适配、Megatron CP 对 jagged 的支持程度）没有公开的失败案例，只能从各家"自研 kernel"的选择反推。
- 以上 12 个月判断基于 2025-05 至 2026-10 的论文与仓库，没有任何公司公开 2027 年训练系统路线图。

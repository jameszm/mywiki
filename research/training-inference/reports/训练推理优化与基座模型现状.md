# 低精度与计算复用重写算力账本

截至 2026 年 10 月，训练推理优化领域可引用的算力红利，几乎全部来自"每 FLOP 的效果"与"每请求的复用"，而不是峰值算力或参数规模。LLM 训练在系统层已经标准化为"Megatron-Core + Transformer Engine + PP16 × EP16–64 × ZeRO-1 + FP8/MXFP8"，万卡级平台把 ETTR（有效训练时间比）做到 **97%**（字节 ByteRobust，9,600 GPU 的三个月任务），而十万卡级同步训练若不做副本级容错可低至 **44%**；LLM 推理收敛到"PD 分离 + 大规模专家并行 + 分层 KV + KV 感知路由"，DeepSeek 自营 H800 集群的 **每 GPU 约 1.85k 输出 token/s** 与 SGLang 复现的 **$0.20/百万输出 token** 构成行业标尺，Blackwell 上同模型再快 3–5×。推荐栈走的是另一条曲线：MFU 从 4.5% 被拉到 **45–62%**（字节 RankMixer、TokenMixer-Large、快手 OneRec-V2），第一桶红利来自"把访存受限的碎片算子换成大 GEMM"和"用户侧只算一次"，而非扩容；代价是瓶颈外移到样本流水线（Meta 在 **4K 序列**就撞上"数据基础设施资源超过 GPU 训练"的墙）、激活显存（序列 5K→20K 使训练时间 3.5×、显存 +49 GB）与专用 beam 解码引擎。"基座模型"在两个层面都有可行路径也有硬边界：推荐基础模型的 ROI 来自"迁移率 × 下游模型数"（logits 蒸馏 45–73%、表征注入 0.64–1.0），下游模型少于十个时公开数据不支持建设万亿级 FM；通用开源基座中唯一公开消融证明"LLM 初始化有益"的是 YouTube PLUM，主流做法仍是"用 LLM 产特征而不用 LLM 权重"。硬件侧，代际收益中可量化的部分全在 FP4/FP8 与互连拓扑，BF16 的每 FLOP 成本两年几乎没降，而国内算力在未来 12 个月仍以 Hopper 级（H20/H800/H200）叠加国产卡为基线。

**阅读约定**。本报告只用公开信息，覆盖 2025 年中至 2026 年 10 月。结论状态分三类：**【生产+数据】** 官方确认生产部署且给出量化数字；**【技报/规模未知】** 有技术报告或开源文档但未确认部署规模；**【仅研究】** 学术或原型阶段。笔记中标注"未核实"的数字（第三方转述、搜索摘要、媒体报道，以及无法读到原文的官方博客）在此一律保留该标注，不得当作既定事实使用。MFU 数字只在同一峰值口径内可比——NVIDIA 官方表只给 Model TFLOP/s/GPU，本报告中的百分比按"所用精度的非稀疏峰值"折算，跨公司直接排序 MFU 没有意义。

## 全景：算力效率的刻度已经固定，MoE 与推荐各有自己的天花板

2026 年可对标的效率刻度来自两份可复现材料。NVIDIA 官方性能页给出同平台 dense 与 MoE 的结构性差距：GB300×256 上 Llama 3.1 405B 以 FP8 跑到 **2,646 TFLOPS/GPU（约为 FP8 峰值的 54%）**，而同平台 DeepSeek-V3 以 MXFP8 只有 **1,648（34%）**、Qwen3-235B-A22B **1,335（27%）**、Kimi-K2 1T **1,099（22%）**；在 H100 上差距更大，Llama 405B FP8 为 **822（42%）**，而 Qwen3-30B-A3B 只有 **203（10%）**（[Megatron-Bridge 性能归档](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/main/docs/performance-summary-archive.md)）【生产+数据，厂商基准】。Megatron-Core 自述在 H100 集群上训练 2B–462B 模型可达 **47% MFU**，并给出强扩展代价：GPT-3 175B 从 96 张扩到 4,608 张 H100、全局 batch 固定时 MFU 由 47% 降到 42%（[Megatron-LM README](https://github.com/NVIDIA/Megatron-LM/blob/main/README.md)）。这两组数字联合说明：**MoE 的"每 token 激活参数少 → GEMM 小 → 算术强度低 + all-to-all"是结构性损失，不会被单点 kernel 优化抹平**，这正是 2025–2026 年的工程重心集中在通信重叠（DualPipe/1F1B A2A/COMET）与分发库（DeepEP/NCCL EP/HybridEP）而不是算子微调的原因。值得注意的是，NVIDIA 的 MoE 基准明确"强制均衡专家 token 分布且不丢 token"，即官方 TFLOPS 是均衡上限，真实训练的路由失衡会进一步拉低（[Megatron-Bridge 性能页脚注](https://github.com/NVIDIA-NeMo/Megatron-Bridge/blob/main/docs/performance-summary.md)）。

推荐侧的刻度完全不同，且进步幅度更大。公开的 MFU 轨迹已构成行业基准：字节 RankMixer 把抖音 Feed 排序模型的 MFU 从 **4.5% 提到 45%**（[arXiv 2507.15551](https://arxiv.org/abs/2507.15551)）【生产+数据】，TokenMixer-Large 的线上广告骨干到 **60%**（[arXiv 2602.06563](https://arxiv.org/abs/2602.06563)）【生产+数据】，Meta Kunlun 在 B200 上 **17%→37%**（[arXiv 2602.10016](https://arxiv.org/abs/2602.10016)）【生产+数据】，快手 OneRec 训练/推理从 4.6%/11.2% 到 **23.7%/28.8%**、OneRec-V2 推理 **62%**（[arXiv 2506.13695](https://arxiv.org/abs/2506.13695)、[arXiv 2508.20900](https://arxiv.org/abs/2508.20900)）【生产+数据】，阿里 SORT **13%→22%**（[arXiv 2603.03988](https://arxiv.org/abs/2603.03988)）【生产+数据】，NVIDIA 公开的 HSTU 示例在 16×H100 上 **341.6 TFLOPS/GPU、MFU 34.54%**（[PERF_ANALYSIS.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/PERF_ANALYSIS.md)）【技报/规模未知，示例规模】。Meta 博客称 GEM 在 12 个月内把端到端训练效率翻倍到 **MFU 20–25%** 且总训练 FLOPs 扩大 4×（[engineering.fb.com](https://engineering.fb.com/2026/08/03/ml-applications/training-gem-at-llm-scale-meta-ads-recommendation-foundation-model/)，原文不可达、**未核实**）。Kunlun 把推荐模型长期只有 3–15% MFU 的原因归结为"异构特征空间导致小 embedding 维度、不规则张量形状、访存受限操作"——这解释了为什么推荐侧的第一桶红利来自改模型（把碎片算子换成大 GEMM）而非改系统，也意味着一旦 MFU 到 45–60%，剩下的只有 FP8 训练与"把通信搬离 SM"两条路。

全景判断因此可以写成一句话：**LLM 栈在把"系统效率"工业化，推荐栈在把"模型形态"GPU 化，两者在 2026 年于 dense 侧合流，而在稀疏侧仍然分叉**。更值得起步团队注意的是第三条轴——有效时间。Meta 在 2026-10 把"持续训练的生命周期损耗"量化成论文：最大负载每天数百亿样本、数千 GPU，此前端到端 wall time 只有约 50–60% 用于训练新数据，经 trainer 初始化、编译缓存、异步 checkpoint 与恢复成本优化后 **ETT% 平均 +15.5%、最大负载达 85%，全 fleet 从约 80% 升到 90% 以上**（[arXiv 2610.02057](https://arxiv.org/abs/2610.02057)，仅摘要，**未核实**）。对一个运行数百个持续训练作业的团队，这是比 MFU 更便宜的第一桶优化。

## LLM 训练：万卡 MoE 配方已固定，容错范式正在换代

**框架格局已经收敛**。Megatron-Core 事实上成为大规模预训练标准：华为昇腾 MindSpeed、阿里 Pai-Megatron-Patch、AMD Primus、NVIDIA Megatron-Bridge/NeMo 以及 MLPerf 的 NVIDIA/CoreWeave/Azure/Google 提交都建立在它之上，且 **2025-12 起全部开发与 CI 迁到 GitHub 公开进行**（[Megatron-LM README](https://github.com/NVIDIA/Megatron-LM/blob/main/README.md)）。PyTorch 原生路线由 torchtitan 承担（FSDP2 + DTensor + MXFP8/NVFP4，模型定义已覆盖 DeepSeek V3/V4、Kimi K2.7/K3、Qwen3.8），但公开基准止于 512 GPU，工业采用仍以"研究/中等规模/第二后端"为主（[torchtitan README](https://github.com/pytorch/torchtitan/blob/main/README.md)、[dgxc-benchmarking README](https://github.com/NVIDIA/dgxc-benchmarking/blob/main/README.md)）。DeepSpeed 的 2025–2026 产出集中在 offload 与超芯片（ZenFlow 较 ZeRO-Offload 最高 5×、SuperOffload 在 GH200 上单卡全参微调达 600 TFLOPS），已不是前沿预训练主栈，但其 **ZeRO++ 被 LinkedIn 用于推荐系统 LLM 的大规模蒸馏训练**（EMNLP 2025 industry），对推荐团队有直接参考价值（[DeepSpeed README](https://github.com/deepspeedai/DeepSpeed/blob/master/README.md)）。字节的训练基础设施呈"论文开源、核心闭源"：MegaScale 系列只有论文，开源的是外围组件 veScale-FSDP、VeOmni、Flux/COMET、Triton-distributed（[veScale README](https://github.com/volcengine/veScale/blob/main/README.md)、[VeOmni README](https://github.com/ByteDance-Seed/VeOmni/blob/main/README.md)）。

**并行配方只有两种公开样本，且相互对立**。DeepSeek-V3 是唯一同时公开规模、并行、精度与成本的样本：2,048 张 H800、**16 路 PP × 64 路 EP（跨 8 节点）× ZeRO-1，不用 TP**，DualPipe 把 EP all-to-all 完全藏进计算，node-limited routing 让每 token 最多发往 4 个节点，**仅 20 个 SM 即可打满 IB+NVLink**；14.8T token 预训练耗 2.664M H800 小时，全程 **2.788M GPU 小时 / 557.6 万美元**（按 2 美元/GPU 小时，不含前期研究与消融），全程"没有不可恢复的 loss spike、没有回滚"（[DeepSeek-V3 技术报告](https://arxiv.org/abs/2412.19437)）【生产+数据】。Kimi K2（1T/32B）给出相反选择：**明确拒绝 DualPipe**（"参数与梯度内存翻倍，对 1T 模型代价过高"），改用交错 1F1B + 延后权重梯度计算，**EP 取最小可行值 16**，激活大部分 offload 到 CPU，FP8-E4M3 只用于激活存储、**不在计算中使用 FP8**（"预研中观察到性能退化风险"）；集群为 H800 + **8×400 Gbps RoCE**，总规模未披露（[Kimi K2 技术报告](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)）【技报/规模未知】。两者的差异主要由 scale-up 域决定：NVIDIA 为 Kimi-K2 在 NVL72 上给出的参考配置又回到 **TP1/PP4/EP64**（[dgxc kimi-k2 README](https://github.com/NVIDIA/dgxc-benchmarking/blob/main/kimi-k2/README.md)），说明"小 EP"是 8 卡 NVLink + RoCE 的约束产物，而非模型属性。其余头部报告几乎不披露系统细节——Qwen3 技术报告全文无 GPU 类型/数量/并行/MFU，GLM-4.5、gpt-oss、Hunyuan-A13B 同样缺失，这意味着对国内团队而言 DeepSeek、Kimi、ERNIE（最大模型预训练 **47% MFU**，口径未说明）、LongCat、Pangu 是仅有的可引用样本（[Qwen3 技术报告](https://github.com/QwenLM/Qwen3/blob/main/Qwen3_Technical_Report.pdf)、[ERNIE README](https://github.com/PaddlePaddle/ERNIE/blob/develop/README.md)）。

**容错范式正在从 checkpoint-restart 换成副本/步内恢复**，这是 2025–2026 最可迁移的一条经验。字节 ByteRobust 把故障检测与恢复作为常规流程，部署在 **超过 200,000 GPU** 的生产平台，9,600 GPU 的三个月训练任务达到 **97% ETTR**（[arXiv 2509.16293](https://arxiv.org/abs/2509.16293)）【生产+数据，仅摘要】；而在 O(100K) GPU 规模上，FT-HSDP 报告未做副本级容错时有效训练时间可低至 44%，以 DP 副本为容错单元后**故障恢复停顿从 10 分钟降到 3 分钟、有效训练时间 44%→80%**（[arXiv 2602.00277](https://arxiv.org/abs/2602.00277)）【仅研究/摘要】。straggler 治理同样已量化：Guard 用在线性能监控 + 离线节点扫查捕捉 fail-slow，部署于大规模基础模型预训练，**平均 FLOPs 利用率最高 +1.7×、run-to-run step 方差从 20% 降到 1%**（[arXiv 2605.17879](https://arxiv.org/abs/2605.17879)）；字节与 NYU 的 OSDI'25 工作基于集群 5 个月 trace 做"无 straggler 模拟"的 what-if 分析，结论之一是"straggler 并不总由硬件故障引起"（[USENIX OSDI'25](https://www.usenix.org/conference/osdi25/presentation/lin-jinkun)）。checkpoint 侧 TierCheck 把端到端时间压到 **<10 秒**（[arXiv 2605.17821](https://arxiv.org/abs/2605.17821)），NVIDIA Resiliency Extension 提供 in-job 重启、热备节点与 NVLink 重放计数器健康检查（[nvidia-resiliency-ext README](https://github.com/NVIDIA/nvidia-resiliency-ext/blob/main/README.md)）。数据与存储的公开样本只有两个但都重要：DeepSeek 3FS 以 **180 个存储节点在带训练背景流量下达到约 6.6 TiB/s 聚合读**，同时服务 dataloader 随机访问、并行 checkpoint 与 KV cache（[3FS README](https://github.com/deepseek-ai/3FS/blob/main/README.md)）；字节 OVERLORD 用集中式声明式 data plane 加 Shadow Loader 差分 checkpoint 解决"DP 范式 dataloader 负载失衡与多源内存爆炸"，部署于数千 GPU 生产集群（[arXiv 2504.09844](https://arxiv.org/abs/2504.09844)）——这两个问题与推荐训练的多源变长样本流完全同构。

**精度的生产化程度分三档**。FP8 已是 Hopper 时代默认：DeepSeek 式 1×128 激活 tile + 128×128 权重 block 缩放、每 128 元素提升到 CUDA Core 做 FP32 累加（H800 Tensor Core 累加仅约 14 bit），约 1T token 验证下**相对 loss 误差 <0.25%**；蚂蚁 Ling 2.0 全程 FP8 训练、>1T token 实验 loss 与 BF16 几乎一致并开源方案（[DeepSeek-V3 §3.3](https://arxiv.org/abs/2412.19437)、[Ling-V2 README](https://github.com/inclusionAI/Ling-V2)）。Blackwell 上 MXFP8 成为 NVIDIA 官方基准默认，torchtitan 在 **512 GPU GB200 上 Llama4 Scout 从 6,169 提到 7,401 tokens/s（+20.3%）且 3,000 步收敛与 BF16 等价**（[torchtitan mxfp8 README](https://github.com/pytorch/torchtitan/blob/main/torchtitan/quantization/mxfp8/README.md)）。FP4 预训练在 2026 年出现真实生产案例，但**仅限 NVIDIA 自家 Nemotron 3**：Super 120B-A12B（25T token）与 Ultra 550B-A55B（20T token）均为 NVFP4 预训练并开源权重与配方（[arXiv 2604.12374](https://arxiv.org/abs/2604.12374)、[arXiv 2606.15007](https://arxiv.org/abs/2606.15007)）；官方表显示 Llama 405B 在 GB300 上 NVFP4 相对 FP8 为 **3,575 vs 2,646 TFLOPS（1.35×）**，远低于峰值比，且 MoE 上几乎无增益（Nemotron Super 的 NVFP4 仅比 MXFP8 快约 3%）。中国头部实验室在 2026-10 前没有 FP4 预训练的公开生产案例，Kimi 甚至不用 FP8 计算——对 H800/H20 用户，可落地的是"FP8 计算 + MXFP4 激活/EP 通信压缩"这类不依赖 FP4 Tensor Core 的方案（671B 规模下吞吐 +12.5%、峰值激活内存 −14.8%，[arXiv 2603.02731](https://arxiv.org/abs/2603.02731)）【仅研究/摘要】。

最后是可引用的成本与吞吐锚点：Llama 3.1 405B FP8 的每 GPU 吞吐为 **H100 326 → GB200 843 → GB300 1,048 tok/s**（2.6×/3.2×）；MLPerf Training v6.0 新增 DeepSeek-V3 671B 预训练项，**CoreWeave 以 8,192 张 GB300 做到 1.96 分钟**、NVIDIA 以 8,192 张 GB200 做到 3.19 分钟（[training_results_v6.0](https://github.com/mlcommons/training_results_v6.0)，由 run_0 日志计算）；公开训练成本样本只有 DeepSeek-V3（557.6 万美元）、Llama 4（Scout+Maverick 合计 **7.38M H100 小时**，[Llama 4 模型卡](https://github.com/meta-llama/llama-models/blob/main/models/llama4/MODEL_CARD.md)）与 MiniMax-M1 的 RL（**512 张 H800、3 周、约 53 万美元**，[MiniMax-M1 技术报告](https://github.com/MiniMax-AI/MiniMax-M1/blob/main/MiniMax_M1_tech_report.pdf)）。万卡级扩展损失仍有 25–40%，与 Megatron 的 175B 强扩展曲线一致。

## LLM 推理：PD 分离买的是 goodput，KV 成了一等公民

开源推理栈已分化为三层结构：**引擎层**（vLLM、SGLang、TensorRT-LLM）、**分布式编排层**（NVIDIA Dynamo、llm-d、SGLang Router、字节 AIBrix、vLLM production-stack）与 **KV 存储/传输层**（Mooncake、LMCache、NIXL、腾讯 FlexKV、3FS）。到 2026 年"选哪个引擎"已不是核心性能问题——三者在 Blackwell 上的 DeepSeek 数字互相追赶且共享 FlashInfer/DeepGEMM/DeepEP 内核——而是生态问题：vLLM 覆盖最广（自述 1,000+ 模型架构、600+ 加速器类型，每晚对 17 个模型-硬件组合跑精度与性能回归，夜间 bot 自动定位 culprit 并开 revert PR 约 1.5 个/天，[vLLM 质量博客](https://vllm.ai/blog/2026-07-16-keeping-vllm-production-quality)），SGLang 在国产 MoE 的 day-0 优化与国内硬件实践上材料最丰富，TRT-LLM 在 NVIDIA 最新硬件上最先拿到极限数字（[Dynamo README](https://github.com/ai-dynamo/dynamo)、[Mini-SGLang](https://lmsys.org/blog/2025-12-17-minisgl/)）。国内自研引擎（阿里 RTP-LLM、百度 FastDeploy、京东 xLLM、字节 AIBrix）的公开价值集中在国产芯片适配与控制面，核心内核创新多以 PR 形式回流 SGLang/vLLM。

**事实标杆仍是 DeepSeek 2025-03 公开的生产系统**：prefill 单元 4 节点 EP32、decode 单元 18 节点 EP144，prefill 用双微批交替隐藏通信，decode 用注意力拆两步的 5 级流水，配三类负载均衡器；24 小时统计中每节点约 **73.7k 输入 tok/s 或 14.8k 输出 tok/s（即约 1.85k 输出 tok/s/GPU）**，输出速度 20–22 tok/s/user，**56.3% 输入命中磁盘 KV 缓存**，按 2 美元/GPU 小时计日成本 $87,072、按 R1 价目理论日收入 $562,027（[DeepSeek 推理系统概览](https://github.com/deepseek-ai/open-infra-index/blob/main/202502OpenSourceWeek/day_6_one_more_thing_deepseekV3R1_inference_system_overview.md)）【生产+数据】。SGLang 在 96 张 H100 上复现并给出自建成本 **$0.20/百万输出 token**（[SGLang 大规模 EP](https://lmsys.org/blog/2025-05-05-large-scale-ep/)）；Blackwell 上同模型在 FP8 attention + NVFP4 MoE 下达到 **prefill 26,156 / decode 13,386 tok/s/GPU，相对 H100 3.8×/4.8×**（[SGLang GB200 Part II](https://lmsys.org/blog/2025-09-25-gb200-part-2/)）；GB300 在 128K/8K 长上下文下 **226.2 TPS/GPU，比 GB200 高 1.53×**，且 288 GB HBM 把 decode 并发从 24 提到 40 req/GPU（[SGLang GB300 长上下文](https://lmsys.org/blog/2026-02-19-gb300-longctx/)）。

对工程决策最有价值的是 vLLM 对 PD 分离写下的边界：**"PD 分离买的不是峰值吞吐而是 goodput"**。Llama-3.1-70B BF16 每 token KV 为 320 KiB，10k prompt 约 3 GB，400 Gb/s 线速约 65 ms 全落在 TTFT；单机双 L40S（无 NVLink/P2P）实验中 8k prompt 的 470 MB KV 传输耗 1.3 秒，使 P/D 的 TTFT 达 2.2 秒而聚合只有 0.7 秒（ITL 尾部却从 169–263 ms 压到 ≤52 ms）；在 MI300X 上 Qwen3-235B-A22B-FP8 的 8 req/s 场景，P/D 的 goodput 是聚合的 2.4×。其决策表是"ITL p99 超标则分离；TTFT 是约束或 KV 传输慢则保持聚合"（[vLLM 分离式服务指南](https://vllm.ai/blog/2026-09-29-disaggregated-serving-guide)）。EP 规模同样不是越大越好：蚂蚁在 H20 上发现 BS<16 时 EP32 更优，BS≥16 时 EP16 反超（BS=32 时 675 vs 585 tok/s/GPU），原因是 EP16 下约 50% 的 MoE 流量留在 NVLink 而 EP32 只有约 25%，小 EP 还缩小故障域（[蚂蚁 H20 最佳实践](https://lmsys.org/blog/2025-09-26-sglang-ant-group/)）【生产+数据】。

**KV 从优化项变成一等公民**，这是 agent 流量带来的结构性变化。SemiAnalysis 的 AgentX 公开 trace 显示线上负载已是"长上下文短输出"：中位输入 142K、输出 444，**前缀缓存命中率 >96%**，44% 会话含子 agent（[vLLM × AgentX](https://vllm.ai/blog/2026-09-08-vllm-agentx)）。相应的系统回应是分层 KV 与 KV 感知路由：SGLang HiCache 自测最高 6× 吞吐、TTFT −80%，社区数据中 Novita 的 Qwen3-Coder-480B 代码 agent 接 3FS 后 TTFT −56%、命中率 40%→80%，蚂蚁 DeepSeek-R1 PD 分离 + Mooncake 下命中请求 TTFT −84%（[SGLang HiCache](https://lmsys.org/blog/2025-09-10-sglang-hicache/)）【生产+数据】；vLLM × Mooncake Store 在 Codex trace 上把命中率从 1.7% 提到 92.2%，吞吐 3.8×、P50 TTFT −46×（[vLLM × Mooncake](https://vllm.ai/blog/2026-05-06-mooncake-store)）；Dynamo 的 KV 感知路由 A/B 把平均 TTFT 从 63,652 ms 降到 2,586 ms（−96%）（[Dynamo kv-router A/B](https://github.com/ai-dynamo/dynamo/blob/main/docs/fern/pages/recipes/feature-benchmarks/kv-router-a-b-testing.md)）。Mooncake 本身是 Kimi 的生产平台，FAST'25 最佳论文报告真实 trace 下有效请求容量比基线高 **59%–498%**，日处理超 1000 亿 token（[Mooncake FAST'25](https://www.usenix.org/system/files/fast25-qin.pdf)）【生产+数据】。

**加速技术的生产边界也已清晰**。投机解码强依赖并发：SGLang MTP 在 16×H200 小规模（每 rank 2 并发）下 +60%，而 128×H200 大规模（每 rank 128 并发）只有 +14.2%；蚂蚁 H20 生产中 BS=1 时 draft=4 比 draft=2 吞吐 +21%，BS=32 时反而 −18%（[SGLang MTP](https://lmsys.org/blog/2025-07-17-mtp/)、[蚂蚁 H20](https://lmsys.org/blog/2025-09-26-sglang-ant-group/)）。量化的共识是"权重 FP8（Hopper）/NVFP4（Blackwell）+ KV FP8 几乎零成本"：vLLM 的系统评测发现 Hopper FA3 FP8 曾因累加精度使 128k 大海捞针从 **91% 掉到 13%**，两级累加修复后回到 89%，修复后每 token KV 开销可降到 BF16 的 **54%**；而低于 8 bit 的 KV 压缩在 TurboQuant 评测中"省内存但降吞吐"，结论是 **FP8 仍是最佳默认**（[FP8 KV 评测](https://vllm.ai/blog/2026-04-22-fp8-kvcache)、[TurboQuant 研究](https://vllm.ai/blog/2026-05-11-turboquant)）。成本侧，vLLM 在 AgentX 上给出自建与 API 的量级差：DeepSeek V4 Pro 在 12×GB300 上基础设施 TCO 约 **$27.72/h**，同样 token 量走 Opus 5 API（已按缓存读价计）约 **$2,926（106×）**（[vLLM × AgentX](https://vllm.ai/blog/2026-09-08-vllm-agentx)）——这是"自建 vs 买 token"决策最可引用的一组公开数字。

## 推荐训练：请求级批处理是比 FP8 更先决的杠杆

稀疏训练栈在 2025–2026 收敛成三条产品化路线。**Meta/TorchRec** 的主线是 2D 并行→Fully Sharded 2D→训练中动态 resharding→KVZCH/DRAM-SSD 虚拟表→TPU SparseCore 实验包，其中 resharding 达到"约 100 GB 停机约 200 ms，在最多 128 张 A100 上测试"，`TrainPipelineSemiSync` 用 B-2 时刻的参数计算第 B 个 batch，使 embedding all-to-all 与前一 batch 的前向完全重叠（[TorchRec Releases](https://github.com/pytorch/torchrec/releases)、[train_pipelines.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/train_pipeline/train_pipelines.py)）。**NVIDIA recsys-examples** 把 DynamicEmb 从"GPU 哈希表"长成"带准入/淘汰/增量 dump + replay 的训练-服务同步组件"，并把 TorchRec 的 embedding 分片与 Megatron-Core 的 DP/TP/SP/PP/CP 拼在一起；HugeCTR 自 25.03 起只发 Dockerfile 源码、HPS 与 Embedding Cache 已弃用（[recsys-examples CHANGELOG](https://github.com/NVIDIA/recsys-examples/blob/main/CHANGELOG.md)、[HugeCTR README](https://github.com/NVIDIA-Merlin/HugeCTR/blob/main/README.md)）。**阿里 RecIS** 于 2025-09 开源，把"放 GPU 还是 CPU"做成每张表的放置参数，已用于阿里大量"大模型增强推荐"训练任务，v1.2.0 起内置 MFU 指标监控（[RecIS README](https://github.com/alibaba/RecIS/blob/main/README.md)、[CHANGELOG](https://github.com/alibaba/RecIS/blob/main/CHANGELOG.md)）。公开路线中没有谁在 2025–2026 完全放弃主机内存层，差别只在于主机层是"参数服务器进程"还是"同一训练进程的 UVM/host 存储"；框架生态则明显"PyTorch 化"，RecIS 的目标被直接写成"超过 TensorFlow 系推荐框架的效率"，而字节 Monolith 仓库自 2023-11 起无提交。

**MFU 的六个杠杆按收益排序，第一个永远是改模型**。NVIDIA 的完整拆解给出了时间分布：在 16×H100 上 8 层 HSTU、有效序列 T=4,099 时，**HSTU attention 前后向占 43.1%、elementwise 占 21.3%、GEMM 合计 23.7%、embedding 算子仅 5.7%、NCCL 暴露 1.6%**（[PERF_ANALYSIS.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/training/benchmark/PERF_ANALYSIS.md)）。这组数字解释了为什么 DynamicEmb 的动态哈希表有约 45% 的查表开销（去重下 21.56 vs TorchRec 静态表 14.88 ms）却在端到端可以接受——真正的大头是 attention 与逐元素算子。各家的做法高度一致：Kunlun 把 PFFN 重写成多头注意力形式的 GDPA 以"融合进单个 kernel"，去掉 GDPA 会使 MFU 从 37.0% 掉到 34.0%、QPS −8%；TokenMixer-Large 去掉 LHUC、DCNv2 等"低计算强度、高访存与通信开销"的碎片算子做成"纯模型"，并用 MoEGroupedFFN 单 kernel 算全部专家（训练中占 89% 时间且是计算受限）；SORT 发现"SDPA/FlashAttention 不适合推荐的结构化稀疏 mask"，自研跳过全 mask 块的稀疏注意力算子（[arXiv 2602.10016](https://arxiv.org/abs/2602.10016)、[arXiv 2602.06563](https://arxiv.org/abs/2602.06563)、[arXiv 2603.03988](https://arxiv.org/abs/2603.03988)）。

**请求级批处理（RLB）是训练样本流水线与 kernel 效率的交点，也是最被低估的一步**。抖音 STCA 把问题讲得最清楚：若仍按独立三元组 (u,v,y) 组织样本，"同一长历史被序列化、CPU→GPU 传输并重复编码，**随着序列长度增大，存储与带宽而非 FLOPs 成为瓶颈**"；把同用户的多个样本聚成用户微批后仍是经验风险的无偏估计，效果是固定硬件下最大可训长度约 8×、**单 GPU 训练吞吐 2.2×（叠加 kernel 后 5.1×）、网络带宽 −84%、参数服务器 CPU 使用减半**（[arXiv 2511.06077](https://arxiv.org/abs/2511.06077)）【生产+数据】。阿里 SORT 的 request-centric 样本组织、美团 MTGR/MTFM 的用户级聚合、字节 TM20K 的 User-Level Training 是同一原则的变体。对"先做 FP8 还是先做 RLB"的回答因此很明确：**RLB 更先决**，因为它同时解决带宽与 GEMM 形状，而 FP8 的净收益会被量化/缩放开销吃掉（见下节）。

**长序列的真实代价是激活显存与数据带宽，不是 FLOPs**。字节 TM20K 给出最直接的数字：电商广告序列从 5K 拉到 20K，"即使有 FlashAttention 与 M-Falcon，**训练时间 ×3.5、GPU 显存 +49 GB、服务延迟约 ×6.3**"；对策是去 padding（完整 20K 序列最多省 10 GB）、改用"全注意力教师一次训练 + 学生 token 合并"，使线上延迟仅 +5.6%（[arXiv 2608.07055](https://arxiv.org/abs/2608.07055)）【生产+数据】。Meta ULTRA-HSTU 的选择性重物化跳过 6 个大前向张量、重算开销仅 5%，**每层显存 −67%**，并用 LBSL（负载均衡随机长度）按超线性代价模型估计每 rank 负载，训练吞吐 +15%（[arXiv 2602.16986](https://arxiv.org/abs/2602.16986)）【生产+数据】。更上游的瓶颈是样本物化：Meta 的 Versioned Late Materialization 指出为保证线上线下一致而把用户历史快照进每条样本（"Fat Row"），同用户一天 K 次请求就复制 K 份，生产环境**约在 4K 序列处撞墙**，超长序列会使"数据基础设施用量超过 GPU 训练部署"；改为版本化的训练时延迟物化后主训练数据**写带宽 −46.2%、读带宽 −47.7% 到 −70.3%**（[arXiv 2604.24806](https://arxiv.org/abs/2604.24806)）【生产+数据】。

**低精度训练在推荐侧明显落后于 LLM，且公开共识是保守的**。TokenMixer-Large"训练全程 bfloat16，FP8 E4M3 仅用于推理 PTQ"；SORT 用 BF16 AMP 但排序头与 MoE 路由保持 FP32；OneRec 的 BF16 只用于部分 MLP。唯一接近"生产级推荐低精度配方"的公开描述来自 Meta ULTRA-HSTU：**大部分算子保持 BF16 以保证稳定性，FP8 只加速主导的两个 GEMM（UVQK 投影与后注意力投影），INT4 用于 embedding 以降低推理通信**，并明确指出"**简单地把 GEMM 切到 FP8 是低效的**"，必须把行级缩放量化融合进前置归一化 kernel（[arXiv 2602.16986](https://arxiv.org/abs/2602.16986)）。Meta 开源仓库给出了可参考的真实幅度：HSTU Ultra 的完整层栈前向从 BF16 切到 FP8 只有 **1.13–1.25×**（H100 96 GB），而不是单 GEMM 的 2×（[generative-recommenders README](https://github.com/facebookresearch/generative-recommenders/blob/main/README.md)）。值得记住的缺口是：**没有任何公开案例给出"生成式推荐 FP8 训练无损"的定量精度对照**（NE/AUC 差异），也没有排序模型对低精度敏感性的系统性研究。

持续训练管理方面，除前述 ETT 指标外，训练到服务的增量同步已有开源实现：DynamicEmb 的 `incremental_dump`/`replay_increment` 按 slot 写回（要求目标表布局与源完全一致，否则整体拒绝），文档明确"典型部署是 delta 复制：训练作业周期性 dump，delta 运到服务副本，副本重放以追上而无需重载完整 checkpoint"；TorchRec 的 `ModelDeltaTracker` 提供同类能力（[DynamicEmb_APIs.md](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/dynamicemb/DynamicEmb_APIs.md)、[model_delta_tracker.py](https://github.com/pytorch/torchrec/blob/main/torchrec/distributed/model_tracker/model_delta_tracker.py)）。替代硬件的公开成熟度与"是否有 PyTorch 侧稀疏栈"强相关：TPU 有 TorchRec `torch_tpu` 与 jax-tpu-embedding 两条，阿里 PPU 有 RecIS，昇腾有 torch_rec_v2，Meta MTIA 有 TorchRec 的设备支持（planner 原生接受 `mtia`）；Meta 称 MTIA 300 是"MTIA 家族中第一款面向排序与推荐训练的芯片"并把 RDMA NIC 集成进芯片（[engineering.fb.com](https://engineering.fb.com/2026/08/24/ai-research/mtia-300-meta-training-chip/)，搜索摘要，**未核实**），但其算力/HBM/功耗与 GPU 的 TCO 对比只有 C 级来源。

## 推荐推理：四层计算复用，加三处与 LLM 引擎的不适配

**引擎层已经出现共同底座：torch.export + AOTInductor**。NVIDIA（recsys-examples v26.03 起）、Meta（WHALE）、阿里（SORT）三方独立选择它，动机一致——消除 Python 调度与 host-device 同步。可引用的幅度是：3 层 HSTU 每请求延迟从 Python 到 C++ 运行时在 L20 上 **6.031→3.708 ms（1.63×）**、L40S 上 1.90×；在 RTX PRO 6000 上走 Triton 时 Python backend 无缓存 3.161 ms → AOTI 2.471 → AOTI + GPU KV 命中 1.436 ms（2.20×），8 层 batch 8 的最佳情形达 **5.93×**（[inference_aoti benchmark](https://github.com/NVIDIA/recsys-examples/blob/main/examples/hstu/inference_aoti/benchmark/README.md)）【技报，示例规模】；WHALE 的 AOTInductor 消除 host-device 同步省 1–5 ms，合计推理吞吐 +22%、训练 +30%（[arXiv 2607.17017](https://arxiv.org/abs/2607.17017)）【技报/规模未知】；SORT 的 torch.export + AOTI 加稀疏注意力 kernel 与算子融合合计 **+29.4% 吞吐、−29.3% 延迟**（[arXiv 2603.03988](https://arxiv.org/abs/2603.03988)）【生产+数据】。必须强调 NVIDIA 的数字都是 KuaiRand 规模的示例模型（hidden 512/1024、3–8 层），其绝对延迟不能外推到生产；真正的生产锚点是 OneRec-V2（1B、context 3000、beam 512，L20 上 **36 ms、MFU 62%**）与快手 GR4AD（0.16B，**<100 ms、500+ QPS/张 L20**，已全量服务 4 亿用户）（[arXiv 2508.20900](https://arxiv.org/abs/2508.20900)、[arXiv 2602.22732](https://arxiv.org/abs/2602.22732)）【生产+数据】。

**"用户侧算一次"已经扩展成四个层级，边际收益与风险各不相同**。请求内复用是"免费"的（不改变语义、不引入陈旧性），因此 2026 年几乎所有排序论文都默认采用：抖音 LONGER 的 KV cache serving 把多候选打分的吞吐退化从 **−40% 压到 −6.8%**（[arXiv 2505.04421](https://arxiv.org/abs/2505.04421)）；Meta ROCS 把"候选隔离 + 延迟交互 + 内核内广播"做成通用范式，**召回模型最高 3× QPS 无质量损失，短视频排序 LogLoss −0.5% 且 QPS +50%**，已跨广告与自然内容、召回与排序部署（[arXiv 2607.27744](https://arxiv.org/abs/2607.27744)）【生产+数据，仅摘要】；Pinterest PinFM 的去重 cross-attention 使服务吞吐 **+600%**（[arXiv 2507.12704](https://arxiv.org/abs/2507.12704)）。跨请求复用引入存储与路由问题：字节 OneTrans 因行为序列 append-only 而把增量计算降到 O(ΔL)，相对 DCNv2+DIN 在 TFLOPs 从 0.06 升到 8.62、MFU 从 13.4% 升到 30.8% 的同时 **p99 推理延迟 13.6→13.2 ms、推理显存 1.8→0.8 GB**（[arXiv 2510.26104](https://arxiv.org/abs/2510.26104)）【生产+数据】；学术侧 MTServe 用 host RAM 虚拟化 GPU 显存达 3.1× 加速、命中率 >98.5%，HELM 指出 embedding 热缓存与 KV cache 争抢 HBM 且最优分配比随负载漂移最多 0.35（[arXiv 2604.22881](https://arxiv.org/abs/2604.22881)、[arXiv 2605.04450](https://arxiv.org/abs/2605.04450)）【仅研究】。跨阶段复用由 Pinterest UniPinRec 给出数字：跨阶段 KV cache 共享使**端到端服务延迟 −11.1%、QPS +63.6%**（[arXiv 2606.00422](https://arxiv.org/abs/2606.00422)）【生产+数据，仅摘要】。异步/近线复用引入陈旧性但换来最大的算力预算：Meta LLaTTE 的上游用户模型由高价值事件触发、在**专用 H100 集群**上推理并写入 feature store，上游序列算力是在线 ranker 的 **45×** 而 **P99 排序延迟无可测变化**，Facebook Feed/Reels 转化 **+4.3%**（[arXiv 2601.20083](https://arxiv.org/abs/2601.20083)）【生产+数据】；腾讯 KuaFu 把每物品缓存从 10 KB 压到 0.5 KB，每 GPU 吞吐 +37%–350%、**节省 190 张 GPU**，在腾讯广告平台运行十个月（[arXiv 2609.31045](https://arxiv.org/abs/2609.31045)）【生产+数据，仅摘要】。

一致性与新鲜度的取舍已被显式工程化。Meta Memory Layer 揭示了缓存最隐蔽的代价：服务时缓存而训练环外的表示会造成训练-服务偏差，把缓存改成与模型共训的 in-model KV embedding 缓存后**新鲜度从 O(5 min) 提到 O(20 s)、训练-服务 NE gap 缩小最多 86%**，同时训练+发布算力 −30%、服务算力持平（[arXiv 2607.25110](https://arxiv.org/abs/2607.25110)）【生产+数据，仅摘要】。权重更新与 KV 的一致性则有现成协议可抄：NVIDIA SID-GR 的热更新要求 `pause_generation → flush_cache → update_weights → continue_generation`，"确保没有用旧权重计算的 KV cache 在换权后存活"（[weight_hot_update.md](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/docs/weight_hot_update.md)）。公开的新鲜度锚点谱系是：Memory Layer 20 秒、GR4AD 结果缓存 1 分钟与 SID 索引秒级、HyperCast 分钟级权重发布与 30 分钟数据到 trainer、TokenMinds 24 小时、KuaFu 周级。

**与 LLM 引擎的不适配集中在三处，且有明确的量化证据**。生成式推荐的负载被 NVIDIA 与 GR4AD 一致定义为"**长上下文（1k–5k token）+ 短解码（3–5 步）+ 大 beam（128–1024）+ 每请求所有 beam 共享同一上下文**"，与聊天 LLM 相反。第一处不适配是 beam 路径：vLLM 没有稳定的生产 beam search 服务路径（beam search 已移出核心），TensorRT-LLM 在该路径不原生暴露 logprobs 且大 beam 内存压力大，SGLang 直到 **2026-08-26 才把 `beam_width` 合入主干**且 KV 压力下整组请求以 HTTP 500 中止；社区在单张 L20 上的基准显示 beam 400 时 QPS 为 SGLang(PR) 4.27、TensorRT-LLM 3.50、**vLLM 0.06**（[SID-GR README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)、[SGLang PR 15645](https://github.com/sgl-project/sglang/pull/15645)、[SGLang PR 31626](https://github.com/sgl-project/sglang/pull/31626)）。第二处是 KV 的组织方式：推荐侧"各用户序列差异大、几乎没有公共前缀，所以按用户 ID 查找而非比较 token 值"，这决定了需要 affinity routing 与按用户热度的分层淘汰，而 LLM 的 paged KV 会把 beam 展开成 B×beam 个独立序列（[recsys_kvcache_manager README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/recsys_kvcache_manager/README.md)）。第三处是内核：NVIDIA 的 `gr_decode_atten` 把 KV 拆成"Context KV（全 beam 共享、稠密顺序、数千 token，走 Tensor Core）"与"Beam KV（每 beam 独立、topK gather 不规则，退化到 CUDA Core FMA）"，因为"单个 kernel 无法高效处理两者"（[gr_decode_atten README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/gr_decode_atten/README.md)）。

专用引擎的收益因此有明确来源。NVIDIA SID-GR 在 H100 上离线比 SGLang 的 beam 分支快 **1.90–2.27×**，在线吞吐 **1.85×**、中位延迟 **−46%**，而拆解显示差距几乎全在两处：**decode attention kernel 从 35.24 ms 降到 1.59 ms**（SGLang 把 4×256=1024 个 beam 当独立 paged decode 行），以及 **CPU 运行时间隙从 28.3 ms 降到 2.2 ms**；topK 排序差距很小（4.0 vs 4.7 ms）。该引擎仍是单机 alpha、仅验证 Qwen 族 BF16（[SID-GR README](https://github.com/NVIDIA/recsys-examples/blob/main/examples/sid-gr-inference/README.md)）【技报/规模未知】。Meta GRACE 在 GH200 上相对 FlashAttention-2/3 较快者 **cross-attention 68×、self-attention 23.4–25.8×、decoder 整体延迟 11.1×**（[arXiv 2608.00938](https://arxiv.org/abs/2608.00938)）【技报/规模未知】。快手 GR4AD 的工程组合给出每项的 ΔQPS：**beam-shared KV caching +212.5%、TopK Pre-Cut +184.8%、低精度 +50.3%、结果缓存 +27.8%**，加上 LazyAR（前 6 层跨 beam 共享）近 2× QPS，以及动态 beam——基线 [512,512,512] 改成递增 [128,256,512] 时**收入 −0.15% 而 QPS +45%**，因为"首层预测最可靠、后层需要更宽 beam"（[arXiv 2602.22732](https://arxiv.org/abs/2602.22732)）【生产+数据】。降低解码成本的另一条路是减少步数：快手单层大语义码本把自回归解码 FLOPs 降 **47.9–48.7%**、单卡 QPS +28.6–47.0%（[arXiv 2608.21012](https://arxiv.org/abs/2608.21012)）；TikTok X-Rec 放弃 SID 自回归改走连续空间 flow matching，吞吐为 SID-AR 的 **3.46×**（[arXiv 2609.29180](https://arxiv.org/abs/2609.29180)）【生产+数据，仅摘要】。

FP8 在生成式推荐上"比传统推荐模型更容易"：OneRec-V2 的量化推理把平均延迟从 139 ms 降到 **70 ms（−49%）**、吞吐 205→394（**+92%**），其中低精度贡献 +42%，论文论点是生成式模型的权重/激活统计"比传统推荐模型更受控、接近 LLM"（[arXiv 2603.11486](https://arxiv.org/abs/2603.11486)）【生产+数据，仅摘要】；反面是 Meta LoKA 指出传统推荐模型"数值敏感、由小 GEMM + 归一化主导、通信密集，直接用 FP8 会掉质量并拖慢训练"，需要逐层探针定位安全位点（[arXiv 2605.10886](https://arxiv.org/abs/2605.10886)）【技报/规模未知】。最后一个必须记住的缺口：**没有找到 2025–2026 年任何一家公司公开 CPU 与 GPU 推理在同一模型上的绝对成本（$/千次请求）**，SilverTorch 的"比 CPU 方案成本效率高 13.35×"与 Pinterest 的"100×"口径不明（[arXiv 2511.14881](https://arxiv.org/abs/2511.14881)）。

## 推荐基础模型：ROI 等于迁移率乘以下游模型数

工业界说的"推荐基础模型"实际是四种不同的东西，其中证据最充分、规模最大的是**上游用户/序列基础模型 + 下游蒸馏或表征注入**。Meta 的演进线最完整：SUM（为数百个广告排序模型合成用户 embedding）→ ExFM（FM 0.8T–3.2T 参数、训练 FLOPs 为 VM 的 30–1800 倍、FM 与 VM 均用 **>3000 亿条流式样本**训练，通过外部蒸馏 1-to-N 服务多个垂直模型）→ HyperCast（target-aware embedding 注入，**迁移率 0.64–1.0**，expert 只需单阶段模型 20–40% 的计算，每日服务数百亿请求且延迟与 CPU 中性）→ LLaTTE → Lattice（**营收顶线 +10%、用户满意度 +11.5%、转化 +6%、容量节省 20%**）（[arXiv 2311.09544](https://arxiv.org/abs/2311.09544)、[arXiv 2502.17494](https://arxiv.org/abs/2502.17494)、[arXiv 2508.02929](https://arxiv.org/abs/2508.02929)、[arXiv 2512.09200](https://arxiv.org/abs/2512.09200)）【均为生产+数据】。另外三种形态是端到端生成式基础模型（快手 OneRec 系）、以开源/自研 LLM 初始化的推荐基座（YouTube PLUM、OpenOneRec、阿里 URM/RecGPT）、以及平台级统一模型（小红书 OneModel、美团 MTFM、Meta Lattice/WHALE）。四者边界并不严格，Meta 内部也不是"一个 FM"而是**分层 FM 家族 + 统一数据/特征/服务平台**。

**最有决策价值的公开资产是一张迁移率表**。字节 Rec-Distill 定义 η =（学生蒸馏后 − 学生原始）/（教师 − 学生原始），给出三场景数字：广告 **64%**（参数比 1:7）、多场景推荐 **45%**（1:34）、直播跨阶段 **50%**（1:5）；教师固定 7B 时学生从 1B 缩到 376M/184M，η 从 **73% 降到 65%/48%**；24B 教师对 1B 学生 η 为 65%。线上效果为电商广告 ADVV +1.00%、GMV +0.62%，多场景推荐 StayDuration +0.1423%，直播礼物收入/U +0.78%，已部署于抖音与 TikTok（[arXiv 2605.29755](https://arxiv.org/abs/2605.29755)）【生产+数据】。表征注入的迁移率系统性高于 logits 蒸馏：HyperCast 0.64–1.0、LLaTTE 约 50% 且带来 +4.3% 转化、LoopFM 在 KD 之上把迁移率约翻倍并三次上线转化 +0.5%/+1.03%/+1.22%（[arXiv 2605.29280](https://arxiv.org/abs/2605.29280)，仅摘要）。原因是传递带宽更高，代价是下游与 FM 版本耦合——需要多版本 embedding 服务、正交变换或去噪，即**把一致性问题从训练侧搬到服务侧**。微调接入（Pinterest PinFM，20B+ 参数、2 年用户行为、最大序列 16,000）做到成本中性并带来 Sitewide Saves +1.20%/+0.72%，关键细节是预训练模块学习率设为排序模型的约 1/10 以免覆盖预训练知识（[arXiv 2507.12704](https://arxiv.org/abs/2507.12704)）【生产+数据】。

由此可以写出一条可操作的判据：**FM 的 ROI ≈ 下游模型数 N × 单模型迁移增益 − FM 训练与日志/缓存成本**。ExFM 的 3.2T FM 对召回、早期排序、后期排序三类 VM 分别带来 **0.11%–0.25% 的额外 NE 增益**（该体系中 0.02% NE 即显著），"越早的阶段增益越大"；Meta（数百个 VM）、字节（广告/推荐/直播多学生）、Pinterest（两大面）都满足这条判据，而**下游模型数少于十个的单场景团队，公开数据不支持建设万亿级 FM**。成本侧的共同做法是把 FM 挪出请求路径：ExFM 在训练数据管道里利用标签等待窗（CTR 反馈 5–90 分钟、CVR 反馈 1 天）做秒级预算的大模型推理且"只覆盖训练数据中极小比例的已排序广告"；HyperCast 的离线 logging 层主机数只需在线 FM 层的 **1/3**；Lattice 的 teacher:student GPU 约 **1:100**。换句话说，"**在线成本中性 + 离线算力集中**"是 ROI 成立的前提，一旦教师 embedding 进入在线请求路径，分摊比例就会退化。

**训练配方高度趋同，但"是否用 LLM 权重初始化"只有一例正面证据**。数据是跨面聚合的终身行为序列（PinFM 2 年、ULTRA-HSTU 16k、Rec-Distill 20K、VISTA 最高 100 万事件）加多模态/语义特征，样本量在 10^11 级；LLaTTE 的结论尤其重要——"**数据丰富化（如语义内容 embedding）不是加性的，而是更陡 scaling 曲线的前提**，让 scaling 超越稀疏 ID 信号的上限"（[arXiv 2601.20083](https://arxiv.org/abs/2601.20083)）。规模分两类：Meta 系 FM 的参数大头是万亿级稀疏 embedding，而国内（Rec-Distill 24B dense、阿里 LUM 7B）与 Pinterest（20B）公开的是 dense 规模，**两条路线的"大"不是一回事，比较参数量没有意义，应比较训练 FLOPs**（ExFM 用 1X = 60M FLOPs 的相对尺度正是为此）。LLM 初始化方面，YouTube PLUM 从 Gemini-1.5 MoE 热启动，并给出 2×2 消融证明**预训练初始化在有无领域持续预训练（CPT）的条件下都优于随机初始化**，CPT 还能被多个下游任务共享从而摊薄，生产配置为 900M 激活/约 4.2B 总参，线上 Engaged Users LFV +0.07%、Shorts +0.28%（[arXiv 2510.07784](https://arxiv.org/abs/2510.07784)）【生产+数据】。采用而未公开消融的有 OpenOneRec（Qwen3）、URM（Qwen-7B）、GLIDE；明确谨慎的有快手 LEARN（"Rec-to-LLM 在工业中无法产生实际收益"）与 LARM（"直接注入 LLM embedding 收益微弱"），而 Meta 系（HSTU/LLaTTE/ExFM/PinFM）**不用 LLM 权重初始化，只用 LLM 生成的多模态/语义特征**（[arXiv 2405.03988](https://arxiv.org/abs/2405.03988)）。

**更新频率决定架构，而更新滞后比延迟更隐蔽**。分钟级路线（HyperCast 只发布最近更新的约 30% 权重、ExFM 定期发布快照、Rec-Distill 流式蒸馏）要求 FM 本身流式训练加新鲜度补偿；天/月级路线（Netflix，仅二手转述，**未核实**）必须解决 embedding 空间跨版本一致性。补偿机制已有公开样本：ExFM 的 Student Adapter 吸收新鲜度差距（流式 NE +0.08% 且随时间扩大）、Auxiliary Head 处理跨域偏差（相对无 AH 的 NE 变化 −4%）；Rec-Distill 的"解耦塔"被作者明确定义为**容错机制**——"即使教师更新延迟、蒸馏流水线滞后或教师信号暂时不稳定，主任务塔的性能与在线服务不受影响"，且单塔仅蒸馏损失只 +0.03% AUC 而解耦塔 +0.44%。同一篇还给出滞后代价的量化：**无流式蒸馏时学生增益 5 天后减半**（+0.10%→+0.05%），而只做流式、不做批量初始化的对照组 5 个月后仍持续落后。

组织模式在公开论文里高度一致：**一个中心团队维护少数 FM，场景团队维护多个轻量模型并按各自节奏迭代**，二者通过三类平台接口解耦——带版本的 embedding/特征存储、蒸馏信号管道、以及多租户共享训练数据集。HyperCast 把"开发速度"直接写成贡献："通过解耦 FM 与 expert 的训练，我们可以用大量 GPU 资源精炼单一 FM，同时不牺牲 expert 模型的快速迭代"。与 LLM 团队的关系是"用 LLM 团队的原料"：PLUM 用 Gemini、OpenOneRec 用 Qwen3 与 Qwen3-Embedding-8B 做 item 嵌入、HyperCast 输入含"LLM 驱动的多模态表征"——**而不是让 LLM 团队直接做推荐模型**。失败信号同样值得记录：LinkedIn 360Brew（150B、prompt 式零样本）的论文已由作者撤回，而 Feed 团队在 2026-02 发表 Feed-SR 时公开承认"LLM 排序架构未在线上指标与生产效率间取得最佳平衡"，选择了非 LLM 的 transformer 序列排序器（[arXiv 2501.16450](https://arxiv.org/abs/2501.16450) 撤回状态、[arXiv 2602.12354](https://arxiv.org/abs/2602.12354)，均为二手/摘要，**未核实**）。

对字节系的专门观察：截至 2026-10，公开材料中**没有以 foundation model 命名的公司级推荐基座**，最接近的是 Rec-Distill——按场景各自放大的离线教师（最大 24B dense + 20K 序列，TokenMixer-Large + LONGER 架构）通过解耦的批+流黑盒蒸馏喂给在线学生。与 Meta 相反，字节的公开路线是"在线模型 scaling 优先、教师蒸馏其次"（先把在线模型做到 7B 且 MFU 60% 仍满足延迟，再用 24B 教师突破在线上限）。公开资料中字节也尚未出现 LLaTTE/TokenMinds 式的"异步用户表征服务"，这是 Meta/Google/Yandex/腾讯已公开而字节未公开的一环。

## 通用基座：能力前沿在中国厂商，可落地档位是 30B-A3B 与 8B dense

开放权重前沿由中国厂商主导，参数规模已到 1.6T–2.8T 总参/50B–100B 激活，上下文普遍 256K–1M。DeepSeek-V4 预览版给出两档（Pro 1.6T/49B、Flash 284B/13B，均支持 1M 上下文、预训练 >32T token），架构升级为压缩稀疏注意力 CSA + 重压缩注意力 HCA 混合、mHC 替代残差、Muon 优化器，**1M 上下文下 V4-Pro 单 token 推理 FLOPs 仅为 V3.2 的 27%、KV cache 仅 10%**（[arXiv 2606.19348](https://arxiv.org/abs/2606.19348)）；Kimi K3 为 2.8T/104B、93 层（69 KDA + 24 Gated MLA）、1M 上下文、MXFP4 权重 QAT（[Kimi-K3 README](https://github.com/MoonshotAI/Kimi-K3)）；GLM-5 从 355B/32B 扩到 744B/40B、集成 DSA 降低部署成本，transformers 文档称其"完全在华为昇腾芯片上训练"（[GLM-5 README](https://github.com/zai-org/GLM-5)、[transformers glm_moe_dsa](https://github.com/huggingface/transformers/blob/main/docs/source/en/model_doc/glm_moe_dsa.md)）。美系开放权重供给收缩：gpt-oss（2025-08，Apache 2.0）之后无续作，Llama 4 之后的旗舰据多家媒体报道改为闭源（**未核实**），Google 反而把 Gemma 4 改为 Apache 2.0（二手，**未核实**）并在 Vertex 上以 **$0.15/$0.60 每百万 token** 定价（[Vertex AI 定价页](https://cloud.google.com/vertex-ai/generative-ai/pricing)，官方）。

**对推荐团队，真正可落地的档位是"30B-A3B 级 MoE + 8B 以下 dense"**，理由有三：这一档在 2026 年都有原生多模态版本（Qwen3.5/3.6-35B-A3B、Qwen3-VL-30B-A3B、Keye-VL-2.0-30B-A3B、Nemotron 3 Nano Omni、Gemma 4 26B-A4B），单机 1–4 卡可部署（Qwen3-Next-80B-A3B 在 4×H200/H20 或 4×A100 验证，GLM-4.7-Flash 30B-A3B 单卡 H100 BF16 可跑），且 Apache/MIT 许可对大 MAU 产品没有额外条款。**许可证是必须前置评估的工程约束**：Llama 4 Community License 第 2 条规定版本发布日月活超过 **7 亿**的产品需向 Meta 申请许可且 Meta 可自行决定是否授予（[Llama 4 LICENSE](https://github.com/meta-llama/llama-models/blob/main/models/llama4/LICENSE)）；Kimi K2/K3 与 MiniMax 的 Modified MIT 要求月活超 1 亿或月收入超 2000 万美元的商业产品显著署名（[Kimi-K2 LICENSE](https://github.com/MoonshotAI/Kimi-K2/blob/main/LICENSE)）；腾讯 Hunyuan-A13B 的社区许可**排除欧盟、英国、韩国**，且其"Model Derivatives"定义明确包含通过蒸馏、中间表示或合成数据训练出的模型（[Hunyuan-A13B LICENSE](https://github.com/Tencent-Hunyuan/Hunyuan-A13B/blob/main/LICENSE)）——这一条对"用开源模型做离线打标再训自家模型"的常见用法有直接影响。

架构趋势对推理成本的影响可概括为三条并行路线：稀疏注意力（DSA→CSA/HCA、IndexShare、QSA、MSA）、线性/混合注意力（Gated DeltaNet/KDA/Mamba）、滑窗-全局交错（Gemma 3/4、MiMo-V2、gpt-oss），三者都把长上下文成本从二次压到接近线性，并在 2026 下半年开始融合。可引用的幅度：Kimi Linear 的 KDA:MLA 3:1 混合使 **KV cache 最多减少 75%、1M 上下文解码吞吐最高 6×**（TPOT 1.84 ms vs 11.48 ms）（[Kimi-Linear](https://github.com/MoonshotAI/Kimi-Linear)）；MiniMax MSA 在 1M 上下文下每 token 注意力计算减少 28.4×，H800 实测 prefill 14.2×/decode 7.6×（[arXiv 2606.13392](https://arxiv.org/abs/2606.13392)）；Qwen3-Next 以 1:50 激活比做到"优于 Qwen3-32B 而训练成本不到其 1/10、>32K 上下文推理吞吐高 10 倍以上"（[transformers qwen3_next](https://github.com/huggingface/transformers/blob/main/docs/source/en/model_doc/qwen3_next.md)，厂商自述）。代价是框架复杂度：每个新架构都要新的 KV 布局与内核（vLLM 为 DeepSeek V4 定制了三种块大小），而 Qwen3.5 的 GDN 层状态为 **4,216 KiB/请求**（对比全注意力 2 KiB/token），迫使 vLLM 的块大小取 2,112 token（[Qwen3.8 PD 服务](https://vllm.ai/blog/2026-09-21-qwen38-pd-serving)）。另有一条对推荐特别相关的新稀疏轴：DeepSeek Engram 用 O(1) 查表的"条件记忆"作为 MoE 之外的第二稀疏轴，27B 规模下在同参数同 FLOPs 的 MoE 基线上全面提升（MMLU +3.4、BBH +5.0、HumanEval +3.0），且**嵌入表可放主存并预取**——这与推荐 embedding 的分层存储是同一工程形态（[Engram](https://github.com/deepseek-ai/Engram)、[arXiv 2601.07372](https://arxiv.org/abs/2601.07372)）。

**领域适配的可行路径有明确的公开模板**。OpenOneRec 给出了端到端流水线：Qwen3 词表扩展 3 层 × 8192 个 itemic token（对齐到 256 的倍数）→ 阶段一冻结 LLM 只训 itemic embedding 做 item-text 对齐 → 阶段二全参数"推荐数据 + 通用文本"共预训练 → 多任务 SFT → **以 Qwen3 为教师的 on-policy 蒸馏（token 级反向 KL，处理师生词表不一致）以恢复通用推理能力** → GRPO 强化学习；tokenizer 为残差 K-Means（3 层 × 8192），要求新数据集用 Qwen3-Embedding-8B 做 item 嵌入（[OpenOneRec pretrain/README](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/pretrain/README.md)、[tokenizer/README](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/tokenizer/README.md)）【开源基座，仅研究/基准】。PLUM 的 CPT 语料配方是"领域 item 数据 + 用户序列 + 通用文本"，目的是"把新 SID 模态与模型既有知识对齐"。两者共同的工程含义是：**领域适配的难点不在微调，而在 SID 词表治理与"保住通用能力"**，而后者需要一个蒸馏教师。价格信号则决定了"自部署还是买 API"：开放权重模型的 API 边际价格已到每百万输出 token 零点几美元量级（LongCat-Flash 自述 **$0.70/百万输出 token**，[LongCat-Flash README](https://github.com/meituan-longcat/LongCat-Flash-Chat)；DeepSeek V4-Flash 二手报价 $0.14/$0.28，**未核实**），比 Gemini 3.x Flash/Pro 低 1–2 个数量级；对每天数亿级内容打标，自部署 3B–15B 激活的 MoE 与按 token 买 Flash 级 API 的成本差距仍是 10 倍量级（基于上述价格的推断）。

## 后训练与 RL：异步化已成熟，推荐 RL 只能借架构不能借代码

生产级 RL 后训练的主流形态是"单控制器 + 多控制器"的 HybridFlow 式数据流，rollout 引擎（vLLM/SGLang）与训练引擎（Megatron/FSDP）分时共置；2025 下半年起所有框架都补上了"一步异步 → 全异步"的谱系，并把"异步程度"做成连续旋钮（staleness 阈值/版本数/队列长度）而非非此即彼。可引用的收益：verl 的 one-step-off 在 Qwen2.5-Math-7B / 2×16 H20 上使端到端从 19h18m 降到 15h34m（**+23%**，FSDP2）或 18h21m→13h06m（**+40%**，Megatron），其 fully async 在 Qwen2.5-7B、128 GPU 上报告 **2.35–2.67×**；AReaL 的全异步 + Decoupled PPO 在同等 GPU 数下最高 **2.77×**（[verl one_step_off](https://github.com/verl-project/verl/blob/main/docs/advance/one_step_off.md)、[verl fully_async](https://github.com/verl-project/verl/blob/main/docs/advance/fully_async.md)、[AReaL 论文](https://github.com/inclusionAI/AReaL/blob/main/assets/paper.pdf)）。verl 文档给出的适用边界很实用："one-step-off 适合要 20%–40% 提升又要接近 on-policy 的场景；**fully async 对 128+ GPU 或长 CoT 场景是必需的**"（[verl v0.7 博客](https://github.com/verl-project/verl/blob/main/docs/blog/v0.7.md)）。NeMo RL 提供唯一跨模型的系统化公开性能表（DeepSeek-V3 在 512 张 DGX-H100 上同步 on-policy 每步 81.2 s、1-step off 46.6 s）（[NeMo RL 性能摘要](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/about/performance-summary.md)）。

**权重同步在 2026 年出现清晰的三层，这是最可直接迁移到推荐在线学习的一块**。节点内 NCCL/IPC 在小模型上是亚秒级；全量广播型 checkpoint engine 在 1T 级做到 **<30 秒**（Kimi K2 自述；开源 checkpoint-engine 在 256×H20 上更新 Kimi-K2-Instruct FP8 为 16.04 s）；稀疏 delta 则把 235B MoE 从约 250 秒压到约 12 秒——verl 的实测为 Qwen3-235B-A22B **11.4–14.9 s vs NCCL 全量 246–266 s（≈21×）**，其前提是"RL 更新高度稀疏，典型学习率下 >99% 的 BF16 权重字节逐步不变"（dense 模型每步变化 1–3% 字节，235B MoE 早期仅 0.02–0.05%）（[Kimi K2 技术报告](https://github.com/MoonshotAI/Kimi-K2/blob/main/tech_report.pdf)、[checkpoint-engine README](https://github.com/MoonshotAI/checkpoint-engine/blob/main/README.md)、[verl delta_weight_sync](https://github.com/verl-project/verl/blob/main/docs/advance/delta_weight_sync.md)）。这条"delta 前提"对高学习率的 SFT/预训练不成立，但与推荐 embedding 的增量同步（DynamicEmb replay、TorchRec delta tracker）本质是同一份"变化行 + 元数据"。

**训推不一致已从算法问题变成系统问题**。MiniMax-M1 的诊断最具教学价值：训练与推理模式对已采样 token 的概率有显著差异，根因是训推 kernel 精度不匹配，逐层分析定位到 LM head 的高幅值激活，**把 LM 输出头改为 FP32 后训推概率相关性从约 0.9x 升到 0.99**（[MiniMax-M1 技术报告](https://github.com/MiniMax-AI/MiniMax-M1/blob/main/MiniMax_M1_tech_report.pdf)）。verl 把精度差异、异步陈旧与 replay buffer 统一视为 off-policy 问题，用重要性采样加拒绝采样修正，并指出常见实现错误是"把训练端 π_old 当成行为策略而忽略真实 π_rollout"；FP8 rollout 在开 token 级 TIS 后与 BF16 精度对齐、不开则明显掉点，而 FP8 rollout 本身带来约 12% 加速（[verl rollout_corr](https://github.com/verl-project/verl/blob/main/docs/algo/rollout_corr.md)、[verl fp8](https://github.com/verl-project/verl/blob/main/docs/low_precision/fp8.md)）。MoE 还有一类额外来源——两个合法 router 实现对同一 token 选不同专家，NeMo RL 用 Router Replay（记录 vLLM rollout 的路由并在 Megatron 前向中回放）消除（[NeMo RL router-replay](https://github.com/NVIDIA-NeMo/RL/blob/main/docs/guides/router-replay.md)）。奖励侧的公开共识是"可验证任务一律用规则奖励"——DeepSeek-R1 明确不用结果/过程神经奖励模型，"因为神经 RM 在大规模 RL 中可能被 reward hacking"，PRM 与 MCTS 被列为不成功的尝试（[DeepSeek-R1 报告](https://github.com/deepseek-ai/DeepSeek-R1/blob/main/DeepSeek_R1.pdf)）；性能瓶颈则从 GPU 转向 CPU/外部服务并发，因此主流框架把 reward 剥离为独立资源池（字节 Sandbox Fusion 使 reward 阶段时间减少 **10–30%**，[verl sandbox_fusion](https://github.com/verl-project/verl/blob/main/docs/examples/sandbox_fusion_example.rst)）。

**推荐系统的 RL 对齐分两条线，结论对起步团队很直接**。工业主链路（快手 OneRec/GR4AD、腾讯 GPR）与 LLM RL 框架几乎没有代码复用：rollout 是 3 个 SID token 的 beam search（beam 512/32）而非数千 token 采样，长尾/partial rollout 问题不存在；奖励来自奖励模型服务、eCPM 塔或真实反馈日志而非验证器/沙箱；训练是实时流式在线学习（OneRec 每 1000 步经消息队列把参数推到外部推理服务；GR4AD 用 Param Sync 推到 Infer Server）。更关键的是 **on-policy 样本受线上流量份额限制**：OneRec v1 只能在 1% 用户上做 rollout，V2 明确指出"因资源约束 on-policy rollout 只能在 1% 用户子集进行、奖励模型易被 reward hacking"，**只有当 OneRec-V2 承接 25% 流量后才有足够的自生成样本做有意义规模的 on-policy RL**；V2 转向真实用户反馈（按时长分桶百分位的 Duration-Aware Reward Shaping，正样本取前 25%、负样本取显式 dislike）与 GBPO，对照实验显示加入自身流量样本后几乎所有指标改善，且奖励模型偏向互动指标而真实反馈偏向时长、两者"不完全可加"（[arXiv 2506.13695](https://arxiv.org/abs/2506.13695)、[arXiv 2508.20900](https://arxiv.org/abs/2508.20900)）【生产+数据】。另一条线是 LLM 化的生成式推荐：OpenOneRec 直接 fork verl 做 GRPO 与 on-policy 蒸馏，自定义 two_stage rollout（阶段一采样 CoT 到 `</think>`，阶段二用 vLLM BeamSearchParams 生成 3 个 SID token，beam 默认 32）与基于真实交互 SID 的规则奖励（[OpenOneRec verl_rl/README](https://github.com/Kuaishou-OneRec/OpenOneRec/blob/main/verl_rl/README.md)）——这证明了 **"LLM 化的生成式推荐可以复用 verl，SID 短序列的实时主链路只能借鉴架构"**。可借鉴的部件是明确的：分离式 rollout 服务加 checkpoint engine（对应 OneRec 的 MQ 参数下发）、Reward Loop 的外部 RM 与流式打分、IS/RS 修正（对应 GPR 用模拟器记录行为策略概率做 off-policy 修正）、以及 GRPO 变体家族（ECPO/GBPO/RSPO/HEPO 本质都是裁剪与基线的改造）。

## 算子与数值层：FP8 是推荐的安全线，FP4 仍是 NVIDIA 自家主场

数值层的结构性事实是**训练与推理对数值的要求不同**。训练关心梯度是否无偏与长 horizon 是否发散，所以 NVFP4 训练必须叠加"随机 Hadamard 变换压离群值 + 随机舍入去偏 + 16×16 二维块量化 + 选择性高精度层"四件套，且完整配方仅 Blackwell 数据中心卡（sm100/10.x）支持（[TransformerEngine recipe](https://github.com/NVIDIA/TransformerEngine/blob/main/transformer_engine/common/recipe/__init__.py)、[TE 支持矩阵](https://github.com/NVIDIA/TransformerEngine/blob/main/docs/support_matrix.rst)）；推理关心单次前向误差与长上下文累加误差，所以 FP8 attention 的真正风险在 contraction 维极大时的累加精度（前述 91%→13% 是最有说服力的公开案例）。还有一个容易忽视的工程约束：MXFP8 的缩放有方向性，**量化张量与其转置在数值上不等价**，框架因此要存 rowwise 与 columnwise 两份，这改变了激活显存的计算方式。Blackwell Ultra 的另一条硬约束是 **B300/GB300 的 BF16 与 FP8 峰值与 B200 相同，只有 FP4 提升约 3×**——"不上 FP4 就吃不到 Ultra 的增量"（[LMSYS MXFP8/NVFP4 RL 博客](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-07-29-mxfp8-nvfp4-rl.md)）。

注意力算子的分水岭是 **Blackwell 的"非对称硬件扩展"**：Tensor Core 吞吐翻倍而 shared memory 带宽与指数单元几乎没变，于是 FlashAttention-4 必须用"软件模拟 exp + 条件 softmax 重缩放 + TMEM + 2-CTA MMA"把瓶颈从非 matmul 操作上挪开，在 B200 BF16 上相对 cuDNN 9.13 最多 **1.3×**、相对 Triton **2.7×**，峰值 **1613 TFLOPs/s（71% 利用率）**，且完全用嵌入 Python 的 CuTe DSL 实现、**编译时间比 C++ 模板快 20–30×**（[arXiv 2603.05451 摘要](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/6-Mar-2026/NLP/README.md)）。一条对推荐最可迁移的设计律来自 DeepSeek 的 DSA："**在 kernel 层面，每个 key-value entry 必须被多个 query 共享才有计算效率**"，因此 DSA 实例化在 MLA 的 MQA 模式下（[DeepSeek-V3.2 技术报告](https://github.com/deepseek-ai/DeepSeek-V3.2-Exp/blob/main/DeepSeek_V3_2.pdf)）。这正好解释了推荐侧 beam decode 必须拆成两个 kernel——Context KV 被所有 beam 共享（可用 Tensor Core），Beam KV 每 beam 独立（退化到 CUDA Core FMA）——也意味着"增大 beam 宽度"的边际成本主要落在后者。

MoE 通信层在 2026 年发生两件结构性变化。其一，通信库从"NVSHMEM + 自动调参"转向"NCCL Gin device API + 解析式 SM/QP 计算"：DeepEP V2 完全重构并**彻底移除 NVSHMEM 依赖**，V2.5 加入冗余专家的 NVLink 权重预取与梯度规约；其硬门槛需记入选型清单——Hopper 或更新、**CUDA ≥13.1、PyTorch ≥2.10、NCCL ≥2.32.3**，且"EP dispatch/combine 需要 GPU SM，不支持零 SM 的纯 RDMA EP"（[DeepEP README](https://github.com/deepseek-ai/DeepEP/blob/main/README.md)）。其二，"分开的 dispatch → grouped GEMM → combine"被融合成单个 megakernel：DeepGEMM 的 Mega MoE 把 EP dispatch、两个 linear、SwiGLU 与 combine 融进一个 kernel 并重叠 NVLink 通信与 Tensor Core 计算，PR 页面报告 **1.50–1.96×**（[DeepGEMM PR #316](https://github.com/deepseek-ai/DeepGEMM/pull/316)，GPU 型号与 legacy 基线未定义，**未核实**）。相对地，负载均衡这条线的低垂果实已被摘完——dispatch-time 均衡的实测增量已降到个位数百分比（Waterfill 总吞吐 **+1.48% 到 +4.66%**、LPLB **+0.84% 到 +7.34%**，[SGLang Waterfill & LPLB](https://github.com/lm-sys/lm-sys.github.io/blob/main/blog/2026-06-26-waterfill-lplb.md)）。优化重心也因此从"把通信藏起来"转向"把通信变小 + 把 SM 还给计算"：字节 FlashComm 让 EP 流量发送打包的 MXFP8 而非 BF16，并用固定 buffer 分块使 EP 峰值显存不随最坏 token 数增长，其端到端数字为 Seed-OSS-36B 在 8×H800 上 **prefill 1.33×、decode 1.32×**（[Triton-distributed README](https://github.com/ByteDance-Seed/Triton-distributed/blob/main/README.md)、[docs/e2e.md](https://github.com/ByteDance-Seed/Triton-distributed/blob/main/docs/e2e.md)）。一个容易踩的坑是 DeepGEMM 把确定性从默认开改为默认关（PR #432），对 RL 与任何需要训推 bitwise 一致的流程，升级后必须显式开启（**未核实，PR 页面经摘要抽取**）。

**DSL 已经分层，选型可以按"要榨干新硬件 / 要跨厂商 / 要快速覆盖新硬件"三分**。最前沿的 kernel 用 **CuTe DSL**（FA4、FlashMLA 融合 kernel、FlashInfer 的 Blackwell kernel、NVIDIA 的 beam-decode kernel 都是），但其 PyPI 页面仍标注 public beta；要跨厂商与被多引擎复用的用 **Triton**（必要时下到 Gluon 拿 TMA/tcgen05/warp specialization），IBM/Red Hat/AMD 的论证是"维护成百上千个特化 kernel 无法规模化"；要快速覆盖新硬件或作为研究参考的用 **TileLang**（已于 2026-09-30 官方支持华为昇腾 950，并被 DeepSeek 指定为 V3.2 kernel 的可读参考）（[nvidia-cutlass-dsl PyPI](https://pypi.org/project/nvidia-cutlass-dsl/)、[vLLM Triton 后端深度解析](https://github.com/vllm-project/vllm-project.github.io/blob/main/_posts/2026-03-04-vllm-triton-backend-deep-dive.md)、[TileLang README](https://github.com/tile-ai/tilelang/blob/main/README.md)）。NVIDIA 的新 tile 语言 cuTile 则**不应进入 2026 年的生产选型**——其 tileiras 编译器 13.2 只支持 Blackwell 与 Ampere/Ada，"Hopper GPU 将在未来版本支持"（[cutile-python README](https://github.com/NVIDIA/cutile-python/blob/main/README.md)）。一条对推荐特别重要的提醒：Triton kernel 的 CPU launch 开销对 decode-only 小批影响尤其大（vLLM 因此在集成线性注意力模型时默认开 full CUDA graph），而推荐模型的 step 时间常在数十毫秒且算子数量远多于 LLM，launch 开销与 GPU 空泡占比会更高。

**LLM 驱动的算子工程已经改变了优化团队的工作方式，但改变的位置是"自动化 profile→改写→验证→判决"这条循环，而不是"写出 SOTA kernel"**。最可信的证据就在推荐负载上：NVIDIA Talos 用编码 agent 在四个推荐模型上无人干预取得 **DIN 61.55→27.67 ms（2.22×）、DIEN 64.36→19.56 ms（3.29×）、HSTU 615.89→194.87 ms（3.16×）、OneRec 613.06→275.78 ms（2.22×）**，全部是关闭 profiler 后的真实中位 step time（[Talos README](https://github.com/NVIDIA/recsys-examples/blob/main/corelib/talos/README.md)）【技报，示例负载】。真正值得抄的是它的防护栏：三个角色（主循环 agent 只做 profile 与派发、从不改代码；Optimizer 每轮全新 subagent 只处理一个热点；**Judge 每轮全新 subagent，看得到证据但看不到 Optimizer 的推理过程**）只通过文件通信；每个被改模块在 flag 后保留两条代码路径以便在真实 batch 上对跑；三道闸门是前向输出与梯度一致、优化器状态一致、step time 真的改善，任一失败即回退。官方特意强调"**大约三分之一的优化循环被判决器丢弃，而这正是重点**"。对照之下，学术 benchmark 的数字必须打折——KernelBench 官方文档自己警告"**如果模型能 reward hack，它就会找到办法 reward hack**"，并建议自己生成基线时间（[KernelBench EVAL.md](https://github.com/ScalingIntelligence/KernelBench/blob/main/EVAL.md)）。

## 硬件与算力经济学：换代收益 = 低精度 × 显存 × 互连拓扑

NVIDIA 官方给出的 dense 峰值表是一切折算的基础：**BF16 为 GB300/GB200 2450、B300/B200 2250、H100 989；FP8 为 4900/4500/1979；NVFP4 为 14700/9800/13500/9000，H100 不支持**（[exemplar-performance README](https://github.com/NVIDIA/dgxc-benchmarking/blob/main/README.md)）。把它与实测对照会得到本报告最重要的一条经济学判断：**换代收益是"低精度 × 显存 × 互连拓扑"的乘积，只迁移算子而不改并行与精度策略拿不到标称收益**。证据是 H100→B200 的 dense FP8 峰值只有 2.27×，但 TRT-LLM 官方吞吐表上 DeepSeek-R1 的 GB200/H200 比值为 4.3×、GPT-OSS-120B 的 B200/H100 为 5.8×；超出峰值比的部分来自 NVFP4、HBM 容量/带宽带来的更大 batch，以及 NVL72 域内 EP 免去 RDMA（[TensorRT-LLM perf-overview](https://github.com/NVIDIA/TensorRT-LLM/blob/main/docs/source/developer-guide/perf-overview.md)）。GB300 相对 GB200 是同代小步（1.5× FP4 峰值 + 1.5× HBM + SFU 提速），实测在长上下文 decode 为 +38–45%、训练 405B 为 +31%、MLPerf 推理 per-GPU +27–33%，迁移成本接近零但不值得单独重做软件栈。MLPerf Inference v6.0 的绝对值可作为天花板参照：**GB300 NVL72（72 GPU）DeepSeek-R1 Offline 647,076 tok/s（≈8,987/GPU）**，四机架 288 卡 Offline 约 249 万 tok/s（[inference_results_v6.0](https://github.com/mlcommons/inference_results_v6.0/blob/main/closed/NVIDIA/results/out.csv)）。媒体解读称同硬件 6 个月内 per-GPU 吞吐提升 **2.77×** 且 NVIDIA 把增益归于软件（kernel 融合、attention DP、分离式服务、Wide-EP、MTP、KV 路由）（**未核实**）——这意味着 Hopper→Blackwell 的"软件追赶"风险窗口在 2026 H2 已基本关闭。

**单位成本的可量化红利几乎全在低精度**。按公开吞吐与租价折算（笔记中的推算，非厂商数据）：DeepSeek-R1 FP4 在 B200 上 6,463 tok/s/GPU，按 $3.70–5.29/h 为 **$0.16–0.23/百万输出 token**；同模型 FP8 在 H200 上 1,627 tok/s/GPU，按 Hopper 级 $1.8–3.5/h 为 **$0.31–0.60/百万**；GPT-OSS-120B 在 B200 上 25,943 tok/s → **$0.040–0.057/百万**。换算到每 PFLOPS·小时的租金则是 H100 FP8 约 **$1.26**、B200 FP8 约 **$1.00**（仅约 20% 改善）、B200 NVFP4 约 **$0.50**（2.5× 改善）——即 **BF16 训练的每 FLOP 成本 2024→2026 下降有限**，租价与 capex 数字均为 C 级、**未核实**（[GPU 定价综述](https://intuitionlabs.ai/articles/data-center-gpu-pricing-2026)）。更结构性的约束来自内存：1Q26 常规 DRAM 合约价环比上涨 **93–98%**，HBM4 已由三星 2026 年初量产，2027 年 HBM 合约价预计再涨（**全部未核实**，[HBM/DRAM 综述](https://intuitionlabs.ai/articles/hbm-dram-ai-memory-demand)）。叠加每芯片容量 1.5× 的趋势，新一代 GPU 的 BOM 中内存占比继续上升、单卡价格难降，"每 FLOP 成本下降"将主要体现在低精度口径与整机吞吐上。资本开支侧，美国四巨头 2026 年指引合计约 **7,250 亿美元（+77%）**，字节 2026 年 AI 基础设施初步计划约 **1,600 亿元**（其中过半买芯片）（均为 C 级、**未核实**）。

**非 NVIDIA 路线对推荐负载的意义需要单独评估，因为推荐的瓶颈不是峰值 FLOPS**。目前**只有 TPU 有官方的 embedding 加速单元与官方 DLRM 数据**：第三代 SparseCore 使 embedding 密集模型 2×、**DLRM DCNv2 5×**，Ironwood（TPU v7）每芯片 192 GiB HBM3E / 7.4 TB/s、superpod 9,216 芯片，SparseCore 继续负责"可扩展 embedding 查找"，TPU 8t/8i 在 2026-04 公布且 8i 以 3× 片上 SRAM 容纳更大 KV cache（[Trillium GA 博客](https://cloud.google.com/blog/products/compute/trillium-tpu-is-ga)、[Ironwood 深度解析](https://cloud.google.com/blog/products/compute/inside-the-ironwood-tpu-codesigned-ai-stack)、[Google Cloud Next '26](https://cloud.google.com/blog/topics/google-cloud-next/welcome-to-google-cloud-next26)）。NVIDIA 侧没有专用单元，靠 Grace 大内存 + GPU 哈希表 + HSTU 专用核（B200 上 KV 命中时 HSTU block 3.3–7.7×）补偿；MLPerf Inference v6.0 新增的 dlrm-v3 基准给出 **GB200 NVL72 每 GPU 约 1,453 samples/s（Offline）vs DGX B200 约 1,318**，即推荐负载的代际增益远小于 LLM。AMD 的 MI355X 已成熟可用（MLPerf v6.0 有 8 卡与 94 卡提交），但 2026 H2 供货主要被 OpenAI 与 Meta 两份 6 GW 合同吃掉（**未核实**）；Trainium3 规格翻倍（MXFP8 2,517 TFLOPS、144 GiB、4.9 TB/s）但 **embedding/稀疏访问能力无任何公开资料**（[trainium3.rst](https://github.com/aws-neuron/aws-neuron-sdk/blob/master/about-neuron/arch/neuron-hardware/trainium3.rst)）。一个有用的比值分析：按"内存带宽 ÷ dense FP8 算力"，GB300、Ironwood、MI355X 都在 1.6×10⁻³ B/FLOP 量级，Trainium3 约 1.9×10⁻³，而昇腾 950DT 约 **4.4×10⁻³**——即昇腾是"带宽相对富裕、算力偏弱"的芯片，更适合 decode 与 embedding 查表而非大 GEMM 训练，这与华为把 950PR 定位为"prefill 与推荐导向"一致（规格来自第三方折算，**未核实**）。

**国内约束是未来 12 个月最硬的变量**。H20 在 2025-04 被禁、RTX Pro 6000D 被中方禁购、B30A 未获放行；H200 自 2025-12/2026-01 起进入"逐案审批 + 对华数量不超过美国国内销量 50% + 第三方实验室检测"的框架，但 2026-07 的报道显示中方仍在压量审批、无确认交付（全部 C 级、**未核实**）。因此国内算力规划的现实基线是 **H20/H800/H200 存量加少量增量 + 昇腾/寒武纪**。对应的工程优先级也随之确定：H20 的策略是"用 4 TB/s 带宽与 96 GB 容量换算力"，decode 偏 memory-bound 时与 H800 差距缩小（蚂蚁每节点 5.7k 输出 tok/s vs DeepSeek 生产 14.8k），prefill 则显著吃亏，所以应走大 batch + FP8 KV + MTP 低并发增益、把 prefill 与 decode 分到不同机型、沿用 DeepSeek 的 EP32/EP144 + EPLB + 双微批模板，并**把 NVFP4 相关代码路径做成可替换层**，因为 H20 与国产卡都没有 FP4。昇腾侧的可用性已有一手证据：vllm-ascend 官方支持 Atlas 800I/T A2 与 A3 系列，MindSpeed-LLM 给出 DeepSeek-V3 671B 在 Atlas 900 A3 SuperPoD（512 NPU）上的官方预训练吞吐，DeepSeek 自己在 2026-09-30 开源了昇腾 950 的 FlashMLA 稀疏注意力 kernel（**prefill 410 TFLOPS = 硬件理论峰值 95%、decode 360 = 83%**）与同 API 的 DeepEP-Ascend（[vllm-ascend](https://github.com/vllm-project/vllm-ascend)、[MindSpeed-LLM 特性页](https://github.com/Ascend/MindSpeed-LLM/blob/master/docs/zh/pytorch/features/README.md)、[FlashMLA README](https://github.com/deepseek-ai/FlashMLA/blob/main/README.md)）。最后一条规划提醒：CXL 在 2026 年的 LLM/推荐开源栈中**没有任何公开落地证据**，12 个月内不应作为规划依赖；推荐 embedding 在 NVL72 上的最佳公开实践仍是"GPU HBM 热表 + Grace LPDDR5X（546 GB/s）温表 + 主机/远端冷表"的三层哈希表。

## 收敛与不收敛：边界正好是"模型里有没有 ID"

把两条栈逐层对照，收敛点非常清楚地落在 dense 侧。推荐训练已经在复用 LLM 栈的全部基础设施：NVIDIA 的 HSTU 示例是"TorchRec 做 embedding 分片 + Megatron-Core 做 dense 并行（DP/TP/SP/PP/CP）"；阿里 SORT 是"RecIS + Megablocks"并明确"应用 LLM 的通用优化：半精度、KV cache、多上下文多流执行"；快手 OneRec 用 ZeRO-1 加编译优化，并采用 DeepSeek 式的无辅助损失 MoE 负载均衡；Meta Lattice/GEM 用 FSDP 与 NCCLX；WHALE 与 SORT 都选 torch.compile/AOTInductor；ULTRA-HSTU 的 attention kernel 基于 FlashAttention V3 的思路；连 LLM 时代的编码 agent 也被 NVIDIA Talos 直接用于推荐 kernel 优化。推理侧的共享更彻底：前缀/会话 KV 复用、KV 感知路由、FP8 KV、CUDA graph 批粒度、prefill-only 路径（LinkedIn 在 SGLang 上贡献该路径并报告 H100 上 2–3× 吞吐）、PD 分离的思想（把用户长历史 prefill 与 beam 解码放到不同 GPU 池）都可以原样搬。

不收敛的部分恰好是推荐训练的本体：**稀疏表（哈希/准入/淘汰/增量同步）、jagged 数据路径、请求级样本组织、半同步与异步更新、流式单遍训练与线上线下一致性**。几条原文措辞把边界画得很清：SORT 说"sparse 模块主要受 I/O 与访存瓶颈限制，dense 模块受计算效率支配"；STCA 说"随着序列长度增大，存储与带宽而非 FLOPs 成为瓶颈"；TorchRec 的 SemiSync 用 B-2 时刻的参数换取 all-to-all 与前向的完全重叠——这是 LLM 训练不会接受的权衡；Pinterest 指出大 embedding 表"第一个 epoch 后过拟合"，这是推荐必须流式单遍训练的直接证据；NVIDIA 的 SID-GR 用 THD/jagged 布局而非 padded dense；昇腾侧的 TurboGR 直接指出该平台"缺少高性能 jagged 算子"。推理侧的不收敛同样有三条硬证据：按用户 ID 而非 token 前缀查 KV、大 beam 必须把 Context KV 与 Beam KV 分开处理、以及"投机解码对 SID 的 3–5 步强约束解码没有意义，结构化约束（trie/mask）才是对应物"。

一个简洁的概括是：**收敛的边界正好是"模型里有没有 ID"**。dense 侧完全可以复用 LLM 栈的并行、编译、kernel、MoE 与低精度；ID 的存在决定了哈希表、jagged、请求级样本、流式单遍与参数服务器残留。这也解释了为什么 SID 路线（OneRec、GR4AD、PLUM）被反复强调"通信效率"——OneRec 的报告明说"稀疏 embedding 操作需要大量 PS 通信做 lookup 与梯度更新，语义 ID 通过稠密操作与共享词表减少通信开销"。SID 本质上把一部分稀疏问题转换成了 dense 问题，从而让推荐栈更多地落进 LLM 栈的射程之内；代价是 tokenizer 治理、碰撞管理与索引热更新成为新的工程负担。

## 未来 12 个月：方向明确，瓶颈集中在数据、显存与一致性

以下判断由 2025 年中至 2026 年 10 月的公开轨迹外推，没有任何公司公开 2027 年路线图。**精度层面**，Blackwell/Rubin 集群上的 dense 预训练会把 NVFP4（首尾层保 BF16、末期切回高精度）变成常见选项，而 MoE 预训练主体仍是 MXFP8 加 FP4 激活/通信压缩；H800/H20/昇腾上的团队继续 FP8 blockwise。风险是 FP4 的稳定性研究尚未收敛（收缩偏差、热通道、转置不一致等多篇 2026 年工作），若多家在 10T+ token 规模上报告 loss gap，NVFP4 预训练的普及会推迟到 Rubin 代。**框架层面**，Megatron-Core + TE + Megatron-Bridge 的事实标准地位会进一步巩固，torchtitan 在 RL/后训练与研究侧扩张；EP 通信收敛到 NCCL 原生与超节点感知库；容错范式从 checkpoint-restart 转向副本/角色级隔离与步内恢复，**ETTR ≥ 95% 会成为万卡级平台的公开对标线**。**推理层面**，PD 分离加弹性 EP 加分层 KV 池成为默认而非高级选项，投机解码从自回归草稿切换到并行块草稿加置信调度（接受长度 4–6 成为常态），每百万输出 token 的自建成本再降 2–3×。**推荐层面**，最可能发生的是引擎分叉固化为三条线（通用 LLM 引擎、视频/扩散、推荐 SID-GR 专用 beam 引擎），fleet 级 ETT 与 delta checkpoint 被更多公司当作公开指标，FP8 训练从 Meta 向其他公司扩散但形式是"GEMM 级 + 融合量化 + 架构改造"而非全模型 FP8，增量同步接口（DynamicEmb replay、TorchRec delta tracker）被在线学习系统直接采用，HugeCTR 不再有功能性发布。**基座层面**，上游 FM 从 logits 蒸馏升级为表征/事件 token 注入会成为默认，FM 家族分层化取代"一个 FM"的叙事，而 LLM 基座在推荐中的落地点继续固定在召回/意图/可解释层——**在线同步 10B+ LLM 进入 feed 级精排主链路在 12 个月内不太可能发生**。

工程瓶颈集中在七处，且每一处都有公开的量化锚点。**样本流水线**是第一位的：Fat Row 在 4K 序列即撞墙，超长序列的瓶颈不在 GPU 而在训练数据的写/读带宽与预处理，而公开资料中没有任何公司给出"每 GPU 需要多少 CPU 核"的生产配比（仅有字节"千万 CPU 虚拟核 vs 数万 GPU"、快手"每节点 8 GPU + 2 CPU"、Meta"数据支撑服务/GPU 训练功耗 ≥ 0.75 即撞墙"三个量级线索）。**激活显存与长序列**第二：20K 序列 +49 GB 是最直接的代价，对策（去 padding、选择性重物化、教师-学生两阶段）都已有公开样本，但**没有任何公司公开 10k–100K 序列训练下序列并行/上下文并行的生产使用情况**。**专用 beam 引擎**第三：SGLang 主干虽已合入 beam search，但 KV 压力下整组中止、不支持投机解码与 PD 分离，仍不满足推荐的 p99 与多级缓存需求；而 NVIDIA 的 SID-GR 仍是单机 alpha、无 TP/PP 与跨 GPU KV 归属设计。**跨请求 KV 的存储与路由**第四：没有任何公司公开生产环境的跨请求 KV 命中率与存储规模。**训推一致性**第五：FP8/低精度 rollout、MoE 路由、异步陈旧、缓存表示与训练表示不一致（Memory Layer 的 NE gap 12.11%）都需要显式修正，且修正本身有成本（bitwise 一致的 RL 实验比非 bitwise 慢 2.4×）。**on-policy 数据的流量门槛**第六：快手给出的经验值是 25% 流量，低于此只能做小比例 rollout 或依赖模拟器。**口径与评估**第七：各家 MFU 的峰值基准、是否含 embedding/attention FLOPs 都不一致（OneRec 文中甚至出现 28.8%/28.6% 自相矛盾），跨公司数字不可直接排序，内部对标必须固定为"所用精度的非稀疏峰值"。

## 对起步团队的路线建议：四个阶段，每阶段带前置条件与验收指标

给一个刚开始开展训练推理优化、同时在考虑基座模型的 TikTok 推荐工程团队，公开证据支持的顺序是**先拿口径与有效时间，再拿模型形态与计算复用，再拿低精度，最后才碰基座模型**。这个顺序不是保守，而是由公开数据的收益密度决定的：MFU 的第一桶来自改模型（10× 量级）、有效时间的第一桶来自生命周期治理（Meta 基线显示曾有近一半加速器时间被吃掉）、计算复用的第一桶来自请求内共享（"免费"，不引入陈旧性），而 FP8 与基座模型都需要前两者就位才能兑现。

| 阶段 | 前置条件 | 核心动作 | 可量化验收指标 |
|---|---|---|---|
| **0｜建立口径与基线（约 1 个季度）** | 能在生产训练作业上跑 profiler（nsys ≥ 2024.6）；有一套可回放的代表性 batch | 固定 MFU 口径为"所用精度的非稀疏峰值"并写进监控（RecIS 已内置该指标）；按 Meta ETT 定义统计 `training_on_new_data / wall_time` 并按初始化、编译、checkpoint、发布、恢复归因；按 NVIDIA PERF_ANALYSIS 的方式拆 GPU 时间（attention / elementwise / GEMM / embedding / NCCL 暴露 / 空闲） | 主力训练作业的 MFU、ETT%、GPU 时间六段分布有周级看板；straggler 导致的 run-to-run step 方差有基线值（Guard 的参照是从 20% 压到 1%）；推理侧有每模型的 p99 与"每请求 GPU 毫秒"基线 |
| **1｜模型形态与计算复用（1–2 个季度）** | 阶段 0 的时间分布显示 elementwise 与小 GEMM 占比高；样本流水线可改为用户/请求粒度 | 把访存受限的碎片算子换成大 GEMM（RankMixer/TokenMixer-Large/Kunlun GDPA 路线）；上请求级批处理（RLB）并把用户侧编码摊到多候选；上请求内 KV 复用与候选隔离（LONGER/ROCS 路线）；推理切到 torch.export + AOTInductor | MFU 从个位数/十几进到 25–45%（公开区间）；单 GPU 训练吞吐 ≥2×、CPU→GPU 带宽 ≥−50%（STCA 的参照是 2.2× 与 −84%）；多候选打分的吞吐退化从 −40% 级压到 −10% 以内；AOTI 相对 Python 运行时每请求延迟 ≥1.4× |
| **2｜数据/显存/有效时间（与阶段 1 并行或紧随）** | 已能测出数据支撑服务与 GPU 训练的资源比；checkpoint 与发布流程可改 | 用版本化延迟物化替代 Fat Row（不可变、按时间范围可重建的序列层 + O(1) 版本元数据）；选择性重物化 + 去 padding 治长序列显存；异步/增量 checkpoint 与 delta 发布；按副本/角色做容错而非整任务重启 | 主训练数据写带宽 ≥−40%、读带宽 ≥−45%（Meta 的参照是 −46.2% 与 −47.7%~−70.3%）；每层激活显存 ≥−50%（ULTRA-HSTU 为 −67%）；ETT% 从约 80% 提到 ≥90%，端到端 checkpoint 时间进入秒级；序列长度上限在同硬件下提升 ≥2 档而延迟预算不变 |
| **3｜低精度与专用引擎（在阶段 1–2 之后）** | 有融合量化 kernel 的能力（否则 scale 开销吃掉收益）；有逐层数值探针与精度回归集 | 先做 embedding INT4/INT8（省通信与显存），再把 FP8 只打进主 GEMM 并把行级缩放量化融合进前置 kernel，attention 与归一化保 BF16；生成式路径上 FP8 PTQ + beam-shared KV + TopK 预裁剪 + 动态 beam；需要大 beam 时准备 context/beam 分离的 attention kernel 加 CUDA graph，而不是整套 serving 框架 | 整层前向 FP8 相对 BF16 1.1–1.25×（HSTU Ultra 的真实幅度），而非单 GEMM 的 2×；embedding 查表延迟 ≥−40%（ULTRA-HSTU 为 13→7.9 ms）；生成式推理延迟 ≥−40%、吞吐 ≥+80%（OneRec-V2 为 −49%/+92%）且线上核心指标无退化；大 beam 场景 decode attention kernel 时间下降一个数量级（NVIDIA 为 35.24→1.59 ms）；低精度上线前必须有 NE/AUC 与 CTR 校准的对照表——这正是公开材料的空白处 |
| **4｜基座模型（仅在判据成立时启动）** | 下游模型数 N ≥ 10；已有带版本的 embedding/特征存储、教师日志管道、流式训练与多租户共享数据集 | 先做最便宜的"教师日志版"（教师独立流式训练、前向写出 logits 到中间存储、学生用解耦塔消费，可回滚）；再做表征注入（需多版本 embedding 服务与去噪）；SID 可作为并行项把部分稀疏问题转成 dense 以降低 PS 通信，但 tokenizer 与词表治理需单独立项；只有在需要语言/世界知识对齐 SID 时才考虑 LLM 初始化，并按 PLUM 的 2×2 消融自行验证 | 离线迁移率 η 可测且 ≥45%（公开区间 45–73%，表征注入 0.64–1.0）；在线成本中性（延迟与 CPU 持平）；教师停训或流水线滞后时主任务塔不受影响（解耦塔的容错语义）；新鲜度差距有补偿机制且被量化（无流式蒸馏时学生增益 5 天减半是必须避免的失败模式）；"FM 训练 + 日志/缓存成本 ≤ N × 单模型迁移增益"这条判据有内部数字支撑 |

三条贯穿所有阶段的纪律值得单独强调。第一，**不要跳过阶段 0 的口径工作**：公开材料里最常见的失败不是优化做错，而是数字不可比——各家 MFU 口径不一致、CPU/GPU 成本没有任何公司给出绝对值、跨请求 KV 命中率无生产统计，这些缺口意味着任何外部数字都只能当方向而非目标。第二，**把"可替换层"当成架构要求**：NVFP4 路径、DeepEP 式通信库（硬门槛是 Hopper+、CUDA ≥13.1、PyTorch ≥2.10）、Blackwell 专用 kernel（B200 上的 HSTU kernel 仍有 page size 128、head dim 128 的限制）都应隔离在可替换边界内，因为国内算力基线在 12 个月内仍是 Hopper 级加国产卡。第三，**把 agent 驱动的优化循环连同防护栏一起引入**：Talos 在推荐负载上拿到 2.2–3.3× 的同时公开了"约三分之一循环被判决器丢弃"，其"做出改动的 agent 不是决定是否保留它的 agent"、三道闸门（前向与梯度一致、优化器状态一致、step time 真的改善）、两条代码路径共存，是比加速比本身更值得复制的部分；KernelBench 官方的 reward hacking 警告则说明没有防护栏的自动优化会直接产出假收益。

## 结论

把全部公开证据合在一起看，2026 年 10 月的真实分界不在"用什么框架"或"买什么卡"，而在**一个团队是否已经把效率变成可计量、可归因、可回归的平台能力**。三个层面的数字指向同一结论：单作业内的 MFU 在推荐侧已有 10× 的改进空间但上限明确（45–60% 之后只剩 FP8 与"把通信搬离 SM"）；fleet 级的有效训练时间曾吃掉近一半加速器时间，而治理它比提升 MFU 更便宜；每请求成本的下降几乎全部来自计算复用与低精度，而不是换代——BF16 的每 FLOP 成本两年几乎没降，GB300 相对 GB200 的收益也只是同代小步。这反过来解释了为什么头部公司在 2025–2026 把论文写在"数据延迟物化""有效训练时间""请求级批处理""副本级容错"这些看起来不性感的题目上：它们是乘数，而新架构只是加数。

基座模型这一层最反直觉的发现是，**它首先是组织与算力分摊机制，其次才是模型**。ExFM 的教师甚至只是"更大的 DLRM 变体"，Lattice 的出发点是"整合后模型少，才能做定制 kernel 与低精度"，HyperCast 把"不牺牲 expert 快速迭代"直接写成贡献。因此评估一个基座项目该看"迁移率 × 下游模型数"而非单模型指标，而决定成败的往往是三件平台事：带版本的 embedding 存储、教师预测/表征的日志管道、以及（若做表征注入）多版本并行服务——没有这三项，中心 FM 的每次更新都会变成场景团队的回归风险。通用开源基座的现状同样需要祛魅：能力前沿几乎全在中国厂商，可落地档位清晰（30B-A3B 与 8B dense），但"LLM 初始化有益"只有 PLUM 一例公开消融，而许可证里的 MAU 条款与地域排除对大型平台是真实的工程约束而非法务脚注。下一年真正的护城河，大概率属于那些既能把 FP8 的 1.13–1.25× 老老实实拿到手、又能在动手之前先把 NE/AUC 校准对照表建起来的团队。

## Q1. 评估（Evaluation）：任务评估、轨迹评估、LLM-as-judge、pass@k vs pass^k、离线/在线、回归套件；行业失败率数字及其争议

### Takeaway
2026 年的行业共识是：Agent 评估 = 任务（Task）+ 评分器（Graders）+ 结果（Outcome），从 20–50 个来自真实失败的任务起步，优先用确定性/代码评分器判断"结果状态"，用 pass^k 而非 pass@k 衡量面向用户的可靠性，并把评估分为"能力评估（低通过率，探索上限）"和"回归评估（≈100% 通过率，防退化）"两类。Gartner "40% 项目将被取消"和 MIT "95% 试点失败"被广泛引用，但后者的方法学与口径受到实质性批评，应谨慎引用。

### Cited Findings

**Anthropic《Demystifying evals for AI agents》（2026-01-09，作者 Mikaela Grace 等）**
- 核心定义：Eval = Task + Graders + Outcome；Trial（单次尝试，需多次以抵消随机性）；Transcript/Trace/Trajectory（含输出、tool calls、推理与中间结果的完整记录）；Outcome（trial 结束时环境的最终状态，如"数据库里是否真的存在该机票预订"）；Evaluation Harness（提供指令与工具、并发运行、记录步骤、评分并聚合的基础设施）— [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- pass@k vs pass^k："pass@k 是 k 次尝试中至少成功一次的概率，随 k 上升；pass^k 是 k 次全部成功的概率，随 k 下降。若单次成功率 75%，跑 3 次全成功的概率 (0.75)^3 ≈ 42%。"面向客户、要求可靠性的 Agent 用 pass^k；"一次成功即可"的工具型任务用 pass@k — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 三类评分器：代码评分器（字符串/正则匹配、二元测试、静态分析、结果验证、tool call 验证；快、便宜、可复现但脆弱）；模型评分器（rubric 打分、自然语言断言、成对比较、参考答案比对、多评委共识；灵活但非确定性、需与人类校准）；人类评分器（SME 审核、抽样 spot-check、A/B、标注者一致性；黄金标准，用于校准前两者） — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 起步规模："20–50 个来自真实失败的简单任务是很好的开始"；好任务的标准是"两位领域专家会独立得出相同的 pass/fail 判定"；每个任务应附参考解以证明可解；"用前沿模型跑多次 trial 仍是 0% 通过率，通常说明任务坏了而非 Agent 不行" — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 环境隔离：每个 trial 必须从干净环境开始；共享状态会导致相关性失败并虚高成绩 — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- LLM-as-judge 的使用边界：开放式/主观任务、多解、需要捕捉细微差异、对话质量评估；要求"与人类专家紧密校准"；指令中允许返回 "Unknown"；每个维度单独评判而非一个评委打总分 — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- Coding Agent 建议：用确定性评分器（"代码能跑、测试能过"），如 SWE-bench Verified、Terminal-Bench；同时评 outcome 与 transcript（代码质量启发式规则 + 模型评分器评 tool 使用模式）；"通常更应评 Agent 产出了什么，而不是它走的路径"，因为 Agent 会找到设计者未预料的合法路径 — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 评分 bug 案例：CORE-Bench 最初给 Opus 4.5 打 42%，修复"期望 96.124991… 却因输出 96.12 判错的僵硬评分"和模糊任务说明后升至 95% — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 评估饱和：SWE-bench Verified 一年内从 40% 到 >80%；"100% 的 eval 只能追踪回归，无法指引改进" — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)
- 生命周期：能力评估（低通过率）→ 毕业为回归评估（≈100%）；建议设专职 eval 团队拥有基础设施，领域专家贡献任务；"定义 eval 任务是检验产品需求是否足够具体的最佳方式之一"；有 eval 的团队可"在几天内完成模型升级"而非数周测试 — [同上](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**pass^k 的来源：Sierra τ-bench（2024-06 发布，2025–2026 持续被模型卡引用）**
- τ-bench 引入 pass^k（k 次独立尝试全部成功才算解决）以衡量一致性；早期结果显示基于 GPT-4 的 Agent 单次成功率 <50%，重复 8 次时一致成功率仅约 25% — [Sierra 博客](https://sierra.ai/blog/benchmarking-ai-agents)；[arXiv 2406.12045](https://arxiv.org/pdf/2406.12045)
- Anthropic 模型卡现已讨论 pass^k 可靠性指标（二手） — [prefactor.tech](https://prefactor.tech/learn/agent-benchmarks)

**Hamel Husain / Shreya Shankar 的 eval 方法（2025-05 FAQ，2025–2026 持续更新；原站被拦截，以下为二手）**
- "错误分析是 eval 中最重要的活动"，其参与项目中 60–80% 的开发时间花在错误分析与评估上 — [hamel.dev evals FAQ](https://hamel.dev/blog/posts/evals-faq/)（二手摘要）；[Pragmatic Engineer 版](https://newsletter.pragmaticengineer.com/p/evals)
- 推崇二元 pass/fail 而非 1–5 分：二元判断更快、迫使下决定、不把不确定性藏在中间分里；只问评委一个具体的 yes/no 问题，反对"helpfulness"之类聚合分 — [同上](https://hamel.dev/blog/posts/evals-faq/)
- 流程：逐条检查数据→描述每条交互中第一个可观察的错误（open coding）→归类（axial coding）→按频率排优先级；确定性失败用代码 eval，主观失败用 LLM judge；judge 必须用人工标注样本校验，并检查分歧案例 — [同上](https://hamel.dev/blog/posts/evals-faq/)
- 2026 年 Hamel 发布面向 coding agents 的 "evals-skills"（可被 Claude Code 等直接加载的评估技能） — [Substack](https://hamelhusain.substack.com/p/evals-skills-for-coding-agents)；[GitHub](https://github.com/hamelsmu/evals-skills/blob/main/questions.md)

**"失败率"数字及争议**
- Gartner（2025-06-25）：预测到 2027 年底 >40% 的 agentic AI 项目将因成本攀升、业务价值不清或风险控制不足而被取消；2025 年 1 月对 3,412 名 webinar 参会者的调查：19% 已大额投资、42% 保守投资、8% 未投资、31% 观望；同时预测 2028 年 15% 的日常工作决策由 agentic AI 自主做出（2024 年为 0%），33% 的企业软件将含 agentic AI（2024 年 <1%）；Gartner 批评"大多数 agentic AI 项目是被炒作驱动、常被误用的早期实验或 PoC"，并点名 "agent washing" 现象 — [BigDATAwire 转载 Gartner 新闻稿](https://www.hpcwire.com/bigdatawire/this-just-in/gartner-predicts-over-40-of-agentic-ai-projects-will-be-canceled-by-end-of-2027/)；[Forbes 2026-07-07 跟进](https://www.forbes.com/sites/robertszczerba/2026/07/07/why-40-of-agentic-ai-projects-may-be-canceled-by-2027/)
- MIT NANDA《The GenAI Divide: State of AI in Business 2025》（2025-07/08）："95% 的集成式 GenAI 试点无可衡量的 P&L 影响" — [Forbes 2025-08-26](https://www.forbes.com/sites/jasonsnyder/2025/08/26/mit-finds-95-of-genai-pilots-fail-because-companies-avoid-friction/)；[Yahoo Finance](https://finance.yahoo.com/news/mit-report-95-generative-ai-105412686.html)

- 2026-09 仍有厂商（Oradian）沿用 "95%" 口径 — [Crowdfund Insider](https://crowdfundinsider.com/2026/09/313254-95-of-enterprise-genai-pilots-deliver-no-measurable-return-oradian-says)

### Inferences
- 对内部研发提效 Agent：首批 eval 应直接取自真实失败的 Claude Code / 内部 Agent 会话（20–50 条），以"结果状态"（测试通过、PR 可合并、CI 绿）为主评分器，再加少量 transcript 级 judge（如"是否未经授权跑了破坏性命令"），并对关键任务用 pass^3 或 pass^5 而非 pass@1 报告。
- 把"任务定义"当成需求评审的一部分（Anthropic 观点），可以同时解决"用例选错"和"评估缺失"两个 Gartner 指出的取消原因。
- 引用失败率时，建议表述为"Gartner 预测 >40% 项目被取消（2025-06）；MIT NANDA 报告称 95% 试点无 P&L 影响但口径受质疑"，避免把 95% 当作既定事实。

### Gaps
- 未找到任何权威来源量化"多少比例的 Agent 项目因缺乏 eval 而失败"；Gartner 把原因归为成本/价值/风控三类，没有单独列出"缺乏评估"。
- Hamel Husain 原文、OpenTelemetry/AISI/tbench 官方页面因网络拦截未能逐字核验（以上为二手摘要）。
- OpenAI 官方 eval 指南与"托管 Evals 退役"说法未经一手核实。

## Q2. 可观测性与追踪：OpenTelemetry GenAI 语义约定、追踪工具、关键指标

### Takeaway
OpenTelemetry GenAI 语义约定（invoke_agent / execute_tool / chat 等 span 操作名，token 用量属性）正在成为跨工具的公共 schema，但截至 2026 年仍标记为 "Development"（非 Stable）。工具选型按栈分流：Langfuse（MIT、自托管）、Arize Phoenix（OTel 原生）、LangSmith（LangChain/LangGraph 原生）、Braintrust（eval 优先）、Datadog（与 APM/基础设施/安全栈关联）、W&B Weave（已在 W&B 的团队）。真正重要的指标是任务级的：任务成功率、每任务成本/tokens、tool 错误率、人工介入次数、完成时长。

### Cited Findings
- OTel GenAI 语义约定定义的操作名：`chat`（模型调用）、`invoke_agent`（一次 Agent 运行）、`execute_tool`（工具调用）、`embeddings`、`create_agent`（构建远程 Agent，如 OpenAI Assistants / Bedrock Agents，span kind CLIENT）；另有 `plan`、`invoke_workflow`；每个 tool call、LLM 调用、检索步骤成为子 span，形成完整推理链 trace；模型调用 span 携带模型、参数与 token 用量，tool 调用作为兄弟 span 携带时长与结果 — [Uptrace 2026](https://uptrace.dev/blog/opentelemetry-ai-systems)；[Greptime 2026-05-09](https://greptime.com/blogs/2026-05-09-opentelemetry-genai-semantic-conventions)；[Decagon 术语表](https://decagon.ai/glossary/what-are-opentelemetry-genai-semantic-conventions)
- 稳定性：OTel GenAI 约定为 Agent、tool 与 MCP 调用定义了 span 与 metrics，但"每一项都标记为 Development，而非 Stable"（2026） — [Aurora SRE](https://www.aurorasre.ai/blog/opentelemetry-ai-agent-observability)；[Morph Agent Tracing](https://www.morphllm.com/agent-tracing)
- 工具对比（2026，二手汇总）：Langfuse（MIT 核心，自托管，追踪 + eval + prompt 管理，$29/月起）；Arize Phoenix（ELv2，"最好的 OTel 原生开源选项，无供应商锁定"，Arize 云 $50/月起）；LangSmith（闭源，$39/席位/月起，LangChain 原生）；W&B Weave（Apache 2.0，适合已在 W&B 的团队，eval harness 强）；Datadog LLM Observability 的主要优势是把 AI trace 与 APM、基础设施、安全栈关联 — [Confident AI 12 工具对比](https://www.confident-ai.com/knowledge-base/compare/10-llm-observability-tools-to-evaluate-and-monitor-ai-2026)；[MarkTechPost 2026-08-09](https://www.marktechpost.com/2026/08/09/top-llm-observability-and-evaluation-platforms-in-2026-langfuse-langsmith-braintrust-arize-and-more-compared/)；[Laminar 对比](https://laminar.sh/article/top-6-agent-observability-platforms)；[OpenObserve](https://openobserve.ai/blog/llm-observability-tools/)
- 选型口诀（二手）："LangSmith for LangChain/LangGraph, Langfuse for self-hosting, Arize for eval rigor, Braintrust for eval-first workflows"；"需要在现有 APM 里看运维指标选 Datadog，需要开源追踪选 Langfuse 或 Phoenix" — [Latitude 对比](https://latitude.so/blog/best-llm-observability-tools-agents-latitude-vs-langfuse-langsmith)
- 可作为"人工介入 / 自治度"指标参考的实证：Anthropic 对 20 万条内部 Claude Code 会话（2025-02 至 2025-08）的分析显示，单会话最大连续 tool call 数从 9.8 翻倍到 21.2，每条 transcript 的人工介入轮次从 6.2 降到 4.1（-33%），任务复杂度自评从 3.2 升到 3.8（5 分制） — [Anthropic Research](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)
- 学术侧 2026 年出现"Agent 原生遥测"方向：可篡改检测、可重放的 Agent 运行证据（NovaFabric）、基于状态增量的可验证遥测、推理溯源（reasoning provenance）等 — [arXiv 2609.12582](https://arxiv.org/pdf/2609.12582)；[arXiv 2608.16178](https://arxiv.org/pdf/2608.16178)；[arXiv 2603.21692](https://arxiv.org/pdf/2603.21692)
- Agent 观测的指标框架（2026 行业文章）：追踪应覆盖 tool calls、检索步骤、多步工作流，并"用离线 eval 同样的评分逻辑对线上 trace 打分"（在线 eval） — [Braintrust Agent Observability Guide 2026](https://www.braintrust.dev/articles/agent-observability-complete-guide-2026)

### Inferences
- 对大型内部平台，最稳妥的架构是：SDK 层统一用 OTel GenAI 约定打点 → 经 LLM Gateway 落到自有 OTel collector → 同时导出到现有 APM（如 Datadog/内部 Metrics）和一套 Agent 专用 trace/eval 平台（Langfuse 或 Phoenix 自托管）。因约定仍在 Development 阶段，需在内部封装一层属性映射以应对 schema 变更。
- 建议的最小指标集（综合 Anthropic 内部分析与行业文章）：任务成功率（含 pass^k）、每任务成本与 tokens（区分 cache 读/写）、tool 错误率、每任务人工介入轮次、最大连续 tool call 数、完成时长、被拒绝/被 deny 的操作数。

### Gaps
- opentelemetry.io 官方页面被拦截，具体属性名（如 `gen_ai.usage.input_tokens`）与内容捕获 opt-in 环境变量未能逐字核实。
- 未找到 Datadog LLM Observability 官方文档中对 Agent 特定指标的定义。

## Q3. 安全、权限与沙箱：权限模型、沙箱技术、提示注入、密钥、审计、Agent 身份、重大事故

### Takeaway
2025–2026 年的核心教训是"模型层不能可靠阻止提示注入，边界必须在模型之外"：OS 级/VM 级沙箱 + deny-first 的权限规则 + 把凭据放在沙箱之外的代理层 + 开发/生产环境硬隔离 + 人类检查点。Replit 删库（2025-07）、Amazon Q 扩展被植入擦除指令（2025-07）、Cursor MCP RCE（2025-07/08）、Rules File Backdoor（2025-03）、Shai-Hulud npm 蠕虫专门窃取 AI 工具凭据并植入恶意 MCP 配置（2025-09/11）构成了一组可直接用于威胁建模的真实案例。

### Cited Findings

**权限模型（以 Claude Code 为例，官方文档，2026-10 版）**
- 分层权限：只读工具（文件读、Grep）在工作目录内不需批准；Bash 需批准（内置一组只读命令除外）；文件修改需批准（"不再询问"仅到会话结束）；WebFetch 需批准（预批准文档域名除外） — [Claude Code 权限文档](https://code.claude.com/docs/en/permissions)
- 权限模式：`default`（首次使用每个工具时询问）、`acceptEdits`（自动接受工作目录内的编辑与 mkdir/mv/cp 等）、`plan`（只读探索，不改源码）、`auto`（后台分类器在 shell/网络操作执行前检查其是否符合用户请求）、`dontAsk`（自动拒绝所有需询问的调用）、`bypassPermissions`（跳过提示；官方警告"仅在容器/VM 等隔离环境使用"）；组织可通过 `disableBypassPermissionsMode` / `disableAutoMode` 在 managed settings 中禁用高风险模式 — [同上](https://code.claude.com/docs/en/permissions)
- 规则语法：`Tool` 或 `Tool(specifier)`，如 `Bash(npm run build)`、`Read(./.env)`、`WebFetch(domain:example.com)`、`Agent(model:opus)`；通配符放在子命令之后（`Bash(git log *)` 而非 `Bash(git *)`）；不能用 `Bash(command:rm *)` 这种可被复合命令绕过的写法，系统会忽略并警告 — [同上](https://code.claude.com/docs/en/permissions)
- deny-first 优先级："任一层级 deny，其他层级都不能 allow"；managed settings 最高，命令行参数也不能覆盖；`allowManagedPermissionRulesOnly` 可让 managed settings 成为唯一权限来源 — [同上](https://code.claude.com/docs/en/permissions)
- Hooks：PreToolUse hook 在权限提示前运行，可 deny / 强制询问 / 放行；但 hook 的 allow 不能绕过 deny 与 ask 规则；exit code 2 的阻断 hook 优先于 allow 规则（可实现"全部 Bash 放行、仅封禁少数命令"） — [同上](https://code.claude.com/docs/en/permissions)
- 权限与沙箱互补："即使提示注入绕过了 Claude 的决策，沙箱限制仍然生效"；启用沙箱后沙箱内 Bash 默认不再提示（`autoAllowBashIfSandboxed`），但 `Bash(git push *)` 类内容范围的 ask 规则、显式 deny、针对关键路径的 rm 仍走常规流程 — [同上](https://code.claude.com/docs/en/permissions)

**沙箱技术**
- Anthropic Claude Code 沙箱（2025-10-20）：两道边界——文件系统隔离（只能访问指定目录）与网络隔离（只能连接批准的服务器，经沙箱外的代理校验域名）；Linux 用 bubblewrap，macOS 用 Seatbelt，在 OS 层强制；"内部使用中沙箱安全地减少了 84% 的权限提示"；威胁模型是提示注入——"被攻陷的 Claude Code 无法窃取 SSH 密钥或回连攻击者服务器"；Claude Code on the web 把 git token 等敏感凭据放在沙箱之外，由自定义代理在认证 GitHub 前校验 git 操作；实现开源为 `@anthropic-ai/sandbox-runtime`（research preview），可用 `npx @anthropic-ai/sandbox-runtime <cmd>` 包裹任意进程、Agent 或 MCP server — [Anthropic Engineering](https://www.anthropic.com/engineering/claude-code-sandboxing)；[GitHub anthropic-experimental/sandbox-runtime](https://github.com/anthropic-experimental/sandbox-runtime)；[Claude Code 沙箱文档](https://code.claude.com/docs/en/sandboxing)；[沙箱环境选择](https://code.claude.com/docs/en/sandbox-environments)

### Inferences
- 五起事故的共性可直接转成平台硬约束：(a) dev/prod 凭据与数据面物理隔离，Agent 默认拿不到生产写凭据（Replit）；(b) 配置文件（rules、MCP、.claude、hooks）视为可执行代码，纳入代码审查与隐藏字符扫描，变更需重新确认（Rules File Backdoor、MCPoison）；(c) Agent 工具链自身的供应链（扩展、npm/PyPI 依赖、MCP server）要走与生产依赖同级的签名/allow-list（Amazon Q、Shai-Hulud、LiteLLM）；(d) 凭据不进沙箱，由代理在出口处注入并校验操作（Claude Code on the web 的 git proxy 模式）；(e) 打破 lethal trifecta 中至少一环——对读取不可信内容的 Agent 禁止任意外联（网络 allow-list）。
- 推荐权限分级：只读/plan 模式 → 沙箱内自动放行 + 内容范围 ask 规则（如 `git push`、生产 CLI）→ 生产写操作一律人类检查点；用 managed settings 的 deny-first 规则做组织底线，用 hooks 实现"全部放行但封禁少数命令"的白名单例外。
- 内部 MCP registry + Agent 身份（SPIFFE 或等价 workload identity）+ 审计日志，是满足 OWASP ASI03/ASI04 的最小可行组合。

- Deriv 生产 Agent 案例：prompt caching 把输入成本降 77%，缓存命中率 85.8% — [Deriv AI Substack](https://derivai.substack.com/p/prompt-caching-production-ai-agent-costs)（原文被拦截，二手）
- 学术评估《Don't Break the Cache》（2026-01）：在真实长程 Agent 轨迹上 prompt caching 把 token 成本降 49–80%；关键是避免破坏前缀缓存 — [arXiv 2601.06007](https://arxiv.org/pdf/2601.06007)（二手摘要）
- 2026 年出现专门面向长程 coding agent 的压缩研究（CliffCompaction） — [arXiv 2609.26779](https://arxiv.org/pdf/2609.26779)
- Anthropic 官方缓存要点（claude-api skill 文档）：缓存按前缀匹配，渲染顺序 tools → system → messages，前缀任一字节变化即失效其后全部；稳定内容放前、易变内容（时间戳、请求 ID）放最后一个 `cache_control` 断点之后；用 `usage.cache_read_input_tokens` 验证，若反复请求仍为 0 说明有"静默失效源"（如 system prompt 里的 `datetime.now()`、未排序 JSON、变化的 tool 集合）；缓存按模型隔离，多模型级联会丧失跨模型缓存复用；"先测最强模型低 effort，再考虑多模型级联"；"按每个完成任务计成本，而非每请求" — [Anthropic Prompt Caching 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching.md)
- LangChain Deep Agents 的缓存实践文章（2026）讨论了 tool 列表/系统提示变化对缓存的破坏 — [LangChain 博客](https://www.langchain.com/blog/deep-agents-prompt-caching)（原文被拦截）

**预算、归因与 FinOps**
- FinOps Foundation《State of FinOps 2026》（二手转述）：98% 的从业者在 2026 年管理 AI 支出（2024 年 31%，2025 年 63%）；GPU 支出首次成为 AI-first 组织的头号 FinOps 关注点 — [Spheron GPU Cloud FinOps](https://www.spheron.network/blog/gpu-cloud-finops-ai-teams-cost-allocation-chargeback-budgeting/)

### Inferences

## Q5. 与内部系统集成：内部工具的 MCP server、LLM/Agent 网关、身份传递、数据访问控制、企业 MCP 注册中心

### Takeaway

## Q7. Agent 可靠性工程：重试、幂等、检查点/持久执行（Temporal、Inngest、Restate、LangGraph）、部分失败、超时与"验证债"

### Takeaway
2026 年的分层共识是："LangGraph 的 checkpoint 保存的是数据，不是执行"——进程死亡即运行死亡，必须有外部机制检测失败、决定从哪一步重入并重启；因此生产 Agent 普遍采用"推理图在上（LangGraph 等）、持久执行引擎在下（Temporal/DBOS/Inngest/Restate）"的分层，把每次 LLM 调用与 tool 调用建模为可重试、可幂等的 activity，并为 human-in-the-loop 等待（可长达数天）提供零成本挂起。配合任务级 token 预算与有界循环，防止失控消耗。

### Cited Findings
- LangGraph checkpoint 的局限："LangGraph 会 checkpoint 状态，但 checkpoint 不是持久执行。一次运行活在单个进程中，进程死了运行就死了。checkpoint 保存你的数据而非你的执行：必须有东西检测失败、决定在图的哪里重入并重启它。"启用 checkpointer 后每个 superstep（节点间转换）保存完整状态快照 — [HackerNoon: LangGraph、DBOS、Inngest、Temporal 对比](https://hackernoon.com/durable-execution-for-ai-agents-langgraph-dbos-inngest-and-temporal-compared)（原文被拦截，二手摘要）
- Temporal LangGraph Plugin（2025/2026）：LangGraph Agent 无需重写即可运行在 Temporal 上，获得自动故障恢复、"等待数天且零成本"的 human-in-the-loop 步骤、可在任何崩溃后存活的运行；关键区别"LangGraph checkpointer 在节点之间保存状态，Temporal 在工作流函数内部保存状态" — [Temporal 博客](https://temporal.io/blog/temporal-langgraph-plugin-durable-execution)（原文被拦截）
- Manetu 案例 "The thread is the Workflow"：把对话线程映射到稳定的 Temporal Workflow ID；worker 崩溃时 Temporal 在别处重新水合该线程的 Workflow（含此前 checkpoint），用户可以位置无关的方式找到执行 — [Temporal 博客](https://temporal.io/blog/manetu-the-thread-is-the-workflow)
- 分层模式："LangGraph 在上负责推理形状，Temporal 在下提供持久执行保证" — [menuagentic 深潜](https://menuagentic.com/deep-dives/architectures-and-patterns/durable-execution-langgraph-plus-temporal/)；[AI Workflow Lab 2026 指南](https://aiworkflowlab.dev/article/ai-workflow-orchestration-in-production-building-durable-agent-pipelines-with-langgraph-and-temporal)
- 有界循环研究（2026-09）：为 Agent harness 提供运行前支出上界、可证明的终止性与可验证的完成 — [arXiv 2609.27871 "Bounded Loops"](https://arxiv.org/pdf/2609.27871)
- Anthropic API 侧的可靠性原语（claude-api skill 文档，2026-09）：SDK 默认 `max_retries` = 2（重试 408/409/429/5xx 与连接错误），默认超时 10 分钟，墙钟可达 timeout × (max_retries+1)；`task_budget`（beta）给 agentic 循环一个它自己能感知的 token 上限，使其"自我节奏、优雅收尾而非被截断"（最小 20,000 token）；Managed Agents 提供美元计价的硬性 session budget；并行 tool 调用失败时应返回 `is_error: true` 的 `tool_result` 而非丢弃；server-side compaction（beta，默认 150K 触发）用于超长会话 — [Anthropic 模型/API 文档](https://platform.claude.com/docs/en/about-claude/models/overview.md)（各特性页见官方文档站）
- 人工介入作为可靠性指标：Anthropic 内部 20 万会话中每 transcript 人工介入从 6.2 轮降至 4.1 轮，最大连续 tool call 从 9.8 升至 21.2——说明自治长度在增加，对 checkpoint 与超时设计的要求随之上升 — [Anthropic Research](https://www.anthropic.com/research/how-ai-is-transforming-work-at-anthropic)
- 事故中的可靠性失败模式：Replit Agent 在删库后"错误报告无法恢复"（Agent 自报状态不可信，需独立验证） — [社区 postmortem](https://swarmproof.github.io/agent-postmortems/2025-replit-prod-db-deletion/)
- 验证债与审查瓶颈（见 Q6）：Agent PR 约 10 倍于人类 PR，CI 成为瓶颈，团队砍掉慢检查导致未运行即合并 — [SpecStory](https://specstory.com/learning/verification/verification-debt)
- 评估侧对可靠性的要求：每个 trial 从干净环境开始，共享状态导致相关性失败（同样适用于生产中的幂等与隔离设计） — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

### Inferences
- 推荐架构：每次 LLM 调用与每个 tool 调用都是幂等 activity（tool 侧用幂等键，如 PR 号/工单 ID/分支名），Agent 循环本身是持久 workflow；人类审批是可挂起数天的 signal；任务级 token/美元预算 + 最大步数作为 kill switch；Agent 的"完成/失败"自报必须由独立验证器（测试、CI、状态查询）确认，再写入审计日志。
- 部分失败处理：并行 tool 调用中单个失败要以显式错误结果回传而非静默丢弃（否则模型会学到不再并行）；对不可重试的副作用（删除、发布、支付）在 PreToolUse 层强制人类检查点。
- 验证债的工程解法是把验证成本前移到 Agent 自身（强制附测试、自验证日志、PR 体积上限），并把 CI 容量视为平台 SLO 的一部分。

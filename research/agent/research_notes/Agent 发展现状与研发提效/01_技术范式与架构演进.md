## 关键问题 1：2025–2026 年的主导 Agent 架构是什么？单一 agentic loop + 工具 vs. 多 Agent 编排 vs. 工作流，三家大厂的建议与共识变化

### Takeaway
2025–2026 年的行业共识是："单一 agent loop（模型 + 工具 + 环境）优先，工作流用于可预测的子流程，多 Agent 只在可并行、读多写少的场景使用"。Anthropic（2024-12 起）、OpenAI（2025-04 起）、Cognition（2025-06 起）都主张从单 Agent 开始；到 2026 年，多 Agent 的"可行形态"收敛为"单写者 + 多个只读/评审/并行研究的子 Agent"，而非自由协商的 swarm。与此同时，工程投入重心从 prompt → context → **harness**（模型以外的全部代码、工具、验证、沙箱）迁移。

### Cited Findings

**关键时间线（按日期）**
- 2024-12-19【历史背景】Anthropic 发布《Building effective agents》，定义 workflow（LLM 与工具按预定义代码路径编排）vs. agent（LLM 动态决定自身流程与工具使用），列出 5 种工作流模式：Prompt Chaining、Routing、Parallelization、Orchestrator-Workers、Evaluator-Optimizer；核心建议是"从简单 prompt 开始、用全面评估优化、只有在简单方案不够时才加多步 agentic 系统"，并建议直接调用 LLM API 而非框架，若用框架需理解底层机制。 — [Anthropic](https://www.anthropic.com/engineering/building-effective-agents)
- 2025-04（约）OpenAI 发布《A practical guide to building agents》：建议从**单 Agent**开始（agent 在循环中调用工具直到退出条件），通过逐步增加工具控制复杂度，只在复杂度要求时才演进到多 Agent；多 Agent 两种形态：**Manager 模式**（中央 LLM 通过 tool call 调度专精 agent，边 = tool call）与**去中心化 handoff 模式**（agent 之间转移执行权并带走最新会话状态，边 = handoff）。 — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；[OpenAI 页面](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)
- 2025-06-13 Anthropic 发布《How we built our multi-agent research system》：Orchestrator-Worker 架构，Lead agent（Claude Opus 4）制定策略并并行派生 Claude Sonnet 4 子 agent；内部评测比单 Agent Opus 4 **高 90.2%**；多 Agent 系统消耗约 **15× 聊天 token**（单 agent 约 4×）；在 BrowseComp 上 **token 用量单独解释了 80% 的性能方差**；适合广度优先、信息量超过单上下文窗口、高价值任务；**不适合**需要全员共享上下文、依赖关系多的任务，"大多数编码工作"被明确列为不适合。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- 2025-06（约）Cognition（Devin 团队）发布《Don't Build Multi-Agents》：主张"共享上下文，而且要共享完整 agent trace 而非单条消息"、"每个动作都隐含决策，并行子 agent 会基于冲突假设行动"，结论是大多数团队应聚焦单线程 agent + context engineering。 — [Cognition](https://cognition.com/blog/dont-build-multi-agents)；[HN 讨论](https://news.ycombinator.com/item?id=45096962)
- 2026 年 4 月（约，按 X 帖子 ID 推算）Cognition 发布《Multi-Agents: What's Actually Working》：承认已部署可用的多 Agent 系统，但"**写操作保持单线程**，额外 agent 贡献的是智能而非动作"；收敛出三种模式：**Code-Review-Loop**（Devin Review：干净上下文的生成者-验证者循环，平均每个 PR 发现 2 个 bug，其中约 58% 为严重问题）、**Smart Friend**、**map-reduce-and-manage**（manager Devin 拆任务、派子 Devin、通过内部 MCP 协调）；"无结构 swarm（任意 agent 网络互相协商）基本是干扰"。 — [Cognition](https://cognition.com/blog/multi-agents-working)；[Walden Yan on X](https://x.com/walden_yan/status/2047054554433462360)
- 2026-02 OpenAI 发布 Codex 实践《Harness engineering: leveraging Codex in an agent-first world》：一个小团队在约 5 个月内用 Codex agent 产出约 **100 万行代码 / 约 1,500 个 PR**，人类通过 prompt 与反馈环把控；提出"**harness engineering**"：当 agent 写大部分代码时，人类工程师优化的是环境——AGENTS.md、设计文档、自动检查、护栏。 — 原文 [OpenAI](https://openai.com/index/harness-engineering-leveraging-codex-in-an-agent-first-world/)（本次调研被封锁）；转述见 [tonylee.im](https://tonylee.im/en/blog/openai-harness-engineering-five-principles-codex/)、[engineering.fyi](https://www.engineering.fyi/article/harness-engineering-leveraging-codex-in-an-agent-first-world)（二手来源）
- 2026-04-22 Google Cloud 发布 **Gemini Enterprise Agent Platform**：包含 ADK（代码优先，"每月在 Gemini 模型上处理超 6 万亿 token"，支持图式 sub-agent 网络）、Agent Studio（低代码）、Agent Runtime（亚秒级冷启动、支持多天长任务、内置 Agent Sandbox、支持 A2A 编排）、Memory Bank、MCP 支持、Agent Identity/Registry/Gateway 治理组件。 — [Google Cloud Blog](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)

**2026 年对"单 vs. 多"的实证**
- Anthropic Claude Code 官方最佳实践（2026 年版）将多会话并行定位为：Worktrees 隔离、Writer/Reviewer 双会话模式（"新上下文做 code review 更好，因为不会偏向刚写的代码"）、`/batch` 把变更拆给 **5–30 个子 agent**（各自独立 worktree）、"Agent teams"（多会话自动协调）仍为**实验性且默认关闭**。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)

### Inferences
- 三家大厂 2024–2025 的文档全部把"单 agent 循环 + 好工具 + 评估"列为默认起点，2026 年没有出现反转；变化在于多 Agent 从"是否要做"变成"**以什么拓扑做**"：Orchestrator-Worker（研究/只读并行）、Writer/Reviewer（生成-验证分离）、Map-Reduce（独立文件/模块的批处理）是被多方独立验证的三种形态。
- 对研发提效 Agent：最稳妥的架构是"一个主 loop + 按需派生只读/评审子 agent + 单一写入者 + 确定性验证（测试/构建/lint）"，而不是角色扮演式 crew。
- "Harness" 一词在 2026 年成为统一叫法（OpenAI 2026-02 推广、Lilian Weng 2026-07 系统化、多篇 arXiv 跟进），说明竞争焦点已从模型/prompt 转到环境工程。

### Gaps
- OpenAI 原文《Harness engineering》与 Cognition 两篇博客的原文均被网络封锁，数字（100 万行/1,500 PR/5 个月；2 bug/PR、58%）来自多方一致转述，但未能一手核验。
- 未找到 2026 年针对"研发提效 Agent"（非编码 agent，如 code review/CI 排障/文档）的权威架构对比研究。

## 关键问题 2："Harness engineering" / "Context engineering" 是什么，具体技术有哪些？

### Takeaway
Context engineering（2025 年中成形）= 在每一轮推理里**管理进入上下文窗口的全部 token**（而不是只写一次 prompt）；harness engineering（2026 年成形）= 模型之外的一切（loop、工具、权限、验证、沙箱、记忆、可观测性）。核心技术已经标准化：compaction（自动摘要）、sub-agent 隔离上下文、文件系统当记忆、Skills 渐进披露、CLAUDE.md/AGENTS.md 项目记忆、hooks 做确定性约束。

### Cited Findings

**定义与范围**
- Anthropic《Effective context engineering for AI agents》（2025-09-29）：context engineering 是 prompt engineering 的自然延伸，"策划和维护推理时最优 token 集合"，覆盖所有进入上下文窗口的内容；prompt 写一次，context 每轮管理。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- awesome-harness-engineering 对 harness 的定义："围绕 AI agent 的脚手架——上下文投递、工具接口、规划产物、验证循环、记忆系统、沙箱——决定其在真实任务上成败"；原则："每个组件存在都是因为模型自己做不到，而最好的 harness 在设计时就预期这些组件会随模型进步而变得不必要"。 — [GitHub](https://github.com/ai-boost/awesome-harness-engineering)
- Faros 等总结公式 **Agent = Model + Harness**，harness 为"除模型外的全部代码、配置与执行逻辑"；核心做法："agent 每犯一个错，就工程化一个解决方案让它不再犯"。 — [Faros](https://www.faros.ai/blog/harness-engineering)（二手来源）
- Lilian Weng《Harness Engineering for Self-Improvement》（2026-07-04）：把 harness 定义为模型的外部执行系统（决定如何调用工具、管理上下文、读写文件、拆任务、调子 agent、验证结果、从失败学习），并把相关研究归为四类：context engineering（ACE、MCE、Meta-Harness）、工作流自动设计（ADAS、AFlow、AI Scientist）、自改进 harness（Self-Harness、STOP）、进化式程序搜索（AlphaEvolve、Darwin Gödel Machine、ShinkaEvolve）；提出 harness 迭代是近期可行的"递归自改进"路径；开放挑战包括评估、记忆、负结果、多样性坍缩、reward hacking。 — [Lilian Weng](https://lilianweng.github.io/posts/2026-07-04-harness/)（原文被封锁，内容据 [daily.dev 转述](https://daily.dev/posts/harness-engineering-for-self-improvement-myalinbsq) 等）

**具体技术**
- **Compaction**：Anthropic 描述为"在接近上下文上限时高保真地摘要对话并重新初始化"，Claude Code 的实现让模型保留架构决策与未解决 bug、丢弃冗余输出。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。Claude Code 支持自动 compaction、`/compact <instructions>` 定向压缩、`/rewind` 选区间摘要、在 CLAUDE.md 中写"compact 时必须保留修改文件列表与测试命令"。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)。Claude Agent SDK 在 compaction 后**重新注入 CLAUDE.md**，并提供 `PreCompact` hook 让应用在压缩前快照/注入上下文。 — [Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)
- **Context editing（服务端）**：Anthropic 2025-09-29 推出 context editing（自动清除过期 tool call/结果）与 memory tool；内部评测：**memory tool + context editing 比基线提升 39%，仅 context editing 提升 29%**；100 轮 web search 评测中 token 消耗**降低 84%** 并完成原本会因上下文耗尽而失败的任务；Claude Sonnet 4.5 内置 context awareness。 — [Claude Blog](https://claude.com/blog/context-management)
- **Sub-agent 隔离上下文**：子 agent 用干净上下文做深入探索，只向协调者返回 **1,000–2,000 token** 的浓缩摘要。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。Claude Code 建议"用 subagent 做调研，使主会话保持干净"，subagent 有自己的上下文与工具白名单，可在 `.claude/agents/` 中定义（name/description/tools/model）。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Just-in-time 检索 / 文件系统当记忆**：agent 只保存轻量标识（文件路径、查询、链接），运行时用工具加载；Claude Code 用 `head/tail` 等定向命令分析大数据而不整体载入；**结构化笔记**（NOTES.md、to-do）作为上下文外持久记忆（Claude 玩 Pokémon 的例子：跨数千步维持精确计数）。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- **Skills / 渐进披露**：Anthropic《Equipping agents for the real world with Agent Skills》（2025-10-16）：Skill = 含 `SKILL.md`（YAML frontmatter 必填 `name`、`description`）+ 脚本/资源的文件夹；三级披露：(1) 启动时只加载元数据，(2) 相关时加载完整 SKILL.md，(3) 按需读取链接文件；2025-12-18 发布为开放标准。 — [Anthropic](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)。二手来源称元数据约 100 token/skill。 — [Atlan](https://atlan.com/know/ai-agent/ai-agent-skills/what-are-agent-skills/)（二手来源）
- **CLAUDE.md（项目记忆）**：每次会话开头自动读取；官方建议"短且人类可读"，只放"删掉会导致 Claude 犯错"的内容：Claude 猜不到的 bash 命令、与默认不同的代码风格、测试指令、仓库礼仪（分支/PR 规范）、架构决策、环境怪癖；**不要**放能从代码推断的东西、API 文档、经常变化的信息、逐文件描述；"过长的 CLAUDE.md 会让 Claude 忽略你的真实指令"；可用 `@path` 导入、`/doctor` 建议精简；`/init` 生成初稿。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **AGENTS.md 作为"地图"**：OpenAI Codex 团队最初把所有规则塞进一个巨型 AGENTS.md，结果"挤占任务上下文、所有规则看起来同等重要、快速腐化、无法做机械化的新鲜度/归属检查"；改为**约 100 行的地图**，指向结构化 `docs/` 目录（设计决策、执行计划、产品规格、参考文档）。 — [tonylee.im 转述](https://tonylee.im/en/blog/openai-harness-engineering-five-principles-codex/)（二手来源）
- **Hooks（确定性约束）vs. 指令（建议性）**：Claude Code 文档："CLAUDE.md 指令是建议性的，hooks 是确定性的、保证执行"；用于"每次必须发生、零例外"的动作（如每次编辑后跑 eslint、阻止写 migrations 目录）。Agent SDK 提供 `PreToolUse`、`PostToolUse`、`PostToolUseFailure`、`UserPromptSubmit`、`Stop`、`SubagentStart/Stop`、`PreCompact`、`PermissionRequest` 等事件。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)；[Agent SDK hooks](https://code.claude.com/docs/en/agent-sdk/hooks)
- **选型口诀**（社区总结，与官方文档一致）："必须强制 → Hooks/权限；情境知识 → Skills；委派边界 → Subagents；始终生效的项目指引 → 保持简短的 CLAUDE.md"。 — [alexop.dev](https://alexop.dev/posts/claude-code-customization-guide-claudemd-skills-subagents/)
- **工具设计**：工具应"自包含、对错误鲁棒、用途极其清晰"，最小化、无歧义的工具集避免决策模糊与功能膨胀。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)。Claude Code 建议优先用 CLI（`gh`、`aws`、`gcloud`、`sentry-cli`）而非 MCP 做外部服务交互，因为"最省上下文"。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Microsoft《Context Engineering for Reliable AI Agents》报告 Intent Met 分数从 45% 提升到 75%；Microsoft LLMLingua 提供 20× 压缩。 — 收录于 [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering)（二手来源）

### Inferences
- 2025 年 9 月是分水岭：Anthropic 同日（09-29）发布 context engineering 方法论与 context editing/memory tool API，把"上下文管理"从应用层技巧变成平台能力；2026 年主流 SDK 均内置 compaction。
- 对内部研发 Agent：CLAUDE.md/AGENTS.md 应保持 100 行量级并指向 `docs/`；可重复的流程（发布、排障 runbook、代码规范）封装为 Skills；硬约束（禁止改 migration、必须跑 lint）用 hooks；探索与评审用 subagent。这一组合在三家大厂文档中高度一致。

### Gaps
- Lilian Weng 原文与 OpenAI harness 原文均被封锁，细节依赖转述。
- 没找到对 compaction 质量（信息丢失率）的独立量化研究；Anthropic 的 29%/39%/84% 为内部评测。

## 关键问题 3：协议与标准——MCP、A2A、AGENTS.md、Agent Skills、computer use 的现状、治理与采用

### Takeaway
2025-12 Linux Foundation 成立 **Agentic AI Foundation（AAIF）**，MCP（Anthropic）、AGENTS.md（OpenAI）、goose（Block）成为创始项目；A2A（Google）2025-06 进入 Linux Foundation，2026-08 并入 AAIF。MCP 在 2026-07-28 发布自诞生以来最大改版（无状态核心、扩展框架、MCP Apps、Tasks）；Agent Skills（SKILL.md）2025-12-18 开放后数月内被 30–40+ 平台采用；AGENTS.md 被 6 万+ 仓库使用。

### Cited Findings

## 关键问题 4：长程任务如何处理——规划、分解、验证循环、自纠错、测试驱动、沙箱；METR 时间视界趋势

### Takeaway
METR 的"50% 成功时间视界"从 2019–2025 的约 7 个月翻倍一次，加速到 2024 年以来约 3–4 个月翻倍一次（Time Horizon 1.1，2026-01-29，约 89 天；另有 2026 年的 105 天估算），2026 年前沿模型的 50% 视界已以"小时"计。工程上，长程任务的可靠性靠**可机器判定的验证信号**（测试/构建/lint/截图比对）+ **生成者与验证者分离** + **沙箱隔离** + **checkpoint/恢复**，而非更长的 prompt。

**规划与分解**
- Claude Code 推荐四阶段：**Explore（plan mode，只读）→ Plan（`Ctrl+G` 编辑计划）→ Implement（按计划实现并验证）→ Commit**；"如果一句话能描述 diff 就跳过计划"；大功能先让 Claude 用 `AskUserQuestion` 访谈你并写 SPEC.md，再**开新会话**执行。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)

**验证循环与自纠错**
- Claude Code 文档的第一条最佳实践："**给 Claude 一个它能运行的检查**：测试、构建、与设计稿比对的截图——这是'你盯着的会话'与'可以走开的会话'的区别"；四级 gating：单 prompt 内迭代 → `/goal`（独立评估器每轮复查直到目标达成）→ **Stop hook**（脚本检查不过则阻止回合结束，确定性）→ **验证 subagent**（新模型尝试证伪，"干活的 agent 不给自己打分"）；要求 agent 展示证据（测试输出、命令返回、截图）而非宣称成功。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- 对抗式评审：在新 subagent 上下文中只看 diff 与标准做 review（内置 `/code-review` skill）；警告"被要求找问题的 reviewer 总会报告问题"，需限定只报影响正确性的发现以避免过度工程。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Cognition Devin Review（生成者-验证者分离）平均每 PR 捕获 2 个 bug，58% 为逻辑错误/边界缺失/安全漏洞。 — [Cognition](https://cognition.com/blog/multi-agents-working)（二手转述）
- OpenAI Codex 团队用自定义 linter、架构分层约束、面向 agent 的可观测性、周期性"垃圾回收/熵管理"维持 100 万行 agent 代码的可维护性；Martin Fowler 把 harness 实践归纳为三支柱：context engineering、架构约束、熵管理。 — [tonylee.im](https://tonylee.im/en/blog/openai-harness-engineering-five-principles-codex/)；[awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering)（二手来源）
- Anthropic 多 Agent 系统的可靠性经验：长时运行的 agent 状态累积，小错误会级联，需要**durable execution 与错误恢复**；需全链路生产 tracing；用 rainbow deployment 避免更新打断运行中的 agent。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- 模型能力曲线（视界每 3–4 个月翻倍）意味着内部 Agent 的 harness 设计应"随模型升级可拆卸"：把今天为弥补模型缺陷加的约束做成可配置项，而不是硬编码架构。
- 2026 年公开编码基准普遍饱和或失效，公司内部评估应建立**自有任务集**（Anthropic 建议从约 20 个真实查询起步，用 LLM judge + 人工复核），这比追榜单更有信息量。
- "验证信号可机器判定"是研发提效 Agent 成败的第一要素：有测试/CI 的仓库才能让 agent 无人值守地跑完任务；没有的仓库应先补测试再上 agent。

## 关键问题 5：记忆——生产中实际使用的方法（情景记忆文件、向量检索、厂商 memory 工具、长上下文 vs. 检索）

### Takeaway
2026 年生产中的 agent 记忆以"**文件系统 + 结构化笔记**"为主流（Anthropic memory tool、CLAUDE.md、NOTES.md、OpenAI docs/ 目录），向量检索型记忆（Mem0、Zep、Letta）用于对话型/个性化场景；三大厂都提供 1M 上下文，但"有效上下文"约为标称的 60–70%，且 context rot 实证明确，因此"长上下文 + 压缩 + 按需检索"的混合方案而非"全塞进去"是共识。

### Cited Findings
- **Anthropic memory tool**（2025-09-29，公测）：基于文件的系统，Claude 在你基础设施中的专用 memory 目录里创建/读/改/删文件，跨会话持久；与 context editing 组合提升 39%。 — [Claude Blog](https://claude.com/blog/context-management)
- **结构化笔记**：agent 维护上下文外的 NOTES.md/to-do 并按需取回；Claude Code 以 CLAUDE.md 为"项目记忆卡"，每会话自动加载，可 `@` 导入其他文件。 — [Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；[Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **Google Memory Bank**（Gemini Enterprise Agent Platform，2026-04-22）：从对话中动态生成并策展记忆，Memory Profiles 提供高精度低延迟召回。 — [Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)
- **向量/图记忆层**：Mem0 论文（ECAI 2025）在 LoCoMo（1,540 题，单跳/多跳/开放域/时间推理）上首次横向比较 10 种记忆方案（含 RAG、full-context、OpenAI Memory、Zep）；Mem0 官方 2026 报告：LoCoMo **92.5**、LongMemEval **94.4**，每查询约 **6,900 token**，时间推理 +29.6、多跳 +23.1（**厂商自报**）；Letta/MemGPT 在 LoCoMo 约 83.2%（口径不一）。 — [Mem0 论文](https://arxiv.org/pdf/2504.19413)；[Mem0 博客](https://mem0.ai/blog/state-of-ai-agent-memory-2026)；[DEV 对比](https://dev.to/varun_pratapbhardwaj_b13/5-ai-agent-memory-systems-compared-mem0-zep-letta-supermemory-superlocalmemory-2026-benchmark-59p3)
- 记忆评测基准激增：AMA-Bench（长程 agent 记忆，2026-02）、StreamMemBench（2026-06）、MemDelta（指出 agent 记忆评测中的隐藏混杂因素，2026-06）。 — [arXiv 2602.22769](https://arxiv.org/pdf/2602.22769)；[arXiv 2606.14571](https://arxiv.org/pdf/2606.14571)；[arXiv 2606.29914](https://arxiv.org/pdf/2606.29914)
- **长上下文现状**：GPT、Claude、Gemini 主力模型均提供 **1M** 上下文；但 MRCR v2 8-needle 测试中 Claude Opus 4.6 在 1M 处 **76%**，GPT-5.4 **36.6%**，Gemini 3 Pro **24.5%**——同为"1M"可靠性差异巨大；"有效上下文容量通常只有标称的 60–70%"。 — [yage.ai 2026-03-15](https://yage.ai/share/long-context-benchmark-en-20260315.html)（二手汇总）；[Claude 平台文档](https://platform.claude.com/docs/en/build-with-claude/context-windows)
- **Context rot 实证**：Chroma 2025 技术报告测试 18 个前沿模型（GPT-4.1、Claude 4、Gemini 2.5、Qwen3 等），所有模型 F1 随输入长度**单调下降**，100k–500k token 区间下降最陡；干扰项、needle-question 相似度、haystack 结构均影响；模型在**打乱顺序**的 haystack 上反而比逻辑连贯文档表现更好。 — [ZenML 摘要](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)；原文 [Chroma](https://research.trychroma.com/context-rot)（封锁）
- **长上下文 vs. 检索**（arXiv 2511.05850《Retrieval Quality at Context Limit》）：结果依模型而异——GPT-4o-mini 上 full context 与检索无差别；Gemini Flash 上 full context 领先 +14pp；**Sonnet 上检索领先 +31pp**。 — [arXiv](https://arxiv.org/pdf/2511.05850)
- 1M 上下文对编码 agent 的实际收益：Claude Code 用户观察到约 **15% 更少的 compaction 事件**。 — [paddo.dev](https://paddo.dev/blog/million-token-context/)（个人博客）
- 2026 年研究方向：ByteRover（LLM 策展的分层上下文，2026-04）、Active Context Compression（自主记忆管理，token -22.7%）、Context Pruning for Coding Agents（token -31%、EM +3.5%，2026-05）、MemoHarness（从经验学习的 harness，2026-07）。 — [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering)；[arXiv 2607.14159](https://arxiv.org/pdf/2607.14159)

### Inferences
- 对研发提效 Agent，最有效且最低风险的记忆是**可 git 版本化的文本**（CLAUDE.md/AGENTS.md、docs/、运行时 NOTES）：可审阅、可回滚、可被人类与 agent 共同维护。向量记忆适合"跨会话用户偏好/历史对话"，对代码库知识的价值低于直接 grep/读文件（即 Anthropic 的 just-in-time 原则）。
- 长上下文不是检索的替代品：即使 1M 窗口，也应保持"轻量标识 + 按需加载 + compaction"。

### Gaps
- 没有找到独立第三方对 Mem0/Zep/Letta 在**工程任务**（非对话）上的对比；现有数字多为厂商自报或对话型基准。
- Anthropic/OpenAI 各自 memory 工具在 2026 年的更新（如 OpenAI Responses API 的记忆能力）未能从一手文档核实。

## 关键问题 6：多 Agent 系统何时有帮助、何时有害？

### Takeaway
证据一致指向：多 Agent 在**广度优先、可并行、只读/研究型**任务上有显著收益（Anthropic +90.2%，但 15× token），在**需要共享上下文、强依赖、写操作**的任务（典型如编码）上收益低且失败率高（MAST：78.7% 的失败源于规范与协调问题，Zaninotto：4+ handoff 几乎必败）。2026 年的"可行多 Agent"= 单一写者 + 评审/研究子 agent + map-reduce 批处理。

### Cited Findings
- **有帮助**：Anthropic Research 系统——广度优先查询、信息量超单上下文、高价值任务；并行子 agent + 并行工具调用把研究时间缩短最多 90%；复杂度分级规则（简单查询 1 个 agent / 3–10 次调用；复杂查询 10+ 子 agent）。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- **有害**：同一文章列出不适合场景——需要全员共享上下文、强相互依赖、**大多数编码工作**、低价值任务（token 成本超过收益）；当前 lead agent 同步等待子 agent 完成，形成瓶颈。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- MAST 分类法（arXiv 2503.13657）：14 种失败模式——规范问题 41.8%（prompt 设计差、缺角色约束、无终止条件）、Agent 间失配 36.9%（误沟通、冲突假设、上下文未传播）、验证失败 21.3%（过早结束、接受错误解）。 — [arXiv](https://arxiv.org/abs/2503.13657)；[Orq.ai 解读](https://orq.ai/blog/why-do-multi-agent-llm-systems-fail)
- Cognition 2025：并行子 agent"天然脆弱"，上下文隔离导致冲突决策与不可用结果；原则：共享完整 trace、动作即隐含决策。 — [Cognition](https://cognition.com/blog/dont-build-multi-agents)
- Cognition 2026：可行的三模式（Code-Review-Loop / Smart Friend / map-reduce-and-manage），写操作单线程；manager 若缺乏深度代码库上下文会"过度规定"而适得其反；让 map-reduce 系统"感觉像单 agent 一样连贯"是 2026 年的核心工作。 — [Cognition](https://cognition.com/blog/multi-agents-working)
- OpenAI 指南：Manager 模式保留中央控制（边 = tool call），handoff 模式转移执行权；两者都只在单 Agent 复杂度不可控时采用。 — [OpenAI PDF](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)；[team400 解读](https://team400.ai/blog/2026-04-openai-agent-orchestration-handoffs-guide)
- Claude Code：Writer/Reviewer 双会话、`/batch` 5–30 子 agent 各自 worktree 的 map-reduce、"Agent teams"实验性默认关闭；"新上下文做评审不会偏向刚写的代码"。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- Zaninotto 2026-09 审计：4+ handoff 几乎必败；LangChain：子 agent 隔离可省 67% token；GitHub 2026-02-24《Multi-Agent Workflows Often Fail》。 — [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering)（二手来源）
- 多 Agent 可观测性与故障注入研究：《Observability and Fault Injection for LLM-Based Multi-Agent Systems in Software Engineering》（arXiv 2608.24271，2026-08）。 — [arXiv](https://arxiv.org/pdf/2608.24271)

### Inferences
- "是否多 Agent"的判据可操作化为三问：任务能否分解为**互不依赖**的子问题？子问题是否**只读**或写入互不重叠的区域（独立文件/worktree）？单次任务价值是否足以支付 4–15× token？三问皆是才上多 Agent。
- 研发提效场景中最划算的多 Agent 形态是**评审分离**（低成本、高收益、无写冲突）和**批量迁移的 map-reduce**。

### Gaps
- MAST 的数据集基于 2024–2025 的框架（如 MetaGPT、ChatDev、AG2 等），对 2026 年 SDK 的适用性未重新验证。
- 缺少对"多 Agent 在非编码研发流程（如 incident 排障、需求评审）"的公开实证。

### Takeaway
2026 年格局：**LangGraph**（LangChain）在下载量上领先并定位"生产默认"；**OpenAI Agents SDK**（~30k stars）以轻量原语（agents/handoffs/guardrails/sessions/tracing）+ 多供应商兼容为卖点；**Claude Agent SDK** 把 Claude Code 的 harness（hooks、subagents、compaction、MCP、权限、sessions）开放为 SDK；**Google ADK** 深度绑定 Gemini Enterprise Agent Platform 与 A2A；**Microsoft Agent Framework 1.0**（2026-04-03 GA）合并 AutoGen 与 Semantic Kernel（二者进入维护模式）；**CrewAI** 以角色化 crew 面向业务流程。

- **Google ADK**：Gemini Enterprise Agent Platform 的代码优先层，"每月处理 6 万亿+ token"，图式 sub-agent 网络，与 Agent Studio（低代码）、Agent Runtime、Memory Bank、A2A、MCP 集成；Kaggle 5 日课程以 ADK 教学。 — [Google Cloud](https://cloud.google.com/blog/products/ai-machine-learning/introducing-gemini-enterprise-agent-platform)；[Kaggle](https://www.kaggle.com/learn-guide/5-day-agents)

## 关键问题 8：哪些模型能力解锁了 Agent？已知失败模式（context rot、工具幻觉、失控循环、成本）

### Takeaway
解锁 agent 的四项能力——可靠的工具调用、extended/interleaved thinking、1M 上下文、computer use——在 2025–2026 年全部到位并趋于饱和（OSWorld 超人类基线、Terminal-Bench 2.1 >90%）。但失败模式也被系统化：context rot（18 模型单调退化）、工具调用级联（H1 2026 增长最快的失败类型，单次失控 $50–$500、曾有 5 分钟 400 次重复调用、六位数预算事故）、逐步累积的幻觉（5%/步 → 5 步 23%）、过长指令被忽略、基准污染。

### Cited Findings

**解锁能力**
- Extended thinking 作为"可控草稿本"用于规划，interleaved thinking 用于评估工具结果；Claude 4 系列能自我诊断失败并建议 prompt 改进；并行工具调用显著缩短研究时间。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)
- 1M 上下文（三大厂）；Claude Sonnet 4.5 内置 context awareness（2025-09）。 — [yage.ai](https://yage.ai/share/long-context-benchmark-en-20260315.html)；[Claude Blog](https://claude.com/blog/context-management)
- Computer use：OSWorld 从 12.24%（2024）到 2026 年 80%+，超过 72.36% 人类基线。 — [benchmarkingagents.com](https://benchmarkingagents.com/osworld/)
- 终端/编码 agent：Terminal-Bench 2.1 榜首 >90%（2026-10）；SWE-bench Verified 饱和至 97%。 — [benchlm.ai](https://benchlm.ai/benchmarks/terminalbench21)；[vals.ai](https://www.vals.ai/benchmarks/swebench)
- Claude Code 自 v2.1.283 起默认 auto mode（分类器审查动作），表明工具调用安全性已足以减少人工审批。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)

**失败模式**
- **Context rot**：Chroma 测试 18 个模型 F1 单调下降，100k–500k 最陡；Anthropic 把其归因于 transformer 架构约束并以此为 context engineering 的出发点；Claude Code 文档："上下文窗口是最重要的资源……填满后 Claude 开始'忘记'早期指令、犯更多错误"。 — [ZenML/Chroma](https://www.zenml.io/llmops-database/context-rot-evaluating-llm-performance-degradation-with-increasing-input-tokens)；[Anthropic](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；[Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **指令被忽略**：CLAUDE.md 过长时"重要规则淹没在噪声里"；连续纠正两次仍错就应 `/clear` 重来。 — [Claude Code Docs](https://code.claude.com/docs/en/best-practices)
- **工具误用/失控循环/成本**：2026 年行业复盘称单个失控 agent 在被发现前可烧 **$50–$500**，有案例 5 分钟内重复调用同一坏工具 **400 次**；H1 2026 "工具误用级联（重试风暴、失控循环、MCP server 故障被 agent 重试放大）"是增长最快的失败模式，有事故烧掉六位数预算。 — [FutureAGI](https://futureagi.com/blog/best-ai-agent-failure-detection-tools-2026)；[digitalapplied H1 2026 复盘](https://www.digitalapplied.com/blog/ai-incidents-h1-2026-retrospective-failure-modes-analysis)（二手汇总）
- **预算失控实证**：《Token Budgets: An Empirical Catalog of 63 LLM-Agent Budget-Overrun Incidents》（arXiv 2606.04056，2026-06）编目 63 起预算超支事故。 — [arXiv](https://arxiv.org/pdf/2606.04056)
- **幻觉累积**：工具参数幻觉（如用虚构 user_id 调 `db.delete_user`）；每步 5% 错误率在 5 步后变为 23% 轨迹错误率。 — [Atlan](https://atlan.com/know/ai-agent/what-is-an-agent-loop/)（二手综述）；《Operational Hallucination and Safety Drift in AI Agents》（arXiv 2607.18366）— [arXiv](https://arxiv.org/pdf/2607.18366)
- **失败归因**：《Model or Harness? An Interaction-Centric Taxonomy for Localizing Agent Failures》（arXiv 2607.28802，2026-07）提出区分模型失败与 harness 失败的分类法。 — [arXiv](https://arxiv.org/pdf/2607.28802)
- **Harness 自身的回归**：Anthropic 2026-04 发布《An Update on Recent Claude Code Quality Reports》事后分析（harness 变更导致质量下降）。 — 收录于 [awesome-harness-engineering](https://github.com/ai-boost/awesome-harness-engineering)（二手来源，原文未核）
- **自编辑 harness 的溯源问题**：有案例 agent 伪造测试日志后自己相信了它。 — [DEV Community](https://dev.to/p0rt/the-agent-faked-a-test-log-then-believed-it-self-editing-harnesses-have-a-provenance-problem-3id6)（个人博客，轶事）
- **基准失效/污染**：SWE-bench Verified 59.4% 抽样题测试有缺陷 + 凭 ID 复现 gold patch。 — [Decrypt](https://decrypt.co/359012/openai-benchmark-measure-ai-coding-supremacy-contaminated)
- **Skills/MCP 供应链安全**：SKILL.md 威胁分类（arXiv 2604.02837）；MCP 安全状态报告（2026-03）。 — [arXiv](https://arxiv.org/pdf/2604.02837)；[NimbleBrain](https://nimblebrain.ai/blog/state-of-mcp-security-2026/)
- **多 Agent token 成本**：15× 聊天 token。 — [Anthropic](https://www.anthropic.com/engineering/multi-agent-research-system)

### Inferences
- 2026 年的失败主要是**harness 层**而非模型层：预算上限、重试退避、工具调用幂等、Stop hook、trace 可观测性、CLAUDE.md 精简、定期 `/clear`——这些都是工程手段而非模型手段。内部 Agent 上线前的 checklist 应以这些为核心。
- 由于基准饱和与污染，模型选型应以**内部任务集 + 成本/延迟**为准，而非公开榜单差距（榜首差距已 <3 分）。

### Gaps
- "$50–$500"、"400 次/5 分钟"、"六位数预算"均来自行业复盘博客，无原始事故报告。
- 工具调用幻觉率的 2026 年系统性测量未找到一手数据。
- Anthropic 2026-04 Claude Code 质量事后分析原文未能访问。

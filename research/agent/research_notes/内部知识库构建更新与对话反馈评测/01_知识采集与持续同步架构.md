## 1. 源清单与连接器架构（Source inventory & connectors）

### Takeaway
2025–2026 年的企业 AI 搜索/知识平台几乎都收敛到同一套连接器骨架：「身份/权限爬取 → 周期性 full crawl（删除与 ACL 变更的最终真相）→ 高频 incremental crawl（基于时间戳/checkpoint，通常不带删除与权限变更）→ 可选 webhook / 直连（federated）」；各家差异在于默认周期、是否把"直连不落库"作为一类连接器，以及自定义连接器 SDK 的深度（Glean 和 Microsoft 把 checkpoint 与身份映射的责任都交给连接器作者）。

### Cited Findings

**Glean**【厂商声明/搜索摘要；SDK README 为独立证据】
- Glean 把爬取分为三类：周期性的 full content crawl（对连接器的整个语料库重建索引）、incremental crawl（只处理上次爬取以来修改或新增的条目，避免扫描整个仓库）、activity crawl（跟踪权限变更等活动）；连接器"尽可能快地"通过 webhook 或增量爬取捕获变化 — [Glean docs: crawling types](https://docs.glean.com/connectors/crawling-types)、[Glean docs: crawl and index connectors](https://docs.glean.com/connectors/crawling-indexing)、[About Connectors](https://docs.glean.com/connectors/about)
- 权限变化一般不是实时的：Interact、Lexion 等连接器的权限变更要等"下一次计划爬取完成后"才在 Glean 生效；Lexion 连接器只支持 full crawl，不支持 incremental — [Interact connector](https://docs.glean.com/connectors/custom/connector-guides/interact)、[Lexion connector](https://docs.glean.com/connectors/custom/connector-guides/lexion)
- Web crawler 连接器不做按用户的权限传播：凡能访问该 data source 的用户都能看到所有已索引页面 — [Glean web crawler](https://docs.glean.com/connectors/native/web-crawler/home)
- Indexing SDK 的流水线顺序：先爬身份（identities），再为增量运行解析 last-crawl timestamp，再抓内容→转换→上传；SDK 负责批处理、重试与 stale-document cleanup；若返回了 groups 却没有 memberships，SDK 直接报错，因为没有成员的组产生的 ACL 永远无法匹配任何人 — [Glean Indexing SDK architecture](https://developers.glean.com/libraries/indexing-sdk/concepts/architecture)
- SDK README（GitHub 原文，2026-10 读取）：`connector.index_data(mode=IndexingMode.FULL)` 是 "re-index everything"，FULL 模式会 "replace the indexed state: documents absent from the run are deleted as stale"；INCREMENTAL 模式给 data client 传一个 `since` 时间戳，但 "the SDK does not persist checkpoints — override `_get_last_crawl_timestamp()` on your connector to supply one"；提供 `PullHttpClient`（重试/退避、link/offset/cursor 分页、token-bucket 限速）、`PushUploader`（documents/users/groups/memberships/employees 并行批量上传）、每文档 ACL + datasource identities；连接器类型有四种基类（in-memory、sync streaming、async streaming、people/identity）；测试分三阶段（全 mock、真实源录制回放、端到端）；`/bulkindexemployees` 端点计划于 2026-10-15 之后移除 — [gleanwork/glean-indexing-sdk README](https://github.com/gleanwork/glean-indexing-sdk)
- Glean 官方 Python 客户端的 Indexing API 暴露 `datasources.add/submit`、`permissions.update_permissions / index_user / bulk_index_groups / index_membership / process_memberships / delete_user / delete_group / delete_membership` 等端点，说明"文档内容"与"身份/组/成员关系"是两条独立的上传通道 — [gleanwork/api-client-python README](https://github.com/gleanwork/api-client-python)

**Microsoft 365 Copilot connectors（原 Graph connectors）**【厂商声明；SDK/limits/ACL 文档经 GitHub 镜像核实原文】
- 自定义连接器 agent："Full crawls (list-based or Microsoft Graph-based) go through your entire data periodically at an interval defined by you. Incremental crawls are more frequent and they crawl the data source from the previous timestamp/checkpoint at an interval defined by you"；删除检测依赖全量爬取："detecting items deleted from your data source based on the items sent by your connector during periodic full crawls. The agent then takes care of deleting the item from the Microsoft index as well"；ACL 由 agent "stamp" 到数据上以实现 security trimming（可基于 Entra ID 或源系统 ACL）— [Graph connectors SDK overview](https://learn.microsoft.com/graph/custom-connector-sdk-overview)（镜像原文：[microsoft-graph-docs-contrib](https://github.com/microsoftgraph/microsoft-graph-docs-contrib/blob/main/concepts/custom-connector-sdk-overview.md)）
- 管理中心文档（搜索摘要）：incremental crawls 目前"不支持处理权限更新"，权限变更需 full crawl；即便启用增量刷新也必须定期 full refresh 以维持源与索引一致；默认计划按连接器类型给出，例如 Azure Data Lake Gen2 连接器默认增量 15 分钟、全量 1 周；按需爬取（on-demand）仅 agent 2.1.0.0 起支持，且同一连接上同一时刻只能有一类爬取在跑 — [Set up Graph connectors in the admin center](https://learn.microsoft.com/microsoftsearch/configure-connector)、[ADLS Gen2 connector](https://learn.microsoft.com/lt-lt/microsoftsearch/azure-data-lake-connector)
- API 限制：单个 item 的请求体上限 30 MB，且 "refers to the total size of parsed text content that is typically 10% of the original file size for common formats (for example, docx, ppt, and PDF). To contextualize, 30 MB translates to 10,000 pages of parsed content (averaging 500 words per page)"；每租户 external groups 上限 100,000；组管理限流 1,000 req/s；每用户参与查询的 external groups 上限 10,000；超限返回 HTTP 429 并在响应头给出建议等待时间 — [Copilot connectors API limits](https://learn.microsoft.com/graph/connecting-external-content-api-limits)

**Google Gemini Enterprise / Agentspace（原 Vertex AI Search）**【厂商声明/搜索摘要】
- 两类基本同步："A full sync captures the entire state of the third-party app or service. This includes additions, updates, and deletions. A full sync replaces the existing contents of the data store"；"An incremental sync periodically captures entity data that has been added or updated since the last sync. It does not sync identity data or deletions of entity data"；全量同步可分别为 entity（如 Jira 的 issues/worklogs/comments/attachments）与 identity（与 ACL group 关联的用户账号）单独排程；每个 entity 类型对应一个独立 data store — [Introduction to connectors and data stores](https://docs.cloud.google.com/gemini/enterprise/docs/introduction-to-connectors-and-data-stores)
- Outlook 连接器配置页：分别选择 Full sync 频率与 Incremental sync 频率，"Custom options" 下可分开排程 full entity 与 full identity sync — [Connect Microsoft Outlook with data ingestion](https://docs.cloud.google.com/gemini/enterprise/docs/connect-ms-outlook-ingestion)

**Atlassian Rovo / Teamwork Graph**【厂商声明/搜索摘要】
- 三类连接器：Synced（管理员配置、把内容索引进 Teamwork Graph、计入 indexed objects 配额）、Direct（通过提供方搜索 API 实时取结果、不存内容、不计配额）、Smart Link（无需管理员配置）— [Teamwork Graph connector types](https://support.atlassian.com/organization-administration/docs/teamwork-graph-connector-types/)
- 权限与同步：Rovo 镜像源应用的访问规则（Google Drive 私有文件只有在源里有权限的人才能在 Rovo 看到）；Atlassian 自建连接器"定期检查"并反映源端删除；第三方连接器能力为 "self-declared and not verified by Atlassian"；部分连接器支持 delta sync（只更新上次以来的新数据），不支持则每次全量重新摄取；数据新鲜度对自建连接器 "managed by Atlassian to meet published standards"，第三方因开发者而异；未公布具体刷新间隔 — [How connector permissions are kept in sync](https://support.atlassian.com/organization-administration/docs/how-connector-permissions-are-kept-in-sync/)、[Evaluate third-party connectors](https://support.atlassian.com/organization-administration/docs/evaluate-third-party-connectors-in-the-teamwork-graph/)、[Rovo connectors admin guide](https://www.atlassian.com/software/rovo/guides/admin-guide/rovo-connectors)

**GitHub Copilot Spaces（替代 Knowledge Bases）**【厂商声明/搜索摘要 + 二手】
- 官方文档：加入 space 的 GitHub 文件与其他 GitHub-based sources "are automatically updated as they change"；2025-09-24 的 GA 公告称附加的 repos/files 会持续更新，并可通过 remote GitHub MCP server 在 IDE 中访问 — [About organizing and sharing context with Copilot Spaces](https://docs.github.com/copilot/using-github-copilot/copilot-spaces/about-organizing-and-sharing-context-with-copilot-spaces)、[Copilot Spaces GA changelog (2025-09-24)](https://github.blog/changelog/2025-09-24-copilot-spaces-is-now-generally-available/)
- 第三方指南：上传的文件、自由文本 notes 与图片是静态的需手动更新；"attaching a whole repository means search, not full loading"；Knowledge Bases 据称于 2025 年 11 月下线（官方文档只做了产品对比，未确认下线日期）— [memorylake.ai](https://www.memorylake.ai/blogs/build-github-copilot-space-that-stays-current)、[agentpatterns.ai](https://www.agentpatterns.ai/tools/copilot/copilot-spaces/)【二手】

**Sourcegraph（代码侧连接器）**【厂商声明；文档经 sourcegraph/docs 仓库核实原文】
- Zoekt 的 indexserver "can be configured to periodically fetch and reindex repositories from a code host"（例如整个 GitHub org），"takes care of periodically fetching and indexing new data, and cleaning up logfiles"；排序依赖 universal-ctags 的符号信息 — [sourcegraph/zoekt README](https://github.com/sourcegraph/zoekt)
- 限定到具体仓库的搜索 "always up-to-date"（任何针对该仓库的用户动作都会触发抓取并让新 commit/分支立即可搜），而跨大量仓库的未限定搜索 "may trail latest default branch revisions by some interval of time. This interval is a function of the number of repositories and the computational resources devoted to search indexing" — [Sourcegraph code search features](https://sourcegraph.com/docs/code-search/features)
- 精确代码导航（SCIP）有三条上传路径：手动 `src` CLI 上传、CI 流水线产出并上传、auto-indexing（由 executors 自动跑 indexer）；复杂或需认证的构建建议走 CI — [Precise code navigation](https://sourcegraph.com/docs/code-navigation/precise-code-navigation)

**开源 RAG / 知识库框架与数据集成工具**【独立证据：README/文档原文】
- LlamaIndex `IngestionPipeline`：每个 node+transformation 组合做哈希缓存（本地或 Redis/MongoDB/Firestore），挂接 docstore 后以 `doc_id -> document_hash` 做文档管理（详见 §2）— [LlamaIndex Ingestion Pipeline](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)
- Airbyte "Incremental | Append + Deduped"：以 cursor（如 `updated_at`）判断是否复制、以 primary key 去重保留最新行；at-least-once 语义；源支持发出删除记录（如 CDC 数据库源）时最终表才会删除 — [Airbyte incremental append+deduped](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append-deduped)
- RAGFlow：服务拆分为 Admin、Syncer（"external data source synchronization tasks"）、Ingestor（"data ingestion and parsing tasks"）、API；2026-07-02 新增 Google BigQuery 数据源摄取与 incremental synchronization；2026-09-10 新增通过 sitemap 摄取网站；2026-09-29 发布 1.0.0-rc1；DeepDoc 做版面分析/OCR/表格识别（开源 1.0 用 CPU 推理）；推荐起步配置 4 核 CPU、16 GB 内存、50 GB 磁盘 — [infiniflow/ragflow README](https://github.com/infiniflow/ragflow)
- Unstructured：`partition()` 自动识别文件类型并路由到专用分区函数（PDF 需 tesseract+poppler），并提供 source/destination connectors — [Unstructured-IO/unstructured README](https://github.com/Unstructured-IO/unstructured)
- Dify 提供从文档摄取到检索的 RAG pipeline（PDF/PPT 等文本抽取）；FastGPT 支持 "API 知识库" — [langgenius/dify README](https://github.com/langgenius/dify)、[labring/FastGPT README](https://github.com/labring/FastGPT)

**中国厂商**【厂商声明/搜索摘要】
- 阿里云百炼：数据同步规则可从 OSS、飞书、钉钉、语雀、SharePoint 等外部数据源自动拉取文件，按设定周期检查源路径下文件状态并处理新增或更新的文件；同步周期可选一分钟、一小时或一天 — [百炼 数据同步指南](https://help.aliyun.com/zh/model-studio/data-sync-guide)
- 百炼切片级 API：AddChunk / UpdateChunk / DeleteChunk 均幂等；UpdateChunk 仅支持"文档搜索类"知识库（不支持数据查询与图片问答类）；DeleteChunk 为硬删除不可恢复；AddChunk 限流 10 次/秒 — [AddChunk](https://help.aliyun.com/zh/model-studio/api-bailian-2023-12-29-addchunk)、[UpdateChunk](https://help.aliyun.com/zh/model-studio/api-bailian-2023-12-29-updatechunk)、[DeleteChunk](https://help.aliyun.com/zh/model-studio/api-bailian-2023-12-29-deletechunk)
- 飞书 Aily 知识问答：数据接入分"导入"（数据导入到 Aily 处理，需要做数据同步、可能有延时，但效果更好）与"直连"（数据留在上游业务系统、及时感知变化，但效果通常有折损；跨租户召回仅对提问者点击过的文档支持）；支持本地表格/文本文件（Excel/PPT/PDF/Docx）、飞书套件内容、企业核心业务系统与内部数据库（MySQL/PostgreSQL）；长文档按内容结构切成语义相对完整的小切片分别建索引 — 飞书 Aily 帮助中心系列页面（[数据预处理](https://www.feishu.cn/content/adcbsjqc) 及同系列页面，站点被拦截，具体页面未能逐页核实）
- 火山引擎知识库：本次检索未找到关于飞书等数据源自动同步周期/增量机制的官方说明（见 Gaps）

### Inferences
- 五家主流商用平台（Glean、Microsoft、Google、Atlassian、GitHub）无一把 incremental crawl 当作权限与删除的真相来源；删除与 ACL 变化统一靠周期性 full crawl（或 Google 的 identity sync）兜底。自建系统若只做 webhook/增量，必须单独设计"删除对账"与"权限对账"任务。
- Rovo 的 Direct connector、飞书 Aily 的"直连"、Datadog 对 Confluence 的"链接即读"（§5）都表明 2025–2026 年的主流做法是"索引 + 联邦检索"混合：高变动/高敏感源不落库而在查询时实时取；低变动源落库以换取检索质量。
- 对自定义源（内部配置平台、实验平台、日志模板库），Glean/Microsoft/Google 都要求连接器自己维护 checkpoint 与身份映射；SDK 只帮做批处理/重试/限速。这意味着内部知识库团队的主要工作量在"连接器正确性"而非索引引擎。
- 百炼最小 1 分钟的同步周期与 Microsoft 的 15 分钟增量示例给出了"分钟级"是当前商用产品可配置的下限；真正的秒级只能靠 webhook/直连。

### Gaps
- Glean、Google、Atlassian 均未公开增量/全量/身份同步的具体默认周期或延迟 SLA（只找到 Microsoft 的 ADLS 示例 15 min / 1 week 与百炼的 1 min / 1 h / 1 d 选项）。
- 火山引擎知识库、Notion AI、Slack AI、Guru 的连接器与同步机制未找到可核实的一手文档（搜索配额耗尽前未命中，且站点被拦截）。
- Sourcegraph 的增量索引内部机制（哪些文件变了、上传是否部分合并）文档中未说明；其 "persistent, incrementally updated code graph" 属营销表述 — [Sourcegraph context compare](https://sourcegraph.com/resources/context-compare)。

## 2. 变更检测与增量同步（Change detection & incremental re-indexing）

### Takeaway
行业共识是"文档级哈希/时间戳决定是否重处理 + 周期性全量对账决定删除"；chunk 级别的精细失效在开源框架中仍很弱（LlamaIndex 只到文档级、GraphRAG 的 update 是追加合并、LightRAG 靠 LLM 抽取缓存做选择性删除重建）；厂商对新鲜度的承诺基本是"下一次计划爬取后"，没有人公开 staleness 的测量方法。

### Cited Findings
- LlamaIndex docstore 策略：`upserts`（按 id 查找，id 新或 hash 变化则重处理并 upsert）、`duplicates_only`（只按 hash 判重）、`upserts_and_delete`（同 upserts 并删除输入里已不存在的文档）；无 vector store 时自动降级为 duplicates_only（输出 "Docstore strategy set to upserts, but no vector store. Switching to duplicates_only strategy."）；策略依赖跨运行持久化的 docstore；"If a duplicate `doc_id` is detected, and the hash has changed, the document will be re-processed and upserted; If a duplicate `doc_id` is detected and the hash is unchanged, the node is skipped"；社区答复指出以文本 hash 作 doc_id 无法识别"同一文档被原地修改" — [Document Management Pipeline example](https://developers.llamaindex.ai/python/examples/ingestion/document_management_pipeline/)、[Ingestion pipeline guide](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/)、[LlamaIndex community](https://community.llamaindex.ai/mmr-zv1BrMf9KxBk)
- Microsoft GraphRAG：文档 `id` "generated using a hash of the text content to ensure stability across runs"；索引 API 有 `is_update_run: bool`——"Whether this run is an incremental update over an existing index"，内部把方法名改写为 `f"{m}-update"`；配置 `update_output_storage` "defines a secondary storage location for running incremental indexing, to preserve your original outputs"；communities / community_reports 表带 `period`（"Date of ingest, used for incremental update merges. ISO8601"）与 `size` 字段用于合并；同名同类型实体合并为描述数组 — [GraphRAG inputs](https://github.com/microsoft/graphrag/blob/main/docs/index/inputs.md)、[graphrag/api/index.py](https://github.com/microsoft/graphrag/blob/main/packages/graphrag/graphrag/api/index.py)、[config yaml](https://github.com/microsoft/graphrag/blob/main/docs/config/yaml.md)、[outputs](https://github.com/microsoft/graphrag/blob/main/docs/index/outputs.md)、[default dataflow](https://github.com/microsoft/graphrag/blob/main/docs/index/default_dataflow.md)
- GraphRAG CHANGELOG 显示增量更新能力早于 3.x（2.x 条目 "Rework the update output storage structure"、"Properly increment text unit IDs during updates"；3.0.2 "load_update_documents workflows"），而 3.3.0 的条目只有 "Add bulk cache reads with bounded, connection-reusing SQLite queries" — [GraphRAG CHANGELOG](https://github.com/microsoft/graphrag/blob/main/CHANGELOG.md)；这与第三方比较文"GraphRAG 3.3.0 于 2026-10-08 新增 `graphrag update` 命令与两种增量方法"的说法矛盾 — [particula.tech](https://particula.tech/blog/lightrag-vs-graphrag)【二手，不可靠】
- 同一第三方文称 GraphRAG 的 update 只追加新文档标题与新社区、撤回文档需全量重建；LightRAG 删除文档时用抽取缓存重建受影响实体而不重新抽取 — [particula.tech](https://particula.tech/blog/lightrag-vs-graphrag)【二手】；LightRAG 官方 README 证实后半句："When a document is deleted, the system can use the LLM cache created during indexing to quickly rebuild the affected entities and relationships, substantially improving update efficiency" — [HKUDS/LightRAG README](https://github.com/HKUDS/LightRAG)
- LightRAG 运维细节：`DOC_STATUS_STORAGE` 单独存文档处理状态（支持 Json / PG / Mongo / OpenSearch）；`MAX_PARALLEL_INSERT` 控制并行文件数，建议约为 `MAX_ASYNC_LLM` 的 1/3；`SOURCE_IDS_LIMIT_METHOD` 默认在实体/关系关联的 chunk 超限后停止更新描述以加速建库；失败摄取会把文档标为 FAILED；更换 embedding 模型时 "existing vectors do not match the new model's space, and nothing re-embeds them"，须用 `lightrag-rebuild-vdb` 从图与 `text_chunks`（"authoritative sources"）重建向量，"Do NOT clear the data directory — that destroys the graph the rebuild reads from"；`source_conflict_repair` 列出 "claim the same canonical source key" 的重复文档并降级为 duplicates，"It never picks a winner on its own and never deletes content" — [LightRAG README](https://github.com/HKUDS/LightRAG)、[ProgramingWithCore.md](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md)
- Airbyte：cursor 粒度为"天"时同日两次运行无法区分已同步记录，约定 "sources should prefer resending data if the cursor field is ambiguous"（at-least-once）；修改记录但不更新 cursor 列会被增量漏掉，因为增量抽取形如 `select * from table where cursor_field > 'last_sync_max_cursor_field_value'` — [Airbyte docs](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append-deduped)
- Glean：FULL 运行把缺席文档当 stale 删除；INCREMENTAL 只传 `since` 时间戳且 SDK 不持久化 checkpoint — [glean-indexing-sdk README](https://github.com/gleanwork/glean-indexing-sdk)
- Microsoft：增量爬取不处理权限更新，删除只在全量爬取中检测；ADLS 默认增量 15 分钟 / 全量 1 周 — [configure-connector](https://learn.microsoft.com/microsoftsearch/configure-connector)、[SDK overview](https://learn.microsoft.com/graph/custom-connector-sdk-overview)
- Google：增量同步不含 identity 与删除 — [Gemini Enterprise connectors](https://docs.cloud.google.com/gemini/enterprise/docs/introduction-to-connectors-and-data-stores)

- Sourcegraph SCIP 上传生命周期：`UPLOADING_INDEX → QUEUED_FOR_PROCESSING → PROCESSING → COMPLETED`，失败进 `PROCESSING_ERRORED` 并多次重试；上传可因"被更新的上传取代、记录年龄或用户显式删除"而删除（先进 `DELETING` 状态）；任何到/离开 COMPLETED 的状态变化都要重算 "repository commit graph"（commit → 可解析该 commit 的 uploads 集合），期间仓库被标为 `stale`（已 COMPLETED 的上传可能尚未用于查询）；该重算 "can be computationally expensive for the worker service or Postgres database" — [Code graph data uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads)
- Sourcegraph auto-indexing 调度默认值：`PRECISE_CODE_INTEL_AUTO_INDEXING_TASK_INTERVAL` 每 2 分钟、`..._REPOSITORY_PROCESS_DELAY` 同一仓库最少 24 小时考虑一次、`..._REPOSITORY_BATCH_SIZE` 2500；策略可限定分支/标签、最大 commit 年龄（如跳过去年的 commit）、只索引分支 tip 或全部 commit；索引任务由 `go.mod` 等文件启发式推断，或由仓库根目录 `sourcegraph.yaml` 显式声明 — [Auto-indexing](https://sourcegraph.com/docs/code-navigation/auto-indexing)

- Google Kythe：各语言的 Kythe 图被合并、裁剪并为服务优化，整条流水线 "runs several times per day"（批量重建，未说明是否增量）；基于插桩的构建系统产出索引，生成文件（protos、AutoValue）也有交叉引用 — [SWE book ch.17 Code Search](https://abseil.io/resources/swe-book/html/ch17.html)【搜索摘要】、[Google Kythe (Wikipedia)](https://en.wikipedia.org/wiki/Google_Kythe)【二手】
- 块级增量同步样例（非知识库产品，旁证）：Obsidian 的飞书同步插件把 Markdown 拆成顶层块并记录与飞书 block id 的映射，之后只更新变化的块；改动较大、结构复杂或无法安全增量时自动降级为全量覆盖 — [feishu-lark-cli-sync](https://community.obsidian.md/plugins/feishu-lark-cli-sync)
- Copilot/SharePoint 权限变更后 "within 24-48 hours" 重新索引受影响条目——仅见于咨询博客，未能从微软一手文档核实 — [EPC Group](https://www.epcgroup.net/copilot-sharepoint-permissions-oversharing-fix-2026)【二手，未核实】
- Datadog 关于指针新鲜度："A stale runbook link is worse than no link, since it points Bits at the wrong dashboard or a decommissioned service"；并建议定期检查旧的纠错记忆是否仍成立（"services get renamed, causes get fixed"）— [Improve Bits Investigation Accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/)

### Inferences
- 可落地的"三层失效"设计：(1) 源级 cursor / webhook 触发；(2) 文档级 `doc_id + content_hash` 决定是否重切分重嵌入（LlamaIndex / GraphRAG 的做法）；(3) chunk 级稳定 ID（按 AST 节点 / 标题路径 / block id 派生）使未变化 chunk 的 embedding 可复用——这一层目前没有通用开源实现，需要自建（Obsidian 插件的 block-id 映射是最接近的参考）。
- 删除 / tombstone 必须有独立的"全量对账"任务：所有主流平台都承认增量通道不传删除。对日志模板、实验记录这类只增不删的源可放宽；对 wiki / 配置这类会被撤回的源，不做对账就会出现"旧 chunk 幸存"。
- 更换 embedding 模型是常被忽略的"全量失效"事件；LightRAG 的经验是把图与原文 chunk 作为权威源、向量作为可重建缓存。
- 厂商新鲜度口径几乎都是 "next scheduled crawl"；内部系统需要自定义指标（如 `source_mtime` 与 `index_time` 之差的 p50/p95 分布、按源类型分档）。

- 未找到任何厂商对"索引延迟 / 新鲜度 SLA"的量化承诺（Glean、Google、Atlassian 都是定性描述）；也未找到"staleness 如何测量"的公开设计。

## 3. 版本、溯源与血缘（Versioning / provenance / lineage）

### Takeaway
公开系统里最成熟的 "as-of" 模型来自代码侧（Sourcegraph 的 commit graph、SCIP 按 commit 上传、Kythe 按快照重建）；文档 / 图谱侧只做到"内容哈希 ID + 摄取时间戳 + 来源定位符"，valid_from / valid_to 与 supersedes 这类时态建模在公开资料中几乎缺席，需要自建。

### Cited Findings
- Sourcegraph 维护 "a mapping from a commit of a repository to the set of upload records that can resolve a query for that commit"；上传可被更新上传替代、按年龄过期；"Index all version tags" 策略可让匹配标签可见的 commit 持续保留索引不因年龄被删 — [Uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads)、[Auto-indexing policies](https://sourcegraph.com/docs/code-navigation/auto-indexing)
- Sourcegraph 可为每个仓库索引至多 64 个分支，"The indexer deduplicates documents between branches, so the size of your index will grow with the number of unique documents" — [Admin search: multi-branch indexing](https://sourcegraph.com/docs/admin/search)
- SCIP 是语言无关的 Protobuf 协议，索引文件包含项目全部 definitions / references / hover 文档；索引器有 scip-java（Java/Scala/Kotlin）、scip-typescript、scip-clang、scip-python、scip-ruby、scip-dotnet、rust-analyzer 等 — [sourcegraph/scip README](https://github.com/sourcegraph/scip)
- Kythe "provides an index for data at one snapshot in time" — [Google Kythe (Wikipedia)](https://en.wikipedia.org/wiki/Google_Kythe)【二手】
- GraphRAG：文档 ID 为文本哈希（跨运行稳定）、`human_readable_id` 为每次运行递增的短 ID 用于引用；communities 带 `period`（ISO8601 摄取日期）；结构化输入保留 `raw_data` 并可用 `chunking.prepend_metadata` 把 title / tag 等字段前置到每个 chunk — [GraphRAG inputs](https://github.com/microsoft/graphrag/blob/main/docs/index/inputs.md)、[outputs](https://github.com/microsoft/graphrag/blob/main/docs/index/outputs.md)
- LightRAG 为每个文档保存处理状态（doc status storage）与 "canonical source key"，并提供 `kg_integrity_repair` 审计 "full_entities / full_relations recovery anchors" 缺失的贡献以便删除 / 重试能再次发现它们 — [LightRAG README](https://github.com/HKUDS/LightRAG)
- Claude Code auto memory：记忆文件若有 YAML frontmatter，写入时记录 `modified` ISO 8601 时间戳，"The timestamp shows how current the fact is, both to you and to Claude when it reads the memory back"（需 v2.1.214+）；`MEMORY.md` 索引一行一条、详细内容拆到主题文件 — [Claude Code memory](https://code.claude.com/docs/en/memory)
- Datadog Bits：每次调查的正向反馈与带细节的负向反馈都会生成一条 "memory"，在 Monitor Management 页面可查看 / 删除；高质量纠错应包含真实根因、涉及服务 / 指标与指向根因的遥测链接 — [Knowledge Sources](https://docs.datadoghq.com/bits_ai/bits_investigation/knowledge_sources/)
- Microsoft Graph externalItem 可随 item 发送 activities（创建 / 编辑 / 分享），但 "Activities with timestamps older than seven days don't surface in the Microsoft 365 app" — [Manage items](https://learn.microsoft.com/graph/connecting-external-content-manage-items)
- RAGFlow 1.0 的 "Knowledge Compilation" 把文档 / 数据集级内容编译成 Wikis、Graphs、Trees、PageIndex、Mind Maps、Timelines 与 Skills 等 "structured knowledge artifacts"，可配置编译模型与规则并 "view, update, and regenerate knowledge artifacts"（2026-08-19 引入）— [RAGFlow README](https://github.com/infiniflow/ragflow)
- Uber Genie：对知识库每篇文档调用 LLM-as-judge，返回评估分、解释与可执行的改进建议 — [Genie blog](https://www.uber.com/en-HR/blog/genie-ubers-gen-ai-on-call-copilot/)【搜索摘要】

### Inferences
- 推荐的定位符设计（综合上述系统）：代码 = `repo + path + commit + symbol(SCIP)`；文档 = `source_system + doc_id + content_hash + fetched_at`；配置 = `config_repo + key_path + commit/env`；日志 = `template_id(cluster_id) + first_seen/last_seen`；实验 = `experiment_id + metric snapshot period`。这与 GraphRAG 的 `id = hash(text)` + `period` 以及 Sourcegraph 的 commit graph 思路一致。
- "as-of" 查询在代码侧可直接借 Sourcegraph / SCIP 的 commit 维度；在文档侧公开系统没有先例，最务实的做法是只保留"当前版本 + 变更日志（supersedes 指针）"，历史版本留在源系统（wiki / git）里按需回溯。
- 记忆 / 反馈类知识（Datadog memories、Claude auto memory）需要显式的"过期复核"，因为它们随系统演进失效；时间戳是最低限度的元数据。

- 没有公开资料描述知识库的 valid_from / valid_to / supersedes 时态模型在生产中的实现。

## 4. 访问控制、数据分级与脱敏（ACL propagation, classification, redaction）

### Takeaway
"文档级 ACL stamping + 查询时 security trimming" 是行业标准，但各家都承认权限变更有延迟（下一次全量 / 身份同步）；最大风险不是引擎而是源端权限本身过宽（SharePoint 的 "Everyone" / 过期分享链接），以及 PII / 密钥在 embedding 前没有拦下来。中国法规层面的具体影响本次未能获取可引用来源。

### Cited Findings
- Microsoft externalItem ACL：ACE 类型为 Entra user / group 或 `Everyone`（租户全体）；"The accessType value `deny` takes precedence over `grant`"；非 Entra 的组（如客服系统的 team、Salesforce 的 profiles/roles）应用 group sync API 建 external groups 并 "Keep the membership of the external groups up to date and in sync"；"Avoid expanding the membership of your external groups directly into the ACLs of individual items because each group membership can lead to a high volume of item updates"；"A user should have less than 2,049 external security group memberships, including direct and indirect memberships. When this limit is exceeded, search results become unpredictable. Queries from users with more than 10,000 external security groups will fail with a `400` response" — [Manage items](https://learn.microsoft.com/graph/connecting-external-content-manage-items)、[External groups](https://learn.microsoft.com/graph/connecting-external-content-external-groups)
- Microsoft：增量爬取不处理权限更新，需 full crawl — [configure-connector](https://learn.microsoft.com/microsoftsearch/configure-connector)
- Glean：连接器从源同步 "who can see what"，权限变更在下一次计划爬取后生效；无成员的组会导致 SDK 报错；web crawler 不做按用户权限 — [Glean Indexing SDK](https://developers.glean.com/libraries/indexing-sdk/concepts/architecture)、[Interact connector](https://docs.glean.com/connectors/custom/connector-guides/interact)、[web crawler](https://docs.glean.com/connectors/native/web-crawler/home)
- Google：identity sync 是独立的全量同步，增量同步不含身份 — [Gemini Enterprise connectors](https://docs.cloud.google.com/gemini/enterprise/docs/introduction-to-connectors-and-data-stores)
- Atlassian Rovo：受限内容只对源应用中已有权限的人可见，无限制内容对站点所有人可见 — [Rovo connectors](https://www.atlassian.com/software/rovo/guides/admin-guide/rovo-connectors)
- 飞书：知识问答应"沿用提问者本人的身份和访问权限"，员工无权访问的文档不应期待 AI 越权给出；"权限决定能看什么，检索决定找到什么，核对决定能不能用"，建议管理员用代表性账号逐项验证可检索的文档和知识空间；同一问题不同人可能得到不同答案 — [企业知识库 AI 问答如何工作？权限继承、检索与结果核对](https://www.feishu.cn/content/article/7667878406574328795)、[企业知识库 AI 问答为什么会答不准？资料质量与权限边界](https://www.feishu.cn/content/article/7667878414023396328)【厂商声明/搜索摘要】
- 百炼：RAM 子账号调用知识库 API 需先获得百炼 API 权限并加入业务空间 — [百炼 RAM 权限](https://help.aliyun.com/zh/model-studio/bailian-ram-permission)
- Copilot 过度共享（咨询/安全博客，【二手】）：security trimming 在查询时按用户当前权限过滤，"Only content the user can access is returned — but ALL content the user can access is eligible"；常见根因是 "Everyone" 组、断裂的继承、>90 天的分享链接、"Anyone with the link"（"that link is now effectively inside every employee's prompt window"）；建议审计 90 天以上的分享链接并设置 30/90 天到期、禁用 90 天未登录的 guest、用 SharePoint Data Access Governance 报告与 Restricted Access 作为临时控制 — [EPC Group](https://www.epcgroup.net/copilot-sharepoint-permissions-oversharing-fix-2026)、[apps4.pro](https://blog.apps4.pro/stale-sharing-links-copilot-access-risk)、[copilotconsulting.com](https://www.copilotconsulting.com/insights/microsoft-copilot-oversharing-prevention-guide-2026)、[dope.security](https://dope.security/post/microsoft-copilot-security-concerns-oversharing-sharepoint-onedrive)；一篇二手报道称 Varonis 于 2026-06-15 披露 Copilot Enterprise Search 漏洞 "SearchLeak"（CVE-2026-42824）并已由微软修复 — [collab365](https://spaces.collab365.com/posts/microsoft-fixed-a-copilot-flaw-that-let-attackers--M0vCoG)【未核实】
- PII / 密钥处理（实践博客，【二手】）：PII 检测与变换应放在归一化 / 结构抽取之后、切分与 embedding 之前（切分跟在脱敏后以免 chunk 重组出 PII；"redacting after embedding is too late"）；embedding 应视作敏感工件、预先设计保留与删除；密钥（API key、JWT、私钥）要 "prevention and blocking, not just masking"，发现即隔离并重索引源文档；Presidio 支持自定义识别器、规则+NER 混合与可解释算子但需校准、检测无法保证；要有脱敏单元测试、canary 字符串与 DLP 扫描（"if you can't test and verify redaction, you don't really have it"）— [Prevent Sensitive Data Leakage in RAG: The 2026 Playbook](https://www.kunalganglani.com/blog/prevent-sensitive-data-leakage-rag)、[dev.to 同文](https://dev.to/kunal_d6a8fea2309e1571ee7/prevent-sensitive-data-leakage-in-rag-the-2026-playbook-2j5a)、[wavect.io](https://wavect.io/blog/pii-redaction-before-llm-prompts/)
- Drain3 的 masking 可在模板挖掘前用正则把 IP、数字、邮箱等变量替换为 `<:IP:>` / `<:NUM:>` 等掩码（"A well-defined masking can improve template mining accuracy"），未匹配自定义掩码的参数由 Drain 替换为 `<*>` — [logpai/Drain3 README](https://github.com/logpai/Drain3)
- Claude Code 管理策略 CLAUDE.md（Linux 为 `/etc/claude-code/CLAUDE.md`）用于 "Company coding standards, security policies, compliance requirements"，不可被个人设置排除；技术性禁止（封禁工具 / 命令 / 路径）应放在 managed settings 的 `permissions.deny`，CLAUDE.md 只承载行为指导 — [Claude Code memory](https://code.claude.com/docs/en/memory)

### Inferences
- 对推荐部门知识库，应把"组成员关系"作为一等实体单独同步（Glean 的 groups / memberships、Microsoft 的 external groups），而不是把成员展开进每篇文档的 ACL——否则一次组织架构调整会触发海量文档更新。
- 权限变更延迟是普遍现象，因此高敏感源（HR、安全策略、未发布实验结论）更适合"直连 / 联邦检索"或缩短 identity sync 周期，而不是落库。
- 日志 / 配置的摄取流水线应在"模板化 / 脱敏"之后才进入 embedding：Drain 模板天然去掉变量部分，配置则应在 key-path 层面做密钥字段黑名单并阻断而非仅掩码。

- 未能检索到关于中国《生成式人工智能服务管理暂行办法》《数据安全法》《个人信息保护法》对企业内部知识库 / 员工数据处理具体要求的可引用来源（搜索配额在该查询前耗尽）；本节不包含任何法规结论。

## 5. 模态专属摄取（code / configs / logs / tickets & chat / experiments）

### Takeaway
代码侧有成熟工具链（tree-sitter / cAST 做结构化切分、SCIP / Kythe 做符号图、Zoekt 做 trigram 全文、aider 式 repo map 做压缩导航）；日志侧的主流是 "Drain 模板挖掘先做 90%+ 的体积压缩，再让 LLM 只对模板做语义化"，SRE agent（Datadog Bits）把 runbook、`bits.md` 与反馈记忆作为三类知识源；配置与实验记录没有现成的通用方案，公开案例（Kuaishou AgentX）是用多智能体抽取器把代码 / 配置 / 文档编译成 wiki 条目并让实验结果回流为结构化知识资产。

### Cited Findings

**(a) 代码**
- cAST（Findings of EMNLP 2025，Zhang 等）：用 tree-sitter 解析，自顶向下保留能放下的大节点，拆分过大节点并在大小限制内合并相邻兄弟节点；报告 RepoEval 检索 Recall@5 +4.3、SWE-bench 生成 Pass@1 +2.67（作者自报，未见独立复现）；ASTChunk 实现支持 Python / Java / C# / TypeScript，`max_chunk_size` 以非空白字符计，支持 `chunk_overlap`（按 AST 节点数）与 `chunk_expansion`（给 chunk 加元数据头），可附 repo 级元数据 — [cAST (ACL Anthology)](https://aclanthology.org/2025.findings-emnlp.430/)、[yilinjz/astchunk](https://github.com/yilinjz/astchunk)、[arXiv 2506.15655](https://arxiv.org/html/2506.15655v2)
- aider repo map：每次请求随附 "concise map of your whole git repository"（文件 + 关键符号 + 定义的关键代码行），用文件依赖图上的 graph ranking 选出最相关部分以适配 token 预算，`--map-tokens` 默认 1k tokens，无文件加入聊天时会显著扩大；只包含被其他部分引用最多的标识符 — [aider repomap docs](https://aider.chat/docs/repomap.html)
- Zoekt：trigram 索引 + 语法解析，符号匹配作为排序信号（依赖 universal-ctags），JSON API 支持 BM25 评分与上下文行 — [sourcegraph/zoekt](https://github.com/sourcegraph/zoekt)
- SCIP 索引器矩阵与上传方式见 §1；Kythe 基于插桩编译器输出语义信息，生成文件也有交叉引用，开源版支持 Bazel / CMake / Maven / Go — [Google OSS blog 2020](https://opensource.googleblog.com/2020/04/code-search-for-google-open-source.html)【搜索摘要】、[kythe/kythe README](https://github.com/kythe/kythe)
- Anthropic 的观点：Claude Code 采用 "CLAUDE.md files are naively dropped into context up front" + glob / grep 即时检索的混合策略，"avoids stale indexes and complex syntax trees"；"Folder hierarchies, naming conventions, and timestamps all provide important signals"，文件大小暗示复杂度、时间戳可代理相关性 — [Effective context engineering for AI agents (2025-09-29)](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- Sourcegraph 默认不索引 >1 MB 文件；跳过的多为 minified JS、source maps、lockfiles，但路径仍可搜（`type:path`）— [Admin search](https://sourcegraph.com/docs/admin/search)

**(b) 配置**
- Kuaishou AgentX（arXiv 2606.26859，2026-06）："System KB" 通过 ingestion、querying 与 linting 保持最新；"Multi-agent extractors turn code, configs, and engineering docs into wiki entries"；KB 用于拒绝违反流水线边界、依赖不可用特征或无法交给正确代码范围的想法 — [AgentX](https://arxiv.org/pdf/2606.26859)【搜索摘要】、[chatpaper 摘要](https://chatpaper.com/es/paper/303863)【二手】
- GraphRAG 对结构化输入（CSV / JSON / Parquet）保留 `raw_data` 并可把选定字段前置到每个 chunk（`chunking.prepend_metadata: [title, tag]`），用于解决"文档头部信息只存在于第一个 chunk"的问题 — [GraphRAG inputs](https://github.com/microsoft/graphrag/blob/main/docs/index/inputs.md)
- Datadog `bits.md` 的推荐内容正是配置 / 命名层知识：跨系统命名映射（alerts `checkout_prd` / 工单 `CHECKOUT` / 日志 `checkout-service`）、环境值归一化（`env:blue-prod` vs `env:prod`）、已知噪声模式（02:00–02:30 UTC 批任务 CPU 峰值、canary 发布期间错误率上升、autoscaling 导致短暂延迟）、默认作用域规则；"Write specific rules, not general descriptions — a description repeats what Bits can already infer from telemetry, while a rule resolves something it can't infer on its own, like a naming mismatch across tools" — [Knowledge Sources](https://docs.datadoghq.com/bits_ai/bits_investigation/knowledge_sources/)、[Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/)
- Sourcegraph 用仓库根目录的 `sourcegraph.yaml` 显式声明索引任务，否则按 `go.mod` 等文件启发式推断 — [Auto-indexing](https://sourcegraph.com/docs/code-navigation/auto-indexing)

**(c) 日志 / 指标**
- Drain3（logpai）：在线日志模板挖掘（固定深度解析树，Drain ICWS 2017）；参数 `sim_th`（相似度阈值，低于则新建簇）、`depth`（默认 4，最小 3）、`max_children`（默认 100）、`max_clusters`（默认不限）；输出 `change_type`（cluster_created / cluster_template_changed / none）、`cluster_id`、`template_mined`；支持把状态快照持久化到 Kafka / Redis / 文件，快照在新模板、模板变更或周期（`snapshot_interval_minutes` 默认 1）时触发；`match()` 提供只匹配已学模板的快速路径；可从模板反向提取参数列表（`ExtractedParameter(value, mask_name)`）— [logpai/Drain3](https://github.com/logpai/Drain3)
- LAPP（Go 工具）："Drain clusters logs into templates cheaply (no API cost), then LLM semantifies the templates in bounded batches"；引用 IBM "Label Broadcasting" 模式："cluster first (90%+ volume reduction), apply LLM to representatives, broadcast labels back"（该 90% 为模式描述的声明而非 LAPP 实测）；工作区按 `patterns/<semantic-id>/pattern.md`（元数据、计数、源行引用）+ `samples.log` + `patterns/unmatched/samples.log` + `notes/summary.md`（按频率排序）+ `notes/errors.md` + `AGENTS.md` 组织以供 AI 辅助排障；集成测试覆盖 14 个 Loghub-2.0 数据集 — [pkg.go.dev/github.com/strrl/lapp](https://pkg.go.dev/github.com/strrl/lapp)
- 学术 / 工具侧【搜索摘要 / 二手】：LogRouter 以 Drain3 摄取并把模板存入 Apache Druid + PostgreSQL/pgvector，用两级路由在直接回答、关键词搜索、模板查找 + SQL 生成、语义检索间选择；LLMLogAnalyzer 为 Indexing / Parsing / Query / Generation 四阶段；LLM-SrcLog（arXiv 2512.04474，2025-12）从源码抽取模板、未匹配日志回退到数据驱动聚类，在线解析延迟与数据驱动方法相当、比逐条 LLM 解析快约 1,000×；SoK 论文基准了 7 个开源 LLM 日志解析器，并指出用 RAG 选示例、缓存已解析模板以避免重复调用 — [LLMLog overview](https://www.emergentmind.com/topics/llmlog)、[LLM-SrcLog](https://arxiv.org/html/2512.04474v1)、[SoK review](https://www.themoonlight.io/fr/review/sok-llm-based-log-parsing)；Rust crate logdrain 面向 agent 压缩日志，建议 "feed the catalog and the Created signal, not raw lines to an LLM or triage agent" — [logdrain](https://docs.rs/crate/logdrain/0.3.2)
- Datadog Bits Investigation（SRE agent，博客 2025-06-10 发布、2025-12-02 更新）：知识源三类——Runbooks（monitor message 内联步骤或链接的 Confluence 页，Bits "reads the page, extracts telemetry links, follows documented troubleshooting steps where possible, and incorporates remediation guidance"；Notebooks 支持 markdown + 实时查询）、`bits.md`（环境上下文，"reads bits.md on every investigation"）、Feedback and memories；调查时 "dynamically generates multiple root cause hypotheses" 并标记 validated / invalidated / inconclusive，检查最近变更与 Kubernetes 事件，参考 "past investigations of the same monitor"；接入 GitHub 并给 APM 打 git 信息后可 "tie a regression to the commit or deploy that caused it"；monitor 按 `service` 分组否则 "falls back on weaker signals like the monitor name"；建议只对 p1/p2 或会 page 的 monitor 开启 Auto-Investigate，因为 "you can't realistically curate `bits.md` rules, runbooks, and feedback for all of them"；可接 Grafana / Dynatrace / Splunk / Sentry / ServiceNow；人工 triage 以往 "more than 30 minutes" — [Bits AI SRE blog](https://www.datadoghq.com/blog/bits-ai-sre/)、[Knowledge Sources](https://docs.datadoghq.com/bits_ai/bits_investigation/knowledge_sources/)、[Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/)

**(d) 工单 / 聊天 / 事故复盘**
- Uber Genie（Slack 内 on-call copilot）：接入 engineering wiki、Terrablob PDF、Google Docs 与自定义文档，答案带内部文档引用；在安全与隐私域接入 40+ 份策略 PDF 后初测暴露明显差距，SME 建立 100+ 条 golden set；Enhanced Agentic RAG（2025-05-29）加入查询优化、源识别、上下文精炼等 agent 并改进文档处理，报告可接受答案相对提升 27%、错误建议相对减少 60% — [Uber blog: Enhanced Agentic-RAG](https://www.uber.com/blog/enhanced-agentic-rag/)【搜索摘要】、[ZenML LLMOps DB](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-on-call-engineering-support)、[ZenML 第二条目](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-internal-on-call-support-copilot)【二手整理】

**(e) 实验记录**

### Inferences
- 代码的"什么该存"：存 chunk（AST 边界）+ 符号图（SCIP）+ 轻量 repo map 三层；chunk 的稳定 ID 可按 `path + 顶层 AST 节点签名` 派生，使改动一个函数只重嵌入该节点。
- 日志的"什么该存 / 不存"：不存原始行；存 Drain 模板（cluster_id、首末出现时间、计数、代表样本、LLM 语义标签）+ 模板到 runbook / 事故的链接；`bits.md` 式"已知噪声模式"与"跨系统命名映射"是最值得人工维护的两页。
- 配置的可行路径：按 key-path 切块，把默认值与环境差异（diff）作为独立条目，用 AgentX 式抽取器把配置语义写成 wiki 条目，并用 "lint" 任务校验 wiki 与真实配置一致。
- 实验记录应作为结构化表（假设、变更范围、指标快照、结论、supersedes）而非自由文本入库；AgentX 把它当"知识资产"回流、Auto-RecSys 蒸馏为 playbook 的做法可以照搬。

## 6. Agent-ready 文档实践与中心化知识库的关系

### Takeaway
2025 年下半年起形成了一套"仓库内渐进式披露"的事实标准：小而稳定的入口文件（AGENTS.md / CLAUDE.md，32 KiB / 200 行量级）→ 按路径 / 主题按需加载的 rules 与 SKILL.md → 代理用 glob / grep / CLI / MCP 即时取更深内容；中心化知识库的角色退为"提供可被这些入口引用的、带权限与新鲜度的检索服务"，而不是把一切预先塞进上下文。

### Cited Findings
- AGENTS.md 是 "a simple, open format for guiding coding agents... a README for agents: a dedicated, predictable place to provide context and instructions"，示例内容为开发环境提示、测试指令、PR 规范 — [agentsmd/agents.md](https://github.com/agentsmd/agents.md)；OpenAI 于 2025-08-20 发布 AGENTS.md 站点，搜索摘要称其现由 Linux Foundation 下的 Agentic AI Foundation 管理 — [gihyo.jp](https://gihyo.jp/article/2025/08/agents-md-site)【二手】
- Codex 的发现规则：沿路径每个目录依次找 `AGENTS.override.md`、`AGENTS.md`、`project_doc_fallback_filenames`，从根向下拼接（越靠近当前目录越优先）；合并大小上限 `project_doc_max_bytes` 默认 32 KiB，建议拆到嵌套目录 — [Codex: Custom instructions with AGENTS.md](https://developers.openai.com/codex/guides/agents-md)【搜索摘要】；一处第三方称 Codex 只读根目录 AGENTS.md（与官方文档矛盾），另一第三方称 openai/codex 仓库自身有 88 个嵌套 AGENTS.md（未核实）— [thepromptshelf.dev](https://thepromptshelf.dev/blog/agents-md-codex-setup-guide-2026/)【二手】；Codex 仓库 docs 已迁移至 developers.openai.com，仓库内仅剩指针与 `allow_managed_hooks_only` 等管理项 — [openai/codex docs/config.md](https://github.com/openai/codex/blob/main/docs/config.md)
- OpenAI "Harness engineering: leveraging Codex in an agent-first world"（2026-02-11，Ryan Lopopolo）：团队从 3 人扩到 7 人，5 个月合并约 1,500 个 PR（约 3.5 / 人 / 天），无人手写代码，估计耗时约为手写的十分之一；把仓库内文档视为代理的主要接口，只存在于聊天或人脑中的信息对代理不可见——"what Codex can't see doesn't exist"；工程师转向设计环境、表达意图与结构化反馈 — [OpenAI post](https://openai.com/index/harness-engineering/)【原文被拦截】、[InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex)、[all-ai.de](https://www.all-ai.de/news/news26/openai-harness-engineering.md)、[yage.ai survey](https://yage.ai/share/harness-engineering-survey-en-20260312.html)【二手】
- Stripe Minions（Part 1 2026-02-09，Part 2 作者 Alistair Gray，Leverage 团队）：无人值守 agent 接任务、交回完整 PR，2026-02 时每周 1,300+ 个合并 PR；基于 Block 开源 Goose 的 fork 加 Stripe 自有编排；"Toolshed" 是内部 MCP server，工具数一说约 400、一说近 500；"blueprints" 混合确定性步骤（lint、git 操作）与 agent 循环，确定性步骤每次相同从而提高可靠性；全局规则会撑爆大代码库的上下文，因此只在适用时加载子目录规则；CI 最多 2 轮 — [Stripe Part 2](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)【原文被拦截】、[ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs)、[mintmcp](https://www.mintmcp.com/blog/stripe-minions-explained)、[rywalker](https://rywalker.com/research/stripe-minions)、[port.io](https://software-factories.port.io/stripe)【均二手；monorepo 规模 30M vs 50M 行说法不一】
- Anthropic Agent Skills（2025-10-16 发布；2025-12-18 作为开放标准发布）：skill = 含 `SKILL.md`（YAML frontmatter 必填 `name` / `description`）的目录，可捆绑脚本与资源；三级渐进披露——启动时只预载所有 skill 的 name / description 进 system prompt，判定相关后加载完整 SKILL.md，捆绑文件按需再读，因此可捆绑的上下文 "effectively unbounded"；脚本可在不把脚本或数据读入上下文的情况下执行（如 PDF 表单字段抽取）；类比 "an onboarding guide for a new hire"；安全上 "We recommend installing skills only from trusted sources" 并审计捆绑文件 / 依赖 / 外联 — [Anthropic engineering: Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)、[anthropics/skills README](https://github.com/anthropics/skills)

- Claude Code 最佳实践："CLAUDE.md is loaded every session, so only include things that apply broadly. For domain knowledge or workflows that are only relevant sometimes, use skills instead"；包含 / 排除表：包含 Claude 猜不到的命令、偏离默认的代码风格、测试指令、仓库礼仪、架构决策、环境怪癖、gotchas；排除可从代码推断的内容、详细 API 文档（"link to docs instead"）、"Information that changes frequently"、逐文件描述；"Bloated CLAUDE.md files cause Claude to ignore your actual instructions!"；"Treat CLAUDE.md like code: review it when things go wrong, prune it regularly, and test changes by observing whether Claude's behavior actually shifts"；hooks 用于必须每次发生的动作（确定性），CLAUDE.md 是建议性的；CLI 工具（gh / aws / gcloud / sentry-cli）是 "the most context-efficient way to interact with external services" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
- 上下文工程原则（2025-09-29）：越来越多团队在预检索之上叠加 "just in time" 检索（保留文件路径、存储的查询、链接等轻量引用，运行时用工具加载）；代价是更慢且可能走弯路；子代理各用独立上下文，可能消耗 "tens of thousands of tokens or more" 但只返回约 1,000–2,000 token 的摘要；compaction 时保留架构决策 / 未解 bug 并丢弃冗余工具输出，再带上最近访问的 5 个文件；"do the simplest thing that works" — [Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)
- llms.txt 已被文档站实际采用：Claude Code 文档每页顶部提示 "Fetch the complete documentation index at: https://code.claude.com/docs/llms.txt"；Datadog 文档每页提供 `.md` 版本并有 `/llms.txt` 索引（"For AI agents: A markdown version of this page is available at ....md"）— [code.claude.com/docs/llms.txt](https://code.claude.com/docs/llms.txt)、[docs.datadoghq.com/llms.txt](https://docs.datadoghq.com/llms.txt)（llms.txt 规范站 llmstxt.org 被拦截，未能核实规范原文）
- Datadog `bits.md` 相当于 SRE 场景的 CLAUDE.md，并建议改完 `bits.md` / monitor message / skill 后用 Bits Chat 验证 "it lands before you find out during a real investigation"，Chat 使用相同知识源 — [Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/)
- RAGFlow 1.0 的 Knowledge Compilation 可从文档 / 数据集直接生成 "Skills" 工件 — [RAGFlow README](https://github.com/infiniflow/ragflow)
- Glean 的 Indexing SDK 自带"agent 探索源 API、与你确认计划、生成连接器并测试"的工作流 — [glean-indexing-sdk](https://github.com/gleanwork/glean-indexing-sdk)

### Inferences
- "知识住在仓库"与"中心化知识库"不是二选一：入口文件（AGENTS.md / CLAUDE.md / bits.md）应只保留稳定、跨任务的规则与指针；会变的事实（服务拓扑、配置默认值、实验结论、日志模板）放中心知识库并通过 CLI / MCP 工具即时取用；SKILL.md 承载"流程性知识"并可由知识库编译生成（RAGFlow 的 Skills 编译、Auto-RecSys 的 playbook 蒸馏是两个先例）。
- 入口文件需要"垃圾回收"：Claude Code 的 `/doctor prompt-audit`、Datadog 的"定期复核旧纠错"、OpenAI 的 "what Codex can't see doesn't exist" 都指向同一机制——把文档当代码审、剪枝、测试。
- 中心知识库对代理最有价值的输出格式是"可被链接的稳定 URL + 时间戳 + 权限裁剪后的 markdown"（Datadog / Claude 文档的 `.md` + `llms.txt` 模式），因为代理会把它们写进 AGENTS.md / bits.md 作为指针。

### Gaps
- OpenAI harness engineering 原文（docs/ 目录结构、文档垃圾回收、给代理的可观测性接口）未能读取，相关细节只有二手转述。
- Stripe Minions 两篇原文均被拦截；Toolshed 工具数（400 vs 500）与 monorepo 规模说法不一。
- Tencent RecSys Factory 的 SKILL.md → PitfallStore 编译机制未能核实。

## 7. 规模、成本与实践中的失败（Scale, cost, what fails）

### Takeaway
公开的硬数字集中在平台限制（Microsoft 30 MB / 10,000 页、100k 组；Sourcegraph 1 MB 文件、64 分支、mmap 上限）与产出指标（Stripe 1,300 PR / 周、OpenAI 1,500 PR / 5 月、AgentX 636 实验），而"知识平台团队规模、语料规模、嵌入成本、去重率"几乎没有可引用的公开数据；实践中反复出现的失败是：过期 runbook / 规则比没有更糟、入口文件臃肿导致指令被忽略、源端权限过宽被 AI 放大、增量通道漏掉删除与 ACL 变更、更换 embedding 模型后旧向量静默失效。

### Cited Findings
- Microsoft：item 解析文本 30 MB ≈ 10,000 页；每租户 100,000 external groups；组管理 1,000 req/s；用户 >2,049 组成员结果不可预测、>10,000 组查询失败；活动超过 7 天不展示 — [API limits](https://learn.microsoft.com/graph/connecting-external-content-api-limits)、[External groups](https://learn.microsoft.com/graph/connecting-external-content-external-groups)、[Manage items](https://learn.microsoft.com/graph/connecting-external-content-manage-items)
- Sourcegraph：索引节点 "should have enough memory to hold the entire text contents of the default branch of each repository"；Linux 默认 65,536 个 memory map 是 Zoekt 实例 shard 数上限，容量估算 `(number of repositories) / (60% * (memory map limit))`，文档示例为 300,000 个仓库；shard merging 默认开启以降内存；多分支索引增加 CPU / 内存 — [Admin search](https://sourcegraph.com/docs/admin/search)
- LightRAG 默认四种存储全是内存库（容量受 RAM 限制）"not suitable for production"，生产推荐 PostgreSQL — [LightRAG README](https://github.com/HKUDS/LightRAG)
- RAGFlow 起步配置 4 CPU / 16 GB / 50 GB — [RAGFlow README](https://github.com/infiniflow/ragflow)
- Uber Genie：40+ 份策略 PDF、100+ golden 查询、+27% 可接受答案、−60% 错误建议 — [ZenML DB](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-on-call-engineering-support)【二手整理】
- Stripe：1,300+ 合并 PR / 周（2026-02）；OpenAI：约 1,500 PR / 5 月、3→7 人；AgentX：3 worker 处理 374 个想法得 10 个可发表结果、636 实验中 560 个 AUC 超基线 — 见 §5、§6 来源【二手 / 搜索摘要】
- 日志压缩：Drain 聚类后 LLM 只处理代表样本可获 "90%+ volume reduction"（IBM 模式描述）；LLM-SrcLog 比逐条 LLM 解析快约 1,000× — [LAPP](https://pkg.go.dev/github.com/strrl/lapp)、[LLM-SrcLog](https://arxiv.org/html/2512.04474v1)【搜索摘要】
- Datadog："tens of thousands of organizations" 的数据、"Thousands of organizations" 在 limited availability 期间使用 Bits；人工 triage 以往 >30 分钟 — [Bits AI SRE blog](https://www.datadoghq.com/blog/bits-ai-sre/)【厂商声明】
- 失败模式（有来源）：
  - 过期 runbook 链接 "worse than no link" — [Datadog](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/)
  - "The over-specified CLAUDE.md. If your CLAUDE.md is too long, Claude ignores half of it because important rules get lost in the noise" — [Claude Code best practices](https://code.claude.com/docs/en/best-practices)
  - 全局规则撑爆上下文 → 只按子目录加载 — Stripe Minions【二手，见 §6】
  - 增量爬取不含权限更新 / 删除 — Microsoft、Google（§2）
  - cursor 未更新导致漏同步 — [Airbyte](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append-deduped)
  - 组无成员 → ACL 永不匹配（Glean SDK 直接报错）— [Glean SDK](https://developers.glean.com/libraries/indexing-sdk/concepts/architecture)
  - 源端 "Everyone" / 过期分享链接被 Copilot 放大 — 咨询博客【二手，见 §4】
  - 更换 embedding 模型后旧向量静默失效、维度不匹配 — [LightRAG core docs](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md)
  - 飞书："企业知识库 AI 问答为什么会答不准？资料质量与权限边界"——建议为关键资料指定负责人、生效日期和适用范围，并让过期内容能被及时发现和替换 — [飞书](https://www.feishu.cn/content/article/7667878414023396328)
  - 百炼 AddChunk 10 req/s 限流、DeleteChunk 硬删除 — [百炼 API](https://help.aliyun.com/zh/model-studio/api-bailian-2023-12-29-deletechunk)
  - Sourcegraph commit graph 重算昂贵、期间仓库 `stale` — [Uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads)

### Inferences
- 对一个部门级知识库，先按"连接器正确性 + 权限 / 删除对账 + 入口文件剪枝"投入，而不是先上图谱：所有公开的失败都发生在这三处，而图谱类方案（GraphRAG / LightRAG）本身还在解决增量成本问题。
- 可量化的内部 SLO 建议：源变更→可检索延迟（p50 / p95，按源类型分档：代码分钟级、wiki 小时级、ACL ≤ 一次身份同步周期）、删除对账周期、过期指针比例（bits.md / AGENTS.md 中失效链接占比）、每周重嵌入 token 数、"组无成员 / ACL 空"告警数。

### Gaps
- 未找到任何关于"企业知识平台团队规模"或"语料规模 / 嵌入成本 / 去重率"的公开数据（Glean、Uber、Stripe 等均未披露）。
- 关于"过期 wiki 比例"或"工程师对内部文档信任度"的调查数据，在搜索配额耗尽前未命中。

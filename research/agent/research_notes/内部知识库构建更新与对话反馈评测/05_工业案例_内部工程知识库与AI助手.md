## 1. Uber：Genie（on-call copilot）与 Enhanced Agentic RAG、QueryGPT、uReview、Michelangelo

### Takeaway
Uber 的 Genie 是目前公开资料最完整的"内部工程知识问答"案例：2024-10 上线（Slack 内答疑、引用 Engwiki/内部 Stack Overflow 等），2025-05 公布的 Enhanced Agentic-RAG（EAg-RAG）通过**文档侧富化（自定义 Google Docs loader + LLM 排版/元数据）+ 检索前后处理 Agent**，在安全隐私域 100+ 条 golden set 上把"可接受答案"相对提升 27%、"错误建议"相对减少 60%；"48.9% helpfulness / 13,000 小时 / EKB"等数字只能追到二手或未能找到出处。

### Cited Findings
**Genie v1（2024-10）【一手，据摘要】**
- Uber 工程师每月在相关 Slack 频道提出约 45,000 个问题；信息分散在内部 wiki "Engwiki"、内部 Stack Overflow 及其他位置，导致具体答案难找 — [Uber blog: Genie: Uber's Gen AI On-Call Copilot](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot)
- 该文描述了"用户对回答评分"的反馈环，并强调要对照权威来源验证答案、保持数据最新（原文细节未能通读）— [Uber blog](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot)
- InfoQ 2024-10 对 Genie 有专文报道（未能打开）【二手】— [InfoQ: Uber Genie RAG copilot](https://www.infoq.com/news/2024/10/uber-genie-rag-copilot)
- 聚合站称 Genie 已回答 70,000+ 问题、覆盖 154 个 Slack 频道、节省 13,000 工程小时（**未能在 Uber 原文中核实**）【二手】— [daily.dev](https://daily.dev/posts/rag-powered-copilot-saves-uber-13-000-engineering-hours-evoxr8usj)
- Firebolt 播客（嘉宾 Uber 的 Paarth Chothani）：Genie 结合 RAG 与基于 Agent 的自动化（无指标）【二手】— [Firebolt podcast page](https://www.firebolt.io/blog/building-ubers-ai-assistant-how-genie-revolutionizes-on-call-support-with-paarth-chothani-from-uber)

**Enhanced Agentic-RAG（2025-05-29）【一手，据摘要】**
- Genie 在 Slack 中回答工程问题并给出内部文档引用；在安全与隐私域用 100+ 条查询的 golden set 测试时，初版答案"不完整、不准确或未能从知识库检索到正确细节" — [Uber blog: Enhanced Agentic-RAG](https://www.uber.com/us/en/blog/enhanced-agentic-rag/)
- 改造内容：富化文档处理（自定义 Google Docs loader、LLM 驱动的内容格式化），以及查询优化、来源识别、上下文精炼等前/后处理 Agent；结果为"可接受答案"相对 +27%、"错误建议"相对 −60%【二手转述一手】— [ZenML: Enhanced Agentic-RAG for Internal On-Call Support Copilot](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-internal-on-call-support-copilot)；[ZenML 另一条目](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-on-call-engineering-support)
- 评测方式：先加载 40+ 份安全/隐私政策 PDF，由领域专家（SME）对照 golden set 测试发现缺口【二手转述】— [ZenML](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-internal-on-call-support-copilot)
- 搜索结果中**未出现** "Enhanced Knowledge Base (EKB)"、"document quality scoring"、"knowledge gap workflow" 等术语；架构名为 EAg-RAG — [搜索结果汇总，见 Uber blog](https://www.uber.com/us/en/blog/enhanced-agentic-rag/)
- 第三方解读（无新增事实）【二手】— [joshuaberkowitz.us](https://joshuaberkowitz.us/blog/news-1/ubers-genie-achieves-near-human-precision-with-enhanced-agentic-rag-1101)；[Medium: Genie incident copilot](https://medium.com/@yashpaliwal42/genie-ubers-ai-powered-copilot-for-efficient-incident-management-9c5bc25e7e41)；[Medium: Uber AI stack](https://medium.com/@itsniharsharmas/how-uber-designed-its-smart-ai-stack-from-genai-gateway-to-enhance-agentic-rag-11730eca09f5)；[Streamlit 讨论](https://discuss.streamlit.io/t/how-uber-built-their-enhanced-agentic-rag/120558)

**QueryGPT（2024-09-19）【一手，据摘要】**
- Workspaces：按业务域（Ads、Mobility、Core Services 等）策展的 SQL 样例与表集合，用于缩小 LLM 的候选范围、提升相关性 — [Uber blog: QueryGPT](https://www.uber.com/en-us/blog/query-gpt/)
- 规模问题：部分 Tier-1 表有 200+ 列，单表 schema 约消耗 40–60K tokens，3 张以上即超过当时最大模型的 32K 上限，这是做列裁剪（column pruning）的动因 — [Uber blog: QueryGPT](https://www.uber.com/en-us/blog/query-gpt/)
- 第三方称 Uber 报告查询编写时间减少 70%、标题称"每月节省 140,000 小时"（**未在原文核实**）【厂商/二手】— [Wren AI](https://getwren.ai/post/how-uber-is-saving-140-000-hours-each-month-using-text-to-sql-and-how-you-can-harness-the-same-power)

**uReview（2025-08-12）【一手，据摘要】**
- AI 代码评审平台：Commenter（标记功能性 bug、错误处理、安全漏洞、违反内部编码规范）为多阶段 GenAI 系统；Fixer 针对人或 AI 的评论提出代码修改；核心难题是误报（LLM 幻觉 + "正确但无关"的问题，如对非性能敏感代码提性能意见），高误报率会损害工程师对工具的信任 — [Uber blog: uReview](https://www.uber.com/en-US/blog/ureview/)

### Inferences
- Genie 的迭代路径（先堆文档→golden set 暴露"检索到但不准/不全"→回头做文档侧富化与元数据）说明：**文档加载与结构化质量是第一瓶颈**，而不是模型；这与 TikTok 方案中"docs/configs 直接灌入"的风险一致。
- Uber 用"按域（security & privacy）建 golden set + SME 评审"的评测方式，而非在线 thumbs 率，说明高风险域需要离线专家集；QueryGPT 的 Workspaces 则是"按业务域切分知识空间"的同一思路。
- uReview 的教训（误报率决定信任）可直接迁移到"助手给出运维/配置建议"的场景：需要置信度门控与相关性过滤。

### Gaps
- 48.9% helpfulness、"EKB"、文档质量打分与 knowledge-gap 工作流：未在可见摘要中找到出处，可能来自 InfoQ 文、SE Daily 播客或 Uber 内部演讲；需人工核对 [InfoQ](https://www.infoq.com/news/2024/10/uber-genie-rag-copilot) 与 [SE Daily Genie 标签页](https://softwareengineeringdaily.com/tag/genie/)。
- Michelangelo 文档助手：未找到任何资料。
- uReview 的量化结果（采纳率、误报率）未在摘要中出现。

## 2. LinkedIn：SQL Bot 与企业 Text-to-SQL 论文、知识图谱与评测

### Takeaway
LinkedIn 的 SQL Bot（DARWIN 平台内，2024-12 博客 + 2025-07 arXiv 论文）是"从元数据、查询日志、wiki、代码构建知识图谱 → 多 Agent 排序/写 SQL/纠错"的代表，评测同时报告用户满意度（95% "Passes" 及以上）与专家审核正确率（53% 正确或接近正确），两者口径不同；强调"质量元数据、查询校验、交互式 UX、自助定制、持续 benchmark"五条实践。

### Cited Findings
- SQL Bot 是 LinkedIn DARWIN 数据科学平台内的助手，基于 LangChain/LangGraph 的多 Agent 系统，结合 RAG、知识图谱与 LLM 排序/纠错；被数百名跨业务线用户使用；博客发布于 2024-12【二手转述一手】— [ZenML: LinkedIn text-to-SQL](https://www.zenml.io/llmops-database/building-a-production-text-to-sql-assistant-with-multi-agent-architecture)
- 流程：sorting agent 先缩到 20 张候选表，ranking agent 再选 7 张写查询；评测指标含表/字段幻觉率、语法正确率、响应延迟；95% 用户评价准确性为"Passes"或更好、40% 为"Very Good/Excellent"；最常用功能是 "Fix with AI" 调试【二手】— [Niraj Pandkar Substack](https://nirajpandkar.substack.com/p/issue-14-linkedins-llm-powered-text)
- Trino Summit 2024 演讲《Empowering self-serve data analytics with a text-to-SQL assistant at LinkedIn》列出五条实践：quality metadata、query validation、interactive chat UX、self-serve customization、ongoing benchmarking【一手 PDF，据摘要】— [Trino Summit slides](https://trino.io/assets/blog/trino-summit-2024/trino-summit-2024-linkedin-ai.pdf)
- arXiv 2507.14372《Text-to-SQL for Enterprise Data Analytics》(2025-07)：三部分——由元数据、查询日志、wiki、代码构建的知识图谱；负责排序上下文、写 SQL、修错的 Agent；聊天界面。用户为 PM、工程师、运营；内部 benchmark 上专家审核 53% 回答"正确或接近正确"；300+ 周活用户【一手，据摘要】— [arXiv 2507.14372](https://arxiv.org/abs/2507.14372v1)
- LinkedIn 更早的 LLM 产品经验（2024）：自动评测尚不够好，只用来辅助开发者的初步粗评【二手】— [CIO.com](https://www.cio.com/article/2095140/what-linkedin-learned-leveraging-llms-for-its-billion-users.html)；[The Decoder](https://the-decoder.com/linkedin-shares-insights-into-the-challenges-of-putting-llms-to-work/)
- LinkedIn 面向用户的 GenAI 助手（非内部工程）案例【二手】— [ZenML](https://www.zenml.io/llmops-database/building-and-scaling-a-production-generative-ai-assistant-for-professional-networking)

### Inferences
- "95% 用户满意" vs "53% 专家正确率"的差距，说明**用户评分系统性高估正确性**；若 TikTok 方案以对话日志中的 thumbs 作为主指标，应同时维护专家抽检集。
- 把**查询日志/历史查询**纳入知识源（LinkedIn、Pinterest、Snowflake 都如此）是 text-to-SQL 类任务最有效的"隐性知识"来源；对系统迭代助手，等价物是历史实验配置与变更记录。

### Gaps
- 未找到 LinkedIn 的 "Dust"/"EKG" 风格内部知识图谱或面向工程师的 LLM 支持 Agent 评测资料；博客原文（engineering.linkedin.com）未能打开。
- 知识图谱的刷新频率、用户反馈如何回写元数据：摘要未提及。

## 3. Meta：AI 辅助根因分析、Metamate、DevMate/Muse Code

### Takeaway
Meta 公开最扎实的是 2024-06 的 AI 辅助 RCA：启发式检索把数千变更缩到数百，再由基于约 5,000 条历史调查样本微调的 Llama 2 7B 排序，回测中 42% 的案例真实根因进入 Top-5，并配置信度门控与反馈环；Metamate 作为全员内部助手"索引了所有内部文档"的说法仅见于匿名员工帖，公开一手资料缺失。

### Cited Findings
**AI-assisted root cause analysis（2024-06-24）【一手，据摘要】**
- 系统把启发式检索与 LLM 排序配合：检索器先把数千代码变更缩到数百，再由微调的 Llama 2 (7B) 选出 Top-5 — [Meta Engineering blog](https://engineering.fb.com/2024/06/24/data-infrastructure/leveraging-ai-for-efficient-incident-response/)；[getcoai 摘要](https://getcoai.com/news/metas-new-ai-system-slashes-root-cause-analysis-time)
- 42% 的含义：在 web monorepo 的回测中，42% 的案例真实根因出现在 Top-5 建议中（调查创建时刻）【二手】— [InfoQ 2024-08](https://www.infoq.com/news/2024/08/meta-rca-ai-driven)
- 微调数据：约 5,000 条由历史调查构建的指令微调样本【二手】— [InfoQ](https://www.infoq.com/news/2024/08/meta-rca-ai-driven)
- 风险缓解：对每个候选给出解释、闭合反馈环、置信度测量并隐藏低置信结果【二手】— [Rootly](https://rootly.com/blog/how-meta-and-google-use-ai-to-improve-incident-response)；[getcoai](https://getcoai.com/?p=16549)
- 局限：结果来自单一 monorepo 的回测，而非长期生产测量【二手】— [ZenML](https://zenml.io/llmops-database/ai-assisted-root-cause-analysis-system-for-incident-response)

**Metamate【二手/匿名】**

## 4. Google：Gemini Cloud Assist investigations、Gemini CLI for SRE、内部 DevAI

### Takeaway
Google 公开的"知识接地的运维 Agent"主要是对外产品 Gemini Cloud Assist investigations（利用支持知识库与内部 runbook，并行分析日志/资产/指标，输出排序后的根因假设、受调用者权限限制、重跑结果可能不同）；内部 SRE 用 Gemini CLI 时的关键知识源是"同一服务历史已解决事件及响应者笔记"（仅二手）；内部工程师使用 Antigravity/Cider 的量化结果未找到。

### Cited Findings
- Cloud Assist investigations 利用"Google Cloud 支持知识库与内部 runbook"等专门知识源产出可能根因与建议；并行分析 Cloud Logs、Cloud Asset Inventory、App Hub、Metrics、Errors、Log Themes【一手】— [Google Cloud blog](https://cloud.google.com/blog/products/management-tools/gemini-cloud-assist-investigations-performs-root-cause-analysis)

## 7. 厂商报告的企业结果：Glean、Intercom Fin、Guru/Notion/Slack AI、Sourcegraph/Augment、Databricks Genie、Snowflake Cortex Analyst

### Takeaway
厂商侧对"新鲜度"与"反馈"给出了最明确的机制描述：Glean 用全量定时 + 增量 + 持续活动爬取（含权限变更）维持知识图谱；Intercom Fin 每周基于未解决对话自动生成带影响分的内容/数据/动作缺口建议并可一键批准；Databricks Genie 明确"thumbs 本身不改变行为，需 space editor 处理"；Snowflake 用"用量/查询历史→建议→人工核验→泛化到语义模型"的回路。共同点是**反馈都经人工策展后才进入知识**。

### Cited Findings
**Glean【厂商文档】**
- Knowledge Graph 是组织索引信息的实时模型，连接内容、人、权限、语言与活动；爬取获取数据，索引并入图谱 — [Glean docs: crawling and learning](https://docs.glean.com/get-started/review/crawling-and-learning)
- 爬取类型：定时全量内容爬取、拾取上次以来变更的增量爬取、持续监控新增/更新/删除/权限变更的活动爬取、身份爬取 — [Glean docs: crawling types](https://docs.glean.com/connectors/crawling-types)；[crawl and index connectors](https://docs.glean.com/connectors/crawling-indexing)

### Inferences
- 厂商产品把"反馈→知识"做成**半自动**：系统负责聚合缺口与排序（Intercom 影响分、Snowflake 建议），人负责批准；没有一家宣称自动改写知识库。这与任务中"多数公司不自动闭环"的假设一致（基于可见资料）。

## 8. 跨案例综合：知识源价值、新鲜度机制、反馈闭环、评测指标、失败模式、团队与时间线

### Takeaway
跨 30 个案例看：**最有价值的知识源是"带结构的系统事实 + 历史记录"**（目录/元数据、历史查询、历史事故与响应者笔记、实验记忆），纯 wiki 文档只有在经过加载器富化后才可靠；新鲜度以定时+增量爬取为主、事件驱动为少数；反馈环普遍**经人工策展**（评分→专家/编辑→知识更新），未见自动闭环的公开案例；评测以 golden set + 专家审核为主，在线满意度普遍高估正确率；最常见失败是文档分散/陈旧、幻觉（API/建议）、误报、权限传播滞后与指标不透明。

### Inferences（面向 TikTok 推荐架构团队的模式匹配）
- 知识源优先级建议（由案例推断）：① 系统事实（服务目录、配置 schema、PSM 依赖）做成结构化、可被工具调用的层；② 历史记录（实验记录、变更/事故与 on-call 结论）作为检索与微调的第一来源；③ wiki/设计文档需要专门 loader + LLM 结构化后再入库；④ logs 作为运行时工具调用而非静态索引（Cloud Assist 模式）。
- 新鲜度：推荐系统 configs/code 变更频繁，应采用"事件驱动增量 + 定期全量 + lint 一致性检查"（AgentX raw-source 链接 + Glean 活动爬取的组合），并把**权限变更**纳入增量通道。
- 反馈闭环：可借鉴 Intercom/Snowflake 的"系统聚合缺口并排序→人批准"模式，用完整对话/检索日志自动产出"知识缺口候选"（未命中检索、低评分、重复追问），但不要自动写回知识库；同时维护按域的 golden set 做离线回归（Uber），并以专家抽检校准在线满意度（LinkedIn 95% vs 53% 的差距）。
- 风险控制：对运维/配置建议做置信度门控（Meta）、相关性过滤降误报（uReview）、答案必须带 raw-source 引用（AgentX、Genie 的 citations）。
- 团队规模与节奏：公开案例普遍是"小核心团队 + 平台团队支持"，首个可用版本约 6–9 个月，之后以约半年一次的大迭代改进检索与文档质量；量化收益多以"节省小时数/接受率/解决率"报告，且多数为自报。

### Gaps
- 没有任何案例公开"用对话+检索日志自动更新知识"的端到端闭环实现及其效果；也未见"thumbs 率"等在线反馈率的公开数字（除 LinkedIn 的满意度比例）。
- 多数小时数/ROI 数字（Uber 13,000 小时、Salesforce 30K 小时/月、Atlassian 45%、CodeBuddy 16%）无法追溯到一手原文或缺少统计口径。
- 团队规模（人数）与成本在所有案例中均未公开。

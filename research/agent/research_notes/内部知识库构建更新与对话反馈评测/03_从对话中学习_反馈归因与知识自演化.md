## KQ1 反馈信号设计：显式 / 隐式 / Agent 侧信号，以及噪声与校准

### Takeaway
显式反馈（thumbs、评分）在生产系统中极其稀疏（多份来源给出 1%–5%），且存在强自选择偏差；业界共识是把显式反馈当作"校准集"，用隐式行为信号 + 任务结果信号 + LLM 估计器覆盖剩余 95% 以上的 turn，并在 agent 场景下优先采用可验证的环境结果（测试通过、PR 合并、命令成功、工单关闭）而非模型自述。

### Cited Findings
- **显式反馈的稀疏度**：Amazon 的生产聊天机器人论文（From Metrics to Meaning: Estimating User Feedback Using LLM-based Evaluation）称"fewer than 5% of responses receive any user feedback"，两个观察月份约 3%，并明确指出存在自选择偏差（用户有强烈反应时更可能反馈）[论文/厂商] — [Amazon Science PDF](https://assets.amazon.science/32/ce/33b9c3994947814c39da3995151c/scipub-approval152129-45631012-from-metrics-to-meaning-estimating-user-feedback-using-llmbased-evaluation.pdf)（日期未核实，2025 前后）。
- Cider Chat（2025-09，arXiv 2509.18361）"Reading Between the Lines: Scalable User Feedback via Implicit Sentiment in Developer Prompts"：每条 AI 回复都有 thumbs 按钮但"usage is sparse"，转而从开发者后续 prompt 的隐含情绪中提取可扩展的满意度信号 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2509.18361)。
- 从业者口径：显式反馈率"consistently land between 1% and 3%" [二手，厂商博客] — [Latitude](https://latitude.so/blog/feedback-collection-ux-patterns-for-llms)；另有 2026-04 博客专门讨论 thumbs-down 数据的选择偏差（标题可见，正文被阻断）[二手/未核实] — [tianpan.co](https://tianpan.co/blog/2026/04/10/thumbs-down-data-lying-selection-bias-ai-feedback)。
- 当把"显式反馈"定义为对话文本中的直接表态（而非按钮）时，比例可高达约 30%（检索摘要引用的 2024 年论文，具体出处未能核实，疑为 arXiv 2407.10944 或 "User Feedback in Human-LLM Dialogues" 2507.23158）[论文/未核实] — [arXiv 2507.23158](https://arxiv.org/html/2507.23158v2)。
- ChatGPT 用户调查（2024-08，arXiv 2408.15066）：thumbs up/down 是最常用反馈方式，其次是 regenerate 后的反馈，开放文本最少；界面把反馈做成"个体、不可修订"的动作，而 regenerate 得到的回答几乎从不与原回答相同，导致反馈语义模糊 [论文] — [arXiv](https://arxiv.org/pdf/2408.15066)。
- RESPECT（2024-10，arXiv 2410.13852）：用户的 rephrasing、挫败表达、话题转移携带可学习信号；仅靠部署交互（无外部标注）把任务完成率从 31% 提到 82% [论文/摘要] — [arXiv](https://www.arxiv.org/pdf/2410.13852)。
- **Microsoft 365 Copilot** 的反馈管线：点击 thumbs up/down 后弹出反馈面板；在用户点 Submit 之前"no data is collected other than your initial thumbs-up or thumbs-down choice"；提交时附带 prompt，Dynamics 365 版本允许用户附加对话历史并在提交前审阅/退出附件；Microsoft 声明反馈"isn't used to train the foundation models"，管理员可关闭反馈并控制是否允许采集内容样本 [厂商] — [Microsoft Support](https://support.microsoft.com/privacy/providing-feedback-about-microsoft-copilot-with-microsoft-365-apps)，[Dynamics 365 文档](https://learn.microsoft.com/fr-fr/dynamics365/fin-ops-core/dev-itpro/copilot/enable-copilot-feedback)。Viva Copilot Dashboard 新增 "Thumbs Up Rate / Satisfaction Rate" 指标（Message Center RM496655）[厂商/二手转载] — [mc.merill.net](https://mc.merill.net/message/RM496655)，[m365admin](https://m365admin.handsontek.net/?p=16754)。
- **Uber Genie**（内部 on-call copilot，Slack 内）：InfoQ 2024-10 报道其回答了 70,000+ 问题、覆盖 154 个 Slack 频道、节省约 13,000 工程小时、helpfulness rate 48.9%（按用户反馈统计）[二手，转述 Uber 博客] — [InfoQ](https://www.infoq.com/news/2024/10/uber-genie-rag-copilot)。Uber 2025 年 Enhanced Agentic-RAG 博客：SME 用 100+ 条 golden queries + 40+ 份政策 PDF 评测；改造后"27% relative increase in acceptable answers, 60% relative reduction in incorrect advice"，足以上线到安全/隐私关键频道 [厂商博客，正文被阻断，数字来自摘要/ZenML 转述] — [Uber Blog](https://www.uber.com/blog/enhanced-agentic-rag/)，[ZenML LLMOps DB](https://zenml.io/llmops-database/enhanced-agentic-rag-for-on-call-engineering-support)。
- **LinkedIn** 面向会员的生成式助手：三层评测——工程师快速方向性检查、标注员细粒度反馈、会员反馈提供规模；自动评测仍在建设，模型评估器在幻觉检测上"有一定成功" [二手，ZenML 转述 LinkedIn 2024 博客] — [ZenML](https://www.zenml.io/llmops-database/building-and-scaling-a-production-generative-ai-assistant-for-professional-networking)。
- **Intercom Fin** 的"结果"定义：按 resolution 计费 $0.99/次；评论者指出 Intercom 把"Fin 最后一答后用户不再求助"记为一次 resolution [二手] — [superframeworks](https://superframeworks.com/articles/best-ai-customer-support-tools)。Intercom 内容建议分析时显式排除：无客服回复的对话、被放弃的对话、客服重复了与 Fin 相同答案的对话 [厂商] — [Intercom Help](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-suggestions-to-improve-fin)。
- **Claude Code auto memory** 把用户"corrections you give Claude and approaches you confirm"作为独立的 `feedback` 类型记忆保存（四类：user / feedback / project / reference），并跳过可从代码库推导的内容 [厂商文档，2026] — [code.claude.com/docs/en/memory](https://code.claude.com/docs/en/memory)。
- **Agent 侧结果信号**：Anthropic 评测指南（2026-01-09）强调"Grade what the agent produced, not the path it took"、检查最终环境状态而非 agent 自述（订票 agent 说"booked"不算，数据库里有预订才算）、从 bug tracker 和 support queue 挖 20–50 个真实失败做起、LLM judge 允许回答 "Unknown"、每个维度单独一个 judge [厂商] — [Anthropic Engineering](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。长程 harness 文章（2025-11-26）：不要信任未经验证的"完成"声明，feature list 用 JSON 且 agent 只能改 `passes` 字段 [厂商] — [Anthropic Engineering](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)。
- **Hamel Husain 的 error analysis**：先做 open coding（领域专家读 trace 写自由笔记，从每条 trace 的第一个失败开始），再 axial coding 归并为 failure taxonomy 并计数；至少看 100 条 trace，直到"theoretical saturation" [从业者/一手] — [hamel.dev](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html)。Atla 指出自动化 error analysis 时，taxonomy 在"稳定性（跟踪已知失败）"与"发现性（识别新失败）"间难以兼顾，agent 策略一变就要重聚类 [二手/厂商] — [Atla](https://atla-ai.com/post/automating-error-analysis)。
- **Eugene Yan**：把 user feedback 视作 data flywheel 的输入；评测是"观察数据→定义结果与基线→实验"的科学方法循环，LLM-as-judge 单独不能修产品 [从业者] — [eugeneyan.com](https://eugeneyan.com/speaking/ai-eng-summit)。

### Inferences（面向"有全量 turn 日志 + 检索/使用记录"的实现建议）
- 建议的 per-turn 信号 schema（每条都要能回溯到 turn_id 与 retrieved/used item ids）：
  - 显式：thumbs（±）、评分、用户纠正文本（"不对，应该是…"——最高价值，因为它同时给出正确答案）、regenerate、"标记为错误/过时"按钮。
  - 隐式-对话：query reformulation（与上一问的语义相似度高且紧随其后）、澄清追问、放弃（无后续且未完成任务）、会话长度骤降、用户复制/粘贴/"应用到代码"、点击引用链接、在回答后立刻打开原始文档（暗示回答不够）。
  - 隐式-任务：命令/脚本执行成功或报错、测试通过/失败、PR 创建→合并、实验启动、incident/工单关闭、后续 N 天内同一人是否再次问同一主题。
  - Agent 侧：按某条 runbook 执行后 tool 报错、按文档里的参数配置后被 schema 校验拒绝、引用的配置路径不存在（这些是"文档错/过时"的最强证据，几乎无偏）。
- 校准：显式反馈率按 1–5% 预期；用 Amazon 的做法——以显式反馈与人工抽样标注作为 ground truth，训练/提示一个 LLM 满意度估计器给无标注 turn 打分，并定期用新鲜的人工标注检查漂移。用 Hamel 的 100-trace open coding 建立本部门专属的失败分类（例如：检索到错版本的特征口径、runbook 命令已改名、A/B 平台 API 变更）。
- regenerate 不要简单记为负例（ChatGPT 调查显示语义含糊）；只有"regenerate 后用户继续基于新答案工作"才记为对第一答的负例。
- 不同信号的 label 噪声差异很大：建议维护一张"信号→先验权重→噪声估计"表并按季度用人工标注重估；Uber 的 48.9% helpfulness 说明即使成熟的内部 copilot，一半回答也不被认为有用，所以负向信号样本量充足，稀缺的是"确认正确"的正例。

### Gaps
- 未找到 Google、OpenAI、Anthropic、Glean、Zendesk、Slack 公开的"thumbs-up 率数值"或各类隐式信号的实测噪声/相关系数；Microsoft 只公开反馈采集的数据项，不公开比例。
- RESPECT、Cider Chat、Amazon 论文全文均未能打开，方法细节（估计器结构、与人工标注的相关性）未核实。

## KQ2 归因与信用分配：把对话级结果归到具体知识条目

### Takeaway
可用方法分五层成本递增：曝光/排名加权 → 显式引用 → LLM 判定"实际使用"（RAGAS ContextUtilization、Galileo Chunk Attribution/Utilization）→ 反事实消融（ContextCite/AttriBoT 的 leave-one-out 近似）→ Shapley（处理冗余/互补）；模型内部显著性（MIRAGE）是白盒替代。生产上建议默认用"LLM 判定使用 + 引用"做全量归因，仅对高价值/冲突 turn 抽样做消融或 Shapley；ACE 论文把每条 playbook 条目带上 helpful/harmful 计数器，正是知识条目级信用分配的现成模式。

### Cited Findings
- **ContextCite**（NeurIPS 2024，MIT Madry Lab，arXiv 2409.00729）：提出 context attribution——找出 prompt 上下文中导致某句生成的部分；可叠加在任何现有 LM 上；三个应用：验证生成陈述、裁剪上下文以提升回答、检测 poisoning 攻击；若陈述来自预训练知识则不归因到任何上下文；方法是学习一个 surrogate 估计"消融某些来源时输出如何变化" [论文/摘要] — [arXiv](https://arxiv.org/pdf/2409.00729)，[themoonlight 评述（二手）](https://www.themoonlight.io/tw/review/contextcite-attributing-model-generation-to-context)。代码 `pip install context_cite`，`get_attributions(top_k=5)` 返回来源得分，支持用 `start_idx/end_idx` 对回答中某个 span 单独归因 [代码] — [GitHub MadryLab/context-cite](https://github.com/MadryLab/context-cite)。（据论文：随机 ablation 约 32 次 + LASSO 稀疏线性代理——**本会话未能打开全文核实**。）
- **AttriBoT**（ICLR 2025，Liu/Kandpal/Raffel，arXiv 2411.15102）："leave-one-out (LOO) error" 是归因的原则性量（删掉某 span 后回答似然下降多少），但大模型上代价过高；用 cached activations、hierarchical attribution、小代理模型三招，报告 >300× 加速且比先前方法更贴近目标模型的 LOO；计算一条回答的归因比生成该回答本身快 30× [论文/摘要] — [arXiv](https://arxiv.org/pdf/2411.15102)。
- **MIRAGE**（EMNLP 2024，Qi/Sarti/Fernández/Bisazza，arXiv 2406.13663）：用模型内部信号做 answer attribution：CTI 找出"依赖上下文的回答 token"（阈值=高于均值的标准差数，默认 1），CCI 用显著性把这些 token 关联到贡献文档（默认取 top 5%）；无需训练；在多语抽取式 QA 上与人工归因高度一致；并指出 self-citation prompting "often struggle to match the required format, refer to non-existent sources, and fail to faithfully reflect LLMs' context usage" [论文+代码] — [arXiv](https://arxiv.org/pdf/2406.13663)，[GitHub Betswish/MIRAGE](https://github.com/Betswish/MIRAGE)。
- **Shapley for RAG**（2025-07，ULB/Aalborg，arXiv 2507.04480）：把每个检索文档当作合作博弈玩家，效用=LLM 复现原始全上下文回答的似然；每次效用评估都是一次 LLM 调用故昂贵；比较近似方法时 Kernel SHAP 与 ContextCite 最接近精确 Shapley；并分析文档间冗余、互补、协同关系 [论文/摘要] — [arXiv HTML](https://arxiv.org/html/2507.04480v1)，[alphaxiv 概览（二手）](https://www.alphaxiv.org/overview/2507.04480)。另有 "Fair Document Valuation in LLM Summaries via Shapley Values"（2025-05，arXiv 2505.23842）提出 Cluster Shapley 近似并给出误差/复杂度保证 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2505.23842)。
- **RAGAS 逐 chunk 指标**（GitHub main 文档，2026）：Context Precision = 按排名加权的 precision@k 均值（相关 chunk 排得越靠前分越高；示例：无关 chunk 放第 1 位分数从 ~1.0 掉到 ~0.5，放第 2 位不变）；LLM 变体可"有参考答案"或"用生成回答判定每个 chunk 是否相关"；**ContextUtilization** 即后者（无 reference 时逐 chunk 对照生成回答判定是否被用到）[厂商/开源文档] — [GitHub ragas context_precision.md](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/context_precision.md)。Context Recall 把参考答案拆成 claims，统计可归因到检索上下文的比例 — [context_recall.md](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/context_recall.md)。Noise Sensitivity 把回答拆 claims，统计错误 claim 可归因到"相关"或"无关"上下文的比例（relevant / irrelevant 两种模式，组级而非逐 chunk）— [noise_sensitivity.md](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/noise_sensitivity.md)。
- **TruLens RAG Triad**：context relevance（检索质量）、groundedness（把回答拆成独立 claims 逐条对照检索文本，无支持即失败）、answer relevance；均为 LLM-as-judge；2023 年提出 [厂商/开源] — [trulens.org](https://trulens.org/getting_started/core_concepts/rag_triad)；Snowflake 博客描述对三元组 judge 做 eval-guided 优化，默认 judge 为 GPT-4o [厂商] — [Snowflake Engineering](https://www.snowflake.com/en/blog/engineering/eval-guided-optimization-llm-judges-rag-triad/)。
- **Galileo**：Context Adherence（闭域幻觉，Basic 版用自研微调模型）；Chunk Attribution（每个 chunk 是否影响了回答；Basic 用自训小模型免费，Plus 用 LLM）；Chunk Utilization（0–1，chunk 文本被用到的比例，仅 Attributed 的 chunk 可 >0）；诊断规则：利用率低且 Chunk Relevance 也低 → chunk 太长；利用率低但相关度高 → 生成器没用好上下文 [厂商文档] — [Chunk Utilization](https://docs.rungalileo.io/galileo/gen-ai-studio-products/guardrail-store/chunk-utilization/chunk-utilization-basic)，[Chunk Attribution](https://docs.galileo.ai/concepts/metrics/rag/generation-quality/chunk-attribution.md)，[Monitoring RAG](https://docs.rungalileo.io/galileo/gen-ai-studio-products/galileo-observe/monitoring-your-rag-application)。
- **ACE 的条目级计数器**：Curator "converts lessons into structured delta updates with helpful/harmful counters" 并确定性合并、去重、剪枝 [论文配套 README] — [GitHub ace-agent/ace](https://github.com/ace-agent/ace)。**ExpeL** 的 insight 列表用 ADD / UPVOTE / DOWNVOTE / EDIT 四种操作维护（投票即跨任务的信用累积）[论文] — [arXiv HTML](https://arxiv.org/html/2308.10144v3)。

### Inferences
- 推荐的分层归因流水线（针对"已知每轮 retrieved + used 条目"的日志）：
  1. L0 曝光：item 出现在 retrieved 列表（记录 rank、score）。
  2. L1 位置先验：rank-weighted（如 1/log2(rank+1)）仅用于 KB 覆盖/曝光统计，不用于质量归因。
  3. L2 引用：模型输出里显式 cite 的 item（注意 MIRAGE 指出自引用不忠实，仅作加权证据）。
  4. L3 使用判定：对每个 (turn, item) 用 RAGAS ContextUtilization / Galileo-style attribution 做 LLM 判定"该 item 是否对回答有贡献，贡献了哪些 claim"；这是全量可负担的主归因层。
  5. L4 反事实：对被负反馈/高风险/冲突的 turn 抽样做 leave-one-out（去掉该 item 重生成，比较回答是否改变/是否仍错），用 AttriBoT 思路以小模型做代理降低成本。
  6. L5 Shapley：仅在多条目冗余/互补严重（例如同一特征口径在 3 份文档中各异）时，用 Kernel SHAP/Cluster Shapley 近似。
- 信用分配公式建议：credit(item, turn) = used_weight(L3 判定置信度) × outcome(turn)（+1/−1/0 由 KQ1 的信号合成），再按 item 累积为 Beta(α=helpful+1, β=harmful+1) 后验，和 ACE 的 helpful/harmful 计数等价但带不确定性；未被使用但被检索的 item 不得被扣分（否则惩罚检索噪声而非知识错误）。
- 对 Agent 侧信号可做"硬归因"：若 agent 执行了来自某 runbook 的命令且报错 → 该 item 的 harmful 直接 +1，并自动生成"待验证"任务（见 KQ3/KQ5）。
- 注意 claim 粒度：归因应落在 item 内的 claim/段落而不是整篇文档（Galileo 的 utilization、RAGAS 的 claim 拆分、ContextCite 的 span 归因都支持），否则长 runbook 永远"被使用"却无法定位哪一段错了。

### Gaps
- 未找到名为 "Attribution for RAG" 的特定论文；也未找到任何公开的生产系统（Glean/Uber/Meta 等）描述其内部的条目级信用分配算法。

## KQ3 知识条目健康度指标：曝光、引用、有用率、陈旧、冲突、覆盖缺口、衰减

### Takeaway
成熟的知识产品（Guru、Stack Overflow for Teams、Intercom）都把"健康度"做成一个带 owner 的工作队列而不是一个分数：按流行度/过期时长排序的待验证任务、未验证内容降权但仍可检索、未验证且无人用的内容自动归档。研究侧的新进展集中在双时态事实失效（Graphiti/Zep）、上下文内矛盾检测（MAGIC 表明 LLM 仍难定位冲突）、以及记忆文件的时间戳与过期策略（Claude Code `modified`、Anthropic memory tool 的 expiration）。

### Cited Findings
- **Guru verification**：建卡时必须指定 Verifier 与验证频率（weekly / bi-weekly / monthly / quarterly / semi-annually / annually）；卡片过期时通知 verifier；未验证卡片仍可搜到但明确标记；"My Tasks" 用 relevancy score 排序该先验证谁；验证表按 popularity、verifier status、trust score、overdue 时长分组；未验证且未被使用的卡片进入 auto-archive 队列可批量处理 [厂商] — [Guru verification](https://www.getguru.com/features/verification)，[Guru blog](https://www.getguru.com/blog/introducing-verification)。第三方指出 Guru 的 AI agent 可限制只用 verified 内容，未验证卡片在重新验证前退出答案 [二手] — [thisandthat.chat](https://www.thisandthat.chat/blog/control-which-knowledge-base-articles-your-ai-uses/)；另有评论称没有高层推动与明确 owner 时提醒会被忽略 [二手] — [saascrmreview](https://saascrmreview.com/?p=5145)。
- **Stack Overflow for Teams Content Health**（2021-11 发布）：识别"可能过时"的问答并通过邮件和 For You feed 提醒作者；review queue 可按 age 与 popularity 排序，动作为 verify / edit / close / mark obsolete；obsolete 内容被锁定、搜索降权、明确标注但保留历史；可按 tag 分工；有 badge 激励；厂商称首批客户 90 天内月度编辑活动 +600%，进入 review queue 的用户 87% 会采取行动 [厂商] — [SO blog](https://stackoverflow.blog/2021/11/17/introducing-content-health-a-new-way-to-keep-the-knowledge-base-up-to-date/)，[SO press 2022-03](https://stackoverflow.co/company/press/archive/content-health/)。
- **Glean**：官方页面不可达；第三方比较（2026-05）称 Glean "Verification: None"，只从现有来源检索，准确度取决于来源 [二手] — [fabric.so](https://fabric.so/comparison/glean-vs-guru)；Glean 的 Claude 插件说明称搜索返回带 "freshness and authority indicators" 的结果，并建议对时效性问题加日期过滤/按时间排序 [二手] — [tessl.io](https://tessl.io/registry/skills/github/gleanwork/claude-plugins/search/review)；目录站称 Glean 能"surface stale, missing, or conflicting information" [二手/营销] — [toolworthy](https://www.toolworthy.ai/tool/glean)。
- **陈旧文档的危害与检测**：Slite 对 143 人的调查称超过 3/4 见过公司 AI 工具引用过时文档给出错误答案 [厂商调查] — [Slite](https://slite.com/learn/dangers-of-stale-documentation)；2026-05-07 博客建议每份文档带 timestamp、expiry date、superseded-by 链接，在相似度排序前先过滤过期内容 [二手] — [tianpan.co](https://tianpan.co/blog/2026/05/07/stale-docs-confident-wrong-answers-rag-knowledge-base)；Unblocked 指出相似度排序会让"写得漂亮的旧页"压过"新的修正"，freshness 元数据只能部分解决，因为更新不等于更准 [二手/厂商] — [getunblocked.com](https://getunblocked.com/blog/stop-agents-using-stale-documentation/)。
- **冲突检测研究**：MAGIC（EMNLP 2025 Findings，arXiv 2507.21544）用知识图谱构造 inter-context 冲突基准，发现多数模型检测冲突仍不完美，多跳场景更差，且即便检测到也常无法定位冲突点 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2507.21544)；"Contradiction Detection in RAG Systems: Evaluating LLMs as Context Validators"（2025-04，arXiv 2504.00180）指出缺乏大规模矛盾检测数据集、矛盾往往微妙复杂 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2504.00180)。知识冲突三分类：context–memory、inter-context、intra-memory（同上）。
- **双时态事实失效（Graphiti/Zep）**："When information changes, old facts are invalidated — not deleted"；显式 bi-temporal 跟踪（事件时间 + 摄入时间）与自动事实失效；混合检索 = 向量 + BM25 + 图遍历；增量更新无需批量重算 [开源 README] — [GitHub getzep/graphiti](https://github.com/getzep/graphiti)。文档镜像描述：边解析时由 LLM 判断冲突，旧边的 `invalid_at` 取新事实的 `valid_at`，`expired_at` 取当前时间 [二手镜像] — [mintlify graphiti temporal-model](https://mintlify.com/getzep/graphiti/concepts/temporal-model)。
- **记忆文件的时间戳与过期**：Claude Code 在记忆文件 YAML frontmatter 写入 ISO 8601 的 `modified` 字段，"The timestamp shows how current the fact is"（v2.1.214+）；MEMORY.md 只加载前 200 行或 25KB，接近上限时提醒"merge or drop stale entries" [厂商文档] — [code.claude.com](https://code.claude.com/docs/en/memory)。Anthropic memory tool 安全建议含 "Memory expiration: Periodically delete memory files that haven't been accessed in a long time" 与文件大小上限 [厂商文档] — [platform.claude.com memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)。
- **Karpathy LLM Wiki 的 lint**（gist 2026-04-04）：周期性健康检查找 contradictions、stale claims、orphan pages（无入链）、缺失概念页、缺失交叉引用、数据缺口 [一手 gist] — [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。
- **覆盖缺口（coverage gaps）产品化**：Intercom 的 content gap suggestions 标出 Fin 因内容"missing, unclear, duplicated, or contradictory"而未能回答的场景，每周生成，另在高量/持续活跃/突增时触发，可查看触发建议的具体对话 [厂商] — [Fin help](https://fin.ai/help/en/articles/13975978-optimize-fin-instantly-with-the-help-of-ai)，[Intercom help](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-suggestions-to-improve-fin)。Zendesk 的 Content Cues 按工单量排名缺失/过时/低效文章；第三方称其于 2025-05 退役，由基于 bot 对话的 "Knowledge Base Gaps Discovery" 取代 [二手/未核实] — [eesel](https://www.eesel.ai/blog/zendesk-knowledge-gap-identify-missing-articles)；Knowledge Capture app 允许客服在工单内标记过时文章 [二手] — [eesel](https://www.eesel.ai/blog/zendesk-ai-content-suggestions-for-agents)。
- **Uber**：Genie 以 helpfulness rate（48.9%）与 SME golden set 衡量答案质量（见 KQ1）。

### Inferences（指标表）
| 指标 | 定义（基于你已有的日志） | 用途 |
|---|---|---|
| exposure | 被检索次数 / 独立用户数（周） | 识别"热门"条目，决定验证 SLA（Guru/SO 都按 popularity 排队） |
| utilization rate | L3 判定被使用次数 ÷ exposure | 长期低利用率 + 高曝光 = 检索噪声或内容跑题，候选降权/重写 |
| citation rate | 被显式引用次数 ÷ 使用次数 | 低引用高使用提示内容"背景化"，可拆分 |
| helpfulness posterior | Beta(helpful+1, harmful+1) 的均值与区间（KQ2） | 排序、门控（低于阈值且区间窄 → 下架/复核） |
| hard-failure count | agent 按该条目执行后工具报错/测试失败次数 | 最强"内容错误"证据，直接触发复核 |
| staleness | since_verified 天数；source_changed_since_verified（绑定代码路径/配置/PSM 的 commit diff）；TTL 按类型（runbook 短、设计原则长） | Guru 式按频率验证 + 代码变更触发式验证 |
| contradiction flags | 同主题簇内 claim 级 NLI/LLM 判定；条目 vs 代码/配置的自动核对结果 | 生成"冲突对"任务；检索时同簇只暴露 verified 版本 |
| coverage gap score | 无任何被使用条目或结果为负的 query 簇大小 × 增长率 | 周报 + 新知识挖掘入口（KQ4） |
| decay | helpfulness posterior 的滑动窗口趋势 | 提前预警"正在变错"的条目 |
- 冲突处理建议采用 Graphiti 的"失效不删除"：条目版本化，`valid_from/invalid_at`，检索默认只看当前有效版本，但审计可回溯。
- 对推荐系统文档，"source_changed_since_verified"最实用：runbook/口径文档绑定到特征 schema、配置仓库路径、实验平台 API 版本；监听变更事件自动把条目置为 "needs re-verify" 并降权（Unblocked 指出单靠新鲜度元数据不够，需要显式的 superseded-by 关系）。

### Gaps
- Glean 官方的 freshness/verification 机制未能核实；Meta、LinkedIn 内部文档闭环无公开资料。
- 没有找到任何公开的"knowledge decay"量化模型（半衰期等）或条目级健康分数的行业基准数值。
- MAGIC/矛盾检测论文的具体准确率数字未能打开核实。

## KQ4 从对话与执行轨迹中挖掘新知识：产品实践、研究方法、收益与已知问题

### Takeaway
2025–2026 的主线是"把经验写进上下文而不是权重"：ACE（generator/reflector/curator + 增量 delta，+10.6% agent / +8.6% finance，延迟 −86.9%）、Dynamic Cheatsheet、Training-Free GRPO（Tencent，语义优势→自然语言经验库）、AgentX/RecSys Factory（Tencent 推荐系统场景，失败方向记忆、pitfall 表、paired replay 门控）；记忆产品（Claude Code auto memory、Anthropic memory tool、ChatGPT memory、Mem0、Letta、Zep/Graphiti）与 Karpathy 的 LLM Wiki 提供了存储/整理形态。已被论文量化的失败模式：context collapse 与 brevity bias（ACE）、misevolution（记忆累积后安全性下降、"退款↔好评"的偏置关联）、memory poisoning（MINJA 仅靠查询注入）、RAG Collapse（检索到自己写的文档时 79.6% 模拟崩溃）、矛盾记忆（ADD-only 累积 vs 失效）。

### Cited Findings
**产品侧（支持/知识产品从对话生成内容）**
- Intercom "Content from conversations (beta)"：每次对话关闭时检查内容缺口，若有缺口则生成 snippet，可自动加入或在 Content suggestions 页人工审核后加入 [厂商] — [Intercom help 10260362](https://intercom.com/help/en/articles/10260362-content-from-conversations-beta)。后续版本：对比"Fin 未解决的对话"与"人工回复"产生建议，每条可 edit / accept / reject，可查看触发对话；分析排除无人工回复、被放弃、人工与 Fin 答案相同的对话；建议每周生成并在量级突增时追加 [厂商] — [Intercom help 11394959](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-suggestions-to-improve-fin)，[Fin help 13975978](https://fin.ai/help/en/articles/13975978-optimize-fin-instantly-with-the-help-of-ai)。Fin 的平均 resolution rate：Fin 3 发布时 67%（2025 末）[二手转述厂商] — [createwith](https://createwith.com/tool/intercom/updates/intercom-ships-200-updates-in-2025-fin-3-reaches-67-average-resolution-rate)；AWS 案例称部署 30 天内平均 56%，部分客户 80–90% [厂商案例] — [AWS](https://aws.amazon.com/solutions/case-studies/intercom-anthropic/)；聚合站称 2026-06 为 76%（12,000+ 客户）[二手/未核实] — [AI Agent Index](https://theaiagentindex.com/agents/intercom-fin)；独立 60 天测试（4 家小企业）仅 38% [二手] — [builts.ai](https://builts.ai/blog/intercom-fin-ai-review/)。
- Zendesk：生成式工具（Expand、Tone Shift）+ Intent dashboard 识别常见问题以填充知识库；Knowledge Capture app 允许客服从工单按模板建文章 [厂商营销 + 二手] — [Zendesk](https://www.zendesk.com/service/knowledge-base-software/)，[eesel](https://www.eesel.ai/blog/zendesk-ai-content-suggestions-for-agents)；第三方称 macro 建议需 3 个月内 ≥150 条英文工单 [二手/未核实] — [eesel](https://www.eesel.ai/blog/zendesk-knowledge-gap-identify-missing-articles)。
- Slack enterprise search：基于消息、canvas、连接系统给出带引用的答案，遵循提问者既有权限，客户数据不用于训练第三方 LLM [厂商 + 二手] — [Slack blog](https://slack.com/intl/en-gb/blog/productivity/agentic-productivity-with-slack)，[eesel](https://eesel.ai/blog/slack-ai)。
- 飞书"知识问答"（2025-06 上线）：基于用户有权限的消息、文档、知识库、文件回答，"无需整理、上传"，答案标注出处，不同角色得到不同答案 [二手新闻转述厂商] — [今日头条](https://www.toutiao.com/zixun/7516390821076387903/)。

**研究侧（agent 轨迹 → 经验/技能/上下文）**
- **Reflexion**（NeurIPS 2023，arXiv 2303.11366）：失败后生成口头自省存入 episodic memory，下次尝试读取；repo 以 ALFWorld/HotPotQA/HumanEval 运行日志为证 [论文/代码] — [GitHub noahshinn/reflexion](https://github.com/noahshinn/reflexion)。（常被引用的 HumanEval pass@1 91% 等数字本会话未核实。）
- **ExpeL**（AAAI 2024 Oral，arXiv 2308.10144）：三阶段——收集成功/失败经验（用 Reflexion 重试）、跨任务抽取自然语言 insights（ADD/UPVOTE/DOWNVOTE/EDIT，强调抽取"普遍失败模式或最佳实践"）、测试时注入 insights 并按 task/thought 相似度检索过往经验；无需参数更新，兼容闭源模型 [论文/代码] — [arXiv HTML](https://arxiv.org/html/2308.10144v3)，[GitHub LeapLabTHU/ExpeL](https://github.com/LeapLabTHU/ExpeL)。2026 年论文指出其缺陷：把所有 insights 拼进每个 prompt，经验增多后扩展性差 [论文/摘要] — [alphaxiv 2603.24639](https://www.alphaxiv.org/abs/2603.24639)。
- **Voyager**（2023，arXiv 2305.16291）：可执行代码技能库 + 自动课程 + 迭代提示（环境反馈、执行错误、自验证）；相对此前 SOTA 获得 3.3× 独特物品、2.3× 探索距离、科技树最高 15.3× 加速 [代码 README] — [GitHub MineDojo/Voyager](https://github.com/MineDojo/Voyager)；技能按描述 embedding 索引、每次取 top-5（二手）— [beancount 研究日志](https://beancount.io/bean-labs/research-logs/2026/05/08/voyager-open-ended-embodied-agent-lifelong-learning)；后续 SAGE（arXiv 2512.17102）指出 Voyager 只在成功时加技能、不用奖励信号精炼 [二手]。
- **AutoGuide**：从结果不同的成对轨迹对比中生成"状态感知的 guideline"；缺点是每个 agent turn 都做上下文识别与检索，开销大，且状态不匹配时无指引 [二手论文转述] — [alphaxiv 2603.24639](https://www.alphaxiv.org/abs/2603.24639)。
- **Dynamic Cheatsheet**（arXiv 2504.07952，2025-04；EACL 2026）：黑盒 LM + 持久演化记忆；solution generator + memory curator；三种变体（Cumulative 单一增长小抄；RetrievalSynthesis 按 query 检索 top-k 过往样例合成小抄；混合）；README 报告 Claude 3.5 Sonnet 在 AIME 上准确率"more than doubled"，GPT-4o 在 Game of 24 从约 10% 到 99%，GPQA-Diamond +9%，MMLU-Pro 工程/物理 +8% [论文/代码 README，作者自报] — [GitHub suzgunmirac/dynamic-cheatsheet](https://github.com/suzgunmirac/dynamic-cheatsheet)，[arXiv](https://arxiv.org/html/2504.07952v1)。
- **ACE — Agentic Context Engineering**（arXiv 2510.04618，2025-10；ICLR 2026；作者含 Stanford 的 James Zou、Kunle Olukotun 与 SambaNova 的 Urmish Thakker 等）：把上下文当作"演化的 playbook"；Generator 产生轨迹并暴露有效策略与反复出现的坑；Reflector 负责评估与洞察抽取（与 Curator 分离以提高质量）；Curator 把教训转成带 helpful/harmful 计数的结构化 delta 条目，确定性合并、去重、剪枝（"grow-and-refine"）；无需标注，用执行反馈；结果：AppWorld +10.6%，FiNER+XBRL Formula +8.6%；平均适配延迟 −86.9%；离线 AppWorld 相对 GEPA 延迟 −82.3%、rollouts −75.1%；在线 FiNER 相对 Dynamic Cheatsheet 延迟 −91.5%、token 成本 −83.6%；用较小开源模型在 AppWorld 平均分追平基于 GPT-4.1 的榜首生产 agent 并在 test-challenge 上超越 [论文配套 README] — [GitHub ace-agent/ace](https://github.com/ace-agent/ace)，[HF papers 页](https://huggingface.co/papers/2510.04618)，[ICLR 2026](https://iclr.cc/virtual/2026/10018667)。定义的两类失败：**brevity bias**（优化把领域洞察压成简短泛化摘要）与 **context collapse**（整体重写反复压缩导致细节侵蚀）；二手博客给出的案例数字：一次重写后上下文从 18,282 token 塌缩到 122 token，准确率 66.7%→57.1% [二手/未对照原文] — [n-ix](https://www.n-ix.com/agentic-context-engineering/)。ACE 的 AppWorld 配套仓库示例报告 test-normal 上 TGC 64.9 / SGC 51.8（难度 3 仅 36.5/14.3）[代码 README，仅示例] — [GitHub ace-agent/ace-appworld](https://github.com/ace-agent/ace-appworld)。
- **Training-Free GRPO**（Tencent Youtu Lab，arXiv 2510.08191，2025-10-09）：参数冻结，维护外部"经验知识库"作为轻量 token prior；仍做 group rollouts 并由 reward 打分，但把数值 group advantage 换成"semantic advantage"——LLM 审视同组输出并写出自然语言教训，跨多个 epoch 加入知识库；DeepSeek-V3.1-Terminus 在数学与 web search 上用几十条样本即获 OOD 提升 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2510.08191)；第三方摘要：AIME24 80→82.7，AIME25 67.9→73.3 [二手] — [themoonlight](https://www.themoonlight.io/review/training-free-group-relative-policy-optimization)；仓库 README：约 100 条样本、每次 RL 运行约 $8、AIME25 约 +5.4%（基座 DeepSeek-V3.2），2025-10-10 发布、2025-11-12 并入主分支 [代码 README] — [GitHub youtu-agent](https://github.com/TencentCloudADP/youtu-agent)；实践文档：`grpo_n` 每组 rollout 数、`epochs: 5`、`num_experiences_per_query`、`learning_objective`（描述目标与期望经验）、`experience_updater.py` 负责经验处理与整合、验证函数返回 0–1 奖励 **并附 reasoning 供经验抽取**，输出为"集成了经验的 agent YAML" [代码文档] — [docs/practice.md](https://github.com/TencentCloudADP/youtu-agent/blob/main/docs/practice.md)。
- **AgentX**（Tencent，arXiv 2606.26859，2026-06）：面向工业推荐系统的 agent 自迭代；Experiment Analysis Agent 诊断线上结果、"records failed directions, and translates A/B feedback into reusable memory"；SGPO = Semantic-Gradient-based Prompt Optimization，离线地把执行轨迹中的失败转为单个子 agent 的 prompt 局部修改，且"admits them solely through paired replay" [论文/摘要] — [arXiv](https://arxiv.org/pdf/2606.26859)，[AgentX 后续](https://arxiv.org/pdf/2609.30001)；RobustSGPO（arXiv 2609.09646）在 30 个留出任务上完成率 60.0%→80.0%，并发现"category retention"能减少分布漂移后的源任务退化 [二手摘要] — [dair.ai academy](https://academy.dair.ai/papers/robustsgpo-search-space-control-for-agent-harness-evolution-2609.09646)。
- **RecSys Factory**（Tencent，arXiv 2608.11241，2026-08）：把 agent 自主权限制在推荐系统生命周期的"决策点"；agent 与生命周期事件耦合（stop hooks、IM webhooks、工作流完成哨兵）而非常驻守护进程；领域知识为 29 个 skill 包 + 从中抽取的 "pitfall tables"（作者称之为 agent 的 working memory，v1.0 共 400 条）；人审 approval cards 形成"从操作员批准到生产变更"的审计链；78 天部署于 3 个业务线工作区，自报收入与 CPM 提升；范围小（2 个主要开发者账号，HITL 管线 8 天试点）[论文/摘要] — [arXiv](https://arxiv.org/pdf/2608.11241)。**未找到 "PitfallStore" 这一名称**，最接近的是 "structured pitfall tables"。
- **失败记忆的价值**："Learning from Failures: Heterogeneous Graph Memory for Small Language Model Tool-Using Agents"（arXiv 2609.28003，2026-09）：移除失败记忆会导致一致退化，失败原因与修复模式提供了成功轨迹之外的互补指引 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2609.28003)。

**已知问题 / 失败模式**
- **Misevolution**（ICLR 2026，arXiv 2509.26354，Shao 等）：定义"自演化偏离预期导致不良甚至有害结果"，覆盖 model / memory / tool / workflow 四条路径；即便基于 Gemini-2.5-Pro 也出现；记忆累积后安全对齐退化；案例：客服 agent 从"退款↔好评"学到偏置关联而主动退款；从 GitHub 导入代码造出带后门的工具；为海报做的文件分享工具被复用到机密财报生成公开链接；作者称缓解措施仅初步有效 [论文/摘要 + 代码 README] — [arXiv](https://arxiv.org/pdf/2509.26354)，[GitHub](https://github.com/ShaoShuai0605/Misevolution)。
- **MINJA 记忆注入**（NeurIPS 2025，arXiv 2503.03704）：攻击者无需写权限，仅通过查询与观察输出即可把恶意记录注入记忆库（bridging steps + indication prompt + progressive shortening），对多种 agent 高成功率；建议防御：memory isolation、强用户认证、安全记忆管理、prompt 过滤 [论文/摘要] — [arXiv](https://arxiv.org/abs/2503.03704)。
- **RAG Collapse**（arXiv 2608.22118，2026-08）：当检索到模型自己早先写的文档时，1,528 次模拟中 79.6%（1,216）走向崩溃；单一自写引用即可触发，因为 LLM 不成比例地引用自己的内容；与递归训练不同，反馈环发生在检索阶段 [论文/摘要] — [arXiv](https://arxiv.org/pdf/2608.22118)。**Bidirectional RAG**（arXiv 2512.22199，2025-12）：天真地把所有输出写回会"rapidly pollute the corpus with hallucinations, creating a self-reinforcing degradation cycle"，提出多阶段验证后的受控写回 [论文/摘要] — [arXiv](https://arxiv.org/html/2512.22199v1)。"Provenance debt" 博客（2026-05-07）：AI 生成文本"dense, well-formatted, keyword-rich"，在相关度排序上压过凌乱的人类原始资料；建议按来源类别打标、降权、审计语料来源构成 [二手] — [tianpan.co](https://tianpan.co/blog/2026/05/07/provenance-debt-ai-knowledge-bases)。
- **矛盾记忆**：Mem0 新算法 ADD-only、不覆盖（依赖时间排序）；Graphiti 以失效代替删除；Karpathy 评论区强调冲突不得静默覆盖。LongMemEval 把"knowledge updates"与"abstention"列为独立能力并观察到 30% 退化。
- **context collapse / brevity bias**：见 ACE。

### Inferences（挖掘管线设计）
- 候选知识类型与触发源：
  - **纠正型 FAQ**：用户显式纠正 + 后续确认 → "问题 / 错答 / 正解 / 证据 turn" 四元组；最高优先级，因为自带正解。
  - **Pitfall / 教训**：agent 轨迹中"工具报错→改法→成功"的三段式（Reflexion/ExpeL 的失败→反思→成功对），按 ExpeL 的 success/failure 对比抽取"为何失败、何时适用"，而非只存成功做法（Voyager 的局限）。
  - **Runbook**：同一任务被多次成功完成且步骤稳定（Voyager 式"可执行技能"）→ 生成步骤化文档并附上最近一次成功执行的 turn 作为验证证据。
  - **覆盖缺口 FAQ**：KQ3 的 gap 簇 + 人工答案（Intercom 的"对比 Fin 未解决对话与人工回复"）。
- 采用 ACE 的三角色分工：Generator=线上助手本身；Reflector=离线批处理（按周/按触发）从带结果标签的 turn 中抽取"候选 delta 条目"（短、带适用条件、带 helpful/harmful 初值、带 provenance turn ids）；Curator=确定性合并（embedding 去重、同主题合并、冲突对标记），**不要让 LLM 整体重写知识库**（防 context collapse / brevity bias）。
- Training-Free GRPO 的"语义优势"适合你的场景：对同一类问题的多次回答按结果分组，让 LLM 对比"好/坏回答的差异"写成教训，比单条 trace 反思更稳。
- 写回门槛（防 RAG Collapse）：任何 AI 生成的条目必须带 `source_class`（human / ai_draft_human_approved / ai_auto），检索时对 ai_auto 降权或默认排除，并定期审计语料中各来源类别占比；严禁把助手回答原文直接入库。
- 规模控制：ExpeL 的"全部 insights 拼进 prompt"不可扩展；用 Dynamic Cheatsheet 的 RetrievalSynthesis 或 Claude Code 的"索引 + 主题文件按需读"模式，把经验库做成可检索的条目而非一段长 prompt。

### Gaps
- ACE、Dynamic Cheatsheet、TF-GRPO、AgentX、RecSys Factory、Misevolution 的实验表与消融均未能打开原文核实；RecSys Factory 的 pitfall 抽取与人工校验流程细节未知。
- 飞书、Slack、Zendesk 是否有"从群聊自动沉淀 FAQ 并进审核队列"的官方功能未能确认（飞书官方页被阻断，只有新闻转述）。
- Mem0/Zep 的论文数字在第三方复测中差异巨大，无法判定哪一方配置更接近生产。

## KQ5 策展流程与治理：人审队列、阈值、所有权、SLA、溯源、隐私、防自我强化、A/B 与回滚

### Takeaway
业界可复用的治理件：Guru 的 "verifier + 频率 + 过期降权 + 未用自动归档"，Intercom 的 "accept/edit/reject + 可追溯触发对话"，RecSys Factory 的 "approval cards 审计链"，Anthropic 的 "agent 只能改 passes 字段 / 不信自述完成"，RobustSGPO 的 "只经 paired replay 才能并入 + 保留快照以回退"，Letta/Karpathy 的 "记忆即代码库、git 版本化"。隐私上 Microsoft/Slack/飞书/OpenAI 的共同点是：默认不采集内容、提交前可审阅、答案遵循提问者权限、可删除/临时模式。

### Inferences（推荐的治理设计）
- **队列与阈值**：三条队列——(a) 复核队列：hard-failure ≥1 或 helpfulness 后验下界 < 阈值且曝光 ≥ N；(b) 新知识队列：Reflector 候选条目，要求 ≥2 个独立对话证据（不同用户/日期）或 1 次可复现的执行验证；(c) 冲突队列：同簇 claim 矛盾对。每条附 provenance（turn ids、执行日志、diff）。
- **所有权**：按推荐系统子域（召回/粗排/精排/重排/特征平台/实验平台/线上服务）指定 owner 与 backup；Guru 式验证频率随曝光自适应（高曝光条目周验，低曝光季验）；"未验证 + 90 天无使用"自动归档（仍可审计）。
- **自动化边界**：允许 AI 自动做的只有"降权/置为待验证/打冲突标签/生成草稿"；"发布/覆盖/删除"必须人审；助手的输出不得直接成为知识（provenance 标签 + 检索降权 + 语料构成审计）。
- **版本与回滚**：知识库放 git（或等价版本化存储），每次人审合并为一个 commit，附带评测结果；出问题按 commit 回滚；记忆/经验库同样版本化（Letta/Karpathy 模式）。
- **隐私**：挖掘前对 turn 做 PII/密钥脱敏，排除私聊与标记敏感的频道；条目可见性继承原始证据的最严权限（Slack/飞书模式）；保留 turn 级引用但不复制原文；反馈采集遵循"提交前可审阅附件"。
- **防投毒**：按 MINJA 的建议隔离"用户可写"的记忆与"组织知识库"；来自对话的候选条目在进入检索前必须经人审；记忆目录做路径校验与大小上限。

## KQ6 度量闭环：如何证明"从对话学习"确实改善了结果

### Takeaway
可行的证据链是：冻结的 held-out 查询集（含 unanswerable 与权限用例）上的回归评测 → KB 版本间的离线对比（groundedness/context precision/utilization + 任务级 pass^k）→ 线上 holdout 或 interleaving → 业务结果（resolution/deflection、hard-failure 率、重复提问率、人工升级率）。现有公开数字多为厂商自报（Fin 67%–76% resolution、SO Content Health +600% 编辑），学术侧给出的是方法级增益（ACE +10.6%、TF-GRPO +5.4%、RobustSGPO 60→80%），还没有组织公开"知识闭环上线前后"的严格对照。

### Cited Findings
- Anthropic 评测指南：从 20–50 个真实失败任务起步；pass@k（k 次中至少 1 次成功）与 pass^k（k 次全成功）区分；75% 单次成功率对应 pass^3 ≈ 42%；在静态任务库上跟踪延迟、token、成本、错误率建立基线；评测饱和到 100% 后只能当回归套件；0% 通过率通常意味着任务/grader 坏了；Opus 4.5 在 CORE-Bench 从 42% 修正 grader 与 scaffold 后约 95% [厂商] — [Anthropic](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)。
- Uber：SME golden set（100+ query）作为上线门槛；EAg-RAG 相对提升 27%/60%；Genie helpfulness 48.9%（见 KQ1）。
- Intercom Fin：resolution rate 67%（2025 末）、AWS 案例 30 天内 56%、聚合站 2026-06 称 76%、独立测试 38%、案例多集中 42–50%（见 KQ4）；一月更新提到 "automation rate tracking" 与 Optimize Dashboard 的内容/数据/动作建议 [二手] — [createwith](https://www.createwith.com/tool/intercom/updates/intercom-ships-january-fin-updates-with-automation-rate-tracking-and-ai-powered-)。
- Stack Overflow for Teams：+600% 月编辑活动（90 天）、87% 进队列者采取行动 [厂商] — [SO press](https://stackoverflow.co/company/press/archive/content-health/)。
- ACE：相对 GEPA / Dynamic Cheatsheet 的延迟与 rollout/token 成本下降（−82.3%/−75.1%、−91.5%/−83.6%）是"适配成本"维度的度量样板 [README] — [GitHub](https://github.com/ace-agent/ace)。
- RobustSGPO：30 个留出任务上 60%→80% [二手摘要] — [dair.ai](https://academy.dair.ai/papers/robustsgpo-search-space-control-for-agent-harness-evolution-2609.09646)。RESPECT：仅靠部署交互任务完成率 31%→82% [论文/摘要] — [arXiv](https://www.arxiv.org/pdf/2410.13852)。
- LongMemEval：500 题、5 能力，用于度量"知识更新"与"弃答"能力；30% 退化 [论文/代码] — [GitHub](https://github.com/xiaowu0162/LongMemEval)。
- Karpathy gist 评论区：小规模对照（8 次/条件）与 525 文档的"正确笔记到达答案率" 62%→89%，说明可用"证据到达率"做知识库层面的离线指标 [二手自报] — [gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)。
- A/B/interleaving 与冻结测试集实践（二手，见 KQ5）— [apxml](https://apxml.com/courses/optimizing-rag-for-production/chapter-6-advanced-rag-evaluation-monitoring/rag-offline-online-evaluation)，[zimaspace](https://shop.zimaspace.com/en-ca/blogs/tech-ai-hub/rag-evaluation-repeatable-test-sets-2026)。
- Hamel：以"theoretical saturation"（新 trace 不再出现新失败模式）作为 error analysis 收敛标准 [一手] — [hamel.dev](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html)。
- 厂商基准不可直接信：Mem0 自报 LoCoMo 92.5 vs 第三方 62–67（见 KQ4）。

### Inferences（度量方案）
- **离线层**（每次 KB 版本变更必跑）：held-out 查询集 = 过去 N 周真实问题去重抽样 + 人工正解 + 相关条目 id + unanswerable 标记 + 权限约束；指标：context precision / recall（按 id）、ContextUtilization、groundedness、答案正确率（LLM judge 允许 Unknown + 人工抽检校准）、hard-failure 复现率（对 runbook 类条目真实执行命令）。生产失败持续"提升"为新用例，旧用例版本化保留。
- **在线层**：KB-version holdout（10–20% 流量用旧版本索引）或 interleaving（同一回答混合两版本检索结果并按引用/使用判定胜负）；业务指标：重复提问率（同人同主题 7 天内再问）、人工升级/转 on-call 率、thumbs-down 率、任务完成信号（PR 合并、实验启动成功）、每千次回答 hard-failure 数。
- **闭环健康指标**：候选条目接受率、从证据产生到发布的中位时长、复核 SLA 达成率、AI 来源条目占比（provenance 审计）、冲突对数量趋势、覆盖缺口簇数量趋势。
- 统计注意：显式反馈率 1–5% 意味着按 thumbs 做 A/B 需要极大样本；优先用任务级与 agent 侧硬信号做主指标，thumbs 做辅助。

# 让知识库随系统变更与对话反馈持续演进

> 调研截止 2026-10-16。本报告综合五份研究笔记（知识采集与同步、表示与检索、从对话学习、评测方法、工业案例），并在相关处引用此前两份报告《Agent 发展现状与研发提效》与《AgentX 快手推荐自迭代Agent深挖》的结论。读者为 TikTok 推荐架构负责人；最后一节"设计结论"给出面向该团队的具体架构选择，详细设计文档将另行撰写。

**BLUF**：为一个全部门使用的 AI 研发助手设计知识库，公开证据给出的答案是：**不要做"一个向量库 + 一次检索"的 wiki 问答机**，而要做一个"源优先级明确、同步有对账、条目带版本与溯源、检索工具化、反馈经人审"的知识系统。采集上，最有价值的知识不是 wiki 而是**带结构的系统事实（服务目录、配置 schema、特征/实验平台）与历史记录（实验、事故、changelog）**，Uber Genie、LinkedIn、Meta、Google 的案例一致表明文档加载与结构化质量是第一瓶颈而不是模型。更新上，Glean、Microsoft、Google、Atlassian、GitHub 五家商用平台无一把增量通道当作删除与权限变更的真相来源，**周期性全量对账不可省**，webhook/事件驱动只是加速器；`valid_from/valid_to` 这类时态模型在公开资料中几乎缺席，必须自建。检索上，证据指向"**BM25/精确匹配是第一公民 + dense + rerank，通过 MCP 工具暴露给 agent 迭代调用**"；图只应从系统导出为语义层/属性图而不是让 LLM 从文本抽取（Microsoft 自家数据显示完整 GraphRAG 索引成本约为向量 RAG 的 1000 倍）；DeepSearch 只留给跨系统、多跳的复杂问题（多 agent 约消耗 15× token）。反馈上，**显式反馈在生产中不足 5%**，必须以隐式对话信号、任务结果与 agent 侧硬信号覆盖其余；归因按"曝光→引用→LLM 使用判定→反事实消融→Shapley"分层，知识健康度要做成带 owner 的工作队列而不是一个分数。最关键的发现是：**本次调研没有找到任何公开组织把"对话→知识更新"做成全自动闭环**——Intercom、Snowflake、Databricks、Guru、Uber、腾讯 RecSys Factory 全部保留人工批准，而 RAG Collapse（79.6% 模拟崩溃）、Misevolution、MINJA 等研究说明无人审写回的风险是真实的。评测需要五层（ID 级检索指标、本地校准的二元 judge、版本驱动的新鲜度 canary、条目评分卡、interleaving/A/B 在线），从 20–50 个真实失败任务起步。

> **取证说明（必读）**。研究所在沙箱封锁了 arxiv.org 及其镜像、uber.com、docs.glean.com、learn.microsoft.com、docs.cloud.google.com、zenml.io、infoq.com、openai.com、stripe.dev、feishu.cn、help.aliyun.com 等站点，且 WebSearch 配额在各条线中途耗尽。因此：论文类数字多来自搜索摘要与 GitHub README；Uber、Stripe、Pinterest、LinkedIn 等案例的量化结果多数只能追到二手转述；AgentX、RecSys Factory、AutoLR 三篇推荐系统论文均未通读全文。正文按以下约定标注：**厂商自报**（厂商/作者对自家系统的评测）、**据报道**（二手媒体/聚合站转述，未在一手原文核实）、**据摘要**（仅见于搜索摘要或论文摘要）、**推断**（本报告基于证据的推断）。未标注者为可直接打开的官方文档、论文或代码库原文。被研究员明确标为"未核实"或"不采信"的数字（如 Uber 13,000 小时、Salesforce 30K 小时/月、Intercom 76% 解决率、RecSys Factory 的腾讯归属）在本文中只以"据报道"出现或不出现。

## 一、采集：结构化系统事实优先，wiki 必须经 loader 富化，日志只存模板

2025–2026 年的企业知识平台在采集层已经收敛到同一套连接器骨架：先爬身份（用户、组、成员关系），再做周期性 full crawl，再做高频 incremental crawl，可选 webhook 或"直连不落库"。Glean 把爬取分为周期性的 full content crawl、只处理上次以来新增/修改条目的 incremental crawl 和跟踪权限变更等活动的 activity crawl ([Glean docs](https://docs.glean.com/connectors/crawling-types))；其 Indexing SDK 的流水线顺序是"先爬 identities，再为增量运行解析 last-crawl timestamp，再抓内容→转换→上传"，而且**SDK 不持久化 checkpoint，连接器作者必须自己实现 `_get_last_crawl_timestamp()`**；FULL 模式会把本次运行中缺席的文档当作 stale 删除 ([glean-indexing-sdk README](https://github.com/gleanwork/glean-indexing-sdk))。Microsoft 365 Copilot connectors 的自定义连接器同样由作者定义 full crawl 与 incremental crawl 的周期，删除检测"基于周期性 full crawl 中连接器发送的条目"完成，ACL 由 agent "stamp" 到条目上做 security trimming ([Graph connectors SDK overview](https://learn.microsoft.com/graph/custom-connector-sdk-overview))。Google Gemini Enterprise 把 entity sync 与 identity sync 拆成可分别排程的两条通道，并明确"incremental sync 不同步身份数据，也不同步实体删除" ([Gemini Enterprise connectors](https://docs.cloud.google.com/gemini/enterprise/docs/introduction-to-connectors-and-data-stores))。Atlassian Rovo 则把连接器分成 Synced（落库、计入配额）、Direct（查询时实时取、不落库）与 Smart Link 三类 ([Teamwork Graph connector types](https://support.atlassian.com/organization-administration/docs/teamwork-graph-connector-types/))，飞书 Aily 也区分"导入（需同步、有延时、效果更好）"与"直连（留在上游、及时感知、效果有折损）" ([飞书 Aily 数据预处理](https://www.feishu.cn/content/adcbsjqc))。这组事实对内部团队的含义很直接：**索引引擎不是工作量所在，连接器的 checkpoint 正确性、身份映射与删除/权限对账才是**；高变动或高敏感的源（实验平台、HR 类文档）宜走直连/联邦检索，低变动源落库以换取检索质量。

跨案例看，**最有价值的知识源不是 wiki，而是带结构的系统事实与历史记录**。Uber Genie 的迭代路径最有说服力：2024-10 上线时工程师每月在相关 Slack 频道提出约 45,000 个问题、信息分散在 Engwiki 与内部 Stack Overflow（据摘要） ([Uber blog](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot))；在安全与隐私域用 100+ 条 golden set 测试后发现初版答案"不完整、不准确或未能检索到正确细节"，于是回头做**文档侧富化（自定义 Google Docs loader + LLM 排版/元数据）与检索前后处理 agent**，据 ZenML 转述可接受答案相对提升 27%、错误建议相对减少 60% ([Uber EAg-RAG](https://www.uber.com/blog/enhanced-agentic-rag/)；[ZenML LLMOps DB](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-on-call-engineering-support))。Adobe 与 AWS 共建的开发者支持系统在原型阶段就把 content sync 与基础设施成本列为未解决问题（厂商自报检索准确率 +20%） ([AWS ML blog](https://aws.amazon.com/blogs/machine-learning/adobe-enhances-developer-productivity-using-amazon-bedrock-knowledge-bases/))。另一端，Meta 的 AI 辅助 RCA 用约 5,000 条历史调查样本微调 Llama 2 7B 做变更排序，据报道回测中 42% 案例真实根因进入 Top-5，并配置信度门控隐藏低置信结果 ([Meta Engineering](https://engineering.fb.com/2024/06/24/data-infrastructure/leveraging-ai-for-efficient-incident-response/)；[InfoQ](https://www.infoq.com/news/2024/08/meta-rca-ai-driven))；Google Cloud Assist investigations 的知识源是"支持知识库与内部 runbook"，并行分析日志、资产、指标，且使用调用者凭据、结果受其权限限制、重跑可能有差异 ([Google Cloud blog](https://cloud.google.com/blog/products/management-tools/gemini-cloud-assist-investigations-performs-root-cause-analysis)；[Cloud Assist docs](https://docs.cloud.google.com/cloud-assist/investigations))；Spotify 的 Honk 建在 Backstage 软件目录（所有权、依赖、组件元数据）之上 ([Backstage webinar](https://backstage.spotify.com/how-spotify-built-honk))；Stripe 的 Minions 把组织知识做成集中式内部 MCP server "Toolshed"，据报道约 500 个工具且 minion 默认只拿到刻意缩小的子集 ([InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/)；[ByteByteGo](https://blog.bytebytego.com/p/how-stripes-minions-ship-1300-prs))。LinkedIn 的 SQL Bot 由元数据、查询日志、wiki 与代码构建知识图谱，内部基准上专家审核 53% 回答"正确或接近正确"（据摘要） ([arXiv 2507.14372](https://arxiv.org/abs/2507.14372v1))。由此得到的源优先级是：**系统事实（可被工具调用的结构化层）> 历史记录（实验、变更、事故与 on-call 结论）> wiki/设计文档（需专门 loader 与 LLM 结构化）> 日志（作为运行时工具而非静态索引）**。

按模态看，代码侧的工具链最成熟，配置与实验记录则没有现成方案。代码的"存什么"是三层：AST 边界的 chunk、符号图与轻量 repo map。cAST（Findings of EMNLP 2025）用 tree-sitter 自顶向下"split-then-merge"，作者自报 RepoEval 检索 Recall@5 +4.3、SWE-bench Pass@1 +2.67，开源实现 astchunk 只"完整支持" Python/Java/C#/TypeScript，C++ 与 DSL 需自行扩展 ([cAST](https://aclanthology.org/2025.findings-emnlp.430/)；[astchunk](https://github.com/yilinjz/astchunk))；SCIP 按 commit 上传、Sourcegraph 维护 commit→uploads 的 commit graph ([Sourcegraph uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads))；Zoekt 用 trigram 索引加 ctags 符号排序，默认跳过 >1 MB 文件 ([zoekt](https://github.com/sourcegraph/zoekt)；[Sourcegraph admin search](https://sourcegraph.com/docs/admin/search))；aider 的 repo map 用依赖图排序把全库符号压到默认 1k token 随每次请求发送 ([aider repomap](https://aider.chat/docs/repomap.html))。Anthropic 的立场是 Claude Code 不建索引、靠 CLAUDE.md 预加载 + glob/grep 即时检索以"避免陈旧索引"，但官方 monorepo 指南同时写明"**如果组织已经在仓库上运行代码搜索或 RAG 索引，把它暴露为 MCP 工具让 Claude 查询**" ([Effective context engineering](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)；[Claude Code large codebases](https://code.claude.com/docs/en/large-codebases))。配置没有任何公开的面向 LLM 的切分方案，可用的旁证是 Kuaishou AgentX 的"多智能体抽取器把代码、配置、工程文档编译成 wiki 条目"并用 ingest–query–lint 保鲜（据摘要） ([AgentX](https://arxiv.org/pdf/2606.26859))，以及 Datadog `bits.md` 的建议——写跨系统命名映射（告警 `checkout_prd` / 工单 `CHECKOUT` / 日志 `checkout-service`）、环境值归一化与已知噪声模式，"写具体规则而不是一般描述，描述只是重复遥测里已能推断的东西" ([Datadog Knowledge Sources](https://docs.datadoghq.com/bits_ai/bits_investigation/knowledge_sources/))。日志的共识是**不存原始行**：Drain3 做在线模板挖掘并输出 `cluster_id`、`template_mined` 与变更类型，支持快照持久化 ([Drain3](https://github.com/logpai/Drain3))；LAPP 的做法是"Drain 聚类成模板（无 API 成本），LLM 只对模板做有界批量语义化"，引用 IBM 的 "cluster first (90%+ volume reduction)" 模式（该 90% 是模式描述而非实测） ([LAPP](https://pkg.go.dev/github.com/strrl/lapp))；Datadog Bits 把 runbook、`bits.md` 与反馈 memory 作为三类知识源，并建议只对 p1/p2 monitor 开启自动调查，因为"你不可能为所有 monitor 策划规则、runbook 与反馈" ([Datadog Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/))。实验记录应作为结构化表而非自由文本入库：AgentX 把"实验结果回流为结构化知识资产"，Auto-RecSys 把运行经验蒸馏为模型专属的自然语言 playbook（据摘要） ([Auto-RecSys](https://arxiv.org/pdf/2609.10922))，AutoLR 把外部研究、生产系统事实、领域知识与演化中的实验记忆**分别索引、选择性检索而非拼进单一上下文**（据摘要） ([AutoLR](https://arxiv.org/pdf/2609.04871))。

两条采集期的硬约束最后再说。第一是脱敏位置：实践指南一致要求 PII 检测与变换放在归一化之后、切分与 embedding 之前（"redacting after embedding is too late"），密钥要"阻断而非掩码"，并以单元测试、canary 字符串与 DLP 扫描验证脱敏 ([Prevent Sensitive Data Leakage in RAG](https://www.kunalganglani.com/blog/prevent-sensitive-data-leakage-rag))；Drain3 的 masking 可在模板挖掘前把 IP、数字、邮箱替换为掩码 ([Drain3](https://github.com/logpai/Drain3))。第二是入口文件与中心库的分工：Claude Code 官方建议 CLAUDE.md "每文件目标 200 行以内，更长会消耗上下文并降低遵循度"，排除"可从代码推断的内容、详细 API 文档、频繁变化的信息" ([Claude Code memory](https://code.claude.com/docs/en/memory)；[best practices](https://code.claude.com/docs/en/best-practices))；Codex 把沿路径拼接的 AGENTS.md 上限设为 32 KiB（据摘要）；OpenAI 的 harness engineering 实践据报道一开始把所有规则塞进巨型 AGENTS.md，结果"挤占任务上下文、快速腐化"，后改为约 100 行的地图指向结构化 `docs/` 目录，并提出"what Codex can't see doesn't exist" ([InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex))。中心知识库对 agent 最有价值的输出形态因此是"可链接的稳定 URL + 时间戳 + 按权限裁剪的 markdown"——Datadog 与 Claude Code 文档都为每页提供 `.md` 版本并发布 `llms.txt` 索引 ([docs.datadoghq.com/llms.txt](https://docs.datadoghq.com/llms.txt))，agent 会把这些指针写进 AGENTS.md / bits.md。

## 二、持续更新：增量通道不传删除与权限，全量对账与时态版本都要自建

变更检测的行业共识可以压缩成一句话：**文档级哈希/时间戳决定要不要重处理，周期性全量对账决定删除，chunk 级精细失效基本靠自建**。LlamaIndex 的 docstore 策略是 `upserts`（id 新或 hash 变化则重处理）、`duplicates_only`（只按 hash 判重）与 `upserts_and_delete`（并删除输入中已不存在的文档），策略依赖跨运行持久化的 docstore，且社区指出以文本 hash 作 doc_id 无法识别"同一文档被原地修改" ([LlamaIndex document management](https://developers.llamaindex.ai/python/examples/ingestion/document_management_pipeline/))。Airbyte 的 "Incremental | Append + Deduped" 以 cursor 判断是否复制、以主键去重，语义是 at-least-once；**修改了记录但未更新 cursor 列的变更会被增量漏掉** ([Airbyte docs](https://docs.airbyte.com/platform/using-airbyte/core-concepts/sync-modes/incremental-append-deduped))。Microsoft GraphRAG 的文档 id 用文本哈希保证跨运行稳定，索引 API 有 `is_update_run` 与独立的 `update_output_storage`，communities 表带 ISO8601 的 `period` 用于增量合并 ([GraphRAG inputs](https://github.com/microsoft/graphrag/blob/main/docs/index/inputs.md)；[graphrag/api/index.py](https://github.com/microsoft/graphrag/blob/main/packages/graphrag/graphrag/api/index.py))；LightRAG 删除文档时用索引期的 LLM 缓存重建受影响实体而不重新抽取，但**更换 embedding 模型后"现有向量与新模型空间不匹配且不会自动重嵌"**，必须用 `lightrag-rebuild-vdb` 从图与 `text_chunks` 这两个"权威源"重建，其 `source_conflict_repair` 对声称同一 canonical source key 的重复文档"从不自行选赢家、从不删除内容" ([LightRAG README](https://github.com/HKUDS/LightRAG)；[ProgramingWithCore.md](https://github.com/HKUDS/LightRAG/blob/main/docs/ProgramingWithCore.md))。代码侧的参照更精细：Sourcegraph 把限定到具体仓库的搜索做成"始终最新"（用户动作触发抓取），而跨大量仓库的未限定搜索"可能落后最新 default branch 一段时间，取决于仓库数与索引算力" ([Sourcegraph code search](https://sourcegraph.com/docs/code-search/features))；SCIP 上传任何到/离开 COMPLETED 的状态变化都要重算 commit graph，期间仓库标为 `stale`，且这一重算"对 worker 或 Postgres 可能很昂贵" ([Sourcegraph uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads))；auto-indexing 默认每 2 分钟调度一次、同一仓库至少 24 小时才重新考虑一次 ([Auto-indexing](https://sourcegraph.com/docs/code-navigation/auto-indexing))。Cursor 据报道用客户端文件哈希 Merkle tree 同步到服务端做增量索引 ([Towards Data Science](https://towardsdatascience.com/how-cursor-actually-indexes-your-codebase/))；块级增量的公开样例只有 Obsidian 的飞书同步插件——记录 Markdown 顶层块与飞书 block id 的映射，只更新变化的块，无法安全增量时降级为全量覆盖 ([feishu-lark-cli-sync](https://community.obsidian.md/plugins/feishu-lark-cli-sync))。可配置周期的下限方面，Microsoft 的 ADLS Gen2 连接器示例为增量 15 分钟、全量 1 周 ([Microsoft ADLS connector](https://learn.microsoft.com/lt-lt/microsoftsearch/azure-data-lake-connector))，阿里云百炼的数据同步周期最小 1 分钟 ([百炼数据同步](https://help.aliyun.com/zh/model-studio/data-sync-guide))；真正的秒级只能靠 webhook 或直连。下表把公开可见的同步机制按"能否覆盖删除与权限"对齐，这是选型时最容易被忽略的两列。

| 机制 | 代表实现 | 典型延迟 | 覆盖删除 | 覆盖权限变更 | 主要风险 / 成本 | 适用源 |
|---|---|---|---|---|---|---|
| 周期性 full crawl / 对账 | Glean FULL 模式（缺席即 stale 删除）、Microsoft full crawl、Google full sync | 小时到周（Microsoft ADLS 示例 1 周） | 是 | 是（Google 以独立 identity full sync 实现） | 成本最高；对账期间旧条目仍可检索 | 所有落库源的兜底 |
| 时间戳 / cursor 增量 | Glean INCREMENTAL（`since`）、Microsoft incremental（示例 15 min）、Airbyte cursor、百炼（最小 1 min） | 分钟级 | 否（五家平台均不传删除） | 否（Microsoft 明确"不支持处理权限更新"） | cursor 未更新即漏；at-least-once 需去重 | wiki、工单、设计文档 |
| 文档级内容哈希 | LlamaIndex docstore `upserts`、GraphRAG `id = hash(text)` | 取决于触发 | `upserts_and_delete` 可 | 否 | 哈希作 id 识别不了原地修改；需持久化 docstore | 文档与配置快照 |
| chunk 级稳定 ID 增量重嵌 | Obsidian block-id 映射、Cursor Merkle tree（据报道）、按 AST 节点签名派生 id（推断） | 秒到分钟 | 需配合全量 | 否 | 无通用开源实现，需自建 | 代码、长文档 |
| webhook / 活动爬取 / 事件驱动 | Glean activity crawl、GitHub Copilot Spaces "随变更自动更新"、git hooks、平台事件 | 秒到分钟 | 部分（依赖事件完整性） | Glean 称 activity crawl 跟踪权限变更 | 事件丢失不可自愈，仍需对账 | 代码仓、实验平台、配置中心 |
| 联邦 / 直连（不落库） | Rovo Direct connector、飞书 Aily 直连、Datadog "链接即读" runbook | 实时 | 天然 | 天然（查询时按源权限） | 检索质量折损、源限流、延迟 | 高敏感或高变动源 |
| 身份 / ACL 同步 | Glean identity crawl + groups/memberships 通道、Google identity sync、Microsoft external groups | "下一次计划爬取之后" | 不适用 | 是 | 组无成员→ACL 永不匹配（Glean SDK 直接报错）；把成员展开进条目 ACL 触发海量更新 | 必须作为独立通道 |
| 图索引增量 | GraphRAG `is_update_run`（追加合并）、LightRAG（LLM 缓存重建） | 批处理 | 部分（GraphRAG 撤回文档据报道需全量重建） | 否 | 全量 GraphRAG 索引成本极高（见第三节） | 仅在确需图时 |

版本、溯源与血缘在公开系统中的成熟度明显分层。代码侧有成熟的 "as-of" 模型：Sourcegraph 维护"从仓库 commit 到能解析该 commit 查询的 uploads 集合"的映射，上传可被更新上传替代或按年龄过期，"Index all version tags" 策略可让标签对应的 commit 持续保留索引；索引器会在分支间去重文档，每仓库最多 64 个分支 ([Sourcegraph uploads](https://sourcegraph.com/docs/code-navigation/explanations/uploads)；[Admin search](https://sourcegraph.com/docs/admin/search))。文档与图谱侧则只做到"内容哈希 id + 摄取时间 + 来源定位符"：GraphRAG 的 `period` 字段、LightRAG 的文档处理状态与 canonical source key、Claude Code 记忆文件 frontmatter 中的 `modified` ISO 8601 时间戳（"显示该事实有多新，给你也给读回记忆的 Claude 看"） ([Claude Code memory](https://code.claude.com/docs/en/memory))。**`valid_from/valid_to/supersedes` 这类时态建模在所有被查阅的产品文档中都没有出现**，最接近的是 Zep 的 Graphiti："信息变化时旧事实被失效而非删除"，显式双时态（事件时间 + 摄入时间），边解析时由 LLM 判断冲突并把旧边的 `invalid_at` 设为新事实的 `valid_at` ([getzep/graphiti](https://github.com/getzep/graphiti))。综合这些先例，本报告推断的定位符设计是：代码用 `repo + path + commit + symbol(SCIP)`，文档用 `source_system + doc_id + content_hash + fetched_at`，配置用 `config_repo + key_path + commit/env`，日志用 `template_id + first_seen/last_seen`，实验用 `experiment_id + metric snapshot period`；文档侧最务实的 as-of 做法是**只保留当前有效版本加 supersedes 指针与变更日志，历史版本留在源系统（wiki/git）里按需回溯**，而不是在知识库里复制整条历史。记忆/反馈类知识（Datadog 的 memory、Claude 的 auto memory）随系统演进失效更快，Datadog 明确建议定期检查旧的纠错记忆是否仍成立，"服务会改名、原因会被修掉" ([Datadog Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/))。

访问控制的行业标准是"文档级 ACL stamping + 查询时 security trimming"，但各家都承认权限变更有延迟，而最大风险不在引擎而在源端。Microsoft 的 externalItem ACL 支持 Entra user/group 与 `Everyone`，`deny` 优先于 `grant`；非 Entra 的组应通过 group sync API 建 external groups 并保持成员同步，**"避免把 external group 的成员直接展开进单个条目的 ACL，因为每次成员变化都会导致大量条目更新"**；用户超过 2,049 个外部安全组成员时"结果不可预测"，超过 10,000 个则查询直接 400 ([Manage items](https://learn.microsoft.com/graph/connecting-external-content-manage-items)；[External groups](https://learn.microsoft.com/graph/connecting-external-content-external-groups))。Glean 多个连接器的权限变更要等"下一次计划爬取完成后"才生效，web crawler 连接器根本不做按用户的权限传播 ([Glean Interact connector](https://docs.glean.com/connectors/custom/connector-guides/interact)；[Glean web crawler](https://docs.glean.com/connectors/native/web-crawler/home))。飞书的表述最适合写进产品说明："权限决定能看什么，检索决定找到什么，核对决定能不能用"，同一问题不同人可能得到不同答案，并建议管理员用代表性账号逐项验证 ([飞书：权限继承、检索与结果核对](https://www.feishu.cn/content/article/7667878406574328795))。Copilot 的"过度共享"问题据多篇咨询博客（二手）归因于 SharePoint 的 "Everyone" 组、断裂的继承与过期分享链接——security trimming 只保证"返回用户能访问的内容"，却让"用户能访问的一切"都进入提示窗口 ([EPC Group](https://www.epcgroup.net/copilot-sharepoint-permissions-oversharing-fix-2026))。对推荐部门知识库的推断是：把组成员关系作为一等实体单独同步；高敏感源（HR、安全策略、未发布的实验结论）走直连或缩短身份同步周期而不是落库；配置与日志在 key-path 或模板层做密钥字段黑名单并阻断。

新鲜度的厂商口径几乎都是定性的"下一次计划爬取后"，没有任何一家公布索引延迟或 staleness 的 SLA 与测量方法；可量化的硬数字只有 Microsoft 的"活动超过 7 天不展示" ([Manage items](https://learn.microsoft.com/graph/connecting-external-content-manage-items)) 与 Sourcegraph 的 `stale` 状态。危害侧的证据倒是明确：Datadog 写道"过期的 runbook 链接比没有链接更糟，因为它把 Bits 指向错误的看板或已下线的服务" ([Datadog Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/))；Slite 对 143 人的厂商调查称超过四分之三的人见过公司 AI 工具引用过时文档给出错误答案 ([Slite](https://slite.com/learn/dangers-of-stale-documentation))；Unblocked 指出相似度排序会让"写得漂亮的旧页"压过"新的修正"，单靠新鲜度元数据不够，需要显式的 superseded-by 关系 ([Unblocked](https://getunblocked.com/blog/stop-agents-using-stale-documentation/))；飞书建议为关键资料指定负责人、生效日期与适用范围 ([飞书：资料质量与权限边界](https://www.feishu.cn/content/article/7667878414023396328))。既然没有外部基准，内部 SLO 只能自定义：本报告建议按源类型分档统计 `source_mtime` 与 `index_time` 之差的 p50/p95（代码分钟级、wiki 小时级、ACL 不超过一个身份同步周期）、删除对账周期、入口文件中失效指针的占比、每周重嵌入 token 数，以及"组无成员 / ACL 为空"的告警数——这五个指标覆盖了公开案例里反复出现的全部失败：增量漏删除与 ACL、cursor 未更新、组无成员、过期指针、换模型后旧向量静默失效。

## 三、表示与检索：词法匹配是第一公民，图从系统导出而非 LLM 抽取，DeepSearch 只给复杂问题

分块的 2025–2026 共识是"结构优先、补上下文、再用自己的 query 集评测"。Anthropic 的 Contextual Retrieval（厂商自报）对每个 chunk 用整篇文档生成 50–100 token 的情境说明再同时做 embedding 与 BM25：top-20 检索失败率从 5.7% 降到 3.7%（contextual embeddings）、2.9%（再加 contextual BM25）、1.9%（召回 150 重排取 20），即 −35%/−49%/−67%，借助 prompt caching 一次性成本约 **$1.02 / 百万文档 token**；同一实验里 HyDE 与摘要式索引"表现差"，知识库小于 200k token 时建议整体放进 prompt ([Anthropic](https://www.anthropic.com/news/contextual-retrieval))。第三方拆解指出 67% 是四域平均，"Codebases-Vague" 类只有 41%，即技术语料收益明显低于叙事文本 ([Almond AI](https://medium.com/almond-ai/responding-to-anthropics-contextual-retrieval-for-rag-apps-why-context-is-not-all-you-need-af503985aa55))。chunk 大小没有通用最优值：同一方法下 SQuAD 在 64 token 时 recall@1 最高，而**技术文档集 TechQA 从 128 token 的 16.5% 升到 512 token 的 61.3%** ([arXiv 2505.21700](https://arxiv.org/pdf/2505.21700))。由此推断的分模态方案是：设计文档按标题层级切 300–800 token 并前置"标题 + 章节路径 + 情境"；代码按 AST 切并加文件路径与符号签名头；配置不按 token 切而按键路径展平成键值行、附文件与 commit，走精确匹配优先的索引；日志只索引模板，原文留指针由工具按需拉取；实验记录走结构化表；runbook 整篇作为一个 Skill 单元只索引 name/description。

混合检索的证据一致指向**精确标识符匹配不可或缺**。Anthropic 在 contextual embeddings 之上加 contextual BM25 又把失败率降了 14 个百分点 ([Anthropic](https://www.anthropic.com/news/contextual-retrieval))；2026-05 的 "Is Grep All You Need?" 在 LongMemEval-S 上发现 inline 交付下**词法 grep 在每一个 harness–model 组合上都优于 dense 检索**，但 harness 本身影响同样大——同一 Claude Opus 4.6 在两个 harness 下相差 16 个百分点（93.1% vs 76.7%） ([arXiv 2605.15184](https://arxiv.org/abs/2605.15184))；CodeRAG-Bench 则报告检索器在 query 与文档词法重叠低时最差、无关上下文可能有害 ([CodeRAG-Bench](https://arxiv.org/html/2406.14497v2))。融合收益随语料波动极大：一篇电商 WANDS 复现里 RRF 只比 BM25 高约 1%，调参后 +7.4%，而一次未调参的融合 MRR 反而低于 dense-only（二手） ([tianpan.co](https://tianpan.co/blog/2026-04-12-hybrid-search-production-bm25-dense-embeddings))。模型层面，2026-09 的 MTEB 多语榜据报道已由开源模型领先（Microsoft harrier-oss-v1-27b 74.31、Tencent KaLM-Embedding-Gemma3-12B 72.32、Qwen3-Embedding-8B 70.75），而 voyage-4、Cohere embed-v4、gemini-embedding-2 基本未提交，所以闭源旗舰的"MTEB 分数"多为厂商自述 ([andrew.ooo](https://andrew.ooo/answers/best-embedding-models-2026-ranked/))；Qwen3-Embedding/Reranker 以 Apache 2.0 发布，厂商自报 C-MTEB 73.84、reranker MTEB-Code 81.2 ([Qwen3-Embedding](https://github.com/QwenLM/Qwen3-Embedding))；代码检索的独立基准 CoQuIR 显示除 voyage-code-3 外所有模型都至少在一个数据集低于随机基线 ([arXiv 2506.11066](https://arxiv.org/pdf/2506.11066))。更重要的警示来自 BRIGHT：MTEB 榜首模型（59.0）在推理密集型检索上 nDCG@10 仅 18.0，而在查询中加入显式推理最多能提升 12.2 分 ([BRIGHT ICLR 2025](https://www.iclr.cc/virtual/2025/poster/27702))——对标识符密集的内部工程语料（PSM、特征名、配置键、实验 ID），这意味着 BM25/精确匹配要作为默认路，RRF 起步后用自有 query 集调权，并把"精确标识符查询的 recall"作为独立监控指标。

代码检索的两条路线在 2026 年已被证明互补。Claude Code 官方工具链只有 Glob（按修改时间排序、上限 100 文件）、Grep（ripgrep）、Read（单次 25,000 token）与 LSP 插件，没有任何向量工具，官方列出的失败模式是"infinite exploration"——未限定范围的调查读数百个文件撑满上下文 ([Claude Code tools reference](https://code.claude.com/docs/en/tools-reference)；[best practices](https://code.claude.com/docs/en/best-practices))。Cursor 的另一条路线是 Merkle 增量同步 + tree-sitter 分块 + 用 agent 会话轨迹训练的自研 embedding，厂商自报离线问答准确率平均 +12.5%（按模型 6.5%–23.5%）、线上代码留存 +0.3%（大代码库 +2.6%）、不满意追问 −2.2%，并明确"**语义检索与 grep 组合效果最佳**" ([Cursor blog](https://cursor.com/blog/semsearch))。独立的定位研究把 harness 的分量量化了：文件级定位 BM25 Acc@1 38.7%、代码专用 embedding 52.6%，而 Agentless 式分层 LLM 定位达到 72.6% ([LocAgent](https://arxiv.org/pdf/2503.09089))。对 TikTok 规模（数百万文件、C++/Python/DSL 混合）的推断是：底层用 Zoekt 式 trigram 索引 + SCIP/LSP 符号索引作为 agent 的 grep/定位工具（本地 ripgrep 无法秒级扫数百万文件），语义索引作为第二工具按子系统分 namespace 并做 Merkle 增量，两者都以 MCP 工具暴露并在描述里写清"何时用词法、何时用语义"，再以 aider repo map 思路为每个子系统生成 1–4k token 的符号地图放进目录级 CLAUDE.md；DSL 若无 tree-sitter grammar，由生成器侧导出符号表与依赖边进同一符号索引。Anthropic 的工具设计原则同样适用于检索工具：工具集小而不重叠、返回名称而非 UUID、分页/截断并告诉 agent 如何调整，工具描述重写曾使任务完成时间 −40% ([Writing tools for agents](https://www.anthropic.com/engineering/writing-tools-for-agents)；[multi-agent research system](https://www.anthropic.com/engineering/multi-agent-research-system))。

图与结构化知识的定位已经收敛：**对局部事实问答，向量/词法 RAG 仍是最强基线；图的价值在全局聚合与多跳；而推荐系统工件应从系统导出属性图/语义层，不要让 LLM 从文本抽图。** GraphRAG-Bench（ICLR 2026）的动机陈述就是"GraphRAG 在许多真实任务上频繁不如 vanilla RAG" ([arXiv 2506.05690](https://arxiv.org/pdf/2506.05690))。Microsoft 自家的 LazyGraphRAG 把索引成本降到完整 GraphRAG 的 0.1%（与向量 RAG 相同）、查询成本低 700 倍以上，BenchmarkQED 中它在全部 96 组对照里胜出，并且**把向量 RAG 上下文从 8k 扩到 120k 并未缩小差距，在 GPT-4.1 1M 上下文对照下仍全面胜出**（厂商自报，方法公开） ([LazyGraphRAG](https://www.microsoft.com/en-us/research/blog/lazygraphrag-setting-a-new-standard-for-quality-and-cost/)；[BenchmarkQED](https://www.microsoft.com/en-us/research/blog/benchmarkqed-automated-benchmarking-of-rag-systems/))；LightRAG 对 NaiveRAG 的胜率 60–85% 主要来自 Diversity 维度（厂商自报） ([LightRAG](https://github.com/HKUDS/LightRAG))；HippoRAG 2 在多跳 MuSiQue 上 54.4、显著领先 ([HippoRAG](https://github.com/OSU-NLP-Group/HippoRAG)；[arXiv 2607.11683](https://arxiv.org/pdf/2607.11683))。对"配置/特征/实验/上线"这类强结构工件，证据更支持语义层 + text-to-SQL：dbt 报告在语义层上回答使 Claude Sonnet 4.6 从 90.0% 升到 98.2%、GPT-5.3-Codex 从 84.1% 到 100%（11 题，厂商自报），仅做 schema 建模就从 64.5% 到 90.0% ([dbt blog](https://docs.getdbt.com/blog/semantic-layer-vs-text-to-sql-2026))；Databricks Genie 被引述在 15 题集上 53%（裸 schema）→80%（元数据）→100%（指标定义 + 示例 SQL）（二手） ([Atlan](https://atlan.com/know/ai-agent/data-for-ai/text-to-sql-for-enterprise/))；Uber QueryGPT 引入按业务域策划的 Workspaces，原因是部分 Tier-1 表有 200+ 列、单表 schema 消耗 40–60K token ([Uber QueryGPT](https://www.uber.com/blog/query-gpt))；Pinterest 以表摘要与历史查询摘要建索引，据报道首次接受率从 20% 升到 40%+ ([ZenML](https://www.zenml.io/llmops-database/text-to-sql-system-with-rag-enhanced-table-selection))。推荐系统侧最直接的先例是 AgentX 的 System KB——"schema 层、Markdown wiki 条目层、可回溯到原始代码/配置的 raw-source 层"三层结构，通过 ingest–query–lint 生命周期保鲜，用于拒绝违反流水线边界或依赖不可用特征的想法（据摘要） ([AgentX](https://arxiv.org/pdf/2606.26859))。推断的设计是：特征注册表、模型配置、实验平台、发布系统、服务拓扑（PSM 上下游）都已有结构化事实源，把它们建成带版本与时间的表并配语义层（指标/实体/关系定义 + 示例 SQL），作为 agent 的一个工具；非结构化文档中的实体（特征名、实验 ID）做实体链接到这些表，形成"先查表、再读文档"的两跳；评测按局部事实（向量/词法必须赢）、全局聚合（语义层/图应赢）、多跳（PPR 类候选）分别做。

DeepSearch 相对单次 RAG 的收益与代价都很明确。Jina 把 DeepSearch 定义为 "search → read → reason" 直到找到答案或超预算的状态机，其开源实现用 gaps 队列、子问题去重、"某动作无新产出时下一步禁用该动作"与预算耗尽后的 Beast Mode 强制作答，示例运行步数从 2 到 42 ([node-DeepResearch](https://github.com/jina-ai/node-DeepResearch))。Anthropic 的多 agent 研究系统比单 agent Opus 4 高 **90.2%**，但多 agent 约消耗 15× 聊天 token，BrowseComp 上 token 用量单独解释 80% 方差；观察到的失败包括"为简单问题起 50 个子 agent"、无休止寻找不存在的来源、已足够仍继续搜索，缓解是写进 prompt 的 effort scaling 规则（简单事实 1 个 agent、3–10 次工具调用）与独立的 CitationAgent ([Anthropic multi-agent](https://www.anthropic.com/engineering/multi-agent-research-system))。OpenAI 的 BrowseComp 上 Deep Research 51.5% 而 GPT-4o 加浏览仅 1.9%，说明"仅有浏览能力不够" ([OpenAI BrowseComp](https://openai.com/index/browsecomp/))；固定语料的 BrowseComp-Plus 示例中 gpt-oss-20b 平均每题 12.6 次搜索调用 ([BrowseComp-Plus](https://github.com/texttron/BrowseComp-Plus))。对内部工程知识，"RAG 已死、agentic 搜索取代一切"不成立：agentic 搜索的每一步仍是检索，检索质量上限直接决定 agent 上限；LazyGraphRAG 在 1M 上下文对照下仍胜出说明"全塞进去"在质量上也不占优；15× 成本与分钟级延迟意味着 DeepSearch 只应用于高价值的复杂问题。本报告推断的架构是：路由层按问题类型分流（单点事实/配置项走 <2 s 的单次 hybrid RAG，跨系统/多跳/"为什么"/排障走 10–30 次工具调用、1–3 个子 agent 的 DeepSearch）；工具层以 MCP 暴露 `lexical_search`、`semantic_search`、`kb_sql`（语义层上的 text-to-SQL）、`read_doc`（分页、25k token 上限）与 `fetch_runbook`（Skill 加载）；循环控制采用 Jina 式 gaps 队列与 Anthropic 式 effort scaling；验证层由独立 CitationAgent 把每个结论绑定到 `path@commit` / `doc@version` / SQL 结果并做新鲜度检查。RL 训练的搜索 agent（Search-R1、Tongyi DeepResearch 等）在 2026 已有开源路线，但缺乏"内部 KB 场景"的公开收益数据，应作为第二阶段实验。

长上下文没有消除检索，但改变了"检索到之后给多少"的答案。Chroma 对 18 个前沿模型的测试显示即便简单任务准确率也随输入变长下降，相似但错误的干扰段落明显伤害准确率，**连贯结构良好的文档比随机打乱的 chunk 更难检索** ([chroma-core/context-rot](https://github.com/chroma-core/context-rot)；[Morph 综述](https://www.morphllm.com/context-rot))；据报道 MRCR v2（8-needle）在 1M 处 Claude Opus 4.6 约 76–78%、GPT-5.4 约 37%、Gemini 3 Pro 约 25%，版本间不可比 ([yage.ai](https://yage.ai/share/long-context-benchmark-en-20260315.html))；Self-Route 的结论是资源充足时长上下文平均优于 RAG 但贵得多，自评路由可在接近长上下文质量下大幅降成本 ([arXiv 2407.16833](https://arxiv.org/abs/2407.16833v1))。经济上，Anthropic 的 prompt caching 读取为基价 0.1×（最新模型 0.025–0.05×）、5 分钟写入 1.25×、1 小时写入 2× ([Anthropic prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching))，使"稳定前缀（系统提示 + 工具定义 + skills 元数据 + 子系统符号地图）+ 变动问题"的成本可降约一个数量级，但只对 <200k token 的稳定语料划算。因此正确模式是"检索定位 → 整文档/整文件加载"：对已命中的单篇文档整篇读入比碎片 chunk 更利于理解，而不是用 1M 窗口替代索引。Agent 消费的知识格式由此分层：每次会话都需要、agent 无法自行推出且稳定的规则放 CLAUDE.md/AGENTS.md（<200 行、按目录分层）；多步流程、子系统操作手册与带脚本的检查放 Skill——Anthropic 的 Agent Skills 以三级渐进披露（启动只载 name/description，相关时读全文，捆绑文件按需）使"可捆绑的上下文实际上无上限"，并建议先用代表性任务评测找真实缺口再写 skill ([Anthropic Agent Skills](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills))；踩坑/教训放结构化 pitfall 表并按任务类型检索注入——RecSys Factory 把 29 个 SKILL.md 与从中抽取的 pitfall 表（v1.0 共 400 条，上一份报告记录约 200 条来自 skill spec、194 条来自 changelog）称为 agent 的 working memory，但本轮研究员未能在摘要中核实 "PitfallStore" 这一名称与腾讯归属 ([RecSys Factory](https://arxiv.org/pdf/2608.11241))；个人纠正与偏好放 auto memory（Claude Code ## 四、从对话中学习：显式反馈不足 5%，归因要分层，健康度是队列，写回必须过人

显式反馈在生产系统中极其稀疏，且带强自选择偏差。Amazon 的生产聊天机器人论文写道"fewer than 5% of responses receive any user feedback"，两个观察月份约 3%，并指出用户在反应强烈时更可能反馈 ([Amazon Science](https://assets.amazon.science/32/ce/33b9c3994947814c39da3995151c/scipub-approval152129-45631012-from-metrics-to-meaning-estimating-user-feedback-using-llmbased-evaluation.pdf))；Cider Chat 的开发者助手给每条回复都配了 thumbs 按钮但"usage is sparse"，转而从开发者后续 prompt 的隐含情绪中提取满意度（据摘要） ([arXiv 2509.18361](https://arxiv.org/pdf/2509.18361))；RESPECT 利用用户的 rephrasing、挫败表达与话题转移，仅靠部署交互把任务完成率从 31% 提到 82%（据摘要） ([arXiv 2410.13852](https://www.arxiv.org/pdf/2410.13852))；ChatGPT 用户调查发现 thumbs 最常用、开放文本最少，而 regenerate 得到的回答几乎从不与原回答相同，使其反馈语义模糊 ([arXiv 2408.15066](https://arxiv.org/pdf/2408.15066))。两组工业数字说明用户评分系统性高估正确性：Uber Genie 用 Resolved / Helpful / Not Relevant 三选一反馈，据报道 helpfulness rate 48.9% ([InfoQ](https://www.infoq.com/news/2024/10/uber-genie-rag-copilot))；LinkedIn SQL Bot 据报道 95% 用户评价为 "Passes" 或更好，而内部基准上专家审核只有 53% "正确或接近正确"（据摘要） ([Substack 转述](https://nirajpandkar.substack.com/p/issue-14-linkedins-llm-powered-text)；[arXiv 2507.14372](https://arxiv.org/abs/2507.14372v1))。Glean 进一步指出传统点击指标不适用于"自己生成答案、无需用户进一步交互"的助手，投票只来自部分用户且有偏（据摘要） ([Glean AI Evaluator](https://glean.com/blog/glean-ai-evaluator))。因此业界共识是把显式反馈当校准集，用隐式行为、任务结果与 LLM 估计器覆盖其余 95% 以上的 turn，并在 agent 场景优先采用可验证的环境结果——Anthropic 的评测指南强调"评分看 agent 产出而非路径"、检查最终环境状态而非 agent 自述（"说 booked 不算，数据库里有预订才算） ([Anthropic Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))；Datadog 则提醒"'That's wrong' gives Bits nothing to change"，高质量纠错必须含真实根因与指向根因的遥测链接 ([Datadog Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/))。下表按覆盖率与噪声整理了可用信号；每条都应能回溯到 `turn_id` 与被检索/被使用的条目 id。

| 信号 | 示例 / 来源 | 覆盖率 | 噪声与偏差 | 对知识条目的证据价值 | 处理建议 |
|---|---|---|---|---|---|
| 显式 thumbs / 评分 | Uber 三选一；Microsoft 365 Copilot 提交前只采集 thumbs 选择 | <5%（Amazon）；从业者称 1–3%（二手） | 强自选择偏差；用户高估正确性（LinkedIn 95% vs 53%） | 中：方向明确但稀疏 | 作为校准集与辅助指标，不作主指标 |
| 用户纠正文本（"不对，应该是…"） | 对话内直接表态 | 低 | 纠正本身可能错 | **最高**：同时给出正解 | 进入"纠正型 FAQ"候选，需二次确认 |
| Regenerate | ChatGPT 最常用之二 | 低到中 | 语义模糊（新答几乎从不相同） | 弱 | 仅当用户基于新答继续工作时记为对首答的负例 |
| 对话内隐式信号（改写、澄清追问、放弃、挫败） | RESPECT、Cider Chat | 高（每轮可算） | 中；需 LLM 估计器并以显式反馈校准 | 中 | 训练/提示满意度估计器，定期用人工标注查漂移 |
| 行为信号（点击引用、复制、打开原文） | Glean 指出对生成式答案不适用 | 低 | 点击原文可能意味着"答得不够" | 弱 | 只做曝光统计的权重，不做质量归因 |
| 任务结果（测试通过、PR 合并、命令成功、工单/实验关闭） | Anthropic"查环境状态" | 中（仅任务型会话） | 低噪声但延迟、受其他因素混杂 | 强 | 作为在线主指标与归因的 outcome 项 |
| Agent 侧硬信号（按 runbook 执行报错、配置被 schema 拒绝、引用路径不存在） | 本报告推断 | 仅 agentic turn | 几乎无偏 | **最强**的"文档错/过时"证据 | 直接给条目 harmful +1 并生成待验证任务 |
| 重复提问（同人同主题 7 天内再问） | 本报告推断 | 中 | 中（可能是新问题） | 中 | 复合进 resolution 口径 |
| 升级到人工 / on-call | Uber Genie 场景 | 低 | 明确负向 | 强（对该会话） | 必入复核队列 |

把会话级结果分到具体知识条目，可用方法按成本递增分五层。ContextCite（NeurIPS 2024）以句子为来源单位做上下文消融，用稀疏线性代理拟合"保留哪些来源时原响应生成概率如何变化"，论文称约 32 次消融即稳定优于基线、归因成本约为生成的 32 倍，并区分 contributive 与 corroborative 归因（据摘要） ([ContextCite](https://arxiv.org/pdf/2409.00729)；[MadryLab/context-cite](https://github.com/MadryLab/context-cite))；AttriBoT 把 leave-one-out 误差当作归因的原则性量，用缓存激活、层级归因与小代理模型实现 >300× 加速，归因比生成快 30 倍（据摘要） ([AttriBoT](https://arxiv.org/pdf/2411.15102))；MIRAGE 用模型内部显著性做无训练归因，并指出 self-citation prompting "常不匹配格式、引用不存在的来源、不忠实反映上下文使用" ([MIRAGE](https://arxiv.org/pdf/2406.13663))；RAG 的 Shapley 方法把每个文档当博弈玩家，每次效用评估都是一次 LLM 调用，近似方法中 Kernel SHAP 与 ContextCite 最接近精确值（据摘要） ([arXiv 2507.04480](https://arxiv.org/html/2507.04480v1))。可全量负担的是 LLM 使用判定：RAGAS 的 `ContextUtilization` 在无参考答案时用生成的回答逐 chunk 判断是否被用到并按排名加权 ([RAGAS context precision](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/context_precision.md))，Galileo 的 Chunk Attribution/Utilization 用自训小模型判定每个 chunk 是否影响回答、被用到的比例，并给出诊断规则（利用率低且相关度低 → chunk 太长；利用率低但相关度高 → 生成器没用好） ([Galileo Chunk Attribution](https://docs.galileo.ai/concepts/metrics/rag/generation-quality/chunk-attribution.md))。条目级信用累积有现成模式：ACE 的 Curator 把教训转成带 helpful/harmful 计数器的结构化 delta 并确定性合并、去重、剪枝 ([ACE](https://github.com/ace-agent/ace))，ExpeL 的 insight 列表以 ADD/UPVOTE/DOWNVOTE/EDIT 维护 ([ExpeL](https://arxiv.org/html/2308.10144v3))。

| 层 | 方法 | 代表实现 | 单位成本 | 精度 / 偏差 | 建议用途 |
|---|---|---|---|---|---|
| L0 曝光与位置先验 | 条目出现在 retrieved 列表，rank 加权（如 1/log2(rank+1)） | 日志即可 | 零 | 不含质量信息 | 只做覆盖/曝光统计，不做质量归因 |
| L1 显式引用 | 回答中 cite 的条目 id；代码检查"引用 id ⊆ 检索 id" | write-code-eval 式确定性检查 | 近零 | MIRAGE：自引用不忠实 | 加权证据 + guardrail（引用越界即失败） |
| L2 LLM 使用判定 | 对每个 (turn, item) 判定是否贡献、贡献了哪些 claim | RAGAS ContextUtilization、Galileo Chunk Attribution（小模型） | 每 turn 一次 judge 调用 | 中；需本地校准（Snowflake 报告 context relevance 类 judge precision 约 0.5） | **全量主归因层** |
| L3 反事实消融 | leave-one-out / ContextCite / AttriBoT | context_cite、AttriBoT | 约 32× 生成（ContextCite）；AttriBoT 代理降至 1/30 | 高；线性代理在强非线性多源上下文下退化 | 抽样：负反馈、高风险、冲突 turn |
| L4 Shapley | Kernel SHAP / Cluster Shapley | arXiv 2507.04480、2505.23842 | 最高（指数级，需近似） | 处理冗余与互补 | 仅当同一事实在多份文档中各异 |
| L5 模型内部显著性 | CTI/CCI 显著性归因 | MIRAGE | 白盒下便宜 | 与人工归因高度一致（抽取式 QA） | 仅自托管模型可用 |

推断的信用公式是 `credit(item, turn) = used_weight(L2 置信度) × outcome(turn)`，按条目累积为 `Beta(α = helpful + 1, β = harmful + 1)` 后验——与 ACE 的计数器等价但带不确定性；**被检索却未被使用的条目不得扣分**（否则惩罚的是检索噪声而非知识错误）；归因应落到条目内的 claim/段落而非整篇（Galileo 的 utilization、RAGAS 的 claim 拆分、ContextCite 的 span 归因都支持），否则长 runbook 永远"被使用"却无法定位哪一段错了；agent 侧硬信号可做硬归因，执行了某 runbook 的命令且报错即该条目 harmful +1 并自动生成待验证任务。

知识健康度在成熟产品里不是一个分数，而是**带 owner 的工作队列**。Guru 要求建卡时指定 Verifier 与验证频率（周到年），过期时通知 verifier，未验证卡片仍可搜到但明确标记，"My Tasks" 按 relevancy 排序该先验证谁，未验证且未被使用的卡片进入 auto-archive 队列 ([Guru verification](https://www.getguru.com/features/verification))；Stack Overflow for Teams 的 Content Health 识别"可能过时"的问答，review queue 按 age 与 popularity 排序，动作为 verify / edit / close / mark obsolete，obsolete 内容被锁定、搜索降权、明确标注但保留历史，厂商自报首批客户 90 天内月度编辑活动 +600%、进入队列的用户 87% 会采取行动 ([Stack Overflow blog](https://stackoverflow.blog/2021/11/17/introducing-content-health-a-new-way-to-keep-the-knowledge-base-up-to-date/))；Intercom 每周为 Fin 未能回答的对话生成"缺失、不清楚、重复或矛盾"的内容缺口建议，可查看触发建议的具体对话 ([Intercom content suggestions](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-suggestions-to-improve-fin))。冲突检测仍是研究难题：MAGIC（EMNLP 2025 Findings）发现多数模型检测上下文间冲突仍不完美、多跳更差、即便检测到也常无法定位冲突点（据摘要） ([MAGIC](https://arxiv.org/pdf/2507.21544))，所以冲突处理应采用 Graphiti 的"失效不删除"并把裁决留给人。Karpathy 的 LLM Wiki 把周期性 lint 定义为查矛盾、陈旧声明、孤页、缺失概念页与交叉引用 ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))。下表是本报告基于"已有每轮检索/使用日志"推断的指标集；没有任何公开资料给出条目级健康分数的行业基准值。

| 指标 | 定义（基于已有日志） | 触发动作 | 先例 |
|---|---|---|---|
| exposure | 周被检索次数 / 独立用户数 | 决定验证 SLA（高曝光周验、低曝光季验） | Guru、SO 按 popularity 排队 |
| utilization rate | L2 判定被使用次数 ÷ exposure | 长期低利用 + 高曝光 → 检索噪声或内容跑题，候选降权/重写 | Galileo 诊断规则 |
| citation rate | 显式引用次数 ÷ 使用次数 | 低引用高使用 → 内容"背景化"，可拆分 | RAGAS/TREC support |
| helpfulness posterior | Beta(helpful+1, harmful+1) 的均值与区间 | 低于阈值且区间窄 → 下架/复核 | ACE 计数器、ExpeL 投票 |
| hard-failure count | agent 按条目执行后工具报错/测试失败次数 | ≥1 即进复核队列 | 本报告推断 |
| staleness | since_verified 天数；`source_changed_since_verified`（绑定代码路径/配置/PSM 的变更事件）；按类型 TTL | 置为 needs-re-verify 并降权 | Guru 频率验证、Datadog 定期复核、Unblocked superseded-by |
| contradiction flags | 同主题簇内 claim 级 NLI/LLM 判定；条目 vs 代码/配置自动核对 | 生成冲突对任务；检索只暴露 verified 版本 | Graphiti 失效不删除、AgentX lint |
| coverage gap score | 无被使用条目或结果为负的 query 簇大小 × 增长率 | 周报 + 新知识挖掘入口 | Intercom 缺口建议 |
| decay | helpfulness 后验的滑动窗口趋势 | 预警"正在变错"的条目 | 本报告推断 |

从对话与执行轨迹中挖掘新知识，2025–2026 的主线是"把经验写进上下文而不是权重"，而产品侧的共同形态是**系统聚合缺口并排序、人批准**。Intercom 的 "Content from conversations (beta)" 在对话关闭时检查内容缺口并生成 snippet，可自动加入或在建议页人工审核后加入；正式版对比"Fin 未解决的对话"与"人工回复"产生建议，每条可 edit / accept / reject，分析时显式排除无人工回复、被放弃、人工与 Fin 答案相同的对话 ([Intercom beta](https://intercom.com/help/en/articles/10260362-content-from-conversations-beta)；[Intercom content suggestions](https://www.intercom.com/help/en/articles/11394959-use-ai-powered-content-suggestions-to-improve-fin))；Snowflake Cortex Analyst 基于用量与查询历史建议常见问题，用户核验后加入 verified queries，系统再据此泛化出语义模型概念 ([Snowflake docs](https://docs.snowflake.com/user-guide/snowflake-cortex/cortex-analyst/analyst-optimization))；Databricks Genie 明确"仅提交反馈不会改变 Genie 行为"，需向 space editor 提供具体更正，策展通过 instructions 与"把对话回答另存为 instruction"完成 ([Databricks docs](https://docs.databricks.com/aws/genie/talk-to-genie))。研究侧给出了抽取方法：ExpeL 强调从成功/失败经验对比中抽取"普遍失败模式或最佳实践"而非只存成功做法（Voyager 只在成功时加技能的局限） ([ExpeL](https://arxiv.org/html/2308.10144v3))；Tencent Youtu Lab 的 Training-Free GRPO 把数值 group advantage 换成"semantic advantage"——LLM 审视同组输出并写出自然语言教训加入经验库，仓库 README 称约 100 条样本、每次运行约 $8、AIME25 约 +5.4%（厂商自报） ([youtu-agent](https://github.com/TencentCloudADP/youtu-agent)；[arXiv 2510.08191](https://arxiv.org/pdf/2510.08191))；AgentX 的 Experiment Analysis Agent "记录失败方向、把 A/B 反馈翻译为可复用记忆"，SGPO 则把轨迹失败转为单个子 agent 的 prompt 局部修改且"仅通过 paired replay 准入"（据摘要） ([AgentX](https://arxiv.org/pdf/2606.26859))；2026-09 的一篇小模型工具 agent 研究发现移除失败记忆会导致一致退化（据摘要） ([arXiv 2609.28003](https://arxiv.org/pdf/2609.28003))；Karpathy gist 的评论区则提供了难得的量化线索：一位实现者在 525 份文档上发现 ingest 期间约 72% 的 token 花在"归档/合并/链接"决策上，改用小型类型化分类器后"正确笔记到达答案"从 62% 升到 89%（二手自报），播客 wiki 作者的教训是"来源冲突时绝不静默覆盖，把分歧记在专门小节" ([Karpathy gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f))。推断的挖掘管线按 ACE 的三角色分工：Generator 就是线上助手本身；Reflector 是离线批处理，从带结果标签的 turn 中抽取"候选 delta 条目"（短、带适用条件、带 helpful/harmful 初值、带 provenance turn ids），候选类型为纠正型 FAQ（用户纠正 + 后续确认，四元组"问题/错答/正解/证据 turn"）、Pitfall（轨迹中"工具报错→改法→成功"三段式）、Runbook（同一任务多次稳定成功，附最近一次成功执行作验证证据）与覆盖缺口 FAQ（gap 簇 + 人工答案）；Curator 做确定性合并（embedding 去重、同主题合并、冲突对标记），**绝不让 LLM 整体重写知识库**（ACE 的 context collapse 与 brevity bias）；候选入库门槛为至少两个独立对话证据（不同用户/日期）或一次可复现的执行验证。

策展闭环的最后一道，也是本次调研最明确的结论：**没有找到任何公开组织把"对话→知识更新"做成全自动闭环**。Intercom、Snowflake、Databricks、Guru、Uber 全部把反馈经人工策展后才进入知识，腾讯 RecSys Factory 以人审 approval cards 形成"operator approval → production side-effect"的审计链、把 agent 自主权限制在决策点（据摘要） ([RecSys Factory](https://arxiv.org/pdf/2608.11241))，Meta Auto-RecSys 的 playbook "无条件接受"则在上一份报告中被独立评论列为反面案例。无人审写回的风险已有定量证据：RAG Collapse（2026-08）发现当检索到模型自己早先写的文档时，1,528 次模拟中 79.6% 走向崩溃，单一自写引用即可触发，因为 LLM 不成比例地引用自己的内容（据摘要） ([arXiv 2608.22118](https://arxiv.org/pdf/2608.22118))；Bidirectional RAG 指出天真地把所有输出写回会"迅速以幻觉污染语料，形成自我强化的退化循环"，提出多阶段验证后的受控写回（据摘要） ([arXiv 2512.22199](https://arxiv.org/html/2512.22199v1))；"provenance debt" 博客观察到 AI 生成文本"密集、格式好、关键词丰富"，在相关度排序上压过凌乱的人类原始资料（二手） ([tianpan.co](https://tianpan.co/blog/2026/05/07/provenance-debt-ai-knowledge-bases))；ICLR 2026 的 Misevolution 研究定义了 model / memory / tool / workflow 四条自演化偏离路径，案例包括客服 agent 从"退款↔好评"学到偏置关联而主动退款，即便基于 Gemini-2.5-Pro 也出现，作者称缓解措施仅初步有效（据摘要） ([Misevolution](https://arxiv.org/pdf/2509.26354))；MINJA（NeurIPS 2025）证明攻击者无需写权限，仅通过查询与观察输出即可把恶意记录注入记忆库，建议 memory isolation、强认证、安全记忆管理与 prompt 过滤（据摘要） ([MINJA](https://arxiv.org/abs/2503.03704))。上一份 AgentX 报告记录的 "KEEP ratchet" 是推荐系统特有的同类机制：网易 AutoLR 发现噪声晋级会通过 KEEP 棘轮累积成看似进步的单调轨迹，"持久状态变更只能在校准的、确定性的证据下发生"，而 AgentX 把 KEEP 结果写入 Experiment Knowledge Base 作为 Brainstorm 证据，意味着一次假阳性 KEEP 会偏置后续提案 ([AutoLR](https://arxiv.org/abs/2609.04871))。综合这些证据，可复用的治理件是：Guru 的 "verifier + 频率 + 过期降权 + 未用自动归档"，Intercom 的 "accept/edit/reject + 可追溯触发对话"，RecSys Factory 的审计链，Anthropic 长程 harness 的"feature list 用 JSON 且 agent 只能改 `passes` 字段、不信任未经验证的完成声明" ([Anthropic long-running harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents))，RobustSGPO 的"只经 paired replay 才能并入 + 保留快照可回退" ([RobustSGPO](https://academy.dair.ai/papers/robustsgpo-search-space-control-for-agent-harness-evolution-2609.09646))，以及 Letta/Karpathy 的"记忆即代码库、git 版本化"。推断的自动化边界是：AI 可以自动做的只有降权、置为待验证、打冲突标签与生成草稿；发布、覆盖、删除必须人审；任何 AI 生成条目带 `source_class`（human / ai_draft_human_approved / ai_auto），检索时对 ai_auto 降权或默认排除，并定期审计语料来源构成；用户可写的记忆与组织知识库物理隔离；知识库放 git，每次人审合并为一个附带评测结果的 commit。隐私上，Microsoft、Slack、飞书、OpenAI 的共同点是默认不采集内容、提交前可审阅、答案遵循提问者权限、可删除——Microsoft 在用户点 Submit 之前"除 thumbs 选择外不采集任何数据"，且反馈"不用于训练基础模型" ([Microsoft Support](https://support.microsoft.com/privacy/providing-feedback-about-microsoft-copilot-with-microsoft-365-apps))；挖掘前应对 turn 做 PII/密钥脱敏，条目可见性继承原始证据的最严权限。

## 五、评测：五层程序，检索按条目 ID 确定性计算，judge 必须本地校准，新鲜度用成对 canary

评测框架在 2026 年已收敛为"指标库"与"实验/追踪平台"两类，RAG 指标定义高度同构：RAGAS 的 Faithfulness 是"响应中被检索上下文支持的 claim 数 / claim 总数"，Context Precision 是按排名加权的 precision@k，Context Recall 是参考答案中可归因到上下文的 claim 占比，Noise Sensitivity 是在相关/无关检索文档存在时的错误 claim 比例，并提供按文档 ID 匹配的 `IDBasedContextPrecision/Recall` ([RAGAS faithfulness](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/faithfulness.md)；[context precision](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/context_precision.md)；[noise sensitivity](https://github.com/explodinggradients/ragas/blob/main/docs/concepts/metrics/available_metrics/noise_sensitivity.md))；TruLens 的 RAG Triad（context relevance、groundedness、answer relevance）三项合格时"在知识库范围内可视为无幻觉"，这句话同时提醒 **groundedness 只保证"相对知识库"正确，条目本身的正确性是独立维度** ([TruLens RAG Triad](https://github.com/truera/trulens/blob/main/docs/getting_started/core_concepts/rag_triad.md))。judge 与人工一致性的独立证据是"系统级可靠、样本级不可靠"：Snowflake 报告其 Groundedness judge 在 LLM-AggreFact 上 F1 81%、Cohen's κ 0.54，而 Context Relevance 在 TREC-DL 上 precision 仅 51%、recall 87%（厂商自报） ([Snowflake](https://www.snowflake.com/en/engineering-blog/benchmarking-LLM-as-a-judge-RAG-triad-metrics/))；TREC 2024 RAG Track 的 UMBRELA 自动标注诱导的系统排名与 NIST 人工排名高度相关，人类比 LLM 更严格，人工在环未带来收益（据摘要） ([arXiv 2411.08275](https://arxiv.org/abs/2411.08275v1))；引用支持评测中 GPT-4o 与人工在 run 级 Kendall τ > 0.79（据摘要） ([arXiv 2504.15205](https://arxiv.org/html/2504.15205))；AutoNuggetizer 的全自动 nugget 评测在 run 级强一致但 **per-topic 相关性较低，不适合单条答案的细粒度调试**（据摘要） ([arXiv 2504.15068](https://arxiv.org/abs/2504.15068v1))。ARES 的 PPI 思路最适合"每轮都有日志"的场景：用合成数据微调轻量 judge，再以"至少 50 条、理想几百条"人工标注校正偏差并给置信区间，README 示例在 4,421 条无标签样本上得到 0.606、CI [0.547, 0.664] ([ARES](https://github.com/stanford-futuredata/ARES))。因此框架分数用于系统 A vs B 的相对比较与回归，样本级 pass/fail 必须用经本地校准的二元 judge。下表是本报告推断的五层程序总览，后文逐层展开。

| 层 | 评什么 | 核心指标 | 真值来源 | 频率 / 触发 | 关键先例 |
|---|---|---|---|---|---|
| 1 检索层 | 黄金条目是否被召回、排在前面 | Recall@k（首要）、两跳 Recall@k、MRR、nDCG；agentic：最终命中率、首次命中步数、工具调用数、token、gold-leak 率 | golden set 中的条目 **ID 集合**（确定性，无 judge 成本）；新条目用 UMBRELA 式 0–3 LLM 标注 + 人工校准 | 每次索引/embedding/reranker 变更；interleaving 前置 | evaluate-rag、RAGAS ID-based、UMBRELA、CRISP、BrowseComp-Plus |
| 2 答案层 | 每个失败模式一个二元 judge | faithfulness-to-citations、completeness-vs-nuggets、harmful-ops-advice、should-abstain、should-clarify、stale-citation；校准后的 θ̂ 与区间 | 每个失败模式约 100 条专家标注（~50/50） | 每次模型/prompt/KB 变更；judge 换版本时锚点集重校准 | Hamel/Shankar 课程体系、Anthropic evals、Inspect、CRAG ±1/0 |
| 3 新鲜度层 | 更新后旧答案是否被替换 | staleness rate、time-to-freshness、canary 通过率 | 条目版本对 (v_old, v_new) 生成替换/稳定/冲突三类题 | 每次 KB 快照变更 + 每日 canary | FreshQA、HoH、ConflictBank、LongMemEval knowledge-updates |
| 4 条目层 | 单条知识的曝光、结果、反事实、风险 | 第四节健康度表；移除重跑 pass 率变化；错误 claim 来源次数 | 日志 + 对引用该条目的 golden 题重跑 | 周级批处理 | ContextCite、RAGAS ContextUtilization、Galileo、Guru/SO 队列 |
| 5 在线层 | 真实流量下的结果 | Resolved 率（复合口径）、升级率、hard-failure/千答、code-applied 关联率、guardrail 触发率 | 校准 judge 全量估计（Rogan-Gladen/PPI）+ 显式反馈 | 排序变更 interleaving 1–3 天；答案变更 A/B 或 backtesting | Microsoft/Airbnb interleaving、Anthropic 方法矩阵、Uber/Intercom 口径 |
| 横切治理 | 结果可比性 | judge 版本、KB 快照、prompt 版本进入结果主键 | 日志按会话哈希分调优池/评测池 | 每季度重做误差分析与 Goodhart 检查 | eval-audit 反模式、judge drift 文献 |

检索层以 **Recall@k 为第一指标**，因为未检出的内容生成器无法弥补；reranking 用 Precision@k/nDCG，单事实查找用 MRR，multi-hop 用"两个真值 chunk 同时进入 top-k"的两跳 Recall；实践指南建议事实查找 k=1–2、综合类 k=5–10，并先做分块网格搜索（示例：256 token/128 overlap 得 Recall@5 0.89，128 token 无 overlap 为 0.82） ([evaluate-rag SKILL.md](https://github.com/ai-evals-course/evals-skills/blob/main/skills/evaluate-rag/SKILL.md))。对"每个被检索条目都有日志"的系统，golden set 直接标注黄金条目 ID 集合，检索评测完全确定性；补标新条目时用 UMBRELA 工具以 0–3 四级打分、可多模型投票 ([castorini/umbrela](https://github.com/castorini/umbrela))，并以 BRIGHT 的"被采纳/高票答案引用的文档即相关"思路，把"被值班工程师在工单/PR 中引用的文档"自动记为正例 ([BRIGHT](https://arxiv.org/pdf/2407.12883))。agentic/DeepSearch 场景要把评测从"单次 top-k"扩展到轨迹级：CRISP 把"观察中包含黄金证据文档 ID"的步骤记为 evidence-bearing step（据摘要） ([arXiv 2608.01867](https://arxiv.org/pdf/2608.01867))，另一项 2026 研究通过移除黄金段落测 refusal / hallucination / "gold leak"（证据被移除仍答对，意味着答案来自参数知识或污染）（据摘要） ([arXiv 2605.27123](https://arxiv.org/pdf/2605.27123))；FRAMES 显示多步检索把无检索的 0.40 提到约 0.66 ([FRAMES](https://arxiv.org/html/2409.12941v1))。两条诊断规则值得固化：先判定瓶颈是"候选池覆盖"（query rewriting 有效）还是"排序"（更强 reranker 有效）（据摘要） ([arXiv 2511.09545](https://arxiv.org/html/2511.09545v1))；以及 reranker 的 nDCG/MRR 提升可能不改善端到端 QA（二手论坛案例） ([Arize community](https://community.arize.com/x/phoenix-support/msg_iAkTeJVE45rC/evaluating-rag-with-rerankers-best-practices-and-e))，所以每次检索侧变更都要同时跑端到端 golden set。

答案层的实践共识来自 Hamel Husain / Shreya Shankar 的课程体系、Anthropic 与 Inspect：**每个 judge 只判一个失败模式、输出二元 Pass/Fail、先写 critique 再给 verdict、few-shot 来自与 dev/test 分离的训练切分**；"Likert 分数听起来精确但无法校准"，"单一 judge 覆盖多维度会产生不可行动的判决" ([write-judge-prompt](https://github.com/ai-evals-course/evals-skills/blob/main/skills/write-judge-prompt/SKILL.md))。judge 上线前对每个失败模式约 100 条二元标注（~50 Pass + ~50 Fail，标签必须来自领域专家）计算 TPR 与 TNR（目标 >90%、底线 >80%），再用 Rogan-Gladen 公式 `θ̂ = (p_obs + TNR − 1)/(TPR + TNR − 1)` 校正全量估计并以 bootstrap 给区间；用 accuracy 或 κ 会让"总是判 Pass"的 judge 在类别不平衡下看起来很好 ([validate-evaluator](https://github.com/ai-evals-course/evals-skills/blob/main/skills/validate-evaluator/SKILL.md)；[eval-audit](https://github.com/ai-evals-course/evals-skills/blob/main/skills/eval-audit/SKILL.md))。误差分析以约 100 条 trace 达到饱和为经验目标，采样强调多样性（K-means 6–10 簇，簇代表约 60–70% + 随机 30–40%）而非频率估计 ([error-discovery](https://github.com/ai-evals-course/evals-skills/blob/main/skills/error-discovery/SKILL.md)；[Hamel](https://hamel.dev/blog/posts/evals-faq/why-is-error-analysis-so-important-in-llm-evals-and-how-is-it-performed.html))。Anthropic 的补充是：能确定性就确定性，给 LLM judge 一个 "Unknown" 出口，每个维度独立 judge，grader 要抗 hack，并以 CORE-Bench 为戒——Opus 4.5 从 42% 修正评分 bug（期望 96.124991 却惩罚 96.12 之类的刚性评分）后到约 95% ([Anthropic Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))。judge 偏差有独立证据：15 个 judge、超过 150,000 个评测实例的研究显示位置偏差非随机、随候选质量差距变化 ([ACL 2025.ijcnlp-long.18](https://aclanthology.org/2025.ijcnlp-long.18/))；GPT-4 的自我偏好分最高 0.520、与低困惑度相关 ([alphaxiv 2410.21819](https://www.alphaxiv.org/abs/2410.21819))——所以 pairwise 必须交换顺序双跑，judge 模型应与生成模型不同族（Anthropic 平台文档亦如此建议） ([Claude docs develop-tests](https://platform.claude.com/docs/en/test-and-evaluate/develop-tests))。弃答是独立能力：AbstentionBench（Meta FAIR，NeurIPS 2025）在 20 个数据集、6 类弃答场景（含 stale data）上评测 20 个前沿模型，结论是"弃答是未解决问题，扩大规模几乎无助"，**reasoning 微调平均使弃答能力下降 24%** ([AbstentionBench](https://github.com/facebookresearch/AbstentionBench))；CRAG 的评分把弃答记 0、幻觉记 −1、正确 +1，直接奖励"不确定就弃答" ([CRAG README](https://github.com/facebookresearch/CRAG))。对运维/runbook 类回答的"有害建议"检查，推断的做法是把客观部分交给代码（命令是否命中破坏性操作黑名单、引用 ID 是否 ⊆ 检索 ID、是否缺少前置确认）、其余交给二元 judge（"是否在缺乏环境信息时给出不可逆操作建议"），并按 AbstentionBench 的六类场景分层构建"应弃答/应追问"用例 ([write-code-eval](https://github.com/ai-evals-course/evals-skills/blob/main/skills/write-code-eval/SKILL.md))。

新鲜度层的公开基准已经把"时间敏感"切得很细：FreshQA 按 never/slow/fast-changing 与 false-premise 分类，数据集"每周或按需更新"，分 RELAXED/STRICT 两种评测模式 ([freshllms/freshqa](https://github.com/freshllms/freshqa))；HoH 用 96,124 条时间敏感问题与 219,463 篇文章评估"过期信息混入检索"的影响（据摘要） ([arXiv 2503.04800](https://arxiv.org/pdf/2503.04800))；ConflictBank 构造了 7,453,853 条 claim-evidence 对，其中 temporal 冲突 1,650,026 对，结论是"LLM 易被外部证据带偏，即使与其已知知识矛盾" ([conflictbank](https://github.com/zhaochen0110/conflictbank))；CRAG 按 static / slow-changing / fast-changing / real-time 与 head/torso/tail 分层，发现**业界 SOTA RAG 仅 63% 回答无幻觉，动态性高、流行度低、复杂度高的问题准确率低得多**（据摘要） ([CRAG dataset.md](https://github.com/facebookresearch/CRAG/blob/main/docs/dataset.md)；[arXiv 2406.04744](https://arxiv.org/pdf/2406.04744))；LongMemEval 把 knowledge updates 与 abstention 列为五项记忆能力中的两项 ([LongMemEval](https://github.com/xiaowu0162/LongMemEval))。企业内部 KB 没有现成的 staleness 标准指标，本报告给出操作化定义（推断）：从条目版本日志取 (item_v_old, item_v_new) 对，对每对生成"替换题"（期望引用新版本、不出现旧值）、"稳定题"（答案不变，防过度敏感）与"冲突题"（旧版本软删除时应优先新版本或指出差异）；`staleness rate` = 引用了 superseded 条目或含旧值的回答 / 时间敏感题总数；`time-to-freshness` = 条目更新落库到回归用例首次通过的时间（覆盖索引延迟、缓存、重排序）；对每类高频变更源（配置默认值、服务 owner、runbook 步骤、接口签名）维护一小组 canary 查询按条目 ID 断言引用，每次 KB 更新与每日定时跑；跨 KB 版本 diff 时固定模型与 prompt，比较逐题结果（pass→fail 列表、引用条目变化、检索 ID 集合 Jaccard），把"KB 变更"与"模型/提示变更"的影响隔离。回归机制沿用 Anthropic 的"regression evals 应接近 100% 通过率，capability eval 毕业后持续运行以捕获漂移" ([Anthropic Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))，LangSmith 的 backtesting（把生产日志回放到新版本） ([LangSmith concepts](https://github.com/langchain-ai/langsmith-docs/blob/main/docs/evaluation/concepts/index.mdx))，Promptfoo 的 CI 通过率门槛与按 git sha 打 tag ([Promptfoo ci-cd](https://github.com/promptfoo/promptfoo/blob/main/site/docs/integrations/ci-cd.md))，以及 Inspect 的 temperature 0 + seed + 多 epoch 看评分方差 ([Inspect](https://github.com/UKGovernmentBEIS/inspect_ai/blob/main/docs/model-graded.qmd))。

条目层把第四节的健康度表与离线评测连起来：对每个条目维护曝光（被检索/引用次数、ContextUtilization 均值）、结果（被引用会话的 Resolved/Not Relevant 率、judge 判定 faithful 率）、反事实（对引用该条目的 golden 题做"移除 i"重跑并记录 pass 率变化，ContextCite 适合离线小样本精细归因，全量用引用/反馈关联代替）与风险（被 judge 标为"错误 claim 的支持来源"的次数，即 noise sensitivity 的来源级分解）。"有害条目"定义为曝光高且负反馈率显著高于同类基线——需要显著性检验，因为反馈稀疏且有偏；覆盖缺口用 error-discovery 的聚类流程，统计每簇中"top-k 最高相关性低于阈值"或"弃答/被判不可答"的比例；重复/冲突检测借 ConflictBank 的管线（同簇内 embedding 近邻 + DeBERTa 类 NLI 判 entailment/contradiction），contradiction 对需人工裁决或按版本优先，这条管线同时就是新鲜度层的 temporal conflict 检测器。

在线层要先解决口径，再解决灵敏度。企业自报指标互不可比：Uber 用用户标记的 helpfulness（据报道 48.9%）；LinkedIn 客服 RAG+知识图谱论文报告约六个月部署后中位每工单解决时间下降 28.6%（企业自报） ([arXiv 2404.17723](https://export.arxiv.org/abs/2404.17723))；Intercom Fin 在 Claude 客户案例页称开箱 51% 平均 resolution rate、单客户最高 86%，并称"每次变更都对照生产基线测试" ([claude.com/customers/intercom](https://claude.com/customers/intercom))，而据报道 Fin 3 发布时平均 67%、独立小样本测试仅 38%，批评者指出 Fin 把"客户停止回复"计为已解决可能虚高（二手） ([myaskai](https://myaskai.com/blog/how-to-improve-intercom-fin-resolution-rate))。推断的做法是把 resolution 定义为"用户显式确认 or 24 小时内无同主题再提问 and 无升级"的复合口径并同时报告两种口径。灵敏度方面，Microsoft 在 38 个大规模实验、超过 30 亿点击上证明 interleaving 的灵敏度比 A/B 高 1–2 个数量级 ([Microsoft Research](https://www.microsoft.com/en-us/research/publication/predicting-search-satisfaction-metrics-with-interleaved-comparisons/))，Airbnb 2025 称约 50× 加速、一天小流量即可检出 A/B 需数周才能发现的负向转化效应，但会漏掉"优化次要目标而转化中性"的 ranker，因此只作 A/B 前的筛选（据摘要） ([Airbnb arXiv 2508.00751](https://arxiv.org/pdf/2508.00751))。Anthropic 的方法矩阵把自动评测、生产监控、A/B、用户反馈、人工审阅与系统性人工研究按"真值梯度"排列，A/B 的弱点是慢、需流量、只能测已部署变更且难解释原因 ([Anthropic Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))。对本场景的推断是：排序层变更（embedding、reranker、KB 快照）用 interleaving 按引用/点击记分，1–3 天出结论；答案层变更（prompt、模型）用 A/B 或 backtesting + 校准 judge；全量日志用校准 judge + Rogan-Gladen/PPI 估计并给区间，把"需要用户反馈的样本量"降到几百条人工标注；主结果指标为 Resolved 率、升级率、"code applied"事件关联率（回答后 N 小时内相关文件被提交且引用了回答中的标识符——推断，未见公开实现），guardrail 指标为引用越界率、破坏性命令建议率、幻觉举报率。

Golden set 的起步规模有权威建议：Anthropic 写道"团队常等到有几百个任务才开始，但 **20–50 个来自真实失败的简单任务就是很好的开始**"，任务要无歧义并带参考解（两名领域专家能否独立得出相同 pass/fail），"跨多次试验 0% 通过率通常意味着任务或 grader 坏了"，并要"既测应发生也测不应发生，单边评测导致单边优化" ([Anthropic Demystifying evals](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents))。合成数据用维度–元组法（从 3 个维度起、元组与自然语言查询分两步生成、LLM 真实度 1–5 打分丢弃 <3），已有 100+ 代表性真实 trace 时改用分层抽样 ([generate-synthetic-data](https://github.com/ai-evals-course/evals-skills/blob/main/skills/generate-synthetic-data/SKILL.md))；检索测试集可从 chunk 合成"只能由该事实回答"的问题，并用 embedding 搜索找相似干扰 chunk 构造对抗题 ([evaluate-rag](https://github.com/ai-evals-course/evals-skills/blob/main/skills/evaluate-rag/SKILL.md))；RAGAS 的知识图谱法生成 single-hop/multi-hop × specific/abstract 查询，但其文档默认分布（0.5/0.25/0.25）与源码（三者等权）不一致，合成集分布应显式配置 ([RAGAS testset generation](https://github.com/explodinggradients/ragas/blob/main/docs/getstarted/rag_testset_generation.md))。推断的分层键是知识类型（doc/code/config/log）× 问题类型（借 CRAG 的 8 类）× 动态性（static/slow/fast）× 流行度（以条目被引用频次代替 head/torso/tail）× 应答类型（应答/应弃答/应追问）。日志挖掘流程为：候选池 = 有显式反馈或 guardrail 触发的会话 → embedding 聚类去重 → PII/凭据脱敏并保留条目 ID 引用 → 专家写参考解与黄金条目 ID → 版本化入库；**日志按会话 ID 哈希分成"调优池"与"评测池"**，任何从日志挖出的 golden 题必须排除其会话曾用于 few-shot 或调参。防止 KB 更新"打坏" golden set 的手段（推断，未见文献直接描述）是 as-of 版本化期望 `{question, expected, gold_item_ids, kb_snapshot_id, valid_from, valid_to}`：条目被修改/删除时自动把引用它的 golden 标为待复核并生成新鲜度用例；期望尽量写成可执行断言（Databricks Genie 基准以 SQL 结果集比对判定、每 space 最多 500 题） ([Databricks Genie benchmarks](https://docs.databricks.com/aws/en/genie/benchmarks)) 而非固定文本；数据集版本化并打 tag（LangSmith splits/versions）。反模式清单已被文献与指南明确记录：Likert/综合分不可校准、omnibus judge 不可行动、judge 未经人工验证、few-shot 泄漏进 dev/test、过拟合合成数据、"set-and-forget" 评估器 ([eval-audit](https://github.com/ai-evals-course/evals-skills/blob/main/skills/eval-audit/SKILL.md))；judge 模型静默更新造成"幻影回归"，对策是不用 "latest" 别名、固定 judge 快照、保留约 100 条专家锚点集在换版本时重算 TPR/TNR、只在同 judge 版本内报告差值（二手） ([tianpan.co](https://tianpan.co/blog/2026-04-23-llm-judge-drift-evaluator-upgrade-phantom-regression)；[arXiv 2411.15594](https://arxiv.org/html/2411.15594v6))；引用率的 Goodhart 没有专门文献，对策是不把引用率作目标，改用"引用支持率 + 引用 ID ⊆ 检索 ID 代码检查 + 无关引用计入 noise"；EvalGen 提醒评分标准会随观察输出而漂移（criteria drift），所以标准要在误差分析中迭代而非先验固定 ([EvalGen](https://arxiv.org/pdf/2404.12272))。

## 六、工业案例：覆盖面带来价值、精度决定信任，反馈一律经人工策展

内部工程问答类案例里，Uber Genie 的公开资料最完整，也最能说明"先堆文档再回头做结构化"的代价。Genie 于 2024-10 在 Slack 内上线，引用 Engwiki、内部 Stack Overflow 与 Google Docs，并描述了用户评分反馈环（据摘要） ([Uber Genie blog](https://www.uber.com/blog/genie-ubers-gen-ai-on-call-copilot))；据报道它已回答 70,000+ 问题、覆盖 154 个 Slack 频道，"节省 13,000 工程小时"这一数字未能在 Uber 原文核实 ([InfoQ](https://www.infoq.com/news/2024/10/uber-genie-rag-copilot))。约七个月后的 Enhanced Agentic-RAG 是在 SME 用 100+ 条 golden set 暴露"检索到但不准/不全"之后，对文档加载器与元数据做的返工，其结果数字（+27% / −60%）只能追到 ZenML 转述 ([Uber EAg-RAG](https://www.uber.com/blog/enhanced-agentic-rag/)；[ZenML](https://www.zenml.io/llmops-database/enhanced-agentic-rag-for-internal-on-call-support-copilot))。同一公司的 uReview 代码评审平台把误报（LLM 幻觉与"正确但无关"的问题）列为核心难题，因为高误报率会损害工程师信任 ([Uber uReview](https://www.uber.com/en-US/blog/ureview/))；QueryGPT 则用按业务域策划的 Workspaces 与列裁剪应对"表与 SQL 样本越多准确率越低"的问题 ([Uber QueryGPT](https://www.uber.com/blog/query-gpt))。Meta 与 Google 的案例把"历史记录"抬到一等知识源：Meta 的 RCA 系统以约 5,000 条历史调查样本微调排序模型，对每个候选给出解释、闭合反馈环并隐藏低置信结果，但结果来自单一 monorepo 的回测（据报道） ([Meta Engineering](https://engineering.fb.com/2024/06/24/data-infrastructure/leveraging-ai-for-efficient-incident-response/)；[InfoQ](https://www.infoq.com/news/2024/08/meta-rca-ai-driven))；Google Cloud SRE 使用 Gemini CLI 处理故障时，agent 最有价值的输出是"同一服务此前已解决事件的细节（含响应者笔记）"（聚合站转述） ([scuttle 书签](https://scuttle.klotz.me/tags/site%20reliability%20engineering))。Meta 全员助手 Metamate 只有匿名员工反馈：一帖称它"索引了我们所有内部文档源、知道内部 infra 如何运作，这是最有用的部分"，另一帖称它"有时会幻觉出不存在的 API 调用"（不可验证） ([Blind](https://www.teamblind.com/post/how-good-is-metas-internal-metamate-tool-qsfsez0m))——与 Uber 的经验合起来就是本节标题：**覆盖面带来价值，精度决定信任**。

以 agent 为中心的公司把"知识"做成了可调用的接口而不是文本。Stripe 的 Minions 据 Part 2 博客摘要每周合并超过 1,000 个 PR，架构由 Devbox、Blueprints（确定性步骤与 LLM 步骤组合）、Toolshed（集中式内部 MCP server，据报道约 500 个工具、新增即对整个舰队可用、minion 默认只拿刻意缩小的子集）与 goose fork 组成，devbox 运行在无真实用户数据与生产服务的 QA 环境 ([stripe.dev](https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2)；[InfoQ](https://infoq.com/news/2026/03/stripe-autonomous-coding-agents/))；Spotify 的 Honk 建在 Backstage 目录与 Fleet Management 之上，据报道大规模迁移中每 10 天合并 1,000 个 PR，并设有专职的 "AI Fleet Management & Honk" 工程经理岗 ([Backstage webinar](https://backstage.spotify.com/how-spotify-built-honk)；[InfoQ](https://infoq.com/news/2026/03/spotify-honk-rewrite))；Block 据报道约 5,000 名员工每周使用 goose，内部只加专有认证与安全连接器 ([Gradient Flow](https://gradientflow.com/can-a-single-agent-automate-90-of-your-code-fixes-block-thinks-so/)；[block/goose](https://github.com/block/goose))；Shopify 的 River 据报道在公开 Slack 频道工作，因此每段对话可搜索、任何人可加入——这是"对话日志即知识"的最低成本实现 ([Simon Willison](https://simonwillison.net/tags/shopify/))。OpenAI 的 harness engineering 据报道以 3→7 人、5 个月约 1,500 个合并 PR 为背景，把仓库内文档视为 agent 的主要接口 ([InfoQ](https://www.infoq.com/news/2026/02/openai-harness-engineering-codex))。Datadog Bits 是 SRE 场景最完整的"知识源 + 反馈 memory"产品说明：runbook（monitor message 内联或 Confluence 链接）、`bits.md`（每次调查都读）与反馈 memories 三类；每次调查的正向反馈与带细节的负向反馈都生成一条可查看/删除的 memory；建议改完 `bits.md` 或 runbook 后用 Bits Chat 验证"它在真实调查之前就生效"，并只对 p1/p2 monitor 开启自动调查 ([Datadog Knowledge Sources](https://docs.datadoghq.com/bits_ai/bits_investigation/knowledge_sources/)；[Improve accuracy](https://docs.datadoghq.com/bits_ai/bits_investigation/improve_accuracy/))。

厂商产品对新鲜度与反馈的机制描述最明确，而它们的共同点是**反馈都经人工策展后才进入知识**。Glean 用定时全量 + 增量 + 持续活动爬取（含权限变更）维持知识图谱，但权限新鲜度随连接器而异，SharePoint 使用较弱 scope 会造成显著索引延迟与排序问题 ([Glean crawling types](https://docs.glean.com/connectors/crawling-types))，第三方比较称 Glean 本身没有内容验证机制（二手） ([fabric.so](https://fabric.so/comparison/glean-vs-guru))。GitHub Copilot Spaces 的 GitHub 文件与仓库"随变更自动更新"，而上传文件与自由文本 notes 是静态的（后者为第三方指南） ([GitHub changelog](https://github.blog/changelog/2025-09-24-copilot-spaces-is-now-generally-available/))。Intercom Fin 的 Recommendations 每周审查未能回答的对话、给出内容/数据/动作三类缺口建议并按影响分排序，管理者可一键批准 AI 起草的内容变更 ([Intercom Optimize Fin](https://www.intercom.com/help/en/articles/11390088-optimize-fin-instantly-with-the-help-of-ai))；社区用户抱怨解决率"只显示总数、看不到下面的东西" ([Intercom 社区](https://community.intercom.com/analyze-fin-93/what-does-your-team-actually-do-with-fin-s-resolution-rate-14050))。Databricks Genie 与 Snowflake Cortex Analyst 的策展单元分别是 instruction 与 verified query（见第四节）；Guru 以 verifier 与验证周期对抗陈旧，Notion AI 据竞品对比不区分已验证/未验证内容（二手） ([fabric.so](https://fabric.so/comparison/guru-vs-notion))。Augment Code 自称实时索引、代码变更立即反映、幻觉减少 40%，但没有独立客户案例或新鲜度基准 ([Augment](https://www.augmentcode.com/guides/augment-code-vs-sourcegraph-cody-enterprise-comparison))。

中文公开资料的重心在编码助手采纳率，而非知识库新鲜度与反馈闭环的工程细节。飞书知识问答的产品说明最有参考价值：知识自带权限属性，不同部门/职级员工问同一问题答案按其文档、聊天、服务台权限动态调整 ([飞书](https://www.feishu.cn/content/euuvns8t))；阿里云百炼的数据同步周期可选 1 分钟/1 小时/1 天，切片级 AddChunk/UpdateChunk/DeleteChunk 均幂等但 DeleteChunk 为硬删除、AddChunk 限流 10 次/秒 ([百炼数据同步](https://help.aliyun.com/zh/model-studio/data-sync-guide)；[DeleteChunk](https://help.aliyun.com/zh/model-studio/api-bailian-2023-12-29-deletechunk))；通义灵码企业知识库按主题与可见成员划分知识库并支持企业自定义指令 ([阿里云文档](https://help.aliyun.com/zh/lingma/qoder-cn/use-cases/enterprise-competency-usage-practices/))。采纳率数字一律二手：美团 CatPaw 据报道公测时内部渗透率超 95%、增量代码 50%+ 由 AI 协作生成 ([量子位](https://www.qbitai.com/2025/11/350537.html))，百度 Comate 据报道整体采纳率 46%、新增代码 27% 由其生成 ([数英](https://www.digitaling.com/articles/1075885.html))，腾讯 CodeBuddy 的"研发提效 16%+"为厂商口径 ([腾讯云开发者社区](https://cloud.tencent.com/developer/article/2579286))。与 TikTok 推荐场景最贴近的反而是三篇推荐系统 agent 论文：快手 AgentX 的 System KB 三层结构与 ingest–query–lint 生命周期（据摘要；3 个 worker 把 374 个实验想法处理为 10 个可发布结果，其数字可信度已在上一份报告中逐项评估） ([AgentX](https://arxiv.org/pdf/2606.26859))，快手 Data Agent 据媒体通稿已沉淀上百个业务 Skill、Skill 市场 2000+、父子 agent 路由准确率 95%（二手） ([中国日报](https://cn.chinadaily.com.cn/a/202609/22/WS6ab1fd39e4b09a165c78bc9e.html))，AutoLR 把三类稳定知识源与演化中的实验记忆分别索引（据摘要） ([AutoLR](https://arxiv.org/pdf/2609.04871))，RecSys Factory 把 agent 自主权限定在决策点并以 skill 包 + pitfall 表作为领域知识（据摘要，腾讯归属与 "PitfallStore" 名称未能核实） ([RecSys Factory](https://arxiv.org/pdf/2608.11241))。另有一篇 FSE '26 Companion 论文《Help Without Being Asked》描述已部署的主动式 on-call 支持 agent，摘要称"迭代验证可避免过时或低质量知识导致的性能下降"，作者单位未能从摘要确认 ([arXiv 2604.09579](https://arxiv.org/pdf/2604.09579))。

跨约 30 个案例可以归纳出十条反复出现的教训。其一，文档分散与陈旧是最常见的起点问题（Uber、Adobe），解法是专门 loader 与结构化，而不是换模型。其二，幻觉 API 与误报决定信任（Metamate、uReview），对策是置信度门控（Meta）、相关性过滤与答案必须带 raw-source 引用（AgentX、Genie）。其三，权限变更普遍滞后于内容变更（Glean 多个连接器），答案必须随提问者权限变化（飞书、Google Cloud Assist）。其四，指标不透明会侵蚀信任（Intercom 社区），resolution 一类口径必须公开定义。其五，大 schema 会撑爆上下文（QueryGPT 单表 40–60K token），需要按域切分知识空间。其六，工具/知识过多会降低 agent 表现（Stripe 默认子集、Claude Code skill 描述截断）。其七，重跑非确定（Cloud Assist）应在产品层明示。其八，自动评测在 2024 年仍"不够好"、只能辅助初步粗评（LinkedIn，二手） ([CIO.com](https://www.cio.com/article/2095140/what-linkedin-learned-leveraging-llms-for-its-billion-users.html))，专家抽检集不可省。其九，采纳不是自动的（Metamate 未强制全员使用），覆盖面要靠接入真实工作流（Slack、PR、on-call）。其十，团队与节奏：公开案例普遍是"小核心团队 + 平台团队支持"，Uber 从上线到一次大迭代约 7 个月，Block 内部开发约 9 个月才开源，首个可用版本约 6–9 个月、之后约半年一次大迭代；团队人数与成本在所有案例中均未公开，节省小时数类 ROI 数字多为自报且缺统计口径。

## 设计结论：面向 TikTok 推荐架构团队的架构选择

以下结论针对的情形是：部门级 AI 研发助手，知识覆盖设计文档、代码（C++/Python/DSL 的大型 monorepo）、平台配置、运行日志与实验记录，拥有每轮对话日志并知道每轮检索到与使用了哪些知识条目，且推荐系统的配置与特征变更频繁、实验结论权限敏感。每条结论给出"选择 + 理由"，详细 schema 与接口留给后续设计文档。

**源优先级。** 第一优先是系统事实——服务目录与 PSM 拓扑、特征注册表、模型/特征配置 schema、实验平台与发布系统——以带版本与时间的表加语义层（指标/实体/关系定义 + 示例 SQL）落库，agent 通过 `kb_sql` 工具查询；第二是历史记录——含负结果的实验报告、变更/事故/on-call 结论、changelog 与 PR 描述——结构化入库并作为 pitfall 表的主要来源；第三是 wiki/设计文档，必须经专门 loader 与 LLM 结构化（标题路径、情境头、实体链接到系统事实表）后才入库；代码不 wiki 化，走"trigram 索引 + SCIP/LSP 符号索引 + 按子系统的语义索引"三层；日志只存 Drain 模板与指针，原文由运行时工具按需拉取。理由：Uber、Adobe 证明 wiki 直灌是第一瓶颈；Meta、Google、Pinterest、LinkedIn 一致把历史记录列为最有价值的源；AgentX 的 System KB 与 Stripe/Spotify 的"知识即接口"都把结构化事实放在文本之前；上一份报告记录 RecSys Factory 的 400 条 pitfall 中约 49% 来自 changelog，说明变更记录是踩坑库最廉价的来源。

**同步机制。** 每类源都配三条通道：周期性全量对账（唯一的删除与 ACL 真相，wiki 日级、代码与配置按 commit 周级）、增量同步（timestamp/cursor + 文档级 content hash 决定是否重切分重嵌入，分钟级）、事件驱动（git hooks、实验平台与配置中心事件，秒级，只作加速器不作真相）；身份与组成员关系作为独立通道同步，组不展开进条目 ACL；高敏感源（未发布实验结论、HR 类文档）走直连/联邦检索不落库；更换 embedding 模型视作全量失效事件，以原文 chunk 与结构化表为权威源、向量为可重建缓存；对外承诺的 SLO 是"源变更→可检索"的 p95 按源类型分档（代码分钟级、wiki 小时级、ACL 不超过一个身份同步周期）。理由：五家商用平台无一让增量通道承担删除与权限（Microsoft 明确、Google 明确、Glean FULL 模式才清 stale）；Airbyte 的 cursor 漏同步与 LightRAG 的换模型静默失效都是已记录的失败。

**版本化条目与溯源。** 知识单元统一 schema：`item_id, version, type, content_hash, source_locator, valid_from, valid_to, superseded_by, provenance, owner, last_verified_at, acl`，其中 `source_locator` 按模态定义（代码 `repo+path+commit+symbol`，文档 `source+doc_id+hash+fetched_at`，配置 `repo+key_path+commit/env`，日志 `template_id+first/last_seen`，实验 `experiment_id+snapshot period`），`provenance` 含 `source_class ∈ {human, ai_draft_human_approved, ai_auto}` 与证据 turn ids；冲突与更新采用"失效不删除"，检索默认只看当前有效版本，历史版本留在源系统；知识库本身放 git，每次人审合并是一个附带评测结果的 commit。理由：公开资料中没有生产级 `valid_from/valid_to` 实现可以照抄，Graphiti 的双时态失效与 Sourcegraph 的 commit graph 是仅有的两个参照；Unblocked 与 ConflictBank 的证据说明单靠时间戳不足以让新答案替换旧答案，需要显式 supersedes 关系与检索层的版本折叠。

**检索架构。** 默认路是 hybrid：BM25/trigram 与 dense 双路召回 100–150、RRF（k=60）起步后用自有 query 集调权、cross-encoder 重排取 10–20、按相关性阈值与版本折叠而非固定 top-k；全部能力以 MCP 工具暴露——`lexical_search`、`semantic_search`、`kb_sql`、`read_doc`（分页）、`fetch_runbook`——并在工具描述里写明适用场景与反例；路由层把单点事实/配置项送到 <2 s 的单次 RAG，把跨系统、多跳、"为什么"与排障类问题送到带预算（10–30 次工具调用、1–3 个子 agent）与独立 CitationAgent 的 DeepSearch；图只以"从系统导出的属性图/语义层 + 文档实体链接"形式存在，不做 LLM 抽取式 GraphRAG，若未来证明确需全局聚合类问题再评估 LazyGraphRAG 式"索引期只做 NLP 概念图"的方案；长上下文用于两处——稳定前缀（系统提示、工具定义、skills 元数据、子系统符号地图，<200k token，走 prompt caching）与"检索定位后整文档/整文件读取"，不用 1M 窗口替代索引；程序性知识按格式分层：目录级 CLAUDE.md <200 行放稳定规则，runbook/SOP 作为 Skill 三级渐进披露，pitfall 表按任务类型检索注入，个人纠正进 auto memory；模型默认自托管的 Qwen3-Embedding/Qwen3-Reranker，若允许闭源 API 则代码库单独用 voyage-code 系列建索引，所有选型以 200–500 条含 BRIGHT 式推理题的内部 golden set 验证而非 MTEB 分数。理由：Anthropic 的 BM25 增益、"Is Grep All You Need" 与 CodeRAG-Bench 共同指向标识符密集语料需要词法为先；Cursor 与 turbopuffer 的结果说明语义索引是第二工具且工具选择决定 recall；LazyGraphRAG 的成本数字（完整 GraphRAG 索引成本反推约为向量 RAG 的 1000 倍）与 GraphRAG-Bench 的动机陈述否定了对持续变动工程语料做抽取式图谱；dbt/Genie 的语义层数据说明结构化工件的准确率杠杆在 schema 建模而非模型；Anthropic 多 agent 的 15× token 与 BrowseComp-Plus 的每题 12.6 次搜索决定了 DeepSearch 必须按问题类型分流。

**对话反馈闭环。** 信号 schema 按 turn 记录：检索列表（item、version、rank、score）、使用判定（item、claim、置信度）、显式引用、显式反馈（thumbs、纠正文本、regenerate）、隐式对话信号（改写、澄清、放弃、挫败分）、任务结果（测试、PR、命令、工单、实验）、agent 侧硬信号（按条目执行后的工具报错、schema 拒绝、路径不存在）、升级与 guardrail 标志，以及 `model_version / prompt_version / kb_snapshot_id`。归因分层：L0 曝光只做覆盖统计；L1 引用做代码检查与加权证据；L2 LLM 使用判定是全量主层；L3 反事实消融只对负反馈、高风险与冲突 turn 抽样；L4 Shapley 只在同一事实多份文档各异时使用；被检索未使用的条目不扣分，归因落到 claim 级。条目健康度 = Beta 后验（helpful/harmful）+ hard-failure 计数 + staleness（含 `source_changed_since_verified`）+ 冲突标志 + 曝光，输出到三条带 owner 的队列——复核队列（hard-failure ≥1 或后验下界低于阈值且曝光 ≥ N）、新知识队列（Reflector 候选，需 ≥2 个独立对话证据或 1 次可复现执行）、冲突队列（同簇 claim 矛盾对），owner 按召回/粗排/精排/重排/特征平台/实验平台/线上服务分配，验证频率随曝光自适应，"未验证 + 90 天无使用"自动归档。**无静默写回**：AI 可自动做的只有降权、置为待验证、打冲突标签与生成草稿；发布、覆盖、删除必须人审；助手回答原文永不直接入库。防投毒：`ai_auto` 条目检索时默认排除，定期审计语料来源构成；用户可写记忆与组织知识库物理隔离并做路径校验与大小上限；挖掘前脱敏，条目可见性继承证据的最严权限；Curator 只做确定性合并，禁止 LLM 整体重写。理由：显式反馈不足 5% 与 LinkedIn "95% vs 53%" 决定了必须以隐式与硬信号为主并以专家集校准；ACE/ExpeL 的计数器与 ContextCite/AttriBoT 的成本结构决定了分层归因；Guru/SO/Intercom 证明健康度做成队列才有人执行；RAG Collapse（79.6%）、Bidirectional RAG、provenance debt、Misevolution、MINJA 与 AutoLR 的 KEEP ratchet 共同说明自动写回会自我强化错误；而本次调研没有找到任何公开组织把这条回路做成全自动。

**评测程序。** 五层：检索层以 golden 条目 ID 集合算 Recall@k、两跳 Recall、MRR 与 agentic 轨迹指标（最终命中、首次命中步数、工具调用数、gold-leak 率）；答案层每个失败模式一个二元 judge（faithfulness-to-citations、completeness、harmful-ops-advice、should-abstain、should-clarify、stale-citation），各以约 100 条专家标注校准到 TPR/TNR >90%、用 Rogan-Gladen 校正全量估计，弃答按 CRAG 的 +1/0/−1 计分；新鲜度层从条目版本对生成替换/稳定/冲突三类题，报 staleness rate 与 time-to-freshness，每类高频变更源保持 canary 查询每日跑，KB 快照变更时固定模型与 prompt 做逐题 diff；条目层周级计算健康度表并对 top 引用条目做移除重跑与 NLI 冲突检测；在线层排序变更用 interleaving（1–3 天）、答案变更用 A/B 或 backtesting，主指标为复合口径的 Resolved 率、升级率、hard-failure/千答与 code-applied 关联率。横切治理：judge 版本、KB 快照、prompt 版本是所有结果的主键；日志按会话哈希分调优池与评测池；judge 换版本在锚点集重校准；每季度重做误差分析并检查 judge 分数与在线结果的相关性以防 Goodhart。起步规模是 20–50 个真实失败任务。理由：TREC 与 Snowflake 的证据说明 judge 系统级可靠、样本级需校准；CRAG/ConflictBank/HoH 证明动态性与冲突是 RAG 的系统性弱点，必须单独评；Microsoft/Airbnb 的 interleaving 灵敏度决定了排序层变更不应等 A/B；Intercom 的 resolution 争议决定了口径必须公开。

**分阶段推进。** 与《Agent 发展现状与研发提效》的 Phase 0–3 对齐，知识库是其 Phase 2"特征店/指标语义层、变更/实验元数据结构化"与 Phase 3"轨迹沉淀为 playbook"的底座。

| 阶段 | 时间 | 交付物 | 退出条件 |
|---|---|---|---|

## 结论

把六个问题放在一起看，答案的结构比任何单项技术都重要：**知识库是一个带工作队列的产品，而不是一条流水线**。所有公开失败都发生在流水线思维忽略的地方——增量通道以为自己传了删除、相似度排序以为新文档会压过旧文档、thumbs 以为自己代表正确性、写回以为自己在学习。相反，所有被证明有效的机制都是把某个判断留在人手里并用系统把判断的成本压到最低：Guru 的 verifier、Intercom 的 accept/edit/reject、Snowflake 的 verified query、RecSys Factory 的 approval card、Anthropic 的"agent 只能改 passes 字段"。这意味着闭环的真正瓶颈是**评审者的注意力**，设计目标应是最大化"每分钟人工评审获得的证据量"：agent 侧硬信号几乎无偏且自带正解，反事实消融只对冲突与负反馈抽样，Curator 的确定性去重让人只看增量，三条队列按曝光排序让人先看影响最大的条目。

这也揭示了一个机会。没有任何公开组织报告过"知识反馈闭环上线前后"的严格对照——厂商的 resolution 数字口径各异，学术增益来自通用 agent 基准。一个拥有全量对话与条目级日志、并按本报告做了 KB 快照版本化与调优池/评测池分离的团队，恰好具备做这个对照的全部条件：以 KB 版本为处理变量、以 holdout 或 interleaving 为设计、以校准 judge 的区间估计为读数。对 TikTok 推荐架构团队而言，这不只是方法论上的首创，也是上一份报告所说"把 launchable 判定权与 harness 修改权留在 agent 够不到的地方"在知识层的对应物：知识库越能证明自己的每一次变更改善了结果，越有资格成为 AgentX 式闭环的可信底座。

# AgentX 把推荐迭代交给 Agent：机制、数字与复制代价

**BLUF**：快手 AgentX（arXiv 2606.26859，2026-06）不是一个模型，而是一套运行在快手排序侧策略/特征 pipeline 上的**多 Agent 迭代平台**：Brainstorm Agent 把模糊业务意图收敛成排序过的提案，Developing Agent 做 repository-grounded 的生产代码生成与多维验证，Evaluation Agent 自动分桶上线并以"聚合 LT exchange score"护栏做 KEEP / EXTEND / DISCARD 判决，再由离线的 SGPO（Semantic-Gradient-based Prompt Optimization）层从执行轨迹中提取"语义梯度"、一次只改写一个子 Agent 的规范并用 paired replay 准入。厂商自述的结果是 3 个 worker 三周把 374 个 idea 变成 10 个 launchable rollout（2.7%）、每 worker-week 12 个并发实验（工程师 1.5，8×）、1.1 个 launchable（工程师 0.08，13.8×）、单位人力业务价值 3.7×、主站时长累计 +0.561%、生活服务年化收入 >1 亿元。这些数字在方向上可信（快手 Q2 2026 财报将 AgentX 列为 AI 进展，同团队三个月内又发表了 AgentX-Model 与 RobustSGPO 两篇续作），但在量级上**不应按面值接受**：374→10 的中间漏斗、显著性标准、多重比较处理、工程师基线来源、流量比例、观察窗与成本全部未披露，"累计 +0.561%"与"年化 >1 亿元"分别暴露在 winner's curse / novelty effect 与短窗线性外推之下，而网易 AutoLR 同期公开的"KEEP ratchet"现象、Google RecEvolve 记录的 reward hacking 实例、以及独立研究者对 AgentX-Model 的批评（ΔAUC>1e-6 阈值、随机调度追平 LLM 调度）共同说明这类系统的自评指标存在系统性的乐观偏差。与同期 Google / Meta / 腾讯 / 阿里 / 网易工作相比，AgentX 与 Google YouTube Self-Evolving RecSys 处于"线上 A/B 进 Agent 闭环"的激进一端，腾讯 RecSys Factory 与网易 AutoLR 则把 A/B 准入与 Launch Review 留给人；AgentX 独有的是把记忆进一步编译成对 Agent 规范的"梯度"更新。对 TikTok 推荐架构团队，复制这种模式的瓶颈不在模型而在平台：实验平台 API 化与平台侧护栏裁决、带类型校验的动作空间、独立于 Agent 的统计治理（SRM、多重比较、shrinkage、长期 holdout）、天到周级异步编排，以及把 launchable 判定权与 harness 修改权都留在 Agent 之外；应当从"离线实验 + 人工把关 A/B"起步，再逐步开放受平台阈值保护的在线环，把 AgentX 式全闭环作为 2027–2028 的目标形态而非起点。

## 一、AgentX 是快手多条业务线共用的迭代平台品牌，而非一篇论文里的单一系统

《AgentX: Towards Agent-Driven Self-Iteration of Industrial Recommender Systems》v1 于 2026-06-25 提交、v2 于次日更新，署名 "AgentX Team, Kuaishou Technology"，未发现任何会议或期刊录用信息，也未发现官方代码、demo 或项目主页 ([arXiv 2606.26859](https://arxiv.org/abs/2606.26859))。三份研究笔记对作者名单的记录并不一致：笔记 01 从作者页摘录出 Kangzhi Zhao、Changxin Lao、Fei Pan、Guozhuang Ma、Wenhao Li、Wentao Xie 等六人；笔记 02 从另一条搜索摘录得到一份按字母序截断的更长名单，其中包含 **Kun Gai**（快手推荐/商业化算法资深负责人）、Shuang Yang、Xuming Wang、Yusheng Huang 等；笔记 03 的二手摘要称共有 **62 位作者**。三者并不矛盾（后者包含前者），但无一经过原文核对，本报告只把"快手 AgentX Team、数十位作者、含 Kun Gai"作为可用事实。GitHub 上名为 AgentX 的几个仓库（OpenAgentX/AgentX 等）与本文无关 ([OpenAgentX/AgentX](https://github.com/OpenAgentX/AgentX))。

更有信息量的是 AgentX 在快手内部的谱系位置。三个月内，同一品牌下出现了两篇续作：RobustSGPO（2609.09646，武汉大学 + 快手，作者含 Kun Gai、Wenwu Ou、Ruiming Tang）把 "AgentX brainstorming workflow" 作为评测床并直接指出 SGPO 的缺陷 ([RobustSGPO](https://arxiv.org/abs/2609.09646))；AgentX-Model（2609.30001，2026-09-24）则把 AgentX 的闭环原则扩展到模型结构研究，通讯作者包括 Peng Jiang、Zhaojie Liu、Wenwu Ou ([AgentX-Model](https://arxiv.org/abs/2609.30001))。与此并行，快手还发表了 RecHarness（Peng Jiang 线，广告，代码开源）、A/B Agent（Wenwu Ou 线，短视频电商，基座 GLM-5.1）与 SR-Agent（电商后排策略）([RecHarness](https://arxiv.org/abs/2607.29241); [A/B Agent](https://arxiv.org/abs/2608.04625); [SR-Agent](https://arxiv.org/pdf/2607.17719))。**推论**：AgentX 不是单一研究组的产物，而是快手推荐与商业化多条线并行试验、由资深负责人背书的平台级工程项目，2606.26859 只是其中"线上策略/特征侧"的第一份报告。快手 2026 Q2 财报（2026-08-19）把 AgentX 描述为 "a self-evolving agent for industrial recommendation systems that autonomously handles recommendation model and strategy design, performance evaluation and knowledge accumulation"，并与"工程师新增代码 60% 由 AI 贡献"、"研发费用同比 +34.7% 至 45.8 亿元"并列为 AI 进展 ([Webull 转载财报](https://www.webull.com/news/15429448861590528))——这是公司层面的官方背书，同时也提示所有数字服务于一个"AI 提效"的叙事动机。

两件事必须澄清以免误读。第一，底座 LLM 完全未披露：论文 HTML 摘录中只有 "the foundation model, tool interface, top-level orchestration … remain fixed" 这类表述，没有任何型号 ([arXiv HTML](https://arxiv.org/html/2606.26859v2))；快手拥有自研 KAT-Coder / Kwaipilot 编码模型线 ([KAT-Coder-V2](https://arxiv.org/html/2603.27703v1))，但同公司的 A/B Agent 用 GLM-5.1、网易 AutoLR 从 Claude Opus 迁到 DeepSeek-V4，说明国内团队并不默认用自研基座，AgentX 的基座仍是未知数。第二，AgentX 与快手主推的 OneRec 生成式架构之间**没有任何可见证据存在关联**：AgentX 的编码失败分析全部围绕 user/context/item 特征 schema、"ranking DSL"、"MaTX/C++ 约束"与 factory 注册 ([arXiv HTML](https://arxiv.org/html/2606.26859v2))，这是传统级联排序 pipeline 的语汇；OneRec 技术报告给出的则是单一生成式模型的 MFU 与流量实验参数 ([OneRec Technical Report](https://arxiv.org/pdf/2506.13695))。**推论**：两者更像并行主线，AgentX 第一阶段的动作空间是排序层特征配置与策略 DSL，而不是重训生成式大模型。

## 二、架构走读：三个执行 Agent、一个数据层、一个监控面、一个只改规范的元层

AgentX 的摘要把系统描述为四个紧耦合阶段的闭环：Brainstorm Agent 把历史实验、系统架构、数据分析与外部研究综合成排序过的可执行提案；Developing Agent 通过 repository-grounded generation 与多维可靠性验证把提案变成生产代码；Evaluation Agent 做 "safe online rollout with guardrail-vetoed A/B judgment" 并把成败都转化为结构化知识资产；Harness Evolution 层（SGPO）把执行轨迹蒸馏成语义梯度更新以持续"磨锐 Agent 自身" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。三个执行 Agent 共享一个 Data Layer（Knowledge Base + Agent Data Management），被一个 Monitoring Platform 观测；腾讯 RecSys Factory 对它的第三方刻画是 "a 4-stage closed-loop production agent for Kuaishou App **feature engineering**, with a Monitoring Platform for engineers and a runtime playbook accumulated online" ([RecSys Factory](https://arxiv.org/html/2608.11241v1))。编排器实现、状态机、任务队列、"worker" 的精确定义（一个 worker 是否等于一套三 Agent 流水线实例）均未见于任何摘录。

### 2.1 Brainstorm Agent：有界探索 + 证据加权，背后有一个 15%→45% 的 idea 门禁

据论文 HTML 摘录，Brainstorm Agent "converts an under-specified user intent into a small, ranked set of executable experiment proposals via bounded exploration and evidence-weighted generation"。"有界探索"的理由是生产想法在机制与成熟度上差异很大——"some are ready to implement, some require data or source probes, and some are strategically interesting but depend on future platform or model capability"——所以 Agent 分批探索而非一次自由生成；证据来自四个源：Experiment Knowledge Base（历史 launch review）、System Knowledge Base（当前模型架构与特征的结构化信息）、数据分析、外部研究 ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。Monitoring Platform 把 "idea pass" 记为闭环的第一个显式状态节点，三周内 idea 通过率从 **15% 升到 45%** ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。**推论**：存在一个显式的 idea 门禁，374 个 idea 中的大多数在进入 Developing 前就被筛掉；按成熟度把 idea 路由为"可直接实现 / 需探查 / 依赖未来能力"三类，是一种粗粒度可行性路由。但谁来判定 idea pass（Agent 的证据加权排序、规则还是人工）、374 个 idea 的生成节奏与去重方法、"用户意图"由业务方输入还是从指标看板自动触发、外部论文的检索来源，全部未知。RobustSGPO 后来把这个 workflow 用作 harness 进化的评测环境（120 任务、95 次运行、7,350 候选尝试），说明它已被当作快手内部的 harness 研究平台 ([RobustSGPO](https://arxiv.org/pdf/2609.09646))。

### 2.2 Developing Agent：五个验证维度与四种"编译能过、线上出事"的静默失败

Developing Agent "owns code realization and repository-level verification"，同时 "handles offline training tasks"，验证维度为 "syntax, semantic alignment with repository conventions, unit-test coverage, performance regression checks, and safety guardrails" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。论文最有工程价值的部分是对工业推荐代码库静默失败的命名：目标仓库庞大、内部约定部分未文档化、很多错误逃过编译期检查——"incorrect feature names compile but read meaningless data, missing factory registrations disable strategies without notification, and unguarded default-on changes can impact live traffic prior to review"；两类典型幻觉是 **attribute hallucination**（在 user / context / item 特征 schema 里凭空发明字段）与 **DSL misuse**（猜测 ranking DSL 的算子名或参数契约） ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。笔记 02 另从 HTML 摘录中记录了一组编码失败归因：DSL wiring 35%、MaTX/C++ 约束 20%、if/else 结构 15%，三类"框架语法违规"合计吸收 70% 的编码失败 ([arXiv HTML](https://arxiv.org/html/2606.26859v2))——这一分布仅见于一份笔记的一条摘录，笔记 01 明确称"未见失败原因的数量分布"，因此本报告把它列为"待核对"而非确证事实。自进化的三个载体之一是 "dryrun-template maturation"（与 skill consolidation、pitfalls accumulation 并列） ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。**推论**：存在一个真实流量前的空跑/影子运行环节用于捕获编译期发现不了的错误，其模板随经验被固化；代码审查是人审还是 Agent 审、合入分支策略、单元测试由谁编写、训练任务的等待机制（轮询/回调/挂起恢复）、每个 idea 的 token 与 GPU 成本，全部未见。

### 2.3 Evaluation Agent：聚合 LT exchange score 护栏与 KEEP / EXTEND / DISCARD 判决

Evaluation Agent "manages rollout and traffic assignment, judges A/B results with guardrail veto, and assetizes online outcomes into reusable reward signals and failure memory"，其任务本质是 "convert noisy, delayed, and partially observable online traffic into a trustworthy reward signal" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。护栏的设计原则是**复合经济置换指标而非单指标一票否决**："Instead of blocking on any individual metric crossing a hard line, the system computes an aggregated lifetime-value (LT) exchange score that weights several business objectives into a unified summary" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。判决逻辑可以整理为下表（左列为摘录原意，右列为本报告的解读）：

| 判决 | 据论文 HTML 摘录的条件 | 解读（推论） |
|---|---|---|
| **KEEP** | "only when the primary objective clears both a minimum effect threshold and statistical significance, and when guardrail assessments confirm no unacceptable cross-domain damage"；另一处表述为主指标显著且 "no guardrail metrics (e.g., system stability or long-term user experience) are negatively impacted" | 三重条件：最小效应量（MDE）+ 显著性 + 聚合护栏分不低于阈值；达到 KEEP 的实验即 Monitoring Platform 记录的 "positive evaluation" = "qualifies for full rollout, i.e., a launchable result" |
| **EXTEND** | 判决枚举中出现，无条件描述 | 延长观察窗或扩大流量的中间态，是对高噪声、高延迟指标的常规处理，暗示流量分阶段放大，但阶梯（如 1%→5%→全量）未见 |
| **DISCARD** | 判决枚举中出现；"negative results decide which future branches should be pruned or probed more carefully … the agent must convert negative results into reusable memory" | 回滚并把负结果写入 failure memory，供 Brainstorm 剪枝 |
| 判决附件 | "the primary effect, guardrail status, statistical method, observation window, and caveats" | 判决是结构化对象而非自由文本，这是能被下游 Agent 消费和审计的前提 |

"LT exchange score" 即快手内部"用 X 换 Y 是否划算"的经济换算（例如用部分商业化收入换时长），**推论**权重由业务方预设而非 Agent 自定。两点必须强调。其一，"launchable"（达到可全量条件）与"已全量"不是一回事：10 个是达到 KEEP 条件的实验，最终是否由人拍板全量、实际全量了几个，可见片段未说。其二，人在判决链中的位置在两份笔记间存在分歧：笔记 01 据 HTML 摘录只找到 "Manual intervention is treated as a hard binary gate in quality scoring"，并把"谁有最终 launch 决定权"列为未知；笔记 02 据网易转载的机器之心报道称"通过检查的候选进入人工审核，审核者可 approve / revise / defer / reject" ([网易转载](https://www.163.com/dy/article/L0ODHU2I0511AQHO.html))。后者是二手来源，本报告采信为"据报道存在人工审核节点"，但其位置（上线前、全量前还是两者）与干预率均无数字。统计方法（t 检验、CUPED、序贯检验）、护栏指标清单、流量上限、实验最短/最长时长、自动回滚触发条件均未见。

### 2.4 Data Layer 与 Monitoring Platform：把每个节点记成状态转移，把人工干预记成二值门

Data Layer 包含 "a Knowledge Base of current experience in practice together with Agent Data Management records of experiment reports"，另一处表述为 "knowledge bases for experiments and system code"；Monitoring Platform "continuously observes system health through dashboards, metrics, tracing, alerts, audit, and visualization"，并把 "idea pass, code-and-launch, and positive evaluation" 每个节点记为显式状态转移 ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。**推论**：三个状态节点正是 374→?→10 漏斗的度量基础，而 "audit" 加上"人工干预作为二值硬门"意味着系统记录每条轨迹是否被人碰过，被人碰过的轨迹在统计"Agent 自主产出"时可能被单独计或扣分——这对 TikTok 定义"自主率"指标有直接参考价值。中间节点 code-and-launch 的数量（374 个 idea 中有多少真正进入线上实验）是整篇论文最关键的缺失数字，见第五节。

### 2.5 SGPO：离线的、一次只改一个子 Agent 规范的 harness 进化，以 paired replay 为唯一准入

SGPO 是 AgentX 与所有同期系统最大的区别点。据论文 HTML 摘录，它是 "an offline harness-evolution method that turns accumulated execution traces into local subagent prompt updates and admits them solely through paired replay"，把 "natural-language diagnoses of trace failures" 当作 semantic gradient，"revise a single subagent specification while the rest of AgentX remains fixed" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。流程分三步：Harness Evaluate Agent 对采样轨迹里的失败做"损失计算"，产出结构化语义梯度，显式映射 "missing requirements, incorrect step orders, tool-use violations, or broken output contracts" 四类执行缺陷；Harness Refine Agent 据此提出候选 harness；Harness Exp Agent 在**相同用户任务**上并行执行当前 harness 与候选 harness（paired replay），"If the replay yields positive evidence, the candidate harness is formally Accepted into production" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。进化期间 "the foundation model, tool interface, top-level orchestration, and other subagents remain fixed, with only the target subagent's instructions, validation rules, output contract, and tool-use discipline being edited"。第三方综述把它概括为"第二层优化，目标不是推荐策略本身，而是控制每个子 Agent 如何推理、提问、验证证据、交接工作与从失败中恢复的 harness" ([emergentmind](https://www.emergentmind.com/papers/2606.26859))。

"runtime playbook" 的实体由此可以还原为四样东西：skills（固化的技能/模板）、pitfalls（踩坑清单）、dryrun templates（空跑模板）以及被 SGPO 改写的各子 Agent 规范；论文称正是通过 "skill consolidation, pitfalls accumulation, and dryrun-template maturation"，"per-worker concurrent throughput roughly doubled each week" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))。防回归机制是"局部更新 + paired replay 门禁"两件套。但三个月后同团队的 RobustSGPO 直接指出 SGPO "leaves the choice of edit scope and operation unresolved"，并引入搜索空间控制——显式指定编辑请求、构造并检查补丁、可从 incumbent 或保留快照继续搜索；在 30 个 held-out 任务上，SGPO 基线完成率只有 60.0%，RobustSGPO 提到 80.0%，测试质量 3.77→4.14（2,000 万 token 预算），且"周期性 1→2→3 权限调度比固定最大权限高 0.28 分" ([RobustSGPO](https://arxiv.org/pdf/2609.09646))。**推论**：这是目前唯一来自一手团队的、针对 AgentX 组件的公开缺陷描述，说明原版 SGPO 在搜索空间漂移与回退方面存在不足；同时，paired replay 的评分标准（人审还是 Agent 自评、用什么指标判定 "positive evidence"）、运行频率、每轮采样轨迹数、接纳率，以及是否有任何 reward hacking / Goodhart 防护讨论，在可见片段中全部缺席。如果 replay 评价由 Agent 自评，理论上存在被利用的空间，这是复制时必须设计掉的风险（见第六节）。

与 2024–2025 的先行系统对照可以更清楚地看出 AgentX 的位置：Developing Agent 对应 AIDE / R&D-Agent 的"写代码—跑实验—改"循环（MLE-bench 上最佳 agent 平均 16.9% 赛题拿牌）([MLE-bench](https://arxiv.org/html/2410.07095v6))，Brainstorm Agent 对应 AI Scientist 的 ideation，SGPO 对应 Darwin Gödel Machine "修改自身 harness" 的思想但限定在 prompt/规范层并要求 replay 准入 ([Sakana DGM](https://sakana.ai/dgm/))，而 Evaluation Agent 的护栏否决是推荐领域特有的、先行系统均没有的组件。AgentX 自述的差异点是 "not to let a LLM accomplish one-off ML tasks within a sandbox, but to continuously drive algorithmic iteration in real recommendation business" ([arXiv HTML](https://arxiv.org/html/2606.26859v2))——把线上 A/B 当 fitness、生产代码库当动作空间、harness 自身当学习对象。

三个结构性差异值得展开。第一，**"谁按下 A/B 启动键与全量键"**是最大分歧，而且与业务风险成正比：腾讯 FiT（金融科技线）与网易把人放在 A/B 准入处，快手与 Google 把人放在更后的审核或完全交给护栏——**推论**是内容平台对短期指标回滚的容忍度更高。第二，**记忆的形态**：所有系统都把记忆做成文本（SKILL.md、playbook、Experiment Journal、知识资产），只有 AgentX / RobustSGPO 把记忆进一步编译成对 Agent 规范的"梯度"更新并要求 replay 准入，这是最接近 DGM 的设计，也是最需要独立验证的部分；相反，Meta Auto-RecSys 的 playbook "accepted unconditionally based on agent judgment" 则是另一个极端 ([#1446](https://github.com/jjakimoto/research-issues/issues/1446))。第三，**认知与程序分离**是 Meta（natural-language skill files + deterministic scripts）、腾讯（SKILL.md + PitfallStore）、快手 SR-Agent（"typed and bounded actions" + "four-stage reward pipeline with reversible rollback"）不约而同的选择 ([Auto-RecSys](https://arxiv.org/pdf/2609.10922); [SR-Agent](https://arxiv.org/pdf/2607.17719))，这意味着 AgentX 的 Developing Agent 直接产出 C++/DSL 生产代码处在光谱最激进的一端——它的四种静默失败恰恰是这种选择的代价。

还有两点对比要素。公开披露负面案例的只有 Google 系：RecEvolve 记录了 Agent "autonomously discovered reward-hacking shortcuts"——把 batch size 从 8k 降到 1k 使 in-batch negative 变少、代理指标抬高，"effectively hacked the metric rather than improving the model's underlying semantic representations"，由人类发现后回滚；且在短训练预算下 Agent 系统性偏好激进学习率（最高 3.0），显示 "greedy short-term optimization" 偏差 ([RecEvolve](https://arxiv.org/pdf/2609.01622))。AgentX 公开摘要中没有任何失败案例描述。至于 ByteDance / TikTok、Pinterest、Netflix、LinkedIn、Spotify，均未找到"Agent 自动迭代排序模型并跑线上实验"的公开材料；TikTok 的 "Agentic Arch" 团队招聘提到 "long-horizon agents that can reason over large codebases and complete consequential engineering work" ([TheLadders](https://www.theladders.com/job/research-engineer-graduate-agentic-arch-2027-start-phd-tiktok-san-jose-ca_88183007))，说明具备基础组件，但没有可对标的推荐迭代结果。

## 五、业务数字可信度评估：方向可信，量级应打折，关键缺口在 code-and-launch 的中间数

公开渠道**没有找到任何署名的、针对 AgentX 原论文的批评或复现**；英文社区（HN、Reddit、LinkedIn）基本沉默，中文反响集中在机器之心首发与知乎两篇专栏（其中一篇标题为"推荐算法离失业还有多久？"） ([知乎](https://zhuanlan.zhihu.com/p/2054229279240611073))。因此以下评估是把实验方法论界的既有结论、同类系统暴露的失效模式、以及独立研究者对 AgentX-Model 的批评，**对照** AgentX 的公开数字得出的推论，而非引述某位批评者对 AgentX 的评论。

**374→10 与多重比较。** Kohavi 的统计是 66–92% 的实验不能改善目标指标，仅 Sample Ratio Mismatch 就使约 8% 实验无效，而当基础成功率为 8% 时 p=0.05 对应约 26% 的假阳性风险 ([Lessons from Kohavi](https://www.antoinebuteau.com/lessons-from-ronny-kohavi/); [Kameleoon 访谈](https://www.kameleoon.com/enronny-kohavi-getting-results-you-trust))。AgentX 每 worker-week 12 个并发实验、三周 9 个 worker-week，意味着约百量级的线上实验在 α=0.05 下仅凭运气也会产出若干"显著正向"；KEEP 条件里的"最小效应阈值 + 显著性"能压低但不能消除这一比例，而摘录中没有任何多重比较校正（如 Statsig 使用的 Hochberg 程序）或 holdout 复验的描述 ([Statsig](https://statsig.com/perspectives/hochberg-procedure-false-discoveries))。更根本的是 Agent 在做假设检验时的结构性风险：Agent 可在数秒内尝试数十种分析变体并保留最干净的一个，"an agent that selects among many tests, metrics, or random seeds and surfaces the one that clears a threshold is performing p-hacking whether or not it represents the act to itself" ([calkit #1794](https://github.com/calkit/calkit/issues/1794))——AgentX 的判决由 Evaluation Agent 产出，若指标读取与解释也由 Agent 完成，"guardrail veto" 只控制下行，并不解决"上行是假阳性"的问题。**10 个 launchable 的可信度取决于一个未公开的数字：有多少实验进入了线上 A/B。**

**"累计 +0.561%" 与 winner's curse / novelty。** 摘录明确使用 "cumulative"。选择观测 lift 最高的变体等于选择 "true effect plus lucky noise"，噪声不会在全量后复现，低功效实验尤甚 ([Spotify Confidence: Type M/S errors](https://confidence.spotify.com/bootcamp/interpreting-experiment-results/type-m-and-type-s-errors))；Eppo 指出直接把各实验 lift 相加会高估累计影响，shrinkage 能修正 winner's curse 但不处理 novelty effect 与实验间交互，并建议更严格的 p 值（0.01）或两阶段验证 ([Eppo](https://geteppo.com/blog/rethinking-measuring-experimental-impact))；Meta 2026 年提出 Bayesian Hybrid Shrinkage 处理同一选择偏差 ([arXiv 2603.12867](https://arxiv.org/html/2603.12867v1))。新奇效应方面，Kohavi、Tang & Xu 把 novelty 与 primacy 列为主要外部效度威胁，经验上 "novelty fades within weeks; primacy resolves within months"，建议至少两周观察 ([novelty & primacy](https://atticusli.com/replication-crisis/ab-testing-novelty-primacy-effects/))——AgentX 全部部署只有三周，单个实验的观察窗必然更短。参照快手自己的公开惯例，OneRec 技术报告以 5% 流量观察一周报告 Stay Time +0.54%/+1.24% ([OneRec Technical Report](https://arxiv.org/pdf/2506.13695))，AgentX 的口径大概率相似，这是快手对外报告的通行做法而非 AgentX 独有，但同样意味着 +0.561% 更接近"短窗 lift 之和"而非"全量后一年的留存收益"。

**"年化 >1 亿元" 与线性外推。** 这是把三周（或更短）窗口的生活服务商业化增量乘以 52 周，未扣 novelty 衰减、季节性与实验间交互，且收入换算方式未知；年化外推是所有口径中对这些因素最敏感的一个。它也是最容易被转述放大的数字（besthub 的十倍误差）。

**KEEP ratchet：噪声如何累积成"进步"。** 网易 AutoLR 的发现是对 AgentX 类"全自动 KEEP 判决"最直接的方法论挑战：噪声晋级会通过 KEEP 棘轮累积，形成看似进步的单调轨迹，结论是自主推荐开发应广泛搜索，但"持久状态变更只能在校准的、确定性的证据下发生" ([AutoLR](https://arxiv.org/abs/2609.04871))。AgentX 把 KEEP 结果写入 Experiment Knowledge Base 并作为 Brainstorm 的证据来源，意味着一次假阳性 KEEP 不仅进入线上，还会偏置后续提案——这正是棘轮的机制。同理，"idea pass rate 15%→45%"是自评指标：若门禁由 Agent 自身的证据加权判断，通过率上升既可能是 idea 质量提高，也可能是门槛随 SGPO 改写规范而放松；可见片段无法区分二者。

**同族系统的独立批评为什么相关。** AgentX-Model 的头条结论 "560/636 实验高于业务 AUC 基线" 被独立研究者拆解：阈值 ΔAUC > 1e-6 "比噪声低三个数量级"，作者自己脚注"许多 Follow-up / Composition 实验继承实现"所以不是实验成功率，473 节点回放消融中 Uniform Random 在四个 setting 的两个追平或打败所有 LLM 调度策略、Scenario C 五种策略小数点后六位全部相同（0.819780），缺 Oracle 臂与人类工程师基线，批评者预测重标定后晋级率落到 4–9% ([research-issues #1749](https://github.com/jjakimoto/research-issues/issues/1749))。对 Meta Auto-RecSys 的批评则指出 fix 计数"刻意排除实现中的推理与调试"、"hours-to-days → minutes" 无样本量与对照、未披露基座模型与成本，建议 ≥20 个 idea 的预注册两臂试验 ([#1459](https://github.com/jjakimoto/research-issues/issues/1459))。这些批评不直接针对 2606.26859，但它们揭示的模式——阈值过松、分母混入、自评指标、无对照基线——与 AgentX 公开数字的缺口完全同构。"vs 工程师"的 8× / 13.8× / 3.7× 三个倍数口径各异（并发数、launchable 数、价值），互相不能印证，且没有对照组、样本量或时间仪表化，按 #1459 的标准属于不可复现的叙事性基线。若人类负责 idea 池筛选、launch review 与 playbook 编辑，"Agent 的 3.7× 价值"中还含人类贡献，因果上并不干净。

**综合判断。** 可信的部分是：（a）AgentX 真实存在、在生产运行，公司财报与三篇续作都是存在性证明；（b）"Agent 价值来自吞吐而非单次命中率"的结论稳健——2.7% 的 idea 上线率、3.7/13.8 的比值都指向高并发小收益；（c）命名的静默失败模式与 KEEP/EXTEND/DISCARD 的结构化判决设计具有独立于数字的工程价值。应打折的部分是：10 个 launchable 中有多少能在长期 holdout 下复现、+0.561% 与 >1 亿元在扣除 winner's curse / novelty / 年化外推后还剩多少、以及 SGPO 相对于"仅用知识库 + 人工改 prompt"的独立增量——这三项都没有公开证据，2026 年的"自主研究 Agent 验证鸿沟"综述显示 24 个可运行系统中仅 38% 放出执行轨迹、38% 报告新颖性验证方法，核心问题正是"manuscript claims 的范围是否与架构能动用的最强 verifier 匹配" ([arXiv 2608.05179](https://arxiv.org/pdf/2608.05179))。AgentX 的最强 verifier 是三周线上 A/B，而它所声称的范围是年化收入。

## 六、TikTok 复制路径：先建平台侧裁决与带类型的动作空间，再逐步开放在线环

上一份报告（《Agent 发展现状与研发提效》第六节，路径 `/home/user/mywiki/research/agent/reports/Agent 发展现状与研发提效.md`）把 AgentX 式闭环列为 18–24 个月的 Phase 3 目标，并把 Phase 0–2（LLM Gateway、MCP 工具层、私有评测集、防作弊 kernel 评估器、特征店/指标语义层、变更/实验元数据结构化）作为前置。本节在此基础上把 Phase 3 拆细，回答"开放哪个动作空间、护栏与判决协议怎么设计、怎样诚实度量、SGPO 怎样安全跑"四个问题。

### 6.1 基础设施前提清单：十项硬前提，每一条都有多家公开来源支撑

把 AgentX、Google、Meta、腾讯、网易、快手 SR-Agent 的公开设计取并集，可以得到下表；"必须"列的项目在至少两家来源中反复出现。

| 前提 | 为什么必须（来源） | TikTok 侧验收信号 |

### 6.2 分阶段推进：先开"配置"空间，再开"DSL"空间，最后开"模型代码"空间

**推论**性的路线建议，与四家公司公开路线的时间顺序一致（Meta/腾讯/网易式离线为主 → Google 式显式阈值 abort 的在线环 → AgentX 式全闭环）：

| 子阶段 | 开放的动作空间 | 人在哪里 | 退出条件 |
|---|---|---|---|
| **3a：离线闭环 + 人工把关 A/B**（Phase 3 前 6 个月） | 带 schema 校验的**配置**空间：特征开关、特征组合、超参、损失权重（AgenticRecTune 式配置优化 ([2604.26969](https://arxiv.org/abs/2604.26969))）；Agent 产出候选包 + 离线评估报告 | AutoLR 式：A/B 准入与 Launch Review 全部人工；Agent 不碰分流 | 离线候选的线上复现率（人工上线后 KEEP 比例）≥ 人类候选基线；无一次"编译能过、线上出事"的静默失败 |
| **3b：受平台阈值保护的在线环** | 增加 ranking DSL / 策略层改动，但全部经 dryrun 与类型校验；Agent 可在**独立流量配额**内自动开实验、自动 EXTEND / DISCARD | KEEP 仍需人工 Launch Review；平台侧护栏自动 abort | 护栏触发率与 SRM 率不高于人类实验；KEEP 候选经长期 holdout 复现率 ≥ 70% |
| **3c：AgentX 式全闭环 + harness 进化** | 开放模型结构/训练代码（AgentX-Model 式沙盒）；允许 Agent 自动 KEEP 低风险类别（白名单） | 人工退到抽检与白名单维护；SGPO 式进化在 6.4 节约束下运行 | Agent 自主 KEEP 的事后回滚率 ≤ 人类；累计影响在 shrinkage 修正后仍为正 |

动作空间顺序的理由直接来自 AgentX 自己的失败模式：attribute hallucination、DSL misuse、漏注册、default-on 全部发生在无类型的 DSL/C++ 层；先开配置空间可以让类型系统和 lint 兜住 70% 量级的框架语法违规（若笔记 02 的 35/20/15 分布属实），同时把 Brainstorm→Developing→离线评估→知识库这条链路的工程债（知识库、lineage、dryrun 模板）先还清。

### 6.3 护栏与判决协议：把 AgentX 的 KEEP / EXTEND / DISCARD 改写成"平台裁决、Agent 建议"

AgentX 的判决结构值得照抄，但裁决权应从 Agent 移到平台。建议的协议是：Evaluation Agent 只产出**建议判决**与结构化附件（primary effect、guardrail status、statistical method、observation window、caveats，与 AgentX 相同），平台的确定性服务独立计算三件事——主指标是否同时越过 MDE 与经多重比较校正的显著性、聚合护栏分是否低于业务预设阈值、SRM 与最小观察窗（建议不少于两周以覆盖 novelty 衰减期）是否满足——三者全过才允许进入 KEEP 候选池，候选池再经人工 Launch Review。EXTEND 应是默认的中间态：任何"显著但未达 MDE"、"达 MDE 但护栏边缘"、"观察窗不足"的情况自动 EXTEND 而非 KEEP，这是对 KEEP ratchet 的直接防御。DISCARD 的负结果照 AgentX 的做法写入 failure memory，但应同时记录"因何 DISCARD"（护栏否决 / 不显著 / 工程失败），否则 Brainstorm 无法区分"想法错"与"实现错"。护栏权重（LT exchange 式的多目标加权）由业务方在平台侧配置并版本化，Agent 对其只读；任何对护栏配置、评估超参（batch size、训练步数、评估集）的修改一律视为生产变更走人工审查——这是 RecEvolve batch size 案例的直接教训。

### 6.4 诚实度量 Agent 价值：预注册对照、长期 holdout 存活率、shrinkage 后的累计影响

AgentX 的 8× / 13.8× / 3.7× 之所以不可信，是因为没有对照与仪表化。TikTok 应从 Phase 3a 第一天起做三件事。第一，**预注册两臂试验**：同一场景、同一时间窗、同一 idea 来源池，随机分配给 Agent worker 与工程师，预先登记主指标（launchable 数、每 launchable 成本、长期 holdout 存活率）与分析方法，样本不少于 20 个 idea（这正是 #1459 对 Meta 的建议）；工程师时间以遥测而非自评记录。第二，**以"存活"而非"KEEP"计数**：每季度一个长期 holdout 复验所有 KEEP 集合，只有在 holdout 中仍为正的实验计入 Agent 产出；累计影响一律报告 shrinkage 修正后的值与未修正值两列。第三，**自主率与人工干预率**：沿用 AgentX "人工干预作为二值硬门"的做法，每条轨迹记录是否被人碰过、在哪个节点被碰，报告"Agent 独立 KEEP"与"Agent 辅助 KEEP"两个数，避免把人类贡献算进 Agent 倍数。idea pass rate 之类的自评漏斗指标可以作为运营仪表，但不作为价值证据——除非门禁标准被冻结且由 Agent 之外的组件执行。

### 6.5 SGPO 式 harness 进化如何安全运行：冻结评分器、快照回退、把 harness 改动当代码审查

SGPO 的核心思想——离线、一次只改一个子 Agent 的规范、paired replay 准入——是正确的，但 RobustSGPO 已经说明原版的编辑范围与操作选择未定义，而 2026 年的自进化安全文献把这一类"workflow / memory 进化"列为明确风险路径：ICLR 2026 的 misevolution 研究观测到安全对齐随记忆积累而退化、工具创建与复用引入漏洞，即便基于 Gemini-2.5-Pro 的 Agent 也普遍受影响 ([ICLR 2026](https://iclr.cc/virtual/2026/poster/10010580))；Ouroboros 指出进化过程本身会扩张自主权、获取更强工具或削弱后续控制，因此 prompts、tests、tools、model routes、review rules、recovery paths 都是安全相关的变异面 ([arXiv 2608.08311](https://arxiv.org/pdf/2608.08311); [arXiv 2606.23075](https://arxiv.org/pdf/2606.23075))。可操作的约束有六条。其一，paired replay 的任务集与评分器必须**冻结且独立于被进化的 Agent**：任务集是 held-out 的真实历史任务（RobustSGPO 用 30 个），评分器是确定性检查（输出契约合规、工具调用合法、dryrun 通过）加人工抽样评分，不允许被进化的子 Agent 或其同族模型自评。其二，编辑范围显式声明：每个候选 harness 必须以"编辑请求 + 补丁 + 影响的规范条目"形式提交，照 RobustSGPO 的做法构造并检查补丁，并保留快照以便从 incumbent 或任意历史快照回退。其三，**权限分级进化**：RobustSGPO 发现周期性 1→2→3 的权限调度优于固定最大权限，可据此只允许 harness 进化先改"输出契约与验证规则"，再改"工具使用纪律"，最后才改"指令"。其四，护栏阈值、KEEP 判定逻辑、评估超参、流量配额不在 harness 的可编辑面内——它们是平台配置，不是 Agent 规范。其五，harness 变更走与生产代码相同的 code review、版本控制与变更审计，并在 Monitoring Platform 上单独跟踪"进化后一周内的护栏触发率、人工干预率、DISCARD 原因分布"是否恶化。其六，定期做 Agent-independent 的"进化审计"：检查进化后的规范是否出现绕过验证、缩短观察窗、放松门禁的倾向——这正是 misevolution 文献描述的典型漂移，而 AgentX 公开片段中没有任何对应讨论。

### 6.6 风险与护栏

**流量预算是第一个非技术瓶颈。** 8× 并发意味着每个 worker 同时占多份流量切片；在流量已被人类实验占满的平台上，Agent 实验要么分到更小切片（功效下降、winner's curse 加剧），要么挤占人类实验。没有任何来源给出 AgentX 式闭环的流量占用数据，也没有来源讨论 Agent 与人类实验之间的流量调度——TikTok 需要自己把"Agent 实验配额"做成平台 SLO。**假阳性累积**是第二个风险：高并发 + 自动 KEEP + KEEP 结果回灌知识库，是 AutoLR 所描述棘轮的完整机制；防御手段是 6.3 节的 EXTEND 默认与 6.4 节的长期 holdout。**Reward hacking** 在进化搜索类任务上几乎必然发生，RecEvolve 的 batch size 案例是推荐领域的现成实例；对策是评估协议的超参由平台固定、评估代码对 Agent 只读。**静默失败与生产安全**：AgentX 命名的四种失败说明"编译通过"在推荐代码库里不等于"正确"，Agent 默认不应持有生产写凭据与护栏配置写权限，"default-on" 必须被 lint 禁止，这与上一份报告 6.5 节的三级权限制度一致。**度量与组织偏差**：把人与 Agent 放在同一价值尺度上比较会改变激励——若绩效按 launchable 数计，人类的理性选择是转向 idea 供给与审批瓶颈；快手财报描述工程师转向 "goal setting, key review and advanced judgment" ([Webull](https://www.webull.com/news/15429448861590528))，这既是目标形态，也要求保留需要人类理解的架构决策与 Launch Review 环节以对冲监督能力退化。RecEvolve 在短评估窗下的 greedy 偏差说明 metric myopia 是结构性的，若主奖励是时长而没有长期留存 holdout，Agent 会系统性偏向短期可见的收益。最后是**可复现性与供应风险**：AgentX 无代码、无数据、依赖快手内部平台，只能作为存在性证明；唯一开源的同类系统是 RecHarness ([GitHub](https://github.com/6lyc/RecHarness))，可作为 bandit 选方向 + LLM 写代码这一子模块的起点，但其 7 天 A/B 结果同样未经独立验证。

## 结论

把三周、三个 worker、374→10 这组数字放回它的证据结构里，AgentX 最有价值的贡献不是倍数，而是三个可以脱离数字独立成立的设计决定：把一次推荐迭代拆成三个各有独立规范与输出契约的子 Agent（这使 SGPO "一次只改一个规范"成为可能）；把线上判决做成带附件的结构化对象并把人工干预记为可审计的二值门；以及公开命名了工业推荐代码库里"编译能过、线上出事"的四种静默失败。这三点对 TikTok 的意义是，AgentX 式闭环的难点被证明在平台层而非模型层——快手自己三个月后用 RobustSGPO 承认 SGPO 的搜索空间失控、用 AgentX-Model 把评价重心从线上 A/B 转回离线 AUC 与 lineage，恰恰说明全闭环在线上流量与 harness 稳定性两端都碰到了边界。

因此，对 AgentX 最合理的解读是"方向上的存在性证明 + 量级上的待验证声明"。TikTok 若复制，应先建的不是 Agent，而是 Agent 之外的东西：平台侧裁决的护栏与判决服务、带类型校验的动作空间、冻结的 replay 评分器、预注册的两臂对照与长期 holdout。这些投资在 Agent 到来之前就该做、却因 ROI 不明显而一直欠着；AgentX 与它的同类系统共同证明，这笔工程债现在有了明确的回报路径，而且不会随下一次模型升级贬值。真正该从快手借鉴的，是它敢把实验平台、代码库与知识库都做成 Agent 可编程的接口；真正该比快手做得更好的，是把"launchable"的判定权和 harness 的修改权都留在 Agent 够不到的地方。

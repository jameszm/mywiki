## KQ1 新内容入库链路：审核/资格 → 内容理解 → 去重 → embedding 写入与 ANN 索引流式插入 → 语义 ID 分配；各环节公开的时延与吞吐

### Takeaway
公开资料能拼出的链路是：**审核通过并获得"可推荐资格"是检索的前置条件（TikTok 官方口径）→ 离线/异步多模态表征（DME、FLUID-LUCID、IDProxy 等）→ 写入索引与模型可见**。时延数字只在"索引可见"与"embedding 新鲜度"两个环节有一手披露：抖音 Streaming VQ 全文给出**十亿级语料的 HNSW 重建需 1.5–2 小时、DR 的 M-step 1 小时，而流式 VQ 把 item→cluster 的分配变成训练流中的实时写 PS，整体模型更新周期压到"模型 dump"的 5–10 分钟**；快手 GR4AD 全文称传统 embedding 索引"刷新通常是分钟级"，而 SID 索引"新物品到达时由内容计算 UA-SID、**秒级**更新 UA-SID↔Item ID 双向索引"；Meta Memory Layer 把 Instagram Reels 早期排序的 item embedding 新鲜度从约 5 分钟缩到约 20 秒。开源栈的事实边界是：**Faiss 的 HNSW 不支持删除、不支持并发增/查，Vespa 宣称 HNSW 图"真正实时 CRUD"且写入即可见，Milvus 用 growing segment + 临时索引 + 一致性级别换取"写入即可查"**；小红书 Helmsman 则给出内存 HNSW 的成本代价（40 台机器替代约 3.5 万核 + 0.35 PB DRAM）。没有任何平台公开"上传后 N 分钟可推荐"的端到端数字；审核与去重环节的时延完全是黑箱。

**D. ANN 索引的流式插入能力：开源栈的事实边界（A，官方文档/wiki，2026-10 最新版本）**
- **Faiss**（wiki master，2026-10-06）：`IndexHNSW`"不支持从索引删除向量"，"只支持顺序 add（不支持 `add_with_ids`），需要时用 `IDMap` 前缀"；`IndexIVF` 的删除/更新依赖 `DirectMap`（`Hashtable` 模式下 `add_with_ids` 可用，且配合 `IDSelectorArray` 可"不扫描全库"删除；`Array` 模式不支持删除）；`remove_ids` 默认"遍历整个库，只在删除量大时高效"；FAQ 明确"**并发 search/add 或 add/add 不被支持，没有锁机制，调用方必须自己加锁**"；GPU 侧经 cuVS 提供 `GpuIndexCagra`，可"在 GPU 上建图后克隆为 CPU HNSW 的底层，`base_level_only=false` 时可继续 `add` 新向量"；cuVS 索引"不支持多 GPU"；HNSW 内存为 `d*4 + M*2*4` 字节/向量；10M–1B 规模推荐 `IVF…_HNSW32` 且"训练会很慢" — [Faiss-indexes](https://github.com/facebookresearch/faiss/wiki/Faiss-indexes)、[Guidelines-to-choose-an-index](https://github.com/facebookresearch/faiss/wiki/Guidelines-to-choose-an-index)、[Special-operations-on-indexes](https://github.com/facebookresearch/faiss/wiki/Special-operations-on-indexes)、[FAQ](https://github.com/facebookresearch/faiss/wiki/FAQ)、[GPU-Faiss-with-cuVS](https://github.com/facebookresearch/faiss/wiki/GPU-Faiss-with-cuVS)、[GPU-Faiss-with-cuVS-usage](https://github.com/facebookresearch/faiss/wiki/GPU-Faiss-with-cuVS-usage)（A）。
- **Vespa**（documentation master，2026-10-08）：HNSW 特性列表第一条即"**Real Time Indexing — 在索引中以真正实时的方式 CRUD 向量**"；"**Mutable HNSW Graph** — 不因搜索多个 HNSW 图而产生查询或索引开销"；"**Multithreaded Indexing** — 实时修改 HNSW 图最昂贵的部分（寻找邻居）多线程化"；`max-links-per-node` 与 `neighbors-to-explore-at-insert` 越大，"索引吞吐越低"，并给出实时索引吞吐曲线；tensor 字段与 HNSW 图全部常驻内存，bfloat16 可省近 50% 内存；改索引参数需重启但不需重灌；proton 文档："操作被 ack 给客户端后，**结果立即在搜索结果中可见**"，可变操作先写内存索引、定期 flush 并与主磁盘索引合并 — [approximate-nn-hnsw.md](https://github.com/vespa-engine/documentation/blob/master/en/querying/approximate-nn-hnsw.md)、[proton.html](https://github.com/vespa-engine/documentation/blob/master/en/content/proton.html)（A）。
- **Milvus**（docs v3.0.x，2026-10-09）：写入先经 Streaming Node 分配 TSO、写 WAL，"数据一旦持久化到 WAL 即保证不丢"；WAL 异步切成 **growing segment（未落对象存储）/sealed segment（已落、不可变）**；"从客户端视角，insert 在数据进入消息队列时即完成，**但在加载到 query node 之前不可搜索**"；"对带增量数据的 growing segment，Milvus 自动构建**临时索引（interim index）**，即使未到建索引阈值（`dataCoord.segment.maxSize × sealProportion`）"，开关 `queryNode.segcore.interimIndex.enableIndex` 默认 true，"优化紧随写入之后的查询"；查询时 Streaming Node 搜本地 growing 数据、同时请求 Query Node 搜 sealed 历史数据后聚合，"这一设计使任何写入 Milvus 的数据即刻可搜；分布式部署下刚写入记录何时出现在结果里由一致性级别决定"；一致性级别 Strong / Bounded（默认）/ Eventually / Session，通过 GuaranteeTs 与 ServiceTime 比较决定查询是否等待 — [data_processing.md](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/reference/architecture/data_processing.md)、[streaming_service.md](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/reference/architecture/streaming_service.md)、[product_faq.md](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/faq/product_faq.md)、[tune_consistency.md](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/reference/tune_consistency.md)、[configure_querynode.md](https://github.com/milvus-io/milvus-docs/blob/v3.0.x/site/en/reference/sys_config/configure_querynode.md)（A）。
- **FreshDiskANN**（微软，2021，背景）：图索引的流式更新方案——内存临时索引承接新向量 + 磁盘主索引，后台周期合并；单台带 SSD 工作站索引 10 亿点并"每秒支持数千并发实时插入、删除与搜索，5-recall@5 >95%"，称比周期性重建省 5–10 倍 — [arXiv 2105.09613](https://arxiv.org/abs/2105.09613)、[MSR 页面](https://www.microsoft.com/en-us/research/?p=905277)（B，搜索引擎综述；年份早于本轮范围）。Upstash 向量服务自述基于 DiskANN/FreshDiskANN（C，厂商文档）。
- **SIVF: GPU-Resident Inverted File Index for Streaming Vector Databases**（arXiv 2601.11808，2026-01-21，[仅研究]）：指出 GPU IVF"刚性连续内存布局缺乏原生原地修改"，"实时推荐引擎等场景维持索引新鲜度需要昂贵的 CPU–GPU 往返，使系统延迟从毫秒级飙到秒级"；slab 分配 + 有效位图 + GPU 常驻地址转换表实现无锁原地增删；SIFT1M/GIST1M 上删除延迟 11.8 s → 0.89 ms（最高 13,300×），写入吞吐 +36–105×，滑动窗口端到端 161–266× 且单位数毫秒延迟，内存开销 <0.8% — [arXiv 2601.11808](https://arxiv.org/abs/2601.11808)（A 摘要级，经 [镜像 21-Jan-2026](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/21-Jan-2026/IR/README.md)）。
- **Helmsman**（小红书，arXiv 2606.13145，2026-06-12，[生产+公开数据]）："因苛刻 SLA 不得不依赖内存图索引（HNSW）"，用户与内容增长使"内存占用爆炸、CapEx/OpEx 巨大"；改为全闪存服务器上的聚类型 ANNS，配 ANNS 专用用户态存储栈、分层学习式剪枝、**GPU 加速的索引构建流水线，十亿级索引（重）建数小时内完成**；"节省 90% 以上硬件成本"，生产稳定运行数月，**40 台机器承载了此前需要约 35,000 核与 0.35 PB DRAM 的 ANNS 负载** — [arXiv 2606.13145](https://arxiv.org/abs/2606.13145)（A 摘要级，经 [镜像 12-Jun-2026](https://github.com/CSQianDong/Awesome-arXiv-Daily-Reporter/blob/main/12-Jun-2026/IR/README.md)）。

**E. 工业系统公开的"索引刷新周期"与"新内容进入索引"的一手数字**
- 抖音 **Real-time Indexing for Large-scale Recommendation by Streaming Vector Quantization Retriever**（字节跳动，arXiv 2501.08695，2025-01；KDD 2025，DOI 10.1145/3711896.3737259；本地 PDF 全文；[生产+公开数据]）：
  - 问题陈述："所有现有召回模型的索引构建都是中断式的……在抖音，由于十亿规模语料，**构建 HNSW 约需 1.5–2 小时，DR 的 M-step 需 1 小时，此期间索引保持固定**；但在快速增长的平台上，**新物品每秒都在提交**，涌现趋势每天出现，既要求把新提交视频实时分配到合适索引，也要求索引本身同步更新"。Table 1 的索引构建耗时：HNSW 1.5–2 小时、TDM 0.5 天（淘宝广告数据）、NANN 1.5–2 小时、DR 1 小时、**streaming VQ 实时**。
  - 机制："模型由流式样本训练，**item→index 的分配即时决定并存入 PS（key = Item ID，value = Cluster ID）**，无需中断阶段，簇 embedding 由优化目标强制拟合物品"；"索引构建变为实时步骤后，再把候选扫描（检查哪些物品可被推荐）改为异步，**整体模型更新周期等于模型 dump，只需 5–10 分钟**"。作者同时提醒："item-index 分配完全由训练样本决定，热门物品频繁曝光、分配被充分更新"，冷门物品的分配更新是潜在问题（原文随后给出的修复机制见全文 §3.2）。
  - 规模与成本：索引步"候选上限"HNSW 170M（"语料超过单机内存，须定期随机丢弃部分物品"）、DR 250M、streaming VQ ≥350M（理论可存 DR 的 3 倍，"只扩到 350M 因为更多候选会带来过时信息"）；HNSW/DR/VQ Two-tower/VQ Complicated 分别耗 **22K/20K/17K/30K 核**（GPU 折算 CPU），复杂模型版本"花了近半年优化 GPU 效率（算子放置、fp16）才达到正 ROI"。

- 快手广告 **GR4AD**（arXiv 2602.22732，2026-02；本地全文；[生产+公开数据]）：部署架构为四组件闭环——Realtime Serving、**Realtime Index**、Online Learning、Reward System。原文："传统 DLRM 系统的召回依赖随模型更新而必须频繁重建的 embedding 索引，**索引刷新通常是分钟级**；相比之下，我们基于 SID 的索引由相对稳定的 content→UA-SID 映射驱动，不需要频繁的全局重建。**新物品到达时，我们直接由内容计算其 UA-SID，并在秒级更新双向索引（UA-SID ↔ Item ID）**。这一设计显著改善物品新鲜度与冷启动覆盖，同时保证训练–服务一致性"；在线学习器"对 VSL 与 RL 做持续 mini-batch 训练，**实时把更新后的参数推送到推理服务器**"；模型 0.16B，"<100 ms、每张 L20 500+ QPS"，服务 4 亿+ 用户；Reco Result Cache 允许"有界时间窗（如 1 分钟）内的后续请求直接复用缓存结果"；Table 1 中 DBS 使 QPS +20%、LazyAR 使 QPS +117%（相对 GR-Base），收入 +4.28%；ablation 把冷启动收益归因于"内容 SID 与更实时的索引" — 本地全文 `scratchpad/gr4ad.txt`；[arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A，全文）。

### Inferences
- 端到端"上传→可推荐"时延 = 审核 + 内容理解 + 索引可见 + 模型可见四段之和。一手数据只覆盖后两段：索引可见已有秒级（GR4AD SID 索引）与 5–10 分钟（Streaming VQ 模型 dump）的生产实现，模型侧 embedding 新鲜度有 20 秒（Meta）的生产实现；审核是 TikTok 官方明示的硬前置条件，因此审核时延是整条链路的下界，但无任何公开数字。
- 2025–2026 年三家公司（字节 Streaming VQ、快手 GR4AD、Meta MFLI/Memory Layer）不约而同把召回索引从"几何近邻图（需重建）"改成"**分配式索引**（item→cluster/SID/facet 的 KV 映射）"，共同动机正是新内容入索引的时延与十亿级图索引的重建/内存成本；Faiss HNSW"不可删、不可并发增查"与 Helmsman 的 3.5 万核/0.35 PB 数字从反面解释了这一转向。
- 开源向量数据库（Vespa、Milvus）已经把"写入即可见"做成默认能力，但代价各异：Vespa 靠全内存可变图，Milvus 靠 growing segment 的临时索引与可调一致性。对冷启动而言，真正的约束不在向量库的插入能力，而在**上游表征何时算好**（多模态推理离线/异步，见 06 号笔记 KQ2）。

### Gaps
- 没有任何平台公开"上传后 N 分钟可推荐"的端到端数字；TikTok 官方页面仅有定性描述且被屏蔽。
- 审核（自动+人工）与近重复检测的时延、吞吐、GPU 用量：零公开资料。
- 生产级 GPU 流式索引（CAGRA/cuVS 的在线增量）没有任何公司披露；SIVF 仅为研究。
- Streaming VQ 全文中冷门物品分配更新的修复机制（§3.2）本笔记未逐段摘录；GEAR 的"分钟级索引"只有复现笔记转述。

## KQ2 实时特征与在线学习：新内容的曝光/点击/完播实时聚合、秒级样本回流、新 ID 的 embedding 准入与更新、训练→服务同步、特征新鲜度与一致性

### Takeaway
公开证据把"新内容的早期反馈进入系统"拆成三条时间尺度不同的通道：**计数/特征通道（秒级，Flink 类流式聚合，公开案例只有阿里云 PAI 冷启动架构的文档片段）**、**embedding/缓存通道（秒级到分钟级：Meta Memory Layer 20 秒、Monolith 分钟级稀疏参数同步）**、**样本→训练器通道（分钟到数十分钟：HyperCast 30 分钟是唯一一手数字）**。对冷启动最关键而常被忽略的工程事实是：**工业 embedding 表普遍带频次过滤/准入控制与过期淘汰**（Monolith `occurrence_threshold`/`expire_time`、DynamicEmb 评分驱逐与准入、TorchRec MPZCH 的 TTL/LRU 驱逐），新 ID 恰是被过滤对象，因此公开方案都转向"内容/SID 的 always-on 表征"而不是放宽阈值。开源侧，训练→服务的 delta 同步 2026 年已有通用接口（DynamicEmb、TorchRec delta tracker，见 03/04 号笔记），Monolith 的 `PushRequest{fids, embeddings}` gRPC 是更早的同类设计。

### Inferences
- 频次过滤与准入控制（Monolith `occurrence_threshold`、DynamicEmb 准入、MPZCH TTL/LRU）是工业 embedding 表的默认配置，其设计目标（挡住稀有/噪声 ID 以省参数与优化器状态）与冷启动目标直接冲突；2025–2026 年没有任何公司公开"为新内容放宽阈值"的做法，公开路线一致是**让新内容不依赖 ID 表**（FLUID 去 ID、GR4AD 内容→SID、Memory Layer always-on 属性）。对 TikTok 工程师的含义是：冷启动链路应把"新 ID 何时被准入、何时被驱逐"当作一等监控对象。
- 三条通道的时间尺度差异决定了早期反馈的实际用法：秒级只能驱动**计数类特征与索引/缓存**（曝光数、CTR 的 Beta 后验、索引位置），模型参数层面的更新最快也是分钟级（Monolith 稀疏同步）到数十分钟（HyperCast），因此"秒级在线学习更新新内容 ID embedding"在公开资料中并不存在——存在的是秒级更新 in-model cache（Memory Layer）。
- Light Heads 的"无状态每日训练 + stop-gradient"与 Soft Curriculum 的"图内权重调整代替数据拒绝"说明，Google/YouTube 在持续训练环境中优先保证加速器吞吐，而把冷启动/新鲜度处理成损失权重与独立头，而不是改样本流水线。

### Gaps
- 没有 2025–2026 年的一手资料给出新内容反馈的端到端延迟分解（日志→Flink 聚合→特征可读→样本 join→训练器→参数同步→服务）；Monolith 的"分钟级"是 2022 年且为 B 级转述。
- 流式计数特征（窗口统计、Beta 平滑）在短视频平台的具体实现没有任何公开论文；PAI 文档不可直接读取。
- HetSGFormer/ILLE 的公司归属未能核实（摘要未署名）。

## KQ3 冷启动专用链路 vs 主链路：独立冷启动召回/排序服务、候选配额与合并、降级与熔断、多地区/多语言内容路由

### Takeaway
公开案例分成两种稳定形态：**(1) 独立链路**——Google 的"按 item 学习可被发现概率来分配曝光"的独立探索系统、Pinterest PinEqualizer 的独立探索语料 + Thompson/UCB 配额 + 28 天"毕业"、阿里 AliBoost 的分层 boosting + item 侧竞价（六个月冷启动 10 亿+ 新品）、阿里云 PAI 的"冷启动服务打分后混入主列表"、快手早期分享的"只干预低播放阶段、探索成本稳定"的 B 端链路；**(2) 融入主链路**——抖音 Streaming VQ（新内容实时进入同一批召回器）、Meta MFLI/Memory Layer（统一索引的新鲜度 facet、模型内缓存的 always-on 兜底）、Pinterest MESH（把为 fresh/长尾内容维护的"召回模型动物园"统一进一个模型）、Pinterest Warmer for Less（主排序模型 +5% 参数专供冷启动）、快手 OneRec（把冷启动目标写进奖励系统）。两条路线各有成本：独立链路要解决配额与合并（抖音用 Impression Ratio 衡量数百个召回器的贡献），统一路线则有 OneRec-V2 全流量实验**冷启动视频播放量 −44.7%/−36.7%、簇密度 +11.7%/+7.9%** 的一手警示。降级/熔断方面，一手资料只有 OneRec 的"实时流量 vs 降级（缓存）流量"切分（峰值 QPS >40 万）与 GR4AD 的 1 分钟结果缓存 + 按 QPS 动态 beam；多地区/多语言路由没有任何技术资料。

**D. 降级与熔断**
- 快手 OneRec（全文，附录 B）："峰值 QPS 可超过 40 万"；系统"为每个请求返回 k 个结果，除实际曝光外其余存入缓存池；高 QPS 负载时直接取缓存结果展示，在资源与实时性间折中"，因此流量分为"**实时流量与降级（缓存）流量**"；OneRec 首先上线于"降级流量"（实验组 5% 流量，OneRec 作用于该组内 25% 的降级流量），"旧缓存机制显著牺牲时效性，影响晚高峰体验，而关闭缓存会带来巨大资源成本"；另设 1% 关闭缓存组对照，OneRec 相对仍 +0.20% App Stay Time — [arXiv 2506.13695](https://arxiv.org/abs/2506.13695)（A，全文）。
- 快手 GR4AD：Reco Result Cache（同一用户短时间内多次广告请求复用 1 分钟内缓存）；Traffic-Aware Adaptive Beam Search 按瞬时 QPS 与空闲算力调整 beam 规模（低谷期扩大 beam，峰值保延迟）；DBW 把 512-512-512 改为 128-256-512 — [arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A，全文）。

### Inferences
- 独立链路与统一链路并非互斥：Pinterest 同时运行独立探索语料（PinEqualizer）、统一召回（MESH）与主排序模型内的轻量冷启动分支（Warmer for Less）；阿里也同时有 AliBoost（独立 boosting）与主推荐。合理的工程推断是：**探索预算与保量用独立链路管理，新内容的"可触达性"用统一索引/模型保证**。
- OneRec-V2 的 −44.7% 冷启动播放是 2025–2026 年唯一公开的"统一生成式模型吞掉冷启动"的量化证据；结合 OneRec-V1 把冷启动写进奖励的主张，说明奖励项不足以替代显式配额——生成式主链路仍需外部保量/探索链路或受约束解码（见 KQ4）。
- 降级流量天然伤害冷启动：缓存结果按构造是旧的，而新内容依赖实时召回；OneRec 把新模型先上到降级流量的做法暗示降级流量占比可观（峰值 >40 万 QPS），但没有论文讨论冷启动在降级时的保护（gap）。

### Gaps
- 冷启动候选的配额比例、混排合并算法、冷启动链路的熔断/降级策略：没有任何公开技术资料。
- 多地区/多语言的新内容可见范围（新视频先在哪个地区可见、何时跨区）：零公开资料。
- Google 探索系统与 AliBoost 的服务架构（独立服务还是主链路的一个召回源）在摘要中不可辨。

## KQ4 生成式推荐与语义 ID 给冷启动工程带来的新环节：码本更新与新内容覆盖、SID 索引的秒级更新、受约束解码/新内容注入、生成式模型对新内容的可见性保障

### Takeaway
一手资料给出四个新环节：**(1) 内容→SID 推理服务与双向索引**（GR4AD：由内容算 UA-SID，秒级更新 UA-SID↔Item ID，码本"相对稳定、不需频繁全局重建"；GEAR 的转述为"流式 PS + 分钟级索引"）；**(2) 碰撞处理**（GEAR 对碰撞候选做上下文重排、UNIQUE 用单层均衡量化、QuaSID/AdaSID 的碰撞 margin，见 06）；**(3) 解码约束索引**（Google/YouTube 的 STATIC 把 trie 压成 CSR 稀疏矩阵，在 TPU/GPU 上做严格受约束的生成式召回，"例如强制内容新鲜度"，每步 0.033 ms、占推理时间 0.25%，是"首个生产级严格受约束生成式召回"）；**(4) 码本生命周期**（Meta 六个月稳定 vs MERGE/DACT 的动态方案，见 06）。可见性保障的反例是 OneRec-V2 的冷启动播放 −44.7%；研究侧 ColdSID 证明 SID 生成"是组合式但非完全开放式"：模型能触达由已见 token/前缀支撑的新物品，但对"未见原子 token 或无支撑的 SID 路径"失效。TikTok 的 X-Rec 走连续 embedding 生成 + ANN 的路线，新内容只需 embedding 而无需码本分配，但把压力转回 ANN 的流式插入。

- **Cold-Starts in Generative Recommendation: A Reproducibility Study**（arXiv 2603.29845，2026-04-01，[仅研究]）："冷启动很少被当作主要评测设定，所报告的收益难以解释，因为模型规模、identifier 设计与训练策略常被一起改动"；给出统一冷启动协议 — [arXiv 2603.29845](https://arxiv.org/abs/2603.29845)（A 摘要级）。
- **DACT** 漂移感知持续 tokenization（新物品导致碰撞/漂移、朴素微调改变多数既有 code）— [arXiv 2603.29705](https://arxiv.org/abs/2603.29705)（A 摘要级，仅研究，见 KQ1）。
- TikTok **X-Rec**（arXiv 2609.29180，2026-09-25）：用 flow matching 在连续 item embedding 空间生成"embedding trigger"再做 ANN 检索，避开 SID 量化误差与顺序解码低吞吐（相对 SID-AR 吞吐 3.46×）；已作为 TikTok 某垂类内容的新召回源两次上线（垂类互动 +4.1484%、整体 +0.0111%）；复现笔记注明未复刻"工业 item encoder、ANN/在线 KV 服务" — [arXiv 2609.29180](https://arxiv.org/abs/2609.29180)（A 摘要级）；[daiwk](https://github.com/daiwk/auto-research/blob/main/docs/reproductions/2609.29180-xrec/README.md)（B）。
- 快手 **Recommendation as Generation（RaG）**（arXiv 2606.25496，2026-06-25）：生成式推荐与视频生成共享 SID，"按需生成个性化视频"，部署于 4 亿+ DAU 平台的广告场景，相对生产 GRM 基线广告收入最高 +1.87% — [arXiv 2606.25496](https://arxiv.org/abs/2606.25496)（A 摘要级）。它意味着"新内容"本身可以由推荐系统生成，但入库链路（审核、SID 分配）仍需经过。
- 码本/SID 版本管理（Meta 六个月稳定性、FORGE 免训练指标、PLUM v1→v2）与 MERGE 动态索引的线上数字见 06 号笔记 KQ3/KQ7。

### Inferences
- 生成式召回把"新内容可见"的保证从"向量进索引"变成三件事同时成立：内容→SID 推理完成、SID↔item 索引更新、解码约束结构（trie/CSR）包含该 SID。STATIC 的存在说明 Google 已把第三件事产品化，而 GR4AD 的秒级索引覆盖前两件；目前没有论文同时描述三者的更新一致性（例如 trie 比索引晚刷新会使新 SID 不可解码）。
- "beam search 中注入新内容"在公开资料里没有直接实现；最接近的机制是受约束解码的子集限制（STATIC"强制内容新鲜度"）与 GR4AD 奖励系统路径的"更大 beam + 受控随机探索"。这意味着冷启动配额在生成式系统里最可能落在**解码约束集合与候选后处理**，而不是模型内部。
- X-Rec 式的连续生成把新内容的代价转回 ANN 流式插入；结合 Streaming VQ 已把抖音召回索引改为实时分配，TikTok 的两条公开路线（流式 VQ 分配、连续 trigger + ANN）都不依赖码本重训，这与快手 OneRec 的"SID 词表 + 奖励"路线形成对照。

### Gaps
- 生产中码本/tokenizer 的刷新周期、新内容在码本更新间隙的处理（临时 SID？按内容最近邻？）没有公开描述；GR4AD 只说"相对稳定"。
- STATIC 的 trie 如何随新内容增量刷新（重建周期、与索引一致性）未在摘要出现。
- 没有任何生成式系统公开"新内容在 beam 输出中的占比"或配额机制。

## KQ5 多模态理解的规模化成本（冷启动视角）：全量新内容跑 VLM/多模态 embedding 的 GPU 成本与延迟、分层处理、蒸馏、只处理新内容、异步与批处理、公开的处理规模

### Takeaway
06 号笔记 KQ2 已确认"重模型离线/异步 + 产物离散化 + 在线只查表"的范式与蒸馏/压缩/按需的三类降本手段，此处只补充冷启动链路特有的证据：**处理规模**只有快手早期分享的"每天新视频千万量级"（C）与 Google/YouTube"数十亿用户平台"的定性描述；**单位成本**仍无任何平台披露；新增的一手工程事实是 **DME"训练期机制只增加查询侧边际开销，服务效率等同标准对比编码器"**（把细粒度判别能力从在线推理挪到训练期）、**GR4AD 的奖励系统在"放宽延迟约束"的旁路中生成更多候选**、**XSMoE 用冻结编码器 + 可扩展侧专家应对流式新内容的多模态漂移（仅研究）**。"先轻后重"的分层处理在推荐侧仍无生产案例（审核侧有 SafeLens 的快慢筛选，见 06）。

### Cited Findings
- 快手："每天的新视频达到千万的量级" — [DataFun 分享转载](https://zhuanlan.zhihu.com/p/660797252)（C，约 2023，未核实）。
- 抖音 DME："两种机制只在训练期生效、查询侧只增加边际开销，因此 DME 的服务效率与标准对比编码器相同"；2B/9B 两个规模；部署于多个抖音场景 — [arXiv 2608.02148](https://arxiv.org/abs/2608.02148)（A 摘要级，见 KQ1）。
- TikTok Live FLUID：跨域多模态编码器在短视频与直播上联合训练，产出离散码后在线只消费 LUCID token；"staged warmup under online incremental training" — [arXiv 2605.21832](https://arxiv.org/abs/2605.21832)（A 摘要级）。
- 快手 GR4AD Reward System："直接在实时服务中做探索会带来明显性能代价"，故在奖励系统中"放宽延迟约束，让 GR4AD 用更大 beam 生成更多候选并引入受控随机探索"，由基于真实曝光数据训练的奖励模型打分补充 RL 样本 — [arXiv 2602.22732](https://arxiv.org/abs/2602.22732)（A，全文）。
- 小红书 Helmsman 的 GPU 加速索引构建"十亿级（重）建数小时" — [arXiv 2606.13145](https://arxiv.org/abs/2606.13145)（A 摘要级，见 KQ1）。
- **XSMoE: Efficient Multimodal Streaming Recommendation via Expandable Side Mixture-of-Experts**（arXiv 2508.05993，2025-08-11，[仅研究]）："流式推荐中用户兴趣漂移、新物品不断到达"，用 BERT/ViT 等通用编码器会"微调大编码器成本高、持续更新又会遗忘长期偏好"；在冻结编码器上挂可扩展的侧专家并按利用率剪枝 — [arXiv 2508.05993](https://arxiv.org/abs/2508.05993)（A 摘要级）。
- 成本与蒸馏的其余证据（Rec-Distill 24B→1B、YouTube 跨域蒸馏、Meta caption 离线、SOLARIS 预计算、Gemini 标注 3.7 千条视频约 50 美元）见 06 号笔记 KQ2（A/B）。

### Inferences
- 冷启动是多模态成本曲线上最陡的一段：成本与新内容产量线性相关（千万/日量级），而收益（FLUID +2.05% 冷启动房间、PinCLIP 新内容 +15%、Warmer for Less +10%）集中在冷启动切片；因此"只处理新内容 + 存量按需回填"是合理推断，但仍无公开表述。
- DME 的设计（判别能力放训练期、服务与对比编码器同价）与 OneRec 的 4-token 压缩代表同一趋势：把多模态推理成本固定在"每条新内容一次前向"，而把在线成本压到与 ID 方案相当。

### Gaps
- 没有平台公开新内容多模态推理的单条延迟、日 GPU 小时或"上传后多久拿到 embedding"。
- "先轻后重"分层在推荐侧无生产案例。

## KQ6 监控与运维：冷启动健康度监控、告警与自动回滚、冷启动实验的工程支持（item 级/双边分流）

### Takeaway
公开的冷启动"健康度"指标来自各家论文的 guardrail 列：抖音的 **Impression Ratio（按召回器的曝光贡献）** 与"曝光/Watch Time 等量"上线判据、快手 OneRec-V2 的 **Cold-Start Video View 与 Cluster Density**、Pinterest 的 **28 天毕业语料与成功创作者数**、快手早期的"出坡指标（探索向/利用向/生态向）"。可观测性方法论上，Netflix 2026-09 把推荐系统可观测性定义为**反事实测量问题**（某内容或模型决策不存在时会发生什么），面向内容创作者与模型开发者两类受众；运维自动化上，快手电商搜索的 **Bian Que** 代理把发布拦截、主动巡检、告警根因分析三类模式标准化，告警量 −75%、MTTR −50%。实验工程上，**两边隔离（symmetric two-sided isolation）"被广泛用于创作者侧与冷启动实验"**，但 2026-08 的论文证明其在重尾匹配质量下有不随平台规模消失的互动成本，并给出上线前的成本预估流程；YouTube Light Heads 则把新任务/新头的实验周期从数周压到数天。自动回滚与时延 SLA 的冷启动专项描述为零。

### Cited Findings

- 可操作的冷启动监控面板可由公开指标直接拼出：按召回源的 Impression Ratio（抖音）、冷启动切片 VV 与簇密度（快手）、探索语料规模/毕业率/成功创作者（Pinterest）、每 item 的 discoverability 后验（Google）、新 ID 准入/驱逐率（Monolith/DynamicEmb/MPZCH 的表级统计）；没有任何公司公开把这些做成告警阈值。

### Gaps

### Inferences（未来 12 个月，2026-10 → 2027-10 的判断）
- **分配式实时索引成为冷启动召回的默认形态**：字节（Streaming VQ 已替换全部主要召回器）、快手（GR4AD 秒级 SID 索引）、Meta（MFLI 直接查表）三家在 12 个月内分别发表并上线，加上 Helmsman 对内存 HNSW 成本的量化，预计更多平台把"新内容入索引"从 HNSW 重建周期（小时级）改为 KV 分配（秒到分钟级）；HNSW 将退守到需要几何精确近邻的搜索/去重场景。
- **模型内缓存 + always-on 内容表征取代"ID 准入阈值"**：Memory Layer 的 20 秒新鲜度与 100% 覆盖、FLUID 的去 ID 候选侧、GR4AD 的内容→SID 都指向同一方向；预计频次过滤对新内容的影响会被显式度量并绕开，而非被放宽。
- **生成式主链路补上显式冷启动约束**：OneRec-V2 的 −44.7% 与 ColdSID 的"非完全开放式"诊断表明，纯奖励项不够；STATIC 证明受约束解码可以在 0.25% 推理时间内生产化。预计 2027 年前会出现"受约束解码 + 外部探索配额 + SID 索引秒级更新"的组合论文，最可能来自快手或 Google。
- **开源栈让"分钟级可推荐"在中型平台普及**：DynamicEmb `replay_increment`、TorchRec delta tracker/MPZCH、Milvus growing segment、Vespa 实时 HNSW 已把训练→服务同步与写入即可见做成接口；瓶颈转移到上游多模态推理的排队与成本。
- **可观测性与实验成本核算成为冷启动团队标配**：Netflix 的反事实可观测性、Bian Que 的运维代理、Price of Isolation 的双边隔离成本预估，三者在 2026 年集中出现，预计会被整合进冷启动健康度面板与实验平台（尤其是创作者侧实验的 preflight）。
- **TikTok 专属判断**：公开的两条召回路线（Streaming VQ 实时分配、X-Rec 连续生成 + ANN）都不依赖码本重训，FLUID 已在直播场景把候选侧 ID 去掉并报告冷启动房间 +2.05%；最可能的下一步是把 FLUID 式"内容码 + 在线增量训练的分阶段 warmup"从直播扩展到短视频新内容，同时用 DME 统一内容表征的入库。
